## 1. 题目

不使用语言内置 dict/map，实现 put/get/remove，并讨论扩容与冲突处理。

### 仓库深化：手推示例

> 示例操作：`put(1,10)`、`put(9,90)`（若容量使其碰撞）、`get(1)`、`remove(1)`。手推同 bucket 多键时的查找和删除，确认碰撞不会误删。

手推时不要只算最终输出，建议同步写出核心结构在每一步的状态变化，这比“看懂答案”更接近真实面试。

## 2. 面试开始先澄清

- 输入规模与合法性：是否允许空输入、重复值、负数，是否保证答案存在？

- 是否允许修改输入？输出是否要求稳定顺序或去重？

- 复杂度目标：题目是否明确要求 O(n)、O(log n) 或 O(1) 额外空间？

## 3. 基线方案与瓶颈

最简单可以使用固定桶数组 + 链表 separate chaining，但固定容量会随着 n 增长导致冲突严重。

### 解法演进对比

| 层级 | 思路 | 代价 / 价值 |
|---|---|---|
| Baseline | 最简单可以使用固定桶数组 + 链表 separate chaining，但固定容量会随着 n 增长导致冲突严重。 | 先保证正确，暴露真正瓶颈 |
| 面试目标 | 围绕 `HashMap / 底层实现` 维护最小必要状态 | 平均 put/get/remove O(1)，最坏 O(n)；resize 一次 O(n) 但摊销后 insert 仍 O(1)。 |

这张表的重点不是“最优解一定唯一”，而是能够解释**为什么新结构减少了哪一类重复工作**。

### 深化解析：先定位重复工作

本题所在章节的核心原则是 **用空间换查询时间**。明确平均 O(1) 与最坏 O(n) 的区别，说明 key 设计、冲突、负载因子以及是否需要保存下标/频次/最后位置。

面试中不要直接报最优结构。先说明基线方案具体重复做了什么，再指出目标结构如何把这部分重复工作缓存、单调淘汰、分层搜索或局部化维护。这样能证明你是在从约束推导算法，而不是背模板。

## 4. 关键洞察：为什么这个数据结构合适

将 key 通过 hash 映射到 bucket；桶内线性查找同 key。负载因子超过阈值时把 capacity 扩大并 rehash 所有键。面试重点是理解“平均 O(1)”来自桶分布与受控负载。

### 结构选择检查表

- **我们反复查询/维护的信息是什么？** 把它写成一句话。
- **这个信息是否具有有序性、单调性、前缀性、局部性或等价关系？** 这些性质通常直接决定数据结构。
- **是否需要在线更新？** 静态问题和动态问题往往需要不同结构。
- **输出规模是否本身构成复杂度下界？** 返回所有答案时尤其重要。
- **是否能说明替代结构为什么更差？** 面试官常通过这一问验证理解深度。

## 5. 不变量与正确性证明

> **原稿不变量：** 每个键只存在于由当前容量和 hash 决定的唯一 bucket；resize 后必须对所有键重新取 模，不能仅复制桶数组。

### 正确性证明框架

1. **初始化：** 证明算法开始时不变量成立。
2. **保持：** 假设处理当前元素/节点前不变量成立，说明一次更新后仍成立。
3. **终止：** 结合循环或递归终止条件，说明得到的状态恰好对应题目要求。
4. **无遗漏/无重复：** 如果题目要求枚举答案，额外说明为何每个合法答案都会被访问，且不会被重复输出。

这是面试中比“跑几个样例看起来对”更强的论证方式。

## 6. 参考实现（Python）

```python
class MyHashMap:
    def __init__(self, cap=8):
        self.cap, self.n = cap, 0
        self.b = [[] for _ in range(cap)]
    def _idx(self, k): return hash(k) % self.cap
    def get(self, k, default=None):
        for key, val in self.b[self._idx(k)]:
            if key == k: return val
        return default
    def put(self, k, v):
        bucket = self.b[self._idx(k)]
        for i, (key, _) in enumerate(bucket):
            if key == k: bucket[i] = (k, v); return
        bucket.append((k, v)); self.n += 1
        if self.n / self.cap > 0.75: self._resize()
    def remove(self, k):
        bucket = self.b[self._idx(k)]
        for i, (key, _) in enumerate(bucket):
            if key == k: bucket.pop(i); self.n -= 1; return True
        return False
    def _resize(self):
        old = [item for bucket in self.b for item in bucket]
        self.cap *= 2; self.b = [[] for _ in range(self.cap)]
        self.n = 0
        for k, v in old: self.put(k, v)
```

### Code Review 视角

- 变量名应直接体现状态含义，不要让 `i/j/tmp` 承担过多语义。
- 修改共享结构前，先确认是否会丢失后续仍需访问的信息。
- 对 Hash/Heap/Queue/Tree 等结构，明确其中保存的是**值、下标、节点还是聚合状态**。
- 让实现与上面的不变量一一对应；如果代码中存在无法解释的特殊分支，通常意味着状态定义还不够干净。
- Python 内置操作也有复杂度：例如 list 头部删除是 O(n)，`heapq` pop/push 是 O(log n)，dict/set 操作是平均 O(1)。

## 7. 复杂度

平均 put/get/remove O(1)，最坏 O(n)；resize 一次 O(n) 但摊销后 insert 仍 O(1)。

### 复杂度审查

| 维度 | 需要回答的问题 |
|---|---|
| 时间 | 是最坏、平均还是摊销？隐藏参数是 n、k、V/E、L 还是窗口 W？ |
| 空间 | 统计的是额外空间还是包含输出？递归栈算不算？ |
| 预处理 | 排序、建索引、建 Trie/Heap 的成本是否被漏算？ |
| 输出下界 | 若答案本身有 m 项，是否至少需要 O(m)？ |

## 8. 高频失分点

- resize 后不 rehash

- 用 mutable key 却忽略 hash 稳定性

- 把最坏 O(n) 错说成严格 O(1)

### 额外边界测试

- 最小合法输入与空输入（若题目允许）
- 重复值/重复状态是否改变算法不变量

建议面试现场至少手推一个“最小输入”、一个“最容易破坏不变量的输入”和一个“规模极端输入”。

## 12. 专业深化：约束驱动的完整面试推导

> 本节属于 **GitHub 仓库深化内容**：在源 PDF 的题意、洞察、不变量与代码之上补充更严格的算法论证、替代方案、测试与工程边界；不新增未经来源支持的公司题库归属。

### 12.1 先从约束识别 Pattern，而不是从题名背模板

本题的目标结构是 **Bucket / 哈希冲突**。出现以下信号时，应主动联想到这一类结构：

- 需要反复判断“某个值/状态是否见过”
- 暴力方案的瓶颈是在线性容器中重复查找
- 输出或状态需要按 key 聚合

把题目抽象成一句“数据结构需求”会更有效：

> 把需要被快速回答的查询显式编码成 key；value 只保存后续真正需要的信息（下标、频次、节点引用或聚合值）。

> **本题特别说明：** 实现题建议明确：key equality、hash function、bucket storage、load factor、resize policy、rehash 五层职责。工业 HashMap 还有攻击面与并发语义，但面试代码不必过度工程化。

### 12.2 状态最小化：到底必须记住什么

源书稿给出的核心不变量是：

> 每个 key 只存在于由当前 capacity 计算出的唯一 bucket 中；扩容后所有旧 key 必须按新 capacity 重新散列。

进一步拆成三个层次：

1. **输入事实**：当前扫描到的元素、节点、边或操作，哪些信息一旦过去就不会再改变？
2. **未来充分统计量**：未来决策真正需要历史中的哪些摘要？只保存这些，而不是保存“所有历史以防万一”。
3. **答案状态**：区分“用于继续计算的状态”和“已经闭合的最终候选”。Tree DP、Heap、窗口和复合结构题尤其容易把两者混在一起。

面试时可以直接用下面这句话验证自己的状态设计：

> **如果我删除当前结构中的某一类信息，未来是否存在一个合法输入让我无法正确决定？如果不存在，它就不应该被保存。**

### 12.3 解法谱系与 Trade-off

| # | 方案 | 定位 |
|---:|---|---|
| 1 | Separate Chaining | 基线/对照 |
| 2 | Open Addressing（linear/quadratic/double hashing） | 可选方案 |
| 3 | 工业实现可在高碰撞 bucket 上树化/随机化 hash | 面试主解 |

选择主解时至少回答三个问题：

- 它具体消除了基线中的哪一类重复工作？
- 它依赖哪些输入性质（有序、非负、单调、树结构、固定窗口等）？
- 如果这些性质被 follow-up 改掉，哪一层会首先失效？

### 12.4 针对本题的正确性证明

- **核心不变量：** 每个 key 只存在于由当前 capacity 计算出的唯一 bucket 中；扩容后所有旧 key 必须按新 capacity 重新散列。
- **初始化：** 初始状态满足该不变量。
- **保持：** 每次更新只修改与当前输入直接相关的局部状态，同时修复所有辅助索引，因此更新后不变量仍成立。
- **终止：** 当所有输入/操作处理完成时，不变量直接蕴含题目要求的输出条件。

> **面试表达建议：** 不要说“代码跑样例是对的”。先说状态语义，再说一次更新为什么保持语义，最后说明终止时为何覆盖所有合法答案。

### 12.5 复杂度：除了 Big-O 还要说明参数和模型

源书稿结论：**平均 put/get/remove 期望 O(1)；最坏冲突可到 O(n)。扩容一次 O(n)，但摊销插入仍可 O(1)。**

进一步需要注意：

- 区分“额外空间”与输出空间；若返回 m 个结果，O(m) 输出本身就是不可避免的下界。

专业回答建议写成：

```text
n = 主输入规模
k / L / V / E / W = 题目中真正影响结构规模的辅助参数
Time = ...（说明 worst / average / amortized）
Aux Space = ...（不含/包含输出，明确递归栈）
Preprocess = ...（若存在排序、压缩、建索引）
```

### 12.7 代码审查：从 AC 代码提升到面试级实现

- 说明 dict/set 的 O(1) 是平均复杂度，不是严格最坏界
- 若 key 很大，讨论 key 构造与 hash 成本；复杂度不能只写元素个数 n
- 如果需要稳定顺序，不要误以为 HashMap 天然提供题目要求的排序语义

此外，对本题代码建议做四次快速 review：

1. **State review**：每个变量能否用一句不变量解释？
2. **Boundary review**：所有 `+1/-1`、开闭区间、空结构分支是否统一？
3. **Mutation review**：修改容器/指针后，另一个索引或引用是否需要同步更新？
4. **Complexity review**：有没有隐藏的切片、排序、线性删除、重复 DFS 让宣称复杂度失真？

### 12.8 对抗性测试矩阵

| 测试维度 | 本题应覆盖的情况 | 目的 |
|---|---|---|
| 最小/空边界 | 重复 key / 重复值 | 验证不变量与边界处理，不只验证最终值 |
| 重复/相等状态 | 大量冲突或极端 hash 分布的理论退化 | 验证不变量与边界处理，不只验证最终值 |
| 结构极端 | 空集合、单元素与不存在答案 | 验证不变量与边界处理，不只验证最终值 |
| 约束破坏/反例 | 扩容后必须 rehash，不能只把桶数组复制过去。 | 验证不变量与边界处理，不只验证最终值 |

- **反例化：** 扩容后必须 rehash，不能只把桶数组复制过去。
- **反例化：** 哈希相等不代表 key 相等。
- **反例化：** 工业实现还需考虑 hash flooding、线程安全、迭代器语义等。

### 12.9 Follow-up 深挖：不是换题，而是定位“哪个前提变了”

#### 12.9.1 Open Addressing 怎么实现？

- **推荐方向：** bucket 数组直接保存 entry，冲突时按 probe sequence 找空位；查找必须沿同一 probe 序列直到遇到 never-used slot。
- **删除语义：** 不能简单清空中间位置，否则会截断后续 key 的 probe path；通常使用 tombstone 或 backward-shift deletion。
#### 12.9.2 为什么容量常选 2 的幂？

- **变化的前提：** 这个追问改变了 `Bucket / 哈希冲突` 方案依赖的某个约束；先指出哪个不变量失效，再决定是否替换数据结构。
- **推荐方向：** 保留原问题中仍成立的部分，只新增满足新约束的最小状态；最后重新分析时间、空间和边界。
#### 12.9.3 Java HashMap 树化 bucket 的动机是什么？

- **变化的前提：** 这个追问改变了 `Bucket / 哈希冲突` 方案依赖的某个约束；先指出哪个不变量失效，再决定是否替换数据结构。
- **推荐方向：** 保留原问题中仍成立的部分，只新增满足新约束的最小状态；最后重新分析时间、空间和边界。

### 12.10 Pattern 迁移：什么时候应该想到它

**识别信号：**

- 需要反复判断“某个值/状态是否见过”
- 暴力方案的瓶颈是在线性容器中重复查找
- 输出或状态需要按 key 聚合

**迁移方法：**

- 先保留本题的不变量形式，再替换数据载体。例如数组窗口换成字符流，核心仍是“进入/离开时可增量更新的统计”。
- 如果从静态变动态，问“原预处理为什么失效”，再引入可更新结构；不要直接跳到更复杂数据结构。
- 如果从单答案变所有答案，先把输出规模写进复杂度，再讨论去重、predecessor 或路径恢复。
- 如果从算法题变系统级 follow-up，明确算法层与工程层边界：算法不变量仍要成立，工程层再叠加并发、分片、缓存与容错。
