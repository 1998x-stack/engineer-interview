# Q069 Autocomplete：前缀返回 Top-K 候选

> **难度：** H  
> **核心：** Trie / Heap  
> **章节：** Trie / Prefix Tree  
> **内容边界：** “原稿”部分来自仓库内 PDF 对应题目；“深化解析”是在原稿基础上的扩展讲解，不新增未经来源支持的公司题库归属。

## 1. 题目

维护字符串及热度，输入前缀时快速返回热度最高的 k 个候选。

### 仓库深化：手推示例

> 候选 `apple:10, app:8, application:6`，查询前缀 `app` 的 Top-2 可返回 `apple, app`。可在查询时临时 Heap，也可在 Trie 节点预缓存 Top-K。

手推时不要只算最终输出，建议同步写出核心结构在每一步的状态变化，这比“看懂答案”更接近真实面试。

## 2. 面试开始先澄清

- 输入规模与合法性：是否允许空输入、重复值、负数，是否保证答案存在？

- 是否允许修改输入？输出是否要求稳定顺序或去重？

- 复杂度目标：题目是否明确要求 O(n)、O(log n) 或 O(1) 额外空间？

## 3. 基线方案与瓶颈

找到前缀节点后 DFS 整棵子树再排序，查询可能与词典总规模同阶。

### 解法演进对比

| 层级 | 思路 | 代价 / 价值 |
|---|---|---|
| Baseline | 找到前缀节点后 DFS 整棵子树再排序，查询可能与词典总规模同阶。 | 先保证正确，暴露真正瓶颈 |
| 面试目标 | 围绕 `Trie / Heap` 维护最小必要状态 | 查询 O(L+k)；更新约 O(L log k)（取决于缓存结构）；空间会增加 O(节点数*k)。 |

这张表的重点不是“最优解一定唯一”，而是能够解释**为什么新结构减少了哪一类重复工作**。

### 深化解析：先定位重复工作

本题所在章节的核心原则是 **共享公共前缀**。字符串长度 L 往往比词典规模更重要；注意节点空间、终止标记、Top-K 缓存和删除/剪枝。

面试中不要直接报最优结构。先说明基线方案具体重复做了什么，再指出目标结构如何把这部分重复工作缓存、单调淘汰、分层搜索或局部化维护。这样能证明你是在从约束推导算法，而不是背模板。

## 4. 关键洞察：为什么这个数据结构合适

读多写少时，可在每个 Trie 节点预计算/缓存该前缀 Top-K；更新单词热度时沿其字符路径更新 K 大候选。 查询变成 O(prefix length + k)。

### 结构选择检查表

- **我们反复查询/维护的信息是什么？** 把它写成一句话。
- **这个信息是否具有有序性、单调性、前缀性、局部性或等价关系？** 这些性质通常直接决定数据结构。
- **是否需要在线更新？** 静态问题和动态问题往往需要不同结构。
- **输出规模是否本身构成复杂度下界？** 返回所有答案时尤其重要。
- **是否能说明替代结构为什么更差？** 面试官常通过这一问验证理解深度。

## 5. 不变量与正确性证明

> **原稿不变量：** 每个节点缓存集合始终是其整棵子树所有 terminal 词中的 Top-K，因此前缀定位后无 需再遍历子树。

### 正确性证明框架

1. **初始化：** 证明算法开始时不变量成立。
2. **保持：** 假设处理当前元素/节点前不变量成立，说明一次更新后仍成立。
3. **终止：** 结合循环或递归终止条件，说明得到的状态恰好对应题目要求。
4. **无遗漏/无重复：** 如果题目要求枚举答案，额外说明为何每个合法答案都会被访问，且不会被重复输出。

这是面试中比“跑几个样例看起来对”更强的论证方式。

## 6. 参考实现（Python）

```python
# 结构草图：面试重点是 trade-off，而非把所有工程细节一次写满。
class AutoNode:
    def __init__(self):
        self.children = {}
        self.top = []   # 可存最多 K 个 (score, word)，更新时维护
```

### Code Review 视角

- 变量名应直接体现状态含义，不要让 `i/j/tmp` 承担过多语义。
- 修改共享结构前，先确认是否会丢失后续仍需访问的信息。
- 对 Hash/Heap/Queue/Tree 等结构，明确其中保存的是**值、下标、节点还是聚合状态**。
- 让实现与上面的不变量一一对应；如果代码中存在无法解释的特殊分支，通常意味着状态定义还不够干净。
- Python 内置操作也有复杂度：例如 list 头部删除是 O(n)，`heapq` pop/push 是 O(log n)，dict/set 操作是平均 O(1)。

## 7. 复杂度

查询 O(L+k)；更新约 O(L log k)（取决于缓存结构）；空间会增加 O(节点数*k)。

### 复杂度审查

| 维度 | 需要回答的问题 |
|---|---|
| 时间 | 是最坏、平均还是摊销？隐藏参数是 n、k、V/E、L 还是窗口 W？ |
| 空间 | 统计的是额外空间还是包含输出？递归栈算不算？ |
| 预处理 | 排序、建索引、建 Trie/Heap 的成本是否被漏算？ |
| 输出下界 | 若答案本身有 m 项，是否至少需要 O(m)？ |

## 8. 高频失分点

- 只说 Trie，不解决 Top-K 排序成本

- 忽略热度更新导致缓存失效

- 大 k 时每节点缓存空间爆炸

### 额外边界测试

- 最小合法输入与空输入（若题目允许）
- 重复值/重复状态是否改变算法不变量
- k=1、k=n 或候选不足 k 个
- 大量相同优先级时的 tie-breaking
- 空串/前缀本身就是完整词
- 字符集/大小写/Unicode 是否受限

建议面试现场至少手推一个“最小输入”、一个“最容易破坏不变量的输入”和一个“规模极端输入”。

## 9. 面试官追问与答题方向

- 写多读少如何改成查询时计算？
  - **答题方向：** 先把新增约束写成需要维护的新不变量，再判断原结构能否继续满足；若不能，明确需要替换或组合的结构。
- 如何做个性化 autocomplete？
  - **答题方向：** 先把新增约束写成需要维护的新不变量，再判断原结构能否继续满足；若不能，明确需要替换或组合的结构。
- 分布式场景如何 shard？
  - **答题方向：** 先定义一致性、时间语义和分片键；再讨论跨节点聚合、时钟偏差、容错与重平衡。

### Follow-up 的统一处理方法

不要把追问当成新题。先问：**原方案依赖的哪个前提被改变了？** 然后只替换受到影响的那一层结构。例如从离线变在线，通常保留问题定义而替换状态维护方式；从单机变分布式，则新增分片、一致性和容错约束。

## 10. 60 秒口述模板

## 12. 专业深化：约束驱动的完整面试推导

> 本节属于 **GitHub 仓库深化内容**：在源 PDF 的题意、洞察、不变量与代码之上补充更严格的算法论证、替代方案、测试与工程边界；不新增未经来源支持的公司题库归属。

### 12.1 先从约束识别 Pattern，而不是从题名背模板

本题的目标结构是 **Trie + Top-K 缓存**。出现以下信号时，应主动联想到这一类结构：

- 大量字符串共享前缀
- 查询以 prefix 为主而不是完整 key equality
- 需要边搜索边剪枝字典候选

把题目抽象成一句“数据结构需求”会更有效：

> Trie 节点表示一个前缀；terminal 与“节点存在”是两个不同概念。增强字段（Top-K、计数）必须有明确更新不变量。

> **本题特别说明：** 工程化自动补全通常不会把整个语言模型/排名模型塞进 Trie。Trie 更像候选召回索引；ranking、freshness、personalization、abuse filtering 是后续层。算法面试应先守住这一边界。

### 12.2 状态最小化：到底必须记住什么

源书稿给出的核心不变量是：

> 节点 cache 必须始终等于该节点子树内按 ranking 规则最高的 K 个终止词。

进一步拆成三个层次：

1. **输入事实**：当前扫描到的元素、节点、边或操作，哪些信息一旦过去就不会再改变？
2. **未来充分统计量**：未来决策真正需要历史中的哪些摘要？只保存这些，而不是保存“所有历史以防万一”。
3. **答案状态**：区分“用于继续计算的状态”和“已经闭合的最终候选”。Tree DP、Heap、窗口和复合结构题尤其容易把两者混在一起。

面试时可以直接用下面这句话验证自己的状态设计：

> **如果我删除当前结构中的某一类信息，未来是否存在一个合法输入让我无法正确决定？如果不存在，它就不应该被保存。**

### 12.3 解法谱系与 Trade-off

| # | 方案 | 定位 |
|---:|---|---|
| 1 | 每次查询遍历整个前缀子树 | 基线/对照 |
| 2 | Trie 节点缓存 Top-K，读快写慢 | 可选方案 |
| 3 | 搜索索引/倒排 + ranking 适合工程级海量候选 | 面试主解 |

选择主解时至少回答三个问题：

- 它具体消除了基线中的哪一类重复工作？
- 它依赖哪些输入性质（有序、非负、单调、树结构、固定窗口等）？
- 如果这些性质被 follow-up 改掉，哪一层会首先失效？

### 12.4 针对本题的正确性证明

- **前缀不变量：** 节点 cache 必须始终等于该节点子树内按 ranking 规则最高的 K 个终止词。
- **路径对应：** Trie 根到当前节点的边标签与当前已处理前缀一一对应。
- **剪枝正确性：** 若某前缀没有对应 child，则词典中不存在任何以该前缀开头的目标，因此整棵后续搜索分支可安全丢弃。
- **终止语义：** 到达 terminal 才表示完整词存在；“节点存在”只证明前缀存在，不能替代完整词判断。

> **面试表达建议：** 不要说“代码跑样例是对的”。先说状态语义，再说一次更新为什么保持语义，最后说明终止时为何覆盖所有合法答案。

### 12.5 复杂度：除了 Big-O 还要说明参数和模型

源书稿结论：**查询 O(L+K)；构建/更新成本依缓存维护策略而定，最朴素每节点 O(K log K)。空间约为 Trie 节点数 × K。**

进一步需要注意：

- 字符串 key 的比较、切片、构造 signature 往往还有长度 L 的成本，不应只写“哈希 O(1)”。
- Heap 的参数通常是候选数 k/F/S，而不是总输入 n；写成 O(log k) 能体现结构规模。
- 题目存在业务/输入模型参数，最好给出符号定义（如 K、F、L、m、W），避免用一个 n 模糊所有规模。

专业回答建议写成：

```text
n = 主输入规模
k / L / V / E / W = 题目中真正影响结构规模的辅助参数
Time = ...（说明 worst / average / amortized）
Aux Space = ...（不含/包含输出，明确递归栈）
Preprocess = ...（若存在排序、压缩、建索引）
```

### 12.7 代码审查：从 AC 代码提升到面试级实现

- children 用定长数组还是 HashMap 取决于 alphabet 大小与稀疏性
- 节点数近似所有插入字符串的不同前缀总数
- 热度缓存等增强字段会把读优化转化为写放大

此外，对本题代码建议做四次快速 review：

1. **State review**：每个变量能否用一句不变量解释？
2. **Boundary review**：所有 `+1/-1`、开闭区间、空结构分支是否统一？
3. **Mutation review**：修改容器/指针后，另一个索引或引用是否需要同步更新？
4. **Complexity review**：有没有隐藏的切片、排序、线性删除、重复 DFS 让宣称复杂度失真？

### 12.8 对抗性测试矩阵

| 测试维度 | 本题应覆盖的情况 | 目的 |
|---|---|---|
| 最小/空边界 | 一个词是另一个词的前缀 | 验证不变量与边界处理，不只验证最终值 |
| 重复/相等状态 | 空字符串/通配符 | 验证不变量与边界处理，不只验证最终值 |
| 结构极端 | 大量共享前缀与完全不共享前缀 | 验证不变量与边界处理，不只验证最终值 |
| 约束破坏/反例 | 真实系统 ranking 可能随时间变化，不能把静态缓存当万能方案。 | 验证不变量与边界处理，不只验证最终值 |

源书稿中的高频失分点也应逐个转成单元测试：

- **反例化：** 真实系统 ranking 可能随时间变化，不能把静态缓存当万能方案。
- **反例化：** 热门前缀节点缓存占用可观。
- **反例化：** 需要明确 tie-break、个性化、敏感词过滤等业务规则。

### 12.9 Follow-up 深挖：不是换题，而是定位“哪个前提变了”

#### 12.9.1 如何支持实时热度更新？

- **变化的前提：** 不能等待完整输入后离线重排，需要把答案维护成增量状态。
- **推荐方向：** 保留只与未来有关的摘要；常见结构是 Hash、Heap、Deque、双 Heap 或平衡树。
#### 12.9.2 个性化推荐如何与全局 Trie 合并？

- **变化的前提：** 这个追问改变了 `Trie + Top-K 缓存` 方案依赖的某个约束；先指出哪个不变量失效，再决定是否替换数据结构。
- **推荐方向：** 保留原问题中仍成立的部分，只新增满足新约束的最小状态；最后重新分析时间、空间和边界。
#### 12.9.3 海量词典如何分片？

- **变化的前提：** 数据不再共享单一内存与全局顺序。
- **推荐方向：** 明确 partition key、局部摘要、跨分片 merge；如果要求精确全局顺序，还要考虑 coordinator/一致性和网络复杂度。

### 12.10 Pattern 迁移：什么时候应该想到它

**识别信号：**

- 大量字符串共享前缀
- 查询以 prefix 为主而不是完整 key equality
- 需要边搜索边剪枝字典候选

**迁移方法：**

- 先保留本题的不变量形式，再替换数据载体。例如数组窗口换成字符流，核心仍是“进入/离开时可增量更新的统计”。
- 如果从静态变动态，问“原预处理为什么失效”，再引入可更新结构；不要直接跳到更复杂数据结构。
- 如果从单答案变所有答案，先把输出规模写进复杂度，再讨论去重、predecessor 或路径恢复。
- 如果从算法题变系统级 follow-up，明确算法层与工程层边界：算法不变量仍要成立，工程层再叠加并发、分片、缓存与容错。

### 12.11 面试官视角：这题真正区分候选人的地方

| 能力层级 | 典型表现 |
|---|---|
| 只会做 | 能写出代码，但无法解释为什么该结构成立 |
| 合格 | 能从 baseline 推出 `Trie + Top-K 缓存`，复杂度与边界基本正确 |
| 较强 | 能写出不变量/证明，并比较至少一种替代方案 |
| 很强 | follow-up 改约束后，能明确指出**失效的前提**并局部替换结构，而不是重新猜算法 |

建议复盘时把目标定为最后两档，而不是“AC 即完成”。
