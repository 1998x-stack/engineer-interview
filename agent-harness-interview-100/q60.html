AGENT HARNESS · 60 / 101

Agent Audit Log 应记录什么？

一句话结论：记录谁以何目标、在什么上下文和授权下调用了什么工具、造成什么状态变化。

难度：★★★★☆　高频：★★★☆☆　岗位：Harness / Infra / Backend　PDF：第 57 页起

内容分层：第 1–13 节以 PDF 原稿为主并做结构化整理；第 14 节是 Repo v1.1 的工程扩展，结合公开一手资料与系统设计方法补强。

1. 面试官真正想考什么

你是否能在 agent autonomy 与安全之间用系统机制做权衡，而不是只靠人工确认。

更深一层： Audit Log 必须关联 identity、authorization、intent、tool args、state diff 与 outcome，才能用于安全追责和事故复盘。

2. Know-Why：为什么这是 Harness 问题

安全的核心不是相信模型，而是把可造成的伤害范围工程化地限制在最小边界，并对越界动作做显式授权。针对本题，关键不是记住术语，而是识别系统中的“控制点”：记录谁以何目标、在什么上下文和授权下调用了什么工具、造成什么状态变化。 这类控制点一旦缺失，模型即使单次推理正确，也可能因为重试、上下文污染、环境状态、权限或错误反馈而在真实任务中失败。

三条工程不变量

  1. Prompt 不是安全边界；真正边界必须由 runtime enforce。
  2. 权限默认最小化，并绑定身份、资源、动作、时间与额度。
  3. 审计记录必须能还原谁在什么授权下造成了什么状态变化。

这些不变量不是“最佳实践口号”，而是用来约束设计空间的。面试时如果方案违反其中一条，应主动解释为什么值得承担风险，以及如何用实验和监控把风险显式化。

3. Know-How：怎样落到生产系统

  • run/actor/model/tool/args/decision/result/timestamps/state diff/artifact refs。

  • 把这一机制做成可配置、可追踪、可评测的 runtime primitive。

推荐的工程 Artifact

建议画 trust boundary，定义 policy decision schema，并列出至少 5 个 adversarial/abuse test。

3A. Production Deep Dive：把概念变成系统协议

3A.1 核心机制

Audit Log 是 security + debugging primitive，必须记录 actor/goal/version/action/decision/result 而不是只记模型文本

Source of Truth： Immutable audit events。在面试中主动指出这一点很重要，因为 Agent 的自然语言状态只是“认知状态”，真正能决定是否继续、是否重试、是否完成的通常是外部持久状态或环境。

3A.2 推荐状态 / 数据模型

Principal { user_id, tenant_id, agent_id, roles }
Capability { tool, resource_scope, action_scope, ttl }
PolicyDecision { decision_id, allow|deny|ask, rule_id, reason }
Approval { principal, action_hash, scope, expires_at }
AuditEvent { actor, action, resource, decision, result, timestamp }

这不是要求所有系统都使用同一 schema；重点是把本题涉及的身份、版本、状态、结果引用和恢复语义从自然语言中提取出来，变成可验证 contract。

3A.3 具体故障场景

Scenario：事故后无法还原是谁授权了哪次工具调用

排查时不要只看最终回答。建议从 goal/version → model decision → policy → tool/action → environment mutation → persisted state → grader 顺序追踪，确认“模型认为发生了什么”与“环境实际发生了什么”在哪一步分叉。

3A.4 可证伪实验

Experiment： 从 audit log 重放 incident timeline。

一个好的 Harness 改动必须能写成可证伪假设，例如：“如果这个机制解决了目标 failure mode，那么在固定 model/task/env 后，专项指标应改善；如果没有改善，就不应把复杂度长期留在 runtime。”

Success criterion / SLO： 关键 action 可完整追溯。

3A.5 Production Checklist

  • [ ] 身份、授权、执行隔离分层
  • [ ] 默认最小权限，能力有 scope 与 TTL
  • [ ] 高风险副作用必须可审计/审批/回滚或补偿
  • [ ] 不可信内容不能提升控制权限
  • [ ] filesystem/network/credential 三类边界分别建模

4. Failure Modes：低分答案与真实故障

  • 只记录 final answer

  • 日志包含明文 secret

生产环境再多想三层

  • Detectability：这个失败在 trace / state diff / tool result / grader 中留下什么证据？
  • Recoverability：失败后是 retry、replan、compensate、rollback、ask human，还是 terminate？
  • Blast Radius：错误最多影响一次 tool call、一个 run、一个 tenant，还是外部真实世界？

5. Trade-offs：不要只讲“最佳方案”

严格隔离提高安全但可能降低可用性；权限放宽提高自治，却必须用 scope、审计和可撤销性控制风险。

面试中建议明确给出 baseline，并说明新机制增加了什么复杂度、成本或延迟。只有当它针对一个可观测 failure mode，并带来可测量收益时，才值得进入 Harness。

6. 最小 Eval：怎样证明设计有效

一个可复用的最小实验框架：

  1. 固定 task set、model version、environment version。
  2. 只改变本题讨论的一个 Harness 变量。
  3. 每个 task 运行多 trial，记录 outcome + trace。
  4. 按 failure taxonomy 聚类，不只比较平均分。
  5. 同时报告质量、稳定性、延迟、token/cost 和安全指标。

建议观测指标

  • unsafe-action escape rate
  • false-deny/false-ask rate
  • approval rate
  • blast-radius proxy
  • credential scope violations

本题专项 Eval： 建议画 trust boundary，定义 policy decision schema，并列出至少 5 个 adversarial/abuse test。

  • 如果这个机制失败，你会在 Trace 中看到什么证据？

  • 如果 prompt injection 已经成功，什么系统边界仍能阻止真实伤害？

建议继续自问：

  • 这个设计里谁拥有最终真相：模型、数据库、环境、grader，还是人工？
  • 如果请求在任意一步 crash，恢复点在哪里？
  • 如果模型能力提升一代，这个 Harness 机制还需要吗？怎样做 ablation？

11. Offer 级回答结构

建议用 4 段式回答：①先给结论和适用边界；②解释 failure mode，也就是“为什么需要它”；③给出最小实现和关键数据结构；④主动给出 trade-off + eval 指标。这样能把概念答案升级为工程答案。第六章复盘：把 10 道题串成一个系统本章一句话 权限不是弹窗，而是 hard deny + contextual policy + sandbox + scoped credentials + audit 共同构成的 capability containment。第七章 Evaluation / Observability本章核心 Agent 评测必须面向 trajectory + outcome；生产 trace 要进入 eval 和 regression 闭环。没有 eval 的 Agent 优化不可重复。Agent 的随机轨迹决定了评测必须同时记录过程、结果和多次试验的稳定性。本章面试目标

  • 能用 task/trial/trace/outcome/grader 语言讨论 eval。

  • 理解多 trial、pass@k/pass^k、judge calibration。

  • 能把生产失败沉淀为 regression。

14. 专业深挖：把“会回答”升级为“会设计”

14.1 核心判断与边界

核心判断： Audit Log 是安全/合规/调试的事实链，必须能回答谁在何时基于何版本做了什么。

必须讲清的边界： 日志要不可抵赖、可查询，同时避免存入不必要敏感 prompt/secret。

这意味着面试时不能只描述一个 happy path。应先明确 source of truth、可接受的错误语义、不可违反的不变量、恢复策略，再谈具体框架。模型提出动作但不拥有授权；安全边界必须由确定性 policy 与执行层强制。

14.2 设计审查：上线前必须回答的问题

  • [ ] 身份/租户是否绑定
  • [ ] 参数是否规范化
  • [ ] sandbox 是否真正 enforce
  • [ ] credential 是否最小权限
  • [ ] audit 是否完整

对于本题，还要额外确认：

  1. 最坏情况下会错成什么样？ 不只问“会不会失败”，而是问错误是否会变成重复副作用、状态漂移、越权、成本爆炸或不可恢复。
  2. 系统如何知道自己错了？ 至少需要一个环境信号、结构化状态、grader 或 trace 证据，而不是模型自我反省。
  3. 失败后下一步是否确定？ retry、repair、reconcile、compensate、rollback、ask-human、terminate 应尽量由错误类型和策略决定。
  4. 模型升级后是否仍需要这层机制？ 若答案无法用 ablation 验证，Harness 很容易累积成永久技术债。

14.3 推荐的实现接口 / 状态语义

class PolicyDecision:
    effect: str  # ALLOW/DENY/ASK
    rule_id: str
    reason: str
    scope: dict
    expires_at: str | None

本题最值得落到白板或代码里的 Artifact 是：设计 append-only audit event + hash/reference。

建议所有关键对象都带 run_id / version / timestamp / provenance；涉及副作用时再加入 operation_id / idempotency_key，涉及安全时加入 principal / tenant / policy_version。这样 trace、checkpoint、audit 和 eval 才能关联成同一条因果链。

14.4 Fault Injection：如何主动证明系统能扛住坏情况

故障注入场景： 删除/篡改中间 tool event，检查能否检测。

专业的 Harness 测试不应该只做“模型有没有回答对”，而应把故障点插到状态提交边界、网络边界、权限边界、上下文转换边界。测试成功的标准不是“不报错”，而是：

  • 最终状态可解释；
  • 不产生不可接受的重复副作用；
  • trace 能定位失败阶段；
  • recovery 不依赖人工猜测；
  • 若无法自动恢复，系统能安全停在可人工处理的状态。

14.5 可证伪实验 / Ablation

实验： event completeness + tamper-evidence tests。

建议用 paired trials：固定 task set、model、environment、seed policy 和 grader，只改变本题对应的 Harness primitive。至少运行足够多 trial 以看到方差，并同时报告均值与分位数/置信区间。若方案只提升平均 solve-rate，却显著恶化尾延迟、成本或高风险错误率，应明确写成 trade-off，而不是宣布“全面提升”。

14.6 指标：至少同时看质量、稳定性和系统代价

指标 Why 建议切片
audit_completeness 衡量本题设计是否真的改善，而不是只增加 Harness 复杂度 建议按 task type / risk / model version 分桶
traceability 衡量本题设计是否真的改善，而不是只增加 Harness 复杂度 建议按 task type / risk / model version 分桶
pii_leak_rate 衡量本题设计是否真的改善，而不是只增加 Harness 复杂度 建议按 task type / risk / model version 分桶

除了专项指标，建议保留四个全局指标：verified_success_rate、cost_per_success、p95_end_to_end_latency、human_intervention_rate。安全敏感题再增加 unsafe_action_rate 或 policy_escape_rate。

14.7 Debugging Playbook

遇到失败时按以下顺序缩小范围：

  1. 重放输入与版本：确认 model / prompt / tools / harness / environment / grader 是否完全一致；
  2. 定位第一个分叉点：从 trace 中找出预期轨迹与失败轨迹首次不同的 model decision、tool result 或 state transition；
  3. 区分认知错误与系统错误：模型“想错了”与工具实际执行失败必须分开；
  4. 检查状态提交窗口：尤其关注 action 已发生但 result/checkpoint 未持久化的窗口；
  5. 构造最小复现：删掉无关上下文和工具，把 failure 固化成 regression case；
  6. 做单变量修复：修改 schema/context/policy/runtime 中最小的一项，再跑原始失败集。

14.8 Senior / Staff 级回答信号

Staff 级会区分 trace（调试）和 audit（合规证据）的 retention/immutability 需求。

面试官通常会继续追问“为什么不是更简单的方案”。因此答案中应主动给出 baseline → failure evidence → mechanism → measurable gain → added complexity → rollback/ablation plan，这比只列组件更能体现 Agent Systems 能力。
