实现 Trie / Implement Trie

定位：Medium · 优先级 S · 高频经典母题（H） · Prefix Tree 章节：回溯、搜索树与 Trie 冻结版：内容源自 docs/assets/algorithm-interview-100-2026.pdf，本页在其基础上扩写。

1. 题目概括

支持插入单词、完整查找与前缀查找。

本仓库不复制 LeetCode 完整题面；正式练习时请从原题链接确认输入输出细节。

2. 面试官在考什么

这题表面考 Prefix Tree，更深层通常考三件事：

  1. 能否从基线解法中识别重复工作；
  2. 能否把关键约束写成稳定的不变量；
  3. 能否在写完代码后解释复杂度、边界与约束变化。

PDF 核心突破： 把公共前缀共享成路径；节点需要 children 映射与 is_end 标记区分单词和前缀。

3. 先做约束澄清

面试开始先确认：输入规模、是否保证存在答案、是否允许修改输入、是否包含重复值/负数，以及返回值对顺序是否有要求。不同约束可能改变最优方案或实现边界。

建议现场至少问/确认 2-3 个与本题最相关的条件，而不是直接开始编码。

4. 暴力基线与瓶颈

直接枚举连续区间会重复计算区间和/状态。使用 prefix[j]-prefix[i] 把区间条件改写为两个前缀状态的关系。

基线方案的作用不是“凑一个答案”，而是暴露优化方向：到底重复枚举了候选、重复查询了历史、还是重复计算了子问题。

5. 关键观察与不变量

问题特定观察： 把公共前缀共享成路径；节点需要 children 映射与 is_end 标记区分单词和前缀。

家族级不变量： 当前前缀状态只与历史前缀状态交互；计数题存频次，最长题通常存最早位置。

在真正写代码前，应该能把不变量压缩成一句话；如果一句话说不清，通常说明边界语义还没有定稳。

6. 最优解法推导

PDF 给出的最优路径： insert 逐字符创建；search 走完后检查 is_end；startsWith 只需路径存在。

可以按下面顺序推导，而不是直接背模板：

  1. 写出基线中被重复处理的对象；
  2. 找到能复用的历史状态或单调结构；
  3. 明确更新顺序与循环边界；
  4. 证明每次丢弃/合并/移动都不会漏掉可能答案；
  5. 最后才落到代码。

7. 正确性说明

每个连续区间唯一对应一对前缀边界，因此统计/优化历史前缀即可覆盖全部候选。

针对本题，证明时应把“把公共前缀共享成路径；节点需要 children 映射与 is_end 标记区分单词和前缀。”对应到代码中的具体状态更新。面试中不必写形式化证明，但要能解释为什么优化后没有漏解、重复计数或错误淘汰候选。

8. 复杂度

冻结版结论： 每操作 O(L) / 总字符节点数

面试中不要只报 Big-O：还要说清复杂度来自哪里。例如线性算法要解释每个元素被推进/入栈/出栈/访问的次数；堆算法要解释为什么是 log k 而不是 log n。

9. Python 参考实现

from __future__ import annotations
class TrieNode:
    def __init__(self): self.children={}; self.end=False

class Trie:
    def __init__(self): self.root=TrieNode()
    def insert(self, word: str) -> None:
        node=self.root
        for ch in word: node=node.children.setdefault(ch,TrieNode())
        node.end=True
    def search(self, word: str) -> bool:
        node=self._walk(word); return bool(node and node.end)
    def startsWith(self, prefix: str) -> bool: return self._walk(prefix) is not None
    def _walk(self, s):
        node=self.root
        for ch in s:
            if ch not in node.children: return None
            node=node.children[ch]
        return node

10. Dry-run：怎样检查代码

画出 prefix/state 序列，并在每一步写出“要查的历史状态”和当前答案增量。

建议把每一步的关键状态写在纸上，不只看最终输出。

  • 空前缀初始化
  • k=0/目标为 0
  • 负数导致普通滑窗失效
  • 同一前缀多次出现

12. 高频失误

只靠 children 不能区分 app 与 apple 中的 app 是否已插入。

此外还要检查：

  • 是否偷偷依赖题目没有承诺的条件；
  • 查询和更新顺序是否改变了允许使用的数据范围；
  • 返回值、下标和区间端点是否与题意一致；
  • 是否为了省几行代码牺牲了可解释性。

14. 算法岗工程化升级

搜索联想系统可在 Trie 节点维护 prefix Top-K；进一步比较 Radix Tree/FST 与热门前缀缓存。

这一步是算法岗区别于纯刷题的重要训练：从“单机、静态、小数据”的 LeetCode 假设继续推到在线、流式、分布式或 ML 系统约束。

16. 迁移训练

  • 同模式变体：保持 Prefix Tree 不变，改变“求数量 / 求最长 / 求最短 / 返回路径”等目标。
  • 约束变体：加入重复值、负数、动态更新、内存限制或流式输入。
  • 实现变体：用另一种数据结构重做，并比较复杂度与代码风险。
  • 表达训练：不看代码，只用 90 秒讲清“基线 -> 瓶颈 -> 不变量 -> 最优解”。

17. 解法谱系：从“能做”到“面试最优”

这一节的目标是避免“只背一个答案”。真正的算法面试通常会沿着 baseline → 瓶颈 → 优化 → trade-off 继续追问。

层级 方案 复杂度/代价 面试价值
基线 枚举所有连续区间并逐段计算 O(n²)~O(n³) 暴露“相邻区间重复计算”的浪费
中间解 前缀数组把单次区间查询降为 O(1) 构建 O(n)，枚举仍 O(n²) 说明 prefix 只是第一层压缩
推荐解 把区间条件改写成当前 prefix 与历史 prefix 的关系并用 Hash 维护。本题落地为：insert 逐字符创建；search 走完后检查 is_end；startsWith 只需路径存在。 通常 O(n) 时间 / O(n) 空间 围绕 Prefix Tree 的关键不变量说明为什么安全。

怎样在白板上自然推到推荐解

  1. 先承认基线是正确的：不要一上来赌最优模板；先建立 correctness anchor。
  2. 指出真正浪费：本题最值得消掉的重复工作可以概括为：把公共前缀共享成路径；节点需要 children 映射与 is_end 标记区分单词和前缀。
  3. 选择结构而不是背 API：说明 Prefix Tree 为什么正好承载需要保留的信息。
  4. 先说 invariant，再写循环：循环条件、更新顺序和边界全部应该从 invariant 推出来。
  5. 最后比较替代方案：什么时候愿意多用空间换更低延迟？什么时候输入已排序/流式/内存受限会换算法？

18. 状态设计与不变量审计

状态 精确定义 必须保持的性质
prefix / balance 当前位置之前的累计状态 更新后代表当前前缀
历史映射 prefix→频次/最早位置 初始化空前缀是关键
答案 满足关系的区间统计 每个区间唯一对应两个前缀

本题的一句话不变量

把公共前缀共享成路径；节点需要 children 映射与 is_end 标记区分单词和前缀。

这句话必须能对应到代码中的某个具体变量、容器或返回值。若只能说“这里用一个 Hash/DP/Heap”，但说不出其中存的精确语义，通常还没有真正掌握。

写代码前的三问

  • 状态何时有效？ 当前元素加入之前还是之后？
  • 状态是否包含当前元素？ 这会直接决定 query-before-update 还是 update-before-query。
  • 丢弃的信息为何永远不再需要？ 若无法回答，空间优化或指针移动可能是不安全的。

19. 正确性证明：面试版 + 严谨版

19.1 面试版证明骨架

  1. 初始化成立：循环/递归开始前，状态满足定义。
  2. 保持性成立：假设处理前缀/子树前 invariant 成立，本轮按照 Prefix Tree 更新后仍成立。
  3. 不漏解：被跳过、弹出、剪枝、覆盖或淘汰的候选，都可以证明不可能产生更优合法答案。
  4. 终止得到答案：扫描结束/递归返回时，所有需要考虑的候选已经被覆盖。

19.2 本题证明抓手

  • 关键事实：把公共前缀共享成路径；节点需要 children 映射与 is_end 标记区分单词和前缀。
  • 转移/操作：insert 逐字符创建；search 走完后检查 is_end；startsWith 只需路径存在。
  • 最容易被质疑的点：只靠 children 不能区分 app 与 apple 中的 app 是否已插入。

面试时不需要写形式化定理，但至少要能给出一个反事实解释：如果不按当前更新顺序/移动规则做，会在哪个最小反例上出错。

20. 复杂度深拆：不要只背 Big-O

目标结论： 每操作 O(L) / 总字符节点数

扫描只前进一次；每个位置做常数次 prefix 更新与 Hash 查询。空间上最坏每个前缀状态都不同，因此历史映射可达 O(n)。

复杂度回答建议

  • 时间：说明循环/递归总共访问多少状态，每个状态执行哪些 O(1)/O(log n) 操作。
  • 空间：区分“输出空间”“输入原地修改”“显式辅助结构”“递归调用栈”。
  • 最坏 vs 平均/期望：Hash、QuickSelect、随机采样等题不要把平均/期望复杂度说成确定最坏上界。
  • 隐藏主项：如果方案需要排序、建图、预处理，必须把它计入总复杂度。

21. 测试工程：从样例测试升级为 bug 定向测试

基础测试矩阵

  • [ ] 空前缀初始化是否正确
  • [ ] 答案从下标 0 开始的区间
  • [ ] 大量重复 prefix 状态
  • [ ] 负数导致滑窗失效的反例
  • [ ] 计数题与最长题 map value 语义是否混淆

本题 bug 定向测试

高频失误是：只靠 children 不能区分 app 与 apple 中的 app 是否已插入。

因此至少手工设计一个样例，让错误实现稳定触发这个问题。测试目标不是“多测几个数”，而是让每个 case 对应一个风险：初始化、边界、重复、更新顺序、数据结构不变量、返回语义。

推荐测试层次

  1. Minimal：最小合法输入；
  2. Boundary：答案卡在边界；
  3. Adversarial：专门攻击高频错误；
  4. Structure：构造最坏形态，如退化树、单调数组、长链、全重复；
  5. Random differential test：小规模随机输入，与暴力基线对拍。

对拍尤其适合 Hard：先写一个慢但显然正确的 reference，再随机生成小输入比较数千次，往往能快速找出边界 bug。

22. 代码 Review Checklist

提交代码前逐项检查：

  • [ ] 函数/变量名能直接表达状态语义，而不是 a/b/tmp1/tmp2。
  • [ ] 初始化值来自 state 定义，而不是“记得模板这么写”。
  • [ ] 查询与更新顺序符合“当前元素能否参与当前答案”的语义。
  • [ ] 每个 while 都能解释终止性；每个 continue/break 都有正确性依据。
  • [ ] 没有把平均 O(1) Hash、期望 O(1) sampling 等误报为绝对最坏复杂度。
  • [ ] 没有漏算排序、建图、递归栈、输出容器等成本。
  • [ ] 至少 dry-run 一个普通样例和一个 adversarial 样例。

Medium / S 级要求： Medium 是算法岗 live coding 主战场：通常要求在 15–25 分钟内完成“推导 + 代码 + dry-run”。

23. Follow-up Tree：面试官可以怎样继续加压

Level 1：证明与边界

  • 为什么当前 invariant 足以保证不漏解？
  • 把更新顺序交换一下会发生什么？给一个最小反例。
  • 输入为空、重复很多、极端长度时，代码哪一行最容易出错？

Level 2：替代算法

  • 不允许使用当前主要辅助结构时，退化到什么方案？复杂度如何变化？
  • 如果输入额外满足“有序 / 值域小 / 全正 / 静态 / 可修改”等条件，能否换更简单或更快的方案？
  • 如果除了答案值还要求恢复具体路径/下标/操作序列，需要额外保存什么？

Level 3：本题经典追问

Autocomplete、前缀 Top-K、压缩 Trie/Radix Tree。

Level 4：算法工程约束

  • 数据量扩大 1000 倍，CPU、内存、I/O 哪一个先成为瓶颈？
  • 输入变为无限流后，哪些状态还能增量维护？
  • 数据分片到多机后，局部结果是否具有可合并性？若不能，需要交换什么中间状态？

24. 算法工程化：从 LeetCode 假设走向真实系统

  • 流式输入可以在线更新 prefix，但“任意历史区间查询”通常要求保留历史映射。
  • 分布式 prefix 需要处理 shard 边界的累计 offset，局部前缀不能直接拼接。
  • 近似计数场景可考虑 sketch，但要接受误差界。

一个通用的系统化分析框架

维度 LeetCode 默认 工业追问
数据规模 单机内存可放 超内存、分片、冷热分层
到达方式 静态数组/字符串 流式、乱序、动态更新
正确性 精确答案 是否允许近似、误差界多大
延迟 单次运行 P50/P95/P99、持续 QPS
状态 进程内临时变量 checkpoint、恢复、TTL、并发一致性
输出 一个答案 Top-K、路径、解释、可审计中间状态

27. 复习卡片 / Active Recall

Q1. 看到怎样的信号应该想到 Prefix Tree？ A. 当题目出现与“把公共前缀共享成路径；节点需要 children 映射与 is_end 标记区分单词和前缀。”相同的结构时，优先尝试该模式；先写清状态和不变量，再写模板。

Q2. 这题最关键的一句话 invariant 是什么？ A. 把公共前缀共享成路径；节点需要 children 映射与 is_end 标记区分单词和前缀。

Q3. 推荐解的复杂度为什么是 每操作 O(L) / 总字符节点数？ A. 不只记结论；按第 20 节把“状态数、每状态操作、辅助结构、递归栈/排序成本”完整说一遍。

Q4. 最容易写错的地方？ A. 只靠 children 不能区分 app 与 apple 中的 app 是否已插入。

Q5. 面试官把规模放大 1000 倍时，第一反应是什么？ A. 先识别当前方案的主要状态与随机访问结构，再判断 CPU、内存还是 I/O 先爆；随后讨论 streaming / sharding / approximation。
