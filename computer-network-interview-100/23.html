为什么 TCP 需要三次握手，不能两次？

定位：进阶 · 面试频率：★★★★★ · 标签：Handshake / 旧报文
本章：第三章 TCP 连接、状态机与可靠性 · 返回总目录

面试官到底在考什么

这道题不只考定义。面试官通常希望确认你能否把 Handshake / 旧报文 放进真实协议栈/系统调用/故障场景中解释，并且在追问发生时仍保持同一个心智模型，而不是切换成互相矛盾的八股结论。

30 秒标准回答（PDF 原内容）

两次只能让服务端知道客户端的 SYN 被收到、客户端知道服务端存在，但服务端无法确认客户端已经收到服务端的初始序列信息。第三次 ACK 完成双向 ISN 确认，也帮助避免旧的延迟连接请求让服务端错误建立连接。

深度解析：Know-How + Know-Why（PDF 原内容）

  1. 握手的本质是双方同步“发送起点”和接收状态。
  2. 网络可能复制、延迟旧 SYN；状态机必须能识别并避免错误复用旧连接上下文。
  3. TCP 的可靠全双工语义需要双方都确认对端序列空间。

二次深化：工程上还必须知道什么

本题的高级回答应主动说明适用范围和观测边界：协议规范描述的是语义与状态机，真实 Linux/云网络实现还会受到内核版本、offload、中间盒、代理和应用框架的影响。面试中若无法确定实现细节，应明确“规范保证”和“常见实现”分别是什么。

本章共同的工程视角

  • TCP 是有状态的可靠字节流；状态机、序号空间、ACK 语义和定时器是理解所有 TCP 题的共同底座。
  • 不要把“内核收到”“对端 TCP 确认”“对端应用读到”“业务处理成功”混成一个层次。
  • 排障时必须把主动关闭方、连接状态、Seq/Ack 时间线和应用生命周期放在一起看。

V2 深入：“为什么三次”应从最小充分信息交换来回答

第一性原理

要建立双向可靠字节流，双方都需要知道：①对方选择了什么初始序号；②自己发出的序号信息确实被对方收到。两次交互后 Server 已确认 Client 的 SYN，但 Client 对 Server SYN 的确认还没有回到 Server，因此三次是常规 active/passive open 下同步双方状态的最小自然流程。

为什么不是“验证双方收发能力”一句话

“收发能力”过于模糊：网络路径可能在握手后马上变化，三次握手也无法永久证明链路可靠。它真正能证明的是这些具体 handshake message 已经按序号/ACK 语义到达，从而允许状态机安全推进。

四次是否更安全

没有必要把 Server 的 SYN 与 ACK 拆成两个 packet，它们可以合并成 SYN+ACK，因此一般是三次。特殊 simultaneous open 等路径可能呈现不同 packet 组合，但不改变双方需要同步序号与确认的核心不变量。

线上案例推演

面试官问“第二次 SYN+ACK 丢了怎么办”，应立即回到状态机和 timer：Client 没看到 SYN+ACK 仍在 SYN-SENT，Server 仍在 SYN-RECEIVED，双方会按各自重传逻辑继续尝试，而不是说“握手自动变两次”。

面试现场推荐回答结构

  1. 先给结论：用 2-4 句话回答“为什么 TCP 需要三次握手，不能两次？”，避免一上来陷入历史背景。
  2. 再给机制：围绕 Handshake、旧报文 说明关键状态、字段或数据路径。
  3. 补 Why：解释为什么协议/内核这样设计，以及少一步或改一种设计会出现什么正确性/性能问题。
  4. 落到证据：至少给出一个可观察信号或实验，例如 ss -tanpi。

面试官常见追问（PDF 原题 + 回答方向）

追问 1：为什么四次握手不是必须？

参考回答：Server 的 SYN 与对 Client SYN 的 ACK 可以合并成一个 SYN+ACK，所以无需机械拆成四次；三次已完成双方 ISN/ACK 同步。

追问 2：如果第二次 SYN+ACK 丢了会怎样？

参考回答：Client 没收到 SYN+ACK 就仍在 SYN-SENT；Server 会按重传定时器重发 SYN+ACK，Client 也可能重发 SYN，直到成功或超时。

追问 3：为什么 QUIC 建连逻辑不同？

参考回答：QUIC 将传输建立与 TLS 1.3 深度集成，并以 Connection ID/packet number 为核心，不复用 TCP 的 SYN/ACK 状态机，所以交互消息和 RTT 模型不同。

高频易错点（PDF 原内容）

  • ❌ 回答“因为 RFC 规定了三次”。
  • ❌ 用“确认收发能力”一句话结束，无法解释旧 SYN。

动手验证 / 抓包实验（PDF 原内容）

画出“旧 SYN 延迟到达服务端”的两次握手反例，再说明第三次确认如何避免服务端单方面误判。

实验验收标准

能从 TCP 状态、Seq/Ack、重传/窗口和应用 close/read/write 行为形成一致时间线。

建议把实验结果记录成：命令/抓包过滤器 → 观察到的字段/状态 → 与理论的对应关系 → 仍不能证明的部分。这比只保存一张截图更接近线上排障习惯。
