TCP 可靠性由哪些机制共同保证？

定位：基础 · 面试频率：★★★★★ · 标签：可靠传输 / 重传 / SACK
本章：第三章 TCP 连接、状态机与可靠性 · 返回总目录

面试官到底在考什么

这道题不只考定义。面试官通常希望确认你能否把 可靠传输 / 重传 / SACK 放进真实协议栈/系统调用/故障场景中解释，并且在追问发生时仍保持同一个心智模型，而不是切换成互相矛盾的八股结论。

30 秒标准回答（PDF 原内容）

TCP 的可靠性不是单一“重传”，而是序号、ACK、校验、发送/接收缓存、RTO、快速重传、SACK、重排序、流量控制与拥塞控制共同构成。它保证的是有序字节流交付，不保证应用业务一定处理成功。

深度解析：Know-How + Know-Why（PDF 原内容）

  1. checksum 检测传输错误；序号/ACK 处理丢失、重复和乱序。
  2. RTO 处理长时间未确认；dup ACK/SACK 提高部分丢包恢复效率。
  3. socket ACK 只代表对端 TCP stack 接收，不代表数据库事务已提交。

二次深化：工程上还必须知道什么

本题的高级回答应主动说明适用范围和观测边界：协议规范描述的是语义与状态机，真实 Linux/云网络实现还会受到内核版本、offload、中间盒、代理和应用框架的影响。面试中若无法确定实现细节，应明确“规范保证”和“常见实现”分别是什么。

本章共同的工程视角

  • TCP 是有状态的可靠字节流；状态机、序号空间、ACK 语义和定时器是理解所有 TCP 题的共同底座。
  • 不要把“内核收到”“对端 TCP 确认”“对端应用读到”“业务处理成功”混成一个层次。
  • 排障时必须把主动关闭方、连接状态、Seq/Ack 时间线和应用生命周期放在一起看。

V2 深入：TCP 可靠的是字节流交付，不是业务事务语义

第一性原理

TCP 的可靠性由 checksum、sequence/ACK、重传、乱序重组、duplicate suppression、流控和拥塞控制等共同组成。它保证在连接有效时向应用提供有序字节流，但无法告诉 Client 某个业务操作是否已经 commit。

“最后请求是否执行”难题

Client 发送支付请求后连接 reset：请求可能没到 Server、到达但未被应用读、应用已处理但 response 丢失、数据库已 commit 但 ACK 未回。TCP 无法区分这些业务状态，因此需要 request ID、idempotency key、事务状态查询等应用协议设计。

SACK/重传的边界

SACK 提升丢包恢复效率，但不会改变 cumulative ACK 的基本语义；TCP checksum 也不是端到端内容真实性机制，不能替代 TLS/application checksum。

线上案例推演

订单 API 因 timeout 自动重试却产生重复扣款，本质不是“TCP 不可靠”，而是业务把 transport uncertainty 错当成“请求一定未执行”。正确方案是幂等 key + 原子状态持久化。

面试现场推荐回答结构

  1. 先给结论：用 2-4 句话回答“TCP 可靠性由哪些机制共同保证？”，避免一上来陷入历史背景。
  2. 再给机制：围绕 可靠传输、重传、SACK 说明关键状态、字段或数据路径。
  3. 补 Why：解释为什么协议/内核这样设计，以及少一步或改一种设计会出现什么正确性/性能问题。
  4. 落到证据：至少给出一个可观察信号或实验，例如 ss -tanpi。

面试官常见追问（PDF 原题 + 回答方向）

追问 1：TCP 为什么不能保证“Exactly Once 业务语义”？

参考回答：TCP 只保证有序字节流，不知道‘支付一次’这类业务事务。timeout/reset 时 Client 不能确定请求是否已被应用/数据库执行，因此需要幂等键、状态查询等上层机制。

追问 2：连接断开后如何判断最后一个请求是否被服务端执行？

参考回答：仅凭连接断开无法判定：请求可能没到、已到未处理、已处理但响应丢失。正确做法是让业务请求有唯一 ID，并能查询/重试同一语义结果。

追问 3：SACK 为什么在高丢包/大窗口下重要？

参考回答：大窗口中一次可能丢多个 segment；SACK 告诉 sender receiver 已缓存哪些非连续范围，使其更精确恢复缺口，避免只靠累计 ACK 重传过多数据。

高频易错点（PDF 原内容）

  • ❌ 把 TCP 可靠性等同于“网络绝不丢包”。
  • ❌ 把 TCP ACK 当作业务 ACK。

动手验证 / 抓包实验（PDF 原内容）

设计一个“扣款 RPC”故障场景：客户端发完后连接断开，讨论为什么必须使用幂等键/业务确认。

实验验收标准

能从 TCP 状态、Seq/Ack、重传/窗口和应用 close/read/write 行为形成一致时间线。

建议把实验结果记录成：命令/抓包过滤器 → 观察到的字段/状态 → 与理论的对应关系 → 仍不能证明的部分。这比只保存一张截图更接近线上排障习惯。
