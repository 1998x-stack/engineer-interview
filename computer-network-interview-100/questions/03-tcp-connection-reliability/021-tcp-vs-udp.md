# 021. TCP 与 UDP 的本质区别是什么？不要只说“可靠/不可靠”。

> **定位**：基础 · **面试频率**：★★★★★ · **标签**：TCP / UDP / 语义  
> **本章**：[第三章 TCP 连接、状态机与可靠性](README.md) · [返回总目录](../../README.md)

## 面试官到底在考什么

这道题不只考定义。面试官通常希望确认你能否把 **TCP / UDP / 语义** 放进真实协议栈/系统调用/故障场景中解释，并且在追问发生时仍保持同一个心智模型，而不是切换成互相矛盾的八股结论。

## 30 秒标准回答（PDF 原内容）

> TCP 提供面向连接、可靠、有序的字节流，并实现重传、流量控制与拥塞控制；UDP 提供无连接的报文数据报服务，保留消息边界但不保证送达、顺序或去重。应用应依据语义和时延/控制需求选择，而不是简单说“TCP 慢、UDP 快”。

## 深度解析：Know-How + Know-Why（PDF 原内容）

1. TCP 的可靠性来自 ACK、序号、重传、接收缓存等组合。
2. UDP 没有内建拥塞控制，但基于 UDP 的上层协议（如 QUIC）必须自己实现。
3. TCP 没有消息边界，UDP 保留 datagram 边界。

## 二次深化：工程上还必须知道什么

本题的高级回答应主动说明适用范围和观测边界：协议规范描述的是语义与状态机，真实 Linux/云网络实现还会受到内核版本、offload、中间盒、代理和应用框架的影响。面试中若无法确定实现细节，应明确“规范保证”和“常见实现”分别是什么。

### 本章共同的工程视角

- TCP 是有状态的可靠字节流；状态机、序号空间、ACK 语义和定时器是理解所有 TCP 题的共同底座。
- 不要把“内核收到”“对端 TCP 确认”“对端应用读到”“业务处理成功”混成一个层次。
- 排障时必须把主动关闭方、连接状态、Seq/Ack 时间线和应用生命周期放在一起看。

## V2 深入：TCP/UDP 的区别是“服务抽象”，不是两个形容词

### 第一性原理

- TCP 向应用提供**有序可靠字节流**与连接状态；UDP 提供**无连接数据报**，保留消息边界但不内建可靠、排序、流控与拥塞恢复语义。
- TCP 的可靠性来自序号、ACK、重传、接收重组和校验等状态；这些能力带来额外延迟、内存和 head-of-line 约束。
- UDP 的“简单”意味着上层可以自行选择需要哪些机制，而不是“UDP 天生更快”。QUIC 正是在 UDP 之上重新构建现代传输能力。

### 选型维度

面试中应从 **可靠性要求、时延预算、消息边界、拥塞控制、连接迁移、部署兼容性**回答，而不是背“视频用 UDP、网页用 TCP”。实时媒体可以容忍部分过期 packet 丢失，因此常选择 UDP + 自定义恢复/FEC；文件传输则通常需要完整可靠交付。

### 边界与反例

- UDP checksum/链路 CRC 不提供应用语义可靠性；TCP 可靠也不等于业务 Exactly Once。
- DNS 普通请求常用 UDP，但大 response、zone transfer、DoT/DoH 等可以使用其他 transport。
- QUIC 的拥塞控制、可靠 stream 和 TLS 安全都是 QUIC 自己提供，不是 UDP 获得了这些能力。

### 线上案例推演

若 UDP 业务“偶发音视频花屏”，应观察 packet loss、jitter、reordering、应用 jitter buffer/FEC；把它当 TCP retransmission 问题会走错诊断路径。

## 面试现场推荐回答结构

1. **先给结论**：用 2-4 句话回答“TCP 与 UDP 的本质区别是什么？不要只说“可靠/不可靠”。”，避免一上来陷入历史背景。
2. **再给机制**：围绕 TCP、UDP、语义 说明关键状态、字段或数据路径。
3. **补 Why**：解释为什么协议/内核这样设计，以及少一步或改一种设计会出现什么正确性/性能问题。
4. **落到证据**：至少给出一个可观察信号或实验，例如 `ss -tanpi`。

## 可观测性：如何证明自己的判断

| 层次 | 工具 / 信号 |
|---|---|
| 首选 | `ss -tanpi` |
| 辅助 | `tcpdump -nn -S` |
| 性能/路径 | `nstat -az` |
| 深挖 | `Wireshark TCP Stream Graph` |

**关键原则**：先用低成本指标定位层次，再用抓包/trace/内核指标证明。不要看到一个 `Retransmission`、`TIME_WAIT` 或 `5xx` 就直接宣布根因。

## 面试官常见追问（PDF 原题 + 回答方向）

### 追问 1：实时音视频为什么常倾向 UDP？

**参考回答**：实时音视频中旧 packet 可能很快失去价值，应用更愿意自己控制重传/FEC/jitter buffer，避免 TCP 严格有序导致一个丢包阻塞后续媒体数据。

### 追问 2：DNS 为什么既可 UDP 也可 TCP？

**参考回答**：DNS 同时支持 UDP/TCP：普通小查询常用 UDP；truncation、大响应、zone transfer 等会用 TCP，现代还可用 DoT/DoH。

### 追问 3：QUIC 为什么建立在 UDP 上？

**参考回答**：UDP 提供可部署的 datagram substrate，QUIC 在用户态自行实现可靠 stream、TLS、拥塞控制和迁移，避免直接修改内核 TCP 与 middlebox ossification。

## 高频易错点（PDF 原内容）

- ❌ 说 UDP 一定更快。
- ❌ 认为 UDP 不需要任何拥塞控制责任。

## 动手验证 / 抓包实验（PDF 原内容）

用 `nc -l`/Python 分别写一个 TCP 与 UDP echo，观察多次 send 的边界行为。

### 实验验收标准

能从 TCP 状态、Seq/Ack、重传/窗口和应用 close/read/write 行为形成一致时间线。

建议把实验结果记录成：**命令/抓包过滤器 → 观察到的字段/状态 → 与理论的对应关系 → 仍不能证明的部分**。这比只保存一张截图更接近线上排障习惯。
