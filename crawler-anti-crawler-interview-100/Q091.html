CRAWLER · 91 / 100

设计一个每天抓取 1 亿网页的系统。

难度： ★★★★★
章节： 第十章 高级系统设计
定位： 面试回答 + 原理理解 + 生产工程。

考察点

  • 容量估算
  • 分布式 Frontier
  • 限速/容错/存储

60-90 秒推荐回答

先做量级：100,000,000 / 86,400 ≈ 1,157 pages/s 平均吞吐。若按 3 倍峰值设计，抓取层约 3,500 pages/s；再根据平均响应大小估带宽和对象存储写入。

架构：Seed → URL Normalize/Dedup → Distributed Frontier → Domain-aware Scheduler → Fetcher Pool → Raw Object Storage → Parser/Validation → Content Dedup/Entity Resolution → Data Lake/Serving。

控制平面独立管理 robots、per-host token bucket、retry/circuit breaker、优先级和 recrawl；数据平面专注 fetch/parse。

Seed → Normalize/Dedup → Frontier → Host Scheduler → Fetchers
                                               ↓
                                         Raw Object Store
                                               ↓
                                    Parser → Validate → Lake

原理深挖

容量还要乘失败重试、动态页面比例和平均页面大小。例如 500KB/page，则 1 亿页原始体量约 50TB/day（未压缩、未扣压缩差异）。

如果 5% 页面走浏览器，Browser Pool 是单独容量模型，不能按普通 fetcher QPS 估算。

容量估算

  • 1 亿/天平均约 1157 pages/s；设计时至少用峰值系数、平均响应大小、重试率和 browser 比例反推带宽/CPU/存储。
  • 系统瓶颈往往不是平均 QPS，而是热点域名、突发、解析 CPU 和存储写入。

关键表达式 / 心智模型：

avg_qps = pages_per_day / 86400; peak_qps = avg_qps * peak_factor

GitHub 增强版：进一步理解

  1. 系统设计题先做量级估算，再画控制平面、状态平面、数据平面。没有容量数字的架构图很难判断是否真的可行。
  2. 任何大规模 crawler 都必须同时回答 coverage、freshness、politeness、cost、fault tolerance、quality、compliance 七个目标；只回答吞吐不完整。
  3. 优秀答案会明确失败模式与降级策略：队列爆炸、热点域名、浏览器 OOM、远端 429/503、parser drift、存储延迟、策略变更分别如何处理。

高级面试扩展

1. 核心边界

系统设计题不能只画组件。先给假设和量级，再定义目标函数与硬约束，然后拆 Control/State/Data Plane；最后用故障模式、SLO 和成本验证设计。

针对 设计一个每天抓取 1 亿网页的系统。，面试时建议先明确讨论边界：容量估算、分布式 Frontier、限速/容错/存储。如果不先定义这些边界，后面的“最佳实践”很容易变成只对某个库、某个站点或某个规模成立的经验。

2. 机制链路

Capacity Estimate → Goals/Constraints → URL/Policy State → Scheduler/Fetcher → Raw/Parse/Quality → Recrawl → Observability/Compliance。架构要同时回答 coverage、freshness、politeness、cost、fault tolerance、quality、compliance。

3. 本题进一步深挖

  1. 1e8/day 平均约 1.16k pages/s；设计机器数不能只除以单机 QPS，还要乘 peak factor、retry、browser fallback，并用实际 p95 服务时间与资源利用率估并发。

4. Trade-off 矩阵

决策维度 收益 代价 / 风险
Coverage vs Freshness 抓更多新 URL 重要页面更新频率可能下降
HTTP vs Browser HTTP 成本低 动态页面需高成本 render
一致性 vs 扩展性 全局状态准确 跨地域/十亿级协调昂贵

面试中不要只说“方案 A 更好”。更专业的表达是：在什么约束下 A 优于 B；规模、延迟、准确性或合规约束变化后，决策是否需要反转。

5. 典型失败模式（FMEA）

Failure Mode 常见原因 检测 / 缓解
容量低估 只算平均 QPS 加入 peak/retry/browser fallback/retention
全局扩容放大 host QPS worker 增加但预算未集中 host-aware global budget
状态不可重建 无 raw/provenance/checkpoint 数据与状态分层、可 replay

6. 如何验证方案

用容量模型 + 压测 + chaos + replay 验证。要求能回答“机器翻倍后谁先成为瓶颈”“某层完全故障时怎么降级”“恢复后是否会造成重复/漏抓”。

建议至少覆盖三类验证：

  • Correctness：协议/算法/业务语义是否正确；
  • Resilience：超时、重试、进程崩溃、依赖变慢时是否可恢复；
  • Scale：数据量或并发扩大 10 倍时，状态、内存、网络和远端预算哪个先成为瓶颈。

7. 高级候选人的回答结构

  1. 先给定义/结论：20 秒内回答题面，不绕圈。
  2. 讲机制：用状态机、数据流或关键公式解释为什么。
  3. 讲 Trade-off：至少指出一个“收益 ↔ 代价”。
  4. 落到生产：给出一个指标、一个失败模式、一个验证方式。
  5. 主动给边界：说明什么规模/场景下需要换方案。

8. 实战演练

先做容量估算，再画 Control/State/Data Plane；给出三种故障（热点站、存储慢、浏览器池崩溃）的降级与恢复路径。

完成后尝试用 3 分钟口述 + 1 张架构/状态图 + 3 个指标 复盘。如果只能写代码却说不清约束、失败模式和验证方法，通常还没有达到高级面试要求。

工程化落地

设计 / Review Checklist

  • [ ] 先估算容量与峰值
  • [ ] 画 control/state/data planes
  • [ ] 列出 SLO 与约束
  • [ ] 明确故障模式与降级
  • [ ] 计算成本并设计扩缩容

建议监控的指标

  • useful pages/s
  • cost per useful page
  • freshness SLA
  • host-budget violations
  • replay recovery time

示例 / 伪代码

capacity inputs:
  pages/day
  peak_factor
  avg_response_bytes
  retry_ratio
  browser_fallback_ratio
  parse_cpu_ms/page
  retention_days

outputs:
  peak fetch QPS
  network egress/ingress
  fetcher/browser/parser worker count
  raw storage/day
  frontier & dedup state size

常见误区与 Gotchas

  • 只说“Kafka + Redis + Scrapy 集群”没有任何容量数字。
  • 忽略 per-domain 限速导致全局吞吐与站点约束冲突。

补充检查：

  • 不要把单机可运行等同于生产可扩展。
  • 不要只描述“怎么做”，还要说明 为什么、代价、失败时如何观测。
  • 涉及站点侧风控/挑战时，本仓库以防守与合规设计为边界，不提供规避访问控制或验证码的操作步骤。

面试追问拆解

追问 1：如何把 1157 pages/s 转成机器数？

参考回答： 先算 peak QPS，再用 required_concurrency ≈ peak_qps × p95_service_time；除以单 worker 可承载并发并加 30%-50% headroom。还要分别受 CPU、网络和连接数限制，最终压测校准。

面试展开： 说明关键假设 → 给机制/数据结构或状态机 → 指出一个 trade-off → 补一个生产指标或失败模式。

追问 2：存储 30 天 raw data 大约多少？

参考回答： pages/day × avg_compressed_raw_bytes × 30 × replication_factor。例如平均压缩 100KB、1e8/day、30 天约 300TB 原始数据（未计副本/元数据）；平均 body 是最敏感参数。

面试展开： 说明关键假设 → 给机制/数据结构或状态机 → 指出一个 trade-off → 补一个生产指标或失败模式。

追问 3：如何保证重要站点 freshness？

参考回答： 按站点/URL importance 建 freshness class，为高价值站点保留最低 recrawl budget；调度优先级综合 stale age、change probability、价值和抓取成本。
