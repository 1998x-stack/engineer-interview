CRAWLER · 96 / 100

设计一个“HTTP + Browser”混合爬虫。

难度： ★★★★★
章节： 第十章 高级系统设计
定位： 面试回答 + 原理理解 + 生产工程。

考察点

  • Fast path / slow path
  • 内容能力检测
  • Browser Queue

60-90 秒推荐回答

所有 URL 先走 HTTP Fetch。Classifier/规则判断初始 HTML 是否含足够数据：若可解析则进入 fast parser；否则进入 Browser Queue，由 Browser Pool 渲染后再解析。

需要防止重复升级：记录 render_required/page_type，缓存静态判断；Browser Pool 采用 Context 隔离，设置超时、TTL、资源限制和健康检查。

原理深挖

关键 KPI 是 Browser Path Ratio，因为 browser 成本通常高一个数量级以上。可以通过 SSR state、JSON-LD、授权结构化接口等方式降低该比例。

双路径架构

  • HTTP 作为 fast path，检测数据不足/需要渲染时才升级到 Browser Queue。
  • 要监控 browser_fallback_rate；它突然上升通常意味着页面架构变化或 HTTP extractor 退化。

GitHub 增强版：进一步理解

  1. 系统设计题先做量级估算，再画控制平面、状态平面、数据平面。没有容量数字的架构图很难判断是否真的可行。
  2. 任何大规模 crawler 都必须同时回答 coverage、freshness、politeness、cost、fault tolerance、quality、compliance 七个目标；只回答吞吐不完整。
  3. 优秀答案会明确失败模式与降级策略：队列爆炸、热点域名、浏览器 OOM、远端 429/503、parser drift、存储延迟、策略变更分别如何处理。

高级面试扩展

1. 核心边界

系统设计题不能只画组件。先给假设和量级，再定义目标函数与硬约束，然后拆 Control/State/Data Plane；最后用故障模式、SLO 和成本验证设计。

针对 设计一个“HTTP + Browser”混合爬虫。，面试时建议先明确讨论边界：Fast path / slow path、内容能力检测、Browser Queue。如果不先定义这些边界，后面的“最佳实践”很容易变成只对某个库、某个站点或某个规模成立的经验。

2. 机制链路

Capacity Estimate → Goals/Constraints → URL/Policy State → Scheduler/Fetcher → Raw/Parse/Quality → Recrawl → Observability/Compliance。架构要同时回答 coverage、freshness、politeness、cost、fault tolerance、quality、compliance。

3. 本题进一步深挖

  1. 混合架构的关键 KPI 是 browser fallback ratio 与 false-upgrade/false-downgrade。可以基于初始 HTML、脚本标记、历史成功率和数据缺失训练 render-required classifier。

4. Trade-off 矩阵

决策维度 收益 代价 / 风险
Coverage vs Freshness 抓更多新 URL 重要页面更新频率可能下降
HTTP vs Browser HTTP 成本低 动态页面需高成本 render
一致性 vs 扩展性 全局状态准确 跨地域/十亿级协调昂贵

面试中不要只说“方案 A 更好”。更专业的表达是：在什么约束下 A 优于 B；规模、延迟、准确性或合规约束变化后，决策是否需要反转。

5. 典型失败模式（FMEA）

Failure Mode 常见原因 检测 / 缓解
容量低估 只算平均 QPS 加入 peak/retry/browser fallback/retention
全局扩容放大 host QPS worker 增加但预算未集中 host-aware global budget
状态不可重建 无 raw/provenance/checkpoint 数据与状态分层、可 replay

6. 如何验证方案

用容量模型 + 压测 + chaos + replay 验证。要求能回答“机器翻倍后谁先成为瓶颈”“某层完全故障时怎么降级”“恢复后是否会造成重复/漏抓”。

建议至少覆盖三类验证：

  • Correctness：协议/算法/业务语义是否正确；
  • Resilience：超时、重试、进程崩溃、依赖变慢时是否可恢复；
  • Scale：数据量或并发扩大 10 倍时，状态、内存、网络和远端预算哪个先成为瓶颈。

7. 高级候选人的回答结构

  1. 先给定义/结论：20 秒内回答题面，不绕圈。
  2. 讲机制：用状态机、数据流或关键公式解释为什么。
  3. 讲 Trade-off：至少指出一个“收益 ↔ 代价”。
  4. 落到生产：给出一个指标、一个失败模式、一个验证方式。
  5. 主动给边界：说明什么规模/场景下需要换方案。

8. 实战演练

先做容量估算，再画 Control/State/Data Plane；给出三种故障（热点站、存储慢、浏览器池崩溃）的降级与恢复路径。

完成后尝试用 3 分钟口述 + 1 张架构/状态图 + 3 个指标 复盘。如果只能写代码却说不清约束、失败模式和验证方法，通常还没有达到高级面试要求。

工程化落地

设计 / Review Checklist

  • [ ] 先估算容量与峰值
  • [ ] 画 control/state/data planes
  • [ ] 列出 SLO 与约束
  • [ ] 明确故障模式与降级
  • [ ] 计算成本并设计扩缩容

建议监控的指标

  • useful pages/s
  • cost per useful page
  • freshness SLA
  • host-budget violations
  • replay recovery time

示例 / 伪代码

URL -> HTTP Fetch -> Extractability Check
                    | yes -> Parser -> Validate -> Store
                    | no  -> Browser Queue -> Browser Pool -> Parser

监控：browser_fallback_rate、browser_cost/page、HTTP-vs-browser result parity

常见误区与 Gotchas

  • 把 browser 当默认路径。

补充检查：

  • 不要把单机可运行等同于生产可扩展。
  • 不要只描述“怎么做”，还要说明 为什么、代价、失败时如何观测。
  • 涉及站点侧风控/挑战时，本仓库以防守与合规设计为边界，不提供规避访问控制或验证码的操作步骤。

面试追问拆解

追问 1：如何训练 render-required classifier？

参考回答： 标签定义为“HTTP fast path 是否能满足目标 Schema/正确性”。特征可包括 initial HTML 字段、脚本框架/内嵌 state、历史 browser-only 成功率、页面类型；优化 false-upgrade 成本与 false-downgrade 数据损失。

面试展开： 说明关键假设 → 给机制/数据结构或状态机 → 指出一个 trade-off → 补一个生产指标或失败模式。

追问 2：HTTP 与 Browser 结果不一致时保留哪个？

参考回答： 保存两者并定义权威规则。Browser 展示值可能经过前端计算，HTTP API 更接近源数据；按业务语义对齐，冲突时进入 validation/quarantine 而不是静默任选一个。

面试展开： 说明关键假设 → 给机制/数据结构或状态机 → 指出一个 trade-off → 补一个生产指标或失败模式。

追问 3：Browser queue 积压如何 backpressure？

参考回答： Browser queue 超阈值时降低 render-required 任务 intake、提高判定门槛、优先高价值 URL，并把压力反馈给 frontier；不能让 browser backlog 无限增长。
