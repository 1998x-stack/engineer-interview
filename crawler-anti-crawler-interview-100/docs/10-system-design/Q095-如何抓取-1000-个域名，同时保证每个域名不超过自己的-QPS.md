# Q095 如何抓取 1000 个域名，同时保证每个域名不超过自己的 QPS？

> **难度：** ★★★★★  
> **章节：** 第十章  高级系统设计  
> **定位：** 面试回答 + 原理理解 + 生产工程。

## 考察点

- per-host queue
- token bucket
- eligible-host scheduling

## 60-90 秒推荐回答

每个 host 有自己的 queue 和 token bucket（r_h, B_h），Global Scheduler 只从当前有 token 且 next_allowed_fetch 已到的 host 中选择任务，再分发给 Fetcher。

这样 worker 数量可以横向扩展，但 host 总 QPS 不随 worker 数量放大。

## 原理深挖

为了避免扫描 1000 个 host，可以用最小堆按 next_eligible_time 管理 host；热门 host 仍保持一个共享 budget。

### Per-host 调度

- 每个 host 一个 token bucket/eligible_time，Global Scheduler 只挑当前可执行 host。
- 多 worker 不能各自独立 sleep，否则总 QPS 会随 worker 数扩大。

### GitHub 增强版：进一步理解

1. 系统设计题先做量级估算，再画控制平面、状态平面、数据平面。没有容量数字的架构图很难判断是否真的可行。
2. 任何大规模 crawler 都必须同时回答 coverage、freshness、politeness、cost、fault tolerance、quality、compliance 七个目标；只回答吞吐不完整。
3. 优秀答案会明确失败模式与降级策略：队列爆炸、热点域名、浏览器 OOM、远端 429/503、parser drift、存储延迟、策略变更分别如何处理。

## 高级面试扩展

### 1. 核心边界

系统设计题不能只画组件。先给假设和量级，再定义目标函数与硬约束，然后拆 Control/State/Data Plane；最后用故障模式、SLO 和成本验证设计。

针对 **如何抓取 1000 个域名，同时保证每个域名不超过自己的 QPS？**，面试时建议先明确讨论边界：per-host queue、token bucket、eligible-host scheduling。如果不先定义这些边界，后面的“最佳实践”很容易变成只对某个库、某个站点或某个规模成立的经验。

### 2. 机制链路

`Capacity Estimate → Goals/Constraints → URL/Policy State → Scheduler/Fetcher → Raw/Parse/Quality → Recrawl → Observability/Compliance`。架构要同时回答 coverage、freshness、politeness、cost、fault tolerance、quality、compliance。

### 3. 本题进一步深挖

1. 正确抽象是 per-host queue + token bucket + eligible-time scheduler + weighted fairness。扩容 scheduler 时 host budget 必须有唯一权威或可证明的分布式配额。

### 4. Trade-off 矩阵

| 决策维度 | 收益 | 代价 / 风险 |
|---|---|---|
| Coverage vs Freshness | 抓更多新 URL | 重要页面更新频率可能下降 |
| HTTP vs Browser | HTTP 成本低 | 动态页面需高成本 render |
| 一致性 vs 扩展性 | 全局状态准确 | 跨地域/十亿级协调昂贵 |

面试中不要只说“方案 A 更好”。更专业的表达是：**在什么约束下 A 优于 B；规模、延迟、准确性或合规约束变化后，决策是否需要反转。**

### 5. 典型失败模式（FMEA）

| Failure Mode | 常见原因 | 检测 / 缓解 |
|---|---|---|
| 容量低估 | 只算平均 QPS | 加入 peak/retry/browser fallback/retention |
| 全局扩容放大 host QPS | worker 增加但预算未集中 | host-aware global budget |
| 状态不可重建 | 无 raw/provenance/checkpoint | 数据与状态分层、可 replay |

### 6. 如何验证方案

用容量模型 + 压测 + chaos + replay 验证。要求能回答“机器翻倍后谁先成为瓶颈”“某层完全故障时怎么降级”“恢复后是否会造成重复/漏抓”。

建议至少覆盖三类验证：

- **Correctness**：协议/算法/业务语义是否正确；
- **Resilience**：超时、重试、进程崩溃、依赖变慢时是否可恢复；
- **Scale**：数据量或并发扩大 10 倍时，状态、内存、网络和远端预算哪个先成为瓶颈。

### 7. 高级候选人的回答结构

1. **先给定义/结论**：20 秒内回答题面，不绕圈。
2. **讲机制**：用状态机、数据流或关键公式解释为什么。
3. **讲 Trade-off**：至少指出一个“收益 ↔ 代价”。
4. **落到生产**：给出一个指标、一个失败模式、一个验证方式。
5. **主动给边界**：说明什么规模/场景下需要换方案。

### 8. 实战演练

> 先做容量估算，再画 Control/State/Data Plane；给出三种故障（热点站、存储慢、浏览器池崩溃）的降级与恢复路径。

完成后尝试用 **3 分钟口述 + 1 张架构/状态图 + 3 个指标** 复盘。如果只能写代码却说不清约束、失败模式和验证方法，通常还没有达到高级面试要求。

### 示例 / 伪代码

```text
HostState {
  next_eligible_at
  token_bucket
  robots_policy
  failure_score
  priority_queue<URL>
}

GlobalScheduler:
  1. 从 eligible-host heap 取可执行 host
  2. 消耗 host token
  3. 从该 host 的 URL queue 取最高优先级 URL
  4. 更新 next_eligible_at 并重新入 heap
```

## 常见误区与 Gotchas

- 每个 worker 自己 sleep，导致全局预算乘以 worker 数。

补充检查：

- 不要把单机可运行等同于生产可扩展。
- 不要只描述“怎么做”，还要说明 **为什么、代价、失败时如何观测**。
- 涉及站点侧风控/挑战时，本仓库以防守与合规设计为边界，不提供规避访问控制或验证码的操作步骤。

## 面试追问拆解
### 追问 1：host scheduler 单点如何扩展？

**参考回答：** 对 host 做一致性分片/单归属 scheduler shard，每 shard 管本地 host heap；上层只做 shard 路由。扩容迁移 host state 时要保持 token/eligible time 不重复。

**面试展开：** 说明关键假设 → 给机制/数据结构或状态机 → 指出一个 trade-off → 补一个生产指标或失败模式。

### 追问 2：域名权重不同如何实现 weighted fairness？

**参考回答：** 可用 Weighted Fair Queuing/Deficit Round Robin 给 domain class 权重；每 host 自己的 token bucket/eligible time 仍是硬约束，权重只决定可抓 host 间的相对份额。

**面试展开：** 说明关键假设 → 给机制/数据结构或状态机 → 指出一个 trade-off → 补一个生产指标或失败模式。
