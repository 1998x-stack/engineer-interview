# Q098 设计一个企业级反爬系统。

> **难度：** ★★★★★  
> **章节：** 第十章  高级系统设计  
> **定位：** 面试回答 + 原理理解 + 生产工程。

## 考察点

- Edge 低延迟
- Feature/Model/Policy 分层
- 误报治理

## 60-90 秒推荐回答

数据面：Request → Edge feature extraction → session/account/reputation state → rules + model → risk score → policy engine。执行动作包括 allow、throttle、challenge、block。

状态面：维护速率、IP/ASN reputation、账户历史、设备/session 摘要；控制面：模型版本、规则发布、allowlist、阈值、shadow/A-B 和 rollback。

可观测性必须记录 feature version、score、decision reason、challenge outcome 和申诉结果。

## 原理深挖

延迟预算通常非常紧，因此 expensive feature 不能同步全算；采用 edge cache、分层模型、异步 enrichment。

模型与规则的最终目标是最小化业务成本：攻击损失 + 误伤损失 + challenge UX 成本。

### 反爬平台分层

- Edge feature -> feature aggregation -> rules/model -> risk score -> policy action -> feedback/analytics。
- 上线必须提供 shadow mode、rule explainability、allowlist、appeal/rollback 与 endpoint-specific policy。

### GitHub 增强版：进一步理解

1. 系统设计题先做量级估算，再画控制平面、状态平面、数据平面。没有容量数字的架构图很难判断是否真的可行。
2. 任何大规模 crawler 都必须同时回答 coverage、freshness、politeness、cost、fault tolerance、quality、compliance 七个目标；只回答吞吐不完整。
3. 优秀答案会明确失败模式与降级策略：队列爆炸、热点域名、浏览器 OOM、远端 429/503、parser drift、存储延迟、策略变更分别如何处理。

## 高级面试扩展

### 1. 核心边界

系统设计题不能只画组件。先给假设和量级，再定义目标函数与硬约束，然后拆 Control/State/Data Plane；最后用故障模式、SLO 和成本验证设计。

针对 **设计一个企业级反爬系统。**，面试时建议先明确讨论边界：Edge 低延迟、Feature/Model/Policy 分层、误报治理。如果不先定义这些边界，后面的“最佳实践”很容易变成只对某个库、某个站点或某个规模成立的经验。

### 2. 机制链路

`Capacity Estimate → Goals/Constraints → URL/Policy State → Scheduler/Fetcher → Raw/Parse/Quality → Recrawl → Observability/Compliance`。架构要同时回答 coverage、freshness、politeness、cost、fault tolerance、quality、compliance。

### 3. 本题进一步深挖

1. 企业级架构要把 Feature、Detection、Policy、Enforcement 分离，支持规则与模型共存、shadow/canary、allowlist、跨地域信誉和审计。

### 4. Trade-off 矩阵

| 决策维度 | 收益 | 代价 / 风险 |
|---|---|---|
| Coverage vs Freshness | 抓更多新 URL | 重要页面更新频率可能下降 |
| HTTP vs Browser | HTTP 成本低 | 动态页面需高成本 render |
| 一致性 vs 扩展性 | 全局状态准确 | 跨地域/十亿级协调昂贵 |

面试中不要只说“方案 A 更好”。更专业的表达是：**在什么约束下 A 优于 B；规模、延迟、准确性或合规约束变化后，决策是否需要反转。**

### 5. 典型失败模式（FMEA）

| Failure Mode | 常见原因 | 检测 / 缓解 |
|---|---|---|
| 容量低估 | 只算平均 QPS | 加入 peak/retry/browser fallback/retention |
| 全局扩容放大 host QPS | worker 增加但预算未集中 | host-aware global budget |
| 状态不可重建 | 无 raw/provenance/checkpoint | 数据与状态分层、可 replay |

### 6. 如何验证方案

用容量模型 + 压测 + chaos + replay 验证。要求能回答“机器翻倍后谁先成为瓶颈”“某层完全故障时怎么降级”“恢复后是否会造成重复/漏抓”。

建议至少覆盖三类验证：

- **Correctness**：协议/算法/业务语义是否正确；
- **Resilience**：超时、重试、进程崩溃、依赖变慢时是否可恢复；
- **Scale**：数据量或并发扩大 10 倍时，状态、内存、网络和远端预算哪个先成为瓶颈。

### 7. 高级候选人的回答结构

1. **先给定义/结论**：20 秒内回答题面，不绕圈。
2. **讲机制**：用状态机、数据流或关键公式解释为什么。
3. **讲 Trade-off**：至少指出一个“收益 ↔ 代价”。
4. **落到生产**：给出一个指标、一个失败模式、一个验证方式。
5. **主动给边界**：说明什么规模/场景下需要换方案。

### 8. 实战演练

> 先做容量估算，再画 Control/State/Data Plane；给出三种故障（热点站、存储慢、浏览器池崩溃）的降级与恢复路径。

完成后尝试用 **3 分钟口述 + 1 张架构/状态图 + 3 个指标** 复盘。如果只能写代码却说不清约束、失败模式和验证方法，通常还没有达到高级面试要求。

## 工程化落地

### 设计 / Review Checklist

- [ ] 先估算容量与峰值
- [ ] 画 control/state/data planes
- [ ] 列出 SLO 与约束
- [ ] 明确故障模式与降级
- [ ] 计算成本并设计扩缩容

### 建议监控的指标

- `useful pages/s`
- `cost per useful page`
- `freshness SLA`
- `host-budget violations`
- `replay recovery time`
## 常见误区与 Gotchas

- 把系统画成“一个 ML 模型 → block”。

补充检查：

- 不要把单机可运行等同于生产可扩展。
- 不要只描述“怎么做”，还要说明 **为什么、代价、失败时如何观测**。
- 涉及站点侧风控/挑战时，本仓库以防守与合规设计为边界，不提供规避访问控制或验证码的操作步骤。

## 面试追问拆解
### 追问 1：如何做模型 shadow deployment？

**参考回答：** shadow 模型只产生 score/recommended action，不执行；与现网 outcome、人工样本和业务转化比较。达到 FPR/latency 门槛后按 1%→10% canary，并保留快速 rollback。

**面试展开：** 说明关键假设 → 给机制/数据结构或状态机 → 指出一个 trade-off → 补一个生产指标或失败模式。

### 追问 2：跨地域 reputation state 怎么同步？

**参考回答：** 高频热信誉可地域本地化并异步汇总；高风险全局事件通过事件流传播。不要每次请求跨地域强一致查询，使用版本/时间戳和冲突合并策略。

**面试展开：** 说明关键假设 → 给机制/数据结构或状态机 → 指出一个 trade-off → 补一个生产指标或失败模式。

### 追问 3：合法 crawler 如何认证？

**参考回答：** 合法 crawler 走验证身份：签名 token/API key、官方 IP/DNS 验证或 mTLS 等；认证后仍应用声明的速率/用途政策，并记录审计。
