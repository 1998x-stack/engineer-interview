Thread、Warp、Block、Grid、SM 分别是什么？

一句话核心：编程层级是 Grid→Block→Thread；硬件调度核心是 SM→Warp，warp=32 threads。

章节：第 1 章 · CUDA 执行模型与 SIMT
难度：★☆☆ · 频率：极高 · 标签：执行模型 / 基础

PDF 基线题解

30 秒答案：编程层级是 Grid→Block→Thread；硬件调度核心是 SM→Warp，warp=32 threads。

考察意图

看你能否把 CUDA 的编程抽象与 GPU 的硬件调度实体分开。

思路拆解

最容易失分的点，是把 warp 当成程序员显式创建的对象，或者说一个 block 会被拆到多个 SM 上执行。面试回答应该先 画出软件层级，再映射到硬件。

标准回答

  • Grid 是一次 kernel launch 的全部 thread blocks；Block 是线程协作与共享内存的基本范围；Thread 是 CUDA 暴露的 逻辑执行单元。
  • 硬件按 warp 调度线程。当前 NVIDIA CUDA 的 warp 为 32 threads；一个 SM 可以同时驻留多个 blocks 和 warps。
  • 一个 thread block 在其生命周期内驻留在一个 SM 上，不会跨 SM 拆分；不同 blocks 可以被动态分配到任意可用 SM。
  • 性能分析时要从“单线程做什么”升级为“同一 warp 的 32 个线程执行什么指令、访问什么地址”。

Gotchas：常见失分点

  • 把 SM 说成一个 CUDA core。
  • 认为 block 与 SM 是一一对应关系。

面试官可能继续追问

  • 为什么 warp size 会影响 block size 选择？
  • 一个 SM 能同时驻留多少 blocks 由哪些资源决定？

深入分析

把“软件层级”和“硬件层级”分开回答。Block 是资源分配/协作边界，warp 是调度/执行粒度，SM 是资源容器。一个 block 不跨 SM；但一个 SM 可同时驻留多个 block。

深入理解：从编程抽象映射到硬件状态

这一章的题，核心不是背 threadIdx/blockIdx，而是建立 logical execution → warp issue → SM residency 的映射。真正的性能问题通常发生在 warp 粒度：同一 warp 的 active mask、memory request、barrier 参与者以及 scheduler 是否有 eligible warp。

建议始终画出两张图：

Programming: Grid → Block → Thread
Hardware:    GPU → SM → Warp Scheduler → Warp(32 lanes)

当回答涉及同步时，再补一层 memory ordering：barrier 解决“谁到达了某个程序点”，memory fence/同步语义解决“谁能看见哪些写入”。

对于本题，建议至少观察：launch configuration、active warps、branch efficiency、barrier behavior。

架构视角

Volta 之后 independent thread scheduling 使隐式 warp-synchronous 假设更危险；显式使用 warp-level sync/mask。

面试回答：30 秒 / 2 分钟 / 深挖

30 秒

编程层级是 Grid→Block→Thread；硬件调度核心是 SM→Warp，warp=32 threads。

2 分钟

  1. 先给定义或结论：直接回答“是什么/为什么”。
  2. 给硬件因果：把 thread/warp、memory transaction、resource 或 pipeline 对应到硬件行为。
  3. 给 trade-off：说明优化会消耗什么资源，避免绝对化结论。
  4. 给验证方法：指出需要用 benchmark/Nsight 的哪些证据确认。

深挖时必须能回答

  • 这个结论在哪些条件下会失效？
  • 如果换 problem shape / datatype / block size，瓶颈会怎样迁移？
  • 如果从 Ampere 换到 Hopper/Blackwell，哪些稳定原理不变，哪些实现细节需要重做？
  • 你会用什么 profiler 指标证明自己的判断？

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute 收集与本题直接相关的指标：launch configuration、active warps、branch efficiency、barrier behavior。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

把 Grid/Block/Thread 当作编程抽象，把 SM/Warp 当作硬件执行抽象。Block 是资源分配与协作边界；warp 是指令发射、分支和内存合并分析的关键粒度。

2. 定量推导 / 性能模型

若 block 含 $T$ 个线程，则 warp 数为 $W=\lceil T/32\rceil$。最后一个 warp 若不足 32 线程，仍占用一个 warp 调度槽，只是部分 lane inactive。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

dim3 block(256);
dim3 grid((n + block.x - 1) / block.x);
kernel<<<grid, block>>>(...);
// 线性线程号
int tid = blockIdx.x * blockDim.x + threadIdx.x;

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • Launch Statistics：threads/block、blocks、waves per SM
  • Occupancy：active warps/SM 与 active blocks/SM
  • Source/SASS：确认热点逻辑实际以 warp 级执行

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

Warp=32 是当前 CUDA 编程模型稳定假设；Hopper/Blackwell 新增 cluster 等更高协作层级，但不会把一个普通 thread block 拆成多个 SM 并行执行。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

分别用 96、128、160、256 threads/block 运行同一轻量 kernel；记录最后一个 warp 的 lane 利用率、waves 和总时间，解释“warp 对齐”与“更多并行度”并非同一概念。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。

7. 深挖追问树

  1. 一个 block 为什么不能跨 SM？
  2. Grid 很小但 block 很大时会发生什么？
  3. Cluster 引入后，Block 与 SM 的映射关系改变了什么、没改变什么？
