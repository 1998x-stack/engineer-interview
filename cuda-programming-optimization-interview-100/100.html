给你一个比理论峰值慢 20 倍的 CUDA Kernel，你如何系统优化？

一句话核心：正确性→Systems 定位→Compute/Roofline 分类→Memory/Execution/Resource 因果链→单变量优化→重新测 量。

章节：第 10 章 · Hopper、Blackwell 与 CUDA 13.x
难度：★★★ · 频率：必问 · 标签：综合 / 性能工程

PDF 基线题解

30 秒答案：正确性→Systems 定位→Compute/Roofline 分类→Memory/Execution/Resource 因果链→单变量优化→重新测 量。

考察意图

这是整套题库的总题。面试官在看你有没有一套稳定、可证伪的性能诊断流程。

思路拆解

优秀回答应从 correctness 和端到端 profile 开始，而不是猜“肯定 memory-bound”。然后用 Roofline、memory traffic、warp stalls、resource/occupancy、instruction mix 一层层缩小瓶颈，做单变量实验，最后验证优化后的因果 指标。

标准回答

  • Step 1：建立 correctness/reference、代表性 input、稳定 benchmark。
  • Step 2：Nsight Systems 找端到端 hot spot：launch、copy、sync、NCCL 还是 kernel。
  • Step 3：Nsight Compute + Roofline 分类：bandwidth、compute、latency、small-grid/launch。
  • Step 4：Memory：coalescing、actual/requested bytes、L2 hit、bank conflict、shared reuse。
  • Step 5：Execution：eligible warps、stall reasons、divergence、instruction mix、Tensor Core usage。
  • Step 6：Resources：register、spill、shared/block、active blocks/SM、occupancy 与 ILP。
  • Step 7：按瓶颈应用 tiling/fusion/vectorization/async copy/TMA/software pipeline/precision/Tensor Core 等。
  • Step 8：重新 profile；只有“时间变短 + correctness 保持 + 指标变化符合假设”才接受优化。

Gotchas：常见失分点

  • 第一句话就说“加 shared memory”。
  • 一次改 5 件事，最后无法解释为什么变快。
  • 只追 peak utilization，不看实际算法 bytes/FLOPs。

面试官可能继续追问

  • 如果 DRAM 和 SM 都只有 30% SOL，你先查什么？
  • 如果 kernel 已 memory roof 95%，下一步怎么提高吞吐？
  • 如果 fusion 后慢了，你会检查哪些 resource metrics？

深入分析

系统优化必须从 correctness 和端到端 timeline 开始，再用 Roofline/SOL 分类，分别检查 memory、execution、resources、parallelism，最后做单变量实验并用 counters 验证。

深入理解：Hopper/Blackwell 的本质是“更强的数据移动与协作原语”

现代架构题不要只背新名词。应把每个能力放进数据流：

HBM --TMA--> Shared/DSM --(copy/MMA path)--> Register or TMEM --> Tensor Core
          ↑ cluster scope / async barriers / producer-consumer pipeline ↑

TMA 是数据移动引擎；DSM 是 cluster 级共享地址空间能力；TMEM 是 Blackwell 的 tensor-oriented memory locale。三者角色完全不同。

架构视角

Hopper/Blackwell 特性需要匹配 compute capability、Toolkit、driver 与编译目标；优化必须明确目标架构。

面试回答：30 秒 / 2 分钟 / 深挖

30 秒

正确性→Systems 定位→Compute/Roofline 分类→Memory/Execution/Resource 因果链→单变量优化→重新测 量。

2 分钟

  1. 先给定义或结论：直接回答“是什么/为什么”。
  2. 给硬件因果：把 thread/warp、memory transaction、resource 或 pipeline 对应到硬件行为。
  3. 给 trade-off：说明优化会消耗什么资源，避免绝对化结论。
  4. 给验证方法：指出需要用 benchmark/Nsight 的哪些证据确认。

深挖时必须能回答

  • 这个结论在哪些条件下会失效？
  • 如果换 problem shape / datatype / block size，瓶颈会怎样迁移？
  • 如果从 Ampere 换到 Hopper/Blackwell，哪些稳定原理不变，哪些实现细节需要重做？
  • 你会用什么 profiler 指标证明自己的判断？

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute/Systems 收集与本题直接相关的指标：Systems timeline、Roofline/SOL、SchedulerStats、Memory Workload、Occupancy、Source/SASS。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

自测题

  1. 不看答案，用 30 秒讲清本题。
  2. 画出本题涉及的数据流或线程/warp/SM 关系。
  3. 写一个最小反例，证明“常见口号”并非无条件成立。
  4. 给出一个 Nsight Compute 指标组合，能支持或推翻你的性能判断。
  5. 说明如果目标从 A100/H100 迁移到 B100/B200，你首先重新验证什么。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

系统优化必须按“正确性→端到端热点→理论性能模型→memory/compute/latency 分类→资源与调度→单变量实验→再 profile”闭环推进。高分关键是先建立证据，而不是列出一串优化技巧。

2. 定量推导 / 性能模型

先计算理论下界/上界：$AI=FLOPs/Bytes$、Roofline $P\le min(P_{peak},BW·AI)$、Amdahl $S\le1/[(1-p)+p/s]$，再判断“20×差距”到底来自哪一层。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

1 correctness + deterministic test
2 nsys: locate hotspot / gaps
3 ncu: roofline + memory + warp + launch
4 formulate ONE hypothesis
5 modify + benchmark
6 accept/reject by causal counters
7 repeat

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • Systems timeline + hotspot share
  • Roofline/SOL
  • Requested vs actual memory traffic
  • Eligible warps/stalls
  • regs/smem/spills/occupancy
  • End-to-end + correctness

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

若目标是 H100/B100/B200，只有在证据表明 mainloop/data movement 是瓶颈后再考虑 TMA、warp specialization、cluster/DSM、TMEM/TCGen05；架构特性不是第一步。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

选择 repo 中 transpose/reduction/GEMM 任一 kernel，故意构造一个慢 5–20× 的版本，写完整 performance investigation report，要求每个优化都有 profiler 证据。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。

7. 深挖追问树

  1. 如果 Roofline 说 memory-bound，但 DRAM 只有 20% peak，你下一步查什么？
  2. 如果 occupancy 25% 但 Tensor Core 95% 利用率，你会强行提高 occupancy 吗？
  3. 如果 kernel 快 2×但端到端只快 3%，怎样解释并决定下一步？

  • [ ] 先用一句话给出正确结论，而不是先铺背景。
  • [ ] 能画出本题涉及的 warp / memory / pipeline 数据流。
  • [ ] 能给至少一个公式、数量级或资源约束。
  • [ ] 能指出一个“看似优化、实际可能变慢”的反例。
  • [ ] 能说出用哪些 Nsight 证据验证。
