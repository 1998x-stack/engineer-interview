Texture / Read-Only Cache 什么时候有价值？

一句话核心：texture/read-only path 适合某些只读、空间局部或不规则访问。

章节：第 2 章 · GPU Memory Hierarchy
难度：★★☆ · 频率：中 · 标签：Texture / Cache

PDF 基线题解

考察意图

考察是否能根据访问局部性选择 memory path。

思路拆解

Texture 路径历史上对二维局部性、不规则只读访问和硬件寻址/过滤非常有价值。现代通用 cache 已增强，因此是否使用 texture 应由数据类型、访问模式和 profile 驱动。

标准回答

  • 二维 spatial locality 或采样/插值类 workload 是典型适用场景。
  • 对完全连续、规整线性读取，普通 global load 通常已经很好。
  • 不要为了“cache 更快”机械改成 texture；额外 API/绑定复杂度也有工程成本。

Gotchas：常见失分点

  • 把 texture cache 当成比 L1 永远更快。

面试官可能继续追问

  • 图像卷积和稀疏 gather 哪类更可能受益？
  • 现代编译器/缓存下怎么 benchmark？

深入分析

texture/read-only path 适合某些只读、空间局部或不规则访问。现代统一缓存较强，因此是否使用应由目标架构和 profile 决定，而非经验主义。

深入理解：性能首先是“数据在哪里”

内存层级题要用 容量、作用域、管理方式、延迟/带宽、可见性、占用资源 六个维度比较，而不是简单排序“register 最快、HBM 最慢”。很多优化本质是把数据从低复用、高成本层级搬到高复用、低成本层级，并控制搬运次数。

HBM/DRAM → L2 → L1/Shared → Register
                ↑ programmer-managed reuse often happens here

同时要记住：register/shared 是稀缺的片上资源，它们会反过来限制 residency；因此数据越靠近计算单元并不自动意味着 kernel 越快。

        ↓

        ↓

对于本题，建议至少观察：register count / spill、shared-memory usage、L1/L2 hit rate、DRAM bytes。

架构视角

Ampere/Hopper/Blackwell 持续增强 cache 与异步数据移动，但 register/shared 仍是 occupancy 的关键资源。

30 秒

texture/read-only path 适合某些只读、空间局部或不规则访问。

2 分钟

  1. 先给定义或结论：直接回答“是什么/为什么”。
  2. 给硬件因果：把 thread/warp、memory transaction、resource 或 pipeline 对应到硬件行为。
  3. 给 trade-off：说明优化会消耗什么资源，避免绝对化结论。
  4. 给验证方法：指出需要用 benchmark/Nsight 的哪些证据确认。

深挖时必须能回答

  • 这个结论在哪些条件下会失效？
  • 如果换 problem shape / datatype / block size，瓶颈会怎样迁移？
  • 如果从 Ampere 换到 Hopper/Blackwell，哪些稳定原理不变，哪些实现细节需要重做？
  • 你会用什么 profiler 指标证明自己的判断？

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute 收集与本题直接相关的指标：register count / spill、shared-memory usage、L1/L2 hit rate、DRAM bytes。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

Texture/read-only path 的价值在特定访问模式、地址计算/采样语义和缓存局部性，而不是“只读一定更快”。现代统一缓存体系增强后，应把它视为专用工具而不是通用优化口诀。

2. 定量推导 / 性能模型

收益依赖访问空间局部性：若相邻 lane/邻近迭代复用相邻 cache line，则缓存能降低下层 bytes；随机访问且 working set 很大时收益有限。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

// 现代 CUDA 中是否使用 texture object 应由访问模式决定，
// 不是把 const pointer 机械替换成 texture。

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • L1/TEX hit rate
  • DRAM bytes
  • Requested/actual bytes 与地址局部性

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

新架构缓存层持续演进，因此旧文档中“texture 比 global 快”的绝对经验不可直接移植；接口语义和采样功能反而更稳定。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

用 2D stencil、线性读、随机读三类访问比较普通 global cache 与 texture/read-only 路径。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。

7. 深挖追问树

  1. texture cache 更偏哪类 locality？
  2. 什么时候 texture 的特殊寻址/采样能力比纯性能更重要？
  3. 如何通过 profiler 证实缓存路径有效？
