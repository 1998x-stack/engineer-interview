为什么 Matrix Transpose 是经典 CUDA 优化题？

一句话核心：transpose 同时暴露 global coalescing 与 shared bank conflict：先用 shared tile 把读写都变连续，再用 padding/swizzle 消除列访问冲突。

章节：第 3 章 · Global Memory 与 Coalescing
难度：★★☆ · 频率：极高 · 标签：Transpose / 综合

PDF 基线题解

考察意图

它同时检查 global coalescing、shared-memory reordering、bank conflict 和 synchronization。

思路拆解

Naive transpose 常出现“读 coalesced、写 strided”或相反。经典解法用 shared tile：global 连续读 → shared 中转置 → global 连续写；随后再用 padding 处理 shared bank conflict。

标准回答

  • 第一层优化：使用 32×32 或类似 tile，使读写都 coalesced。
  • 第二层：shared tile 若按列读取可能造成 32-way bank conflict，典型用 tile[32][33] padding。
  • 第三层：处理矩阵边界、block shape、每线程处理多元素以控制 block size。
  • 最终以 effective bandwidth 与 copy kernel 上限对比，而不只看 absolute time。

Gotchas：常见失分点

  • 只解决 global coalescing，忘了 bank conflict。

面试官可能继续追问

  • 为什么 +1 padding 有效？
  • 怎样设计非方阵/非 32 倍数版本？

深入分析

transpose 同时暴露 global coalescing 与 shared bank conflict：先用 shared tile 把读写都变连续，再用 padding/swizzle 消除列访问冲突。

深入理解：把地址模式翻译成 transaction

Global-memory 题的统一方法是：先站在一个 warp 的视角写出 32 个地址，再问这些地址覆盖多少个 transaction/cache sector。这比背“连续访问就是 coalesced”更可靠，因为 alignment、element size、vector width、stride 都会改变请求覆盖范围。

性能判断最好区分三层：

  1. requested bytes：算法真正需要的字节；
  2. transferred bytes：memory subsystem 实际搬运的字节；
  3. achieved bandwidth：这些字节在时间维度上的吞吐。

优化的目标通常不是让 DRAM 更忙，而是让 每个搬运字节更有用。

架构视角

现代 GPU 的 cache 会缓和部分 misalignment，但 warp transaction/sector 浪费仍会降低有效带宽。

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute 收集与本题直接相关的指标：Global Load/Store Efficiency、L1/L2 sectors、DRAM bytes、effective bandwidth。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

Transpose 是经典综合题，因为 naive 实现必有一侧读/写呈 strided pattern；shared tile 可以把 global 读写都变成 coalesced，但 tile 转置又会暴露 bank conflict，迫使候选人处理两层 memory layout。

2. 定量推导 / 性能模型

理想 transpose 只需读写各一次，effective bandwidth $BW=2MN\cdot sizeof(T)/t$；优化目标是让实际 transferred bytes 尽量接近这个下界。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

__shared__ float tile[32][33];
tile[ty][tx] = in[y * width + x];
__syncthreads();
out[y2 * height + x2] = tile[tx][ty];

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • Global load/store efficiency
  • Shared bank conflicts
  • Effective bandwidth vs copy kernel

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

padding 解决经典 32-bank 冲突是稳定方法，但具体 tile shape 与 vectorized/TMA 搬运策略会随架构变化。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

实现 copy、naive transpose、coalesced transpose、padded transpose 四版；把 copy bandwidth 作为更公平的上界参照。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
