为什么 `tile[32][32]` 的列访问会出现 32-Way Bank Conflict？

一句话核心：[32][32] 按列访问时相邻 lane 的 word index 相差 32，模 32 后全落同一 bank，因此形成典型 32-way conflict。

章节：第 4 章 · Shared Memory、Warp 与 Divergence
难度：★★☆ · 频率：极高 · 标签：Transpose / Bank

PDF 基线题解

考察意图

考察能否手算 bank mapping。

思路拆解

若二维数组按 row-major，每行 32 个 float。沿同一列访问时，相邻线程地址相差 32 words；(base + 32*t) mod 32 恒 定，因此 32 lanes 映射到同一 bank 的不同地址。

标准回答

  • stride=32 words 与 bank count=32 发生周期共振。
  • 结果是同一 warp 的列读取被高度序列化。
  • 这就是 transpose shared tile 的第二层优化问题。

Gotchas：常见失分点

  • 只说“因为按列访问不连续”，没有算 bank。

面试官可能继续追问

  • 如果维度是 31 或 33 会怎样？
  • 如何用 gcd(stride, banks) 快速判断冲突模式？

深入分析

[32][32] 按列访问时相邻 lane 的 word index 相差 32，模 32 后全落同一 bank，因此形成典型 32-way conflict。

深入理解：Shared Memory 不是“自动高速缓存”

Shared memory 的价值来自可控复用与线程协作，但必须同时处理 bank mapping、同步、layout。分析 bank conflict 时，应写出每个 lane 的 word address，再做 bank = word_index mod bank_count 的映射。

Warp-level primitive 则是在“线程之间交换数据”这个问题上绕开 shared-memory round trip；其代价是作用域更小，并要求正确的 active mask 与同步语义。

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute 收集与本题直接相关的指标：shared bank conflicts、warp execution efficiency、branch efficiency、barrier stalls。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

tile[32][32] 以 row-major 存储时，按列访问相邻 lane 的地址相差 32 words。模 32 后所有 lane 落到同一 bank，因此形成经典 32-way conflict。

2. 定量推导 / 性能模型

$bank(lane)=(base+32\cdot lane)\bmod32=base$。这是一条面试现场应能立即写出的推导。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

__shared__ float tile[32][32];
float v = tile[lane][col_fixed]; // lane 变化导致 stride=32 words

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • Shared bank conflicts
  • Shared transactions/request
  • Transpose kernel effective bandwidth

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

这是 row-major 32×32 float 的经典例子；更换元素宽度、layout、tile shape 后应重新做 bank mapping，而不是机械加 1。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

把第二维从 32 扫到 33、34、36、40，计算 gcd(stride,32) 并对照 profiler conflict。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
