Predication 是什么？为什么“消灭 if”不一定更快？

一句话核心：predication 让指令执行但用 predicate 控制结果提交，适合短分支；长分支全 predication 会浪费大量指令，因此“去掉 branch”不是目标。

章节：第 4 章 · Shared Memory、Warp 与 Divergence
难度：★★☆ · 频率：中高 · 标签：Predication / Compiler

PDF 基线题解

考察意图

考察编译器如何处理短控制流。

思路拆解

编译器可能把短分支转成 predicated instructions：指令被发射，但只有 predicate 为真的 lanes 写回结果。这样避免显 式 branch/reconvergence，但会执行一些被屏蔽的指令。

标准回答

  • 短、简单分支常适合 predication。
  • 长路径用 predication 会执行太多无效工作，因此编译器可能保留 branch。
  • 性能判断应看 SASS、executed instruction count、branch/warp execution efficiency。

Gotchas：常见失分点

  • 把 branchless 写法当绝对优化。

面试官可能继续追问

  • 如何从 SASS 看 predicate？
  • compiler heuristics 受什么影响？

深入分析

predication 让指令执行但用 predicate 控制结果提交，适合短分支；长分支全 predication 会浪费大量指令，因此“去掉 branch”不是目标。

深入理解：Shared Memory 不是“自动高速缓存”

Shared memory 的价值来自可控复用与线程协作，但必须同时处理 bank mapping、同步、layout。分析 bank conflict 时，应写出每个 lane 的 word address，再做 bank = word_index mod bank_count 的映射。

Warp-level primitive 则是在“线程之间交换数据”这个问题上绕开 shared-memory round trip；其代价是作用域更小，并要求正确的 active mask 与同步语义。

架构视角

bank 组织和共享内存能力随架构演进，但“按 lane 地址映射 bank、避免同 bank 不同地址冲突”的分析方法稳定。

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute 收集与本题直接相关的指标：shared bank conflicts、warp execution efficiency、branch efficiency、barrier stalls。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

Predication 把短条件块转换为“指令照发射，但用 predicate 决定 lane 是否产生有效结果”，避免显式分支与重汇合开销。代价是未激活 lane 仍可能消耗某些执行资源，所以长分支并不适合无限 predication。

2. 定量推导 / 性能模型

若被 predicated 的块含 $I$ 条昂贵指令，哪怕只有比例 $p$ lane 有效，warp 仍可能为这 $I$ 条指令占用 issue slot；因此有效 work/issued work 比下降。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

// C++ 代码保持可读；用 SASS 判断是否变成 predicate
y = cond ? a : b;

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • SASS predicate (@P...) 与 branch 指令
  • Issued instructions vs useful active lanes
  • Branch statistics

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

编译器 heuristic 会随版本/架构变化，因此“几行以内一定 predication”的固定阈值不可靠。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

把分支 body 从 1、4、16、64 条算术指令递增，观察 compiler 何时从 predication 转为 branch 以及性能拐点。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
