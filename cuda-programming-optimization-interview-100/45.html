如何查看 Kernel 使用多少 Registers / Shared Memory / Spills？

一句话核心：编译期用 -Xptxas=-v/资源报告，运行期看 Nsight Occupancy/Memory，必要时下钻 SASS。

章节：第 5 章 · Occupancy、Register 与 Latency Hiding
难度：★☆☆ · 频率：极高 · 标签：工具 / 编译

PDF 基线题解

考察意图

考察基本工具链。

思路拆解

编译阶段先用 ptxas verbose 查看静态资源；运行阶段用 Nsight Compute 看 achieved occupancy、local memory、 spill 相关访问、动态 shared memory 与 source/SASS。

标准回答

  • nvcc -Xptxas=-v 查看 registers、stack、spill stores/loads 等。
  • Nsight Compute 的 Launch Statistics/Occupancy 等 sections 可检查 block resource constraints。
  • 必要时查看 PTX/SASS 和 source correlation，定位是哪个代码段延长 live range。

Gotchas：常见失分点

  • 只依赖 nvcc 优化级别猜测。

面试官可能继续追问

  • 为什么 debug build 的 resource usage 不能代表 release？
  • 如何验证一次源码改动是否减少 spill？

深入分析

编译期用 -Xptxas=-v/资源报告，运行期看 Nsight Occupancy/Memory，必要时下钻 SASS。三层证据能区分“分配多”与“真的 spill”。

深入理解：Occupancy 只是 latency hiding 的一个代理变量

Occupancy 题最重要的结论是：目标不是 occupancy，而是 throughput。增加 resident warps 可以帮助隐藏 latency，但会和 register/thread、shared/block、tile size、ILP 发生资源竞争。

一个成熟的回答应讨论：

registers/thread ↑ → ILP/data reuse 可能 ↑ → blocks/SM 可能 ↓
shared/block ↑    → reuse 可能 ↑       → blocks/SM 可能 ↓
warps/SM ↑         → latency hiding ↑   → 每线程资源预算可能 ↓

因此调优必须用真实 benchmark 与 profiler 验证，而不能把 occupancy calculator 当最终答案。

对于本题，建议至少观察：ptxas resource report、local-memory traffic、Occupancy section、SASS local load/store。

架构视角

不同 compute capability 的 SM 资源上限不同；面试时应强调“先查目标架构限制，再算 residency”。

面试回答：30 秒 / 2 分钟 / 深挖

30 秒

编译期用 -Xptxas=-v/资源报告，运行期看 Nsight Occupancy/Memory，必要时下钻 SASS。

2 分钟

  1. 先给定义或结论：直接回答“是什么/为什么”。
  2. 给硬件因果：把 thread/warp、memory transaction、resource 或 pipeline 对应到硬件行为。
  3. 给 trade-off：说明优化会消耗什么资源，避免绝对化结论。
  4. 给验证方法：指出需要用 benchmark/Nsight 的哪些证据确认。

深挖时必须能回答

  • 这个结论在哪些条件下会失效？
  • 如果换 problem shape / datatype / block size，瓶颈会怎样迁移？
  • 如果从 Ampere 换到 Hopper/Blackwell，哪些稳定原理不变，哪些实现细节需要重做？
  • 你会用什么 profiler 指标证明自己的判断？

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute/Systems 收集与本题直接相关的指标：ptxas resource report、local-memory traffic、Occupancy section、SASS local load/store。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

资源诊断要跨编译期和运行期：ptxas 报告静态 registers/smem/spill，Nsight Compute 报告 launch/achieved occupancy 与真实 memory 行为，必要时看 PTX/SASS 确认编译器 lowering。

2. 定量推导 / 性能模型

静态资源是“可能限制 residency”的输入，动态 profiler 是“实际发生了什么”的证据；二者不能互相替代。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

nvcc -Xptxas=-v -lineinfo kernel.cu -o app
ncu --set full ./app
# cuobjdump / nvdisasm 可进一步看 SASS

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • ptxas Used registers / spill bytes
  • Launch Statistics
  • Local memory transactions

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

编译器版本和 target -arch=sm_XY 会改变 register allocation 与指令选择；发布 benchmark 必须记录 toolchain 与 target。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

同一 source 用两个 -arch/compiler version 编译，比较 ptxas 资源和 SASS，理解“源代码相同≠kernel 相同”。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。

7. 深挖追问树

  1. PTX 和 SASS 哪个更接近实际执行？
  2. 为什么 -lineinfo 对 profiler 有帮助？
  3. 怎么看 dynamic shared memory？
