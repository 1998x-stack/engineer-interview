ILP 与 TLP 有什么区别？

一句话核心：TLP 用更多 warps/threads 隐藏延迟，ILP 用同一 thread/warp 内的独立指令填充流水。

章节：第 5 章 · Occupancy、Register 与 Latency Hiding
难度：★★☆ · 频率：极高 · 标签：ILP / TLP

PDF 基线题解

考察意图

考察延迟隐藏的两条路线。

思路拆解

TLP 依靠更多 warps/threads 在一个 warp 等待时切换；ILP 依靠同一 thread/warp 中多个独立指令，让流水线有别的工 作可发射。二者常与 register 使用互相制约。

标准回答

  • TLP 的代理指标包括 occupancy、eligible warps。
  • ILP 常来自 loop unroll、multiple accumulators、software pipelining。
  • 增加 ILP 往往增加 registers；增加 TLP 往往要求控制 per-thread resources。
  • 高性能 GEMM 通常不是追求最大 TLP，而是用很强 ILP + 足够 TLP。

Gotchas：常见失分点

  • 把 unroll 只理解成减少 loop overhead。

面试官可能继续追问

  • 为什么 multiple accumulators 能隐藏 FMA latency？
  • 如何从 scheduler metrics 判断缺 ILP 还是缺 warps？

深入分析

TLP 用更多 warps/threads 隐藏延迟，ILP 用同一 thread/warp 内的独立指令填充流水。ILP 通常需要更多 register，因此和 TLP 存在资源竞争。

深入理解：Occupancy 只是 latency hiding 的一个代理变量

Occupancy 题最重要的结论是：目标不是 occupancy，而是 throughput。增加 resident warps 可以帮助隐藏 latency，但会和 register/thread、shared/block、tile size、ILP 发生资源竞争。

一个成熟的回答应讨论：

registers/thread ↑ → ILP/data reuse 可能 ↑ → blocks/SM 可能 ↓
shared/block ↑    → reuse 可能 ↑       → blocks/SM 可能 ↓
warps/SM ↑         → latency hiding ↑   → 每线程资源预算可能 ↓

因此调优必须用真实 benchmark 与 profiler 验证，而不能把 occupancy calculator 当最终答案。

架构视角

不同 compute capability 的 SM 资源上限不同；面试时应强调“先查目标架构限制，再算 residency”。

30 秒

2 分钟

  1. 先给定义或结论：直接回答“是什么/为什么”。
  2. 给硬件因果：把 thread/warp、memory transaction、resource 或 pipeline 对应到硬件行为。
  3. 给 trade-off：说明优化会消耗什么资源，避免绝对化结论。
  4. 给验证方法：指出需要用 benchmark/Nsight 的哪些证据确认。

深挖时必须能回答

  • 这个结论在哪些条件下会失效？
  • 如果换 problem shape / datatype / block size，瓶颈会怎样迁移？
  • 如果从 Ampere 换到 Hopper/Blackwell，哪些稳定原理不变，哪些实现细节需要重做？
  • 你会用什么 profiler 指标证明自己的判断？

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute 收集与本题直接相关的指标：theoretical/achieved occupancy、registers/thread、shared/block、eligible warps / issue slots、local-memory traffic。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

TLP 用更多独立 warps/threads 隐藏延迟；ILP 让同一 thread/warp 同时拥有多个互不依赖指令链。增加 ILP 通常增加 register pressure，增加 TLP 又要求更多 residency，因此二者存在资源 trade-off。

2. 定量推导 / 性能模型

若单条依赖链 latency 为 $L$、每 warp 有 $k$ 条独立链，理论可把同 warp 可发射机会扩大约 $k$ 倍；仍需 scheduler 与功能单元容量支持。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

// ILP: 4 个独立 accumulator
acc0 += a0*b0; acc1 += a1*b1;
acc2 += a2*b2; acc3 += a3*b3;

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • Eligible warps
  • Dependency/scoreboard stalls
  • Registers/thread 与 IPC/issue utilization

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

Tensor Core kernels 常同时依赖 warp-level TLP 与每 warp 多 stage/多 accumulator 的 ILP；software pipeline 进一步提供 memory/computation overlap。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

对 reduction/dot kernel 使用 1/2/4/8 accumulators，观察 dependency stalls 降低与 register pressure 上升。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。

7. 深挖追问树

  1. 为什么多个 accumulator 能加速 reduction？
  2. ILP 能否在 occupancy 很低时补偿？
  3. 怎样从 stall reason 识别依赖链太长？
