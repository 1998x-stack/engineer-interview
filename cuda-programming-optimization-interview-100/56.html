现场写 Optimized Matrix Transpose。

一句话核心：optimized transpose 的经典链：coalesced global read → shared tile → sync → transposed read → coalesced write；再用 TILE_DIM+1 或 swizzle 去 bank conflict。

章节：第 6 章 · 经典 CUDA Kernel 现场编程
难度：★★★ · 频率：极高 · 标签：Coding / Transpose

PDF 基线题解

考察意图

考察你能否把 coalescing 与 bank conflict 连起来。

思路拆解

标准思路：每 block coalesced 读取一个 tile 到 shared；block barrier；交换 block 坐标并从 shared 的转置位置读取； coalesced 写出。Shared tile 使用 +1 padding 或 swizzle。

标准回答

  • 用 32×8 threads 处理 32×32 tile，可让每线程循环处理 4 行，控制 block threads=256。
  • global load/store 都按 x 连续，获得 coalescing。
  • tile[TILE][TILE+1] 避免列读 bank conflict。
  • 边界版本需要 x<width、y<height 的 guards，但 barrier 必须保持 block 一致。

代码 / 白板骨架

constexpr int TILE=32, ROWS=8;
__global__ void transpose(float* out, const float* in, int w, int h) {
__shared__ float tile[TILE][TILE+1];
int x = blockIdx.x*TILE + threadIdx.x;
int y = blockIdx.y*TILE + threadIdx.y;
for (int j=0; j<TILE; j+=ROWS)
if (x<w && y+j<h) tile[threadIdx.y+j][threadIdx.x] = in[(y+j)*w+x];

__syncthreads();
x = blockIdx.y*TILE + threadIdx.x;
y = blockIdx.x*TILE + threadIdx.y;
for (int j=0; j<TILE; j+=ROWS)
if (x<h && y+j<w) out[(y+j)*h+x] = tile[threadIdx.x][threadIdx.y+j];
}

Gotchas：常见失分点

  • 在第一次 bounds if 内放 __syncthreads()。

深入分析

optimized transpose 的经典链：coalesced global read → shared tile → sync → transposed read → coalesced write；再用 TILE_DIM+1 或 swizzle 去 bank conflict。

深入理解：经典算法题考的是“逐版优化能力”

现场 coding 题通常不要求一步写出最优 kernel，而是考察你能否从正确的 baseline 出发，逐个消除瓶颈：

Correct baseline
→ coalesced access
→ shared/register reuse
→ reduce divergence/barriers
→ warp primitive
→ vectorization / multi-element per thread
→ device-wide library / architecture specialization

每一版都要能说明：减少了什么成本、引入了什么新约束、用什么指标验证。

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute 收集与本题直接相关的指标：kernel time、memory throughput、branch/barrier stalls、atomic throughput、correctness error。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

优化 transpose 的标准过程：先写 naive 正确版，识别一侧 strided global access；用 shared tile 让 global 读写都 coalesced；再用 +1 padding 或 swizzle 消除列读 shared 的 bank conflict；最后调 tile/thread shape。

2. 定量推导 / 性能模型

$BW_{eff}=2MN\cdot sizeof(T)/t$。一个优秀 transpose 应接近同尺寸 copy kernel 的有效带宽，而不是与 GEMM FLOPS 比。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

constexpr int TILE=32, ROWS=8;
__shared__ float tile[TILE][TILE+1];
// 32x8 threads，每线程循环处理 4 行，可减 block thread 数并保持 32x32 tile。

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • Global load/store efficiency
  • Shared conflicts
  • Effective BW vs copy baseline

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

Hopper TMA 可简化/异步化多维 tile 搬运，但数据 layout 与写回模式仍要满足高效 memory access。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

copy→naive→coalesced→padded→vectorized/TMA（若支持）逐版 benchmark，并验证非 32 倍尺寸的边界。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
