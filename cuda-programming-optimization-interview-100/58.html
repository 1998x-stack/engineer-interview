为什么 GEMM Tile 越大不一定越快？

一句话核心：tile 变大提高 reuse，却同步增加 shared/register/live state，可能减少 resident CTAs、增加 bank/fragment 管理开销。

章节：第 6 章 · 经典 CUDA Kernel 现场编程
难度：★★★ · 频率：高 · 标签：GEMM / 资源

PDF 基线题解

考察意图

考察 reuse 与 occupancy/register pressure 的约束优化。

思路拆解

更大的 tile 通常提高 A/B reuse，减少 global bytes/FLOP；但也消耗更多 shared memory、registers 和线程资源，可能 减少 active CTAs/warps，增加 spill 或降低 scheduler flexibility。

标准回答

  • tile shape 要匹配 M/N/K 与硬件 Tensor Core/MMA shape。
  • K tile 影响 pipeline depth 和 shared bytes；M/N tile 影响 accumulator registers。
  • 边界/小矩阵还会出现 tile waste。
  • 高性能库通常根据 architecture、dtype、shape 提供多个 kernel schedules，而不是一个万能 tile。

Gotchas：常见失分点

  • 只追求最大 arithmetic intensity。

面试官可能继续追问

  • 为什么 skinny GEMM 需要不同 schedule？
  • Stream-K 解决什么问题？

深入分析

tile 变大提高 reuse，却同步增加 shared/register/live state，可能减少 resident CTAs、增加 bank/fragment 管理开销。最优 tile 与 problem shape/architecture 强相关。

深入理解：经典算法题考的是“逐版优化能力”

现场 coding 题通常不要求一步写出最优 kernel，而是考察你能否从正确的 baseline 出发，逐个消除瓶颈：

Correct baseline
→ coalesced access
→ shared/register reuse
→ reduce divergence/barriers
→ warp primitive
→ vectorization / multi-element per thread
→ device-wide library / architecture specialization

每一版都要能说明：减少了什么成本、引入了什么新约束、用什么指标验证。

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute 收集与本题直接相关的指标：kernel time、memory throughput、branch/barrier stalls、atomic throughput、correctness error。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

更大 tile 提高复用，却同时增加 shared memory、register accumulator、每 block 工作量和 tail waste。tile 过大可能减少 active blocks、降低 latency hiding，或导致 spill；因此 GEMM 是典型多资源 Pareto 优化。

2. 定量推导 / 性能模型

共享内存约 $S\approx(M_bK_b+K_bN_b)sizeof(T)\times stages$；accumulator register 规模与每线程输出 tile 成正比。tile 每扩大一维，资源可能非线性增长。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

// autotune dimensions: BM, BN, BK, stages, warps
// 不是只调一个 TILE 常量。

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • Registers/thread、smem/block
  • Active blocks/SM
  • Tensor utilization / memory throughput
  • Tail waves / shape efficiency

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

CUTLASS/CuTe 的价值之一就是系统表达 tile hierarchy + pipeline + scheduler，并针对不同架构和 shape 提供多个 kernel families。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

固定 M=N=K=4096，sweep 16/32/64/128 tile；再换 skinny matrix，观察最优 tile 如何迁移。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
