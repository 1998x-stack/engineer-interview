Kernel Fusion 为什么经常有效？什么时候会适得其反？

一句话核心：fusion 减少 launch 与中间 HBM traffic，却会扩大 kernel live state，提升 register/shared pressure，甚至降低 occupancy。

章节：第 7 章 · Stream、异步拷贝与 Software Pipeline
难度：★★☆ · 频率：极高 · 标签：Fusion / Memory

PDF 基线题解

考察意图

考察 memory traffic 与资源压力的权衡。

思路拆解

Fusion 把多个 kernels 的中间结果留在 register/shared/cache 范围，减少 global store/load 与 launch overhead。对 AI inference 的 elementwise/epilogue 特别常见。

标准回答

  • 主要收益：减少 HBM bytes、kernel launches、同步边界。
  • 主要风险：code size、register live ranges、shared memory、divergence 增加，使 occupancy 或 instruction cache 变差。
  • Fusion 还可能减少并行度：原本两个阶段可以有不同最佳 grid/block 配置。
  • 是否融合要用 end-to-end profile 验证。

Gotchas：常见失分点

  • “能融合就全部融合”。

面试官可能继续追问

  • 为什么 FlashAttention 属于算法级 fusion？
  • epilogue fusion 为什么通常收益高？

深入分析

fusion 减少 launch 与中间 HBM traffic，却会扩大 kernel live state，提升 register/shared pressure，甚至降低 occupancy。判断标准是端到端时间和 bytes，而不是 kernel 数。

深入理解：高性能 pipeline 的目标是让硬件单元同时忙起来

异步编程的核心不是“API 名字带 Async”，而是建立真正的 producer/consumer dependency，使数据搬运、Tensor Core/ALU 计算、store 尽可能重叠。

Stage k:     Compute(tile k)
Stage k+1:   Load(tile k+1)   ← overlap
Stage k-1:   Store(tile k-1)  ← overlap when possible

要区分 host-side concurrency（streams/graphs）和 device-side pipeline（cp.async/TMA/barrier/warp specialization）。

Ampere 重点是 async global→shared；Hopper 进一步用 TMA + barrier + warp specialization 做硬件化 pipeline。

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute/Systems 收集与本题直接相关的指标：HBM bytes、launch count、registers/thread、shared/block、occupancy、end-to-end time。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

Kernel fusion 的收益来自消除中间 global round-trip 和 launch 边界，并允许中间值停留在 register/shared；风险是融合后 live values、register/smem、指令体积和 divergence 增加，导致 occupancy/ICache/调度恶化。

2. 定量推导 / 性能模型

若中间 tensor 大小 B，融合理论至少可省一次写 B + 一次读 B，即约 2B bytes；但若 spill 新增超过这部分，收益可能消失。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

// unfused: y=f(x); z=g(y) 两 kernel
// fused:  float y=f(x); z[i]=g(y);  // y 仅 register 生命周期

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • DRAM bytes 前后
  • Kernel launch count
  • Registers/spill/occupancy
  • End-to-end latency

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

编译器/DSL（如 Triton、CUDA Tile、图编译器）越来越多自动做融合，但硬件资源 trade-off 仍需 profiling。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

elementwise chain 从 2→4→8→16 ops 逐步融合，找出“继续 fusion 开始变慢”的点并解释资源原因。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
