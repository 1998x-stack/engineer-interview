如何判断 Memory-Bound 还是 Compute-Bound？

一句话核心：先算 arithmetic intensity 并看 Roofline/SOL，再结合 DRAM/SM throughput。

章节：第 8 章 · Nsight、Roofline 与性能诊断
难度：★★☆ · 频率：极高 · 标签：Roofline / AI

PDF 基线题解

考察意图

考察 Roofline 的核心。

思路拆解

计算 arithmetic intensity（AI = FLOPs / bytes from the limiting memory level），比较机器 compute peak / memory bandwidth 的 ridge point。AI 低通常受 bandwidth ceiling，AI 高才有机会进入 compute ceiling。

标准回答

  • Roofline：P = min(P_compute_peak, BW × AI)。
  • 注意 bytes 应针对你分析的 memory level；L2 与 HBM 可有不同 roof。
  • 实际 kernel 还可能 latency-bound、launch-bound、dependency-bound，因此 Roofline 是第一层分类，不是全部 诊断。

Gotchas：常见失分点

  • 只看 SM utilization 与 DRAM utilization 二选一。

面试官可能继续追问

  • 如何计算 GEMM AI？
  • 为什么小 GEMM 可能既没到 compute roof 也没到 memory roof？

深入分析

先算 arithmetic intensity 并看 Roofline/SOL，再结合 DRAM/SM throughput。memory-bound、compute-bound、latency-bound、launch-bound、parallelism-bound 要分开。

深入理解：Profiler 是假设检验工具，不是“指标排行榜”

性能诊断应遵循 timeline → hot kernel → roofline/SOL → scheduler/memory/resource counters → source/SASS 的顺序。任何单个 metric 都不能脱离上下文解读。

尤其是 stall reason：只有当 scheduler 无法持续 issue 时，stall 才值得作为主要矛盾继续深挖；否则高 stall 百分比可能只是正常流水行为。

性能因果链

题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证

对于本题，建议至少观察：Arithmetic Intensity、SM SOL、Memory SOL、DRAM throughput、achieved FLOP/s。

架构视角

Nsight Compute 指标名称会随版本变化；稳定方法是从 throughput、scheduler、memory、resource 四类证据建立因果链。

面试回答：30 秒 / 2 分钟 / 深挖

30 秒

先算 arithmetic intensity 并看 Roofline/SOL，再结合 DRAM/SM throughput。

2 分钟

  1. 先给定义或结论：直接回答“是什么/为什么”。
  2. 给硬件因果：把 thread/warp、memory transaction、resource 或 pipeline 对应到硬件行为。
  3. 给 trade-off：说明优化会消耗什么资源，避免绝对化结论。
  4. 给验证方法：指出需要用 benchmark/Nsight 的哪些证据确认。

深挖时必须能回答

  • 这个结论在哪些条件下会失效？
  • 如果换 problem shape / datatype / block size，瓶颈会怎样迁移？
  • 如果从 Ampere 换到 Hopper/Blackwell，哪些稳定原理不变，哪些实现细节需要重做？
  • 你会用什么 profiler 指标证明自己的判断？

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute/Systems 收集与本题直接相关的指标：Arithmetic Intensity、SM SOL、Memory SOL、DRAM throughput、achieved FLOP/s。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

先用 Roofline/算术强度给出理论分类，再用 profiler 验证硬件实际是否接近 memory/compute roof。Memory-bound 不等于“有很多 load”，compute-bound 也不等于“SM utilization 高”。

2. 定量推导 / 性能模型

$AI=FLOPs/Bytes$，ridge point $AI^=PeakFLOPs/PeakBW$。若 $AI\ll AI^$ 且实际 BW 接近可达上限，更像 memory-bound。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

double AI = flops / bytes;
double roof = min(peak_flops, peak_bw * AI);

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • Roofline chart
  • DRAM/L2 throughput SOL
  • Compute pipe/Tensor utilization
  • Stall reasons

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

不同 dtype 的 compute peak 不同，所以 ridge point 会随 FP32/TF32/FP16/FP8 等显著变化；同一算法可因 dtype 改变 bound 类型。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

vector add、naive GEMM、tiled GEMM 三例计算 AI 并实测 roofline 位置。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
