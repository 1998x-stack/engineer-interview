Roofline Model 如何指导具体优化？

一句话核心：Roofline 只告诉你性能上限受 compute 还是 bandwidth 主导；具体怎么改要结合 bytes、reuse、instruction mix、Tensor Core 使用和 scheduler counters。

章节：第 8 章 · Nsight、Roofline 与性能诊断
难度：★★☆ · 频率：极高 · 标签：Roofline / 方法论

PDF 基线题解

考察意图

考察从模型到动作。

思路拆解

若点靠近 memory roof，减少 bytes/增加 reuse/提高 AI；若靠近 compute roof，优化 Tensor Core、指令效率、 precision、pipeline。若远离两条 roof，说明还有 latency、occupancy、divergence、launch 等其他问题。

标准回答

  • Memory-bound：coalescing、tiling、fusion、lower precision。
  • Compute-bound：Tensor Core、MMA shape、instruction mix、数学近似/低精度。
  • 低于两 roof：看 stalls、eligible warps、small grid、serial dependencies。
  • 优化后重新在 Roofline 上观察点是否向目标 roof 移动。

Gotchas：常见失分点

  • 把 Roofline 当成只有一条 DRAM roof 的图。

面试官可能继续追问

  • 如何构建 L1/L2/DRAM hierarchical roofline？
  • Tensor Core roof 与 CUDA Core roof 如何区分？

深入分析

Roofline 只告诉你性能上限受 compute 还是 bandwidth 主导；具体怎么改要结合 bytes、reuse、instruction mix、Tensor Core 使用和 scheduler counters。

深入理解：Profiler 是假设检验工具，不是“指标排行榜”

性能诊断应遵循 timeline → hot kernel → roofline/SOL → scheduler/memory/resource counters → source/SASS 的顺序。任何单个 metric 都不能脱离上下文解读。

尤其是 stall reason：只有当 scheduler 无法持续 issue 时，stall 才值得作为主要矛盾继续深挖；否则高 stall 百分比可能只是正常流水行为。

对于本题，建议至少观察：Roofline position、FLOPs、bytes、SM/DRAM SOL、cache traffic。

2 分钟

  1. 先给定义或结论：直接回答“是什么/为什么”。
  2. 给硬件因果：把 thread/warp、memory transaction、resource 或 pipeline 对应到硬件行为。
  3. 给 trade-off：说明优化会消耗什么资源，避免绝对化结论。
  4. 给验证方法：指出需要用 benchmark/Nsight 的哪些证据确认。

深挖时必须能回答

  • 这个结论在哪些条件下会失效？
  • 如果换 problem shape / datatype / block size，瓶颈会怎样迁移？
  • 如果从 Ampere 换到 Hopper/Blackwell，哪些稳定原理不变，哪些实现细节需要重做？
  • 你会用什么 profiler 指标证明自己的判断？

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute/Systems 收集与本题直接相关的指标：Roofline position、FLOPs、bytes、SM/DRAM SOL、cache traffic。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

Roofline 的价值是把优化方向约束住：memory roof 下优先减少 bytes/提高 reuse/coalescing；compute roof 下优先提高指令/矩阵单元效率；离任何 roof 都很远则多半还有 latency、并行度、依赖或软件开销问题。

2. 定量推导 / 性能模型

$P\le\min(P_{peak}, BW\times AI)$。优化要么让点“向右”提高 AI，要么“向上”提高实际带宽/compute efficiency。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

// 例：fusion 省中间读写 -> AI 向右移动
// Tensor Core 替代 scalar math -> 提高 compute roof 可利用率

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • Nsight Compute Roofline
  • Memory/compute SOL
  • Instruction mix and stalls

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

Tensor Core dtype 变化会改变 compute roof；HBM/L2 变化会改变 bandwidth roof，所以跨 GPU 的同一点需要重新定位。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

对同一 kernel 做 fusion（减 bytes）和 unroll（增 ILP）两类改造，观察 roofline 点的不同移动方向。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
