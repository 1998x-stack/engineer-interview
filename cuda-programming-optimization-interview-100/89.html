什么是 Persistent Kernel？

一句话核心：persistent kernel 让少量 CTA 长驻 SM，不断领取 tiles/work items，减少 launch/调度开销并改善不均匀工作负载的负载均衡；代价是自定义调度复杂。

章节：第 9 章 · GEMM、Tensor Core 与 CUTLASS
难度：★★★ · 频率：高 · 标签：Persistent / Scheduler

PDF 基线题解

考察意图

考察减少 launch/调度开销与动态负载均衡。

思路拆解

Persistent kernel 让一组 CTAs 长时间 resident，通过循环从 work queue 或 tile scheduler 获取多份工作，而不是“一 block 一 tile 然后退出”。

标准回答

  • 可 amortize kernel prologue/launch/scheduling overhead。
  • 可做动态 load balancing，对 irregular work 有利。
  • resident CTAs 数常按 SM 数/资源有意控制。
  • 代价是自定义 work scheduling、fairness、同步和更复杂的尾部处理。

Gotchas：常见失分点

  • 把 grid-stride loop 和 persistent kernel 完全等同。

面试官可能继续追问

  • CUTLASS persistent cooperative kernel 为什么有两个 consumer warp groups？
  • persistent kernel 如何避免 work queue contention？

深入分析

persistent kernel 让少量 CTA 长驻 SM，不断领取 tiles/work items，减少 launch/调度开销并改善不均匀工作负载的负载均衡；代价是自定义调度复杂。

深入理解：GEMM 是“数据移动 + 复用 + 专用计算单元”的综合优化

现代 GEMM 的关键不是三重 for-loop，而是让 A/B 数据沿 HBM → shared → register/TMEM → Tensor Core 的路径被尽量多次复用，并通过多级 tiling 与 pipeline 保持计算单元持续供料。

CUTLASS/CuTe 的价值就在于把 tile shape、copy atom、MMA atom、pipeline、scheduler、epilogue 拆成可组合策略；面试中要能解释这些抽象对应什么硬件约束。

实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

  1. 写一个正确但未优化的 baseline。
  2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
  3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
  4. 使用 Nsight Compute/Systems 收集与本题直接相关的指标：active CTAs、work-queue imbalance、tail effect、launch overhead、kernel time。
  5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

专业增强版 V2：机制、量化与验证

本节是在 PDF 基线题解之上的仓库扩展。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

1. 硬件机制与核心心智模型

Persistent kernel 让少量 CTA 长时间 resident，循环从 work queue/scheduler 领取多个 tiles/tasks，而不是“一 block 一任务立即退出”。它减少 launch/调度开销，并能做动态 load balance，但需要显式任务调度与公平性设计。

2. 定量推导 / 性能模型

传统 grid 若有 $N_t$ tiles 产生多 waves；persistent 可用约 O(SM×k) resident CTAs 处理全部 tiles，调度 overhead 从每 tile 隐式 launch scheduling 转为内部 work fetch。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

3. 代码 / 白板核心片段

while (true) {
  int tile = fetch_next_tile();
  if (tile >= total) break;
  process(tile);
}

白板代码优先保证：边界正确、同步范围正确、地址模式可解释。如果为了展示优化而省略边界处理，要主动说明省略条件。

4. Nsight 证据链：怎样证明你的判断

  • Waves/tail efficiency
  • Scheduler/work-queue overhead
  • Load balance across SMs
  • Long-running kernel residency

推荐把分析写成四列：

假设 预期指标变化 实测指标变化 结论
当前瓶颈是本题讨论的问题 指标应出现可预测变化 benchmark 后填写 接受 / 推翻假设
优化应减少对应硬件成本 时间与因果指标同向改善 benchmark 后填写 是否保留优化

5. 架构迁移视角

Blackwell CLC、CUTLASS persistent schedulers 等进一步提供硬件/框架支持；persistent 不等于“固定 1 block/SM”，具体 occupancy 可多 CTA。

这里要区分两类知识：

  • 稳定原理：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
  • 架构实现：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

6. 可复现实验（建议真的做）

构造 tiles 计算量不均的 workload，对比静态一 tile/block 与 persistent dynamic scheduler 的 tail。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。

7. 深挖追问树

  1. persistent kernel 如何避免 work queue contention？
  2. 它为什么可能影响其他 GPU work 的公平性？
  3. persistent 与 CUDA Graph 解决的是同一问题吗？
