“真题”口径分两类：少数题可在公开面经中直接核验，例如 synchronize、reduction、memory hierarchy，以及

题 01｜Thread、Warp、Block、Grid、SM 分别是什么？
难度      ★☆☆      频率      极高          标签        执行模型 / 基础




 30 秒答案 编程层级是 Grid→Block→Thread；硬件调度核心是 SM→Warp，warp=32 threads。




考察意图
看你能否把 CUDA 的编程抽象与 GPU 的硬件调度实体分开。

思路拆解
最容易失分的点，是把 warp 当成程序员显式创建的对象，或者说一个 block 会被拆到多个 SM 上执行。面试回答应该先
画出软件层级，再映射到硬件。

标准回答
 Grid 是一次 kernel launch 的全部 thread blocks；Block 是线程协作与共享内存的基本范围；Thread 是 CUDA 暴露的
  逻辑执行单元。
 硬件按 warp 调度线程。当前 NVIDIA CUDA 的 warp 为 32 threads；一个 SM 可以同时驻留多个 blocks 和 warps。
 一个 thread block 在其生命周期内驻留在一个 SM 上，不会跨 SM 拆分；不同 blocks 可以被动态分配到任意可用
  SM。
 性能分析时要从“单线程做什么”升级为“同一 warp 的 32 个线程执行什么指令、访问什么地址”。

Gotchas：常见失分点
 把 SM 说成一个 CUDA core。
 认为 block 与 SM 是一一对应关系。

面试官可能继续追问
 为什么 warp size 会影响 block size 选择？
 一个 SM 能同时驻留多少 blocks 由哪些资源决定？
参考：R1, R2

题 02｜CUDA 为什么称 SIMT，而不是传统 SIMD？
难度     ★☆☆          频率       高             标签        SIMT / 架构




考察意图
考察你是否理解 CUDA “线程语义”与底层矢量化执行之间的关系。

思路拆解
SIMD 把 lane 暴露给程序员，而 SIMT 给每个 CUDA thread 独立的线程语义、寄存器状态和控制流，再由硬件把线程聚成
warp。这个差异直接解释了 divergence 为什么存在。

标准回答
 SIMD 的抽象是“一条显式向量指令操作多个 lane”；SIMT 的抽象是“多个逻辑线程被硬件以 warp 形式共同发
  射”。
 每个 CUDA thread 有自己的 threadIdx、寄存器和逻辑控制流状态；但 warp 中 active lanes 通常共享同一条被发射的
  指令。
 发生分支时，SIMT 能表达不同线程走不同路径；硬件通过 active mask/重汇合机制执行这些路径，因此可能降低 lane
  利用率。

Gotchas：常见失分点
 把 SIMT 解释成“32 个 CUDA core 同时执行”。
 忽略 independent thread scheduling 对 warp-synchronous 代码的影响。

面试官可能继续追问
 Volta 之后 independent thread scheduling 改变了什么？
 为什么 warp-level primitive 需要 mask？
参考：R1, R8

conflict、branch divergence、warp shuffle、scheduler eligibility。

标准回答
 Global memory coalescing 是把一个 warp 的地址请求合并成尽量少的 memory transactions。

题 04｜Kernel launch 后，Block 是如何调度到 SM 的？
难度     ★★☆         频率       高             标签        调度 / Occupancy




考察意图
考察资源约束和动态 block 调度的理解。

思路拆解
Block 调度不是静态绑定。SM 只有在 register、shared memory、thread/warp slots、block slots 等资源都够时，才可
以让新 block resident。

标准回答
 Grid 中 blocks 可被动态分派给可用 SM，程序通常不应依赖某个 block 被放在哪个 SM。
 一个 SM 的 resident blocks 上限是多个约束的最小值：线程数、warp 数、寄存器、shared memory、block slot 等。
 当一个 resident block 完成，释放资源后，SM 才能接纳后续 block；因此 grid 足够大才能形成持续的 waves。
 尾部只剩少量 blocks 时，可能出现 tail effect，即一部分 SM 已空闲但 kernel 尚未结束。

Gotchas：常见失分点
 把 block 调度顺序当作确定的。
 依赖 blockIdx 推断物理 SM。

面试官可能继续追问
 什么是 wave quantization / tail effect？
 persistent kernel 为什么会改变 block 工作方式？
参考：R1, R2

题 05｜为什么 block size 常从 128/256 开始，而不是随便选？
难度      ★☆☆        频率       极高            标签        Block Size / Warp




考察意图
考察 block size 与 warp 填充、资源占用、延迟隐藏之间的权衡。

思路拆解
“256 最快”不是规律。合理起点来自两个事实：threads/block 应是 32 的倍数以减少 under-populated warp；同时
128-256 往往能在并行度与 block 数之间提供不错的初始平衡。最终必须 profile。

标准回答
 blockDim 最好是 warp size 的整数倍；例如 100 threads 会生成 4 个 warps，其中最后一个只有 4 个 active lanes。
 较大 block 可增加单 block 并行度，但也会增加每 block 的 register/shared-memory 总消耗。
 较小 block 可能让更多 blocks 同时 resident，有利于隐藏 barrier 或 memory latency。
 官方 Best Practices 把 128-256 作为实验起点，而非固定答案。

Gotchas：常见失分点
 回答“256 是官方推荐，所以一定最优”。

面试官可能继续追问
 64、128、256、512 应该怎么系统 benchmark？
 block 维度形状会影响 coalescing 吗？
参考：R2




题 06｜什么是 Grid-Stride Loop？为什么它是 CUDA 常用模式？
难度      ★☆☆        频率       高             标签        索引 / 工程




考察意图
考察是否具备可扩展 kernel 的基本编码习惯。

思路拆解
Grid-stride loop 让线程处理多个逻辑元素，解耦数据规模 N 与 launch 的 block 数；它还能控制 grid 大小、复用线程上
下文，并方便做 persistent-style 工作分配。

标准回答
 初始索引 i = blockIdx.x * blockDim.x + threadIdx.x。
 步长 stride = blockDim.x * gridDim.x；每个线程处理 i, i+stride, ...。
 连续线程的第一次访问仍保持连续，因此可以保留 coalescing。
 它允许将 gridDim 调到与 SM 数、work chunking 等更适配，而不是盲目发 N/threads 个 blocks。

代码 / 白板骨架

 __global__ void saxpy(int n, float a, const float* x, float* y) {
     for (int i = blockIdx.x * blockDim.x + threadIdx.x;
          i < n;
          i += blockDim.x * gridDim.x) {
         y[i] = a * x[i] + y[i];
     }
 }




Gotchas：常见失分点
 stride 写成 blockDim.x 而忽略 gridDim.x。
 把 grid-stride loop 与 strided memory access 混为一谈：前者每一轮 warp 内仍可连续。

题 07｜`__syncthreads()` 到底同步什么？
难度      ★★☆            频率        极高               标签        同步 / 内存模型




考察意图
考察 barrier 语义，而不是只会背“同步 block”。

思路拆解
正确答案至少包含两层：它是 block 范围的 barrier；同时对参与线程建立内存顺序，使 barrier 前的共享/全局内存操作在
相应语义下对参与线程可见。

标准回答
 同一个 thread block 中所有尚未退出且需要参与该 barrier 的线程必须到达同一个同步点。
 `__syncthreads()` 常用于“shared memory 生产者写完 → 消费者读取”之间。
 把 barrier 放在非一致控制流中非常危险：如果部分线程到达、部分线程永远到不了，行为是错误的。
 同步不是缓存刷新魔法；跨 block 通信需要更高层同步/原子/内存顺序机制。

代码 / 白板骨架

 // 错误范式：条件可能在 block 内不一致
 if (threadIdx.x < valid) {
     __syncthreads();
 }


 // 更常见的正确思路：所有线程都到 barrier，
 // 只有读写本身按 valid 条件屏蔽。

题 08｜CUDA 有哪些同步层级？
难度     ★★☆         频率      高              标签        同步 / Cooperative Groups




考察意图
考察你能否构建从 warp 到 system 的同步层级。

思路拆解
CUDA 同步成本随作用域扩大而增加。回答时应明确“barrier”和“memory ordering”不是同一个概念，且不同
primitives 有不同 scope。

标准回答
 warp：`__syncwarp(mask)` 和 warp-level primitives。

 cluster：Hopper/CC 9.0+ 的 cluster synchronization。
 grid：cooperative launch/grid group 或 kernel boundary；普通 blocks 不能随意做全 grid barrier。
 host-device / stream：events、stream waits、`cudaDeviceSynchronize()` 等。

Gotchas：常见失分点
 把 atomic 当成全局 barrier。
 忽略 thread scope 与 memory order。

题 09｜为什么 kernel launch 通常是异步的？如何正确计时？
难度     ★☆☆        频率     极高            标签       异步 / Benchmark




考察意图
考察是否会做正确 benchmark。

思路拆解
Host 发起 kernel launch 通常只是把工作 enqueue 到 stream；如果直接用 CPU wall-clock 包住 launch 而不等待完成，
测到的可能主要是 launch 时间。

标准回答
 同 stream 内操作保持顺序，但 host 可在 GPU 工作未完成时继续执行。
 测 kernel 时间优先使用 CUDA events，在同一 stream 记录 start/stop，并同步 stop event。
 端到端时间要包含用户真正关心的 H2D、kernel、D2H、同步和 CPU orchestration。
 benchmark 要 warm-up、多次迭代并报告统计量。

Gotchas：常见失分点
 用 `std::chrono` 只包 kernel launch 就宣称 kernel 耗时。

面试官可能继续追问
 CUDA event 计时与 Nsight timeline 有什么差别？
 为什么频繁 device-wide synchronize 会破坏 overlap？

题 10｜为什么 GPU 更偏 throughput，而 CPU 更偏 latency？
难度     ★☆☆        频率     高             标签       架构 / Latency Hiding




考察意图
考察你是否理解 GPU 为何需要大量线程。

思路拆解
GPU 不追求把单个 DRAM load 的延迟变得极低，而是保存大量 warp 状态，在一个 warp 等待时发射其他可运行 warp，
从而用并行度覆盖延迟。

标准回答
 CPU 用复杂缓存、分支预测、乱序执行等机制优化少量线程的单线程 latency。
 GPU 投入更多面积到算术吞吐与大量 resident threads，依赖 warp scheduling 隐藏 latency。
 因此 GPU 需要足够并行工作量；小任务、强串行依赖、频繁全局同步通常难以发挥 GPU。
 这也是 occupancy/TLP 与 ILP 成为 CUDA 性能优化核心变量的原因。

题 11｜请完整描述 GPU Memory Hierarchy。
难度      ★☆☆        频率       极高            标签       Memory / 基础




 30 秒答案 Register/Shared 在片上；Global/Local/Constant/Texture 主要驻留 device memory；L1/L2 是硬件 cache。




考察意图
这是公开 CUDA 面经可核验的高频题，核心是理解不同空间的 scope、latency 与管理方式。

思路拆解
回答不应只背“register/shared/global”，还要指出 local memory 虽然 thread-private，但通常位于 device
memory；L1/L2 是 cache 层级，shared 是显式管理 scratchpad。

标准回答
 Registers：on-chip、thread-private、最快但容量受限。
 Shared memory：on-chip、block-scoped、显式管理，可用于 reuse、reordering、协作。
 L1/texture/read-only cache：SM 侧硬件管理缓存路径；L2 是所有 SM 共享的 device-level cache。
 Global memory/HBM：容量大、延迟高、带宽高。Local memory 逻辑上属于线程，但物理上通常落到 device
  memory 并由 cache 缓解。
 Constant memory 适合 warp 内相同地址的广播式读取。

 说 local memory 在 SM 上。
 把 shared memory 与 L1 完全等同。

题 12｜Register 为什么快？为什么又不能无限使用？
难度     ★★☆          频率      高              标签       Register / 资源




考察意图
考察 register file 的双重角色：低延迟存储与 occupancy 限制。

思路拆解
Registers 是 thread-private 的片上存储，编译器尽量把标量和小型静态对象留在 register。但 register file 是每 SM 共享
的有限资源，per-thread 使用量越高，能同时驻留的 threads/warps/blocks 越少。

标准回答
 register access 延迟低，适合 accumulator、循环变量和 thread tile。
 总 register 需求大致随 registers/thread × resident threads 增长，并按架构粒度分配。
 过多 register 会降低 occupancy；过少则可能造成 spill，增加 local-memory traffic。
 高性能 kernel 往往有意接受较低 occupancy 来换取更大的 register tile 和 ILP。

Gotchas：常见失分点
 “寄存器越少越快”。
 只看 occupancy，不看 spills。

考察意图

题 21｜什么叫 Global Memory Coalescing？
难度      ★☆☆          频率       极高             标签       Coalescing / Global Memory




考察意图
这是 CUDA 优化的第一核心题：把 32 个线程的地址模式映射为实际 memory transactions。

思路拆解
Coalescing 不是简单说“线程地址连续”。正确分析要以 warp 为单位，看请求落在哪些对齐的 memory
segments/sectors 上，并尽可能用最少 transaction 覆盖有用数据。

标准回答
 对 compute capability 6.0+ 的常见简化：warp 请求会被服务成覆盖其地址所需的若干 32-byte transactions。
 连续且对齐的 32 个 float load（128 B useful）理想情况下可由 4 个 32-B transactions 覆盖。
 stride、misalignment、稀疏 gather 都可能使 transferred bytes 远大于 requested bytes。
 优化目标是提高 useful bytes / transferred bytes，而不是“看起来代码连续”。

Gotchas：常见失分点
 逐 thread 分析，不把 32 lanes 放在一起。
 认为只要相邻线程访问相邻元素就一定没有额外 transaction，忽略 alignment/边界。

考察意图

思路拆解
对于简单读写 kernel，effective bandwidth = (logical bytes read + logical bytes written) / time。它是“有用数据吞
吐”，可与实际 DRAM throughput/理论峰值联合分析。

标准回答
 例如 N 个 float 从 x 读、向 y 写：逻辑流量约 8N bytes。
 如果 N=1e9，时间 10 ms，则 effective BW≈800 GB/s。
 若 profiler 显示 DRAM 实际传输了远大于 8N bytes，说明访问效率差。
 若 effective BW 已接近设备可达峰值，则优化重点应转为减少 bytes，而非让 memory subsystem 更忙。

Gotchas：常见失分点
 把 cache 命中后的真实 DRAM bytes 与算法 logical bytes 混为一谈。

题 31｜Shared Memory Bank 是什么？

考察意图

思路拆解

题 32｜什么是 Bank Conflict？Broadcast 为什么是例外？
难度      ★☆☆        频率      极高            标签         Bank Conflict / Shared Memory




考察意图
考察冲突定义的精确性。




                                 GPU Kernel / HPC / AI Infra / 推理优化 · 26
                                                                          CUDA 编程优化面试 100 题 · 专业版


思路拆解
同一 warp 的一次 shared-memory 请求若多个不同地址映射到同一 bank，硬件需要拆成多个 conflict-free 请求，降低有
效带宽。但多个线程读取同一 shared address 可以广播，不按普通 conflict 处理。

标准回答
 冲突的本质是“same bank + different addresses”。
 n-way conflict 可近似理解为该 bank 上请求被分成 n 个阶段服务。
 broadcast/multicast 是重要例外，所以“同 bank 就冲突”是错误答案。

Gotchas：常见失分点
 把相同地址广播也算 32-way conflict。

题 33｜为什么 `tile[32][32]` 的列访问会出现 32-Way Bank Conflict？
难度      ★★☆       频率     极高             标签       Transpose / Bank




考察意图
考察能否手算 bank mapping。

思路拆解
若二维数组按 row-major，每行 32 个 float。沿同一列访问时，相邻线程地址相差 32 words；`(base + 32*t) mod 32` 恒
定，因此 32 lanes 映射到同一 bank 的不同地址。

标准回答
 stride=32 words 与 bank count=32 发生周期共振。
 结果是同一 warp 的列读取被高度序列化。
 这就是 transpose shared tile 的第二层优化问题。

Gotchas：常见失分点
 只说“因为按列访问不连续”，没有算 bank。

题 34｜为什么 `tile[32][33]` 能消除典型 Transpose Bank Conflict？
难度      ★★☆           频率       极高              标签      Padding / Bank




考察意图
考察 padding 的数学原因。

思路拆解
加一列 padding 后行 stride 从 32 变成 33 words。由于 33 mod 32 = 1，相邻 lane 的列访问会依次落到 bank 0,1,...31，
而不是都落同一 bank。

标准回答
 padding 改变的是 shared-memory address mapping，不是 global layout。
 代价是少量额外 shared capacity，通常远小于冲突序列化收益。
 更现代的高性能库也会使用 swizzled layouts，而不只依赖 +1 padding。

代码 / 白板骨架

 constexpr int TILE = 32;
 __shared__ float tile[TILE][TILE + 1]; // +1 改变列访问的 bank 映射


 int x = blockIdx.x * TILE + threadIdx.x;
 int y = blockIdx.y * TILE + threadIdx.y;
 tile[threadIdx.y][threadIdx.x] = in[y * width + x];
 __syncthreads();
 // 之后按转置坐标读取 tile，避免 32-way bank conflict。




Gotchas：常见失分点
 把 `[32][33]` 理解成改变矩阵逻辑形状。

题 35｜什么是 Warp Divergence？
难度      ★☆☆           频率       极高              标签      Divergence / Warp




考察意图
考察控制流效率。




                                      GPU Kernel / HPC / AI Infra / 推理优化 · 28
                                                                            CUDA 编程优化面试 100 题 · 专业版


思路拆解
Divergence 是同一 warp 内 active lanes 需要执行不同控制流路径。硬件会分别执行这些路径并用 mask 屏蔽不参与的

 长且代价相近的两条路径最容易造成明显浪费；短分支可能被 predication。

Gotchas：常见失分点
 “有 if 就 divergence”。

题 40｜如何写一个 Warp-Level Reduction？

思路拆解
32-lane warp 的和可以按 offset 16、8、4、2、1 做 `__shfl_down_sync`，每轮让低 lane 累加来自更高 lane 的值。完
整 block reduction 通常先每 warp reduction，再把 warp sums 合并。

标准回答
 32 个值归约到 1 个需要 log2(32)=5 轮。
 partial warp 要用 `__activemask()` 或 `__ballot_sync` 构造有效 mask。
 对于 floating-point sum，树形顺序与串行顺序不同，数值结果可能有舍入差异。

代码 / 白板骨架

 __device__ float warp_sum(float x, unsigned mask) {
     for (int offset = 16; offset > 0; offset >>= 1)
         x += __shfl_down_sync(mask, x, offset);
     return x;
 }

 只会写 shared-memory reduction。

题 41｜什么是 Occupancy？

题 44｜什么是 Register Pressure？如何权衡？

考察意图

题 51｜现场手写一个高性能 Reduction：你会如何逐版优化？
难度      ★★★            频率        极高               标签        Coding / Reduction




 30 秒答案 Reduction 的优化主线：减少 global atomics、减少 barriers/shared traffic、提高每线程工作量，最后用 warp
 shuffle。




考察意图
公开 CUDA 面经可核验的典型现场题。重点不是一次写出终极版，而是展示“发现瓶颈 → 逐版优化”的能力。

思路拆解
建议像《剑指 Offer》式按版本讲：global atomic 基线 → shared tree → sequential addressing → 每线程多元素 →
warp shuffle → vectorized/global grid reduction。每一步说明减少了什么成本。

标准回答
 V0：每元素 global atomic，正确但 contention 大。
 V1：每 block 在 shared 中归约，只让一个 thread global atomic。
 V2：使用 sequential addressing，减少 interleaved divergence 与地址运算。
 V3：每 thread 先累加多个元素，提高 load 吞吐与 arithmetic/loop efficiency。
 V4：最后一个 warp 用 shuffle，减少 shared traffic 和 block barriers。
 V5：大规模场景用两阶段 kernel、cooperative groups 或合适的 device-wide primitive；工程上优先考虑 CUB。

          i < n; i += gridDim.x * BLOCK * 2) {
         v += x[i];
         if (i + BLOCK < n) v += x[i + BLOCK];
     }
     unsigned mask = __activemask();
     for (int off = 16; off > 0; off >>= 1)
         v += __shfl_down_sync(mask, v, off);


     __shared__ float warp_sum[32];

题 57｜手写 Tiled Matrix Multiplication，并解释为什么快。

考察意图

思路拆解

 每 thread 做多个 outputs/register tiling 可进一步提高 reuse 和 ILP。
 现代高性能 GEMM 会继续分成 CTA tile、warp tile、MMA tile、thread/register tile，并使用 Tensor Core。

         Bs[threadIdx.y][threadIdx.x] = B[(k0 + threadIdx.y)*N + col];
         __syncthreads();

     }

题 61｜CUDA Stream 是什么？不同 Stream 真的能并发吗？
难度     ★☆☆         频率      极高             标签       Stream / 并发




考察意图
考察异步执行模型。

思路拆解
Stream 是有序的 GPU work queue。同一 stream 中操作按顺序建立依赖；不同 streams 之间在没有显式依赖且硬件资
源允许时，可以并发或 overlap。

标准回答
 不同 stream 并发不是保证：如果一个 kernel 已占满所有 SM/resource，另一个可能没有空间。
 copy/compute overlap 还依赖 copy engines、pinned memory、方向和平台能力。
 default stream 的语义需明确，避免无意的全局依赖。
 events 可在 streams 之间表达依赖，而不做 device-wide barrier。

Gotchas：常见失分点
 “两个 stream 就一定同时跑”。

题 66｜什么是 Software Pipelining？
难度      ★★★            频率        极高              标签       Software Pipeline / 真题




 30 秒答案 Software pipelining = 把不同迭代的 load/compute 重叠，用额外 buffer/stage 换 latency hiding。




考察意图
这是公开 NVIDIA 面经可核验的现代 CUDA 题。考察你能否把循环迭代拆成多个重叠阶段。

思路拆解
在 tiled GEMM 等 K-loop 中，不再“load tile i → compute i → load tile i+1”，而是提前预取 future tile，使 memory
stage 与 current compute 同时进行。

标准回答
 把循环拆成 prologue、steady state、epilogue。
 需要至少双缓冲：一个 buffer 被 consumer 计算，另一个 buffer 被 producer 填充。
 更深 pipeline 可进一步隐藏 latency，但会消耗更多 shared/register resources。
 Software pipeline 的目标是减少 exposed latency，而不是减少 total bytes。

题 67｜什么是 Double Buffering / Multi-Stage Pipeline？

考察意图

题 98｜为什么 `cudaMallocAsync` / Stream-Ordered Allocator 更适合高性能程
序？

 现代 Best Practices 明确推荐使用 stream-ordered pool allocator 管理设备内存。

 把异步 allocator 当成无生命周期约束的普通 malloc。

题 99｜CUDA Tile C++ / Tile Programming 为什么值得关注？

考察意图
考察 2026 年的新编程模型趋势。

思路拆解
CUDA 13.3 首次正式引入 CUDA Tile C++ API，把“tile”而非 thread 作为主要程序抽象之一，旨在更自然表达

 SIMT 与 Tile 可共存；高级岗位应比较 CUDA Tile、Triton、CuTe/CUTLASS 的抽象边界。
