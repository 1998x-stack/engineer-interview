# Q002｜CUDA 为什么称 SIMT，而不是传统 SIMD？

> **一句话核心**：SIMT 允许每个 thread 拥有独立逻辑状态，而硬件按 warp 共同发射指令。
>
> **章节**：第 1 章 · CUDA 执行模型与 SIMT  
> **难度**：★☆☆ · **频率**：高 · **标签**：SIMT / 架构

## PDF 基线题解

## 考察意图
考察你是否理解 CUDA “线程语义”与底层矢量化执行之间的关系。

## 思路拆解
SIMD 把 lane 暴露给程序员，而 SIMT 给每个 CUDA thread 独立的线程语义、寄存器状态和控制流，再由硬件把线程聚成
warp。这个差异直接解释了 divergence 为什么存在。

## 标准回答
- SIMD 的抽象是“一条显式向量指令操作多个 lane”；SIMT 的抽象是“多个逻辑线程被硬件以 warp 形式共同发
射”。
- 每个 CUDA thread 有自己的 threadIdx、寄存器和逻辑控制流状态；但 warp 中 active lanes 通常共享同一条被发射的
指令。
- 发生分支时，SIMT 能表达不同线程走不同路径；硬件通过 active mask/重汇合机制执行这些路径，因此可能降低 lane
利用率。

## Gotchas：常见失分点
- 把 SIMT 解释成“32 个 CUDA core 同时执行”。
- 忽略 independent thread scheduling 对 warp-synchronous 代码的影响。

## 面试官可能继续追问
- Volta 之后 independent thread scheduling 改变了什么？
- 为什么 warp-level primitive 需要 mask？

---

## 深入分析

SIMT 允许每个 thread 拥有独立逻辑状态，而硬件按 warp 共同发射指令。divergence 的成本来自 active mask 下的路径序列化，而不是 `if` 语法本身。

### 深入理解：从编程抽象映射到硬件状态

这一章的题，核心不是背 `threadIdx`/`blockIdx`，而是建立 **logical execution → warp issue → SM residency** 的映射。真正的性能问题通常发生在 warp 粒度：同一 warp 的 active mask、memory request、barrier 参与者以及 scheduler 是否有 eligible warp。

建议始终画出两张图：

```text
Programming: Grid → Block → Thread
Hardware:    GPU → SM → Warp Scheduler → Warp(32 lanes)
```

当回答涉及同步时，再补一层 memory ordering：barrier 解决“谁到达了某个程序点”，memory fence/同步语义解决“谁能看见哪些写入”。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`launch configuration`、`active warps`、`branch efficiency`、`barrier behavior`。

### 架构视角

Volta 之后 independent thread scheduling 使隐式 warp-synchronous 假设更危险；显式使用 warp-level sync/mask。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

SIMT 让每个 CUDA thread 保留独立的寄存器状态、predicate 与逻辑控制流，同时硬件把 32 个线程组织成 warp 发射指令。它比“显式向量寄存器 + lane”更适合表达通用并行程序。

### 2. 定量推导 / 性能模型

若 warp 的两个分支分别激活比例 $p$ 与 $1-p$，且两条路径成本接近，则粗略 lane 利用率可下降到约 $1/2$；真实代价还取决于 predication、路径长度和重汇合。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
int lane = threadIdx.x & 31;
float y;
if (lane < 16) y = f_a(x);
else           y = f_b(x);
// 逻辑上每线程独立；硬件可能需要分别执行两条路径。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Warp State / Branch Statistics`
- `Branch Efficiency 与 divergent branch 指标`
- `Eligible/Active warps：判断 divergence 是否真的成为吞吐瓶颈`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Volta 以后 independent thread scheduling 弱化了“warp 内永远严格 lockstep”的旧假设；warp-synchronous 算法要使用正确的 mask 与同步原语。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

构造同 warp 内 0%、25%、50%、75%、100% 线程走慢路径的 kernel，对比短分支与长分支，观察编译器 predication 和真实 divergence 成本。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
