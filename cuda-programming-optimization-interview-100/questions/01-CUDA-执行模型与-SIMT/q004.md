# Q004｜Kernel launch 后，Block 是如何调度到 SM 的？

> **一句话核心**：Block 调度受 registers、shared memory、threads/warps、block slot 等多个上限共同约束。
>
> **章节**：第 1 章 · CUDA 执行模型与 SIMT  
> **难度**：★★☆ · **频率**：高 · **标签**：调度 / Occupancy

## PDF 基线题解

## 考察意图
考察资源约束和动态 block 调度的理解。

## 思路拆解
Block 调度不是静态绑定。SM 只有在 register、shared memory、thread/warp slots、block slots 等资源都够时，才可
以让新 block resident。

## 标准回答
- Grid 中 blocks 可被动态分派给可用 SM，程序通常不应依赖某个 block 被放在哪个 SM。
- 一个 SM 的 resident blocks 上限是多个约束的最小值：线程数、warp 数、寄存器、shared memory、block slot 等。
- 当一个 resident block 完成，释放资源后，SM 才能接纳后续 block；因此 grid 足够大才能形成持续的 waves。
- 尾部只剩少量 blocks 时，可能出现 tail effect，即一部分 SM 已空闲但 kernel 尚未结束。

## Gotchas：常见失分点
- 把 block 调度顺序当作确定的。
- 依赖 blockIdx 推断物理 SM。

## 面试官可能继续追问
- 什么是 wave quantization / tail effect？
- persistent kernel 为什么会改变 block 工作方式？

---

## 深入分析

Block 调度受 registers、shared memory、threads/warps、block slot 等多个上限共同约束。Grid 足够大时，block 会动态填充可用 SM；尾部 wave 可能产生 tail effect。

### 深入理解：从编程抽象映射到硬件状态

这一章的题，核心不是背 `threadIdx`/`blockIdx`，而是建立 **logical execution → warp issue → SM residency** 的映射。真正的性能问题通常发生在 warp 粒度：同一 warp 的 active mask、memory request、barrier 参与者以及 scheduler 是否有 eligible warp。

建议始终画出两张图：

```text
Programming: Grid → Block → Thread
Hardware:    GPU → SM → Warp Scheduler → Warp(32 lanes)
```

当回答涉及同步时，再补一层 memory ordering：barrier 解决“谁到达了某个程序点”，memory fence/同步语义解决“谁能看见哪些写入”。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`launch configuration`、`active warps`、`branch efficiency`、`barrier behavior`。

### 架构视角

Volta 之后 independent thread scheduling 使隐式 warp-synchronous 假设更危险；显式使用 warp-level sync/mask。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Block 调度是资源约束下的动态 residency 问题。一个 SM 能接纳新 block，必须同时满足 threads、warps、register file、shared memory、block slots 等限制。

### 2. 定量推导 / 性能模型

可写成 $B_{resident}=\min(B_{threads},B_{warps},B_{regs},B_{smem},B_{slots})$。任意一项先触顶，就成为 residency limiter。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// 例：动态 shared memory 会直接改变每 SM 可驻留 block 数
kernel<<<grid, 256, smem_bytes>>>(...);
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Occupancy / Launch Statistics 中的 limiting factor`
- `Waves per SM：判断 grid 是否足够覆盖设备`
- `Registers per thread 与 shared memory per block`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Hopper/Blackwell 的 thread-block cluster 会约束一组 blocks 在同一 GPC 中协同调度；普通 block 的资源分配原则仍然成立，但 cluster shape 又增加一层调度约束。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

固定计算逻辑，逐步增加动态 shared memory，从 0KB 到接近 SM 上限；画出 active blocks/SM 与 kernel time 的阶梯变化。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
