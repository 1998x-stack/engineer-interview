# Q005｜为什么 block size 常从 128/256 开始，而不是随便选？

> **一句话核心**：128/256 只是实验起点：warp 整数倍减少空 lane，同时常能在 occupancy、调度开销和每 block 资源之间取得平衡。
>
> **章节**：第 1 章 · CUDA 执行模型与 SIMT  
> **难度**：★☆☆ · **频率**：极高 · **标签**：Block Size / Warp

## PDF 基线题解

## 考察意图
考察 block size 与 warp 填充、资源占用、延迟隐藏之间的权衡。

## 思路拆解
“256 最快”不是规律。合理起点来自两个事实：threads/block 应是 32 的倍数以减少 under-populated warp；同时
128-256 往往能在并行度与 block 数之间提供不错的初始平衡。最终必须 profile。

## 标准回答
- blockDim 最好是 warp size 的整数倍；例如 100 threads 会生成 4 个 warps，其中最后一个只有 4 个 active lanes。
- 较大 block 可增加单 block 并行度，但也会增加每 block 的 register/shared-memory 总消耗。
- 较小 block 可能让更多 blocks 同时 resident，有利于隐藏 barrier 或 memory latency。
- 官方 Best Practices 把 128-256 作为实验起点，而非固定答案。

## Gotchas：常见失分点
- 回答“256 是官方推荐，所以一定最优”。

## 深入分析

128/256 只是实验起点：warp 整数倍减少空 lane，同时常能在 occupancy、调度开销和每 block 资源之间取得平衡。最终值必须通过 occupancy/resource + benchmark 确定。

### 深入理解：从编程抽象映射到硬件状态

这一章的题，核心不是背 `threadIdx`/`blockIdx`，而是建立 **logical execution → warp issue → SM residency** 的映射。真正的性能问题通常发生在 warp 粒度：同一 warp 的 active mask、memory request、barrier 参与者以及 scheduler 是否有 eligible warp。

建议始终画出两张图：

```text
Programming: Grid → Block → Thread
Hardware:    GPU → SM → Warp Scheduler → Warp(32 lanes)
```

当回答涉及同步时，再补一层 memory ordering：barrier 解决“谁到达了某个程序点”，memory fence/同步语义解决“谁能看见哪些写入”。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`launch configuration`、`active warps`、`branch efficiency`、`barrier behavior`。

### 架构视角

Volta 之后 independent thread scheduling 使隐式 warp-synchronous 假设更危险；显式使用 warp-level sync/mask。

## 实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

1. 写一个**正确但未优化**的 baseline。
2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
4. 使用 Nsight Compute 收集与本题直接相关的指标：`launch configuration`、`active warps`、`branch efficiency`、`barrier behavior`。
5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

128/256 只是搜索起点：它们是 warp 的整数倍，并通常能在并行度、调度粒度、register/shared resource 与 barrier 成本之间取得不错平衡。最终最优值由 kernel 资源和 problem shape 决定。

### 2. 定量推导 / 性能模型

block size 改变 $W_{block}=T/32$，同时影响 $B_{resident}$；实际可用 warp 数约为 $W_{active}=W_{block}\times B_{resident}$。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
for (int bs : {64,128,256,512}) {
  // benchmark kernel<<<grid_for(bs), bs>>>()
}
// 不以 occupancy 单指标选赢家。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Kernel time：最终判据`
- `Achieved occupancy / active warps`
- `Register allocation、smem/block、waves per SM`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

不同 compute capability 的 SM 资源上限不同；迁移 GPU 时应重新 sweep block size，而不是把 A100 上的 256 固化成跨架构常数。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

对 memory-bound、compute-bound、barrier-heavy 三类微基准分别 sweep 64–1024 threads/block，比较最优点为何不同。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
