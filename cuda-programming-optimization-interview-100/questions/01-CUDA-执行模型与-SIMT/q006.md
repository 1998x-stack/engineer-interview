# Q006｜什么是 Grid-Stride Loop？为什么它是 CUDA 常用模式？

> **一句话核心**：Grid-stride loop 把“问题规模”与“launch 规模”解耦，便于限制 blocks 数、复用线程、实现 persistent 风格，也便于用 1 block/1 thread 调试同一 kernel。
>

## PDF 基线题解

## 考察意图
考察是否具备可扩展 kernel 的基本编码习惯。

## 思路拆解
Grid-stride loop 让线程处理多个逻辑元素，解耦数据规模 N 与 launch 的 block 数；它还能控制 grid 大小、复用线程上
下文，并方便做 persistent-style 工作分配。

## 标准回答
- 初始索引 i = blockIdx.x * blockDim.x + threadIdx.x。
- 步长 stride = blockDim.x * gridDim.x；每个线程处理 i, i+stride, ...。
- 连续线程的第一次访问仍保持连续，因此可以保留 coalescing。
- 它允许将 gridDim 调到与 SM 数、work chunking 等更适配，而不是盲目发 N/threads 个 blocks。

## 代码 / 白板骨架

```cpp
__global__ void saxpy(int n, float a, const float* x, float* y) {
for (int i = blockIdx.x * blockDim.x + threadIdx.x;
i < n;
i += blockDim.x * gridDim.x) {
y[i] = a * x[i] + y[i];
}
}

```

## Gotchas：常见失分点
- stride 写成 blockDim.x 而忽略 gridDim.x。
- 把 grid-stride loop 与 strided memory access 混为一谈：前者每一轮 warp 内仍可连续。

## 深入分析

Grid-stride loop 把“问题规模”与“launch 规模”解耦，便于限制 blocks 数、复用线程、实现 persistent 风格，也便于用 1 block/1 thread 调试同一 kernel。

### 深入理解：从编程抽象映射到硬件状态

这一章的题，核心不是背 `threadIdx`/`blockIdx`，而是建立 **logical execution → warp issue → SM residency** 的映射。真正的性能问题通常发生在 warp 粒度：同一 warp 的 active mask、memory request、barrier 参与者以及 scheduler 是否有 eligible warp。

建议始终画出两张图：

```text
Programming: Grid → Block → Thread
Hardware:    GPU → SM → Warp Scheduler → Warp(32 lanes)
```

当回答涉及同步时，再补一层 memory ordering：barrier 解决“谁到达了某个程序点”，memory fence/同步语义解决“谁能看见哪些写入”。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓

        ↓

```

对于本题，建议至少观察：`launch configuration`、`active warps`、`branch efficiency`、`barrier behavior`。

### 架构视角

Volta 之后 independent thread scheduling 使隐式 warp-synchronous 假设更危险；显式使用 warp-level sync/mask。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Grid-stride loop 把“并行 worker 数”与“问题元素数”解耦。它允许控制 grid 大小、线程重复处理多个元素，并自然支持 persistent-style 或 cache-friendly 的工作分配。

### 2. 定量推导 / 性能模型

线程起点 $i_0=b\cdot T+t$，步长 $S=T\cdot G$。只要相邻 lane 的 $i_0$ 连续，每次迭代仍可保持 coalesced access。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
for (int i = blockIdx.x * blockDim.x + threadIdx.x;
     i < n;
     i += blockDim.x * gridDim.x) {
  y[i] = f(x[i]);
}
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Memory coalescing：确认 stride loop 没破坏 lane 连续性`
- `Waves per SM / grid size`
- `Instruction overhead：循环控制在小 workload 中是否显著`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

它是架构无关的基础模式；在 persistent kernel 中会进一步把 grid 固定到与 SM 数相关的规模，并从 work queue 取任务。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

对同一 vector kernel 比较“一元素一线程的超大 grid”和“约 2–4×SM 数 blocks 的 grid-stride loop”，观察 launch/grid 管理和缓存差异。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
