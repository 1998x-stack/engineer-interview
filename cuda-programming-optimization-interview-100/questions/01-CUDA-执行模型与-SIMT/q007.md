# Q007｜`__syncthreads()` 到底同步什么？

> **一句话核心**：`__syncthreads()` 是 block barrier，并带有对 block participating threads 有意义的内存可见性语义。
>
> **章节**：第 1 章 · CUDA 执行模型与 SIMT  
> **难度**：★★☆ · **频率**：极高 · **标签**：同步 / 内存模型

## PDF 基线题解

## 考察意图
考察 barrier 语义，而不是只会背“同步 block”。

## 思路拆解
正确答案至少包含两层：它是 block 范围的 barrier；同时对参与线程建立内存顺序，使 barrier 前的共享/全局内存操作在
相应语义下对参与线程可见。

## 标准回答
- 同一个 thread block 中所有尚未退出且需要参与该 barrier 的线程必须到达同一个同步点。
- `__syncthreads()` 常用于“shared memory 生产者写完 → 消费者读取”之间。
- 把 barrier 放在非一致控制流中非常危险：如果部分线程到达、部分线程永远到不了，行为是错误的。
- 同步不是缓存刷新魔法；跨 block 通信需要更高层同步/原子/内存顺序机制。

## 代码 / 白板骨架

```cpp
// 错误范式：条件可能在 block 内不一致
if (threadIdx.x < valid) {
__syncthreads();
}

// 更常见的正确思路：所有线程都到 barrier，
// 只有读写本身按 valid 条件屏蔽。

```

## Gotchas：常见失分点
- 在 `if (tid < n) __syncthreads();` 中让不同线程条件不同。
- 认为 `__syncthreads()` 可以同步整个 grid。

## 深入分析

`__syncthreads()` 是 block barrier，并带有对 block participating threads 有意义的内存可见性语义。最大陷阱是条件分支导致部分线程永远到不了 barrier。

### 深入理解：从编程抽象映射到硬件状态

这一章的题，核心不是背 `threadIdx`/`blockIdx`，而是建立 **logical execution → warp issue → SM residency** 的映射。真正的性能问题通常发生在 warp 粒度：同一 warp 的 active mask、memory request、barrier 参与者以及 scheduler 是否有 eligible warp。

建议始终画出两张图：

```text
Programming: Grid → Block → Thread
Hardware:    GPU → SM → Warp Scheduler → Warp(32 lanes)
```

当回答涉及同步时，再补一层 memory ordering：barrier 解决“谁到达了某个程序点”，memory fence/同步语义解决“谁能看见哪些写入”。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`launch configuration`、`active warps`、`branch efficiency`、`barrier behavior`。

### 架构视角

Volta 之后 independent thread scheduling 使隐式 warp-synchronous 假设更危险；显式使用 warp-level sync/mask。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

`__syncthreads()` 同时是 block barrier 与相应范围的内存可见性同步点。所有需要参与该 barrier 的线程必须以一致的控制流到达，否则代码可能未定义或挂起。

### 2. 定量推导 / 性能模型

barrier 成本不仅是指令本身；真正损失来自 $T_{wait}=\max_i t_i-\min_i t_i$：线程到达时间越不均衡，等待越严重。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
__shared__ float s[256];
s[threadIdx.x] = x;
__syncthreads();
// 此后 block 内线程可安全读取其他线程写入的 s[]。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Warp Stall: Barrier`
- `Warp State：到达 barrier 前的 imbalance`
- `Source Counters：定位高频 barrier 源码行`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

异步 pipeline、TMA 和 warp specialization 越复杂，越不应把 `__syncthreads()` 当万能同步；应选择 warp/barrier/mbarrier 等最小必要同步范围。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

构造 barrier 前每个 warp 工作量不同的 kernel，再把工作重新平衡；即使 barrier 数不变，也可观察 barrier stall 明显下降。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
