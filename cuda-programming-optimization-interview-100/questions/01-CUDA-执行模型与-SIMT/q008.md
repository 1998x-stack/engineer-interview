# Q008｜CUDA 有哪些同步层级？

> **一句话核心**：同步要区分作用域（warp/block/cluster/grid/host）与语义（barrier、event、fence、atomic order）。
>
> **章节**：第 1 章 · CUDA 执行模型与 SIMT  
> **难度**：★★☆ · **频率**：高 · **标签**：同步 / Cooperative Groups

## PDF 基线题解

## 考察意图
考察你能否构建从 warp 到 system 的同步层级。

## 思路拆解
CUDA 同步成本随作用域扩大而增加。回答时应明确“barrier”和“memory ordering”不是同一个概念，且不同
primitives 有不同 scope。

## 标准回答
- warp：`__syncwarp(mask)` 和 warp-level primitives。
- block：`__syncthreads()`、block-scoped barrier。
- cluster：Hopper/CC 9.0+ 的 cluster synchronization。
- grid：cooperative launch/grid group 或 kernel boundary；普通 blocks 不能随意做全 grid barrier。
- host-device / stream：events、stream waits、`cudaDeviceSynchronize()` 等。

## Gotchas：常见失分点
- 把 atomic 当成全局 barrier。
- 忽略 thread scope 与 memory order。

## 面试官可能继续追问
- 什么是 release/acquire？
- 为什么跨 GPU/system scope 更昂贵？

## 深入分析

同步要区分作用域（warp/block/cluster/grid/host）与语义（barrier、event、fence、atomic order）。高分回答会说明“同步执行进度”和“建立内存顺序”不是完全同一个问题。

### 深入理解：从编程抽象映射到硬件状态

这一章的题，核心不是背 `threadIdx`/`blockIdx`，而是建立 **logical execution → warp issue → SM residency** 的映射。真正的性能问题通常发生在 warp 粒度：同一 warp 的 active mask、memory request、barrier 参与者以及 scheduler 是否有 eligible warp。

建议始终画出两张图：

```text
Programming: Grid → Block → Thread
Hardware:    GPU → SM → Warp Scheduler → Warp(32 lanes)
```

当回答涉及同步时，再补一层 memory ordering：barrier 解决“谁到达了某个程序点”，memory fence/同步语义解决“谁能看见哪些写入”。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`launch configuration`、`active warps`、`branch efficiency`、`barrier behavior`。

### 架构视角

Volta 之后 independent thread scheduling 使隐式 warp-synchronous 假设更危险；显式使用 warp-level sync/mask。

## 实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

1. 写一个**正确但未优化**的 baseline。
2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
4. 使用 Nsight Compute 收集与本题直接相关的指标：`launch configuration`、`active warps`、`branch efficiency`、`barrier behavior`。
5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

CUDA 同步要同时区分“参与者范围”和“内存顺序/可见性”。常见范围包括 warp、block、cluster、grid/cooperative launch、stream/device/host；选择过大的同步范围会把本可并行的工作串行化。

### 2. 定量推导 / 性能模型

同步优化的原则可写成：选择满足 correctness 的最小 scope，令 $T_{sync}=T_{barrier}+T_{imbalance}+T_{serialization}$ 尽可能小。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
__syncwarp(mask);      // warp 范围
__syncthreads();       // block 范围
// cluster.sync();      // cluster 范围（支持的架构/编程接口）
// cudaEventRecord...   // stream 间依赖可用 event 建立
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Warp stall barrier`
- `Timeline 上的 stream/device synchronization gaps`
- `Memory ordering bug 用 Compute Sanitizer 辅助检查`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Compute Capability 9.0+ 的 thread-block cluster 增加 cluster 级同步与 DSM；现代异步内存操作又引入 barrier phase/arrival 语义。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

实现同一 producer-consumer 逻辑，分别使用 device-wide sync、event、block sync 和 warp sync，在保证正确性的版本中比较同步范围与并发度。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
