# Q009｜为什么 kernel launch 通常是异步的？如何正确计时？

> **一句话核心**：默认 kernel launch 对 host 异步，因此 CPU wall-clock 若不同步通常只量到 enqueue。
>
> **章节**：第 1 章 · CUDA 执行模型与 SIMT  
> **难度**：★☆☆ · **频率**：极高 · **标签**：异步 / Benchmark

## PDF 基线题解

## 考察意图
考察是否会做正确 benchmark。

## 思路拆解
Host 发起 kernel launch 通常只是把工作 enqueue 到 stream；如果直接用 CPU wall-clock 包住 launch 而不等待完成，
测到的可能主要是 launch 时间。

## 标准回答
- 同 stream 内操作保持顺序，但 host 可在 GPU 工作未完成时继续执行。
- 测 kernel 时间优先使用 CUDA events，在同一 stream 记录 start/stop，并同步 stop event。
- 端到端时间要包含用户真正关心的 H2D、kernel、D2H、同步和 CPU orchestration。
- benchmark 要 warm-up、多次迭代并报告统计量。

## Gotchas：常见失分点
- 用 `std::chrono` 只包 kernel launch 就宣称 kernel 耗时。

## 面试官可能继续追问
- CUDA event 计时与 Nsight timeline 有什么差别？
- 为什么频繁 device-wide synchronize 会破坏 overlap？

## 深入分析

默认 kernel launch 对 host 异步，因此 CPU wall-clock 若不同步通常只量到 enqueue。GPU event 更适合测 stream 中的设备执行时间，并要做 warm-up。

### 深入理解：从编程抽象映射到硬件状态

这一章的题，核心不是背 `threadIdx`/`blockIdx`，而是建立 **logical execution → warp issue → SM residency** 的映射。真正的性能问题通常发生在 warp 粒度：同一 warp 的 active mask、memory request、barrier 参与者以及 scheduler 是否有 eligible warp。

建议始终画出两张图：

```text
Programming: Grid → Block → Thread
Hardware:    GPU → SM → Warp Scheduler → Warp(32 lanes)
```

当回答涉及同步时，再补一层 memory ordering：barrier 解决“谁到达了某个程序点”，memory fence/同步语义解决“谁能看见哪些写入”。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`launch configuration`、`active warps`、`branch efficiency`、`barrier behavior`。

### 架构视角

Volta 之后 independent thread scheduling 使隐式 warp-synchronous 假设更危险；显式使用 warp-level sync/mask。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Kernel launch 通常只把工作 enqueue 到 CUDA stream，CPU 立即继续。因此 host wall-clock 若不等待 GPU 完成，会主要测到 enqueue/launch cost，而不是 kernel execution。

### 2. 定量推导 / 性能模型

正确设备侧计时常用 $T=(event_{stop}-event_{start})$；若 kernel 极短，还应区分 launch overhead、queueing 与 device execution。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
cudaEventRecord(start, stream);
kernel<<<grid, block, 0, stream>>>(...);
cudaEventRecord(stop, stream);
cudaEventSynchronize(stop);
cudaEventElapsedTime(&ms, start, stop);
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Nsight Systems：CPU launch 到 GPU execution 的时间线`
- `CUDA API Statistics：launch/sync overhead`
- `GPU event：隔离设备执行时间`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

CUDA Graph 对大量微小、重复 launch 的收益，本质上就是减少 host-side launch/dispatch overhead；这与“kernel 本身是否快”是两个层次。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

用空 kernel、1–5µs kernel、100µs kernel 比较 CPU wall-clock、GPU event 和 Nsight Systems 时间线，理解 launch overhead 占比。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
