# Q010｜为什么 GPU 更偏 throughput，而 CPU 更偏 latency？

> **一句话核心**：GPU 用大量 resident warps 与宽吞吐资源隐藏长 latency；CPU 则投入更复杂的缓存、预测、乱序与少量强核心降低单线程 latency。
>
> **章节**：第 1 章 · CUDA 执行模型与 SIMT  
> **难度**：★☆☆ · **频率**：高 · **标签**：架构 / Latency Hiding

## PDF 基线题解

## 考察意图
考察你是否理解 GPU 为何需要大量线程。

## 思路拆解
GPU 不追求把单个 DRAM load 的延迟变得极低，而是保存大量 warp 状态，在一个 warp 等待时发射其他可运行 warp，
从而用并行度覆盖延迟。

## 标准回答
- CPU 用复杂缓存、分支预测、乱序执行等机制优化少量线程的单线程 latency。
- GPU 投入更多面积到算术吞吐与大量 resident threads，依赖 warp scheduling 隐藏 latency。
- 因此 GPU 需要足够并行工作量；小任务、强串行依赖、频繁全局同步通常难以发挥 GPU。
- 这也是 occupancy/TLP 与 ILP 成为 CUDA 性能优化核心变量的原因。

## Gotchas：常见失分点
- 把 GPU 说成“每个 core 比 CPU core 更快”。

## 面试官可能继续追问
- 什么情况下 CPU 版本反而可能更快？
- GPU 的 register file 为什么很大？

## 深入分析

GPU 用大量 resident warps 与宽吞吐资源隐藏长 latency；CPU 则投入更复杂的缓存、预测、乱序与少量强核心降低单线程 latency。

### 深入理解：从编程抽象映射到硬件状态

这一章的题，核心不是背 `threadIdx`/`blockIdx`，而是建立 **logical execution → warp issue → SM residency** 的映射。真正的性能问题通常发生在 warp 粒度：同一 warp 的 active mask、memory request、barrier 参与者以及 scheduler 是否有 eligible warp。

建议始终画出两张图：

```text
Programming: Grid → Block → Thread
Hardware:    GPU → SM → Warp Scheduler → Warp(32 lanes)
```

当回答涉及同步时，再补一层 memory ordering：barrier 解决“谁到达了某个程序点”，memory fence/同步语义解决“谁能看见哪些写入”。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`launch configuration`、`active warps`、`branch efficiency`、`barrier behavior`。

### 架构视角

Volta 之后 independent thread scheduling 使隐式 warp-synchronous 假设更危险；显式使用 warp-level sync/mask。

## 实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

1. 写一个**正确但未优化**的 baseline。
2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

CPU 用复杂控制、缓存、乱序执行追求单线程/少线程 latency；GPU 用大量执行上下文和宽吞吐资源，让另一个 ready warp 在当前 warp 等待时接管 issue slot。

### 2. 定量推导 / 性能模型

粗略上，要隐藏延迟 $L$，需要足够独立工作满足 $N_{ready}\times I_{issue}$ 覆盖等待窗口；因此“更多 warp”只是增加可隐藏延迟机会，而非降低 DRAM 本身 latency。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// GPU 风格：大量独立工作项
int i = blockIdx.x * blockDim.x + threadIdx.x;
if (i < n) out[i] = f(in[i]);
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Eligible warps per scheduler`
- `Issue slot utilization`
- `Long/short scoreboard stall 与 active warps`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

新架构通过更强异步数据移动、Tensor Core 与专门 pipeline 继续强化 throughput 设计；高性能 kernel 的任务是让这些流水持续有独立 work。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

用 pointer chasing（强依赖、低并行）和独立数组操作（高并行）对比 GPU 利用率，展示 latency-bound 与 throughput-friendly workload 的差异。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
