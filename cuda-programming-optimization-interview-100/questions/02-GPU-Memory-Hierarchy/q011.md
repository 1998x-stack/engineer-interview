# Q011｜请完整描述 GPU Memory Hierarchy。

> **一句话核心**：Register/Shared 在片上；Global/Local/Constant/Texture 主要驻留 device memory；L1/L2 是硬件 cache。
>
> **章节**：第 2 章 · GPU Memory Hierarchy  
> **难度**：★☆☆ · **频率**：极高 · **标签**：Memory / 基础

## PDF 基线题解

> **30 秒答案**：Register/Shared 在片上；Global/Local/Constant/Texture 主要驻留 device memory；L1/L2 是硬件 cache。

## 考察意图
这是公开 CUDA 面经可核验的高频题，核心是理解不同空间的 scope、latency 与管理方式。

## 思路拆解
回答不应只背“register/shared/global”，还要指出 local memory 虽然 thread-private，但通常位于 device
memory；L1/L2 是 cache 层级，shared 是显式管理 scratchpad。

## 标准回答
- Registers：on-chip、thread-private、最快但容量受限。
- Shared memory：on-chip、block-scoped、显式管理，可用于 reuse、reordering、协作。
- L1/texture/read-only cache：SM 侧硬件管理缓存路径；L2 是所有 SM 共享的 device-level cache。
- Global memory/HBM：容量大、延迟高、带宽高。Local memory 逻辑上属于线程，但物理上通常落到 device
memory 并由 cache 缓解。
- Constant memory 适合 warp 内相同地址的广播式读取。

## Gotchas：常见失分点
- 说 local memory 在 SM 上。
- 把 shared memory 与 L1 完全等同。

## 面试官可能继续追问
- 哪些数据应该放 shared，而不是依赖 L1？
- L2 对跨 block 复用有什么意义？

## 深入分析

不要只背层级顺序，要能说明每层的作用域与管理方式：register thread-private；shared block-scoped programmer-managed；L2 device-wide；HBM 大容量高带宽但高延迟。

### 深入理解：性能首先是“数据在哪里”

内存层级题要用 **容量、作用域、管理方式、延迟/带宽、可见性、占用资源** 六个维度比较，而不是简单排序“register 最快、HBM 最慢”。很多优化本质是把数据从低复用、高成本层级搬到高复用、低成本层级，并控制搬运次数。

```text
HBM/DRAM → L2 → L1/Shared → Register
                ↑ programmer-managed reuse often happens here
```

同时要记住：register/shared 是稀缺的片上资源，它们会反过来限制 residency；因此数据越靠近计算单元并不自动意味着 kernel 越快。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`register count / spill`、`shared-memory usage`、`L1/L2 hit rate`、`DRAM bytes`。

### 架构视角

Ampere/Hopper/Blackwell 持续增强 cache 与异步数据移动，但 register/shared 仍是 occupancy 的关键资源。

## 实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

1. 写一个**正确但未优化**的 baseline。
2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
4. 使用 Nsight Compute 收集与本题直接相关的指标：`register count / spill`、`shared-memory usage`、`L1/L2 hit rate`、`DRAM bytes`。
5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

GPU memory hierarchy 要同时按“物理位置、作用域、缓存行为、生命周期、管理方式”回答。Registers/shared 片上，global/local 通常落在 device memory；L1/L2 是缓存层，constant/texture 具有特殊访问路径。

### 2. 定量推导 / 性能模型

可用近似代价模型：$T_{mem}=T_{latency}+Bytes/BW+T_{serialization}$；不同层级的优化重点分别是 latency、带宽、复用和冲突。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
__global__ void k(const float* g) {
  __shared__ float s[256]; // block scope
  float r = g[threadIdx.x]; // r 倾向寄存器
  s[threadIdx.x] = r;
}
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Memory Workload Analysis：L1/L2/DRAM`
- `Local memory load/store：发现 spill`
- `Shared memory throughput / bank conflicts`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Hopper/Blackwell 增加 TMA、DSM、TMEM 等新数据通路，但经典 hierarchy 仍是分析基础；TMEM 与 TMA 不应混为一类“缓存”。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

同一数据分别以重复 global load、shared tile reuse、register reuse 三种方式计算，测 bytes 与 latency/throughput 差异。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
