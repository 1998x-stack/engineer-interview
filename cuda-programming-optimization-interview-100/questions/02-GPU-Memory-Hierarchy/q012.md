# Q012｜Register 为什么快？为什么又不能无限使用？

> **一句话核心**：register 快但稀缺。
>
> **章节**：第 2 章 · GPU Memory Hierarchy  
> **难度**：★★☆ · **频率**：高 · **标签**：Register / 资源

## PDF 基线题解

## 考察意图
考察 register file 的双重角色：低延迟存储与 occupancy 限制。

## 思路拆解
Registers 是 thread-private 的片上存储，编译器尽量把标量和小型静态对象留在 register。但 register file 是每 SM 共享
的有限资源，per-thread 使用量越高，能同时驻留的 threads/warps/blocks 越少。

## 标准回答
- register access 延迟低，适合 accumulator、循环变量和 thread tile。
- 总 register 需求大致随 registers/thread × resident threads 增长，并按架构粒度分配。
- 过多 register 会降低 occupancy；过少则可能造成 spill，增加 local-memory traffic。
- 高性能 kernel 往往有意接受较低 occupancy 来换取更大的 register tile 和 ILP。

## Gotchas：常见失分点
- “寄存器越少越快”。
- 只看 occupancy，不看 spills。

## 面试官可能继续追问
- 如何查看 register usage？
- 为什么 GEMM consumer warp 常常很吃 registers？

---

## 深入分析

register 快但稀缺。更多 register 可提高 ILP、减少 reload，却可能降低 active blocks；超过可分配预算还会 spill 到 local memory。

### 深入理解：性能首先是“数据在哪里”

内存层级题要用 **容量、作用域、管理方式、延迟/带宽、可见性、占用资源** 六个维度比较，而不是简单排序“register 最快、HBM 最慢”。很多优化本质是把数据从低复用、高成本层级搬到高复用、低成本层级，并控制搬运次数。

```text
HBM/DRAM → L2 → L1/Shared → Register
                ↑ programmer-managed reuse often happens here
```

同时要记住：register/shared 是稀缺的片上资源，它们会反过来限制 residency；因此数据越靠近计算单元并不自动意味着 kernel 越快。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`register count / spill`、`shared-memory usage`、`L1/L2 hit rate`、`DRAM bytes`。

### 架构视角

Ampere/Hopper/Blackwell 持续增强 cache 与异步数据移动，但 register/shared 仍是 occupancy 的关键资源。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Register 由编译器分配、thread-private、位于 SM register file，访问无需普通地址生成/缓存查找。但 register file 是有限的共享资源：每线程用量上升会降低 resident threads/blocks，甚至引发 spill。

### 2. 定量推导 / 性能模型

$R_{block}=R_{thread}\times T_{block}$，实际分配还受 allocation granularity 影响；因此 occupancy 常呈离散阶梯而非连续变化。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
float acc0=0, acc1=0, acc2=0, acc3=0;
// 更大的 register tile 可提高 reuse/ILP，
// 也可能显著增加 registers/thread。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Registers Per Thread`
- `Achieved Occupancy / active blocks`
- `Local Load/Store：spill 的直接证据`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Tensor Core kernel 常故意使用较多 registers 换取 register tiling 和 ILP；Blackwell 某些 accumulator workflow 还会使用 TMEM 改变寄存器压力分配。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

逐步扩大每线程 accumulator 数量，观察性能先升后降以及 register allocation、occupancy、spill 的拐点。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
