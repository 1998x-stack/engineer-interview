# Q013｜什么情况下变量会 Spill 到 Local Memory？如何发现？

> **一句话核心**：spill 常由高 register pressure、大局部数组或动态索引触发。
>
> **章节**：第 2 章 · GPU Memory Hierarchy  
> **难度**：★★☆ · **频率**：极高 · **标签**：Spill / 编译器

## PDF 基线题解

## 考察意图
考察从源码到 PTX/SASS 的资源诊断能力。

## 思路拆解
Spill 常由 register pressure 过高、动态索引的局部数组、过度 unroll、大量 live ranges 等触发。Local memory 访问可
能命中 L1/L2，但本质上仍是 memory traffic。

## 标准回答
- 用 `nvcc -Xptxas=-v` 查看 registers 与 spill load/store。
- Nsight Compute 可观察 local memory instructions/traffic，并关联 source。
- 优化方法包括缩短 live range、减少不必要临时变量、调整 unroll、改变 tile、重新权衡 block size/register cap。

- 不要机械使用 `-maxrregcount`；它可能让 occupancy 上升但 spill 更严重。

## Gotchas：常见失分点
- 把 spill 误认为 shared-memory spill。

## 面试官可能继续追问
- 动态索引为什么更容易阻止 registerization？
- 如何用 SASS 判断 local load/store？

## 深入分析

spill 常由高 register pressure、大局部数组或动态索引触发。用 ptxas verbose、Nsight local-memory traffic、SASS local load/store 三层证据确认。

### 深入理解：性能首先是“数据在哪里”

内存层级题要用 **容量、作用域、管理方式、延迟/带宽、可见性、占用资源** 六个维度比较，而不是简单排序“register 最快、HBM 最慢”。很多优化本质是把数据从低复用、高成本层级搬到高复用、低成本层级，并控制搬运次数。

```text
HBM/DRAM → L2 → L1/Shared → Register
                ↑ programmer-managed reuse often happens here
```

同时要记住：register/shared 是稀缺的片上资源，它们会反过来限制 residency；因此数据越靠近计算单元并不自动意味着 kernel 越快。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`register count / spill`、`shared-memory usage`、`L1/L2 hit rate`、`DRAM bytes`。

### 架构视角

Ampere/Hopper/Blackwell 持续增强 cache 与异步数据移动，但 register/shared 仍是 occupancy 的关键资源。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Spill 发生在编译器无法把 live values 全部保留在 register file 时。常见来源是过多 live temporaries、过度 unroll、大型 thread-local array、复杂索引和函数内联后 live range 扩张。

### 2. 定量推导 / 性能模型

若每线程产生 $B_{spill}$ bytes，而线程数为 $N$，额外流量可达 $N\times B_{spill}$，并可能被循环重复放大；所以少量 spill 指令也可能成为大带宽成本。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// 编译时查看
// nvcc -Xptxas=-v ...
// ptxas info : Used XX registers, YY bytes spill stores, ZZ bytes spill loads
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `ptxas spill stores/loads`
- `Nsight Compute local memory transactions`
- `SASS 中 LDL/STL 或相关 local load/store`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

架构 register file 容量与 allocation 规则不同；迁移架构后要重新检查是否从“无 spill”变为 spill，不能只复制旧 `-maxrregcount`。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

设计一个逐步增加局部 accumulator 数组大小的 kernel，记录首次 spill 出现时性能与 memory traffic 的突变。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
