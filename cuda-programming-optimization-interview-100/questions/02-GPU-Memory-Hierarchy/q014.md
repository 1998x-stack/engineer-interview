# Q014｜Shared Memory 为什么快？它解决的三个核心问题是什么？

> **一句话核心**：shared memory 的三个核心用法：跨线程协作、重用 global data、重排访问以获得 coalescing。
>
> **章节**：第 2 章 · GPU Memory Hierarchy  
> **难度**：★☆☆ · **频率**：极高 · **标签**：Shared Memory / Reuse

## PDF 基线题解

## 考察意图
考察是否知道 shared memory 的真正价值不是“比 global 快”这句口号。

## 思路拆解
Shared memory 是程序员可控的片上 scratchpad。最典型的价值是：把不规则 global access 转成 coalesced
load/store；缓存一个 tile 以消除重复 global load；在 block 内线程之间交换数据。

## 标准回答
- 显式 staging 可提高 data reuse 和 arithmetic intensity。
- 可以先 coalesced 地读入 shared，再按任意索引重排，例如 matrix transpose。
- 可以用于 reduction、scan、histogram 等 block 内协作。
- 代价包括额外 load/store 指令、barrier、bank conflict，以及 shared-memory capacity 对 occupancy 的限制。

## Gotchas：常见失分点
- 把所有 global data 都搬 shared，忽略一次性读取的 copy/sync 成本。

## 面试官可能继续追问
- 什么时候 L1 已经足够，不值得手工 shared tiling？
- shared-memory tile 太大有什么副作用？

## 深入分析

shared memory 的三个核心用法：跨线程协作、重用 global data、重排访问以获得 coalescing。它的主要成本是显式 copy、同步、bank conflict 与 occupancy 占用。

### 深入理解：性能首先是“数据在哪里”

内存层级题要用 **容量、作用域、管理方式、延迟/带宽、可见性、占用资源** 六个维度比较，而不是简单排序“register 最快、HBM 最慢”。很多优化本质是把数据从低复用、高成本层级搬到高复用、低成本层级，并控制搬运次数。

```text
HBM/DRAM → L2 → L1/Shared → Register
                ↑ programmer-managed reuse often happens here
```

同时要记住：register/shared 是稀缺的片上资源，它们会反过来限制 residency；因此数据越靠近计算单元并不自动意味着 kernel 越快。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`register count / spill`、`shared-memory usage`、`L1/L2 hit rate`、`DRAM bytes`。

### 架构视角

Ampere/Hopper/Blackwell 持续增强 cache 与异步数据移动，但 register/shared 仍是 occupancy 的关键资源。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Shared memory 的三大价值：跨线程复用 global 数据、把不规则 global access 重排成 coalesced transaction、提供 block 内低延迟交换。它是软件管理的 scratchpad，而不是自动 cache。

### 2. 定量推导 / 性能模型

若一个 tile 从 global 读取一次后被 $R$ 次复用，理想 global traffic 可从 $R\times Bytes$ 降到约 $Bytes$；收益必须减去 shared load/store 与 barrier 成本。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
__shared__ float tile[256];
tile[threadIdx.x] = g[idx];
__syncthreads();
// 多次复用 tile[...]

```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `DRAM bytes 是否下降`
- `Shared load/store throughput`
- `Bank conflict 与 barrier stalls`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Ampere `cp.async`、Hopper TMA 让 global→shared 搬运可异步化；shared memory 的核心角色从“手工缓存”进一步变成 software pipeline 的 staging buffer。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

对有 8×数据复用的 kernel 比较直接 global reload 与 shared tile；再人为引入 bank conflict，证明“用了 shared”不等于自动更快。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
