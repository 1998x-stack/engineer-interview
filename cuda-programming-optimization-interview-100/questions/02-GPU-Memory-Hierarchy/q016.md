# Q016｜L2 Cache 为什么对多 Block / 多 SM 工作负载重要？

> **一句话核心**：L2 是全 GPU 共享缓存，能承接跨 SM 的复用与写回。
>
> **章节**：第 2 章 · GPU Memory Hierarchy  
> **难度**：★★☆ · **频率**：中高 · **标签**：L2 / 跨 SM

## PDF 基线题解

## 考察意图
考察 device-level 数据复用视角。

## 思路拆解
L1/shared 的复用范围偏 SM/block，而 L2 是 GPU 设备级共享层。不同 SM 上 blocks 访问共同只读数据、相邻 tiles 或
producer/consumer kernel 的中间数据时，L2 可能显著减少 HBM 流量。

## 标准回答
- L2 对跨 SM 的重复读取、kernel 间 temporal locality 很重要。
- 性能分析要同时看 L2 hit rate 和 DRAM bytes；高 L2 命中可能让“global memory”访问并不真正到 HBM。
- 数据布局、工作分块和 kernel launch 顺序都能影响 L2 locality。
- 若 working set 远大于 L2 或访问没有 temporal locality，不能依赖 L2“自动救场”。

## Gotchas：常见失分点
- 把 global load 都当作 HBM transaction。

## 面试官可能继续追问
- 如何通过 tile ordering 提升 L2 locality？
- fusion 和 L2 reuse 的关系是什么？

## 深入分析

L2 是全 GPU 共享缓存，能承接跨 SM 的复用与写回。对多个 block 重读权重/KV/索引数据的 workload，L2 命中率可能决定是否真的打到 HBM roof。

### 深入理解：性能首先是“数据在哪里”

内存层级题要用 **容量、作用域、管理方式、延迟/带宽、可见性、占用资源** 六个维度比较，而不是简单排序“register 最快、HBM 最慢”。很多优化本质是把数据从低复用、高成本层级搬到高复用、低成本层级，并控制搬运次数。

```text
HBM/DRAM → L2 → L1/Shared → Register
                ↑ programmer-managed reuse often happens here
```

同时要记住：register/shared 是稀缺的片上资源，它们会反过来限制 residency；因此数据越靠近计算单元并不自动意味着 kernel 越快。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`register count / spill`、`shared-memory usage`、`L1/L2 hit rate`、`DRAM bytes`。

### 架构视角

Ampere/Hopper/Blackwell 持续增强 cache 与异步数据移动，但 register/shared 仍是 occupancy 的关键资源。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

L2 是全 GPU 共享的最后一级片上缓存，连接多个 SM 与 HBM。跨 block、跨 SM 或相邻 kernel 的数据复用，通常只能通过 L2/HBM 层自然发生，因此 L2 locality 对 producer-consumer 和大模型 workload 很关键。

### 2. 定量推导 / 性能模型

若 working set $W$ 可显著落入 L2，有效 HBM traffic 可从多次读取的 $R\times W$ 降低；若 $W\gg L2$ 且无时间局部性，则 hit rate 会快速下降。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// kernel A 写 tmp，kernel B 紧接着读 tmp
A<<<...>>>(tmp);
B<<<...>>>(tmp); // 可能受益于 L2 residency，但不可把它当 correctness 保证
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `L2 hit rate / bytes`
- `DRAM read/write bytes`
- `Nsight Systems：kernel 间时间距离`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Blackwell 等新架构提升 L2 容量/带宽，但算法仍需关注工作集大小、访问时序与多 SM 竞争；更大 L2 不是无限 cache。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

对 1MB、10MB、100MB、1GB working set 做多次读取，画 L2 hit rate 与带宽随 working set 的变化。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
