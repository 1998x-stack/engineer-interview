# Q019｜`cudaMalloc` 与 Unified Memory / `cudaMallocManaged` 怎么选？

> **一句话核心**：显式 `cudaMalloc` 给你更可控的数据放置；Unified Memory 提供统一地址与迁移便利。
>
> **章节**：第 2 章 · GPU Memory Hierarchy  
> **难度**：★★☆ · **频率**：高 · **标签**：Unified Memory / 系统

## PDF 基线题解

## 考察意图
考察显式数据管理与统一地址/迁移机制的权衡。

## 思路拆解
Managed memory 简化了可编程性，但页迁移、page fault、oversubscription 和 CPU/GPU 交替访问可能引入不可预测
的成本。高性能场景需要理解实际 residency。

## 标准回答
- `cudaMalloc` + 显式 memcpy 给数据移动更强的可控性。
- Managed memory 提供统一地址空间和运行时迁移，适合开发效率或复杂数据结构。
- 可使用 prefetch/advice 等机制引导 residency；同时关注 NUMA 和 CPU/GPU 访问模式。
- 性能敏感代码不能只因为 API 简单就假设 Unified Memory 自动最优。

## Gotchas：常见失分点
- 把 Unified Memory 说成“同一块物理内存，永远无需传输”。

## 面试官可能继续追问
- 什么是 page fault/migration？
- oversubscription 时会发生什么？

---

## 深入分析

显式 `cudaMalloc` 给你更可控的数据放置；Unified Memory 提供统一地址与迁移便利。性能敏感场景要关注 page fault、prefetch、oversubscription 与访问局部性。

### 深入理解：性能首先是“数据在哪里”

内存层级题要用 **容量、作用域、管理方式、延迟/带宽、可见性、占用资源** 六个维度比较，而不是简单排序“register 最快、HBM 最慢”。很多优化本质是把数据从低复用、高成本层级搬到高复用、低成本层级，并控制搬运次数。

```text
HBM/DRAM → L2 → L1/Shared → Register
                ↑ programmer-managed reuse often happens here
```

同时要记住：register/shared 是稀缺的片上资源，它们会反过来限制 residency；因此数据越靠近计算单元并不自动意味着 kernel 越快。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`register count / spill`、`shared-memory usage`、`L1/L2 hit rate`、`DRAM bytes`。

### 架构视角

Ampere/Hopper/Blackwell 持续增强 cache 与异步数据移动，但 register/shared 仍是 occupancy 的关键资源。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

`cudaMalloc` 代表显式 device allocation 与显式数据移动；Unified Memory 提供统一虚拟地址与按需迁移/放置机制。选择关键是访问模式是否可预测、是否跨 CPU/GPU 共享，以及能否接受 page migration/fault 的不确定性。

### 2. 定量推导 / 性能模型

若迁移页面总量为 $B$，迁移成本至少受 $B/BW_{link}$ 约束，还叠加 fault、page management 与同步；高复用时一次预取可被后续大量计算摊销。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
cudaMallocManaged(&p, bytes);
cudaMemPrefetchAsync(p, bytes, device, stream);
// 用预取把按需 page fault 变成更可控的数据移动。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Nsight Systems Unified Memory migration/page faults`
- `H2D/D2H transfer volume`
- `Kernel 中的 replay/stall 与迁移时间`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

UM 在多 GPU、CPU-GPU memory coherence 和 oversubscription 上能力持续增强，但高性能场景仍应显式理解数据放置而非依赖“自动就最优”。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

同一数组分别用 explicit memcpy、UM demand paging、UM prefetch 三种方式跑多轮 kernel，对比首轮与稳态时间。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
