# Q026｜Vectorized Load/Store（如 float4）什么时候有收益？

> **一句话核心**：vectorized load/store 的收益来自更少指令、更宽 memory op 与更好的 copy throughput；前提是满足 alignment、连续性和编译器 codegen，且不能因为 padding/overfetch 反而搬更多数据。
>
> **章节**：第 3 章 · Global Memory 与 Coalescing  
> **难度**：★★☆ · **频率**：高 · **标签**：Vectorization / 指令

## PDF 基线题解

## 考察意图
考察指令数、alignment 和 layout 的联合优化。

## 思路拆解
Vector load/store 可能减少 load/store 指令和 address calculation，但要求正确对齐与足够连续的数据。它不会自动修
复糟糕的 warp address pattern。

## 标准回答
- 先保证 pointer alignment 与数据长度边界。
- vectorized access 主要优化 instruction overhead；memory transaction 是否更优仍由 warp 的地址集合决定。
- 尾部元素需要 scalar cleanup 或 masked handling。
- 向量化可能增加每线程 register 使用，需要一起看 occupancy。

## Gotchas：常见失分点
- 认为 float4 会自动把 4 倍数据合并成 1 个 DRAM transaction。

## 深入分析

vectorized load/store 的收益来自更少指令、更宽 memory op 与更好的 copy throughput；前提是满足 alignment、连续性和编译器 codegen，且不能因为 padding/overfetch 反而搬更多数据。

### 深入理解：把地址模式翻译成 transaction

Global-memory 题的统一方法是：**先站在一个 warp 的视角写出 32 个地址，再问这些地址覆盖多少个 transaction/cache sector**。这比背“连续访问就是 coalesced”更可靠，因为 alignment、element size、vector width、stride 都会改变请求覆盖范围。

性能判断最好区分三层：

1. requested bytes：算法真正需要的字节；
2. transferred bytes：memory subsystem 实际搬运的字节；
3. achieved bandwidth：这些字节在时间维度上的吞吐。

优化的目标通常不是让 DRAM 更忙，而是让 **每个搬运字节更有用**。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`Global Load/Store Efficiency`、`L1/L2 sectors`、`DRAM bytes`、`effective bandwidth`。

### 架构视角

现代 GPU 的 cache 会缓和部分 misalignment，但 warp transaction/sector 浪费仍会降低有效带宽。

建议为本题建立一个最小可复现实验（microbenchmark）：

1. 写一个**正确但未优化**的 baseline。
2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Vectorized load/store 的潜在收益是减少 load/store 指令与地址计算，并匹配更宽的数据搬运；但前提是 alignment、连续性和寄存器压力合适。它不会自动减少必须传输的总字节。

### 2. 定量推导 / 性能模型

若 scalar 需要 4 条 32-bit load，而 float4 用 1 条向量 load，指令数可下降；但每线程一次引入 4 个 live values，可能增加 register pressure。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
const float4* p4 = reinterpret_cast<const float4*>(p);
float4 v = p4[i]; // 需要满足对齐和边界条件
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Executed load/store instructions`
- `Registers/thread`
- `Memory sectors 与 kernel time`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

不同编译器/架构可能把高级向量类型 lowering 成不同指令组合；最终要检查 SASS，而不是假设 C++ `float4` 必然等于单条硬件指令。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

同一 memcpy-like transform 用 scalar、float2、float4，控制 alignment，比较 instruction count 与 register usage。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
