# Q029｜Requested Bandwidth 与 Actual DRAM Bandwidth 有什么区别？

> **一句话核心**：requested bandwidth 是有效负载，actual DRAM bandwidth 是硬件真实搬运。
>
> **章节**：第 3 章 · Global Memory 与 Coalescing  
> **难度**：★★☆ · **频率**：高 · **标签**：Profiler / Memory

## PDF 基线题解

## 考察意图
考察是否会区分“忙”与“有效”。

## 思路拆解
一个 kernel 可能 DRAM 吞吐很高，却因为 scattered access 搬运大量无用 bytes。Requested 是程序逻辑需要的数据；
actual 是 cache/DRAM 真正传输的数据。

## 标准回答
- requested/actual 比例低通常说明 transaction utilization 差。
- 高 DRAM utilization + 低 useful throughput，优先修访问模式或减少 bytes。
- L2 hit 会让部分 global requests 不到 DRAM，因此还要结合 L2 sectors/bytes。

## Gotchas：常见失分点
- 看到 DRAM 95% 就宣布“已经最优”。

## 面试官可能继续追问
- 如何识别 over-fetch？
- sector miss 与 cache hit 如何共同解释？

---

## 深入分析

requested bandwidth 是有效负载，actual DRAM bandwidth 是硬件真实搬运。actual 很高但 requested 很低，说明你把带宽花在无效 sector/重复数据上。

### 深入理解：把地址模式翻译成 transaction

Global-memory 题的统一方法是：**先站在一个 warp 的视角写出 32 个地址，再问这些地址覆盖多少个 transaction/cache sector**。这比背“连续访问就是 coalesced”更可靠，因为 alignment、element size、vector width、stride 都会改变请求覆盖范围。

性能判断最好区分三层：

1. requested bytes：算法真正需要的字节；
2. transferred bytes：memory subsystem 实际搬运的字节；
3. achieved bandwidth：这些字节在时间维度上的吞吐。

优化的目标通常不是让 DRAM 更忙，而是让 **每个搬运字节更有用**。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`Global Load/Store Efficiency`、`L1/L2 sectors`、`DRAM bytes`、`effective bandwidth`。

### 架构视角

现代 GPU 的 cache 会缓和部分 misalignment，但 warp transaction/sector 浪费仍会降低有效带宽。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Requested bandwidth 是程序语义真正请求的 useful bytes；actual/physical traffic 是 cache/memory subsystem 实际搬运的 bytes。二者差距揭示了 overfetch、misalignment、stride、write allocation 等效率问题。

### 2. 定量推导 / 性能模型

$\eta_{mem}=B_{requested}/B_{actual}$。例如 128B useful、1024B actual，效率 12.5%，即使 DRAM 已达 90% 峰值也说明访问模式很差。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// 同样每线程只消费一个 float，stride 可让 actual bytes 激增
float v = a[tid * stride];
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Global Load/Store Efficiency`
- `Sectors/request`
- `DRAM Throughput + Requested Throughput 联合判断`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Profiler 指标名称会随 Nsight 版本变化，但“useful work 与 physical traffic 分离”是稳定诊断思想。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

构造相同 useful FLOPs、不同 stride 的 kernel，使 DRAM throughput 上升但有效带宽下降，训练识别“假繁忙”。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
