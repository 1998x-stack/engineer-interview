# Q034｜为什么 `tile[32][33]` 能消除典型 Transpose Bank Conflict？

> **一句话核心**：padding 到 33 后 stride 从 32 变 33，`33 mod 32 = 1`，相邻 lane 轮转到不同 bank。
>
> **章节**：第 4 章 · Shared Memory、Warp 与 Divergence  
> **难度**：★★☆ · **频率**：极高 · **标签**：Padding / Bank

## PDF 基线题解

## 考察意图
考察 padding 的数学原因。

## 思路拆解
加一列 padding 后行 stride 从 32 变成 33 words。由于 33 mod 32 = 1，相邻 lane 的列访问会依次落到 bank 0,1,...31，
而不是都落同一 bank。

## 标准回答
- padding 改变的是 shared-memory address mapping，不是 global layout。
- 代价是少量额外 shared capacity，通常远小于冲突序列化收益。
- 更现代的高性能库也会使用 swizzled layouts，而不只依赖 +1 padding。

## 代码 / 白板骨架

```cpp
constexpr int TILE = 32;
__shared__ float tile[TILE][TILE + 1]; // +1 改变列访问的 bank 映射

int x = blockIdx.x * TILE + threadIdx.x;
int y = blockIdx.y * TILE + threadIdx.y;
tile[threadIdx.y][threadIdx.x] = in[y * width + x];
__syncthreads();
// 之后按转置坐标读取 tile，避免 32-way bank conflict。

```

## 深入分析

padding 到 33 后 stride 从 32 变 33，`33 mod 32 = 1`，相邻 lane 轮转到不同 bank。更复杂 layout 可用 swizzle 达到同样目的。

### 深入理解：Shared Memory 不是“自动高速缓存”

Shared memory 的价值来自可控复用与线程协作，但必须同时处理 **bank mapping、同步、layout**。分析 bank conflict 时，应写出每个 lane 的 word address，再做 `bank = word_index mod bank_count` 的映射。

Warp-level primitive 则是在“线程之间交换数据”这个问题上绕开 shared-memory round trip；其代价是作用域更小，并要求正确的 active mask 与同步语义。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Padding 把 row stride 从 32 words 改成 33 words；因 33 与 32 互质，相邻 lane 的列访问会遍历全部 bank，而不是重复落入同一 bank。代价是每行多一个元素的 shared 容量。

### 2. 定量推导 / 性能模型

$bank(lane)=(base+33lane)\bmod32=(base+lane)\bmod32$，因此 32 lane 映射 32 个不同 bank。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
__shared__ float tile[32][33]; // +1 padding
// 写入按行 coalesced；读取按列时 bank 分散
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Shared conflict 降至接近 1 transaction/request`
- `Shared-memory allocation 增量`
- `Transpose effective bandwidth`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

现代高性能库还常用 swizzle/layout algebra 解决冲突；padding 是最易解释的入门方案，但不是所有矩阵指令 layout 的最佳方案。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

比较 32×32、32×33、swizzled layout 三版 transpose，记录 shared usage 与 conflict。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
