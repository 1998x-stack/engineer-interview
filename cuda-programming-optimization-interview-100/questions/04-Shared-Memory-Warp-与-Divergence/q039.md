# Q039｜`__syncwarp()` 什么时候必须用？

> **一句话核心**：Volta+ independent scheduling 下，不能依赖“warp 天然 lockstep”完成 shared-memory producer/consumer。
>
> **章节**：第 4 章 · Shared Memory、Warp 与 Divergence  
> **难度**：★★☆ · **频率**：高 · **标签**：Warp Sync / 内存顺序

## PDF 基线题解

## 考察意图
考察 Volta+ independent thread scheduling 下的正确性。

## 思路拆解
如果 warp lanes 通过 shared/global memory 交换数据，且存在“写后读”依赖，不能只靠“warp 本来一起执行”的历
史假设。`__syncwarp(mask)` 可同步指定 lanes，并提供相应 memory ordering。

## 标准回答
- shuffle/vote 自带其定义的同步语义，但 shared-memory 手工通信通常需要显式同步。
- mask 必须准确描述参与线程。
- warp sync 只覆盖 warp 范围；跨 warp 仍需 block/barrier 等更强机制。

## Gotchas：常见失分点
- 认为 warp 永远隐式 lockstep，所以不需要 sync。

## 面试官可能继续追问
- 什么叫 warp-synchronous programming？
- independent thread scheduling 为什么会暴露旧代码 bug？

---

## 深入分析

Volta+ independent scheduling 下，不能依赖“warp 天然 lockstep”完成 shared-memory producer/consumer。需要 `__syncwarp(mask)` 或更强同步原语建立顺序。

### 深入理解：Shared Memory 不是“自动高速缓存”

Shared memory 的价值来自可控复用与线程协作，但必须同时处理 **bank mapping、同步、layout**。分析 bank conflict 时，应写出每个 lane 的 word address，再做 `bank = word_index mod bank_count` 的映射。

Warp-level primitive 则是在“线程之间交换数据”这个问题上绕开 shared-memory round trip；其代价是作用域更小，并要求正确的 active mask 与同步语义。

### 架构视角

bank 组织和共享内存能力随架构演进，但“按 lane 地址映射 bank、避免同 bank 不同地址冲突”的分析方法稳定。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

`__syncwarp(mask)` 用于让 mask 中参与线程在 warp 级汇合，并提供相应 memory ordering。当代码依赖“一个 lane 写 shared、另一个 lane 随后读”时，不能仅凭“同 warp”假定安全。

### 2. 定量推导 / 性能模型

同步范围缩小可减少不相关线程等待；但 correctness 前提是所有数据依赖参与者都包含在 mask 中。遗漏一个 producer/consumer 比使用更大 barrier 更危险。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
s[lane] = v;
__syncwarp(mask);
float left = (lane ? s[lane-1] : 0);
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Compute Sanitizer racecheck（适用时）`
- `Warp stall barrier`
- `SASS/source dependency`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Volta+ independent thread scheduling 是显式 warp sync 更重要的背景；旧代码依赖“warp lockstep”的隐式假设需要审计。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

写一个不加 `__syncwarp` 的 shared warp exchange microbenchmark，在不同优化级别/架构验证结果，再加入同步作为正确版本。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
