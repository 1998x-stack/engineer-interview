# Q041｜什么是 Occupancy？

> **一句话核心**：Occupancy 只回答“SM 上有多少 active warps”，不是“这些 warps 做得是否高效”。
>
> **章节**：第 5 章 · Occupancy、Register 与 Latency Hiding  
> **难度**：★☆☆ · **频率**：极高 · **标签**：Occupancy / 资源

## PDF 基线题解

> **30 秒答案**：Occupancy 只回答“SM 上有多少 active warps”，不是“这些 warps 做得是否高效”。

## 考察意图
高频陷阱题：考察你是否知道 occupancy 只是 latency-hiding 的代理变量。

## 思路拆解
Occupancy = active warps per SM / theoretical maximum warps per SM。它说明有多少 warp 状态可用于调度，但不
能直接代表算术效率、memory efficiency 或最终性能。

## 标准回答
- 低 occupancy 往往削弱隐藏 latency 的能力。
- 高 occupancy 超过“足够隐藏 latency”的点后，继续提高未必增益。
- register、shared memory、threads/block、block slots 等都可能限制 occupancy。
- 官方 Best Practices 明确指出 higher occupancy does not always mean higher performance。

## Gotchas：常见失分点
- 把 occupancy 当目标函数。

## 面试官可能继续追问
- 为什么 50% occupancy 的 GEMM 可能比 100% 更快？
- achieved occupancy 与 theoretical occupancy 有何区别？

---

## 深入分析

occupancy 是 active warps/max warps 的比例，是潜在 latency hiding 能力的 proxy；它不直接衡量 IPC、bandwidth 或有用计算。

### 深入理解：Occupancy 只是 latency hiding 的一个代理变量

Occupancy 题最重要的结论是：**目标不是 occupancy，而是 throughput**。增加 resident warps 可以帮助隐藏 latency，但会和 register/thread、shared/block、tile size、ILP 发生资源竞争。

一个成熟的回答应讨论：

```text
registers/thread ↑ → ILP/data reuse 可能 ↑ → blocks/SM 可能 ↓
shared/block ↑    → reuse 可能 ↑       → blocks/SM 可能 ↓
warps/SM ↑         → latency hiding ↑   → 每线程资源预算可能 ↓
```

因此调优必须用真实 benchmark 与 profiler 验证，而不能把 occupancy calculator 当最终答案。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`Theoretical Occupancy`、`Achieved Occupancy`、`Active Warps`、`Eligible Warps`、kernel time。

### 架构视角

不同 compute capability 的 SM 资源上限不同；面试时应强调“先查目标架构限制，再算 residency”。

## 实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

1. 写一个**正确但未优化**的 baseline。
2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
4. 使用 Nsight Compute/Systems 收集与本题直接相关的指标：`Theoretical Occupancy`、`Achieved Occupancy`、`Active Warps`、`Eligible Warps`、kernel time。
5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Occupancy 是 active warps 与硬件最大 resident warps 的比值，是“隐藏延迟的潜在并行上下文”指标，不是性能目标。它不反映 warp 是否 eligible、memory coalescing 是否好、Tensor Core 是否忙。

### 2. 定量推导 / 性能模型

$Occ=W_{active}/W_{max}$。若达到某个阈值后已有足够 ready warps 覆盖 latency，继续提高 occupancy 可能没有收益。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// 使用 occupancy API 估算只是起点
// cudaOccupancyMaxActiveBlocksPerMultiprocessor(...);
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Theoretical vs Achieved Occupancy`
- `Eligible warps per scheduler`
- `SM / memory throughput`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Tensor Core/async pipeline kernel 常用较高 registers/smem 换取 tile reuse，因此高性能实现经常主动接受中等 occupancy。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

通过动态 smem 或寄存器变化构造 25%、50%、75%、100% occupancy 版本，证明性能可能在 50% 已饱和。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
