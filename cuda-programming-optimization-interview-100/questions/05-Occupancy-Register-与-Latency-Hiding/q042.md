# Q042｜为什么 100% Occupancy 不一定最快？

> **一句话核心**：高 occupancy 可能迫使每线程 register 太少、tile 太小、reuse 下降。
>
> **章节**：第 5 章 · Occupancy、Register 与 Latency Hiding  
> **难度**：★★☆ · **频率**：极高 · **标签**：Occupancy / ILP

## PDF 基线题解

## 考察意图
考察 TLP 与每线程资源之间的 trade-off。

## 思路拆解
为了追求 100% occupancy 强行降低 registers/thread，可能造成 spill、缩小 register tile、降低 ILP 或增加指令数。某
些高算术强度 kernel 在较低 occupancy 下仍能用 ILP 覆盖延迟。

## 标准回答
- 方案 A：更多 warps，但每线程资源少。
- 方案 B：更少 warps，但每线程有更大 register tile、更少 memory traffic、更高 ILP。
- 性能取决于瓶颈；当 latency 已被隐藏时，继续增加 warps 不会线性提速。

## Gotchas：常见失分点
- 为了 occupancy 使用 `-maxrregcount`，不检查 spill。

## 面试官可能继续追问
- 如何人为增加 dynamic shared memory 来做 occupancy sensitivity 实验？
- 什么时候 occupancy 确实是主要瓶颈？

---

## 深入分析

高 occupancy 可能迫使每线程 register 太少、tile 太小、reuse 下降。达到足够 latency hiding 后，更多 warp 的边际收益可能为零甚至负。

### 深入理解：Occupancy 只是 latency hiding 的一个代理变量

Occupancy 题最重要的结论是：**目标不是 occupancy，而是 throughput**。增加 resident warps 可以帮助隐藏 latency，但会和 register/thread、shared/block、tile size、ILP 发生资源竞争。

一个成熟的回答应讨论：

```text
registers/thread ↑ → ILP/data reuse 可能 ↑ → blocks/SM 可能 ↓
shared/block ↑    → reuse 可能 ↑       → blocks/SM 可能 ↓
warps/SM ↑         → latency hiding ↑   → 每线程资源预算可能 ↓
```

因此调优必须用真实 benchmark 与 profiler 验证，而不能把 occupancy calculator 当最终答案。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：occupancy、registers/thread、local-memory spill、eligible warps、kernel time。

### 架构视角

不同 compute capability 的 SM 资源上限不同；面试时应强调“先查目标架构限制，再算 residency”。

## 实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

1. 写一个**正确但未优化**的 baseline。
2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
4. 使用 Nsight Compute/Systems 收集与本题直接相关的指标：occupancy、registers/thread、local-memory spill、eligible warps、kernel time。
5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

100% occupancy 可能以牺牲 register tiling、ILP 或 shared-memory reuse 为代价。一个 50% occupancy 但每 warp 更高效、数据复用更强的 kernel 完全可能更快。

### 2. 定量推导 / 性能模型

可把吞吐粗略写成 $Throughput\approx N_{eligible}\times work_{warp}/time$；occupancy 只影响上限中的 resident 数，不描述每 warp work efficiency。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// A: 少寄存器、多 warp
// B: 更多 accumulator，较少 warp，但更高 reuse/ILP
// 只能 benchmark 决定。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Kernel time`
- `Eligible warps`
- `Register spills、memory traffic、Tensor/ALU utilization`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

高性能 CUTLASS GEMM 是经典反例：大量 shared/register/TMEM staging 追求 pipeline efficiency，而不是追求 100% occupancy。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

矩阵/卷积微基准中调整 per-thread tile，记录 occupancy 下降但 arithmetic intensity 和吞吐上升的区域。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
