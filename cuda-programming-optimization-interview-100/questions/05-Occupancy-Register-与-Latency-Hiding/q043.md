# Q043｜哪些资源会限制 Resident Blocks / Occupancy？

> **一句话核心**：resident blocks 取 registers、shared memory、threads、warps、block slots 等限制的最小值。
>
> **章节**：第 5 章 · Occupancy、Register 与 Latency Hiding  
> **难度**：★★☆ · **频率**：极高 · **标签**：资源模型 / SM

## PDF 基线题解

## 考察意图
考察是否会算 occupancy 约束。

## 思路拆解
每个 SM 能驻留多少 blocks 由多个上限共同决定，取最紧的那个：threads、warps、register file、shared memory、最
大 blocks/SM 以及架构特定限制。

## 标准回答
- thread/block × blocks ≤ max threads/SM。
- warp/block × blocks ≤ max warps/SM。
- register allocation 与 shared-memory allocation 必须满足 SM 总资源。
- 即使 thread 数很少，block slot 上限也可能成为约束。

## Gotchas：常见失分点
- 只算 threads，不算 register/smem。

## 面试官可能继续追问
- 如何使用 occupancy API/Calculator？

- register allocation granularity 为什么会造成“少 1 个 register 突然多一个 block”？

---

## 深入分析

resident blocks 取 registers、shared memory、threads、warps、block slots 等限制的最小值。任何一个资源先耗尽都成为 occupancy limiter。

### 深入理解：Occupancy 只是 latency hiding 的一个代理变量

Occupancy 题最重要的结论是：**目标不是 occupancy，而是 throughput**。增加 resident warps 可以帮助隐藏 latency，但会和 register/thread、shared/block、tile size、ILP 发生资源竞争。

一个成熟的回答应讨论：

```text
registers/thread ↑ → ILP/data reuse 可能 ↑ → blocks/SM 可能 ↓
shared/block ↑    → reuse 可能 ↑       → blocks/SM 可能 ↓
warps/SM ↑         → latency hiding ↑   → 每线程资源预算可能 ↓
```

因此调优必须用真实 benchmark 与 profiler 验证，而不能把 occupancy calculator 当最终答案。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：registers/thread、shared memory/block、threads/block、resident blocks/SM、warps/SM。

### 架构视角

不同 compute capability 的 SM 资源上限不同；面试时应强调“先查目标架构限制，再算 residency”。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Resident block 上限来自多个离散资源的最小值：threads、warps、registers、shared memory、architectural block slots，以及 cluster 等更高层约束。调优要找“谁先触顶”。

### 2. 定量推导 / 性能模型

$B=\min(\lfloor T_{SM}/T_B\rfloor,\lfloor R_{SM}/R_B\rfloor,\lfloor S_{SM}/S_B\rfloor,B_{slots},...)$。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// ptxas + Nsight Launch Statistics
// 结合 blockDim、register/thread、static/dynamic smem 计算 limiter。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Launch Statistics occupancy limiters`
- `Registers/thread`
- `Static + dynamic shared memory/block`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

不同 compute capability 资源上限不同；Hopper/Blackwell cluster launch 还可能引入 cluster residency/shape 限制。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

逐个只改变 blockDim、register limit、dynamic smem，验证每一种资源触顶时 active blocks 的阶梯。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
