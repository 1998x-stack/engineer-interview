# Q047｜`__launch_bounds__` 用来解决什么问题？

> **一句话核心**：`__launch_bounds__` 给编译器 launch 约束，使寄存器分配能围绕目标 block size/residency 优化；它是编译提示，不是性能保证。
>
> **章节**：第 5 章 · Occupancy、Register 与 Latency Hiding  
> **难度**：★★☆ · **频率**：高 · **标签**：Launch Bounds / Compiler

## PDF 基线题解

## 考察意图
考察编译器资源约束提示。

## 思路拆解
`__launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor)` 向编译器声明 launch 上界/期望
residency，使其在 register 分配与指令数之间做更合适的权衡。

## 标准回答
- 第一参数可防止编译出在目标 block size 下资源过量的 kernel，并帮助前向兼容。
- 第二参数会影响 compiler 推导 register 上限，试图允许至少指定数量 blocks resident。
- 编译器有时会主动增加 register 使用来减少指令，只要不破坏给定 bounds。
- 它不是“保证性能”的 annotation，仍需 profile。

## Gotchas：常见失分点
- 把 `minBlocksPerMultiprocessor` 当运行时硬保证。

## 面试官可能继续追问
- 为什么 bound 太激进会增加 local memory？
- 不同 architecture 是否需要不同 bounds？

## 深入分析

`__launch_bounds__` 给编译器 launch 约束，使寄存器分配能围绕目标 block size/residency 优化；它是编译提示，不是性能保证。

### 深入理解：Occupancy 只是 latency hiding 的一个代理变量

Occupancy 题最重要的结论是：**目标不是 occupancy，而是 throughput**。增加 resident warps 可以帮助隐藏 latency，但会和 register/thread、shared/block、tile size、ILP 发生资源竞争。

一个成熟的回答应讨论：

```text
registers/thread ↑ → ILP/data reuse 可能 ↑ → blocks/SM 可能 ↓
shared/block ↑    → reuse 可能 ↑       → blocks/SM 可能 ↓
warps/SM ↑         → latency hiding ↑   → 每线程资源预算可能 ↓
```

因此调优必须用真实 benchmark 与 profiler 验证，而不能把 occupancy calculator 当最终答案。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：register allocation、blocks/SM、occupancy、kernel time。

### 架构视角

不同 compute capability 的 SM 资源上限不同；面试时应强调“先查目标架构限制，再算 residency”。

1. 写一个**正确但未优化**的 baseline。
2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

`__launch_bounds__` 向编译器声明最大 block threads 和期望 residency，使 register allocation 能围绕特定 launch configuration 做权衡。它影响编译决策，但不“保证运行时一定达到指定 occupancy”。

### 2. 定量推导 / 性能模型

如果声明希望每 SM 至少 $B$ blocks，编译器会尝试把每 block register 预算控制在约 $R_{SM}/B$（还受分配粒度/其他约束影响）。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
__global__ __launch_bounds__(256, 2)
void kernel(...) { ... }
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `ptxas registers/thread 前后变化`
- `Active blocks/SM`
- `Spill 与 runtime`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

不同架构资源不同，所以 launch bounds 的“意图”可以复用，实际 register budget 和结果需按 target 重新验证。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

同一 kernel 比较无 launch bounds、(256,1)、(256,2)、(256,3)，记录 ptxas 与 runtime。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
