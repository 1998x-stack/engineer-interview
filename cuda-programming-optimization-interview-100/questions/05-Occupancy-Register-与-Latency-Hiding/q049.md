# Q049｜GPU 如何用 Warp Scheduling 隐藏 Memory Latency？

> **一句话核心**：warp 等 memory 时 scheduler 可选择其他 eligible warp 发射。
>
> **章节**：第 5 章 · Occupancy、Register 与 Latency Hiding  
> **难度**：★★☆ · **频率**：极高 · **标签**：Latency Hiding / Scheduler

## PDF 基线题解

## 考察意图
考察 GPU throughput 架构的核心机制。

## 思路拆解
一个 warp 发出高延迟 load 后，如果后续指令依赖结果，它会进入等待；scheduler 可从其他 eligible warps 发射指令。
如果没有足够可运行 warp 或独立指令，latency 就暴露为 stall。

## 标准回答
- resident warp 多不等于 eligible warp 多；如果所有 warps 都等同一内存依赖，occupancy 再高也可能一起 stall。
- ILP 可以让同一 warp 在等待一个 load 时继续执行不依赖该 load 的工作。
- software prefetch/pipeline 的本质就是更早发出 load，把等待期塞进有用计算。

## Gotchas：常见失分点
- 认为 warp switch 有 CPU context switch 那样的高成本。

## 面试官可能继续追问
- long scoreboard 高说明什么？
- 怎样把 load 提前几个迭代？

---

## 深入分析

warp 等 memory 时 scheduler 可选择其他 eligible warp 发射。若 active warp 很多但 eligible warp 很少，应进一步查依赖链、barrier 或内存长延迟。

### 深入理解：Occupancy 只是 latency hiding 的一个代理变量

Occupancy 题最重要的结论是：**目标不是 occupancy，而是 throughput**。增加 resident warps 可以帮助隐藏 latency，但会和 register/thread、shared/block、tile size、ILP 发生资源竞争。

一个成熟的回答应讨论：

```text
registers/thread ↑ → ILP/data reuse 可能 ↑ → blocks/SM 可能 ↓
shared/block ↑    → reuse 可能 ↑       → blocks/SM 可能 ↓
warps/SM ↑         → latency hiding ↑   → 每线程资源预算可能 ↓
```

因此调优必须用真实 benchmark 与 profiler 验证，而不能把 occupancy calculator 当最终答案。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`theoretical/achieved occupancy`、`registers/thread`、`shared/block`、`eligible warps / issue slots`、`local-memory traffic`。

### 架构视角

不同 compute capability 的 SM 资源上限不同；面试时应强调“先查目标架构限制，再算 residency”。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Warp scheduler 在某个 warp 因 memory dependency 不 eligible 时，从其他 ready warp 发射指令。Latency hiding 依赖“有足够 resident 且 eligible 的独立 work”，并不降低内存本身的物理延迟。

### 2. 定量推导 / 性能模型

若 memory latency 约 $L$ cycles，单 scheduler 每周期可发射能力有限，需要大致 $O(L/ILP)$ 的独立 warp/instruction opportunities 才能充分隐藏；具体数值依架构与指令混合。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// pointer chasing: 强依赖，难隐藏
p = next[p];
// independent loads: 可提供更多 MLP/ILP
a= A[i]; b=B[i2]; c=C[i3];
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Eligible warps per scheduler`
- `Long Scoreboard`
- `Memory-level parallelism / outstanding requests（相关指标）`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

异步 copy/TMA 把一部分 latency hiding 从“仅靠更多 warps”升级为显式 producer-consumer pipeline。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

比较 pointer-chasing、单独 load chain、4 独立 load streams，在相同 bytes 下观察 scoreboard stall。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
