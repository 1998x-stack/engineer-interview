# Q057｜手写 Tiled Matrix Multiplication，并解释为什么快。

> **一句话核心**：tiled GEMM 的加速来源是 A/B tile 被多个线程/多个 FMA 重用，提高 arithmetic intensity。
>
> **章节**：第 6 章 · 经典 CUDA Kernel 现场编程  
> **难度**：★★★ · **频率**：极高 · **标签**：Coding / GEMM

## PDF 基线题解

## 考察意图
考察 shared tiling、reuse 与 arithmetic intensity。

## 思路拆解
Naive GEMM 每个 C 元素反复从 global 读取 A/B。Tiled GEMM 让一个 block 先把 A/B 的 K 维片段读入 shared，每个元
素被 block 内多个 threads 重用，再推进下一个 K tile。

## 标准回答
- global bytes 被多个 FMA 摊薄，arithmetic intensity 上升。
- load tile 后需要 block synchronization，确保 shared 数据完整。
- 每 thread 做多个 outputs/register tiling 可进一步提高 reuse 和 ILP。
- 现代高性能 GEMM 会继续分成 CTA tile、warp tile、MMA tile、thread/register tile，并使用 Tensor Core。

## 代码 / 白板骨架

```cpp
template<int T>
__global__ void gemm(const float* A, const float* B, float* C, int N) {
__shared__ float As[T][T], Bs[T][T];
int row = blockIdx.y*T + threadIdx.y;
int col = blockIdx.x*T + threadIdx.x;
float acc = 0.f;
for (int k0=0; k0<N; k0+=T) {
As[threadIdx.y][threadIdx.x] = A[row*N + k0 + threadIdx.x];
Bs[threadIdx.y][threadIdx.x] = B[(k0 + threadIdx.y)*N + col];
__syncthreads();
#pragma unroll

for (int k=0;k<T;++k) acc += As[threadIdx.y][k] * Bs[k][threadIdx.x];
__syncthreads();
}
C[row*N+col] = acc;
}

```

## Gotchas：常见失分点
- 只做 shared tile，但 global loads 没 coalesce。
- tile 越大越好。

### 深入理解：经典算法题考的是“逐版优化能力”

现场 coding 题通常不要求一步写出最优 kernel，而是考察你能否从正确的 baseline 出发，逐个消除瓶颈：

```text
Correct baseline
→ coalesced access
→ shared/register reuse
→ reduce divergence/barriers
→ warp primitive
→ vectorization / multi-element per thread
→ device-wide library / architecture specialization
```

每一版都要能说明：**减少了什么成本、引入了什么新约束、用什么指标验证**。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Tiled GEMM 的本质是提高 reuse：每个 A/B global tile 只加载一次到 shared，再被 block 内多次乘加；进一步用 register tile 让 shared 数据也被多次复用。高性能版本还要 coalesced、bank-safe、pipeline 化。

### 2. 定量推导 / 性能模型

naive 每个 C 元素做 K 次 A/B load；block tile $M_b\times N_b\times K_b$ 可让加载的 A/B tile 分别被 $N_b$/$M_b$ 方向复用，显著提高 arithmetic intensity。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
for (int kb=0; kb<K; kb+=BK) {
  load_A_B_tiles_to_shared();
  __syncthreads();
  #pragma unroll
  for(int k=0;k<BK;++k) acc += As[...] * Bs[...];
  __syncthreads();
}
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Tensor/FP32 throughput`
- `DRAM bytes / arithmetic intensity`
- `Shared conflicts`
- `Registers/occupancy`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

真实高性能 GEMM 在 Ampere/Hopper/Blackwell 上进一步使用 async copy/TMA、Tensor Core、warp specialization、TMEM 等；手写 scalar tiled GEMM 是理解这些机制的基础。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

naive→shared tile→register tile→vectorized load，最后与 cuBLAS/CUTLASS 对比，解释为何自写通用 GEMM 很难追平库。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
