# Q060｜Top-K / Sort / Selection 什么时候不应该自己写 CUDA？

> **一句话核心**：Top-K/sort/selection 是成熟库高度优化的 primitive。
>
> **章节**：第 6 章 · 经典 CUDA Kernel 现场编程  
> **难度**：★★☆ · **频率**：极高 · **标签**：工程 / 库

## PDF 基线题解

## 考察意图
考察工程判断：高性能不是“所有东西手写”。

## 思路拆解
成熟库通常已经包含架构特化、边界处理和大量调优。面试中先确认 CUB/Thrust/cuBLAS/cuDNN/CUTLASS 是否满足语
义与性能，只有在数据分布、融合机会或定制约束明显时才考虑自写。

## 标准回答
- CUB 对 scan/reduce/select/sort 等 primitives 很成熟。
- cuBLAS/cuBLASLt 对 GEMM 有自动算法选择与 epilogue。
- CUTLASS 适合需要定制 layout/epilogue/schedule 的 GEMM 家族。

- 自写 kernel 的成本包括正确性、跨架构维护、数值稳定性和回归测试。

## Gotchas：常见失分点
- 把“会 CUDA”理解成拒绝任何 library。

## 面试官可能继续追问
- 何时 fused top-k 值得自写？
- 如何验证自写 kernel 真正优于库？

## 深入分析

Top-K/sort/selection 是成熟库高度优化的 primitive。工程优先 CUB/Thrust/专用库；只有 shape、fusion、数据布局或 latency 约束特殊时才值得自定义。

### 深入理解：经典算法题考的是“逐版优化能力”

现场 coding 题通常不要求一步写出最优 kernel，而是考察你能否从正确的 baseline 出发，逐个消除瓶颈：

```text
Correct baseline
→ coalesced access
→ shared/register reuse
→ reduce divergence/barriers
→ warp primitive
→ vectorization / multi-element per thread
→ device-wide library / architecture specialization
```

每一版都要能说明：**减少了什么成本、引入了什么新约束、用什么指标验证**。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：`kernel time`、`memory throughput`、`branch/barrier stalls`、`atomic throughput`、`correctness error`。

### 架构视角

现代库（CUB/CUTLASS/Thrust/cuBLAS）往往比手写通用实现更稳；手写题重点在理解优化路径。

## 实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

1. 写一个**正确但未优化**的 baseline。
2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
4. 使用 Nsight Compute 收集与本题直接相关的指标：`kernel time`、`memory throughput`、`branch/barrier stalls`、`atomic throughput`、`correctness error`。
5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

工程判断优先级：先确认 CUB/Thrust/cuBLAS/cuDNN/CUTLASS 等库是否已有成熟 primitive；只有当需要融合、特殊数据布局、固定小 shape、领域特定语义或库成为可证实瓶颈时才手写。

### 2. 定量推导 / 性能模型

Amdahl 视角：若库调用只占总时长 5%，即便自写快 2×，端到端收益也只有约 2.6%；维护成本却可能长期存在。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// 先建立 library baseline，再写 custom kernel。
// benchmark 必须包含真实 shape / dtype / batch，而非只挑有利样例。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `End-to-end time`
- `Library kernel time / workspace / launch count`
- `Custom vs library correctness + perf across shapes`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

官方库会持续吸收新架构特性；手写 kernel 的隐藏成本之一是每代 GPU 都要重新调优。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

任选 top-k/sort，比较 CUB、Thrust、自写版本在 5 种 N 和 dtype 上的性能/代码量/维护复杂度。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
