# Q078｜为什么很短或 Block 很少的 Kernel，Occupancy 指标可能没意义？

> **一句话核心**：小 grid/短 kernel 可能根本没有足够 blocks 形成稳定 occupancy，主要瓶颈是 launch、wave/tail 或并行度不足。
>
> **章节**：第 8 章 · Nsight、Roofline 与性能诊断  
> **难度**：★★☆ · **频率**：高 · **标签**：Small Kernel / Tail

## PDF 基线题解

## 考察意图
考察 grid-level parallelism。

## 思路拆解
Occupancy 描述“若有足够 blocks，单 SM 可驻留多少 warp”，但如果整个 grid 只有少数 blocks，许多 SM 根本拿不
到工作，瓶颈是 insufficient parallelism 或 launch overhead。

## 标准回答
- small grid 先看 active SM 数、waves、kernel duration。
- 通过 batch、fusion、persistent work queue、增加并行维度等扩大工作。
- 对于微秒级 kernel，CPU launch overhead 可能占主要比例，CUDA Graph 更重要。

## Gotchas：常见失分点
- 对 4-block kernel 花大量时间调 theoretical occupancy。

## 面试官可能继续追问
- 什么是 tail effect？
- 为什么 batched small GEMM 需要专门 kernel？

---

## 深入分析

小 grid/短 kernel 可能根本没有足够 blocks 形成稳定 occupancy，主要瓶颈是 launch、wave/tail 或并行度不足。此时 theoretical occupancy 容易误导。

### 深入理解：Profiler 是假设检验工具，不是“指标排行榜”

性能诊断应遵循 **timeline → hot kernel → roofline/SOL → scheduler/memory/resource counters → source/SASS** 的顺序。任何单个 metric 都不能脱离上下文解读。

尤其是 stall reason：只有当 scheduler 无法持续 issue 时，stall 才值得作为主要矛盾继续深挖；否则高 stall 百分比可能只是正常流水行为。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：grid size、active SMs、waves per SM、kernel duration、launch overhead。

### 架构视角

Nsight Compute 指标名称会随版本变化；稳定方法是从 throughput、scheduler、memory、resource 四类证据建立因果链。

1. 写一个**正确但未优化**的 baseline。

3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

如果 grid 只有很少 blocks，设备大部分 SM 根本拿不到 work；此时“每个 active SM 上 occupancy 80%”无法代表整个 GPU 利用率。短 kernel 还可能主要受 launch overhead、single-wave/tail wave 限制。

### 2. 定量推导 / 性能模型

若 GPU 有 S 个 SM、grid 只有 B<S 个 blocks，则瞬时最多只使用 B/S 的 SM（忽略 cluster 等约束），无论单 SM occupancy 多高。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// 小 N：gridDim 可能只有几块
int grid=(N+block-1)/block;
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Grid size / waves per SM`
- `SM active distribution / duration`
- `Nsight Systems launch overhead`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

更大 GPU 反而可能让固定小 workload 的“设备利用率”更低；这就是 scale-up 时需要 batching/fusion/persistence 的原因之一。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

固定 N，在 20SM 与 100+SM 级 GPU（或模拟减少 blocks）比较，展示 parallelism starvation。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
