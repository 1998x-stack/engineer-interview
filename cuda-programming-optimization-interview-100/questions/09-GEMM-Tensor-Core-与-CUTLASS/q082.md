# Q082｜GEMM 为什么 Arithmetic Intensity 很高？

> **一句话核心**：GEMM 的每个 A/B 元素通过 tiling 被多次用于 FMA，计算量 O(MNK) 而必要数据量增长更慢，因此可达到高 arithmetic intensity。
>

## PDF 基线题解

## 考察意图
考察 FLOPs/bytes 与数据复用。

## 思路拆解
矩阵乘法的计算量为 O(MNK)，通过 blocking 同一个 A/B tile 可以被多个输出元素反复使用，因此 bytes 增长可以慢于
FLOPs，问题在足够大时可走向 compute-bound。

## 标准回答
- 理想 GEMM 每个输入 tile 被多次 reuse。
- 小矩阵/skinny shape 的 reuse 不足或并行度不足，可能仍是 memory/latency-bound。
- 实际 AI 要考虑读 C、写 C、epilogue、cache hit 和 dtype bytes。

## Gotchas：常见失分点
- 只用数学 O(MNK) 就断言任何 GEMM compute-bound。

- 为什么 K 很小的 GEMM 常不饱和 Tensor Core？

## 深入分析

GEMM 的每个 A/B 元素通过 tiling 被多次用于 FMA，计算量 O(MNK) 而必要数据量增长更慢，因此可达到高 arithmetic intensity。

### 深入理解：GEMM 是“数据移动 + 复用 + 专用计算单元”的综合优化

现代 GEMM 的关键不是三重 for-loop，而是让 A/B 数据沿 **HBM → shared → register/TMEM → Tensor Core** 的路径被尽量多次复用，并通过多级 tiling 与 pipeline 保持计算单元持续供料。

CUTLASS/CuTe 的价值就在于把 tile shape、copy atom、MMA atom、pipeline、scheduler、epilogue 拆成可组合策略；面试中要能解释这些抽象对应什么硬件约束。

### 性能因果链

对于本题，建议至少观察：FLOPs、HBM bytes、Arithmetic Intensity、Roofline position。

### 架构视角

Hopper 的 warp-specialized GEMM 与 Blackwell SM100 的结构不同；不能把某代 CUTLASS kernel 机械迁移。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

GEMM 高 arithmetic intensity 来自复用：A 的一个元素参与 N 个输出列，B 的一个元素参与 M 个输出行；合理 tiling 让从 HBM 读入的数据在 shared/register/Tensor Core 层被多次消费。

### 2. 定量推导 / 性能模型

理想大矩阵下 FLOPs $2MNK$，最低读写量约 $(MK+KN+MN)sizeof(T)$，因此 $AI\approx2MNK/[(MK+KN+MN)s]$，尺寸增大时很高。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// arithmetic intensity 不是代码中的某条指令，
// 它由 problem shape + data movement strategy 共同决定。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Roofline`
- `DRAM bytes`
- `Tensor FLOPs`
- `L2/smem reuse`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

降低 dtype bytes 会进一步提高 FLOP/byte，同时 Tensor Core peak 又升高，因此 ridge point 也变化；要按具体 dtype 重新判断 bound。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

M=N=K 从 128→16384，计算理论 AI，并对比实际从 launch/memory-bound 逐渐进入 compute-bound 的趋势。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
