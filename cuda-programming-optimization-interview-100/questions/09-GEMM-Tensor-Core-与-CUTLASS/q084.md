# Q084｜Tensor Core 与普通 CUDA Core 的区别是什么？

> **一句话核心**：CUDA Core 执行通用标量/向量算术，Tensor Core 针对小矩阵 MMA 提供极高吞吐。
>
> **章节**：第 9 章 · GEMM、Tensor Core 与 CUTLASS  
> **难度**：★★☆ · **频率**：极高 · **标签**：Tensor Core / MMA

## PDF 基线题解

## 考察意图
考察 AI kernel 的基础计算单元。

## 思路拆解
CUDA cores 执行标量/向量风格算术指令；Tensor Cores 提供专用矩阵乘加吞吐，以特定 tile/layout/dtype 进行 MMA。
要获得高性能，数据必须满足相应 shape、layout、alignment 和 pipeline。

## 标准回答
- 抽象操作为 D = A×B + C 的矩阵块。
- 支持的 dtype 随架构扩展，包括 TF32、FP16/BF16、FP8、FP4/block-scaled 等。
- Tensor Core 高峰值只有在足够工作量和有效 feed 时才有意义；memory/pipeline 不够仍会饿死 Tensor Core。

## Gotchas：常见失分点
- “用了 half 就自动走 Tensor Core”。

## 面试官可能继续追问
- 如何确认 SASS/PTX 真的发出 MMA？
- TF32 在数值上与 FP32 有何差别？

## 深入分析

CUDA Core 执行通用标量/向量算术，Tensor Core 针对小矩阵 MMA 提供极高吞吐。要获得收益必须满足 datatype/layout/tile/对齐并保持供料。

### 深入理解：GEMM 是“数据移动 + 复用 + 专用计算单元”的综合优化

现代 GEMM 的关键不是三重 for-loop，而是让 A/B 数据沿 **HBM → shared → register/TMEM → Tensor Core** 的路径被尽量多次复用，并通过多级 tiling 与 pipeline 保持计算单元持续供料。

CUTLASS/CuTe 的价值就在于把 tile shape、copy atom、MMA atom、pipeline、scheduler、epilogue 拆成可组合策略；面试中要能解释这些抽象对应什么硬件约束。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：Tensor Core utilization、MMA instruction count、datatype throughput、kernel time。

### 架构视角

Hopper 的 warp-specialized GEMM 与 Blackwell SM100 的结构不同；不能把某代 CUTLASS kernel 机械迁移。

## 实战验证建议

建议为本题建立一个最小可复现实验（microbenchmark）：

1. 写一个**正确但未优化**的 baseline。
2. 只改变一个变量（访问模式、tile、block size、register budget、pipeline stage 等）。
3. 使用 CUDA Event 做设备侧计时，至少 warm-up 后重复多次。
4. 使用 Nsight Compute/Systems 收集与本题直接相关的指标：Tensor Core utilization、MMA instruction count、datatype throughput、kernel time。
5. 把结果写成“假设 → 指标变化 → 时间变化 → 结论”，而不是只保存最终最快参数。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

CUDA Core 执行通用 scalar/vector ALU 指令；Tensor Core 面向矩阵乘加等专用矩阵操作，以 tile/fragment 为工作单元，单位周期完成更高密度的 multiply-accumulate。要获得收益必须满足支持的 dtype/layout/shape。

### 2. 定量推导 / 性能模型

普通 FMA 每次大致贡献 2 FLOPs；Tensor Core 一条矩阵指令覆盖整个小矩阵乘加，等价 FLOPs 可达数百/更多，因此峰值吞吐数量级更高。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// 高层可由 cuBLAS/CUTLASS/WMMA/DSL 表达
// 底层最终映射到架构对应 MMA/Tensor Core 指令。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Tensor pipe utilization`
- `Tensor FLOPs`
- `Fallback scalar instructions`
- `Alignment/layout efficiency`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

Volta→Ampere→Hopper→Blackwell 的 Tensor Core 指令族持续演进；接口层最好避免写死单代 PTX，除非确有必要。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

同尺寸 GEMM 用 scalar FP32 与 Tensor Core 支持的 TF32/FP16 方案比较，连同误差一起报告。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
