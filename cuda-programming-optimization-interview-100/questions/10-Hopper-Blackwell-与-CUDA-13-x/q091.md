# Q091｜Hopper Thread Block Cluster 是什么？

> **一句话核心**：Thread Block Cluster 在 block 与 grid 之间提供协作层级，使 cluster 内 blocks 可同步并使用 DSM。
>
> **章节**：第 10 章 · Hopper、Blackwell 与 CUDA 13.x  
> **难度**：★★★ · **频率**：高 · **标签**：Hopper / Cluster

## PDF 基线题解

## 考察意图
考察 CC 9.0+ 的新层级。

## 思路拆解
Thread Block Cluster 在 Grid 与 Block 之间引入可编程协作层级。一组 blocks 被保证并发调度在相邻硬件范围内，可以
做 cluster-level sync、访问 distributed shared memory，并协同驱动异步单元。

## 标准回答
- 层级扩展为 Grid → Cluster → Block → Thread。
- cluster 内 blocks 可使用 cluster group 同步。
- cluster size 影响 locality、可调度性与资源；不是越大越好。
- 普通 block 仍然只驻留一个 SM，但 cluster 让多个 blocks 跨 SM 协作。

## Gotchas：常见失分点
- 说“一个 block 现在可以跨多个 SM”。

## 面试官可能继续追问
- `__cluster_dims__` 如何指定？
- cluster size 为什么影响 occupancy/scheduling？

---

## 深入分析

Thread Block Cluster 在 block 与 grid 之间提供协作层级，使 cluster 内 blocks 可同步并使用 DSM。它改变了以前“跨 block 只能靠 global/kernel boundary”的部分假设。

### 深入理解：Hopper/Blackwell 的本质是“更强的数据移动与协作原语”

现代架构题不要只背新名词。应把每个能力放进数据流：

```text
HBM --TMA--> Shared/DSM --(copy/MMA path)--> Register or TMEM --> Tensor Core
          ↑ cluster scope / async barriers / producer-consumer pipeline ↑
```

TMA 是数据移动引擎；DSM 是 cluster 级共享地址空间能力；TMEM 是 Blackwell 的 tensor-oriented memory locale。三者角色完全不同。

### 性能因果链

```text
题目现象 / 代码模式
        ↓
定位真实硬件行为
        ↓
识别主要资源或依赖
        ↓
提出一个可证伪优化假设
        ↓
修改实现
        ↓
Profiler 指标 + Kernel Time 验证
```

对于本题，建议至少观察：cluster size、resident clusters、cluster barriers、DSM/TMA traffic。

### 架构视角

Hopper/Blackwell 特性需要匹配 compute capability、Toolkit、driver 与编译目标；优化必须明确目标架构。

## 专业增强版 V2：机制、量化与验证

> 本节是在 PDF 基线题解之上的**仓库扩展**。目标是把“能背答案”升级为“能解释硬件因果、能量化、能用 profiler 证伪”。

### 1. 硬件机制与核心心智模型

Thread Block Cluster 是 CC 9.0+ 的协作层级：把若干 blocks 作为一个 cluster 安排在同一 GPC 内，使它们能 cluster-level synchronize 并访问彼此的 distributed shared memory。Grid/block 索引体系仍存在，只是多了一层分组。

### 2. 定量推导 / 性能模型

cluster size 过大可能降低可调度 cluster 数；可用并行度取决于 GPC/SM 资源与 cluster shape，不能把“8 blocks/cluster”当普适最佳值。

面试时不要只报公式。至少说明：公式里的变量对应什么硬件资源、哪些是假设、实际值应该如何由 profiler 或 microbenchmark 得到。

### 3. 代码 / 白板核心片段

```cpp
// compile-time 示例
__global__ __cluster_dims__(2,1,1) void k(...);
// runtime 可用 cudaLaunchKernelEx 指定 cluster dimension。
```

白板代码优先保证：**边界正确、同步范围正确、地址模式可解释**。如果为了展示优化而省略边界处理，要主动说明省略条件。

### 4. Nsight 证据链：怎样证明你的判断

- `Cluster launch configuration`
- `Active clusters / occupancy（工具支持项）`
- `DSM/synchronization behavior`

推荐把分析写成四列：

| 假设 | 预期指标变化 | 实测指标变化 | 结论 |
|---|---|---|---|
| 当前瓶颈是本题讨论的问题 | 指标应出现可预测变化 | benchmark 后填写 | 接受 / 推翻假设 |
| 优化应减少对应硬件成本 | 时间与因果指标同向改善 | benchmark 后填写 | 是否保留优化 |

### 5. 架构迁移视角

CUDA Programming Guide 13.3：CC 9.0+ 支持 thread-block cluster；cluster 内 blocks 被安排在同一 GPC 并可使用 Cooperative Groups 通信。

这里要区分两类知识：

- **稳定原理**：warp 粒度、数据复用、依赖、Roofline、资源平衡等；
- **架构实现**：具体指令、cache/SM 资源、TMA/TMEM/cluster/TCGen05 等。

面试中如果不确定某代 GPU 的精确容量或吞吐，不要猜数字；说明“会查目标 compute capability / tuning guide 并重新 profile”比报错数字更专业。

### 6. 可复现实验（建议真的做）

在 H100+ 设计两个 blocks 共享 partial histogram/lookup 的 cluster 版本，与 global-memory 协作版本比较。

实验至少记录：GPU 型号、compute capability、CUDA/driver、编译参数、输入 shape/dtype、warm-up、迭代次数、median/p95、correctness tolerance，以及关键 Nsight 指标。
