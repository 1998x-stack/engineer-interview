## 2-5 分钟标准回答

### 1. 核心要点

参数≈Kh·Kw·Cin·Cout（加 bias 则 +Cout）

**深入理解：** 这类结论必须先声明计算口径和 tensor shape。面试时把“公式”继续落到显存访问、并行度和目标硬件；否则只能说明理论工作量，不能推出真实 latency。

### 2. 核心要点

MACs≈Hout·Wout·Kh·Kw·Cin·Cout；若乘加各算一次，FLOPs≈2×MACs

**深入理解：** 这类结论必须先声明计算口径和 tensor shape。面试时把“公式”继续落到显存访问、并行度和目标硬件；否则只能说明理论工作量，不能推出真实 latency。

### 3. 核心要点

Group conv 再除 groups；Depthwise 约 Kh·Kw·Cin，Pointwise 为 Cin·Cout

**深入理解：** 这一章不要停留在“模块是什么”。面试中更重要的是解释它如何改变前向信号、反向梯度、参数效率和硬件执行；同时能说清 train/eval 差异与数值稳定性。

## 关键公式 / 数学口径

若输出空间为 $H_o\times W_o$，标准卷积参数量与 MACs 为：

$$
\text{Params}=K_hK_wC_{in}C_{out}
$$

$$
\text{MACs}=H_oW_oK_hK_wC_{in}C_{out}
$$

若把一次乘法和一次加法分别计为一次 FLOP，常用近似 $\text{FLOPs}\approx2\times\text{MACs}$。

## 代码 / 伪代码

```python
def conv2d_cost(h_out, w_out, cin, cout, kh=3, kw=3, groups=1, bias=False):
    params = kh * kw * cin * cout // groups + (cout if bias else 0)
    macs = h_out * w_out * kh * kw * cin * cout // groups
    flops = 2 * macs
    return params, macs, flops
```

> 面试手撕时先说明输入 shape、坐标/数值口径和边界条件，再写主逻辑。正确性优先于过早微优化。

## 高频追问与参考答案

### 追问 1：给定 224×224×64，3×3 到128通道怎么算？

若输入/输出空间都是 224×224、kernel=3、Cin=64、Cout=128，则参数约为 $3	imes3	imes64	imes128$，MACs 再乘 $224^2$；若 stride/padding 改变输出尺寸，要用实际 $H_o,W_o$。

**回答加分点：** 最后补一句它会如何改变指标、训练稳定性或部署成本；若答案依赖实现约定，先声明约定。

### 追问 2：为什么 FLOPs 与 latency 不等价？

FLOPs 不包含内存访问、kernel launch、layout transform、同步和硬件利用率。低 FLOPs 的 depthwise/小算子可能 memory-bound，因此真实 latency 必须在目标硬件实测。

**回答加分点：** 最后补一句它会如何改变指标、训练稳定性或部署成本；若答案依赖实现约定，先声明约定。

## V2 专业深化

> 这一节是在 PDF/原题解基础上的**专业扩展**：用于把“会答”提升到“能推导、能诊断、能做工程决策”。其中的扩展内容属于通用计算机视觉与工程知识，不用于声称某家公司曾逐字问过这些内容。

### 1. 更精确的技术表述

- 参数量需区分 weight 与 bias；普通 2D conv 权重为 $K_hK_wC_{in}C_{out}/groups$，输出空间大小由 padding/stride/dilation 决定。
- MAC 与 FLOP 口径必须声明：有的系统把一次乘加计 1 MAC，有的把乘和加计 2 FLOPs，面试计算差一倍常只是口径问题。
- 理论 FLOPs 不能推出真实 latency；还要看 memory traffic、kernel fusion、tensor core 对齐、batch 和 operator implementation。

### 2. 回答时必须显式声明的前提

- 写清 tensor shape、参数量/FLOPs 口径、前向信息流和反向梯度路径。
- 把“优化更容易”落到方差、Jacobian、条件数、梯度范数或训练曲线，而不是口号。
- 理论计算量与真实硬件 latency 分开讨论；移动端尤其关注 memory access 和算子支持。

面试中尤其建议先把输入/输出、坐标或 tensor shape、训练/推理阶段以及评价口径说清楚。很多看似“知识点错误”的争论，本质是双方默认的实现约定不同。

### 4. 工程诊断矩阵

| 观察到的现象 | 优先怀疑 | 最小验证实验 |
|---|---|---|
| 训练 loss 不降/震荡 | 初始化、学习率、梯度传播或 normalization | 记录 layer-wise activation/gradient norm 与 LR sweep |
| FLOPs 降但延迟不降 | memory-bound/算子碎片/硬件不友好 | 用 profiler 看 kernel 时间、带宽与 occupancy |

如果这两行都无法解释项目中的真实失败，再继续向数据版本、标注协议、随机性、导出后端或线上流量结构扩展，而不是直接堆更多模型模块。

### 5. 建议做的最小消融

- **Control**：保留原 baseline 的训练预算、数据版本、输入尺寸和评测脚本，只改变与本题直接相关的一项。
- **Slice**：至少增加一个与本题机制直接相关的子集指标；例如尺寸、遮挡、边界、长尾、噪声或设备域。
- **Cost**：同时记录参数量/FLOPs 之外的真实成本：显存、wall-clock、目标硬件 latency、P95/P99 或后处理开销。
- **Regression**：列出方案新增的 FP/FN 或退化场景，避免只展示改善样本。
- **Repeatability**：若提升幅度较小，使用多随机种子或 bootstrap 置信区间，判断收益是否超出自然波动。
