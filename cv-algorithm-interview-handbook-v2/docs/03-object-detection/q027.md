## 30 秒回答

Backbone 提特征，RPN 生成 proposals，ROIAlign/Pooling 抽取固定尺寸特征，RCNN head 分类并回归 bbox。

如果只能再补一句：**Faster R-CNN = shared feature + RPN 候选 + ROI 精修。**

## 面试官真正想听什么

这题不是只检查名词记忆，而是在看你能否把**机制、边界条件和工程后果**连起来。一个高质量回答至少覆盖下面三个层次：

1. **定义/结构**：先说明对象是什么，避免一上来堆历史或模块名。
2. **为什么有效**：用关键公式或信息流解释机制，而不是只说“效果更好”。
3. **什么时候会失效**：主动给出 trade-off、数据条件与部署注意事项。

## 2-5 分钟标准回答

### 1. 核心要点

RPN 对 anchors 预测 objectness + bbox delta，并按 IoU 分正负样本

**深入理解：** 检测中的表示、匹配、后处理和评测是耦合的：改变一个阈值可能同时移动 recall/precision。回答时最好明确“训练阶段的匹配”与“评测/部署阶段的匹配或去重”不是同一个概念。

### 2. 核心要点

proposal 经 NMS/top-k 后送 ROI head

**深入理解：** 检测中的表示、匹配、后处理和评测是耦合的：改变一个阈值可能同时移动 recall/precision。回答时最好明确“训练阶段的匹配”与“评测/部署阶段的匹配或去重”不是同一个概念。

### 3. 核心要点

常见 loss=L_rpn_cls+L_rpn_box+L_roi_cls+L_roi_box；Mask R-CNN 再加 mask loss

**深入理解：** 检测题建议始终沿着“表示 - 匹配 - 分类/回归 - 后处理 - 指标”五层回答。很多线上问题并不是 backbone 不够强，而是 label assignment、阈值、NMS、尺度分布或数据漏标共同造成。

## 高频追问与参考答案

### 追问 1：RPN 与 Fast R-CNN 区别？

RPN 负责“哪里可能有目标”，输出 objectness 与 proposal box；Fast R-CNN head 对 proposal 做类别判定和更精细的 bbox regression。

**回答加分点：** 最后补一句它会如何改变指标、训练稳定性或部署成本；若答案依赖实现约定，先声明约定。

### 追问 2：Faster R-CNN 有几个 loss？

Faster R-CNN 典型有 RPN classification、RPN bbox regression、ROI classification、ROI bbox regression 四类损失，具体实现可能做加权或共享。

**回答加分点：** 最后补一句它会如何改变指标、训练稳定性或部署成本；若答案依赖实现约定，先声明约定。

### 追问 3：bbox delta 为什么对 w/h 取 log？

宽高是乘法尺度变化，取 log 后变成近似加法偏移，更容易建模不同绝对尺寸下的相对缩放。

**回答加分点：** 最后补一句它会如何改变指标、训练稳定性或部署成本；若答案依赖实现约定，先声明约定。

## V2 专业深化

> 这一节是在 PDF/原题解基础上的**专业扩展**：用于把“会答”提升到“能推导、能诊断、能做工程决策”。其中的扩展内容属于通用计算机视觉与工程知识，不用于声称某家公司曾逐字问过这些内容。

### 1. 更精确的技术表述

- Faster R-CNN 的关键链路是 backbone/FPN → RPN → proposal sampling → ROIAlign → classification/bbox head；训练时 RPN 与 ROI head 各有匹配规则和 loss。
- RPN 的 anchor/objectness 与 ROI head 的最终类别不是同一任务；proposal recall 是二阶段检测上限的重要前置指标。
- 诊断时应分开看 RPN recall、ROI classification error、box regression error 和 NMS，而不是只看最终 mAP。

### 2. 回答时必须显式声明的前提

- 检测问题统一沿“表示→匹配/assignment→分类/回归→后处理→评测”定位。
- 始终区分训练正负样本匹配、推理 threshold/NMS、评测 IoU matching，这三者语义不同。
- 至少报告一个尺寸/遮挡/类别切片，避免总体 mAP 掩盖真实 failure mode。

面试中尤其建议先把输入/输出、坐标或 tensor shape、训练/推理阶段以及评价口径说清楚。很多看似“知识点错误”的争论，本质是双方默认的实现约定不同。

### 3. 从“结论”推进到“机制”的推理链

针对 **Faster R-CNN 完整流程是什么？**，推荐强制自己完成以下链条：

```text
现象/任务约束
  → 数学对象或网络中的信息流
  → 为什么当前设计能改变梯度/表示/几何/搜索空间
  → 得到什么收益
  → 付出什么代价
  → 哪些数据分布下会失效
  → 用什么切片实验和 profiler 证明
```

不要把“论文上更好”当作最后一层证据。真正专业的答案需要把方法映射到**具体 failure mode**，再设计能证伪自己的实验。

### 4. 工程诊断矩阵

| 观察到的现象 | 优先怀疑 | 最小验证实验 |
|---|---|---|
| Recall 低 | 漏标、assignment、score/NMS 或小目标信息丢失 | 建立 FN taxonomy 并分别扫描 conf/NMS threshold |
| AP75 低但 AP50 尚可 | 定位精度不足 | 检查 bbox error、输入分辨率与回归 loss/ROI alignment |

如果这两行都无法解释项目中的真实失败，再继续向数据版本、标注协议、随机性、导出后端或线上流量结构扩展，而不是直接堆更多模型模块。

### 5. 建议做的最小消融

- **Control**：保留原 baseline 的训练预算、数据版本、输入尺寸和评测脚本，只改变与本题直接相关的一项。
- **Slice**：至少增加一个与本题机制直接相关的子集指标；例如尺寸、遮挡、边界、长尾、噪声或设备域。
- **Cost**：同时记录参数量/FLOPs 之外的真实成本：显存、wall-clock、目标硬件 latency、P95/P99 或后处理开销。
- **Regression**：列出方案新增的 FP/FN 或退化场景，避免只展示改善样本。
- **Repeatability**：若提升幅度较小，使用多随机种子或 bootstrap 置信区间，判断收益是否超出自然波动。
