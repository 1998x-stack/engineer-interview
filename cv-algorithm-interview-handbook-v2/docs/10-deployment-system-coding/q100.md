# Q100 · 项目终极拷问：你的模型为什么提升了 3 个点？

## 30 秒回答

用 Failure→Hypothesis→Change→Ablation→Cost→Business Decision 的因果链证明，而不是罗列模块。

如果只能再补一句：**黄金链：失败模式→假设→改动→消融→成本→业务结论。**

## 面试官真正想听什么

这题不是只检查名词记忆，而是在看你能否把**机制、边界条件和工程后果**连起来。一个高质量回答至少覆盖下面三个层次：

1. **定义/结构**：先说明对象是什么，避免一上来堆历史或模块名。
2. **为什么有效**：用关键公式或信息流解释机制，而不是只说“效果更好”。
3. **什么时候会失效**：主动给出 trade-off、数据条件与部署注意事项。

## 2-5 分钟标准回答

### 1. 核心要点

先给 baseline 和明确 failure slice，例如总体 AP43.1、AP_s21.3

**深入理解：** 检测中的表示、匹配、后处理和评测是耦合的：改变一个阈值可能同时移动 recall/precision。回答时最好明确“训练阶段的匹配”与“评测/部署阶段的匹配或去重”不是同一个概念。

### 2. 核心要点

提出机制假设并对应改动，例如 stride 过大→加 P2/改 assignment

**深入理解：** 部署与系统题必须从端到端 SLA 出发。FLOPs、参数量只是代理指标；真正决策依赖目标硬件、内存访问、算子支持、batch、并发、前后处理和 P95/P99。

### 3. 核心要点

逐项消融并报告关键 slice 与成本，例如 latency 8.1→9.5ms、memory+12%，再说明 SLA 内为何值得

**深入理解：** 部署结论只能在明确硬件、精度、batch、并发、输入尺寸和前后处理后成立。建议把理论复杂度、kernel profile 与端到端 SLA 三层同时报告。

## 深入解析：从原理到工程

部署与系统题必须从端到端 SLA 出发。FLOPs、参数量只是代理指标；真正决策依赖目标硬件、内存访问、算子支持、batch、并发、前后处理和 P95/P99。

对 **Q100** 尤其要注意：优秀项目陈述应展示 failure migration 和可复现实验记录。 这不是附加知识，而是把理论答案变成“可上线判断”的关键一步。

### 推荐的口述顺序

```text
一句定义 → 关键公式/结构 → 设计动机 → 优势 → 局限/失败模式 → 工程验证
```

## 高频追问与参考答案

### 追问 1：如何证明不是参数量带来的？

构造参数量/计算量匹配的 control，例如加宽 baseline 或替换同等参数模块；若只有目标模块提升，因果证据更强。

**回答加分点：** 最后补一句它会如何改变指标、训练稳定性或部署成本；若答案依赖实现约定，先声明约定。

### 追问 2：如何证明不是随机种子？

至少重复多个 seed，报告均值/标准差或置信区间；若提升小于 run-to-run variance，不能宣称稳定收益。

**回答加分点：** 最后补一句它会如何改变指标、训练稳定性或部署成本；若答案依赖实现约定，先声明约定。

### 追问 3：涨点但超 SLA 怎么办？

先判断是否能通过量化、蒸馏、分辨率/后处理优化回收成本；若仍超 SLA，就要按业务目标做 Pareto trade-off，而不是用离线指标强行上线。

**回答加分点：** 最后补一句它会如何改变指标、训练稳定性或部署成本；若答案依赖实现约定，先声明约定。

## 常见失分点

- “加 attention 所以涨了”没有因果证据，只报 best run 也有 selection bias。
- 只背结论，不解释“为什么”，或没有指出结论成立的前提。
- 论文/离线结论直接套到自己的数据，却没有给出切片实验或消融。

## 工程 / 项目视角

优秀项目陈述应展示 failure migration 和可复现实验记录。

建议把自己的项目补成以下四个事实：

- **数据条件**：这个机制在哪些尺寸/类别/光照/噪声/设备上最重要？
- **评价切片**：不能只看总体均值，至少有一个与本题机制直接相关的 slice。
- **成本**：训练显存、参数量、FLOPs、目标硬件 latency、前后处理成本至少知道一个。
- **回归**：新增方案让哪些场景变差？上线前如何兜底？

## V2 专业深化

> 这一节是在 PDF/原题解基础上的**专业扩展**：用于把“会答”提升到“能推导、能诊断、能做工程决策”。其中的扩展内容属于通用计算机视觉与工程知识，不用于声称某家公司曾逐字问过这些内容。

### 1. 更精确的技术表述

- “涨 3 点”必须形成 Failure→Hypothesis→Change→Ablation→Cost→Business Decision 的证据链；模块名不是因果解释。
- 最强证据包括多个 seed、参数/FLOPs 匹配 control、关键 failure slice 的定向改善、回归场景和显著性/置信区间。
- 项目陈述还应报告训练与部署成本、SLA 是否满足以及为什么业务愿意接受 trade-off；这能区分研究 demo 与生产决策。

### 2. 回答时必须显式声明的前提

- 系统题先固定硬件、batch、输入尺寸、precision、并发和 SLA，再谈模型快慢。
- 理论 FLOPs/参数量、kernel profile、端到端 latency 是三层不同证据，不能混为一谈。
- 任何导出/量化/加速都必须配 numerical parity 与业务指标回归。

面试中尤其建议先把输入/输出、坐标或 tensor shape、训练/推理阶段以及评价口径说清楚。很多看似“知识点错误”的争论，本质是双方默认的实现约定不同。

### 3. 从“结论”推进到“机制”的推理链

针对 **项目终极拷问：你的模型为什么提升了 3 个点？**，推荐强制自己完成以下链条：

```text
现象/任务约束
  → 数学对象或网络中的信息流
  → 为什么当前设计能改变梯度/表示/几何/搜索空间
  → 得到什么收益
  → 付出什么代价
  → 哪些数据分布下会失效
  → 用什么切片实验和 profiler 证明
```

不要把“论文上更好”当作最后一层证据。真正专业的答案需要把方法映射到**具体 failure mode**，再设计能证伪自己的实验。

### 4. 工程诊断矩阵

| 观察到的现象 | 优先怀疑 | 最小验证实验 |
|---|---|---|
| 理论模型快但线上慢 | 前后处理/数据搬运/queue/kernel 瓶颈 | 端到端 trace + GPU profiler + P95/P99 |
| 加速后精度掉 | 数值误差/算子替换/预处理不一致 | PyTorch→ONNX→backend 分阶段 parity 与阈值回归 |

如果这两行都无法解释项目中的真实失败，再继续向数据版本、标注协议、随机性、导出后端或线上流量结构扩展，而不是直接堆更多模型模块。

### 5. 建议做的最小消融

- **Control**：保留原 baseline 的训练预算、数据版本、输入尺寸和评测脚本，只改变与本题直接相关的一项。
- **Slice**：至少增加一个与本题机制直接相关的子集指标；例如尺寸、遮挡、边界、长尾、噪声或设备域。
- **Cost**：同时记录参数量/FLOPs 之外的真实成本：显存、wall-clock、目标硬件 latency、P95/P99 或后处理开销。
- **Regression**：列出方案新增的 FP/FN 或退化场景，避免只展示改善样本。
- **Repeatability**：若提升幅度较小，使用多随机种子或 bootstrap 置信区间，判断收益是否超出自然波动。

### 6. 专家级追问清单

1. **如何证明不是参数量带来的？**：先给结论，再说明一个成立前提、一个反例/边界和一个可验证实验。
2. **如何证明不是随机种子？**：先给结论，再说明一个成立前提、一个反例/边界和一个可验证实验。
3. **涨点但超 SLA 怎么办？**：先给结论，再说明一个成立前提、一个反例/边界和一个可验证实验。
4. **在指定硬件/precision/batch 下瓶颈是 compute 还是 memory？**：先给结论，再说明一个成立前提、一个反例/边界和一个可验证实验。
5. **如何设计数值 parity 和性能 regression gate？**：先给结论，再说明一个成立前提、一个反例/边界和一个可验证实验。

### 7. 面试表达升级模板

> “我先明确这里的实现/评价口径。核心机制是 **A**，它通过 **B** 改变了 **C**，所以在 **D 类数据**上预期有效；代价是 **E**。如果这是我的项目，我会用 **一个控制实验 + 一个关键切片 + 一个真实硬件/线上指标** 来验证，而不是只看总体平均分。”

把这个模板替换成当前题目的具体名词后，通常可以自然从 30 秒回答扩展到 3–5 分钟，并且给面试官留下继续追问的接口。
