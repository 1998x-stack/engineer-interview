# 内容质量标准（v2-deep）

本仓库不是“100 道定义题”的集合。每个 Markdown 都需要通过 **知识正确性、面试表达、数学/Shape、工程验证、失败边界、项目证据链** 六类检查。

## 每题必须具备的层次

1. **一句话结论**：20 秒内给出不绕弯的核心判断。
2. **60–90 秒标准回答**：真实面试首轮回答，不堆砌所有细节。
3. **深度解析**：解释 Why，而不只是 What。
4. **数学 / Shape / 复杂度**：能定量的题必须定量；不能硬套闭式公式的系统题要给资源量或变量关系。
5. **工程实现 / 验证协议**：必须是该题特定实验，不允许通用占位模板。
6. **工程实践与诊断**：说明训练、推理、数据或系统中的实际表现。
7. **连续追问与失分点**：覆盖面试官常见第二、第三层追问。
8. **90 分深挖**：机制、定量、工程、失败边界与专项白板练习。
9. **项目化证据链**：告诉读者面试时应该拿出哪些 metric、ablation、profiling 或线上数据证明自己真的做过。
10. **自测与关联题目**：用于形成知识图谱，而非孤立背题。

## 自动质量门槛

`scripts/check_repo.py` 当前检查：

- Q001–Q100 恰好 100 个题目文件且编号连续；
- 每题包含 v2-deep 必需章节；
- 每题正文不少于 3500 字符；
- 不允许残留“建议的最小验证套路”等通用占位；
- 每题必须具有题目特定的 `推荐验证协议`；
- 内部 Markdown 链接必须可解析；
- `metadata/questions.json` 保持 100 条记录；
- README 索引由 `build_index.py --check` 保持同步。

## 写作原则

### 不把经验规律写成定理

例如“SGD 泛化一定比 Adam 好”“FlashAttention 把 O(T²) 变成 O(T)”“BF16 精度比 FP16 更高”都属于需要明确纠正的表述。答案应说明成立条件、近似、硬件和任务依赖。

### 不把 API 当原理

`torch.nn.MultiheadAttention`、`FSDP`、`vLLM`、`PEFT` 都只是实现入口。面试答案必须能退回到 tensor shape、通信、内存和数学目标层面。

### 不只报告平均值

训练、评估与 Serving 都需要关注 slice 与长尾。系统题至少考虑 P95/P99；Post-training 要看 held-out 与 regression；推荐/分类要看类别/人群/时间切片。

### 优先原始论文和官方文档

快速变化主题（LoRA 生态、FSDP2、PyTorch SDPA、vLLM 等）应优先链接官方/原始资料，并在必要时标明这是现代实现扩展，而不是原论文中的设计。

## Review 建议

PR Review 时建议用下面的问题审阅每一题：

- 读完能不能在 90 秒内回答？
- 能不能在白板上写出关键公式或 shape？
- 是否有一个可以运行或执行的验证方法？
- 是否明确指出至少一个失败边界？
- 是否能把该题落到项目指标、profiling、ablation 或线上数据？
- 是否和相邻题的概念边界清楚？
