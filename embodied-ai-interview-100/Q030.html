为什么端到端策略仍常配 classical low-level controller？

难度：★★★☆☆
模块：第三篇 规划、控制与 Manipulation
标签：control / manipulation / planning

[!NOTE] 内容边界：PDF Core 小节忠实保留 PDF 题解的术语、结构与结论；标记为 Repository Expansion 的内容是为了 GitHub 版进一步补充的标准理论、工程实践与 2026 资料。

1. 这道题在考什么？ — PDF Core

考察系统分层。

为什么重要 — Repository Expansion

规划与控制题考察“从目标到安全轨迹”的完整链路。越接近实机，稳定性、碰撞、接触、控制频率和执行器约束越重要。

这题建议始终放回具身闭环理解：Observation → State/Representation → Policy/Planner → Action → Controller → Robot → New Observation。面试官通常会从定义继续追到“如果真的上机器人，接口、误差和失败模式是什么”。

2. 30 秒回答 — PDF Core

学习策略擅长语义、任务与中频动作；经典 controller 擅长高频稳定、限幅、安全和动力学。两者分工使系统更稳定、更可迁移。

3. 5-10 分钟深度题解

3.1 典型 VLA 5-50Hz，joint servo 100-1000Hz，驱动器更高

典型 VLA 5-50Hz，joint servo 100-1000Hz，驱动器更高。

3.2 低层可以插值 action chunk、处理关节限位、速度/力矩 limit

低层可以插值 action chunk、处理关节限位、速度/力矩 limit。

3.3 安全相关 constraints 不应完全寄希望于概率模型

4. 数学 / 公式 / 结构 — PDF Core + Expansion

high-level intelligence + low-level stability

面试白板上写出公式后，不要停在符号层。至少解释：变量属于哪个空间、维度是什么、哪个量可观测、哪个量需要估计/优化，以及公式在接近边界条件时是否稳定。

5. 白板实现应该写到什么程度？ — Repository Expansion

不要求现场实现完整工业系统，但应能写清状态表示、主要循环、关键约束和失败回退。若涉及学习算法，还要能指出训练 loop 与 rollout/evaluation loop 的区别。

6. 工程实现与系统接口 — Repository Expansion

把规划层和控制层职责拆开：规划产生可行路径/参考，控制保证高频跟踪与接触稳定；VLA/策略通常位于更上层，不应承担所有实时稳定性职责。

建议关注的指标

  • 路径长度与规划耗时

  • 最小障碍距离 / 碰撞率

  • 跟踪误差 / 超调 / 稳态误差

  • 接触力峰值与任务成功率

最小验证实验

  1. 先构造一个可控、可复现的最小场景作为 baseline。
  2. 只改变一个变量做 A/B；记录均值之外的失败分布。
  3. 对边界条件或 OOD 场景单独建立回归测试。
  4. 最后才进入全系统实机验证，并保留日志、视频和时序数据以便复盘。

7. 工程 Gotchas — PDF Core

  • ⚠️ 把“端到端”理解成不允许任何 classical module。

Debug Checklist — Repository Expansion

  • [ ] 把失败分成“无可行路径”“轨迹不平滑”“控制跟不上”“模型目标错误”。

  • [ ] 优先检查频率、限幅和坐标系。

  • [ ] 接触任务必须同时看位置与力。

13. 深度增强题解 — Repository Expansion v2.0

本节是 GitHub 版二次研究扩展，不替代前面的 PDF Core。目标是把“知道概念”提升到“能推导、能实现、能定位实机失败”。

13.1 从定义升级到问题建模

端到端 policy 的输出频率通常远低于关节伺服频率。低层 classical controller 提供确定性的约束、稳定性和安全包络，相当于把高维硬件动态从学习策略中抽象掉。

系统设计里应明确 policy/controller responsibility boundary：policy 决策目标，controller 保证可执行；出错时日志能区分 perception/policy/planning/control/hardware。

面试时建议主动定义四件事：输入是什么、输出是什么、变量属于哪个空间/时间尺度、成功由什么指标判定。这会显著减少后续追问中的歧义。

13.2 Why：这个机制为什么有效？

  1. 先找瓶颈/约束：本题的方法不是孤立技巧，而是在特定假设下消除一个明确瓶颈。
  2. 再找替代方案：至少能说出一种替代路线，并说明它在数据、计算、稳定性、实时性或泛化上的取舍。
  3. 最后落到闭环：真正机器人系统最终都会回到 感知 → 状态 → 决策 → 动作 → 控制 → 新观测；任何局部优化都要验证是否提高闭环 task metric。

一个常用的工程化表达是：

离线指标改善
   ↓（必要但不充分）
模块级接口正确
   ↓
闭环 rollout 稳定
   ↓
OOD / 长尾仍成立
   ↓
实机 SLO / 安全约束满足

13.3 白板 / 实现骨架

Goal → Planning Scene/State → Global/Task Planner
     → Feasible trajectory → Time parameterization
     → Low-level controller → actuator
     → safety monitor / fallback

规划成功不等于执行成功；必须分别观测 planning、execution、control 三层。

白板必画：画 planner→trajectory→controller→robot→sensor feedback，并标出 safety/fallback 插入位置。

13.4 失败模式：不要只会解释“成功时为什么工作”

失败类型 典型现象 优先检查的证据
F1 规划成功但轨迹不可执行 最小可复现实验 + 原始时序日志
F2 控制频率/延迟导致闭环失稳 边界条件 / OOD 分桶统计
F3 接触模型或 force sensor 误差 模块输入输出与数值范围
F4 安全约束只在规划层而非执行层 闭环回放、视频、控制/系统 telemetry

专业回答应避免“模型效果不好”这种不可诊断描述，而是把失败拆成可观测类别，并给每一类一个证据链。

13.5 指标体系：怎样证明你的答案在工程上成立？

本题至少建议关注：plan success、planning time、clearance、trajectory jerk、tracking error、contact force、collision rate。

评估时优先使用：

  • 均值 + 分位数/置信区间，避免只报单个平均数；
  • 按场景分桶：seen / OOD、短时 / 长时、成功 / near-miss；
  • A/B 单变量实验：一次只改一个核心变量；
  • 闭环指标优先于离线 proxy：离线 loss/accuracy 只能解释部分问题。

13.6 面试追问树：从“会答”到“扛得住追问”

  • 何时可以直接学 torque policy？：先给 1 句结论；再回到本题的核心变量/公式；最后给一个可测的实机或离线证据。不要只复述名词。
  • 控制器会不会限制策略能力？：先给 1 句结论；再回到本题的核心变量/公式；最后给一个可测的实机或离线证据。不要只复述名词。

进一步的 Senior 追问通常会变成：

  1. 如果这个方法不起作用，你如何判断是数据、模型、控制还是系统问题？
  2. 如果算力减半 / 数据减半 / 延迟预算减半，你会保留什么？
  3. 如何设计最小 ablation 证明改进来自你声称的机制，而不是额外参数量或更多数据？
  4. 这个结论在哪些 robot / task / control regime 下可能失效？

13.8 一页速记

  • 一句话本质：端到端 policy 的输出频率通常远低于关节伺服频率。
  • 最容易答错：只背术语，不定义 frame / state / action / time scale / metric。
  • 工程优先级：先验证输入输出和时序，再优化模型；先建立 failure taxonomy，再增加数据/参数。
  • 面试高分信号：能给公式或结构图 + 能说替代方案 + 能给失败证据 + 能设计 A/B。

记忆锚点：先说机制，再说边界；先画闭环，再谈模型。
