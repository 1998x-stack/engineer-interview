如果给你 1000 小时机器人数据预算，如何分配？

难度：★★★☆☆
模块：第四篇 模仿学习与机器人数据
标签：behavior-cloning / imitation-learning / robot-data

[!NOTE] 内容边界：PDF Core 小节忠实保留 PDF 题解的术语、结构与结论；标记为 Repository Expansion 的内容是为了 GitHub 版进一步补充的标准理论、工程实践与 2026 资料。

1. 这道题在考什么？ — PDF Core

考察数据战略与闭环。

为什么重要 — Repository Expansion

模仿学习的核心不是把 demonstration 拟合得更低，而是让部署分布上的闭环行为可靠。数据覆盖、多模态策略、错误恢复和 operator bias 往往比网络结构更关键。

这题建议始终放回具身闭环理解：Observation → State/Representation → Policy/Planner → Action → Controller → Robot → New Observation。面试官通常会从定义继续追到“如果真的上机器人，接口、误差和失败模式是什么”。

2. 30 秒回答 — PDF Core

先覆盖通用 primitives 和多场景，再针对模型失败状态、稀有接触、高难任务做主动采样；同时保留一定失败/恢复数据和 cross-embodiment 数据。

4. 数学 / 公式 / 结构 — PDF Core + Expansion

budget_i ∝ expected deployment frequency × current failure × marginal gain

面试白板上写出公式后，不要停在符号层。至少解释：变量属于哪个空间、维度是什么、哪个量可观测、哪个量需要估计/优化，以及公式在接近边界条件时是否稳定。

5. 白板实现应该写到什么程度？ — Repository Expansion

不要求现场实现完整工业系统，但应能写清状态表示、主要循环、关键约束和失败回退。若涉及学习算法，还要能指出训练 loop 与 rollout/evaluation loop 的区别。

6. 工程实现与系统接口 — Repository Expansion

数据应保存来源、操作者、任务、场景、成功/失败、控制模式和时间戳。训练/验证切分应按场景或任务隔离，避免同一轨迹邻近帧泄漏。

建议关注的指标

  • offline action error / NLL

  • 真实或仿真 rollout success

  • 干预次数 / recovery rate

  • 数据覆盖度与跨场景泛化

最小验证实验

  1. 先构造一个可控、可复现的最小场景作为 baseline。
  2. 只改变一个变量做 A/B；记录均值之外的失败分布。
  3. 对边界条件或 OOD 场景单独建立回归测试。
  4. 最后才进入全系统实机验证，并保留日志、视频和时序数据以便复盘。

7. 工程 Gotchas — PDF Core

  • ⚠️ 只按任务数平均。

Debug Checklist — Repository Expansion

  • [ ] 先看失败状态是否在训练集出现。

  • [ ] 检查 action normalization 与控制频率。

  • [ ] 对多模态动作避免只看 MSE。

  • [ ] 检查 train / validation / deployment 的 observation、action、单位、频率和 normalization 是否完全一致。

13. 深度增强题解 — Repository Expansion v2.0

本节是 GitHub 版二次研究扩展，不替代前面的 PDF Core。目标是把“知道概念”提升到“能推导、能实现、能定位实机失败”。

13.1 从定义升级到问题建模

1000 小时预算应按“边际信息价值”分配，而不是平均分。先覆盖基础 primitive 和关键任务，再主动采样模型低置信、失败恢复、OOD 物体/姿态与长尾场景。

建立 data flywheel：rollout→failure taxonomy→优先级→采集/修正→retrain。每轮都记录 Δsuccess / robot-hour，才能判断数据是否有效。

面试时建议主动定义四件事：输入是什么、输出是什么、变量属于哪个空间/时间尺度、成功由什么指标判定。这会显著减少后续追问中的歧义。

13.2 Why：这个机制为什么有效？

  1. 先找瓶颈/约束：本题的方法不是孤立技巧，而是在特定假设下消除一个明确瓶颈。
  2. 再找替代方案：至少能说出一种替代路线，并说明它在数据、计算、稳定性、实时性或泛化上的取舍。
  3. 最后落到闭环：真正机器人系统最终都会回到 感知 → 状态 → 决策 → 动作 → 控制 → 新观测；任何局部优化都要验证是否提高闭环 task metric。

一个常用的工程化表达是：

离线指标改善
   ↓（必要但不充分）
模块级接口正确
   ↓
闭环 rollout 稳定
   ↓
OOD / 长尾仍成立
   ↓
实机 SLO / 安全约束满足

13.3 白板 / 实现骨架

for batch in loader:
    obs, action = batch['obs'], batch['action']
    pred = policy(obs)
    loss = behavior_loss(pred, action)
    loss.backward(); opt.step()
# 单独做 closed-loop rollout，不能只看 validation loss

IL 的核心质量门槛是 closed-loop success 与 failure distribution，不是 offline MSE。

白板必画：画 expert dataset 与 policy rollout 的分布差异，解释为什么 offline supervised metric 不能替代闭环评测。

13.4 失败模式：不要只会解释“成功时为什么工作”

失败类型 典型现象 优先检查的证据
F1 offline loss 好但 rollout 崩溃 最小可复现实验 + 原始时序日志
F2 多模态被平均 边界条件 / OOD 分桶统计
F3 数据覆盖不足/重复度高 模块输入输出与数值范围
F4 operator/style/domain 泄漏造成虚假泛化 闭环回放、视频、控制/系统 telemetry

专业回答应避免“模型效果不好”这种不可诊断描述，而是把失败拆成可观测类别，并给每一类一个证据链。

13.5 指标体系：怎样证明你的答案在工程上成立？

本题至少建议关注：closed-loop success、recovery rate、OOD success、action NLL/MSE（仅辅助）、data coverage、robot-hour efficiency。

评估时优先使用：

  • 均值 + 分位数/置信区间，避免只报单个平均数；
  • 按场景分桶：seen / OOD、短时 / 长时、成功 / near-miss；
  • A/B 单变量实验：一次只改一个核心变量；
  • 闭环指标优先于离线 proxy：离线 loss/accuracy 只能解释部分问题。

13.6 面试追问树：从“会答”到“扛得住追问”

  • 失败数据占比多少？：先给 1 句结论；再回到本题的核心变量/公式；最后给一个可测的实机或离线证据。不要只复述名词。
  • 如何评估新增 100h 数据值不值？：先给 1 句结论；再回到本题的核心变量/公式；最后给一个可测的实机或离线证据。不要只复述名词。

进一步的 Senior 追问通常会变成：

  1. 如果这个方法不起作用，你如何判断是数据、模型、控制还是系统问题？
  2. 如果算力减半 / 数据减半 / 延迟预算减半，你会保留什么？
  3. 如何设计最小 ablation 证明改进来自你声称的机制，而不是额外参数量或更多数据？
  4. 这个结论在哪些 robot / task / control regime 下可能失效？

13.8 一页速记

  • 一句话本质：1000 小时预算应按“边际信息价值”分配，而不是平均分。
  • 最容易答错：只背术语，不定义 frame / state / action / time scale / metric。
  • 工程优先级：先验证输入输出和时序，再优化模型；先建立 failure taxonomy，再增加数据/参数。
  • 面试高分信号：能给公式或结构图 + 能说替代方案 + 能给失败证据 + 能设计 A/B。

记忆锚点：先说机制，再说边界；先画闭环，再谈模型。
