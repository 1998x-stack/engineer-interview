Absolute Action 与 Relative Action 有什么区别？

难度：★★★☆☆
模块：第九篇 仿真、数据工程与实机部署
标签：data-engineering / deployment / simulation

[!NOTE] 内容边界：PDF Core 小节忠实保留 PDF 题解的术语、结构与结论；标记为 Repository Expansion 的内容是为了 GitHub 版进一步补充的标准理论、工程实践与 2026 资料。

1. 这道题在考什么？ — PDF Core

考察 action representation。

为什么重要 — Repository Expansion

仿真与部署题考察研究系统能否真正运行：数据 schema、同步、控制率、延迟、simulator fidelity 和可复现性通常决定线上效果。

这题建议始终放回具身闭环理解：Observation → State/Representation → Policy/Planner → Action → Controller → Robot → New Observation。面试官通常会从定义继续追到“如果真的上机器人，接口、误差和失败模式是什么”。

2. 30 秒回答 — PDF Core

Absolute action 直接给目标位姿/关节值；relative action 给相对当前状态的 Δ。Relative 通常更局部、跨场景更自然，但误差可累积；absolute 更有全局纠偏能力但对坐标/标定更敏感。

3. 5-10 分钟深度题解

3.1 Relative action 必须定义在哪个 frame：base、EE、camera

Relative action 必须定义在哪个 frame：base、EE、camera。

3.2 训练频率改变时 delta-per-step 的物理速度会改变

训练频率改变时 delta-per-step 的物理速度会改变。

3.3 混合方案可预测 relative motion + occasional absolute target

混合方案可预测 relative motion + occasional absolute target。

3.X 专题增强 — Repository Expansion

  • 动作定义必须和 control period 绑定。Delta action 在不同频率下对应完全不同的物理速度；训练与部署若改变频率，应重新解释/缩放 action，而不能只修改 inference loop。

4. 数学 / 公式 / 结构 — PDF Core + Expansion

absolute: a=x*;  relative: a=Δx

面试白板上写出公式后，不要停在符号层。至少解释：变量属于哪个空间、维度是什么、哪个量可观测、哪个量需要估计/优化，以及公式在接近边界条件时是否稳定。

5. 白板实现应该写到什么程度？ — Repository Expansion

不要求现场实现完整工业系统，但应能写清状态表示、主要循环、关键约束和失败回退。若涉及学习算法，还要能指出训练 loop 与 rollout/evaluation loop 的区别。

6. 工程实现与系统接口 — Repository Expansion

所有传感器与动作应有统一 timestamp；数据集应版本化 calibration、robot config、任务和 episode metadata；训练和部署的 action semantics、频率与图像预处理必须一致。

建议关注的指标

  • 采样/仿真吞吐

  • sensor-action 时间偏差

  • 端到端 inference latency

  • 实机成功率、干预率和复现率

最小验证实验

  1. 先构造一个可控、可复现的最小场景作为 baseline。
  2. 只改变一个变量做 A/B；记录均值之外的失败分布。
  3. 对边界条件或 OOD 场景单独建立回归测试。
  4. 最后才进入全系统实机验证，并保留日志、视频和时序数据以便复盘。

7. 工程 Gotchas — PDF Core

  • ⚠️ 没说明 delta 的坐标系和单位。

Debug Checklist — Repository Expansion

  • [ ] 先做数据/时间/单位一致性检查。

  • [ ] 把模型耗时拆成采集、预处理、推理、通信、控制。

13. 深度增强题解 — Repository Expansion v2.0

本节是 GitHub 版二次研究扩展，不替代前面的 PDF Core。目标是把“知道概念”提升到“能推导、能实现、能定位实机失败”。

13.1 从定义升级到问题建模

Absolute action 直接给目标 pose/joint；relative action 给局部增量。Relative 更具局部平移不变性且平滑，但误差会累计；absolute 可纠正累计漂移却对坐标系和标定更敏感。

跨 embodiment/scene 时常用 normalized Cartesian delta，但要明确 frame（base/tool/camera）和 delta rotation representation。

面试时建议主动定义四件事：输入是什么、输出是什么、变量属于哪个空间/时间尺度、成功由什么指标判定。这会显著减少后续追问中的歧义。

13.2 Why：这个机制为什么有效？

  1. 先找瓶颈/约束：本题的方法不是孤立技巧，而是在特定假设下消除一个明确瓶颈。
  2. 再找替代方案：至少能说出一种替代路线，并说明它在数据、计算、稳定性、实时性或泛化上的取舍。
  3. 最后落到闭环：真正机器人系统最终都会回到 感知 → 状态 → 决策 → 动作 → 控制 → 新观测；任何局部优化都要验证是否提高闭环 task metric。

一个常用的工程化表达是：

离线指标改善
   ↓（必要但不充分）
模块级接口正确
   ↓
闭环 rollout 稳定
   ↓
OOD / 长尾仍成立
   ↓
实机 SLO / 安全约束满足

13.3 白板 / 实现骨架

Robot/Sensor → timestamped raw log → validated episode
           → dataset version / provenance
           → train/eval split → policy
           → deployment telemetry → failure mining
           → next data iteration

把数据 schema、时间同步、控制频率、软件版本纳入 dataset contract。

白板必画：画 raw log→dataset→train→deploy→telemetry→failure mining 的数据闭环，标 timestamp/schema/version。

13.4 失败模式：不要只会解释“成功时为什么工作”

失败类型 典型现象 优先检查的证据
F1 episode 时间戳或 schema 不一致 最小可复现实验 + 原始时序日志
F2 数据版本不可追溯 边界条件 / OOD 分桶统计
F3 仿真高吞吐但分布错误 模块输入输出与数值范围
F4 平均 latency 合格但 jitter 破坏控制 闭环回放、视频、控制/系统 telemetry

专业回答应避免“模型效果不好”这种不可诊断描述，而是把失败拆成可观测类别，并给每一类一个证据链。

13.5 指标体系：怎样证明你的答案在工程上成立？

本题至少建议关注：dataset validation pass rate、timestamp skew、sim FPS、robot utilization、E2E latency/jitter、deployment failure rate。

评估时优先使用：

  • 均值 + 分位数/置信区间，避免只报单个平均数；
  • 按场景分桶：seen / OOD、短时 / 长时、成功 / near-miss；
  • A/B 单变量实验：一次只改一个核心变量；
  • 闭环指标优先于离线 proxy：离线 loss/accuracy 只能解释部分问题。

13.6 面试追问树：从“会答”到“扛得住追问”

  • rotation delta 怎么 compose？：先给 1 句结论；再回到本题的核心变量/公式；最后给一个可测的实机或离线证据。不要只复述名词。
  • relative action 如何防 drift？：先给 1 句结论；再回到本题的核心变量/公式；最后给一个可测的实机或离线证据。不要只复述名词。

进一步的 Senior 追问通常会变成：

  1. 如果这个方法不起作用，你如何判断是数据、模型、控制还是系统问题？
  2. 如果算力减半 / 数据减半 / 延迟预算减半，你会保留什么？
  3. 如何设计最小 ablation 证明改进来自你声称的机制，而不是额外参数量或更多数据？
  4. 这个结论在哪些 robot / task / control regime 下可能失效？

13.8 一页速记

  • 一句话本质：Absolute action 直接给目标 pose/joint；relative action 给局部增量。
  • 最容易答错：只背术语，不定义 frame / state / action / time scale / metric。
  • 工程优先级：先验证输入输出和时序，再优化模型；先建立 failure taxonomy，再增加数据/参数。
  • 面试高分信号：能给公式或结构图 + 能说替代方案 + 能给失败证据 + 能设计 A/B。

记忆锚点：先说机制，再说边界；先画闭环，再谈模型。
