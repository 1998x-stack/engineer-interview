终局题：10 台机器人、1000 GPU、6 个月，如何构建通用机器人模型？

难度：★★★★★
模块：第十篇 系统设计、项目拷打与 2026 前沿
标签：frontier / robot-foundation-model / system-design

[!NOTE] 内容边界：PDF Core 小节忠实保留 PDF 题解的术语、结构与结论；标记为 Repository Expansion 的内容是为了 GitHub 版进一步补充的标准理论、工程实践与 2026 资料。

1. 这道题在考什么？ — PDF Core

考察你是否具备研究负责人/系统负责人视角。

为什么重要 — Repository Expansion

系统设计题考察你能否把数据、模型、机器人学、评测和运维组成可迭代闭环。高分答案一定包含 baseline、失败分类、指标、实验优先级和成本约束。

这题建议始终放回具身闭环理解：Observation → State/Representation → Policy/Planner → Action → Controller → Robot → New Observation。面试官通常会从定义继续追到“如果真的上机器人，接口、误差和失败模式是什么”。

2. 30 秒回答 — PDF Core

先建 data engine 和统一评测，再做 broad multi-task/multi-robot pretraining；使用 action chunk + generative action head；随后高质量 post-training 与在线 RL；通过 failure mining 形成数据飞轮。GPU 不是第一瓶颈，机器人数据吞吐和评测可信度才是。

3. 5-10 分钟深度题解

3.1 Data：teleop、existing datasets、simulation、human video、autonomous rollout；统一 lineage/schema

Data：teleop、existing datasets、simulation、human video、autonomous rollout；统一 lineage/schema。

3.2 Model：vision-language-proprio-embodiment backbone + action expert + memory/high-level planner

Model：vision-language-proprio-embodiment backbone + action expert + memory/high-level planner。

3.3 Training：broad pretrain → task/robot adaptation → RL refinement；Evaluation：seen/OOD/compositional/cross-embodiment/long horizon/safety

Training：broad pretrain → task/robot adaptation → RL refinement；Evaluation：seen/OOD/compositional/cross-embodiment/long horizon/safety。

3.4 Operations：fleet scheduling、reset、hardware health、active data collection、canary deployment

Operations：fleet scheduling、reset、hardware health、active data collection、canary deployment。

3.X 专题增强 — Repository Expansion

  • 这类终局系统题的第一资源不是 GPU，而是 robot-hours。先估计 fleet 每天有效 episode、reset/teleop 占比和 failure coverage，再决定训练规模；没有可信 data engine 与 evaluation，1000 GPU 只会更快拟合偏差。

4. 数学 / 公式 / 结构 — PDF Core + Expansion

maximize (generalization × success × robot throughput) / (data cost + compute + human intervention)

面试白板上写出公式后，不要停在符号层。至少解释：变量属于哪个空间、维度是什么、哪个量可观测、哪个量需要估计/优化，以及公式在接近边界条件时是否稳定。

5. 白板实现应该写到什么程度？ — Repository Expansion

不要求现场实现完整工业系统，但应能写清状态表示、主要循环、关键约束和失败回退。若涉及学习算法，还要能指出训练 loop 与 rollout/evaluation loop 的区别。

6. 工程实现与系统接口 — Repository Expansion

从用户任务与 SLO 出发定义 observation/action/control 接口，再设计 data engine、policy stack、safety layer、fleet rollout、failure mining 和迭代机制。

建议关注的指标

  • 任务成功率 / 长时完成率

  • 机器人吞吐与人工干预

  • 数据小时到性能提升的边际收益

  • 训练/部署成本与安全事件

最小验证实验

  1. 先构造一个可控、可复现的最小场景作为 baseline。
  2. 只改变一个变量做 A/B；记录均值之外的失败分布。
  3. 对边界条件或 OOD 场景单独建立回归测试。
  4. 最后才进入全系统实机验证，并保留日志、视频和时序数据以便复盘。

7. 工程 Gotchas — PDF Core

  • ⚠️ 先花 1000 GPU 训练最大模型，再考虑数据。

Debug Checklist — Repository Expansion

  • [ ] 不要一上来换更大模型。

  • [ ] 先建立 failure taxonomy 与可观测性。

  • [ ] 用 canary 和回放集验证每次策略升级。

  • [ ] 检查 train / validation / deployment 的 observation、action、单位、频率和 normalization 是否完全一致。

13. 深度增强题解 — Repository Expansion v2.0

本节是 GitHub 版二次研究扩展，不替代前面的 PDF Core。目标是把“知道概念”提升到“能推导、能实现、能定位实机失败”。

13.1 从定义升级到问题建模

10 台机器人×6 个月首先受 robot-hours、reset、人类标注和评测吞吐约束，而不是 1000 GPU。第一阶段必须建立统一数据 schema、fleet telemetry、benchmark、failure taxonomy，再决定模型 scaling。

研究计划应有月度 stage-gate：data engine→strong baseline→multi-task pretrain→OOD/compositional benchmark→online correction/RL→fleet canary。每阶段定义 go/no-go 指标和 GPU/robot-hour ROI。

面试时建议主动定义四件事：输入是什么、输出是什么、变量属于哪个空间/时间尺度、成功由什么指标判定。这会显著减少后续追问中的歧义。

13.2 Why：这个机制为什么有效？

  1. 先找瓶颈/约束：本题的方法不是孤立技巧，而是在特定假设下消除一个明确瓶颈。
  2. 再找替代方案：至少能说出一种替代路线，并说明它在数据、计算、稳定性、实时性或泛化上的取舍。
  3. 最后落到闭环：真正机器人系统最终都会回到 感知 → 状态 → 决策 → 动作 → 控制 → 新观测；任何局部优化都要验证是否提高闭环 task metric。

一个常用的工程化表达是：

离线指标改善
   ↓（必要但不充分）
模块级接口正确
   ↓
闭环 rollout 稳定
   ↓
OOD / 长尾仍成立
   ↓
实机 SLO / 安全约束满足

13.3 白板 / 实现骨架

SLO / task definition
  → measurable benchmark
  → baseline
  → failure taxonomy
  → intervention + ablation
  → canary deployment
  → telemetry / rollback
  → data flywheel

系统设计题一定要出现 SLO、预算、failure recovery、迭代闭环。

白板必画：从 SLO 开始画完整架构，并在每层写 metric、failure、fallback 和预算。

13.4 失败模式：不要只会解释“成功时为什么工作”

失败类型 典型现象 优先检查的证据
F1 直接堆大模型而没有 baseline 最小可复现实验 + 原始时序日志
F2 只有 happy path 没有 recovery 边界条件 / OOD 分桶统计
F3 评测集与训练数据泄漏 模块输入输出与数值范围
F4 GPU/robot-hours/人工成本没有 ROI 约束 闭环回放、视频、控制/系统 telemetry

专业回答应避免“模型效果不好”这种不可诊断描述，而是把失败拆成可观测类别，并给每一类一个证据链。

13.5 指标体系：怎样证明你的答案在工程上成立？

本题至少建议关注：task/SLO success、p95/p99 latency、robot throughput、human intervention、Δperformance/robot-hour、compute cost、安全事件。

评估时优先使用：

  • 均值 + 分位数/置信区间，避免只报单个平均数；
  • 按场景分桶：seen / OOD、短时 / 长时、成功 / near-miss；
  • A/B 单变量实验：一次只改一个核心变量；
  • 闭环指标优先于离线 proxy：离线 loss/accuracy 只能解释部分问题。

13.6 面试追问树：从“会答”到“扛得住追问”

  • 前 2 周做什么？：先给 1 句结论；再回到本题的核心变量/公式；最后给一个可测的实机或离线证据。不要只复述名词。
  • 如何决定 robot fleet 采哪些任务？：先给 1 句结论；再回到本题的核心变量/公式；最后给一个可测的实机或离线证据。不要只复述名词。
  • 怎样证明 scaling 有效？：先给 1 句结论；再回到本题的核心变量/公式；最后给一个可测的实机或离线证据。不要只复述名词。

进一步的 Senior 追问通常会变成：

  1. 如果这个方法不起作用，你如何判断是数据、模型、控制还是系统问题？
  2. 如果算力减半 / 数据减半 / 延迟预算减半，你会保留什么？
  3. 如何设计最小 ablation 证明改进来自你声称的机制，而不是额外参数量或更多数据？
  4. 这个结论在哪些 robot / task / control regime 下可能失效？

13.7 项目化回答模板

Context
  → Robot / Task / Sensors / Control rate
Problem
  → 用一个可测失败指标定义问题
Baseline
  → 给出至少一个数字

  → 日志 / 回放 / profiling / ablation

  → 只修改关键变量

13.8 一页速记

  • 一句话本质：10 台机器人×6 个月首先受 robot-hours、reset、人类标注和评测吞吐约束，而不是 1000 GPU。
  • 最容易答错：只背术语，不定义 frame / state / action / time scale / metric。
  • 工程优先级：先验证输入输出和时序，再优化模型；先建立 failure taxonomy，再增加数据/参数。
  • 面试高分信号：能给公式或结构图 + 能说替代方案 + 能给失败证据 + 能设计 A/B。

记忆锚点：先说机制，再说边界；先画闭环，再谈模型。
