## 1. 这道题在考什么？ — PDF Core

考察旋转表示的工程权衡。

### 为什么重要 — Repository Expansion

机器人学基础题真正考的是“几何量是否定义清楚、坐标系是否一致、模型动作是否物理可执行”。好的回答会把配置空间、任务空间、约束和控制接口串成闭环，而不是停留在公式记忆。

这题建议始终放回具身闭环理解：**Observation → State/Representation → Policy/Planner → Action → Controller → Robot → New Observation**。面试官通常会从定义继续追到“如果真的上机器人，接口、误差和失败模式是什么”。

## 2. 30 秒回答 — PDF Core

> Euler 直观但有 gimbal lock；旋转矩阵稳定但冗余；Quaternion 紧凑且适合插值，但有单位范数约束和 q/-q 双覆盖。选择取决于模型学习、数值优化还是控制接口。

### 3.X 专题增强 — Repository Expansion

- 旋转误差更专业的写法是使用几何距离，例如 theta = acos((trace(R_err)-1)/2)。学习系统若直接回归旋转，需考虑表示连续性；控制系统则更常使用 axis-angle / Lie algebra 小扰动。

## 4. 数学 / 公式 / 结构 — PDF Core + Expansion

```text
q=(w,x,y,z),  ||q||=1;  q 与 -q 表示同一旋转。
```

面试白板上写出公式后，不要停在符号层。至少解释：**变量属于哪个空间、维度是什么、哪个量可观测、哪个量需要估计/优化，以及公式在接近边界条件时是否稳定**。

## 5. 白板实现应该写到什么程度？ — Repository Expansion

不要求现场实现完整工业系统，但应能写清**状态表示、主要循环、关键约束和失败回退**。若涉及学习算法，还要能指出训练 loop 与 rollout/evaluation loop 的区别。

## 6. 工程实现与系统接口 — Repository Expansion

工程实现优先明确 frame convention、单位、控制频率、关节限位和数值稳定性。常见工具包括 URDF、Pinocchio/KDL、MoveIt 2、Eigen/Numpy；任何数值结果都应配合可视化或实机几何误差验证。

### 建议关注的指标

- 末端位置误差 / 姿态误差

- Jacobian condition number / 最小奇异值

- IK 成功率与求解耗时

- 关节限位、碰撞和轨迹连续性

### 最小验证实验

1. 先构造一个可控、可复现的最小场景作为 baseline。
2. 只改变一个变量做 A/B；记录均值之外的失败分布。
3. 对边界条件或 OOD 场景单独建立回归测试。
4. 最后才进入全系统实机验证，并保留日志、视频和时序数据以便复盘。

### 13.1 从定义升级到问题建模

Euler 角最直观但有奇异点；旋转矩阵冗余但稳定；Quaternion 紧凑且适合 SLERP，不过 q 与 -q 表示同一旋转。学习问题里常用 6D continuous representation 来避免 quaternion 双覆盖和 Euler 不连续。

如果损失直接写 ||q_pred-q_gt||²，需要先处理符号等价，例如 min(||q-q*||,||q+q*||)。控制接口还要明确是 absolute orientation 还是 delta rotation。

面试时建议主动定义四件事：**输入是什么、输出是什么、变量属于哪个空间/时间尺度、成功由什么指标判定**。这会显著减少后续追问中的歧义。

### 13.2 Why：这个机制为什么有效？

1. **先找瓶颈/约束**：本题的方法不是孤立技巧，而是在特定假设下消除一个明确瓶颈。
2. **再找替代方案**：至少能说出一种替代路线，并说明它在数据、计算、稳定性、实时性或泛化上的取舍。
3. **最后落到闭环**：真正机器人系统最终都会回到 `感知 → 状态 → 决策 → 动作 → 控制 → 新观测`；任何局部优化都要验证是否提高闭环 task metric。

一个常用的工程化表达是：

```text
离线指标改善
   ↓（必要但不充分）
模块级接口正确
   ↓
闭环 rollout 稳定
   ↓
OOD / 长尾仍成立
   ↓
实机 SLO / 安全约束满足
```

### 13.3 白板 / 实现骨架

```python
# 几何/运动学类题的最小可验证骨架
q = robot.get_joint_state()
T_ee = fk(q)
J = jacobian(q)
assert np.isfinite(T_ee).all() and np.isfinite(J).all()
# 与数值差分或已知解析构型交叉验证
J_fd = finite_difference_fk(q)
check_relative_error(J, J_fd)
```
工程原则：**解析/库实现 + 数值差分 + 可视化 frame** 三重验证。

**白板必画**：画 world/base/ee 三个 frame，写出 q→T 与 J 的关系，再指出 singularity/joint-limit 约束。

### 13.4 失败模式：不要只会解释“成功时为什么工作”

| 失败类型 | 典型现象 | 优先检查的证据 |
|---|---|---|
| F1 | frame/单位定义错误 | 最小可复现实验 + 原始时序日志 |
| F2 | 接近奇异或关节限位 | 边界条件 / OOD 分桶统计 |
| F3 | 数值解与真实标定参数不一致 | 模块输入输出与数值范围 |
| F4 | 高层 action 与低层 controller 语义不一致 | 闭环回放、视频、控制/系统 telemetry |

专业回答应避免“模型效果不好”这种不可诊断描述，而是把失败拆成可观测类别，并给每一类一个证据链。

### 13.5 指标体系：怎样证明你的答案在工程上成立？

本题至少建议关注：**pose error、IK success、σ_min(J)/condition number、collision margin、control smoothness**。

评估时优先使用：

- **均值 + 分位数/置信区间**，避免只报单个平均数；
- **按场景分桶**：seen / OOD、短时 / 长时、成功 / near-miss；
- **A/B 单变量实验**：一次只改一个核心变量；
- **闭环指标优先于离线 proxy**：离线 loss/accuracy 只能解释部分问题。
