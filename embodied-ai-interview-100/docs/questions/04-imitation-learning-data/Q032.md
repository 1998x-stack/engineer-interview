## 1. 这道题在考什么？ — PDF Core

### 为什么重要 — Repository Expansion

模仿学习的核心不是把 demonstration 拟合得更低，而是让部署分布上的闭环行为可靠。数据覆盖、多模态策略、错误恢复和 operator bias 往往比网络结构更关键。

这题建议始终放回具身闭环理解：**Observation → State/Representation → Policy/Planner → Action → Controller → Robot → New Observation**。面试官通常会从定义继续追到“如果真的上机器人，接口、误差和失败模式是什么”。

## 2. 30 秒回答 — PDF Core

> 训练状态来自 expert 分布，而部署时策略自己造成的新状态逐渐偏离 expert manifold；小误差改变下一帧输入，再引发更大误差。

### 3.X 专题增强 — Repository Expansion

- BC 的闭环风险可用 covariate shift 表述：训练状态来自 expert distribution d_E，部署状态来自 d_π。单步 error 很小也会把系统推到 d_E 未覆盖的区域。真正有效的验证应做 rollout，而不只看 action MSE。

> 本节是 GitHub 版二次研究扩展，不替代前面的 PDF Core。目标是把“知道概念”提升到“能推导、能实现、能定位实机失败”。

### 13.1 从定义升级到问题建模

Compounding error 来自 covariate shift：一个小动作误差把机器人带入专家数据未覆盖的状态，随后预测误差进一步放大。有限 horizon 下误差增长可能远高于独立一步误差。

解决思路分三类：收集 on-policy correction（DAgger）、增强 recovery/failure data、使用闭环 action chunk/replanning。不能只靠增加同分布成功 demonstration。

面试时建议主动定义四件事：**输入是什么、输出是什么、变量属于哪个空间/时间尺度、成功由什么指标判定**。这会显著减少后续追问中的歧义。

### 13.2 Why：这个机制为什么有效？

1. **先找瓶颈/约束**：本题的方法不是孤立技巧，而是在特定假设下消除一个明确瓶颈。
2. **再找替代方案**：至少能说出一种替代路线，并说明它在数据、计算、稳定性、实时性或泛化上的取舍。
3. **最后落到闭环**：真正机器人系统最终都会回到 `感知 → 状态 → 决策 → 动作 → 控制 → 新观测`；任何局部优化都要验证是否提高闭环 task metric。

一个常用的工程化表达是：

```text
离线指标改善
   ↓（必要但不充分）
模块级接口正确
   ↓
闭环 rollout 稳定
   ↓
OOD / 长尾仍成立
   ↓
实机 SLO / 安全约束满足
```

```python

```
IL 的核心质量门槛是 **closed-loop success 与 failure distribution**，不是 offline MSE。

### 13.4 失败模式：不要只会解释“成功时为什么工作”

| 失败类型 | 典型现象 | 优先检查的证据 |
|---|---|---|
| F1 | offline loss 好但 rollout 崩溃 | 最小可复现实验 + 原始时序日志 |
| F2 | 多模态被平均 | 边界条件 / OOD 分桶统计 |
| F3 | 数据覆盖不足/重复度高 | 模块输入输出与数值范围 |
| F4 | operator/style/domain 泄漏造成虚假泛化 | 闭环回放、视频、控制/系统 telemetry |

专业回答应避免“模型效果不好”这种不可诊断描述，而是把失败拆成可观测类别，并给每一类一个证据链。

### 13.5 指标体系：怎样证明你的答案在工程上成立？

本题至少建议关注：**closed-loop success、recovery rate、OOD success、action NLL/MSE（仅辅助）、data coverage、robot-hour efficiency**。

评估时优先使用：

- **均值 + 分位数/置信区间**，避免只报单个平均数；
- **按场景分桶**：seen / OOD、短时 / 长时、成功 / near-miss；
- **A/B 单变量实验**：一次只改一个核心变量；
- **闭环指标优先于离线 proxy**：离线 loss/accuracy 只能解释部分问题。
