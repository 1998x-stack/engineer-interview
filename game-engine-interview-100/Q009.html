new/delete 与 malloc/free 有什么区别？为什么不能混用？

[!IMPORTANT] 内容分层：PDF 核心内容严格以仓库附带的原 PDF 为基线；专业扩展是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

章节：C++ 对象模型与语言机制
学习级别：Intermediate（仓库学习分级，不是对 PDF 星级符号的重解释）
PDF 位置：物理页 18
来源口径：公开面经/官方资料可核验 · [M2]

1. 这道题在考什么

这题属于 C++ 对象模型与语言机制。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

  1. 机制：数据/状态究竟怎样流动；
  2. 成本：CPU、GPU、内存、同步或数值误差的成本在哪里；
  3. Trade-off：什么场景适合，什么场景会失败；
  4. Engine Context：在真实 renderer / core / asset / simulation 中怎么落地；
  5. Evidence：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：对象 ABI 与插件边界、组件/资源生命周期、运行时类型系统与编辑器工具链。

2. 30 秒回答（PDF 核心内容）

malloc/free 只管理原始字节；new/delete 同时涉及对象构造/析构以及匹配的分配函数。通过 new 创建对象后使用 free，会绕过析构且分配/释放协议不匹配，属于未定义行为。

3. PDF 深入拆解（Source-derived）

C++ 的 new-expression 概念上包含“调用 operator new 获取内存 + 在该内存上构造对象”； delete-expression 先执行析构，再调用匹配的 operator delete。placement new 则只执行构造，不分配存储。引擎自定义 allocator 常重载 operator new 或完全绕开 new-expression，但仍必须维护对象生命周期与对齐。

PDF 核心抓手

  • 区分 allocation 与 object lifetime
  • 了解 placement new
  • new[] 必须匹配 delete[]
  • 自定义 allocator 仍需显式构造/析构

PDF 工程 Gotcha

把原因仅说成“会内存泄漏”。真正问题是未定义行为，包括析构未执行和 allocator metadata 被破坏。

PDF 面试官在听什么

能否区分“内存”和“对象”两个概念。

4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 可实现、可测量、可讨论 trade-off 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

4.1 先修知识与概念边界

  • 对象生命周期
  • raw storage 与 object construction
  • allocator pairing
  • placement new

4.2 核心心智模型

malloc/free 管理“原始字节存储”；new/delete 同时承担 C++ 对象生命周期。混用破坏的不只是 allocator 配对，还可能跳过构造/析构和使用错误的释放协议。

4.3 底层机制：逐层拆开

  • new T(args...) 通常先调用 operator new 获得 raw storage，再在该地址构造 T；失败时按语言规则释放。
  • delete p 先调用析构函数，再调用匹配的 operator delete；数组 new/delete[] 还涉及元素个数与逐个析构。
  • placement new 只在已有 storage 上开始对象生命周期，不分配内存；之后必须显式析构。
  • 自定义 allocator/arena 可把 storage acquisition 与 object lifetime 分离，但仍要遵守 alignment 和 lifetime rules。

4.4 必须守住的不变量 / 正确性条件

  • 分配/释放协议必须匹配：new/delete、new[]/delete[]、malloc/free、自定义 allocator pair。
  • “有一块足够大的内存”不等价于“某个 C++ 对象的生命周期已经开始”。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

4.5 Trade-off：什么时候该用，什么时候不该用

  • 引擎常用 allocator + placement new 获得可控内存布局，但复杂度上升，必须正确处理异常、alignment 与析构。
  • 跨 DLL 最好由分配方释放，避免不同 CRT/heap。

4.6 在真实游戏引擎中的落点

  • ECS chunk：一次分配大块 raw storage，再对 component column 显式构造/销毁。
  • Frame arena 中放 trivially destructible 临时对象最简单；非平凡析构对象需要 destructor list。
  • 插件 API 提供 allocator callback 或 Create/Destroy pairing。

4.7 最小实现 / 数学骨架

void* mem = arena.allocate(sizeof(Foo), alignof(Foo));
Foo* p = ::new (mem) Foo(args...); // 开始对象生命周期
p->~Foo();                         // 显式结束

面试建议：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

4.8 Profiling / Validation：如何证明你的判断

  • ASan/UBSan 能捕获部分 mismatch/free 问题；heap verifier 可定位跨模块错误释放。

4.9 常见错误答案与为什么错

  • “new 就是 malloc + 构造，所以任何时候 free(new T) 都只是少调用析构。”——属于未定义行为，allocator 也可能完全不同。
  • “placement new 后要 delete。”——storage 所有权不由 placement new 获得，应按原 storage 协议释放。

4.10 Senior 级追问与参考思路

  1. 为什么 arena 常限制元素类型？
    若允许大量非平凡析构对象，就要维护析构顺序/列表，削弱 reset=O(1) 的优势。
  2. operator new 能重载什么？
    可按类/全局定制 storage acquisition，但不能改变 new-expression 的构造语义。

4.11 推荐实战

实现一个支持 alignment 的 arena，并可选注册 destructor callback；比较只允许 trivially destructible 类型时的简化程度。

完成实战时建议保留 baseline、指标、实验变量、结果、结论 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

5. 如何验证，而不是“凭感觉优化”

  • 查看对象布局/生成汇编，确认假设是否成立
  • 对 microbenchmark 与真实 frame profile 做区分
  • 用 ASan/UBSan/TSan 等工具验证生命周期或并发错误

推荐实战

写一个最小 C++ 程序，用编译器输出/汇编验证对象布局或生命周期假设；记录优化前后差异。

6. 工程 Gotchas（扩展）

  • 不要只从 Big-O/语法推性能，必须讨论数据布局与编译器优化
