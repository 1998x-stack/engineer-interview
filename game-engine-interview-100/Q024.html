Mutex、Spinlock、Semaphore 怎么选？

[!IMPORTANT] 内容分层：PDF 核心内容严格以仓库附带的原 PDF 为基线；专业扩展是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

章节：操作系统、多线程与并发
学习级别：Intermediate（仓库学习分级，不是对 PDF 星级符号的重解释）
PDF 位置：物理页 35
来源口径：高频能力重构

1. 这道题在考什么

这题属于 操作系统、多线程与并发。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

  1. 机制：数据/状态究竟怎样流动；
  2. 成本：CPU、GPU、内存、同步或数值误差的成本在哪里；
  3. Trade-off：什么场景适合，什么场景会失败；
  4. Engine Context：在真实 renderer / core / asset / simulation 中怎么落地；
  5. Evidence：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：Job System 与 worker pool、Game/Render/RHI 线程所有权、低延迟同步与无锁消息通道。

2. 30 秒回答（PDF 核心内容）

Mutex 适合等待时间可能较长的互斥；Spinlock 适合极短临界区，因为等待线程会忙等； Semaphore 表示可用资源计数或并发配额，不等价于二元互斥。

3. PDF 深入拆解（Source-derived）

正确选择取决于等待时间、竞争概率和调度成本。Spinlock 在单核或线程可能被抢占时尤其危险；持有 spinlock 做 I/O 更是灾难。Mutex 的实现也可能先短暂自旋再睡眠。Semaphore 常用于“最多 N 个资源/工作槽”。引擎中更重要的原则是减少共享可变数据，而非精细挑锁。

PDF 核心抓手

  • 短临界区才适合 spin
  • blocking primitive 会让出 CPU
  • semaphore 表达数量
  • 优先减少锁粒度和共享写

PDF 工程 Gotcha

认为 spinlock 一定比 mutex 快。高竞争下它可能浪费整核。

PDF 面试官在听什么

是否基于 workload 做同步原语选择。

4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 可实现、可测量、可讨论 trade-off 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

4.1 先修知识与概念边界

  • 互斥
  • 忙等
  • sleep/wakeup
  • 资源计数

4.2 核心心智模型

这三者解决不同问题：Mutex 保护互斥临界区；Spinlock 用 CPU 时间换短等待延迟；Semaphore 表示可用许可数量/用于通知。选择依据是等待时长、竞争概率和线程是否允许阻塞。

4.3 底层机制：逐层拆开

  • mutex 竞争时实现可能先自旋再进入内核等待，具体策略由平台/runtime 决定。
  • spinlock 在锁被占用时循环读取，若持锁线程被抢占会极其糟糕。
  • semaphore 的计数 >0 时 acquire 消耗许可，=0 时等待；适合 producer/consumer slot、资源池容量。
  • 条件变量用于“状态条件变化”而非互斥本身，通常配 mutex 并用 while 检查 predicate。

4.4 必须守住的不变量 / 正确性条件

  • 临界区必须尽量短且不能做未知耗时 I/O/回调。
  • 自旋只有在预计等待短于 sleep/wakeup 成本且系统不 oversubscribe 时才合理。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

4.5 Trade-off：什么时候该用，什么时候不该用

  • mutex 易用、可阻塞；spinlock 低延迟但耗核心；semaphore 能表达 N 个资源但不是直接替代 mutex。
  • 读多写少可考虑 RW lock，但写饥饿和 cache coherence 也需测量。

4.6 在真实游戏引擎中的落点

  • Command queue slots 用 semaphore 控制有界容量。
  • 极短 allocator metadata 更新可使用细粒度 spin/atomic，前提是 contention 低。
  • 资源加载条件用 condition variable/event，不应 busy-wait 几十毫秒。

4.7 最小实现 / 数学骨架

预计等待 < ~几百 ns 且有空闲核心? -> 可考虑 spin
未知/可能长等待 -> mutex/event
N 个许可/生产消费 -> semaphore

面试建议：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

4.8 Profiling / Validation：如何证明你的判断

  • profile lock hold time、wait time、contention count、spin cycles。
  • 检查持锁线程是否被抢占以及 lock convoy。

4.9 常见错误答案与为什么错

  • “spinlock 比 mutex 高性能。”——竞争或 oversubscription 下可能灾难性更差。
  • “semaphore 可以保护任意临界区。”——它表达计数，不自动提供业务不变量的互斥语义。

4.10 Senior 级追问与参考思路

  1. 为什么 critical section 里不能调用用户回调？
    回调耗时/重入未知，可能形成锁顺序反转和长时间持锁。
  2. Adaptive mutex 是什么思想？
    先短暂自旋，若预计锁即将释放可避免内核睡眠，否则再阻塞。

4.11 推荐实战

构造 50ns、5us、1ms 三种临界区，对 mutex/spinlock 测 throughput、CPU usage、P99 latency。

完成实战时建议保留 baseline、指标、实验变量、结果、结论 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

5. 如何验证，而不是“凭感觉优化”

  • 在 trace 中标注 task/lock/wait，先看 critical path
  • 统计 contention、wake-up、context switch，而非只看平均 CPU
  • 并发正确性用 sanitizer/stress test 验证

推荐实战

写一个可重复的多线程小实验，并用 sanitizer/trace 验证 happens-before 与 contention。

6. 工程 Gotchas（扩展）

  • “lock-free”不等于 wait-free，更不等于一定更快
  • 并发正确性与性能要分开证明
