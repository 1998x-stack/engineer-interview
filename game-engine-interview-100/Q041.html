GAME ENGINE · GRAPHICS · 1 / 100

游戏渲染中有哪些坐标空间？

[!IMPORTANT] 内容分层：PDF 核心内容严格以仓库附带的原 PDF 为基线；专业扩展是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

章节：3D 数学与几何
学习级别：Intermediate（仓库学习分级，不是对 PDF 星级符号的重解释）
PDF 位置：物理页 54
来源口径：高频能力重构

1. 这道题在考什么

这题属于 3D 数学与几何。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

  1. 机制：数据/状态究竟怎样流动；
  2. 成本：CPU、GPU、内存、同步或数值误差的成本在哪里；
  3. Trade-off：什么场景适合，什么场景会失败；
  4. Engine Context：在真实 renderer / core / asset / simulation 中怎么落地；
  5. Evidence：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：camera/view/projection、碰撞与 picking、raster attribute interpolation。

2. 30 秒回答（PDF 核心内容）

典型链路是 Local/Model → World → View → Clip → NDC → Screen。列向量约定下常写 p_clip = P V M p_local；具体乘法顺序必须与数学 convention 一致。

3. PDF 深入拆解（Source-derived）

World 负责对象定位，View 把世界转换到相机坐标，Projection 把视锥映射到 clip space；之后做 clipping 与 perspective divide 得 NDC，再 viewport map 到屏幕。高级回答应明确 clip space 中 w 的作用、NDC z 范围在不同 API 的差异，以及 row-major/column-major memory layout 与数学上的 row/column vector 并非同一个概念。

PDF 核心抓手

  • 明确各空间职责
  • clip 发生在 perspective divide 之前
  • API 的 NDC depth range 可能不同
  • 矩阵存储布局与向量约定要分开

PDF 工程 Gotcha

背“模型-世界-观察-裁剪”但无法从一个点手推转换。

PDF 面试官在听什么

能否把矩阵、API convention 和实际 shader 串起来。

4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 可实现、可测量、可讨论 trade-off 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

4.1 先修知识与概念边界

  • 矩阵变换
  • 局部/世界坐标
  • 相机模型
  • Clip/NDC/Viewport

4.2 核心心智模型

坐标空间不是背名词，而是为了把不同计算放在最合适的参考系。面试要能画出数据从 Model→World→View→Clip→NDC→Screen 的完整链，并说明每一步哪些量适合在哪个空间计算。

4.3 底层机制：逐层拆开

  • Model/Local space 描述资源自身坐标，Model matrix 将其放入 World space。
  • View matrix 本质上是相机 world transform 的逆，把世界变成“以相机为原点”的 View space。
  • Projection 把 view frustum 映射到 Clip space；随后进行 homogeneous clipping 和 perspective divide 得到 NDC。
  • Viewport transform 再把 NDC 映射到 framebuffer/window 坐标；不同 API 的 NDC z 范围、Y 方向约定可能不同。

4.4 必须守住的不变量 / 正确性条件

  • 必须先确认向量是 row/column vector、矩阵乘法顺序和 handedness。
  • Clip space 仍是齐次坐标，不能在 divide w 前把它当 NDC。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

4.5 Trade-off：什么时候该用，什么时候不该用

  • World-space 统一直观但大世界浮点精度差；camera-relative/render-relative 坐标可减误差。
  • View-space lighting 易统一相机相关计算，world-space 更方便共享场景数据。

4.6 在真实游戏引擎中的落点

  • World origin rebasing / camera-relative rendering。
  • CPU culling 与 GPU shader 必须使用一致矩阵/clip convention。
  • Shadow map 额外有 Light View/Projection space。

4.7 最小实现 / 数学骨架

p_{clip}=P\,V\,M\,p_{local},\qquad p_{ndc}=p_{clip}/w

面试建议：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

4.8 Profiling / Validation：如何证明你的判断

  • 用 debug axis/grid 可视化每个空间；在 RenderDoc 检查 VS 输出与 NDC。
  • 单元测试变换 round-trip 与 handedness，避免镜像/深度方向错误。

4.9 常见错误答案与为什么错

  • “NDC 就是 screen space。”——NDC 仍是规范化坐标，之后才 viewport。
  • “View matrix 就是相机 transform。”——通常是相机 world transform 的逆。

4.10 Senior 级追问与参考思路

  1. 为什么大世界常用 camera-relative？
    float 在大数附近绝对精度变差；减去相机原点后把渲染坐标保持在较小量级。
  2. DX/Vulkan/OpenGL clip convention 差异？
    NDC z 范围、Y 方向/viewport convention 等不同，需要 RHI 层统一或 shader 宏适配。

4.11 推荐实战

写一个 CPU 变换测试，把同一点依次输出 local/world/view/clip/NDC/screen，并对 Vulkan/D3D/OpenGL convention 做对照。

完成实战时建议保留 baseline、指标、实验变量、结果、结论 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

5. 如何验证，而不是“凭感觉优化”

  • 用已知几何构造单元测试：单位矩阵、极端角度、退化三角形
  • 显式固定坐标系 convention 并在 debug draw 中可视化
  • 检查浮点 epsilon、归一化与数值稳定性

推荐实战

用 Python/C++ 写数值单元测试，并做 debug draw 可视化几何结果。

6. 工程 Gotchas（扩展）

  • 先声明坐标系与矩阵 convention，否则公式可能“都对但互相矛盾”
  • 对退化/近平行/极小角度等数值边界要有处理策略

  4. 主动补 1 个 Gotcha / 失败条件；
