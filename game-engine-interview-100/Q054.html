GAME ENGINE · GRAPHICS · 54 / 100

什么是 Early-Z？它为什么能加速？

[!IMPORTANT] 内容分层：PDF 核心内容严格以仓库附带的原 PDF 为基线；专业扩展是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

章节：实时渲染管线
学习级别：Advanced（仓库学习分级，不是对 PDF 星级符号的重解释）
PDF 位置：物理页 68
来源口径：公开面经/官方资料可核验 · [M2], [M4], [M6]

1. 这道题在考什么

这题属于 实时渲染管线。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

  1. 机制：数据/状态究竟怎样流动；
  2. 成本：CPU、GPU、内存、同步或数值误差的成本在哪里；
  3. Trade-off：什么场景适合，什么场景会失败；
  4. Engine Context：在真实 renderer / core / asset / simulation 中怎么落地；
  5. Evidence：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：base pass / depth / lighting、GPU overdraw 与 bandwidth、draw submission / visibility。

2. 30 秒回答（PDF 核心内容）

在昂贵 fragment shading 之前先做深度测试，若 fragment 必然被更近几何遮挡，就直接拒绝， 从而避免无效 pixel shader 工作。

3. PDF 深入拆解（Source-derived）

Early-Z 是概念，不应假设硬件严格按一个固定阶段实现。GPU 可能维护 hierarchical depth， 在 primitive 或 tile 级提前 reject。收益取决于 overdraw 和 fragment cost；前向渲染常通过 front-to-back 排序提高已有深度的有效性。若 shader 有影响深度/可见性的副作用，硬件必须保守处理。

PDF 核心抓手

  • 目标是避免无效 fragment work
  • Hi-Z 可在更粗粒度拒绝
  • front-to-back 增强 early reject
  • 实际实现由 GPU 决定

PDF 工程 Gotcha

说“Early-Z 在 fragment shader 前固定有一个阶段”，过度简化硬件。

PDF 面试官在听什么

是否从可见性与成本理解深度优化。

4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 可实现、可测量、可讨论 trade-off 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

4.1 先修知识与概念边界

  • depth buffer
  • opaque rendering
  • depth test
  • overdraw

4.2 核心心智模型

Early-Z 的本质是“在执行昂贵 pixel shader 前，用已有深度证明该 fragment 不可能贡献最终颜色”。收益取决于深度可用性、遮挡程度和 shader 成本。

4.3 底层机制：逐层拆开

  • Raster 后产生 depth；若硬件能确定 shader 不会改变深度/产生影响最终可见副作用，可提前比较 depth buffer。
  • 被遮挡 fragment 在 early test 失败后不执行或不完成昂贵 shading。
  • Hierarchical-Z 可在 tile/primitive 粗粒度提前拒绝大量 samples。
  • Depth prepass 先只写 depth，为后续 heavy GBuffer/forward pass 提供高质量 early-z，但自身也有 draw/vertex/bandwidth 成本。

4.4 必须守住的不变量 / 正确性条件

  • Early depth correctness 依赖 shader side effects/depth semantics。
  • Z ordering 影响遮挡发现时间；front-to-back opaque 常有利。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

4.5 Trade-off：什么时候该用，什么时候不该用

  • Depth prepass 在重 pixel/高 overdraw 场景收益大；简单 shader/几何重场景可能得不偿失。
  • 移动 TBDR 架构的 hidden surface removal/tiling 使优化策略不同。

4.6 在真实游戏引擎中的落点

  • Opaque pass front-to-back sort。
  • Depth-only prepass + GBuffer。
  • Occlusion/Hi-Z pyramid build。

4.7 最小实现 / 数学骨架

Raster -> Early Depth? -> (fail: kill) -> Pixel Shader -> Late tests/output

面试建议：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

4.8 Profiling / Validation：如何证明你的判断

  • 比较 PS invocations、early-z kill rate、depth prepass ms、GBuffer ms。
  • 做开关实验，不凭经验默认 always prepass。

4.9 常见错误答案与为什么错

  • “Early-Z 就是先渲染一遍深度。”——early test 与显式 depth prepass 是不同概念。
  • “有 depth buffer 就一定 early-z。”——shader/状态可能限制。

4.10 Senior 级追问与参考思路

  1. 为什么 front-to-back 有帮助？
    早写入近深度后，后续远表面更容易 early reject。
  2. 什么时候 depth prepass 反而变慢？
    geometry/vertex bound、overdraw低、pixel shader便宜，额外 pass和depth bandwidth超过节省。

4.11 推荐实战

为场景加可切换 depth prepass，分别在 foliage/室内/低多边形场景测 PS invocations 与 GPU ms。

完成实战时建议保留 baseline、指标、实验变量、结果、结论 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

5. 如何验证，而不是“凭感觉优化”

  • 用 RenderDoc/Nsight/RGP 检查 pass、draw、overdraw 与 shader cost
  • 用 GPU timestamp 分离 geometry/pixel/bandwidth bottleneck
  • 修改一项渲染策略后比较同场景同相机基线

推荐实战

在高 overdraw 场景对比 depth prepass on/off，记录 fragment invocation 与 GPU time。

6. 工程 Gotchas（扩展）

  • 不要把 API 语义顺序等同于硬件严格串行顺序
  • 只看 draw call 数量无法证明 GPU 更快，bandwidth/overdraw/shader 可能才是瓶颈
