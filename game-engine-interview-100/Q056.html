Hi-Z / Hierarchical Z 是什么？

[!IMPORTANT] 内容分层：PDF 核心内容严格以仓库附带的原 PDF 为基线；专业扩展是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

章节：实时渲染管线
学习级别：Advanced（仓库学习分级，不是对 PDF 星级符号的重解释）
PDF 位置：物理页 70
来源口径：公开面经/官方资料可核验 · [M2]

1. 这道题在考什么

这题属于 实时渲染管线。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

  1. 机制：数据/状态究竟怎样流动；
  2. 成本：CPU、GPU、内存、同步或数值误差的成本在哪里；
  3. Trade-off：什么场景适合，什么场景会失败；
  4. Engine Context：在真实 renderer / core / asset / simulation 中怎么落地；
  5. Evidence：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：base pass / depth / lighting、GPU overdraw 与 bandwidth、draw submission / visibility。

2. 30 秒回答（PDF 核心内容）

把深度缓冲构成层次化的 min/max 表示，让 GPU 或 compute culling 在粗粒度先判断一块区域是否完全被遮挡，避免逐像素/逐三角形测试。

3. PDF 深入拆解（Source-derived）

用于 occlusion culling 时，先把对象 AABB 投影到屏幕，选合适 mip 的 Hi-Z 深度做保守比较； 如果整个对象的最近深度仍在已有遮挡之后，就可以剔除。Reverse-Z 时层次聚合规则要相应变化。Hi-Z 也用于 SSR、ray marching 和 software occlusion。关键是保守：宁可多画，不能错误剔除可见对象。

PDF 核心抓手

  • 深度金字塔
  • 粗粒度保守拒绝
  • 选择 mip 与屏幕包围范围相关
  • Reverse-Z 改变 min/max 语义

PDF 工程 Gotcha

用单个中心采样判定整个对象遮挡，可能产生错误剔除。

PDF 面试官在听什么

是否理解“层次保守测试”的工程原则。

4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 可实现、可测量、可讨论 trade-off 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

4.1 先修知识与概念边界

  • depth pyramid
  • min/max reduction
  • occlusion culling
  • reverse-Z

4.2 核心心智模型

Hi-Z 是深度的多分辨率保守摘要。每层把更细层 block 聚合成一个能安全判断遮挡的 min/max 深度，使大物体/区域可用少量样本快速判定。选择 min 还是 max 取决于 depth convention（normal/reverse Z）和比较方式。

4.3 底层机制：逐层拆开

  • 从 depth buffer 构建 mip pyramid，每级 2×2/更多 reduction。
  • Occlusion test 将 object screen-space rect 选适当 mip，使 rect 覆盖少量 texel，再比较物体最近/最远深度与 pyramid。
  • 必须使用 conservative reduction：保证若判定 occluded 就绝不会误删可见对象。
  • Hi-Z 还用于 SSR/ray marching，通过粗层快速跳过空区再 refine。

4.4 必须守住的不变量 / 正确性条件

  • 正常 Z/reverse-Z 的“近/远”数值方向不同，reduction operator 必须对应。
  • Occlusion culling 允许 false visible，不允许 false occluded。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

4.5 Trade-off：什么时候该用，什么时候不该用

  • 构建 pyramid 有 compute/bandwidth 成本；如果场景简单或对象少收益有限。
  • 使用上一帧 Hi-Z 避免同帧依赖，但相机快速移动会产生 temporal conservatism/错误风险，需要扩大 bounds。

4.6 在真实游戏引擎中的落点

  • GPU-driven object/meshlet occlusion。
  • SSR/SSGI hierarchical ray marching。
  • Software occlusion buffer 的类似层级。

4.7 最小实现 / 数学骨架

Depth L0 -> reduce -> L1 -> L2 -> ...
Object screen rect -> choose mip -> conservative depth compare

面试建议：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

4.8 Profiling / Validation：如何证明你的判断

  • 统计 Hi-Z build ms、occlusion queries、culled objects、false visible ratio。
  • 高速相机 stress test 检查 pop-in。

4.9 常见错误答案与为什么错

  • “Hi-Z 就是 depth texture 自动 mipmap。”——普通平均 mip 不满足保守遮挡要求。
  • “永远取 min。”——取决于深度 convention。

4.10 Senior 级追问与参考思路

  1. 如何选 mip level？
    根据 object screen-space bounding rect 尺寸选择 texel footprint，使查询覆盖少量 texel且保持保守。
  2. 上一帧 Hi-Z 如何防漏？
    使用 previous transform/velocity 扩张 bounds、camera reprojection 或先允许一帧可见，宁可 false positive。

4.11 推荐实战

实现 CPU/GPU Hi-Z occlusion demo，支持 reverse-Z 并统计不同 mip 选择策略的误判与成本。

完成实战时建议保留 baseline、指标、实验变量、结果、结论 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

5. 如何验证，而不是“凭感觉优化”

  • 用 RenderDoc/Nsight/RGP 检查 pass、draw、overdraw 与 shader cost
  • 用 GPU timestamp 分离 geometry/pixel/bandwidth bottleneck
  • 修改一项渲染策略后比较同场景同相机基线

推荐实战

在一个最小 renderer 中实现或切换该技术，用 GPU timestamp + frame capture 对比。

6. 工程 Gotchas（扩展）

  • 不要把 API 语义顺序等同于硬件严格串行顺序
  • 只看 draw call 数量无法证明 GPU 更快，bandwidth/overdraw/shader 可能才是瓶颈

7. 高频追问树

  1. 如何处理上一帧 Hi-Z 的 temporal occlusion？
    先给结论，再说明机制、一个边界条件，以及在引擎中的实际后果；必要时用上方 Senior 级参考思路展开。
  2. occlusion culling 的 false negative 为什么危险？
    先给结论，再说明机制、一个边界条件，以及在引擎中的实际后果；必要时用上方 Senior 级参考思路展开。
