GAME ENGINE · GRAPHICS · 71 / 100

如果从零设计游戏引擎，最核心模块有哪些？

[!IMPORTANT] 内容分层：PDF 核心内容严格以仓库附带的原 PDF 为基线；专业扩展是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

章节：引擎架构与资源系统
学习级别：Advanced（仓库学习分级，不是对 PDF 星级符号的重解释）
PDF 位置：物理页 87
来源口径：公开面经/官方资料可核验 · [M1], [O1]

1. 这道题在考什么

这题属于 引擎架构与资源系统。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

  1. 机制：数据/状态究竟怎样流动；
  2. 成本：CPU、GPU、内存、同步或数值误差的成本在哪里；
  3. Trade-off：什么场景适合，什么场景会失败；
  4. Engine Context：在真实 renderer / core / asset / simulation 中怎么落地；
  5. Evidence：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：runtime/editor 数据边界、asset cook/streaming、render scheduling 与跨平台后端。

2. 30 秒回答（PDF 核心内容）

至少需要 Platform/Core、Memory/Jobs、Filesystem/Asset、Reflection/Serialization、 World/Scene、Rendering/RHI、Physics、Animation、Audio/Input、Scripting、Editor/Profiler 等，但真正关键是依赖方向和生命周期。

3. PDF 深入拆解（Source-derived）

“列模块”只是入门。系统设计要回答：谁依赖谁？哪些模块可离线？runtime 是否必须知道 editor？ 跨平台层在哪里？资源 ID 与文件路径如何解耦？线程所有权如何划分？常见原则是底层 core 不依赖高层 gameplay，RHI 不感知具体游戏对象，Editor 通过反射/命令接口操作 runtime 数据。模块边界决定后续能否热重载、测试和跨平台。

PDF 核心抓手

  • 先定义 dependency direction
  • offline pipeline 与 runtime 解耦
  • 平台抽象在底层
  • Profiler 是核心基础设施而非附加功能

PDF 工程 Gotcha

画一个“所有模块互相调用”的大图，没有依赖规则。

PDF 面试官在听什么

是否具备架构边界意识，而不是功能清单思维。

4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 可实现、可测量、可讨论 trade-off 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

4.1 先修知识与概念边界

  • 模块化
  • platform abstraction
  • asset/runtime/editor separation
  • dependency graph

4.2 核心心智模型

“从零设计引擎”不是模块枚举题，而是边界设计题：谁拥有数据、模块依赖方向、运行时与工具链如何分离、如何观测和演进。优秀回答会先给 core/platform，再讲资源/世界/渲染/模拟，最后讲 editor/build/profiler。

4.3 底层机制：逐层拆开

  • Core/Platform 层提供 allocator、containers、thread/job、filesystem、logging、time、platform window/input 等最小基础。
  • Asset pipeline 负责 import/cook/version/streaming；runtime 不应理解 FBX/PSD 等源格式。
  • World/Scene/ECS/Reflection/Serialization 组织运行时数据与编辑器可见类型。
  • Renderer/Physics/Animation/Audio/Network 等大系统通过明确接口依赖 core/world，而不是相互任意调用。

4.4 必须守住的不变量 / 正确性条件

  • 依赖图应尽量单向，底层模块不能回调/包含上层 gameplay 细节。
  • 运行时格式、编辑器 authoring data 和 source asset 是不同层。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

4.5 Trade-off：什么时候该用，什么时候不该用

  • 高度抽象提高可移植性但可能遮蔽平台特性。
  • 统一 mega-engine 易共享基础设施但 build time/耦合大；模块化 plugin 化复杂但可演进。

4.6 在真实游戏引擎中的落点

  • Platform→Core→Asset/World→Rendering/Simulation→Gameplay/Editor。
  • Profiler/telemetry 横切所有系统，但不应形成业务依赖环。
  • Build/cook tools 可共享 serialization/type metadata，但运行在独立 tool process。

4.7 最小实现 / 数学骨架

Platform/Core
  ├─ Asset/IO
  ├─ World/Reflection
  ├─ Job/Memory
  └─ RHI
       ↓
 Renderer / Physics / Animation / Audio / Network
       ↓
 Gameplay & Editor authoring

面试建议：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

4.8 Profiling / Validation：如何证明你的判断

  • 模块 compile dependency、binary size、startup time、跨模块 calls、runtime memory budgets。
  • 架构评审用 dependency graph 查 cycle。

4.9 常见错误答案与为什么错

  • “列出 Renderer/Physics/Audio 就答完。”——没有 ownership、数据流和依赖方向。
  • “所有系统都通过全局 ServiceLocator 访问。”——方便但隐藏依赖、难测试并产生初始化顺序问题。

4.10 Senior 级追问与参考思路

  1. 哪个模块最先设计？
    通常 core platform/data/lifetime 约束先定，但应从目标游戏/平台需求反推，不是造全能引擎。
  2. 如何支持 headless server？
    渲染/音频等必须可裁剪，game/world/core 不依赖具体 GPU/window。

4.11 推荐实战

画一张 15 模块 dependency DAG，并解释为什么每条边方向合理；禁止任何环。

完成实战时建议保留 baseline、指标、实验变量、结果、结论 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

5. 如何验证，而不是“凭感觉优化”

  • 画清 module/resource ownership graph 与线程边界
  • 给 asset/build/streaming 记录版本、依赖和 telemetry
  • 用 failure injection 测试资源缺失、热重载、设备丢失等路径

推荐实战

画模块/资源/线程依赖图，再写一个最小接口原型说明 ownership 与失败路径。

6. 工程 Gotchas（扩展）

  • 抽象层不能以丢失关键平台能力为代价
  • 资源 identity、ownership、versioning 是长期维护成本中心

7. 高频追问树

  1. 谁拥有 World？
    先给结论，再说明机制、一个边界条件，以及在引擎中的实际后果；必要时用上方 Senior 级参考思路展开。
  2. Renderer 是否能直接访问 Entity？
    先给结论，再说明机制、一个边界条件，以及在引擎中的实际后果；必要时用上方 Senior 级参考思路展开。
  3. 如何做 plugin/module hot reload？
    先给结论，再说明机制、一个边界条件，以及在引擎中的实际后果；必要时用上方 Senior 级参考思路展开。

8. 面试评分 Rubric

层级 面试表现
0 - 记忆点 只能给出一个术语或结论，无法解释原因。
1 - 原理 能解释核心机制与至少一个关键不变量。
2 - 工程 能讨论 trade-off、边界条件，并把它落到真实引擎模块。
3 - Senior signal 能给出可测量的成本模型、profiling/验证方法和替代方案。

2 分钟回答组织法

  1. 用 PDF 的“30 秒回答”先给结论；
  2. 选择 2 个机制点 展开，不要一次倾倒全部知识；
  3. 给出 1 个真实引擎场景；
  4. 主动补 1 个 Gotcha / 失败条件；
  5. 用 1 个 profiler / test / counter 收尾，说明如何验证。
