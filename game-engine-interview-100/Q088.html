GAME ENGINE · GRAPHICS · 88 / 100

NavMesh 为什么比规则 Grid 更适合 3D 游戏角色？

[!IMPORTANT] 内容分层：PDF 核心内容严格以仓库附带的原 PDF 为基线；专业扩展是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

章节：动画、物理、AI 与网络
学习级别：Intermediate（仓库学习分级，不是对 PDF 星级符号的重解释）
PDF 位置：物理页 105
来源口径：高频能力重构

1. 这道题在考什么

这题属于 动画、物理、AI 与网络。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

  1. 机制：数据/状态究竟怎样流动；
  2. 成本：CPU、GPU、内存、同步或数值误差的成本在哪里；
  3. Trade-off：什么场景适合，什么场景会失败；
  4. Engine Context：在真实 renderer / core / asset / simulation 中怎么落地；
  5. Evidence：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：character animation、physics simulation、network latency hiding / determinism。

2. 30 秒回答（PDF 核心内容）

NavMesh 用凸多边形覆盖可行走连续区域，节点更少、路径不受栅格方向限制；A* 在 polygon adjacency 上搜索，再用 funnel algorithm 穿过 portal 得到直线路径。

3. PDF 深入拆解（Source-derived）

NavMesh 还天然编码角色可通行区域，可在 bake 时考虑 slope、step height、clearance。缺点是动态世界更新复杂、不同角色半径可能需要多套数据或 runtime query。开放世界会把 navmesh 分 tile 流式加载，动态 obstacle 用局部 carve 或 avoidance，而不一定重烘全局。

PDF 核心抓手

  • polygon graph 降节点数量
  • funnel 做路径拉直
  • bake 可加入角色几何约束
  • tile 化适合 streaming

PDF 工程 Gotcha

认为 NavMesh 直接存“最终路径”，实际上它是可通行空间表示。

PDF 面试官在听什么

是否理解导航从表示到查询的完整系统。

4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 可实现、可测量、可讨论 trade-off 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

4.1 先修知识与概念边界

  • walkable surface
  • polygon graph
  • A*
  • funnel

4.2 核心心智模型

NavMesh 直接表示“角色可行走的连续自由空间”，用较大凸多边形压缩大量 grid cells。寻路先在 polygon adjacency 上 A* 找 corridor，再用 funnel/string pulling 得到几何上更直的路径。

4.3 底层机制：逐层拆开

  • 从场景几何按 agent radius/slope/step 生成 walkable regions，再 polygonize 成 convex nav polygons。
  • 每 polygon 是图节点，共享 portal edge 形成 adjacency。
  • A* 找 polygon corridor，而不是每几十厘米一个 grid node。
  • Funnel 在 portal 序列中维护 left/right cone，生成最短-ish piecewise line path。

4.4 必须守住的不变量 / 正确性条件

  • NavMesh 是针对特定 agent 尺寸/移动能力生成或参数化的。
  • 动态障碍不必总重建整 mesh，可局部 carving/avoidance。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

4.5 Trade-off：什么时候该用，什么时候不该用

  • NavMesh 节点少、路径自然；规则 grid 更容易表达任意离散 cost/破坏地形。
  • 复杂3D多层地形需要 off-mesh links、tiles 和高度处理。

4.6 在真实游戏引擎中的落点

  • Humanoid navigation。
  • Jump/ladder/elevator off-mesh links。
  • Open-world tiled navmesh streaming。

4.7 最小实现 / 数学骨架

Geometry -> Walkable spans -> Regions -> Convex NavPolys
A*: polygon corridor -> Funnel: world-space corners -> Steering

面试建议：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

4.8 Profiling / Validation：如何证明你的判断

  • navmesh tile build time、poly count、A* expanded polys、path length、replan count。
  • agent radius边界与窄门 stress test。

4.9 常见错误答案与为什么错

  • “NavMesh 本身会自动避开移动角色。”——动态局部避障是另一层。
  • “Funnel 就是平滑曲线。”——它在 portal corridor 上做 string pulling/拐点选择。

4.10 Senior 级追问与参考思路

  1. 不同体型 agent 怎么做？
    多套 navmesh、clearance metadata 或基于最大/最小半径的可通行性；取决于角色种类。
  2. NavMesh tile streaming 如何跨tile寻路？
    tile portal/高层图保持连接，未加载远端可用 coarse world graph。

4.11 推荐实战

实现简单凸 polygon corridor + funnel，和直接连接 polygon centers 比较路径长度。

完成实战时建议保留 baseline、指标、实验变量、结果、结论 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

5. 如何验证，而不是“凭感觉优化”

  • 固定随机种子/输入录制，保证问题可复现
  • 区分 simulation state 与 render interpolation state
  • 记录 latency、correction magnitude、contact/joint error 等领域指标

推荐实战

构造可重复 simulation/network demo，记录 state error、latency 或 contact/joint metrics。
