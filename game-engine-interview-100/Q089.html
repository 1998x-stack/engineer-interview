Client Prediction 为什么需要 Server Reconciliation？

[!IMPORTANT] 内容分层：PDF 核心内容严格以仓库附带的原 PDF 为基线；专业扩展是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

章节：动画、物理、AI 与网络
学习级别：Advanced（仓库学习分级，不是对 PDF 星级符号的重解释）
PDF 位置：物理页 106
来源口径：高频能力重构

1. 这道题在考什么

这题属于 动画、物理、AI 与网络。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

  1. 机制：数据/状态究竟怎样流动；
  2. 成本：CPU、GPU、内存、同步或数值误差的成本在哪里；
  3. Trade-off：什么场景适合，什么场景会失败；
  4. Engine Context：在真实 renderer / core / asset / simulation 中怎么落地；
  5. Evidence：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：character animation、physics simulation、network latency hiding / determinism。

2. 30 秒回答（PDF 核心内容）

客户端为了手感立即模拟本地输入，但服务器保持权威状态；服务器状态返回后，客户端若发现偏差，需要回滚到确认状态并重放尚未确认的输入。

3. PDF 深入拆解（Source-derived）

客户端为每个 input 带 sequence number，保存预测历史。Server ack 某序号并返回 authoritative state；客户端丢弃已确认输入，把状态校正后 replay remaining inputs。视觉上常用 smoothing 避免瞬移。预测必须与服务器规则足够一致，否则会频繁纠正。作弊防护也要求客户端不能直接声明最终位置。

PDF 核心抓手

  • 低延迟与权威性并存
  • 输入序号/历史缓存
  • rewind + replay
  • 视觉平滑与逻辑状态分离

PDF 工程 Gotcha

只做“收到服务器位置就 lerp”，没有解决未来输入的状态连续性。

PDF 面试官在听什么

是否理解实时网络的时序问题。

4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 可实现、可测量、可讨论 trade-off 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

4.1 先修知识与概念边界

  • authoritative server
  • RTT
  • input sequence
  • rollback/replay

4.2 核心心智模型

Client Prediction 用本地立即执行输入隐藏网络延迟；Server Reconciliation 用权威服务器状态纠正预测误差，并重放服务器尚未确认的输入。关键是序列号、可重放模拟和视觉平滑。

4.3 底层机制：逐层拆开

  • client 每个 input 带 sequence/tick，本地 simulate 并保存 pending input history。
  • server 按 tick 处理输入并返回 authoritative state + last processed input seq。
  • client 收到后把状态回滚到 server state，删除已确认 inputs，重新 replay 余下 pending inputs。
  • 直接 snap 会视觉跳变，可把 simulation correction 与 render smoothing 分离。

4.4 必须守住的不变量 / 正确性条件

  • 权威 state 最终必须以 server 为准。
  • prediction simulation 要足够接近 server，同一输入/初始状态应产生可控差异。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

4.5 Trade-off：什么时候该用，什么时候不该用

  • 预测越激进响应越快，但误差/纠正更明显。
  • 完整 rollback 成本随 history/实体数上升，可只预测本地 player 或关键对象。

4.6 在真实游戏引擎中的落点

  • FPS player movement。
  • Vehicle prediction。
  • Ability activation 的 local responsiveness + server validation。

4.7 最小实现 / 数学骨架

Input#42 -> local simulate -> save
Server ack state at #40
Client: set state40 -> replay #41,#42 -> render smooth correction

面试建议：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

4.8 Profiling / Validation：如何证明你的判断

  • prediction error distribution、reconciliation count/magnitude、RTT/jitter、history length。
  • 模拟50-200ms latency + packet loss。

4.9 常见错误答案与为什么错

  • “客户端预测后服务器只要偶尔同步位置。”——没有 input ack/replay 会持续漂移。
  • “Reconciliation 就是 lerp 到服务器位置。”——纯视觉 lerp 不修 simulation state/history。

4.10 Senior 级追问与参考思路

  1. 碰撞世界不同步怎么办？
    server authoritative collision snapshot/version；client用近似预测，遇动态物体可能需要 rollback/特殊容错。
  2. 如何防作弊？
    server验证 input rate、速度、碰撞/能力规则；客户端预测不赋予权威。

4.11 推荐实战

做2D movement 网络模拟器，加入100ms RTT/5% loss，实现 sequence、prediction、replay、visual smoothing。

完成实战时建议保留 baseline、指标、实验变量、结果、结论 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

5. 如何验证，而不是“凭感觉优化”

  • 固定随机种子/输入录制，保证问题可复现
  • 区分 simulation state 与 render interpolation state
  • 记录 latency、correction magnitude、contact/joint error 等领域指标

推荐实战

构造可重复 simulation/network demo，记录 state error、latency 或 contact/joint metrics。

6. 工程 Gotchas（扩展）

  • 视觉平滑不能改变 authoritative simulation state
  • 网络与物理问题必须显式考虑时间与确定性
