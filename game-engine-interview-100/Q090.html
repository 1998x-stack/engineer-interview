GAME ENGINE · GRAPHICS · 90 / 100

Lockstep 和 State Replication 如何选择？

[!IMPORTANT] 内容分层：PDF 核心内容严格以仓库附带的原 PDF 为基线；专业扩展是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

章节：动画、物理、AI 与网络
学习级别：Advanced（仓库学习分级，不是对 PDF 星级符号的重解释）
PDF 位置：物理页 107
来源口径：高频能力重构

1. 这道题在考什么

这题属于 动画、物理、AI 与网络。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

  1. 机制：数据/状态究竟怎样流动；
  2. 成本：CPU、GPU、内存、同步或数值误差的成本在哪里；
  3. Trade-off：什么场景适合，什么场景会失败；
  4. Engine Context：在真实 renderer / core / asset / simulation 中怎么落地；
  5. Evidence：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：character animation、physics simulation、network latency hiding / determinism。

2. 30 秒回答（PDF 核心内容）

Lockstep 主要同步输入， 各端做相同确定性模拟， 带宽低但要求强 determinism； State Replication 由服务器模拟并同步状态，更通用但带宽更高。

3. PDF 深入拆解（Source-derived）

RTS 常能容忍输入延迟并拥有大量单位，因此 lockstep 很合适；FPS/动作游戏需要服务器权威和局部预测，更偏 snapshot/state replication。State replication 还会做 delta compression、 interest management、snapshot interpolation。Lockstep 若任一客户端慢会拖累整体，并对浮点/随机数/执行顺序高度敏感。

PDF 核心抓手

  • Lockstep 省状态带宽但要求确定性
  • Replication 适合服务器权威
  • interest management 是扩展关键
  • 选择取决于玩法与延迟模型

PDF 工程 Gotcha

把“P2P=Lockstep，Client-Server=Replication”当绝对绑定。

PDF 面试官在听什么

是否从游戏类型和网络约束选择同步模型。

4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 可实现、可测量、可讨论 trade-off 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

4.1 先修知识与概念边界

  • deterministic simulation
  • input replication
  • snapshot replication
  • bandwidth/latency

4.2 核心心智模型

Lockstep 复制“输入”并要求所有节点得到相同模拟结果；State Replication 由权威服务器模拟并复制状态/增量。选择依据是实体规模、determinism、带宽、作弊模型和交互实时性。

4.3 底层机制：逐层拆开

  • Lockstep 每 tick 等/收集各玩家命令，再所有 peer/server 同步模拟；带宽小但对延迟/确定性敏感。
  • RTS 可用 delayed lockstep：输入延迟若干 ticks，等待所有命令后推进。
  • State replication 周期发送 entity snapshots/deltas，客户端 interpolation/extrapolation；不要求完全相同 physics。
  • 现代动作游戏常混合：server authoritative state + client prediction，某些确定性子系统可 rollback。

4.4 必须守住的不变量 / 正确性条件

  • Lockstep 的 simulation 必须对所有参与者 deterministic，包括随机数、浮点、迭代顺序。
  • State replication 需要 interest management，否则世界大时带宽爆炸。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

4.5 Trade-off：什么时候该用，什么时候不该用

  • Lockstep 带宽低但延迟由最慢参与者/输入窗口限制。
  • State replication 容忍非确定性但带宽和 server CPU 高。

4.6 在真实游戏引擎中的落点

  • RTS lockstep。
  • FPS authoritative replication。
  • Rollback fighting game：输入同步+本地回滚。

4.7 最小实现 / 数学骨架

Lockstep: inputs -> identical sim -> same state
Replication: server sim -> snapshots/deltas -> client interpolate/predict

面试建议：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

4.8 Profiling / Validation：如何证明你的判断

  • bytes/sec、tick delay、desync rate/hash、snapshot age、correction magnitude。

4.9 常见错误答案与为什么错

  • “Lockstep 不需要服务器。”——可以 peer-to-peer，也可以 server relay/validate；核心是输入驱动确定性。
  • “State replication 就不会 desync。”——客户端预测/插值仍可能偏，但权威服务器可纠正。

4.10 Senior 级追问与参考思路

  1. 如何检测 lockstep desync？
    周期交换 deterministic state hash，二分/记录输入重放定位首次 divergence tick。
  2. Interest management 怎么做？
    按空间/团队/可见性/优先级选择 relevant entities，并对更新频率分层。

4.11 推荐实战

实现确定性小模拟，每100 tick交换 state hash；故意引入 unordered iteration 产生 desync 并定位。

完成实战时建议保留 baseline、指标、实验变量、结果、结论 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

5. 如何验证，而不是“凭感觉优化”

  • 固定随机种子/输入录制，保证问题可复现
  • 区分 simulation state 与 render interpolation state
  • 记录 latency、correction magnitude、contact/joint error 等领域指标

推荐实战

构造可重复 simulation/network demo，记录 state error、latency 或 contact/joint metrics。

6. 工程 Gotchas（扩展）

  • 视觉平滑不能改变 authoritative simulation state
  • 网络与物理问题必须显式考虑时间与确定性
