GAME ENGINE · GRAPHICS · 95 / 100

Compute Shader 可以在游戏引擎里做什么？

[!IMPORTANT] 内容分层：PDF 核心内容严格以仓库附带的原 PDF 为基线；专业扩展是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

章节：GPU API、现代引擎与性能优化
学习级别：Intermediate（仓库学习分级，不是对 PDF 星级符号的重解释）
PDF 位置：物理页 113
来源口径：公开面经/官方资料可核验 · [M1]

1. 这道题在考什么

这题属于 GPU API、现代引擎与性能优化。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

  1. 机制：数据/状态究竟怎样流动；
  2. 成本：CPU、GPU、内存、同步或数值误差的成本在哪里；
  3. Trade-off：什么场景适合，什么场景会失败；
  4. Engine Context：在真实 renderer / core / asset / simulation 中怎么落地；
  5. Evidence：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：Vulkan/D3D12 显式资源状态、GPU-driven pipeline、CPU/GPU profiling 与平台 scalability。

2. 30 秒回答（PDF 核心内容）

适合大量独立或局部协作的数据并行任务：粒子、culling、skinning、lighting、prefix sum、image processing、simulation、mip 生成等。

3. PDF 深入拆解（Source-derived）

选择 Compute 不应只因为“GPU 并行”。要考虑 dispatch 规模、memory access coalescing、 shared memory、workgroup occupancy、barrier、读写带宽以及与 graphics queue 的同步。对很小任务，dispatch/sync overhead 可能得不偿失；对 irregular pointer-heavy 算法，CPU 可能更适合。好的回答会拿一个具体算法说明线程映射与数据布局。

PDF 核心抓手

  • 数据并行度
  • memory bandwidth/occupancy
  • workgroup shared memory
  • dispatch 与 graphics 同步成本

PDF 工程 Gotcha

列十个用途但说不出一个 compute kernel 如何组织线程。

PDF 面试官在听什么

是否理解 GPU 计算模型而不是 API 名称。

4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 可实现、可测量、可讨论 trade-off 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

4.1 先修知识与概念边界

  • thread groups
  • shared memory
  • UAV/storage
  • synchronization

4.2 核心心智模型

Compute Shader 是通用GPU并行入口，适合规则的大规模数据并行和producer-consumer GPU pipelines。判断能否用 compute 的关键不是“算法能并行”，还要看数据布局、group-locality、barrier、occupancy和CPU/GPU同步。

4.3 底层机制：逐层拆开

  • Dispatch 定义 thread groups；group 内可用 shared/local memory 和 barrier协作，group间无普通全局同步。
  • 适合 map/reduce/scan、culling、particles、postprocess、skinning、simulation。
  • 全局 atomics/UAV随机写可能成为瓶颈；常用分块、prefix sum、hierarchical reduction。
  • Compute 与 graphics可异步queue重叠，但共享cache/bandwidth/compute units，async不等于免费。

4.4 必须守住的不变量 / 正确性条件

  • group barrier只能同步同一workgroup。
  • 写完storage资源给后续graphics读取需要显式memory/barrier。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

4.5 Trade-off：什么时候该用，什么时候不该用

  • Compute自由度高但失去固定功能硬件优势；能用raster/depth/blend高效完成的任务不一定该compute化。
  • group size影响occupancy、shared memory和wave利用率。

4.6 在真实游戏引擎中的落点

  • Hi-Z build、light culling、skinning、particles、prefix scan、image filters。
  • Async compute for SSAO/denoise。

4.7 最小实现 / 数学骨架

[numthreads(8,8,1)]
void CS(uint3 id:SV_DispatchThreadID, uint3 tid:SV_GroupThreadID) { ... }

面试建议：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

4.8 Profiling / Validation：如何证明你的判断

  • occupancy/wave active、LDS/shared usage、memory throughput、atomics contention、dispatch count。
  • 不同group size A/B，不能默认8×8/256最好。

4.9 常见错误答案与为什么错

  • “Compute Shader 可以访问任意线程结果，所以像CPU线程。”——group间没有普通同步/共享局部内存。
  • “Async Compute 一定提升性能。”——可能与graphics争抢同一CU/bandwidth。

4.10 Senior 级追问与参考思路

  1. Prefix sum为什么常分多级？
    单group scan后输出group sums，再scan sums并回填，突破group同步范围。
  2. 如何选group size？
    结合wave size、register/LDS、问题维度和memory coalescing，用occupancy profiler实测。

4.11 推荐实战

实现GPU prefix sum或particle update，测试64/128/256 threads group与shared memory版本。

完成实战时建议保留 baseline、指标、实验变量、结果、结论 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

5. 如何验证，而不是“凭感觉优化”

  • 先看 CPU/GPU timeline，再深入 hardware counters
  • 给 GPU object/pass 设置 debug name/marker
  • 记录 P50/P95/P99 frame time 和 memory residency，而非只看平均 FPS

推荐实战

在 Vulkan/D3D12/现代引擎 demo 中打 marker，抓取 frame trace 并写一页瓶颈报告。

6. 工程 Gotchas（扩展）

  • 显式 API 的同步越多不代表越正确，可能只是把 GPU 串行化
  • 任何“优化技巧”都必须用 profiler 证明在目标硬件上有效
