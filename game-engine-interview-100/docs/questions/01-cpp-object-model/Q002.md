# Q002 · 为什么基类析构函数经常必须是 virtual？

## 2. 30 秒回答（PDF 核心内容）

如果对象会经由基类指针被删除，基类析构函数必须是 virtual，才能沿动态类型正确执行完整析构链。

---

## 3. PDF 深入拆解（Source-derived）

关键不是“所有基类都加 virtual destructor”，而是 ownership API 的契约。如果一个类型是 polymorphic base 且允许 delete through base pointer，应提供 virtual destructor；若明确禁止这种删除，可以使用 protected non-virtual destructor。虚析构会让类进入多态对象模型并产生相应 ABI/尺寸成本，所以值类型、数学类型、final 类型不应机械添加。

### PDF 核心抓手
- 理解 delete-expression 的动态析构语义
- 区分接口基类与值类型
- 知道 protected non-virtual destructor 的设计用途

### PDF 工程 Gotcha

回答成“基类析构必须 virtual”。只有需要经由基类指针销毁时才是必须。

### PDF 面试官在听什么

能否把语言规则与所有权设计联系起来。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- 对象生命周期
- delete expression 语义
- 基类/派生类析构顺序
- 多态基类设计

### 4.2 核心心智模型

问题的本质是“通过什么静态类型销毁一个具有不同动态类型的对象”。虚析构确保删除表达式能从动态类型开始完整执行派生析构，再回到基类并释放正确对象。

### 4.3 底层机制：逐层拆开

- `delete Base*` 需要找到对象的 final overrider destructor；若基类析构非 virtual，而对象实际是 Derived，语言层面会落入未定义行为。
- 析构链顺序是派生类成员/本体 → 基类；虚析构解决“从基类入口找到正确析构链”，并不改变正常析构顺序。
- 若类完全不打算被多态删除，可以使用 protected 非虚析构，阻止外部通过基类指针 delete。
- 虚析构往往意味着类已经是 polymorphic type；额外 vtable 成本通常不是单独由析构引入，而是由整体多态设计决定。

### 4.4 必须守住的不变量 / 正确性条件

- 只要允许 `delete base_ptr` 指向派生对象，基类析构就必须可安全地动态分派。
- “有 virtual function”与“必须 public virtual destructor”不是完全等价；关键看 ownership 与销毁入口。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 接口类常用 `virtual ~I() = default`；禁止多态销毁的基类可用 protected destructor。
- 引擎对象若统一由 arena/handle/GC 管理，可能不直接暴露 delete，但仍需定义清晰的销毁协议。

### 4.6 在真实游戏引擎中的落点

- 插件对象常提供 `Destroy()`/factory pair，确保分配与释放发生在同一模块。
- ECS component 通常不需要多态析构，因为 component storage 可按类型批量销毁。
- Resource handle 的销毁应和 GPU fence 生命周期分离：C++ 对象析构不等于 GPU 资源立即可释放。

### 4.7 最小实现 / 数学骨架

```cpp
struct Interface {
    virtual ~Interface() = default;
    virtual void Run() = 0;
};

struct NonOwningBase {
protected:
    ~NonOwningBase() = default; // 禁止 delete base*
};
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- 用 ASan/UBSan 和带资源成员的 Derived 验证错误删除的后果，不要依赖“看起来能运行”。

### 4.9 常见错误答案与为什么错

- “只要派生类析构是 virtual 就行。”——虚属性由基类声明并沿继承链传播。
- “所有基类都应该虚析构。”——没有多态销毁需求时会增加不必要语义和对象模型负担。

### 4.10 Senior 级追问与参考思路

1. **什么时候可以不写 virtual destructor？**  
   当基类不用于多态删除；例如析构受保护、对象由外部 owner 按动态类型销毁，或类型根本不是 polymorphic base。
2. **插件为什么常提供 Release/Destroy 而不是让宿主 delete？**  
   避免跨模块 allocator/CRT/ABI 不一致，并能把销毁策略与版本控制封装在插件内部。

### 4.11 推荐实战

> 设计一个插件接口：宿主只能拿 opaque handle，插件提供 Create/Destroy；解释为什么这比直接返回 `IPlugin*` 并由宿主 delete 更稳健。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 查看对象布局/生成汇编，确认假设是否成立
- 对 microbenchmark 与真实 frame profile 做区分
- 用 ASan/UBSan/TSan 等工具验证生命周期或并发错误

### 推荐实战

> 写一个最小 C++ 程序，用编译器输出/汇编验证对象布局或生命周期假设；记录优化前后差异。
