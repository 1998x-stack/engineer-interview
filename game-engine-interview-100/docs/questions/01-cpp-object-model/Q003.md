# Q003 · 为什么构造函数不能是 virtual？构造期间调用 virtual function 会怎样？

## 1. 这道题在考什么

这题属于 **C++ 对象模型与语言机制**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：对象 ABI 与插件边界、组件/资源生命周期、运行时类型系统与编辑器工具链。

---

## 2. 30 秒回答（PDF 核心内容）

构造函数负责建立对象本身，动态分派所依赖的“完整派生对象”此时尚未形成；构造/析构期间的虚调用只分派到当前正在构造/析构的层级。

---

## 3. PDF 深入拆解（Source-derived）

构造顺序是 base subobject 先于 derived subobject。基类构造运行时，派生类字段还未初始化， 因此如果允许分派到派生实现，派生实现可能读取不存在的状态。主流实现会在不同构造阶段更新对象的虚表指针，使动态类型随生命周期阶段变化。析构时过程相反：派生部分先被销毁， 再退化到基类。

### PDF 核心抓手
- 掌握对象生命周期阶段
- 知道构造/析构内调用虚函数的实际分派
- 理解 factory pattern 为什么可替代“virtual constructor”

### PDF 工程 Gotcha

把“构造函数不能 virtual”仅解释成“语法不允许”，没有说明对象尚未完整建立的根因。

### PDF 面试官在听什么

是否能从对象生命周期解释语言设计。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- 对象构造/析构阶段
- 动态类型语义
- 虚函数分派
- 工厂模式

### 4.2 核心心智模型

构造期间对象是“逐层成为最终类型”的：Base 构造时 Derived 子对象尚未建立，不能安全地依赖派生状态。C++ 因此在构造/析构期间按当前正在构造/析构的类进行虚分派。

### 4.3 底层机制：逐层拆开

- 构造函数不能 virtual 的直接原因是：在选择构造函数之前对象尚不存在，连用于动态分派的完整动态类型状态都还没建立。
- Base 构造函数内调用 virtual function，不会像普通运行期那样分派到 Derived override；否则会访问尚未初始化的 Derived 成员。
- 析构阶段相反：Derived 部分已经先被销毁，进入 Base destructor 后同样不能再调用依赖 Derived 状态的 override。
- 需要“虚构造”语义时使用 factory/clone：通过普通或静态函数根据运行时信息创建正确具体类型。

### 4.4 必须守住的不变量 / 正确性条件

- 构造函数职责是建立类自身不变量，不应依赖尚未构造的派生部分。
- 析构函数应只依赖当前仍然存活的子对象。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 构造中调用非虚 helper 可复用逻辑；需要多态初始化则显式两阶段初始化，但要管理“半初始化对象”的风险。
- Factory 能提供运行时类型选择，但增加注册表、错误处理与生命周期管理。

### 4.6 在真实游戏引擎中的落点

- Reflection factory：type-id → constructor function，用于序列化加载、蓝图/脚本实例化。
- Asset loader 不应在基类 ctor 中调用虚 `LoadImpl`；应由 factory 完成对象构造后再触发加载阶段。
- Editor component 初始化可以拆为 Construct → Register → BeginPlay，明确每阶段哪些依赖已成立。

### 4.7 最小实现 / 数学骨架

```cpp
class Base {
public:
    Base() { InitBaseOnly(); }
    virtual void Start() = 0;
};

std::unique_ptr<Base> Create(TypeId id) {
    auto p = registry[id]();
    p->Start(); // 对象完整构造后再进行多态初始化
    return p;
}
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- 通过在 Base ctor/Derived ctor 中打印动态分派结果理解语义；再用 sanitizer 验证错误两阶段初始化导致的未初始化访问。

### 4.9 常见错误答案与为什么错

- “构造函数不能 virtual 是因为 vtable 还没分配内存。”——过度依赖某种 ABI，根本原因是语言生命周期语义。
- “构造函数里调用 virtual 一定是编译错误。”——通常合法，但分派受限且设计上危险。

### 4.10 Senior 级追问与参考思路

1. **如何实现 clone？**  
   基类提供 virtual `Clone()`，派生类返回自身复制；若追求无虚开销，可由 type registry 保存 copy function。
2. **两阶段初始化的主要风险？**  
   对象在 constructed 但 not-ready 状态可能被外部观察；应隐藏构造、用 factory 保证原子式发布。

### 4.11 推荐实战

> 实现一个反射工厂注册表，禁止外部直接构造，并保证对象只有在 `PostConstruct()` 成功后才被发布到 World。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 查看对象布局/生成汇编，确认假设是否成立
- 对 microbenchmark 与真实 frame profile 做区分
- 用 ASan/UBSan/TSan 等工具验证生命周期或并发错误

### 推荐实战

> 写一个最小 C++ 程序，用编译器输出/汇编验证对象布局或生命周期假设；记录优化前后差异。
