# Q004 · unique_ptr、shared_ptr、weak_ptr 底层有什么区别？

## 2. 30 秒回答（PDF 核心内容）

unique_ptr 表示独占所有权，通常只保存裸指针和 deleter；shared_ptr 通过 control block 维护 strong/weak 引用计数；weak_ptr 不增加 strong count，用于观察共享对象而不延长生命周期。

---

## 3. PDF 深入拆解（Source-derived）

shared_ptr 的成本包括控制块分配、引用计数原子操作和更复杂的对象生命周期。make_shared 往往把对象与控制块合并分配，减少一次 allocation 并改善 locality，但会改变对象内存何时真正释放：即使 strong count 为零，只要 weak count 仍存在，合并块可能继续驻留。游戏引擎中应优先建立清晰 ownership，而不是把 shared_ptr 当“安全裸指针”。

### PDF 核心抓手
- 控制块通常包含 strong/weak count、deleter/allocator
- 理解 make_shared 的单次分配
- weak_ptr::lock 的竞态安全语义
- 知道 shared_ptr 别名构造的存在

### PDF 工程 Gotcha

把 shared_ptr 当成“线程安全对象”。引用计数操作线程安全，不代表被指对象本身线程安全。

### PDF 面试官在听什么

是否理解所有权、控制块与并发成本。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- RAII
- 所有权语义
- 原子引用计数
- control block

### 4.2 核心心智模型

三种智能指针不是“不同语法的裸指针”，而是三种所有权协议：unique 是单一 owner；shared 是共享 owner + control block；weak 是非 owning observer。先定义 ownership graph，再选类型。

### 4.3 底层机制：逐层拆开

- `unique_ptr<T,D>` 通常只保存对象指针和可能的 deleter；空 deleter 可通过 EBO/压缩布局降低额外空间。
- `shared_ptr` 通常含 object pointer 与 control-block pointer；control block 保存 strong/weak count、deleter、allocator 等。
- `make_shared` 可把对象与 control block 一次分配，提高 locality、减少 allocation；但 weak_ptr 存活时整个联合 allocation 可能延迟释放。
- `weak_ptr::lock()` 需要原子地尝试增加 strong count，保证对象不会在获取 shared_ptr 的瞬间被销毁。

### 4.4 必须守住的不变量 / 正确性条件

- shared count 到 0 时销毁对象；weak count 到 0 时才销毁 control block。
- 线程安全通常仅保证“不同 shared_ptr 实例操作同一 control block”的计数安全，不代表 `T` 本身线程安全。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 热路径避免无意义复制 shared_ptr，因为原子 refcount 会造成 cache-line contention。
- 资源图中若 owner 清晰，优先 unique_ptr/handle；shared_ptr 适合确实存在共享生命周期而非“懒得设计 owner”。
- GPU 资源可使用 intrusive refcount/handle，但真正销毁仍需等待 GPU fence。

### 4.6 在真实游戏引擎中的落点

- Asset manager：数据库/manager 持 owner，游戏对象只持轻量 handle，通常比遍地 shared_ptr 更可控。
- 异步任务捕获 weak_ptr，任务执行时 lock，避免任务延长对象生命周期或访问已销毁对象。
- Entity handle 使用 generation index 解决悬空引用，比 shared ownership 更适合海量实体。

### 4.7 最小实现 / 数学骨架

```cpp
std::weak_ptr<Texture> weak = tex;
jobSystem.Enqueue([weak] {
    if (auto tex = weak.lock()) {
        tex->BuildMip();
    }
});
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- profile 原子指令与 cache-line bouncing；大量 shared_ptr copy 在多线程任务图中可能明显。
- 统计 allocation 次数比较 `shared_ptr(new T)` 与 `make_shared<T>()`。

### 4.9 常见错误答案与为什么错

- “shared_ptr 本身就是线程安全对象。”——引用计数线程安全不等于 pointee 线程安全。
- “weak_ptr 不占任何额外状态。”——仍依赖 control block，并维护 weak count。

### 4.10 Senior 级追问与参考思路

1. **为什么引擎常用 handle 而不是 shared_ptr？**  
   handle 更小、可序列化、可重定位、能集中管理生命周期，还能避免 refcount 原子流量。
2. **make_shared 的缺点？**  
   对象与 control block 共分配；即使对象析构，存在 weak_ptr 时内存块仍可能保留。

### 4.11 推荐实战

> 把一个资源管理器从 shared_ptr 图改成 manager-owned + generation handle，比较内存占用、生命周期可观测性和多线程 refcount 开销。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 查看对象布局/生成汇编，确认假设是否成立
- 对 microbenchmark 与真实 frame profile 做区分
- 用 ASan/UBSan/TSan 等工具验证生命周期或并发错误

### 推荐实战

> 写一个最小 C++ 程序，用编译器输出/汇编验证对象布局或生命周期假设；记录优化前后差异。
