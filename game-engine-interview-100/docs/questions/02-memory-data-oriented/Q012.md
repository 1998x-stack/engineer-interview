# Q012 · Stack 和 Heap 的区别是什么？实时引擎如何选择？

## 1. 这道题在考什么

这题属于 **内存、STL 与数据导向设计**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：帧内热点循环、粒子/动画/渲染数据批处理、内存预算与 allocator telemetry。

---

## 2. 30 秒回答（PDF 核心内容）

栈通常是线程私有、线性增长、自动生命周期，分配极快；堆支持任意生命周期，但通用 allocator 需要元数据、同步和碎片管理。实时循环应避免不可预测的高频堆分配。

---

## 3. PDF 深入拆解（Source-derived）

“栈快、堆慢”只是现象。栈分配通常只移动 stack pointer，而通用 heap 要寻找合适块、维护 free list/bin，并可能触发锁。游戏引擎会把不同生命周期映射到不同 allocator：frame scratch 用 linear arena；大量同尺寸对象用 pool；长期资源用 general heap；GPU 内存另有 suballocation。 关键是让释放策略与生命周期天然一致。

### PDF 核心抓手
- 每个线程有独立栈
- heap fragmentation 与 allocator contention
- 按生命周期选择 allocator
- 大对象不一定适合直接上栈

### PDF 工程 Gotcha

把“局部变量都在栈上”当绝对规律。编译器优化和对象逃逸会改变实际存储。

### PDF 面试官在听什么

是否能从生命周期和可预测性解释 allocator 选择。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- 线程栈
- heap allocator
- 生命周期
- 递归/大对象风险

### 4.2 核心心智模型

Stack/Heap 的核心差异不是“一个快一个慢”，而是生命周期、分配策略和局部性。实时引擎真正关心的是 allocation predictability：是否会锁、是否可能 page fault、是否制造碎片、是否产生不可控 hitch。

### 4.3 底层机制：逐层拆开

- 线程栈通常是预留虚拟地址区 + 按需提交物理页，函数调用通过调整 stack pointer 分配局部对象，成本极低。
- heap 由 allocator 管理自由大小/生命周期对象，可能需要 free lists、size classes、锁或系统调用。
- 大栈对象可能触碰 guard page 或导致 stack overflow；递归深度在不可信数据上尤其危险。
- heap allocation 不一定每次调用 OS；高性能 allocator 会使用 thread cache、slab/arena 降低锁竞争。

### 4.4 必须守住的不变量 / 正确性条件

- 对象应该放哪取决于生命周期和大小，不是“能放栈就永远放栈”。
- 每帧热路径要避免不可预测的通用 heap 行为。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 栈生命周期简单但容量有限；heap 灵活但要承担碎片、同步和 ownership。
- frame arena/stack allocator 把两者优点结合：动态容量 + 栈式批量回收。

### 4.6 在真实游戏引擎中的落点

- 每 job 小型 scratch data 用栈或 per-thread arena。
- 大型 asset/texture 数据放 heap/virtual memory/streaming allocator。
- 临时 render graph descriptors 使用 frame arena，frame end 批量释放。

### 4.7 最小实现 / 数学骨架

```cpp
void Tick(FrameArena& frame) {
    auto temp = frame.make_span<VisibleItem>(estimated);
    // frame 完成后整体 reset
}
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- allocator telemetry：alloc count、bytes、contention、fragmentation、largest free block、P99 latency。
- stack usage 可通过 compiler stack report/guard page telemetry 监控。

### 4.9 常见错误答案与为什么错

- “heap 每次都系统调用，所以一定很慢。”——现代 allocator 大多缓存。
- “stack object 自动就 cache-friendly。”——访问模式和对象大小仍决定 cache 行为。

### 4.10 Senior 级追问与参考思路

1. **为什么 frame allocator 能降低 hitch？**  
   消除大量独立 free 与通用 allocator metadata/锁；回收变成一次 pointer reset。
2. **如何处理超大临时 allocation？**  
   可 fallback 到 page allocator/secondary arena，并记录 telemetry，避免 silently 爆栈或扩大常驻 arena。

### 4.11 推荐实战

> 给主循环加 allocation hook，统计每帧通用 heap 调用；把热点临时分配迁到 frame arena，并比较 P99 frame time。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 记录 allocator 次数、峰值、fragmentation 与 high-water mark
- 使用 CPU profiler / hardware counters 观察 cache miss 与 bandwidth
- 用真实数据规模测试，而非只测小样本

### 推荐实战

> 实现一个小型 allocator/容器基准，统计 allocation、峰值内存和 cache 行为。

## 6. 工程 Gotchas（扩展）

- allocator 优化必须有生命周期假设；生命周期错配会制造更隐蔽的泄漏
- 对齐/padding/池化都会换取额外内存，不能只谈收益
