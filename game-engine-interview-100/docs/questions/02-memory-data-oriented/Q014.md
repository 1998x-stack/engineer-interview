# Q014 · Arena / Linear Allocator 为什么适合每帧临时对象？

## 1. 这道题在考什么

这题属于 **内存、STL 与数据导向设计**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：帧内热点循环、粒子/动画/渲染数据批处理、内存预算与 allocator telemetry。

---

## 2. 30 秒回答（PDF 核心内容）

它只维护一个 offset，分配就是对齐后递增；帧结束统一 reset，不逐对象 free，因此开销小且碎片几乎为零。

---

## 3. PDF 深入拆解（Source-derived）

Linear allocator 的本质是把“成百上千次释放”替换成一次阶段性回收。它最适合生命周期天然同批结束的数据：render command build、临时可见列表、动画 scratch、查询结果。若对象拥有需要析构的资源，应另外记录 destructor list，或者只放 trivial/arena-owned 数据。常见增强是双缓冲/多帧 arena，保证 GPU 或其他线程仍在读取旧帧数据时不会被 reset。

### PDF 核心抓手
- bump pointer allocation
- 统一 reset
- 配合 frame-in-flight 设计多套 arena
- 非平凡析构需要额外管理

### PDF 工程 Gotcha

把长生命周期对象放入 frame arena，导致下一帧 reset 后悬空。

### PDF 面试官在听什么

是否把 allocator 与系统生命周期真正绑定。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- bump allocator
- 生命周期分区
- alignment
- 析构语义

### 4.2 核心心智模型

Linear allocator 把分配简化为 `align(offset); offset += size`，优势来自“对象生命周期几乎相同”。它不是通用 heap 替代品，而是利用生命周期信息换取极低成本。

### 4.3 底层机制：逐层拆开

- bump pointer 单调前进；单次 allocation 只需 alignment 计算和边界检查。
- reset 整个 arena 即可回收，无需逐对象 free，因而几乎没有 fragmentation metadata。
- 支持 marker/rewind 可形成 stack-like 临时作用域。
- 非平凡析构类型需要注册 destructor 或限制使用，否则 reset 会跳过资源释放。

### 4.4 必须守住的不变量 / 正确性条件

- arena 内对象不能活过 arena reset。
- 跨 frame/异步任务保存 arena pointer 是典型 use-after-reset。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- arena 容量固定可预测，但峰值不足时需要 overflow policy。
- 允许任意析构会增加 bookkeeping；很多 frame arena 只允许 trivial/scope-managed resources。

### 4.6 在真实游戏引擎中的落点

- 每帧 culling output、render packet、UI layout 临时节点。
- 编译 shader/asset 的阶段性 scratch memory。
- Task graph 每 worker scratch arena，任务结束 rewind。

### 4.7 最小实现 / 数学骨架

```cpp
size_t aligned = (offset + alignment-1) & ~(alignment-1);
void* p = base + aligned;
offset = aligned + size;
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- 记录 arena high-water mark 和 overflow 次数；用 P99 峰值决定容量，而非平均。
- debug reset 后 poison memory，尽早发现跨帧悬空引用。

### 4.9 常见错误答案与为什么错

- “arena 里可以随时 delete 任意对象。”——这会破坏它的核心简化。
- “arena 不会 OOM。”——只是更可预测，仍需明确 overflow policy。

### 4.10 Senior 级追问与参考思路

1. **如何支持嵌套临时作用域？**  
   保存 marker，scope 结束 rewind 到 marker；要求作用域内对象无跨界引用。
2. **异步 job 如何用 frame arena？**  
   只有保证 job 在 reset 前完成；否则使用 job-owned arena/ref-counted page。

### 4.11 推荐实战

> 实现 marker/rewind 的 linear allocator，并在 debug 模式用 generation 标记检测跨 frame pointer。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 记录 allocator 次数、峰值、fragmentation 与 high-water mark
- 使用 CPU profiler / hardware counters 观察 cache miss 与 bandwidth
- 用真实数据规模测试，而非只测小样本

### 推荐实战

> 实现一个小型 allocator/容器基准，统计 allocation、峰值内存和 cache 行为。

## 6. 工程 Gotchas（扩展）

- allocator 优化必须有生命周期假设；生命周期错配会制造更隐蔽的泄漏
- 对齐/padding/池化都会换取额外内存，不能只谈收益
