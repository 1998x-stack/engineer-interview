# Q025 · 什么是 Deadlock？四个必要条件是什么？

## 1. 这道题在考什么

这题属于 **操作系统、多线程与并发**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：Job System 与 worker pool、Game/Render/RHI 线程所有权、低延迟同步与无锁消息通道。

## 2. 30 秒回答（PDF 核心内容）

经典必要条件是 mutual exclusion、hold-and-wait、no preemption、circular wait。工程上最常用的预防方式是固定锁顺序、缩短持锁时间和减少嵌套锁。

---

## 3. PDF 深入拆解（Source-derived）

引擎复杂之处在于锁跨系统：Asset Manager、Render Thread、GC、Editor callbacks 可能形成很长依赖链。仅靠“发现死锁后加 timeout”不可靠。更好的策略是 ownership 分区、message passing、task dependency，或者调试版记录 lock-order graph。对 GPU fence 的等待也要警惕 CPU-GPU 循环依赖，虽然它不一定是传统 mutex deadlock。

### PDF 核心抓手
- 四个必要条件
- lock ordering
- 避免持锁调用未知回调
- 异步系统也会形成等待环

### PDF 工程 Gotcha

把 starvation 与 deadlock 混为一谈。

### PDF 面试官在听什么

是否有系统级依赖图意识。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- 资源分配图
- 锁顺序
- blocking wait
- deadlock/livelock/starvation

### 4.2 核心心智模型

Deadlock 是等待图形成无法自行打破的环。四个 Coffman 条件是理论框架，工程上最有效的做法通常是破坏 circular wait：建立全局锁顺序、减少嵌套锁并用消息/任务依赖替代。

### 4.3 底层机制：逐层拆开

- mutual exclusion：资源一次只能被一个参与者占有。
- hold and wait：持有资源同时等待其他资源。
- no preemption：资源不能被外部强制夺走。
- circular wait：A等B、B等C、C等A；四条件同时存在才可能 deadlock。

### 4.4 必须守住的不变量 / 正确性条件

- 所有多锁路径必须遵守一致 lock ordering。
- 超时只能让问题更可恢复，不能证明逻辑没有死锁。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 粗锁减少死锁组合但降低并行；细锁提高并行却让锁图复杂。
- lock-free 消除特定锁死但引入 ABA、memory reclamation 等更难问题。

### 4.6 在真实游戏引擎中的落点

- Asset manager 与 renderer 双向锁最容易在加载/销毁路径形成环。
- Game thread 等 render thread fence，同时 render thread 同步请求 game thread 是经典跨线程死锁。
- 调试 UI/日志在持锁时触发其他系统也可能产生隐藏 lock order。

### 4.7 最小实现 / 数学骨架

```text
规则：ResourceManagerMutex < SceneMutex < RenderMutex
任何代码只能按左→右获取；禁止反序。
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- debug build 记录每线程 held-lock stack，检测 lock-order inversion。
- hang dump 抓所有线程 stack，构建 wait-for graph。

### 4.9 常见错误答案与为什么错

- “加 timeout 就没有死锁。”——只是最终放弃等待。
- “只有两个 mutex 才会死锁。”——任意资源/等待链都可能形成环。

### 4.10 Senior 级追问与参考思路

1. **如何做运行时 deadlock detector？**  
   记录线程等待的 lock 和每个 lock owner，周期构建 wait-for graph 找 cycle。
2. **为什么 task graph 能减少 deadlock？**  
   把依赖显式化并让 worker 执行其他任务，减少同步嵌套锁和线程互等。

### 4.11 推荐实战

> 为引擎 mutex wrapper 增加 lock rank，debug build 在获取低 rank 锁时 assert；再写测试故意制造 inversion。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 在 trace 中标注 task/lock/wait，先看 critical path
- 统计 contention、wake-up、context switch，而非只看平均 CPU
- 并发正确性用 sanitizer/stress test 验证

### 推荐实战

> 写一个可重复的多线程小实验，并用 sanitizer/trace 验证 happens-before 与 contention。
