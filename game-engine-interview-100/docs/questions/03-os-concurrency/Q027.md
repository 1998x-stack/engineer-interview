## 2. 30 秒回答（PDF 核心内容）

relaxed 只保证该原子操作本身原子，不建立跨变量顺序；release 发布此前写入，acquire 观察对应 release 后，建立 happens-before，使先前写对读取线程可见。

---

## 3. PDF 深入拆解（Source-derived）

典型 producer-consumer：先写 payload，再 release-store ready；consumer acquire-load ready 后再读 payload。seq_cst 额外提供单一全局顺序，最易推理但可能限制优化。真正的面试重点是能否从一个小例子说明“为什么 relaxed 不够” ，而不是背枚举。也要理解编译器重排与 CPU 重排都受 memory ordering 约束。

### PDF 核心抓手
- 原子性与可见性/顺序性是不同概念
- release/acquire 常用于发布对象
- seq_cst 最强但不是默认答案
- 数据竞争仍是 UB

### PDF 工程 Gotcha

认为 volatile 可以替代 atomic 或内存屏障。C++ volatile 不提供线程同步语义。

### PDF 面试官在听什么

是否能进行跨线程 happens-before 推理。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- C++ memory model
- happens-before
- atomic
- 编译器/CPU 重排

### 4.2 核心心智模型

Memory order 不是“CPU 是否执行这条指令”，而是约束不同线程观察操作的顺序。release 发布之前的写，acquire 读取到该发布后，建立跨线程 happens-before；relaxed 只提供该 atomic 的原子性和 modification order。

### 4.3 底层机制：逐层拆开

- `relaxed`：原子读写不撕裂，并在该 atomic 上有一致 modification order，但不把普通内存操作同步给其他线程。
- `release store`：当前线程在它之前的写不能被其他线程在同步观察后“看不到”。
- `acquire load` 读取到对应 release（或 release sequence）后，后续读取能看到发布前状态。
- `seq_cst` 额外要求所有 seq_cst 操作参与一个单一全序，推理简单但可能限制优化/硬件映射。

### 4.4 必须守住的不变量 / 正确性条件

- 必须先画出“谁发布什么、谁消费什么”的 happens-before 图，再选 memory order。
- atomic 变量本身安全，不代表它保护的 payload 自动安全。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- x86 TSO 上 acquire/release 可能生成与普通 load/store 类似指令，但编译器约束仍重要；ARM 等弱内存模型差异更明显。
- 过度 seq_cst 易正确但可能隐藏对同步协议理解不足。

### 4.6 在真实游戏引擎中的落点

- lock-free queue/ freelist。
- double-buffer state publish。
- job completion counter：worker writes result → release decrement/flag → waiter acquire observe。

### 4.7 最小实现 / 数学骨架

```text
Producer: payload writes -> release(flag=1)
                         | synchronizes-with
Consumer: acquire(flag) -> payload reads
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- 用 herd7/litmus test 或专门并发测试验证 memory-order 模型；不能仅靠“本机跑一亿次没出错”。

### 4.9 常见错误答案与为什么错

- “volatile 可以做线程同步。”——C++ volatile 不建立跨线程 happens-before。
- “relaxed 比 acquire 快很多所以尽量用。”——错误同步比性能差更严重。

### 4.10 Senior 级追问与参考思路

1. **release/acquire 必须操作同一个 atomic 吗？**  
   synchronizes-with 需要 acquire 读到对应 release 写入（或 release sequence）的值；不能凭时间顺序跨无关 atomic 自动建立。
2. **为什么 lock-free 代码要关心对象回收？**  
   即使指针原子更新正确，另一个线程可能仍持旧指针；需要 hazard pointer/epoch 等防 use-after-free。

### 4.11 推荐实战

> 写 message-passing litmus：payload 普通变量 + atomic ready，分别用 relaxed 和 release/acquire；解释语言模型下哪个有数据竞争/可见性保证。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 在 trace 中标注 task/lock/wait，先看 critical path
- 统计 contention、wake-up、context switch，而非只看平均 CPU
- 并发正确性用 sanitizer/stress test 验证

### 推荐实战

> 写一个可重复的多线程小实验，并用 sanitizer/trace 验证 happens-before 与 contention。
