# Q053 · Vertex Shader 与 Fragment Shader 谁调用次数更多？

## 1. 这道题在考什么

这题属于 **实时渲染管线**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：base pass / depth / lighting、GPU overdraw 与 bandwidth、draw submission / visibility。

---

## 2. 30 秒回答（PDF 核心内容）

没有绝对答案。典型高分辨率/高 overdraw 场景 fragment workload 更大；高几何密度、复杂 vertex deformation 或 Nanite 类场景也可能 geometry/vertex 侧很重。

---

## 3. PDF 深入拆解（Source-derived）

判断必须看 profiler：vertex count、post-transform cache 命中、screen coverage、overdraw、pixel shader 指令/纹理访存。一个 1 像素三角形可能让 vertex 开销远高于有效 pixel；反过来 fullscreen post pass 几乎没有 vertex 成本却有数百万 fragment。优化前先确定 geometry-bound、pixelbound、bandwidth-bound 或 submission-bound。

### PDF 核心抓手
- 不要用调用次数单独判断成本
- 关注每次 shader cost
- 小三角形会浪费 raster eﬀiciency
- overdraw 放大 pixel workload

### PDF 工程 Gotcha

回答“Fragment Shader 一定更多”。

### PDF 面试官在听什么

是否会用 workload 数据而非经验口号。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- vertex reuse
- overdraw
- screen resolution
- shader workload

### 4.2 核心心智模型

不能用一个固定答案比较 VS/PS 调用次数。VS 取决于 unique post-transform vertices/instances；PS 取决于 covered samples、overdraw、early-z、MSAA 和 helper lanes。正确做法是量化场景。

### 4.3 底层机制：逐层拆开

- Indexed draw 有 post-transform vertex cache，同一 index 顶点可能不重复执行 VS（具体硬件缓存）。
- PS invocation 随屏幕覆盖和 overdraw 增长；4K fullscreen pass≈8.3M pixels/次，远大于常见 mesh vertex 数。
- 高 tessellation/microtriangle 场景可能 geometry/vertex bound；大量透明/粒子常 fragment bound。
- Depth prepass/early-z 可减少 expensive PS，但增加一次 geometry processing 和 depth bandwidth。

### 4.4 必须守住的不变量 / 正确性条件

- 调用次数不等于成本：一个 VS 可很重，一个 PS 也可纹理/分支极重。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 优化应先判断 geometry-bound / pixel-bound / bandwidth-bound，而不是凭“PS通常更多”。

### 4.6 在真实游戏引擎中的落点

- Nanite/microgeometry 关注 triangle/pixel ratio。
- VR/4K 强化 pixel cost。
- Skinning heavy VS/compute path 与透明 overdraw。

### 4.7 最小实现 / 数学骨架

```text
Approx VS work ~ unique transformed vertices × instances
Approx PS work ~ covered samples × overdraw × shading rate
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- pipeline statistics：VS invocations、PS invocations、primitives。
- GPU profiler 看 shader busy、texture/bandwidth、quad utilization。

### 4.9 常见错误答案与为什么错

- “Fragment Shader 永远调用更多。”——高几何/低分辨率可相反。
- “调用次数多的阶段就是瓶颈。”——单 invocation 成本差异巨大。

### 4.10 Senior 级追问与参考思路

1. **如何判断 microtriangle 问题？**  
   看 triangles per pixel、rasterizer/quad utilization、PS helper ratio；许多 <1 pixel triangle 浪费 setup/quad。
2. **VRS 会改变什么？**  
   降低 shading invocation rate而不必降低 raster/depth sample rate，减少 pixel shading cost。

### 4.11 推荐实战

> 选择同一场景在720p/4K、low/high tessellation下抓 pipeline stats，分析瓶颈如何迁移。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 用 RenderDoc/Nsight/RGP 检查 pass、draw、overdraw 与 shader cost
- 用 GPU timestamp 分离 geometry/pixel/bandwidth bottleneck
- 修改一项渲染策略后比较同场景同相机基线

### 推荐实战

> 在一个最小 renderer 中实现或切换该技术，用 GPU timestamp + frame capture 对比。

## 6. 工程 Gotchas（扩展）

- 不要把 API 语义顺序等同于硬件严格串行顺序
- 只看 draw call 数量无法证明 GPU 更快，bandwidth/overdraw/shader 可能才是瓶颈
