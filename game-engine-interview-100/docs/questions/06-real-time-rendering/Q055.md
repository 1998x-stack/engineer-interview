# Q055 · Early-Z 什么时候可能失效或受限？

## 1. 这道题在考什么

这题属于 **实时渲染管线**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：base pass / depth / lighting、GPU overdraw 与 bandwidth、draw submission / visibility。

---

## 2. 30 秒回答（PDF 核心内容）

当 fragment shader 可能改变最终深度或可见性，或存在需要保留副作用的写操作时，GPU 不能随意在 shader 前丢弃该 fragment。

---

## 3. PDF 深入拆解（Source-derived）

典型因素包括写 gl_FragDepth/SV_Depth、 某些 discard/alpha test 路径以及 UAV/storage side effects。不同 GPU/API 会采用 early/late test 的保守规则，也可能启用 early_fragment_tests 等显式语义。重点不是背一份“失效清单” ，而是推理：如果提前 kill 会改变程序可观察结果，就不能安全提前。

### PDF 核心抓手
- 从程序副作用推理是否允许 early reject
- 写深度是最直接限制
- discard 的实际影响依架构/编译器而异
- 显式 early tests 也要理解语义

### PDF 工程 Gotcha

把 alpha test 简单说成“必然关闭 Early-Z”。现实更细，需要看硬件与 shader 行为。

### PDF 面试官在听什么

是否能用 correctness 推导 GPU 优化条件。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- Early/Late depth
- discard
- SV_Depth/gl_FragDepth
- UAV/side effects

### 4.2 核心心智模型

Early-Z 受限的根本问题是：如果 shader 的执行会改变“这个 fragment 是否通过”或产生不可撤销副作用，GPU 就不能简单跳过 shader。实际硬件有 early test、early reject、late update 等更细策略。

### 4.3 底层机制：逐层拆开

- shader 写 depth（`SV_Depth/gl_FragDepth`）时最终深度未知，传统 early compare 可能不安全；某些 conservative depth qualifier 可恢复部分优化。
- `discard/clip` 决定是否保留 fragment，硬件可能先做 early reject 但延后 depth write，具体实现依赖架构。
- UAV/storage writes、atomics 等 side effects 若 fragment 最终应被 depth kill，提前/延后执行的语义需满足 API 规则，因此会限制 early execution。
- Alpha test foliage 常同时有大量 overdraw 与 discard，是 Early-Z 效率复杂的典型场景。

### 4.4 必须守住的不变量 / 正确性条件

- 不要把“Early-Z 开/关”当单一二值状态；硬件可拆 early test、late write。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- Alpha-to-coverage/MSAA、dithered masks 可在视觉/early depth间做不同折中。
- 将 side-effect pass 与 shading pass 分离可能恢复优化，但增加额外 pass。

### 4.6 在真实游戏引擎中的落点

- Foliage/alpha-tested materials。
- Decal/custom depth shader。
- OIT/UAV-based transparency。

### 4.7 最小实现 / 数学骨架

```text
阻碍因素：shader depth output / discard / storage side effects / special blend-depth modes
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- GPU vendor counters 看 early/late depth tests、killed pixels；shader variant 开关 discard/UAV 做对比。

### 4.9 常见错误答案与为什么错

- “用了 discard 就一定完全没有 Early-Z。”——实现可仍做部分 early reject，只是深度更新/执行语义受限。
- “force early fragment tests 总是安全优化。”——会改变某些 depth write/side effect 可见语义，需理解 API。

### 4.10 Senior 级追问与参考思路

1. **Conservative depth 有什么用？**  
   声明 shader depth 只会比原深度更大/更小等，让硬件保留部分 early depth 优化。
2. **alpha-tested foliage 如何优化？**  
   depth prepass masked、alpha coverage simplification、cluster culling、LOD/impostor；必须实测带宽与重复采样成本。

### 4.11 推荐实战

> 写三种 shader：纯 opaque、discard、写 depth/UAV，使用 vendor profiler 比较 early/late depth counter。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 用 RenderDoc/Nsight/RGP 检查 pass、draw、overdraw 与 shader cost
- 用 GPU timestamp 分离 geometry/pixel/bandwidth bottleneck
- 修改一项渲染策略后比较同场景同相机基线

### 推荐实战

> 在一个最小 renderer 中实现或切换该技术，用 GPU timestamp + frame capture 对比。

## 6. 工程 Gotchas（扩展）

- 不要把 API 语义顺序等同于硬件严格串行顺序
- 只看 draw call 数量无法证明 GPU 更快，bandwidth/overdraw/shader 可能才是瓶颈
