# Q073 · 游戏引擎 Serialization 系统如何设计？

## 1. 这道题在考什么

这题属于 **引擎架构与资源系统**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：runtime/editor 数据边界、asset cook/streaming、render scheduling 与跨平台后端。

---

## 2. 30 秒回答（PDF 核心内容）

序列化需要把对象状态映射到稳定格式，并处理类型元数据、对象引用、版本迁移、endianness、 可选字段与资产 GUID。最难的是 schema evolution。

---

## 3. PDF 深入拆解（Source-derived）

成熟系统不应把裸内存 dump 作为通用格式，因为 compiler padding、指针、版本和平台都会改变。字段应有稳定 ID/名字，引用保存 GUID/handle 而不是地址。加载时可以先构造对象表， 再第二阶段 resolve references。版本升级可通过 per-type migration 或 tagged field 兼容。编辑器格式可以可读，runtime cooked 格式则追求解析速度和紧凑。

### PDF 核心抓手
- 不要序列化裸指针
- 稳定字段 ID/版本
- 两阶段 resolve reference
- 编辑器格式与 runtime cooked format 可不同

### PDF 工程 Gotcha

把 C++ struct 直接 fwrite 到磁盘。

### PDF 面试官在听什么

是否理解数据长期演化，而不仅是“读写 JSON”。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- schema
- type metadata
- object graph
- version migration

### 4.2 核心心智模型

Serialization 的难点不在“写 JSON”，而在长期稳定地表达类型、引用和版本。资产可能跨几年存在，因此必须把内存布局与持久化 schema 解耦，并支持增删改字段、类型迁移和引用解析。

### 4.3 底层机制：逐层拆开

- Archive 按 TypeId/FieldId 访问 metadata，而不是 memcpy 整个 C++ struct。
- 对象引用用 AssetGUID/EntityID/ObjectID 序列化，加载后第二阶段 resolve；裸指针不可持久化。
- 版本号/field version 触发 converter，从 old schema 迁到 new schema。
- 二进制格式还需处理 endian、alignment、compression、chunking、随机访问和 corruption validation。

### 4.4 必须守住的不变量 / 正确性条件

- 持久化 ID 必须稳定；runtime pointer/offset 不稳定。
- 加载失败要可诊断，不应部分写坏对象后继续运行。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- Self-describing 格式易调试/兼容但体积大；cooked binary 紧凑快但依赖版本工具。
- Schema evolution 可在 import/cook 阶段一次迁移，减少 runtime 分支。

### 4.6 在真实游戏引擎中的落点

- Scene/prefab serialization。
- Network replication schema 与 save-game schema 不应简单共用全部规则。
- Cooked asset header 存 version/hash/dependencies/chunks。

### 4.7 最小实现 / 数学骨架

```text
Header{magic, version, typeId}
Fields[{fieldId, type, byteRange}...]
References -> IDs -> resolve phase
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- round-trip、old-version fixtures、fuzz/corruption tests、load throughput、seek count。
- 统计迁移失败和未知字段。

### 4.9 常见错误答案与为什么错

- “直接 fwrite struct 最快所以最好。”——padding/endian/pointer/version 全不稳定。
- “字段改名只要字符串换一下。”——旧资产仍存旧 schema，需要 alias/migration。

### 4.10 Senior 级追问与参考思路

1. **如何支持 partial loading/streaming？**  
   格式按 chunks/subresources 建索引，metadata 与 bulk data 分离，依赖可独立请求。
2. **如何做 backward/forward compatibility？**  
   未知字段可跳过、缺字段用默认值；破坏性变化通过 version converter。

### 4.11 推荐实战

> 设计一个 versioned binary scene format，模拟 V1→V3 字段重命名/拆分并加载旧 fixture。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 画清 module/resource ownership graph 与线程边界
- 给 asset/build/streaming 记录版本、依赖和 telemetry
- 用 failure injection 测试资源缺失、热重载、设备丢失等路径

### 推荐实战

> 画模块/资源/线程依赖图，再写一个最小接口原型说明 ownership 与失败路径。

## 6. 工程 Gotchas（扩展）

- 抽象层不能以丢失关键平台能力为代价
- 资源 identity、ownership、versioning 是长期维护成本中心

| 0 - 记忆点 | 只能给出一个术语或结论，无法解释原因。 |

1. 用 PDF 的“30 秒回答”先给结论；
