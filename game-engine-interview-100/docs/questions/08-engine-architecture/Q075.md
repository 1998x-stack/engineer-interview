# Q075 · 如何设计 Asset GUID？

## 1. 这道题在考什么

这题属于 **引擎架构与资源系统**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：runtime/editor 数据边界、asset cook/streaming、render scheduling 与跨平台后端。

---

## 2. 30 秒回答（PDF 核心内容）

资产 identity 应与文件路径解耦。用稳定 GUID 作为引用键，再由数据库映射到当前路径/包位置，移动或重命名文件不会破坏引用。

---

## 3. PDF 深入拆解（Source-derived）

还要解决 GUID 的生成、复制、冲突和版本控制。若复制一个资产文件时也复制元数据 GUID，会造成 collision；编辑器需要检测并重生成。runtime 可以把长 GUID cook 成紧凑 integer handle。 依赖图、redirector、软引用和异步加载都建立在稳定 identity 上。

### PDF 核心抓手
- 路径是 location，不是 identity
- GUID 需要冲突检测
- cook 后可映射成紧凑索引
- 软引用允许目标暂未加载

### PDF 工程 Gotcha

直接把绝对路径写入场景文件。跨机器、重命名、打包都会出问题。

### PDF 面试官在听什么

是否具备数据血缘/长期维护意识。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- stable identity
- path vs ID
- asset database
- rename/move

### 4.2 核心心智模型

Asset GUID 解决“身份不等于路径”。路径是可变用户界面属性，GUID 是跨 rename/move 稳定引用键。正确系统还要处理复制、导入、删除、冲突和版本控制合并。

### 4.3 底层机制：逐层拆开

- Meta file/database 为每个 logical asset 生成稳定 GUID；引用序列化 GUID 而非文件路径。
- Asset DB 维护 GUID→current path/import state/dependencies。
- rename/move 只更新 path mapping，不改 GUID，因此 prefab/scene 引用不破。
- 复制资产通常要生成新 GUID；版本控制冲突若复制 meta 可能造成 duplicate GUID，需检测修复。

### 4.4 必须守住的不变量 / 正确性条件

- 同一项目 namespace 中 GUID 必须唯一且稳定。
- GUID 解决 identity，不自动解决内容版本；可另加 content hash。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 随机 UUID 易用但不可从内容重建；content hash 天然去重但内容变化 ID 也变化，不适合作稳定编辑器引用。
- 可组合 stable GUID + content hash。

### 4.6 在真实游戏引擎中的落点

- Prefab/material/scene reference。
- Cook dependency graph。
- Asset redirector 支持历史 path/ID 迁移。

### 4.7 最小实现 / 数学骨架

```text
GUID -> AssetRecord { path, type, sourceHash, cookedHash, deps[] }
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- 启动/导入时扫描 duplicate/missing GUID。
- rename/move/copy/delete 自动化测试确保引用完整。

### 4.9 常见错误答案与为什么错

- “用绝对路径做ID。”——项目迁移/重命名必坏。
- “用内容 hash 做唯一 GUID 就完美。”——内容任何编辑都会改变 identity。

### 4.10 Senior 级追问与参考思路

1. **跨项目迁移 GUID 怎么办？**  
   需要 namespace/冲突策略；若目标已有相同 GUID 但不同资产，要 remap 并修引用。
2. **删除后重建同路径是否沿用旧GUID？**  
   通常不应自动视作同一 logical asset，除非 meta 仍存在/显式恢复。

### 4.11 推荐实战

> 实现一个小 AssetDB：meta GUID、rename/move/copy、duplicate detection 和引用 remap 测试。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 画清 module/resource ownership graph 与线程边界
- 给 asset/build/streaming 记录版本、依赖和 telemetry
- 用 failure injection 测试资源缺失、热重载、设备丢失等路径

### 推荐实战

> 画模块/资源/线程依赖图，再写一个最小接口原型说明 ownership 与失败路径。
