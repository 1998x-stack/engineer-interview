# Q076 · 什么是 Resource Streaming？

## 1. 这道题在考什么

这题属于 **引擎架构与资源系统**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：runtime/editor 数据边界、asset cook/streaming、render scheduling 与跨平台后端。

---

## 2. 30 秒回答（PDF 核心内容）

在有限 RAM/VRAM 和 I/O 带宽下，根据相机、重要度和未来需求按需加载/卸载纹理 mip、 mesh LOD、音频块等，而不是一次把整个世界放进内存。

---

## 3. PDF 深入拆解（Source-derived）

一个 streaming system 需要需求估计、priority、I/O scheduling、decode/transcode、GPU upload、 residency budget 和 eviction。最危险的是“刚看到才加载” ：SSD、解压、upload 都有延迟，因此需要根据相机速度和预测提前请求。纹理 virtual/streaming mip、geometry streaming 都是把大资源切成可独立 residency 的 page/chunk。

### PDF 核心抓手
- 需求预测
- 预算与驱逐
- 异步 I/O + decode + upload pipeline
- 粒度必须可独立加载

### PDF 工程 Gotcha

只讨论“异步加载线程”，忽略 GPU residency 和预算。

### PDF 面试官在听什么

是否能设计端到端数据流。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- residency
- IO/decompression/upload
- LOD/mips
- memory budget

### 4.2 核心心智模型

Resource Streaming 是一个闭环控制系统：预测近期需求→异步 IO→解压/转码→上传→进入 residency，同时在有限 RAM/VRAM 预算下 eviction。它的目标不是“尽量多加载”，而是用最少驻留满足未来几帧质量。

### 4.3 底层机制：逐层拆开

- 需求由 camera distance、screen size、priority、gameplay hints、prefetch path 等产生。
- IO scheduler 合并小读、按 storage block/chunk 排序，后台解压并准备 GPU upload。
- Texture 以 mip、mesh 以 LOD/page/cluster 分级 residency；高细节可渐进到达。
- Eviction 根据 LRU/priority/cost/last-use/fence 安全回收，防止超 budget。

### 4.4 必须守住的不变量 / 正确性条件

- GPU 正在使用的 resource page 不能立即 evict/reuse。
- Streaming 必须有 fallback representation，miss 时不能崩或黑屏。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 更激进 prefetch 减 pop-in 但增加 IO/内存。
- 高压缩省 IO 但增加 CPU/GPU decode。

### 4.6 在真实游戏引擎中的落点

- Texture mip streaming。
- Virtual texture pages。
- Open-world geometry cell/mesh pages。
- Audio stream chunks。

### 4.7 最小实现 / 数学骨架

```text
Demand -> Priority Queue -> IO -> Decompress -> Upload -> Resident Set
                                      ^                |
                                      └-- Evict <------┘ budget
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- IO MB/s、queue latency、decompress ms、upload MB/frame、VRAM residency、miss/pop-in count。
- 记录 camera teleport 和高速移动 P99。

### 4.9 常见错误答案与为什么错

- “Streaming 就是开个线程异步加载。”——还缺预测、优先级、分级数据、residency/eviction。
- “加载完 CPU 内存就可释放。”——GPU upload/fence/后续重建需求要明确。

### 4.10 Senior 级追问与参考思路

1. **如何处理相机 teleport？**  
   应急优先级、低LOD/fallback立即显示、限速高LOD请求，避免把IO队列淹没。
2. **如何选择 eviction？**  
   结合 last-use、未来预测、reload cost、quality impact；纯 LRU 对大资源/巡航路径未必好。

### 4.11 推荐实战

> 实现模拟 streaming scheduler：固定 RAM/VRAM 和 IO 带宽，比较 LRU 与 priority-aware eviction 在相机轨迹上的 miss。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 画清 module/resource ownership graph 与线程边界
- 给 asset/build/streaming 记录版本、依赖和 telemetry
- 用 failure injection 测试资源缺失、热重载、设备丢失等路径

### 推荐实战

> 画模块/资源/线程依赖图，再写一个最小接口原型说明 ownership 与失败路径。
