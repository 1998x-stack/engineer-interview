## 1. 这道题在考什么

这题属于 **引擎架构与资源系统**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：runtime/editor 数据边界、asset cook/streaming、render scheduling 与跨平台后端。

## 2. 30 秒回答（PDF 核心内容）

把一帧渲染表示成 Pass 与 Resource 的依赖图。每个 pass 声明读写，编译阶段自动确定执行顺序、resource lifetime、barrier、transient allocation/aliasing。

---

## 3. PDF 深入拆解（Source-derived）

传统手写 render pass 容易出现资源生命周期过长、barrier 过保守、隐藏依赖。Render Graph 把“我要读什么/写什么”声明化，系统可做 dead-pass culling、自动 transition、别名复用。真正难点是 side effect、external resource/import、跨 queue async compute 和 debugging；如果 pass 隐式访问全局资源，图就无法正确优化。

### PDF 核心抓手
- 声明式 resource dependency
- 自动 lifetime/barrier
- transient memory aliasing
- 能做 pass culling 和 async scheduling

### PDF 工程 Gotcha

把 Render Graph 当成“画流程图”的工具，不理解它是资源/同步编译器。

### PDF 面试官在听什么

是否理解现代 renderer 的资源调度核心。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- resource dependency graph
- barrier
- transient allocation
- pass culling

### 4.2 核心心智模型

Render Graph 是“帧级资源与同步编译器”：pass 声明 reads/writes，不直接手写大部分 lifetime/barrier；编译器据此构建 DAG、剔除无贡献 pass、规划 transient memory、插入状态转换并调度 graphics/compute。

### 4.3 底层机制：逐层拆开

- Builder 阶段创建 logical resources 和 pass declarations；每条 read/write edge 形成 dependency。
- 从 external outputs/present/side-effect pass 反向可达，未影响输出的 pass 可 cull。
- 资源 first-use/last-use 形成 lifetime interval；不重叠且兼容的 transient resources 可 alias 同一物理内存。
- 跨 queue 依赖需 semaphore/fence；同 queue 需 layout/state/access barrier，graph compiler可从声明推导。

### 4.4 必须守住的不变量 / 正确性条件

- 任何资源访问都必须显式声明；隐藏 global/UAV side effect 会让图推导错误。
- Imported/external/history resource 生命周期跨 frame，需要区别 transient。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 声明式系统减少人工 barrier 错误，但调试需能可视化编译后图、physical allocation 和 barrier。
- 过度细 pass 提高优化机会也增加 graph build/command overhead。

### 4.6 在真实游戏引擎中的落点

- UE RDG。
- FrameGraph-style transient RT aliasing。
- Async compute scheduling。

### 4.7 最小实现 / 数学骨架

```text
Pass A writes Depth
Depth -> Pass B(read) -> GBuffer
GBuffer -> Lighting -> Final
Compiler: topological order + barriers + lifetime + aliasing + culling
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- graph compile ms、pass count/cull count、transient peak bytes、barrier count、async overlap。
- 输出 DOT/可视化图对比 logical/physical resources。

### 4.9 常见错误答案与为什么错

- “Render Graph 只是把 pass 画成图。”——核心是依赖推导、资源生命周期与同步编译。
- “有 graph 后就不需要懂 barrier。”——错误声明会产生错误同步，性能调优仍需理解 API。

### 4.10 Senior 级追问与参考思路

1. **history texture 如何处理？**  
   作为 external/persistent resource 跨 frame import/export，不能参与普通 transient alias 生命周期。
2. **async compute 如何调度？**  
   分析资源依赖找可与 graphics 重叠的 compute interval，插入跨 queue signal/wait；收益受共享资源/带宽竞争限制。

### 4.11 推荐实战

> 实现 toy render graph：DAG、dead-pass culling、first/last use、greedy aliasing，并输出 barrier plan。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 画清 module/resource ownership graph 与线程边界
- 给 asset/build/streaming 记录版本、依赖和 telemetry
- 用 failure injection 测试资源缺失、热重载、设备丢失等路径

### 推荐实战

> 实现一个 5-pass toy Render Graph，自动计算 resource first/last use 和简单 aliasing。
