# Q080 · 如何设计跨平台 RHI？

> **内容分层**：`PDF 核心内容`严格以仓库附带的原 PDF 为基线；`专业扩展`是为了让题目达到更强的工程面试深度，来自通用工程知识与下方列出的官方/权威资料。两者刻意分开，便于追踪来源。

## 1. 这道题在考什么

这题属于 **引擎架构与资源系统**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：runtime/editor 数据边界、asset cook/streaming、render scheduling 与跨平台后端。

---

## 2. 30 秒回答（PDF 核心内容）

对 Buffer、Texture、Pipeline、CommandList、Fence、Descriptor 等核心概念提供平台无关接口，下层分别映射 DX12/Vulkan/Metal；同时必须保留足够能力，不要为了“统一”抹平现代 API 特性。

---

## 3. PDF 深入拆解（Source-derived）

好的 RHI 往往以 capability/query 驱动差异，而不是大量 if(platform)。需要决定同步模型、 resource state、descriptor binding、queue、memory allocation 由上层还是后端负责。如果抽象过高，无法使用 Vulkan/DX12 的显式并行；过低则 renderer 到处暴露 API 差异。实际引擎通常还在 RHI 上再有更高层 Render Graph。

### PDF 核心抓手
- 抽象稳定概念而非 API 函数名
- capability-driven
- 显式 API 的同步/descriptor 不能完全隐藏
- RHI 与 Render Graph 分层

### PDF 工程 Gotcha

设计成“把 OpenGL 函数重命名成统一接口”，无法表达现代 API。

### PDF 面试官在听什么

是否具备跨 API 抽象能力。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- D3D12/Vulkan/Metal
- resource/pipeline/command abstraction
- capability model

### 4.2 核心心智模型

RHI 的目标不是把所有 API 磨平成最小公分母，而是建立稳定高层资源/命令模型，同时保留平台特性和性能控制。好 RHI 常是“common core + capability/extension path”，并把平台差异显式化。

### 4.3 底层机制：逐层拆开

- 核心对象：Device/Queue/CommandList/Buffer/Texture/View/Sampler/Shader/Pipeline/Fence/Descriptor。
- RHI 负责统一资源生命周期、状态语义、debug names、memory allocation接口，但具体 barrier/layout/descriptor模型差异要谨慎抽象。
- Capabilities 查询描述 bindless、mesh shader、ray tracing、tile features、format支持等；renderer按能力选择 path。
- Backend translation 应尽量薄，避免在每 draw 做昂贵动态适配；PSO/descriptor layout 多在创建期预计算。

### 4.4 必须守住的不变量 / 正确性条件

- 抽象不能隐藏对 correctness 必需的同步/资源状态。
- RHI object 不应把某 API 原生 handle 语义泄漏到所有上层，但要允许受控 escape hatch。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 过低层 RHI 上层代码平台分支多；过高层会无法利用 async/tile/descriptor 等特性。
- 统一 memory allocator 简化上层，但 UMA/discrete residency 策略需要 backend 特化。

### 4.6 在真实游戏引擎中的落点

- D3D12/Vulkan common explicit RHI。
- Metal/tile GPU 单独优化 render pass load/store。
- Ray tracing API 通过 optional interface/capability。

### 4.7 最小实现 / 数学骨架

```text
Renderer -> RHI common API -> {D3D12, Vulkan, Metal}
                     \-> Capabilities / native extension path
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- backend API calls/draw、translation CPU ms、PSO creation/hit、validation errors。
- 跨平台 golden frame + performance regression。

### 4.9 常见错误答案与为什么错

- “RHI 就是把函数名统一。”——真正难的是资源状态、descriptor、memory、queue语义。
- “只支持最小公分母最可移植。”——会牺牲现代平台关键性能。

### 4.10 Senior 级追问与参考思路

1. **Barrier 如何抽象？**  
   可定义 engine access/state model，再由 backend 映射；必须能表达 read/write stages/layout，不能只用“ResourceState::GenericRead”。
2. **如何支持平台特有 fast path？**  
   capability + extension interface 或 renderer strategy，不污染每个普通调用。

### 4.11 推荐实战

> 设计一页 RHI API：Buffer/Texture/Pipeline/CommandList/Barrier；分别说明映射 D3D12/Vulkan 的困难点。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 画清 module/resource ownership graph 与线程边界
- 给 asset/build/streaming 记录版本、依赖和 telemetry
- 用 failure injection 测试资源缺失、热重载、设备丢失等路径

### 推荐实战

> 画模块/资源/线程依赖图，再写一个最小接口原型说明 ownership 与失败路径。

## 6. 工程 Gotchas（扩展）

- 抽象层不能以丢失关键平台能力为代价
- 资源 identity、ownership、versioning 是长期维护成本中心

## 8. 面试评分 Rubric

| 层级 | 面试表现 |
|---|---|
| 0 - 记忆点 | 只能给出一个术语或结论，无法解释原因。 |
| 1 - 原理 | 能解释核心机制与至少一个关键不变量。 |
| 2 - 工程 | 能讨论 trade-off、边界条件，并把它落到真实引擎模块。 |
| 3 - Senior signal | 能给出可测量的成本模型、profiling/验证方法和替代方案。 |

### 2 分钟回答组织法

1. 用 PDF 的“30 秒回答”先给结论；
2. 选择 **2 个机制点** 展开，不要一次倾倒全部知识；
3. 给出 **1 个真实引擎场景**；
4. 主动补 **1 个 Gotcha / 失败条件**；
5. 用 **1 个 profiler / test / counter** 收尾，说明如何验证。
