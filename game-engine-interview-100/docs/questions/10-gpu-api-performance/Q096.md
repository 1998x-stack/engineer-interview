# Q096 · 一帧只有 20 FPS，你如何定位问题？

> [!IMPORTANT]

## 1. 这道题在考什么

这题属于 **GPU API、现代引擎与性能优化**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：Vulkan/D3D12 显式资源状态、GPU-driven pipeline、CPU/GPU profiling 与平台 scalability。

---

## 2. 30 秒回答（PDF 核心内容）

20 FPS50ms/frame。第一步不是“优化代码” ，而是确定 CPU-bound、GPU-bound、sync-bound、 I/O hitch 还是内存/温度问题，再用 profiler 找 critical path。

---

## 3. PDF 深入拆解（Source-derived）

CPU 先看主线程/worker timeline、sampling profile、任务等待；GPU 看 pass timestamp、pipeline counters、overdraw、bandwidth、occupancy；再检查 CPU-GPU queue 是否一方 starving。优化必须闭环：measure → hypothesis → change → measure。平均 FPS 会掩盖 hitch，应同时看 frame-time percentile（P95/P99）和 spike。移动端还要考虑 thermal throttling。

### PDF 核心抓手
- 先分类瓶颈
- 看 frame time 而非只看 FPS
- CPU/GPU timeline 找 critical path
- P99 hitch 与平均性能都重要

### PDF 工程 Gotcha

一看到 GPU 慢就降分辨率；可能真正是 CPU submission 或同步 bubble。

### PDF 面试官在听什么

这是工程岗最重要的“问题定位能力”题。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- frame budget
- CPU/GPU timeline
- critical path
- hardware counters

### 4.2 核心心智模型

20 FPS=50ms/frame。第一原则是先定位瓶颈域，再优化：CPU-bound、GPU-bound、sync/wait、IO/streaming、memory/page fault。性能工程是“测量→假设→最小实验→再次测量”，不是列优化技巧。

### 4.3 底层机制：逐层拆开

- 先看 frame timeline：Game/Render/RHI/worker是否总共占50ms，GPU是否50ms，还是CPU在wait GPU/present。
- CPU用sampling/instrumentation profiler找self/total time、locks、cache misses、allocs；GPU按pass看时间再看shader/ROP/bandwidth counters。
- 若GPU 50ms，缩分辨率测试：若时间近似随像素降，pixel/bandwidth；降geometry测试判断vertex/raster。
- IO hitch看storage read、decompress、page fault、upload/fence，不应混在平均FPS。

### 4.4 必须守住的不变量 / 正确性条件

- 优化必须针对critical path；优化非critical并行线程可能对frame time零收益。
- 平均FPS会掩盖hitch，必须看P95/P99/1% low。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 快速quality scaling可先救帧率，但root cause仍需定位。
- GPU/CPU overlap意味着各自总和不直接相加，应看最长链。

### 4.6 在真实游戏引擎中的落点

- Budget sheet：Game 4ms/RenderCPU 3ms/GPU 14ms等。
- Per-pass GPU markers。
- Streaming telemetry + hitch recorder。

### 4.7 最小实现 / 数学骨架

```text
1) Reproduce + capture
2) CPU vs GPU vs wait/IO
3) Find critical path
4) Form hypothesis
5) One controlled change
6) Re-capture and guard regression
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- P50/P95/P99 frame time、CPU ready/wait、GPU pass ms、VRAM/RAM、IO/decompress。
- 自动性能场景做commit regression。

### 4.9 常见错误答案与为什么错

- “先把draw call降一半。”——如果GPU shader bound可能毫无意义。
- “GPU利用率99%说明优化很好。”——可能只是某个低效pass吃满。

### 4.10 Senior 级追问与参考思路

1. **CPU 8ms GPU20ms先优化谁？**  
   若能完整重叠，frame≈max(8,20)，GPU是critical；除非CPU hitch/latency另有目标。
2. **如何判断bandwidth-bound？**  
   分辨率/format变化、vendor memory counters、ALU轻微变化不影响时间而bytes改变明显。

### 4.11 推荐实战

> 选一个真实慢帧写性能诊断报告：timeline截图、3个假设、每个A/B实验、最终证据。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 第一步只做定位：CPU-bound / GPU-bound / sync-bound / I/O-bound
- 第二步缩小到具体 thread/job/pass，然后看硬件 counter
- 优化后复测 P50/P95/P99 与 hitch，防止平均值掩盖长尾

### 推荐实战

> 选一个真实帧抓取，输出 CPU/GPU critical path、前三热点、证据和仅一个最优先实验。

## 6. 工程 Gotchas（扩展）

- 显式 API 的同步越多不代表越正确，可能只是把 GPU 串行化
- 任何“优化技巧”都必须用 profiler 证明在目标硬件上有效

## 8. 面试评分 Rubric

| 层级 | 面试表现 |
|---|---|
| 0 - 记忆点 | 只能给出一个术语或结论，无法解释原因。 |
| 1 - 原理 | 能解释核心机制与至少一个关键不变量。 |
| 2 - 工程 | 能讨论 trade-off、边界条件，并把它落到真实引擎模块。 |
| 3 - Senior signal | 能给出可测量的成本模型、profiling/验证方法和替代方案。 |

### 2 分钟回答组织法

1. 用 PDF 的“30 秒回答”先给结论；
2. 选择 **2 个机制点** 展开，不要一次倾倒全部知识；
3. 给出 **1 个真实引擎场景**；
4. 主动补 **1 个 Gotcha / 失败条件**；
5. 用 **1 个 profiler / test / counter** 收尾，说明如何验证。
