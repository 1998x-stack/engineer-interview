# Q097 · 为什么移动 GPU 和桌面 GPU 优化思路不同？

## 1. 这道题在考什么

这题属于 **GPU API、现代引擎与性能优化**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：Vulkan/D3D12 显式资源状态、GPU-driven pipeline、CPU/GPU profiling 与平台 scalability。

---

## 2. 30 秒回答（PDF 核心内容）

移动芯片大量采用 tile-based 架构，片上 tile memory 能显著减少外部内存带宽；因此 render pass 合并、attachment load/store、overdraw、带宽与能耗比桌面更敏感。

---

## 3. PDF 深入拆解（Source-derived）

TBDR/tiler 会先分 bin，再在 tile 内完成部分 raster/shading，尽量不把中间 framebuffer 往 DRAM 反复读写。错误的 pass 边界或必须 store/reload 的 attachment 会破坏优势。移动端还受统一内存、功耗和 thermal budget 约束，峰值性能不能长时间持续。桌面优化经验不能直接照搬。

### PDF 核心抓手
- tile memory 降低带宽
- render pass/load-store 很关键
- 功耗/温度是长期预算
- overdraw 和透明常很昂贵

### PDF 工程 Gotcha

认为“移动 GPU 就是更慢的桌面 GPU”。

### PDF 面试官在听什么

是否具备平台架构敏感性。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- IMR vs TBDR
- tile memory
- bandwidth/power
- thermal

### 4.2 核心心智模型

移动GPU往往以Tile-Based Deferred Rendering降低外部内存带宽：先把primitive bin到tile，在片上tile memory完成depth/color再必要时store。桌面IMR通常拥有更高带宽/功耗预算。优化差异的核心是“外部内存访问和tile load/store代价”。

### 4.3 底层机制：逐层拆开

- TBDR先geometry/binning，逐tile处理可见samples，许多hidden fragments在片上解决。
- Render target若能在一个render pass/tile内消费，避免store到DRAM再reload。
- 频繁切render pass、读取前一RT、MSAA resolve可能迫使tile memory flush。
- 移动还受thermal throttling、共享系统内存、较低cache/compute预算影响。

### 4.4 必须守住的不变量 / 正确性条件

- 不能把所有移动GPU都视为同一架构；Apple/ARM/Qualcomm等细节不同。
- 优化应看bandwidth/power而不只峰值FLOPS。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- Deferred大GBuffer在tile memory容纳得下时也可有特殊优化，但外存store成本需谨慎。
- Framebuffer fetch/subpass/input attachment等可利用tile locality，跨平台抽象较难。

### 4.6 在真实游戏引擎中的落点

- Mobile forward/clustered。
- Render pass merging。
- ASTC/texture compression、half precision、减少overdraw/RT bandwidth。

### 4.7 最小实现 / 数学骨架

```text
TBDR: Bin primitives -> Tile on-chip shade/depth/blend -> Store final tile
目标：少走外部DRAM
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- external memory bandwidth、tile load/store、overdraw、thermal/frequency、power。
- 真机长时间跑，观察5-10分钟后throttling，不只冷启动30秒。

### 4.9 常见错误答案与为什么错

- “移动GPU性能低所以只要降画质。”——应利用tile架构和带宽特征做结构优化。
- “Deferred在移动一定不行。”——取决于架构/render pass/RT格式与具体实现。

### 4.10 Senior 级追问与参考思路

1. **为什么discard在tile GPU也可能贵？**  
   shader仍可能执行且会影响early tests/quad效率；alpha foliage带来的overdraw/texture也重。
2. **Render pass merge为什么重要？**  
   让intermediate attachments保留在tile memory，避免DRAM store/load。

### 4.11 推荐实战

> 在移动设备比较两个pass分离与subpass/merged版本，记录external bandwidth和功耗/温度。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 先看 CPU/GPU timeline，再深入 hardware counters
- 给 GPU object/pass 设置 debug name/marker
- 记录 P50/P95/P99 frame time 和 memory residency，而非只看平均 FPS

### 推荐实战

> 在 Vulkan/D3D12/现代引擎 demo 中打 marker，抓取 frame trace 并写一页瓶颈报告。

## 6. 工程 Gotchas（扩展）

- 显式 API 的同步越多不代表越正确，可能只是把 GPU 串行化
- 任何“优化技巧”都必须用 profiler 证明在目标硬件上有效
