## 1. 这道题在考什么

这题属于 **GPU API、现代引擎与性能优化**。面试官通常不是只听一个定义，而是在判断你能否把答案推进到：

1. **机制**：数据/状态究竟怎样流动；
2. **成本**：CPU、GPU、内存、同步或数值误差的成本在哪里；
3. **Trade-off**：什么场景适合，什么场景会失败；
4. **Engine Context**：在真实 renderer / core / asset / simulation 中怎么落地；
5. **Evidence**：如何通过 profiler、测试、frame capture 或汇编证明判断。

本章常见工程落点：Vulkan/D3D12 显式资源状态、GPU-driven pipeline、CPU/GPU profiling 与平台 scalability。

## 2. 30 秒回答（PDF 核心内容）

先把 16.67ms/frame 当硬预算，再按 CPU、GPU、RAM/VRAM、I/O 建预算与 telemetry；世界分区、资源 streaming、可见性、任务系统、Render Graph 和异步上传必须围绕“只处理玩家当前需要的数据”协同。

## 3. PDF 深入拆解（Source-derived）

一个完整方案至少包含：World Partition/streaming cells；纹理/几何/动画分块加载；frustum+LOD+occlusion+GPU culling；Game/Job/Render/RHI 多线程；Render Graph 管理 transient resource/barrier；GPU graphics/compute/copy overlap；arena/pool 与 deferred GPU resource deletion；帧时 profiler 和 P99 hitch tracking。关键是说明每个系统如何影响同一个 frame budget，而不是罗列技术名。设计时还要预留平台差异和降级路径。

### PDF 核心抓手
- 预算驱动而不是 feature 驱动
- 只处理可见/需要的数据
- CPU/GPU/I/O 流水并行
- 所有优化必须有 profiler 反馈闭环

### PDF 工程 Gotcha

堆砌 Nanite、Lumen、ECS、Job System 等名词，却没有资源/线程依赖和帧预算。

### PDF 面试官在听什么

这是把前 99 题串成“工程系统能力”的终极题。

## 4. 专业扩展（Repository v2）

这一节不再重复 PDF 的“定义答案”，而是把问题推进到 **可实现、可测量、可讨论 trade-off** 的层级。面试时不要求把下面所有内容一次讲完；更好的策略是先给结论，再根据面试官追问选择其中 2–3 个层次深入。

### 4.1 先修知识与概念边界

- frame budget
- streaming
- job/render graph
- GPU-driven
- scalability/telemetry

### 4.2 核心心智模型

60 FPS开放世界设计必须从预算与最坏情况开始，而不是从功能清单开始：16.67ms frame、RAM/VRAM、IO/decompress/upload、CPU core budgets都要量化。所有子系统围绕“只处理当前/即将需要的数据”协同，并有overload degradation和持续telemetry。

### 4.3 底层机制：逐层拆开

- World partition把世界切streaming cells；高层预测相机/玩家路径，异步读取并维护CPU/GPU residency。
- CPU用job graph并行animation/physics/AI/culling prep，render extraction形成稳定snapshot，render graph管理GPU资源/同步。
- Visibility pipeline按frustum→LOD→occlusion/Hi-Z→GPU-driven compact，减少CPU draw和无效GPU work。
- GPU按graphics/compute/copy queue组织，但只在真正无依赖且不争同一瓶颈资源时overlap；资源生命周期用frame/timeline fences。

### 4.4 必须守住的不变量 / 正确性条件

- frame time由critical path决定，预算必须可观测。
- 任何streaming资源必须有fallback/LOD，任何队列必须有backpressure/overflow策略。
- 所有内存预算需要eviction与fence-safe reuse，不允许“只增不减”。

这些不变量比“记住某个 API”更重要：平台、实现或引擎版本可以变化，但只要不变量没变，你就能重新推导正确方案。

### 4.5 Trade-off：什么时候该用，什么时候不该用

- 画质/可见距离/RT/GI/shadow/animation更新率都要有scalability阶梯。
- 增加frames in flight改善吞吐但增加latency和内存。
- 预取提高稳定性但可能挤占当前必需资源。

### 4.6 在真实游戏引擎中的落点

- CPU budget示例：Game 2ms、Jobs 4ms、Render prep 2ms；GPU budget按Depth/GBuffer/Lighting/GI/Post等分配，实际依项目。
- Streaming budget：IO MB/s、decompress ms、upload MB/frame、VRAM target/headroom。
- Hitch system：shader/PSO warmup、page faults、asset miss、GC/allocator、OS scheduling全部记录。

### 4.7 最小实现 / 数学骨架

```text
Prediction -> World/Asset Streaming -> Resident Set
Game -> Job DAG -> Render Snapshot -> Render Graph -> GPU Queues
Visibility -> GPU-driven commands
Profiler/Telemetry feeds budgets, eviction and scalability decisions
```

> **面试建议**：代码或公式不是为了炫技。写完后要解释：输入是什么、输出是什么、最贵的步骤在哪里、哪个条件一旦破坏就会出错。

### 4.8 Profiling / Validation：如何证明你的判断

- P50/P95/P99 frame time、1% low、CPU ready/wait、GPU critical passes。
- RAM/VRAM residency headroom、IO queue latency、decompress/upload、stream miss。
- 场景级自动benchmark：城市、森林、战斗、高速移动、teleport、内存压力。

### 4.9 常见错误答案与为什么错

- “上Nanite/Lumen/ECS/Async Compute就能60FPS。”——这些是工具，不是预算证明。
- “平均16ms就达标。”——P99 50ms会让体验明显卡顿。
- “CPU/GPU各16ms所以总共32ms。”——流水重叠时应看critical path，但同步可让它们串行。

### 4.10 Senior 级追问与参考思路

1. **相机高速移动导致streaming来不及怎么办？**  
   低LOD/fallback先可见，预测加大prefetch，prioritize visible blockers，限制高LOD请求，必要时动态缩可视距离/质量。
2. **CPU8ms GPU20ms先优化谁？**  
   若完整overlap，GPU是帧critical；但仍检查CPU P99/hitch和input latency。
3. **如何做memory budget？**  
   按类别设soft/hard budget+headroom，持续residency telemetry；eviction看未来需求/重载成本/last-use，并fence-safe。
4. **如何防性能回归？**  
   固定replay/benchmark场景，CI采集平台P50/P95/GPU pass/memory并设阈值，版本间趋势而非单次手测。

### 4.11 推荐实战

> 写一份真正的60FPS budget sheet：CPU/GPU/IO/RAM/VRAM，每项给target、warning、hard limit、telemetry和降级策略；再为“城市战斗+高速相机”设计压力测试。

完成实战时建议保留 **baseline、指标、实验变量、结果、结论** 五项记录。真正能在面试中形成 Senior signal 的不是“我写过”，而是“我能解释为什么这个实现更快/更稳，以及证据是什么”。

## 5. 如何验证，而不是“凭感觉优化”

- 先看 CPU/GPU timeline，再深入 hardware counters
- 给 GPU object/pass 设置 debug name/marker
- 记录 P50/P95/P99 frame time 和 memory residency，而非只看平均 FPS

### 推荐实战

> 给一个 16.67ms 目标写完整 budget sheet：Game/Render CPU、各 GPU pass、I/O、RAM/VRAM，并设计 overload/scalability 策略。

## 8. 面试评分 Rubric

| 层级 | 面试表现 |
|---|---|
| 0 - 记忆点 | 只能给出一个术语或结论，无法解释原因。 |
| 1 - 原理 | 能解释核心机制与至少一个关键不变量。 |
| 2 - 工程 | 能讨论 trade-off、边界条件，并把它落到真实引擎模块。 |
| 3 - Senior signal | 能给出可测量的成本模型、profiling/验证方法和替代方案。 |

### 2 分钟回答组织法

1. 用 PDF 的“30 秒回答”先给结论；
2. 选择 **2 个机制点** 展开，不要一次倾倒全部知识；
3. 给出 **1 个真实引擎场景**；
4. 主动补 **1 个 Gotcha / 失败条件**；
5. 用 **1 个 profiler / test / counter** 收尾，说明如何验证。
