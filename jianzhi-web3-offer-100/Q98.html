WEB3 · SOLIDITY · 98 / 101

System Design：设计中心化交易平台 Deposit System。

难度 ★★★★★ | 高频度 ★★★★★ | 岗位 Backend/Exchange | PDF 第 111 页

本文件以 PDF 中 Q98 为主干；“GitHub 扩展”部分是在原内容上增加的工程化学习材料。原 PDF：Jianzhi_Web3_Offer_100_Interview_Questions_2026.pdf.

1. 面试官为什么问这题

金融账本、一致性和链重组综合题。

高分回答的层级

  • L1 - 定义正确：术语不混淆，先给一到两句话结论。
  • L2 - 原理可推导：能解释为什么，以及底层状态/数据/执行路径。
  • L3 - Failure Mode：主动说明什么时候结论不成立、常见攻击或工程故障。
  • L4 - Invariant / Trade-off：能给出不变量、信任假设或系统设计取舍。

2. 30 秒标准回答

流程：地址归属/标签 -> chain ingestion -> detect inbound transfer -> confirmation/finality policy -> deposit record -> double-entry ledger credit -> reconciliation。链上事件与内部账本之间必须通过幂等状态机连接。

3. 原理深挖（PDF 主干）

3.1 关键推导

绝不能只做 user.balance += amount。内部账本要有不可变 journal：例如借记平台 onchain asset/clearing account，贷记用户 liability account，使每个 entry 借贷平衡并可审计。

3.2 关键推导

风险包括 reorg/double credit、token decimals、fee-on-transfer、wrong chain、memo/tag、contract deposits、duplicate events、address reuse、hot/cold sweep。大额可采用更高 confirmation tier。

4. 白板模型

flowchart LR
  UI[User intent] --> SIGN[Wallet / signer]
  SIGN --> SUB[RPC / bundler]
  SUB --> CHAIN[Chain execution]
  CHAIN --> EVT[Events]
  EVT --> IDX[Indexer]
  IDX --> DB[(DB / ledger)]
  DB --> API[API / UI]

在面试中不必追求图漂亮；图的作用是让状态、信任边界、调用方向或资产流一眼可见。

5. 必须说出的关键点

  • double-entry ledger
  • idempotent deposit identity
  • confirmation/finality tiers
  • reorg compensation
  • reconciliation with onchain balances

6. GitHub 扩展：工程化理解

下面内容是在 PDF 主干之上增加的生产/审计视角，用于把“知道概念”升级为“能落地”。

  • 先澄清 functional / non-functional requirements，再画数据流和用户可见状态机。
  • 列资产不变量和信任边界，再决定链上/链下边界、升级与权限模型。
  • 故障设计覆盖 timeout、retry、idempotency、reorg、replacement、backfill、灾备和降级。
  • 最后才谈吞吐、缓存、分片与成本；Staff 级答案必须给 observability 和 runbook。
  • 链上观察与内部账本分离；入账必须幂等并支持 reorg reversal。
  • 不要直接修改 balance；使用可审计 ledger entries 和 reconciliation。

6.1 面试推导顺序

  1. 先下定义：用本题 30 秒回答建立边界。
  2. 再给机制：把对象、输入、状态变化或执行上下文说清楚。
  3. 主动给失败模式：从本题常见误区反推“哪里会出问题”。
  4. 给 mitigation / 工程做法：说明如何测试、监控或限制 blast radius。
  5. 用 invariant 收尾：让面试官看到你能从局部 API 上升到系统正确性。

6.2 验证 / 测试清单

  • [ ] 对状态机每个 transition 写幂等测试。
  • [ ] 做故障注入：RPC、DB、queue、signer、oracle、sequencer。
  • [ ] 对资产流做 double-entry/invariant reconciliation。

6.3 前置知识与概念边界

这题属于 System Design / Coding / Debug。以下 6.3–6.12 属于 GitHub 专业深化（通用工程知识与推导），并非 PDF 原文；PDF 主干仍以上文第 1–5 节为准。

在进入细节前，建议先确认下面三个前置层次：

  • 前九章的状态、安全、DeFi 与 infra 基础
  • 幂等、事务、队列、缓存、数据库与 SRE 基础
  • 威胁建模与可观测性

本题已有关键点可以进一步拆成：

  1. double-entry ledger：面试中需要把它从关键词展开成“定义 → 机制 → 边界 → 工程后果”，不能只念术语。
  2. idempotent deposit identity：面试中需要把它从关键词展开成“定义 → 机制 → 边界 → 工程后果”，不能只念术语。
  3. confirmation/finality tiers：面试中需要把它从关键词展开成“定义 → 机制 → 边界 → 工程后果”，不能只念术语。
  4. reorg compensation：面试中需要把它从关键词展开成“定义 → 机制 → 边界 → 工程后果”，不能只念术语。
  5. reconciliation with onchain balances：面试中需要把它从关键词展开成“定义 → 机制 → 边界 → 工程后果”，不能只念术语。

边界原则：能回答“它是什么”只能达到基础分；高级回答必须继续回答“它不是什么、依赖什么假设、失败时会怎样”。

6.4 形式化模型 / 白板推导

系统设计题先分离 On-chain source of truth、Off-chain orchestration 和 Derived read model。然后画资产流、状态机、信任边界和失败恢复路径；最后才讨论具体数据库、队列或框架。

白板时建议固定使用以下推导顺序：

  1. 对象：列出参与者、状态、资产或数据结构；
  2. 输入：哪些交易/消息/价格/签名会驱动状态变化；
  3. 规则：哪些条件决定有效、排序、授权或价格；
  4. 状态变化：写出成功路径和失败/回滚路径；
  5. Invariant：任何正常或恶意输入下必须保持什么；
  6. Trust assumption：哪些条件不是代码能独立保证的。

6.5 本题最值得深挖的一层：Deposit System 先做 ledger，再做余额

链上 deposit 只是外部事实，内部 credit 必须通过可审计双重记账和 confirmation policy；reorg 后需要冻结/冲正而不是直接减余额。

如果面试官继续追问，不要立刻换新术语。先从上述核心模型推出一个具体后果，再给一个反例或边界条件，最后说明生产系统如何验证/缓解。

6.6 生产工程决策

  • 先写功能/非功能需求和 invariant，再画组件图，避免一上来堆技术名词。
  • 所有写路径都要回答幂等键、重试、重复消息、事务边界和补偿策略。
  • 链上与内部 ledger 必须可对账；金额、decimals、chain/token identity 都要有强类型语义。
  • 安全设计必须覆盖 admin key、upgrade、pause、incident response、审计日志与最坏情况用户退出。

对本题而言，工程答案最好至少包含一个“正常路径”和一个“故障路径”。前者证明你理解功能，后者证明你理解系统。

6.7 Threat Model / Failure Modes

把失败模式分成三类会更专业：

  • 语义错误：概念或状态模型理解错，导致实现从根上错误；
  • 对抗性输入：攻击者利用排序、回调、价格、签名、权限等主动破坏假设；
  • 系统性故障：RPC、节点、sequencer、oracle、数据库或管理员路径异常。

本题重点检查：

  • 把数据库 balance 当账本。
  • 链上 watcher 和用户 credit 写在两个无法恢复的独立步骤。
  • 没有定义 source of truth，链上与数据库互相覆盖
  • 只画 happy path，没有 reorg/RPC/queue/db failure
  • 余额直接 UPDATE 而非 ledger/可审计账务
  • 把“去中心化”当作自动高可用而忽略前端/RPC/indexer 单点

面试时最好把“风险”改写成可验证句式：在条件 A 下，攻击者/故障 B 可以让状态 C 违反 invariant D，影响资产/可用性 E。

6.8 测试策略：Unit → Fuzz → Invariant → Integration

  • [ ] 故障注入：RPC/DB/queue/worker 重启与网络分区
  • [ ] 幂等与 exactly-once-like 行为验证
  • [ ] reorg/backfill/replay 的恢复演练
  • [ ] 容量、延迟、资金安全和权限边界的压测/攻防测试

进一步建议：

  • Unit test：验证局部 API 与边界输入；
  • Fuzz test：搜索你没有手工枚举的输入组合；
  • Invariant test：验证任意调用序列下核心关系仍成立；
  • Integration/Fork test：验证真实 token、oracle、RPC、链状态或跨合约行为；
  • Failure injection：主动让依赖超时、重组、停机、返回异常，验证恢复路径。

6.9 可观测性与线上排障

如果这道题变成线上事故，不要只说“看日志”。先定义你要观察的链上事实、派生状态与外部依赖。本章常用信号包括：

  • end-to-end settlement latency
  • queue lag / retry rate
  • ledger reconciliation delta
  • reorg/RPC/indexer incident indicators

排障顺序建议固定为：

用户现象
  ↓
确认 chain / tx / block / request identity
  ↓
确认 source of truth
  ↓
定位状态机停在哪一步
  ↓
查看依赖与权限变化
  ↓
复现 / simulate / trace
  ↓
决定 retry / rollback / pause / compensate

6.10 不同岗位如何回答同一道题

  • 通用工程视角：先给定义，再给机制、边界、失败模式、测试与生产取舍。
  • 高级面试升级：最后补一句“这个结论依赖哪些假设、线上怎样观测、出现异常如何回滚/降级”，通常能明显区分 Senior 与纯知识型回答。

7. 高频追问与回答方向

追问 1：为什么链上 balance != 用户 liabilities？

回答方向： 还有 fees、hot/cold transfers、pending deposits。

进一步展开时应回扣：double-entry ledger，并至少补一个边界条件或反例。

追问 2：重复看到同 tx/log 怎么办？

回答方向： 唯一键 + 幂等。

进一步展开时应回扣：idempotent deposit identity，并至少补一个边界条件或反例。

追问 3：已 credit 后发生深 reorg？

回答方向： 冻结/逆向 ledger entry/风险储备，不能静默改历史。

进一步展开时应回扣：confirmation/finality tiers，并至少补一个边界条件或反例。

8. 常见错误回答 / Gotchas

  • 错误模式： 把数据库 balance 当账本。
  • 错误模式： 链上 watcher 和用户 credit 写在两个无法恢复的独立步骤。
  • 面试修正方式： 不要只换一个更专业的名词；要明确指出错误假设、给出正确模型，并说明该错误在生产环境可能造成的后果。

9. 记忆锚点

交易所入金系统的本质是把“可能回滚的外部链事件”安全映射成“可审计的内部金融账本”。

10.1 实战训练：把这题变成可展示的工程证据

场景任务：把 System Design：设计中心化交易平台 Deposit System。 作为真实系统设计题：先写需求和 invariant，再给组件/状态机/数据模型，最后完成故障注入、安全测试、容量估算和事故恢复方案。

建议输出物：

  1. 一张状态机 / 资产流 / 调用图；
  2. 一份 10～30 行的最小代码、伪代码或数据结构；
  3. 3 个 happy-path 测试 + 3 个 adversarial/failure-path 测试；
  4. 至少 1 个 invariant；
  5. 一段 2 分钟口述答案，要求不看稿；
  6. 与 Q97、Q99、Q96 做一次对比复盘，说明相同底层机制与不同工程边界。

10.2 反向面试：你可以问面试官什么

为了判断团队真实工程成熟度，可以围绕本题反问：

  • 这个系统当前最关键的 invariant / SLO 是什么？
  • 过去出现过哪类与本题相关的线上事故或审计问题？
  • 团队如何做 fork/invariant/failure-injection 测试？
  • 协议升级或依赖变更时，谁负责 compatibility review 和 rollback plan？
  • 哪些安全/可靠性判断是链上强制，哪些依赖 off-chain service 或人工流程？

这些问题既能帮助你了解岗位，也能体现你关注长期正确性和运行质量，而不只是完成一次编码任务。
