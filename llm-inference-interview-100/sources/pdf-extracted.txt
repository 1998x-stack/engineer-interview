前言｜为什么需要一本“推理优化版剑指 Offer”
LLM 推理面试的难点不在知识点数量，而在跨层推理：同一个“模型很慢”问题，可能来自模型结构、KV Cache、
GPU 内存带宽、CUDA kernel、NCCL、调度器、请求长度分布或 SLO。面试官真正想看到的是你能否建立成本模
型，并用证据逐层定位。

因此本书不把 100 题做成“名词解释”。每题固定提供 30 秒回答、关键公式、Know-Why、工程场景、常见错误、
追问链和评分标准。建议先尝试口头回答，再阅读深挖；第二遍只做公式和估算；第三遍按追问链模拟面试。

“真题”在这里指真题级问题：来自真实工业系统与公开技术体系中反复出现的核心考点。对于无法公开核验的公
司匿名面经，不标注“某公司原题”。这样可以避免把传闻当事实。

    全书主线 为什么慢 → 慢在哪里 → 这个优化为什么有效 → 它牺牲什么 → 哪些 workload 下无效 → 如何用实验验证。

3. KV Cache M_KV = B × T × L × 2 × H_kv × D_head × bytes

5. 通信成本 T_comm ≈ α + bytes / effective bandwidth

7. Goodput Goodput = requests meeting SLO / second

Q001 为什么 LLM 的 Prefill 和 Decode 是两种完全不同的计算？
难度 ★★★★★ · 章节 推理性能基本原理 · 关键词 prefill,decode,roofline


    30 秒回答 Prefill 一次处理整段 prompt，矩阵 M 维较大，GEMM/Attention 更容易提高算术强度，常偏 compute-bound；
    Decode 每步只新增少量 token，却要反复读取模型权重与历史 KV，低 batch 下常偏 memory-bandwidth-bound；两阶段
    分别主导 TTFT 与 TPOT，因此不能用同一套优化策略。




01｜考察本质
     这道题不是考名词定义，而是看你能否从系统资源出发解释：Prefill 一次处理整段 prompt，矩阵 M 维较
      大，GEMM/Attention 更容易提高算术强度，常偏 compute-bound；Decode 每步只新增少量 token，却要反复读取模型权
      重与历史 KV，低 batch 下常偏 memory-bandwidth-bound；两阶段分别主导 TTFT 与 TPOT，因此不能用同一套优化策
      略。
     面试中应先给结论，再给成本模型/瓶颈，再给适用边界。只背框架参数通常拿不到高分。

02｜关键公式 / 成本模型

    公式 Prefill: Q,K,V∈R^{T×d}; Decode: Q∈R^{B×d}. 低并发 Decode 的下界常近似受 weight bytes / HBM bandwidth 限
    制。




03｜Know-Why：为什么成立
     1. Prefill 一次处理整段 prompt，矩阵 M 维较大，GEMM/Attention 更容易提高算术强度，常偏 compute-bound
     2. Decode 每步只新增少量 token，却要反复读取模型权重与历史 KV，低 batch 下常偏 memory-bandwidth-bound
     3. 两阶段分别主导 TTFT 与 TPOT，因此不能用同一套优化策略。
     把这一结论放进 Roofline / 内存容量 / 调度 / 通信四类模型中检查，确认瓶颈是否真的位于关键路径，而不是只优化了一个
      非关键算子。

04｜工程场景

    现场推演 32K prompt + 100 输出 token 的服务，优先关心 Prefill 切分与 TTFT；1K prompt + 16K 推理输出则更应优化
    Decode、KV 与 speculative decoding。




05｜常见错误
     ✗ 把“Prefill compute-bound、Decode memory-bound”当成绝对结论
     ✗ 高 batch、MoE、长上下文或通信开销都可能改变瓶颈。

06｜追问链
     → 为什么增大 batch 对 Decode 特别有效？
     → 为什么 Chunked Prefill 能同时改善吞吐与 ITL？
     → 如何用 Roofline 验证你的判断？

07｜面试官评分标准
     及格：能给出正确概念和基本方向。
     良好：能写出成本/显存/通信公式，能解释为什么。
     优秀：能指出反例、适用边界，并能把问题落到 profiler、SLO 或真实系统配置。

Q002 TTFT、TPOT、ITL、E2E Latency、Throughput、Goodput 分
别是什么？
难度 ★★★★☆ · 章节 推理性能基本原理 · 关键词 metrics,SLO,goodput


    30 秒回答 TTFT 衡量请求到首 token；TPOT/ITL 衡量生成阶段 token 间隔；E2E 是用户完整等待时间；Throughput 是单位
    时间完成的 token 或请求；Goodput 只统计满足 SLO 的工作量。生产系统通常应围绕 p95/p99 与 Goodput 而非平均吞吐优
    化。




01｜考察本质
     这道题不是考名词定义，而是看你能否从系统资源出发解释：TTFT 衡量请求到首 token；TPOT/ITL 衡量生成阶段 token 间
      隔；E2E 是用户完整等待时间；Throughput 是单位时间完成的 token 或请求；Goodput 只统计满足 SLO 的工作量。生产
      系统通常应围绕 p95/p99 与 Goodput 而非平均吞吐优化。
     面试中应先给结论，再给成本模型/瓶颈，再给适用边界。只背框架参数通常拿不到高分。

02｜关键公式 / 成本模型

    公式 E2E≈TTFT+(N_out-1)×TPOT；Goodput = 满足 TTFT/TPOT SLO 的 request/s。




03｜Know-Why：为什么成立
     1. TTFT 衡量请求到首 token
     2. TPOT/ITL 衡量生成阶段 token 间隔
     3. E2E 是用户完整等待时间
     4. Throughput 是单位时间完成的 token 或请求
     5. Goodput 只统计满足 SLO 的工作量。生产系统通常应围绕 p95/p99 与 Goodput 而非平均吞吐优化。
     把这一结论放进 Roofline / 内存容量 / 调度 / 通信四类模型中检查，确认瓶颈是否真的位于关键路径，而不是只优化了一个
      非关键算子。

04｜工程场景

    现场推演 A 系统 100 req/s 但仅 60% 满足 SLO，Goodput=60；B 系统 85 req/s 且 95% 满足 SLO，Goodput≈80.75，B 对
    线上更优。




05｜常见错误
     ✗ 只报平均 latency 或峰值 tokens/s
     ✗ 忽略排队时间、首 token 与后续 token 的体验差异。

06｜追问链
     → 为什么 p99 比平均值更重要？
     → RAG 与长 CoT 应分别重点看哪些指标？
     → Streaming 场景里 TPOT 和 E2E 谁更重要？

Q003 为什么 batch=1 的 Decode 经常是 Memory Bound？
难度 ★★★★★ · 章节 推理性能基本原理 · 关键词 decode,memory-bandwidth

    FLOPS 增长往往快于 HBM 带宽增长，所以算力没有吃满时 HBM 已接近瓶颈。增大 batch 可以摊薄每 token 的权重读取成
    本。

     这道题不是考名词定义，而是看你能否从系统资源出发解释：每生成一个 token 都要执行全模型层。batch=1 时同一份权重
      只服务一个 token，权重读取复用极低；现代 GPU FLOPS 增长往往快于 HBM 带宽增长，所以算力没有吃满时 HBM 已接近
      瓶颈。增大 batch 可以摊薄每 token 的权重读取成本。
     面试中应先给结论，再给成本模型/瓶颈，再给适用边界。只背框架参数通常拿不到高分。

02｜关键公式 / 成本模型

    公式 粗略上界 tokens/s ≤ HBM_BW / model_weight_bytes；70B BF16 权重约 140 GB。




03｜Know-Why：为什么成立

     2. 现代 GPU FLOPS 增长往往快于 HBM 带宽增长，所以算力没有吃满时 HBM 已接近瓶颈。增大 batch 可以摊薄每 token 的

Q004 什么是 Roofline Model？如何用于分析 LLM inference？
难度 ★★★★★ · 章节 推理性能基本原理 · 关键词 roofline,profiling


    30 秒回答 Roofline 用算术强度 AI=FLOPs/Bytes 把 kernel 放到“带宽屋顶”或“算力屋顶”下。先估算某算子的 FLOPs 与
    HBM/缓存流量，再比较 AI 与设备 machine balance；这能回答应该优化访存、量化还是 Tensor Core/GEMM。




01｜考察本质
     这道题不是考名词定义，而是看你能否从系统资源出发解释：Roofline 用算术强度 AI=FLOPs/Bytes 把 kernel 放到“带宽屋
      顶”或“算力屋顶”下。先估算某算子的 FLOPs 与 HBM/缓存流量，再比较 AI 与设备 machine balance；这能回答应该优
      化访存、量化还是 Tensor Core/GEMM。
     面试中应先给结论，再给成本模型/瓶颈，再给适用边界。只背框架参数通常拿不到高分。

02｜关键公式 / 成本模型

    公式 Performance ≤ min(PeakFLOPS, AI×MemoryBandwidth)。临界 AI*=PeakFLOPS/MemoryBandwidth。




03｜Know-Why：为什么成立
     1. Roofline 用算术强度 AI=FLOPs/Bytes 把 kernel 放到“带宽屋顶”或“算力屋顶”下。先估算某算子的 FLOPs 与
      HBM/缓存流量，再比较 AI 与设备 machine balance
     2. 这能回答应该优化访存、量化还是 Tensor Core/GEMM。
     把这一结论放进 Roofline / 内存容量 / 调度 / 通信四类模型中检查，确认瓶颈是否真的位于关键路径，而不是只优化了一个
      非关键算子。

04｜工程场景

    现场推演 同一 Linear 在 Prefill 的 M 很大时更接近 GEMM，AI 提升；Decode 小 batch 时近似 GEMV/small GEMM，AI 明显
    下降。




05｜常见错误
     ✗ 只看 GPU Utilization=100% 就判断 compute-bound
     ✗ utilization 不等于 SM/Tensor/HBM 的有效利用率。

Q005 如何估算一个模型 Decode 的理论 token/s？
难度 ★★★★★ · 章节 推理性能基本原理 · 关键词 estimation,bandwidth


    30 秒回答 先做一阶 bandwidth model：模型权重字节、KV 读取字节、必要中间流量除以有效 HBM 带宽；再加入 batch 权
    重复用、TP collective、MoE all-to-all 和 kernel 效率，得到更可信的上界。估算的目的不是预测到个位数，而是识别最值得
    优化的资源。




01｜考察本质
     这道题不是考名词定义，而是看你能否从系统资源出发解释：先做一阶 bandwidth model：模型权重字节、KV 读取字节、

      界。估算的目的不是预测到个位数，而是识别最值得优化的资源。
     面试中应先给结论，再给成本模型/瓶颈，再给适用边界。只背框架参数通常拿不到高分。

    公式 t_token≈max(T_compute,T_HBM,T_comm)+T_overhead；batch=1 时 T_HBM≈bytes_read/effective_BW。




03｜Know-Why：为什么成立

     2. 再加入 batch 权重复用、TP collective、MoE all-to-all 和 kernel 效率，得到更可信的上界。估算的目的不是预测到个位

     把这一结论放进 Roofline / 内存容量 / 调度 / 通信四类模型中检查，确认瓶颈是否真的位于关键路径，而不是只优化了一个
      非关键算子。

05｜常见错误
     ✗ 把参数量×字节当作唯一流量
     ✗ 忽略 KV Cache、embedding/lm_head、量化 scale/dequant、TP 通信。

Q051 Tensor Parallelism 是什么？

    30 秒回答 TP 把同一层的大矩阵沿行/列切到多 GPU 并行，每层都需要某些 AllReduce/AllGather/ReduceScatter 来组合结

     4. 长期 scale-out 或模型结构调整。
     把这一结论放进 Roofline / 内存容量 / 调度 / 通信四类模型中检查，确认瓶颈是否真的位于关键路径，而不是只优化了一个
      非关键算子。

04｜工程场景

    现场推演 如果权重仅占 40% 显存、KV 55%，继续把权重从 INT8 降 INT4 只释放有限总空间，KV 优化更直接。




05｜常见错误
     ✗ 第一反应 empty_cache
     ✗ 它不能解决活跃 KV 的真实容量需求。
