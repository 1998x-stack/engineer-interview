Cosine Decay 为什么常见？Continued Pretraining 如何重设 LR？

定位：B 类等价追问题 · 难度 中 · 频率 ★★★★☆ 章节：目标函数、Optimizer 与 Training Recipe

1. 面试官为什么问

考察 schedule 的机制与阶段切换。

这道题真正区分的是：能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”。

本题的三层观察镜

  • 更新尺度：LR、batch、momentum 如何共同决定参数更新？
  • token 对齐：所有曲线是否按 consumed tokens 对齐？
  • 稳定性：warmup、clip、precision 与 optimizer state 如何相互作用？

2. 30 秒结论

阶段化训练时，LR schedule 应跟着数据分布与 optimizer state 一起设计。

30 秒版本的目标不是覆盖所有细节，而是先给出正确结论 + 最关键因果关系，让面试官知道你掌握主线。

3. 3 分钟标准回答

3.1 核心机制

Cosine decay 从 peak LR 平滑降到较小值，前期维持较强探索，后期逐渐减小更新幅度；它的优势更多是稳定、平滑和工程经验成熟，而非唯一理论最优。

3.2 关键 Trade-off / 边界

Continued pretraining 若发生明显 domain/context 分布变化，常需要新的 warmup/较低 peak LR；若完全延续原 optimizer states 和同分布数据，则重启大 LR 可能破坏已有能力。决策必须基于 phase transition 的强度。

4. 深度展开：从定义走向 Production

本题的深挖重点是：阶段化训练时，LR schedule 应跟着数据分布与 optimizer state 一起设计。

建议沿下面的因果链继续展开：

  1. 定义/状态语义：先把对象、tensor、数据分布或训练状态说准确；
  2. 机制：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
  3. 代价：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
  4. 可验证性：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
  5. 规模化边界：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

5. Know-how：如何落到实现与训练系统

  1. 动作 1：用 consumed tokens 记录每个 phase 的 LR，保证可重现。
  2. 动作 2：阶段切换前后对通用域和目标域都做 held-out loss，观察遗忘。
  3. 动作 3：小规模 sweep peak LR × warmup tokens。

优化曲线实验

保持模型与数据固定，比较 LR/batch/optimizer 变体的 token-normalized loss、grad norm、更新范数和稳定性。

  • 以 consumed tokens 而非 step 对齐。
  • 记录 effective batch tokens。
  • 避免只看最终 loss 而忽略 wall-clock。

回答方向：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

追问 2：为什么 CTP 常用较小 LR？

回答方向：从“旧方案瓶颈 → 阶段化训练时，LR schedule 应跟着数据分布与 optimizer state 一起设计。 → 新代价/边界条件”三段式回答。

追问 3：optimizer states 重置会产生什么影响？

回答方向：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

7. 常见失分点：为什么错

  • ❌ 把 continued pretraining 当成“接着跑原 schedule”或“永远重置 optimizer”的固定答案。
  • 改进：回到“阶段化训练时，LR schedule 应跟着数据分布与 optimizer state 一起设计。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
