Scaling Law 能否用于 Data Mixture 优化？

定位：B 类等价追问题 · 难度 难 · 频率 ★★★★☆ 章节：Scaling Law 与预算设计

1. 面试官为什么问

连接 scaling 与数据配方，是更偏研究型的开放题。

这道题真正区分的是：能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”。

本题的三层观察镜

  • 约束优化：到底固定的是 FLOPs、GPU-hours、成本还是推理预算？
  • 外推：小规模曲线在哪些条件下可以外推？
  • 等成本比较：Dense/MoE/不同数据 recipe 是否真的比较公平？

2. 30 秒结论

Data scaling 的终极问题不是“要多少数据”，而是“下一批 token 应来自哪里”。

30 秒版本的目标不是覆盖所有细节，而是先给出正确结论 + 最关键因果关系，让面试官知道你掌握主线。

3. 3 分钟标准回答

3.1 核心机制

可以把验证 loss 看作 N、各域 token D_i 或采样比例 p_i 的函数，通过多组小模型 mixture experiments 拟合不同 domain 的边际收益与 transfer effect。

3.2 关键 Trade-off / 边界

难点在于不同域之间不是独立可加：代码可能促进 reasoning，数学数据可能影响通用语言；高重复域还会出现收益饱和。因此需要多维实验和受控简化，而不是简单为每个域拟合一条曲线。

4. 深度展开：从定义走向 Production

本题的深挖重点是：Data scaling 的终极问题不是“要多少数据”，而是“下一批 token 应来自哪里”。

建议沿下面的因果链继续展开：

  1. 定义/状态语义：先把对象、tensor、数据分布或训练状态说准确；
  2. 机制：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
  3. 代价：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
  4. 可验证性：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
  5. 规模化边界：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

5. Know-how：如何落到实现与训练系统

  1. 动作 1：先选择 3-5 个高影响域做 mixture grid，避免维度爆炸。
  2. 动作 2：按 target capability 构造加权 validation objective。
  3. 动作 3：定期在训练阶段重新估计边际收益，支持 curriculum。

Scaling Proxy

用多个模型尺寸、Token 预算和 seed 构造 proxy grid，拟合 loss/compute 曲线，再用 hold-out 规模验证外推误差。

  • 拟合前确认数据 mixture 一致。
  • 报告置信区间/外推范围。
  • 区分训练 FLOPs optimum 与生命周期成本 optimum。

6. 高频追问与回答方向

追问 1：如何处理 domain 间 transfer？

回答方向：给出可执行步骤，并补充至少一个可观测指标和一个对照实验，避免只给概念。

追问 2：数据不足导致重复时 scaling 怎么变？

回答方向：给出可执行步骤，并补充至少一个可观测指标和一个对照实验，避免只给概念。

追问 3：mixture 优化目标是 loss 还是 benchmark？

回答方向：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

7. 常见失分点：为什么错

  • ❌ 假设每个域完全独立。
  • 改进：回到“Data scaling 的终极问题不是“要多少数据”，而是“下一批 token 应来自哪里”。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
