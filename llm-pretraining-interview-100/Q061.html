MoE 为什么能“总参数很大、每 Token FLOPs 较小”？

定位：B 类等价追问题 · 难度 易 · 频率 ★★★★★ 章节：Mixture-of-Experts

1. 面试官为什么问

MoE 基础，但必须说清 total vs activated parameters。

这道题真正区分的是：能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”。

本题的三层观察镜

  • 稀疏性：total params、active params 与 active FLOPs 如何区分？
  • 路由学习：负载均衡如何与语义 specialization 共存？
  • 通信：A2A 是否把算术节省吃掉？

2. 30 秒结论

MoE 用稀疏激活解耦“容量”和“每 token 计算”，但通信并不会随 FLOPs 自动消失。

30 秒版本的目标不是覆盖所有细节，而是先给出正确结论 + 最关键因果关系，让面试官知道你掌握主线。

3. 3 分钟标准回答

3.1 核心机制

MoE 将 dense FFN 替换为多个 experts 和 router。对每个 token，router 只选择 Top-k experts 执行，因此模型可以拥有很大的 total capacity，而单 token 只激活少量 expert parameters。

3.2 关键 Trade-off / 边界

Attention、embedding 等部分通常仍是 dense，因此 active FLOPs 不是简单用“激活参数/总参数比例”缩放全部网络。系统上还要付 routing 与通信成本。

4. 深度展开：从定义走向 Production

本题的深挖重点是：MoE 用稀疏激活解耦“容量”和“每 token 计算”，但通信并不会随 FLOPs 自动消失。

建议沿下面的因果链继续展开：

  1. 定义/状态语义：先把对象、tensor、数据分布或训练状态说准确；
  2. 机制：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
  3. 代价：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
  4. 可验证性：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
  5. 规模化边界：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

5. Know-how：如何落到实现与训练系统

  1. 动作 1：参数报告同时写 total params、active params/token、experts、top-k。
  2. 动作 2：统计真实 tokens/expert 与 active FLOPs。
  3. 动作 3：比较 dense baseline 时对齐总训练成本。

MoE 端到端实验

同时监控 routing entropy、expert load、dropped tokens、A2A 时间、expert GEMM 利用率和模型 loss。

  • 负载均衡不是唯一目标。
  • 按 activated FLOPs 和 wall-clock 做公平比较。
  • 检查跨节点 EP 的网络代价。

6. 高频追问与回答方向

追问 1：MoE 是否天然更快？

回答方向：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

追问 2：为什么 expert 主要替换 FFN？

回答方向：从“旧方案瓶颈 → MoE 用稀疏激活解耦“容量”和“每 token 计算”，但通信并不会随 FLOPs 自动消失。 → 新代价/边界条件”三段式回答。

追问 3：Top-k routing 是否可微？

回答方向：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

7. 常见失分点：为什么错

  • ❌ 把 total params 当每 token compute。
  • 改进：回到“MoE 用稀疏激活解耦“容量”和“每 token 计算”，但通信并不会随 FLOPs 自动消失。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
