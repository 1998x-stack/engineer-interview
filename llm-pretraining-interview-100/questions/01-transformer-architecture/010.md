# Q010. 给你 7B 参数预算，如何从零设计 Decoder-only 架构？

> **定位**：B 类等价追问题 · 难度 **难** · 频率 **★★★★★**
> 章节：[Transformer 与模型架构](./README.md)

## 1. 面试官为什么问

从单点知识升级到完整 architecture sizing，考察参数手算与硬件意识。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **数学尺度**：公式是否解释了数值尺度、梯度和表示能力？
- **结构成本**：参数量、FLOPs、KV Cache 与 kernel shape 如何变化？
- **生命周期**：训练架构选择会如何影响推理成本？

## 2. 30 秒结论

> 架构 sizing 是“参数预算 × 优化稳定 × 硬件效率 × 推理成本”的联合设计。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

先明确约束：参数预算、目标上下文、训练硬件、推理形态与词表。Dense Transformer 的粗略 block 参数可从 Attention 与 FFN 估算，再决定 depth/width、head_dim、GQA heads、SwiGLU intermediate。

### 3.2 关键 Trade-off / 边界

最优设计不是“复制 Llama”。层数/宽度影响优化与 GEMM shape；head_dim 影响 attention；GQA 影响 KV Cache；词表影响 embedding；TP 要求维度可整除。最终需要小规模 proxy runs 验证训练稳定与能力。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**面试现场可先写 P≈L·(P_attn+P_ffn)+P_embed，再逐项补 GQA/SwiGLU 修正。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：先做参数 spreadsheet，再做单卡/多卡 kernel benchmark。
2. **动作 2**：确保 hidden、heads、FFN dim、vocab size 对 TP 友好。
3. **动作 3**：用多个宽深比例的小模型做等 FLOPs 对照，而非只训练一个配置。

### 架构 Ablation

固定训练 Token 与大部分 recipe，只改变目标组件；同时比较 validation loss、下游能力、训练稳定性、参数/FLOPs 与推理成本。

- 不要只比较最终 benchmark；记录收敛速度。
- 至少做等参数或等 FLOPs 对照。
- 改变 head/hidden 等 shape 时同时检查 kernel efficiency。

## 6. 高频追问与回答方向

### 追问 1：为什么更深不一定更好？

**回答方向**：从“旧方案瓶颈 → 架构 sizing 是“参数预算 × 优化稳定 × 硬件效率 × 推理成本”的联合设计。 → 新代价/边界条件”三段式回答。

### 追问 2：如何反推 intermediate size？

**回答方向**：给出可执行步骤，并补充至少一个可观测指标和一个对照实验，避免只给概念。

### 追问 3：如果 serving KV Cache 是硬约束，你会改哪几项？

**回答方向**：先声明 dtype 与 batch/seq/layers/heads 等变量，再拆 weights、states、activation、buffer；最后说明分片轴。

## 7. 常见失分点：为什么错

- ❌ **直接报某开源模型配置，没有推导。**
  - 改进：回到“架构 sizing 是“参数预算 × 优化稳定 × 硬件效率 × 推理成本”的联合设计。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
- ❌ **只满足参数量，不看硬件矩阵形状与推理成本。**
  - 改进：回到“架构 sizing 是“参数预算 × 优化稳定 × 硬件效率 × 推理成本”的联合设计。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
