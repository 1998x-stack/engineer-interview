# Q013. 什么是 Tokenizer Fertility？为什么中文/多语言必须看？

> **定位**：B 类等价追问题 · 难度 **中** · 频率 **★★★☆☆**
> 章节：[Tokenizer 与预训练数据](./README.md)

## 1. 面试官为什么问

检验你是否会用可量化指标评估 tokenizer，而不是主观举例。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **分布**：每个过滤/采样动作怎样改变 p_train(x)？
- **信息密度**：单位 Token 的新颖性、正确性和覆盖度怎样衡量？
- **可追溯**：能否从训练异常追到具体 shard/domain/sample？

## 2. 30 秒结论

> 多语言 tokenizer 的公平性，本质上也是每种语言获得多少有效 compute 的问题。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

Fertility 可理解为一个自然语言单位平均被切成多少 token；工程上也常用 chars/token、bytes/token 等更稳定指标。若同一段中文在 tokenizer A 中需要 20 token、B 中需要 35 token，那么相同 32K token context 的实际信息容量差很多。

### 3.2 关键 Trade-off / 边界

多语言预训练中，高 fertility 的语言需要更多 compute 才能看见同样文本量，也更容易在 fixed context 下被截断，因此 tokenizer 会隐式改变语言间的训练资源分配。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**多语言 tokenizer 的公平性，本质上也是每种语言获得多少有效 compute 的问题。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：按语言、脚本、domain 建 tokenization dashboard。
2. **动作 2**：统计 p50/p95 而不只均值，识别异常文本。
3. **动作 3**：把 fertility 与 validation loss / downstream capability 做相关分析。

### 数据闭环

从样本级 provenance 到 domain-level held-out loss 建立闭环：数据变更必须能追溯到采样率、重复率、污染率和能力变化。

- 所有过滤规则可版本化。
- Mixture 调整用 proxy run 或受控消融。
- benchmark contamination 与训练质量评估分开。
