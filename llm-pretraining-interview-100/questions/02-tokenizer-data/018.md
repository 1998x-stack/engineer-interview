# Q018. 什么是 Benchmark Contamination？如何系统检测？

> **定位**：B 类等价追问题 · 难度 **难** · 频率 **★★★★★**
> 章节：[Tokenizer 与预训练数据](./README.md)

## 1. 面试官为什么问

考察评测可信度、数据治理与泄漏边界。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **分布**：每个过滤/采样动作怎样改变 p_train(x)？
- **信息密度**：单位 Token 的新颖性、正确性和覆盖度怎样衡量？
- **可追溯**：能否从训练异常追到具体 shard/domain/sample？

## 2. 30 秒结论

> 可信评测的前提是：不仅“题没见过”，连答案、解析和近似改写也要被审计。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

污染不只指 benchmark 问题原文进入训练集，还包括答案、解析、改写题、镜像页面和语义等价版本。Exact contamination 可用 n-gram/substrings；near duplicate 可用 MinHash/LSH；semantic contamination 可用 embedding retrieval 与人工复核。

### 3.2 关键 Trade-off / 边界

检测必须在数据版本层面可重现，并区分“题目本身”“答案/解析”“同源模板”。否则 benchmark 提升可能只是记忆而非泛化。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**可信评测的前提是：不仅“题没见过”，连答案、解析和近似改写也要被审计。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：建立 benchmark canonicalization：去格式、标准化数字/空白后再匹配。
2. **动作 2**：对候选污染输出 source URL、时间戳、相似片段供审计。
3. **动作 3**：报告 contamination rate，并在 clean subset 上重算评测。

### 数据闭环

从样本级 provenance 到 domain-level held-out loss 建立闭环：数据变更必须能追溯到采样率、重复率、污染率和能力变化。

- 所有过滤规则可版本化。
- Mixture 调整用 proxy run 或受控消融。
- benchmark contamination 与训练质量评估分开。
