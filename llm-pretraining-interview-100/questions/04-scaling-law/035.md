# Q035. 给定固定 GPU-hours，如何决定模型大小和 Token 数？

> **定位**：A 类高频真题型 · 难度 **难** · 频率 **★★★★★**
> 章节：[Scaling Law 与预算设计](./README.md)

## 1. 面试官为什么问

最接近真实预训练立项的系统设计题。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **约束优化**：到底固定的是 FLOPs、GPU-hours、成本还是推理预算？
- **外推**：小规模曲线在哪些条件下可以外推？
- **等成本比较**：Dense/MoE/不同数据 recipe 是否真的比较公平？

## 2. 30 秒结论

> 立项不是“选参数”，而是把算力、数据、架构和部署约束联合求解。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

先把 GPU 数、时长、峰值算力与预期 MFU 转成可用训练 FLOPs，再利用 scaling-law proxy runs 在候选 N/D 上寻找低 loss 区域。之后加入硬件约束：显存能否 fit、TP/PP 并行效率、数据供应和目标上下文。

### 3.2 关键 Trade-off / 边界

最终还要加入部署目标。一个数学上 compute-optimal 的超宽模型，可能因 TP 通信或推理成本而不是系统最优。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**先算得起，再算最优，最后算能不能稳定跑完。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：先做粗预算，再做 100M/1B 级 proxy grid。
2. **动作 2**：对每个候选记录预计训练天数、MFU、内存余量和推理成本。
3. **动作 3**：保留 5-10% 预算用于 pilot、失败恢复和关键 ablation。

### Scaling Proxy

用多个模型尺寸、Token 预算和 seed 构造 proxy grid，拟合 loss/compute 曲线，再用 hold-out 规模验证外推误差。

- 拟合前确认数据 mixture 一致。
- 报告置信区间/外推范围。
- 区分训练 FLOPs optimum 与生命周期成本 optimum。

## 6. 高频追问与回答方向

### 追问 1：如果数据只有 2T 高质量 token 怎么办？

**回答方向**：给出可执行步骤，并补充至少一个可观测指标和一个对照实验，避免只给概念。

### 追问 2：MFU 估错 10% 会怎样影响计划？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

### 追问 3：为什么系统最优可能偏离 scaling-law 最优？

**回答方向**：从“旧方案瓶颈 → 立项不是“选参数”，而是把算力、数据、架构和部署约束联合求解。 → 新代价/边界条件”三段式回答。

## 7. 常见失分点：为什么错

- ❌ **拿到预算直接选行业常见模型大小。**
  - 改进：回到“立项不是“选参数”，而是把算力、数据、架构和部署约束联合求解。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
