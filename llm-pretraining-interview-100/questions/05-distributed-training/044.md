# Q044. Pipeline Parallel 为什么有 Bubble？1F1B 如何改善？

> **定位**：A 类高频真题型 · 难度 **中** · 频率 **★★★★★**
> 章节：[分布式训练](./README.md)

## 1. 面试官为什么问

考察时间维度并行与 schedule。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **切分语义**：每个并行轴到底切哪个 tensor/state？
- **collective**：每一步需要 AG/RS/AR/A2A/P2P 中的什么？
- **拓扑**：高频通信是否留在 NVLink/NVSwitch 域？

## 2. 30 秒结论

> PP 的效率问题既有调度 bubble，也有 stage 负载不均。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

PP 将不同层放到不同 stage。流水线开始时后续 stage 等待输入，结束时前面 stage 等待反向传播，形成 warmup/drain bubble；microbatch 数越少、stage 越多，空闲比例通常越高。

### 3.2 关键 Trade-off / 边界

1F1B 在 warmup 后交替执行一个 forward 与一个 backward，使 activation 更快释放并提高 steady-state 利用率；interleaved/virtual pipeline 进一步细化 stage 以降低 bubble。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**PP 的效率问题既有调度 bubble，也有 stage 负载不均。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：画 Gantt chart 比文字更清楚。
2. **动作 2**：监控每 stage step time，避免一个 stage 计算量更大形成额外 bubble。
3. **动作 3**：microbatch 数既影响 bubble，也影响 global batch 与 activation memory。

### 分布式 Profiling

对每个并行轴画出“切分对象—rank 状态—collective—通信量—拓扑”，再用 trace 验证通信是否可 overlap。

- 先保证数值一致性再优化性能。
- 比较 per-rank peak memory 与 step time。
- 识别最慢 rank 和 collective hotspot。
