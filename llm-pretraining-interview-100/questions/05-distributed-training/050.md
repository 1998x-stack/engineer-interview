# Q050. 给你 1024 张 GPU，TP/PP/DP/CP/EP 怎么设计？

> **定位**：A 类高频真题型 · 难度 **难** · 频率 **★★★★★**
> 章节：[分布式训练](./README.md)

## 1. 面试官为什么问

综合考察显存约束、通信频率、拓扑和模型形态。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **切分语义**：每个并行轴到底切哪个 tensor/state？
- **collective**：每一步需要 AG/RS/AR/A2A/P2P 中的什么？
- **拓扑**：高频通信是否留在 NVLink/NVSwitch 域？

## 2. 30 秒结论

> 大规模并行设计顺序：先满足 fit，再减少高频通信，最后最大化可扩展的数据并行。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

先用模型是否能 fit 决定最小模型并行：单层/大矩阵需要 TP；深度或总参数需要 PP；长序列 activation 需要 CP；MoE experts 需要 EP。满足这些约束后，剩余资源尽量给 DP，因为 DP 通常通信频率相对低且吞吐扩展更自然。

### 3.2 关键 Trade-off / 边界

并行度不是整数分解游戏。要考虑 TP/EP 的交互、PP stage balance、网络拓扑与 microbatch。框架中某些轴可能共享/折叠，必须按实际并行 group 定义核对。

### 核心公式

```text
N_GPU ≈ TP × PP × CP × EP × DP（具体轴关系以框架为准）
```

> 面试时不要只写公式。要逐个解释符号、shape/量纲，以及公式如何导出工程结论。

## 4. 深度展开

### 1024 GPU 的决策顺序
先求**可行解**再求**最优解**：
1. 单层/单 expert 是否能 fit，决定 TP/ETP 下限；
2. 深度是否需要 PP；
3. 长序列 activation 是否需要 CP；
4. MoE experts 是否需要 EP；
5. 剩余设备尽量给 DP；
6. 用真实网络拓扑重新映射，并 profile 通信 overlap。

总 GPU 数的乘法关系只是约束，不是优化策略本身。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：先写 GPU factorization，再画 node/rack 映射。
2. **动作 2**：用 profiler 比较 compute、collective、bubble 三类时间。
3. **动作 3**：从最小必要 TP/PP/CP/EP 出发，不盲目把 model parallel 开大。

### 分布式 Profiling

对每个并行轴画出“切分对象—rank 状态—collective—通信量—拓扑”，再用 trace 验证通信是否可 overlap。

- 先保证数值一致性再优化性能。
- 比较 per-rank peak memory 与 step time。
- 识别最慢 rank 和 collective hotspot。

## 6. 高频追问与回答方向

### 追问 1：为什么先最大化 DP 常是好策略？

**回答方向**：从“旧方案瓶颈 → 大规模并行设计顺序：先满足 fit，再减少高频通信，最后最大化可扩展的数据并行。 → 新代价/边界条件”三段式回答。

### 追问 2：如果 128K context，CP 应怎样介入？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

### 追问 3：MoE attention 与 expert 能否用不同 TP？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

- ❌ **只给 TP=8、PP=16、DP=8 一组数字，不说明模型和拓扑。**
