# Q057. 什么是 Arithmetic Intensity？为什么 LLM 工程必须懂？

> **定位**：B 类等价追问题 · 难度 **中** · 频率 **★★★★☆**
> 章节：[显存、数值精度与性能](./README.md)

## 1. 面试官为什么问

把算法 FLOPs 与真实硬件瓶颈连接起来。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **bytes**：每种 state/activation 实际占多少字节？
- **IO**：瓶颈是计算还是 HBM/网络搬运？
- **峰值**：steady-state memory 与 transient peak 是否分开？

## 2. 30 秒结论

> FLOPs 告诉你算多少，Arithmetic Intensity 告诉你更可能卡在算力还是搬数据。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

Arithmetic intensity = 执行 FLOPs / 从内存层级搬运的 bytes。若 AI 低，性能更受内存带宽限制；AI 高且矩阵足够大，才更可能接近 compute-bound。

### 3.2 关键 Trade-off / 边界

这解释了为什么某个 FLOPs 更少的实现不一定更快：它可能产生更多 HBM traffic、小 GEMM 或同步。Roofline 思维比只看理论 FLOPs 更接近端到端训练。

### 核心公式

```text
AI = FLOPs / bytes moved
```

> 面试时不要只写公式。要逐个解释符号、shape/量纲，以及公式如何导出工程结论。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**FLOPs 告诉你算多少，Arithmetic Intensity 告诉你更可能卡在算力还是搬数据。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：profile kernel 的 achieved FLOPs、HBM bandwidth 与 occupancy。
2. **动作 2**：通过 tiling/fusion/batching 提高数据复用。
3. **动作 3**：将 kernel 优化最终映射到 step time / tokens/s。

### Roofline / Memory Accounting

先做理论 bytes/FLOPs 预算，再用 profiler、memory snapshot 和 kernel trace 对账。

- 把参数/梯度/优化器/activation/临时 buffer 分开。
- 注明 dtype 与分片假设。
- 区分理论峰值与可持续吞吐。
