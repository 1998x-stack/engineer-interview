# Q066. Shared Expert 的意义是什么？

> **定位**：B 类等价追问题 · 难度 **中** · 频率 **★★★★☆**
> 章节：[Mixture-of-Experts](./README.md)

## 1. 面试官为什么问

考察 MoE 中通用知识与专业化的职责分配。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **稀疏性**：total params、active params 与 active FLOPs 如何区分？
- **路由学习**：负载均衡如何与语义 specialization 共存？
- **通信**：A2A 是否把算术节省吃掉？

## 2. 30 秒结论

> Shared expert 用固定 compute 承担公共能力，换取 routed expert 更充分的 specialization。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

Shared expert 对所有 token 都激活，可承担通用变换；routed experts 则按 token 选择，负责更细的专业化。这样可减少每个 routed expert 重复学习通用模式的压力。

### 3.2 关键 Trade-off / 边界

但 shared expert 增加固定 active compute，太大又会削弱稀疏优势。是否采用、容量多大需要按质量与 FLOPs 验证。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**Shared expert 用固定 compute 承担公共能力，换取 routed expert 更充分的 specialization。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：分开统计 shared/routed expert 的 FLOPs 与参数。
2. **动作 2**：用表示/路由分析检查 routed experts 是否真的更专业。
3. **动作 3**：比较相同 active FLOPs 下有无 shared expert。

### MoE 端到端实验

同时监控 routing entropy、expert load、dropped tokens、A2A 时间、expert GEMM 利用率和模型 loss。

- 负载均衡不是唯一目标。
- 按 activated FLOPs 和 wall-clock 做公平比较。
- 检查跨节点 EP 的网络代价。

## 6. 高频追问与回答方向

### 追问 1：Shared expert 会不会成为新的 dense bottleneck？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

### 追问 2：多个 shared experts 如何设计？

**回答方向**：给出可执行步骤，并补充至少一个可观测指标和一个对照实验，避免只给概念。

### 追问 3：为什么通用知识不能完全由 routed experts 学？

**回答方向**：从“旧方案瓶颈 → Shared expert 用固定 compute 承担公共能力，换取 routed expert 更充分的 specialization。 → 新代价/边界条件”三段式回答。

## 7. 常见失分点：为什么错

- ❌ **把 shared expert 说成“永远更好”。**
  - 改进：回到“Shared expert 用固定 compute 承担公共能力，换取 routed expert 更充分的 specialization。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
