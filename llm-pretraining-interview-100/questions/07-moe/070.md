# Q070. Qwen3 MoE 与 DeepSeek-V3 MoE 应该怎样专业比较？

> **定位**：A 类高频真题型 · 难度 **难** · 频率 **★★★★★**
> 章节：[Mixture-of-Experts](./README.md)

## 1. 面试官为什么问

公开面经直接出现类似比较题，考察能否超越参数背诵。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **稀疏性**：total params、active params 与 active FLOPs 如何区分？
- **路由学习**：负载均衡如何与语义 specialization 共存？
- **通信**：A2A 是否把算术节省吃掉？

## 2. 30 秒结论

> 比较 MoE 的正确顺序：容量 → 激活 → 路由 → 平衡 → 通信 → 实际成本。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

比较框架应至少包括：total/activated params、expert 数与 top-k、expert granularity、shared experts、router/负载均衡、attention 架构、训练目标与系统通信。Qwen3 官方资料披露其 MoE 版本使用 128 experts、每 token 激活 8；DeepSeek-V3 报告为 671B total、约 37B active，并强调 DeepSeekMoE、aux-loss-free balancing 与 MTP。

### 3.2 关键 Trade-off / 边界

不要只背“谁有多少专家”。架构差异最终要落到 capacity、active FLOPs、routing quality、A2A pressure、training stability 与 serving cost。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**这类“模型对比题”不是记忆题；面试官真正看你能否建立统一分析坐标系。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：先做统一字段比较表，避免不同报告口径混杂。
2. **动作 2**：所有数字注明具体 model variant。
3. **动作 3**：将算法差异映射到可观测系统指标。

### MoE 端到端实验

同时监控 routing entropy、expert load、dropped tokens、A2A 时间、expert GEMM 利用率和模型 loss。

- 负载均衡不是唯一目标。
- 按 activated FLOPs 和 wall-clock 做公平比较。
- 检查跨节点 EP 的网络代价。

## 6. 高频追问与回答方向

### 追问 1：为什么 expert 数不能直接表示 capacity？

**回答方向**：从“旧方案瓶颈 → 比较 MoE 的正确顺序：容量 → 激活 → 路由 → 平衡 → 通信 → 实际成本。 → 新代价/边界条件”三段式回答。

### 追问 2：两者负载均衡思路有何不同？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

### 追问 3：Attention 结构会怎样影响整体 active compute？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

## 7. 常见失分点：为什么错

- ❌ **混淆不同 Qwen3 variant。**
  - 改进：回到“比较 MoE 的正确顺序：容量 → 激活 → 路由 → 平衡 → 通信 → 实际成本。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
- ❌ **只比较总参数和 benchmark。**
  - 改进：回到“比较 MoE 的正确顺序：容量 → 激活 → 路由 → 平衡 → 通信 → 实际成本。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
