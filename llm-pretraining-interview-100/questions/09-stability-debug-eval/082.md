# Q082. 如何区分 Bad Batch 与 Optimizer Instability？

> **定位**：B 类等价追问题 · 难度 **难** · 频率 **★★★★★**
> 章节：[训练稳定性、Debug 与评测](./README.md)

## 1. 面试官为什么问

故障定位中最实用的因果实验题。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **first bad event**：能否定位第一个异常 step/rank/tensor？
- **可复现**：同 checkpoint+batch 是否重现？
- **因果验证**：修复是否有最小变量对照和回归？

## 2. 30 秒结论

> 最强诊断工具是交叉 replay：把数据和模型状态拆开做因果测试。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

从 spike 前 checkpoint 固定 RNG 与数据顺序，重放异常 batch。若每次都在相同位置出现异常，而换正常 batch 恢复，则强烈支持 data/forward 特异问题；若不同 batch 都逐步失稳，说明参数/optimizer state 已进入不稳定区域。

### 3.2 关键 Trade-off / 边界

还可将异常 batch 送入较早 checkpoint，或将正常 batch 送入临近 checkpoint，形成 2×2 交叉实验，把“数据因素”和“状态因素”解耦。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**最强诊断工具是交叉 replay：把数据和模型状态拆开做因果测试。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：保存 batch hash/source/length/token stats。
2. **动作 2**：做 checkpoint×batch 交叉矩阵并比较 loss/gradnorm。
3. **动作 3**：确定是否 deterministic，排查 fused kernel/硬件随机故障。

### 故障可复现闭环

锁定 first bad step，保存 batch/rank/RNG/checkpoint，执行 deterministic replay，再用最小变量实验定位根因。

- 先定位，不要先“调参试试”。
- 保留正常 step 对照。
- 修复后做回归与长期稳定性验证。

## 6. 高频追问与回答方向

### 追问 1：异常 batch 一定要删除吗？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

### 追问 2：如果 bad batch 只在大模型上炸怎么办？

**回答方向**：给出可执行步骤，并补充至少一个可观测指标和一个对照实验，避免只给概念。

### 追问 3：如何定位 batch 内具体 sample？

**回答方向**：给出可执行步骤，并补充至少一个可观测指标和一个对照实验，避免只给概念。

## 7. 常见失分点：为什么错

- ❌ **仅凭“这一 step 数据看起来怪”下结论。**
  - 改进：回到“最强诊断工具是交叉 replay：把数据和模型状态拆开做因果测试。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
