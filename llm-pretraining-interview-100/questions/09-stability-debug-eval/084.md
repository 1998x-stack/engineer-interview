# Q084. Overall Loss 在降，但 Math/Code Benchmark 不涨，为什么？

> **定位**：B 类等价追问题 · 难度 **中** · 频率 **★★★★★**
> 章节：[训练稳定性、Debug 与评测](./README.md)

## 1. 面试官为什么问

考察平均 loss 掩盖 domain 能力的现象。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **first bad event**：能否定位第一个异常 step/rank/tensor？
- **可复现**：同 checkpoint+batch 是否重现？
- **因果验证**：修复是否有最小变量对照和回归？

## 2. 30 秒结论

> 总体 loss 是加权平均；预训练能力必须按目标 domain 拆开看。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

总体 token loss 被高占比、较易 domain 主导。若 Web 通用文本占绝大多数，哪怕 math/code 的 loss 停滞，总 loss 仍可能稳定下降；离散 benchmark 还存在阈值与格式影响。

### 3.2 关键 Trade-off / 边界

正确做法是维护 domain-conditioned validation loss、能力 proxy 和数据 consumed tokens，观察目标域边际收益。如果目标能力停滞，再判断 mixture、数据难度、tokenizer 或模型容量。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**总体 loss 是加权平均；预训练能力必须按目标 domain 拆开看。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：为 math/code/语言分别建 held-out validation。
2. **动作 2**：对每个阶段记录 mixture 与实际 sample consumption。
3. **动作 3**：结合 loss 与 benchmark，避免只盯一个。

### 故障可复现闭环

锁定 first bad step，保存 batch/rank/RNG/checkpoint，执行 deterministic replay，再用最小变量实验定位根因。

- 先定位，不要先“调参试试”。
- 保留正常 step 对照。
- 修复后做回归与长期稳定性验证。

## 6. 高频追问与回答方向

### 追问 1：domain loss 能直接跨域比较吗？

**回答方向**：先统一比较维度（质量、FLOPs、memory、communication、wall-clock），再逐项对齐，避免只比一个指标。

### 追问 2：增加 math 比例会伤通用能力吗？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

### 追问 3：如何判断是数据不够还是模型容量不够？

**回答方向**：给出可执行步骤，并补充至少一个可观测指标和一个对照实验，避免只给概念。

## 7. 常见失分点：为什么错

- ❌ **因为 benchmark 不涨就立刻加数据比例。**
  - 改进：回到“总体 loss 是加权平均；预训练能力必须按目标 domain 拆开看。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
