# Q089. Checkpoint 应保存什么，才能做到真正可恢复？

> **定位**：B 类等价追问题 · 难度 **难** · 频率 **★★★★★**
> 章节：[训练稳定性、Debug 与评测](./README.md)

## 1. 面试官为什么问

考察预训练的状态机，而非只保存模型权重。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **first bad event**：能否定位第一个异常 step/rank/tensor？
- **可复现**：同 checkpoint+batch 是否重现？
- **因果验证**：修复是否有最小变量对照和回归？

## 2. 30 秒结论

> Checkpoint 的定义是“完整训练状态的可验证快照”，不是一堆权重文件。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

完整恢复通常需要模型参数、optimizer states、LR scheduler、RNG states、data loader/shuffle state、consumed tokens/step、并行拓扑与 scaler 等。否则 resume 后虽然权重一样，后续数据和随机性可能不同。

### 3.2 关键 Trade-off / 边界

大规模 checkpoint 还涉及分片格式、异步写、原子提交、校验和与跨并行度加载。可恢复性必须做定期演练。

## 4. 深度展开：从定义走向 Production

本题的深挖重点是：**Checkpoint 的定义是“完整训练状态的可验证快照”，不是一堆权重文件。**

建议沿下面的因果链继续展开：

1. **定义/状态语义**：先把对象、tensor、数据分布或训练状态说准确；
2. **机制**：解释为什么该设计会改变 loss、memory、FLOPs、通信或稳定性；
3. **代价**：指出它牺牲了什么，不把工程 trick 说成“免费午餐”；
4. **可验证性**：说明你会用什么指标、profile 或 ablation 判断结论是否成立；
5. **规模化边界**：把 1 GPU/小模型结论推进到千卡、长序列或 MoE 场景。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：采用 manifest + checksum，最后原子标记 checkpoint 完成。
2. **动作 2**：训练中定期做 disaster-recovery drill。
3. **动作 3**：保存数据 cursor/seed，验证 resume 后若干 step 可复现。

### 故障可复现闭环

锁定 first bad step，保存 batch/rank/RNG/checkpoint，执行 deterministic replay，再用最小变量实验定位根因。

- 先定位，不要先“调参试试”。
- 保留正常 step 对照。
- 修复后做回归与长期稳定性验证。

## 6. 高频追问与回答方向

### 追问 1：改变 DP/TP 后能否加载？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

### 追问 2：异步 checkpoint 如何保证一致性？

**回答方向**：给出可执行步骤，并补充至少一个可观测指标和一个对照实验，避免只给概念。

### 追问 3：只保存 consumed step 为什么不够？

**回答方向**：从“旧方案瓶颈 → Checkpoint 的定义是“完整训练状态的可验证快照”，不是一堆权重文件。 → 新代价/边界条件”三段式回答。

## 7. 常见失分点：为什么错

- ❌ **checkpoint 文件存在就认为可恢复。**
  - 改进：回到“Checkpoint 的定义是“完整训练状态的可验证快照”，不是一堆权重文件。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
