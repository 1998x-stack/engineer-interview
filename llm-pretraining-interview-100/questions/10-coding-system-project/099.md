# Q099. 面试官问“你真的从 0 预训练过模型吗？”怎样证明？

> **定位**：A 类高频真题型 · 难度 **中** · 频率 **★★★★★**
> 章节：[手撕、系统设计与项目拷打](./README.md)

## 1. 面试官为什么问

项目真实性拷打，不靠术语靠可核对细节。

这道题真正区分的是：**能否把“知道概念”推进到“解释机制、量化成本、落到训练系统并设计验证”**。

### 本题的三层观察镜

- **正确性**：代码/公式/系统是否在边界条件下仍正确？
- **量化**：参数、显存、吞吐、成本是否可手算/实测？
- **证明**：项目贡献是否有对照实验和可归因结果？

## 2. 30 秒结论

> 项目可信度来自可核对的数字、失败案例和个人决策，而不是工具名。

30 秒版本的目标不是覆盖所有细节，而是先给出**正确结论 + 最关键因果关系**，让面试官知道你掌握主线。

## 3. 3 分钟标准回答

### 3.1 核心机制

真正做过的人应自然给出：参数规模、训练 token、GPU 型号/数量、sequence length、global batch tokens、peak LR/warmup、optimizer、precision、TP/PP/DP/CP/EP、MFU/tokens/s、checkpoint cadence、最终 validation loss。

### 3.2 关键 Trade-off / 边界

更有说服力的是讲一个真实事故：什么时候 OOM/loss spike/straggler，如何定位、改了什么、吞吐/质量变化多少。具体数字和因果链比“熟悉 Megatron”有力得多。

## 4. 深度展开

### “做过”的证据链
至少准备一张表：参数量、训练 tokens、GPU 类型/数量、seq len、global batch tokens、parallel mapping、precision、peak LR、warmup、MFU/tokens-s、checkpoint 周期、最大事故、最终验证指标。任何数字都要能继续解释“为什么是这个值”。

## 5. Know-how：如何落到实现与训练系统

1. **动作 1**：提前为自己项目做一张 one-page fact sheet。
2. **动作 2**：所有指标准备“定义与口径”，防止追问时自相矛盾。
3. **动作 3**：区分团队工作与个人负责模块。

### 白板到 Production

要求答案同时包含正确性、复杂度、测试、边界条件、工程约束和量化结果。

- 代码题写 shape/assert/unit test。
- 设计题先声明约束。
- 项目题必须给数字和对照。

## 6. 高频追问与回答方向

### 追问 1：你亲手改了哪段 pipeline？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

### 追问 2：MFU 怎么算的？

**回答方向**：给出可执行步骤，并补充至少一个可观测指标和一个对照实验，避免只给概念。

### 追问 3：如果重来一次你会改什么？

**回答方向**：回到定义、数学/状态语义、工程代价和可验证实验四层作答。

## 7. 常见失分点：为什么错

- ❌ **只列技术栈。**
  - 改进：回到“项目可信度来自可核对的数字、失败案例和个人决策，而不是工具名。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。
- ❌ **把团队成果全部说成个人成果。**
  - 改进：回到“项目可信度来自可核对的数字、失败案例和个人决策，而不是工具名。”这一主线，并补充可量化的状态/公式/实验，而不是只给结论。

## 8. 面试评分 Rubric

| 层级 | 表现 |
|---|---|
| 0 — 不合格 | 只会名词或结论，定义/公式/状态语义存在明显错误。 |
| 1 — 基础 | 能复述：项目可信度来自可核对的数字、失败案例和个人决策，而不是工具名。 |
| 2 — 良好 | 能解释 Why + How，回答至少一个追问，并指出主要 trade-off。 |
| 3 — 强 | 能手算/画通信或数据流/给出实验设计，把算法与系统联系起来。 |
| 4 — 研究/Production | 能说明失效边界、诊断指标、等成本对照和规模化约束，并结合真实项目给数字。 |

## 9. 自测与白板练习

闭卷完成下面练习，建议每题控制在 5–10 分钟：

1. 你亲手改了哪段 pipeline？
2. MFU 怎么算的？
3. 如果重来一次你会改什么？
4. 把答案写成可运行代码/可核算公式/可量化项目复盘之一。
