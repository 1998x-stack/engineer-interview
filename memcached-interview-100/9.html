为什么 struct item 是 Memcached 最核心的数据结构？

必刷题 · P0 · ★★★★★ · Item 与 SET/GET 源码链路
本文是 PDF 对应题目的扩展版：保留原答案，并补充源码、复杂度、并发不变量、生产实践与实验。

题目

为什么 struct item 是 Memcached 最核心的数据结构？

面试官在考什么

这道题用于判断候选人是否真正理解 Item 生命周期、publication、refcount 与源码热路径。

面试官通常不会满足于“术语定义”，而会沿着 为什么 struct item 是 Memcached 最核心的数据结构？ 继续追问到：状态如何变化、哪个模块拥有这份状态、并发下怎样保持不变量、生产中用什么指标证明判断。优秀回答应先给 30 秒结论，再主动给出一个反例或故障场景。

30-90 秒标准回答

一个 item 同时承载 KV 数据、Hash 冲突链节点、LRU 双向链节点及 Slab class/lifetime metadata，是四大子系统的交汇点。

面试时建议先讲上面这句话，再根据追问选择展开源码或生产侧影响，不要一开始就陷入函数细节。

心智模型

对象生命周期： 核心不变量是 construct-before-publish 与 unlink-before-free。Item 把 Hash 索引、LRU 生命周期、Slab 物理内存和并发引用连接起来。

flowchart TD
  A[SET header] --> B[item_alloc]
  B --> C[Slab chunk]
  C --> D[read value into ITEM_data]
  D --> E[store_item]
  E --> F[assoc_find old]
  F --> G[do_item_link / replace]
  G --> H[assoc_insert]
  G --> I[item_link_q]

深度机制

1. next/prev 受 LRU lock 保护；h_next 属于 hash chain。

h_next 属于哈希冲突链，和 LRU 的 next/prev 是两套不同索引；同一个 Item 同时被多种数据结构引用，是源码阅读的关键。

2. refcount 把“逻辑删除”与“物理释放”分离。

refcount 解决的是对象“仍被谁使用”的问题。一个 item 可以已经从 Hash/LRU 逻辑删除，但只要其他线程还持有引用，就不能把底层 chunk 重新分配。

3. ITEM_key/ITEM_data 通过连续内存布局减少额外对象分配。

从“对象生命周期”看，这一结论的重点不是记住术语，而是明确职责边界和失败方式。核心不变量是 construct-before-publish 与 unlink-before-free。Item 把 Hash 索引、LRU 生命周期、Slab 物理内存和并发引用连接起来。

系统不变量

  • 不变量 1： 未完整构造的 Item 不能被 Hash 发布。
  • 不变量 2： 逻辑 unlink 后，只要 refcount 未归零就不能物理复用 chunk。

这些不变量比记忆具体函数名更稳定。版本升级可能调整代码组织，但破坏这些约束通常意味着正确性或生命周期出现问题。

复杂度与性能分析

  • 单次操作通常很便宜，生产尾延迟更多由网络 RTT、序列化、锁等待和 miss 路径决定。
  • 面试回答要把“算法复杂度”和“系统成本模型”分开。

进一步分析时要区分三个层面：算法复杂度（如 Hash 平均 O(1)）、微架构成本（cache miss、pointer chasing、cache-line bouncing）和 系统成本（RTT、序列化、回源）。高水平回答会主动指出这三者不是一回事。

工程与生产实践

  1. 先确认语义边界： 本题讨论的是 Item 生命周期、publication、refcount 与源码热路径，先区分 server 内部机制、客户端路由和应用回源三层，避免跨层归因。
  2. 把关键路径画出来： 对 为什么 struct item 是 Memcached 最核心的数据结构？ 至少能指出输入、关键状态、输出以及失败路径；如果涉及 Item，要明确 Hash/LRU/Slab/refcount 中哪些会变化。
  3. 用指标证伪： 用 gdb 打印同一 item 的地址、h_next、next、prev、refcount，并在 SET→GET→DELETE 中观察状态变化。
  4. 准备一个故障反例： 任何一条删除路径若只从 Hash 删除而忘记 LRU，或只从 LRU 删除而保留 Hash，都可能产生 zombie pointer 或逻辑不可达内存。
  5. 版本意识： 本仓库源码锚定 Memcached 1.6.45；默认参数与现代特性应以该版本官方源码/文档为准。

常见易错点

若只看 key/value 字段，就错过了 Memcached 的系统设计核心。

再补充两个通用陷阱：

  • 把“默认值”说成“协议永远固定值”；例如 item size、线程数等都应区分默认配置与不可变约束。
  • 把“当前实现细节”说成“KV cache 必然原理”；面试中应先讲不变量，再讲 Memcached 的具体实现。

专家级展开（V2）

A. 从第一性原理推导

struct item 是“一个对象同时属于多套索引”的连接点：h_next 服务 Hash collision chain，next/prev 服务 LRU，slabs_clsid 指向内存 class，refcount 管理并发生命周期。

这道题建议使用“状态 → 所有者 → 转移条件 → 失败后果”四步法推导，而不是背结论。先确定哪份状态是核心，再问由哪个模块维护，随后说明状态何时迁移，最后指出违反不变量会表现为什么 bug 或性能问题。

B. 关键源码符号与阅读顺序

  • struct _stritem
  • h_next
  • next
  • prev
  • refcount
  • slabs_clsid
  • it_flags

git grep -n "\bprev\b" -- proto_text.c proto_parser.c items.c thread.c assoc.c slabs.c

阅读函数时至少记录 5 个问题：入参中的 key/hash/item 是谁创建的、当前持有哪些锁、item 是否已 ITEM_LINKED、refcount 谁持有、失败路径最终由谁释放资源。

C. 边界条件与反例

不要把 item 看成只有 key/value 的 DTO；一旦忽略多索引身份，就无法解释 unlink、eviction、refcount 或为什么不能立即 free。

面试中主动讲边界条件很加分，因为它能证明你区分了“默认实现”“协议语义”“架构经验”和“数学近似”。尤其要避免把平均 O(1)、默认 1MB、client-side hashing 等表述成无条件真理。

D. 生产故障推演

任何一条删除路径若只从 Hash 删除而忘记 LRU，或只从 LRU 删除而保留 Hash，都可能产生 zombie pointer 或逻辑不可达内存。

遇到这类问题时，建议把故障链写成：

触发条件 → Memcached 内部状态变化 → HIT/MISS/P99 变化 → origin/网络/CPU 后果 → 保护或恢复动作

这样回答能自然从源码层过渡到生产系统，而不是把“源码题”和“系统设计题”割裂开。

E. 定量分析 / 可验证指标

用 gdb 打印同一 item 的地址、h_next、next、prev、refcount，并在 SET→GET→DELETE 中观察状态变化。

工程上至少给出一个可以测量或计算的量。没有数字的“性能更好”“内存更省”“更稳定”通常无法指导容量规划，也很难在故障现场验证。
