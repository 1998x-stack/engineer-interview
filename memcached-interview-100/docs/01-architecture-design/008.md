# 第 008 题 · 为什么 Memcached 不支持 SQL、范围查询和 JOIN？

> **P0** · ★★★★☆ · 基础架构与设计哲学  
> 本文是 PDF 对应题目的扩展版：保留原答案，并补充源码、复杂度、并发不变量、生产实践与实验。

## 题目

**为什么 Memcached 不支持 SQL、范围查询和 JOIN？**

## 面试官在考什么

这道题用于判断候选人是否真正理解 **架构边界、KV 语义与“为什么做减法”**。

面试官通常不会满足于“术语定义”，而会沿着 `为什么 Memcached 不支持 SQL、范围查询和 JOIN？` 继续追问到：**状态如何变化、哪个模块拥有这份状态、并发下怎样保持不变量、生产中用什么指标证明判断**。优秀回答应先给 30 秒结论，再主动给出一个反例或故障场景。

## 30-90 秒标准回答

> 核心索引只优化完整 key 等值查找；加入二级索引、范围树、优化器与事务会改变系统复杂度和性能模型。

面试时建议先讲上面这句话，再根据追问选择展开源码或生产侧影响，不要一开始就陷入函数细节。

## 心智模型

**系统边界：** 把 Memcached 看成“网络接口 + 本地 KV 内核”。关键不是 API 多，而是主动缩小问题：完整 key 精确查找、数据可丢、价值可重建。

```mermaid
flowchart LR
  C[Client] --> N[Network / Protocol]
  N --> H[Assoc / Hash]
  H --> I[Item]
  I --> S[Slab]
  I --> L[LRU / TTL]
```

## 深度机制

### 1. HashTable 对精确 key 访问最自然。

哈希层需要同时考虑分布质量、计算成本、冲突链和扩容；“能正确 hash”只是第一层要求，生产性能更依赖均匀性与访问局部性。
### 2. 范围查询需要有序结构，如 B+Tree/LSM 的额外索引。

从“系统边界”看，这一结论的重点不是记住术语，而是明确职责边界和失败方式。把 Memcached 看成“网络接口 + 本地 KV 内核”。关键不是 API 多，而是主动缩小问题：完整 key 精确查找、数据可丢、价值可重建。
### 3. “不支持”本身就是性能设计。

从“系统边界”看，这一结论的重点不是记住术语，而是明确职责边界和失败方式。把 Memcached 看成“网络接口 + 本地 KV 内核”。关键不是 API 多，而是主动缩小问题：完整 key 精确查找、数据可丢、价值可重建。

## 系统不变量

- **不变量 1：** Cache 数据必须可重建；MISS 不是异常。
- **不变量 2：** Key 是服务端唯一主要查询入口；value 对服务端近似 opaque bytes。

这些不变量比记忆具体函数名更稳定。版本升级可能调整代码组织，但破坏这些约束通常意味着正确性或生命周期出现问题。

## 复杂度与性能分析

- 单次操作通常很便宜，生产尾延迟更多由网络 RTT、序列化、锁等待和 miss 路径决定。
- 面试回答要把“算法复杂度”和“系统成本模型”分开。

进一步分析时要区分三个层面：**算法复杂度**（如 Hash 平均 O(1)）、**微架构成本**（cache miss、pointer chasing、cache-line bouncing）和 **系统成本**（RTT、序列化、回源）。高水平回答会主动指出这三者不是一回事。

## 工程与生产实践

1. **先确认语义边界：** 本题讨论的是 架构边界、KV 语义与“为什么做减法”，先区分 server 内部机制、客户端路由和应用回源三层，避免跨层归因。
2. **把关键路径画出来：** 对 `为什么 Memcached 不支持 SQL、范围查询和 JOIN？` 至少能指出输入、关键状态、输出以及失败路径；如果涉及 Item，要明确 Hash/LRU/Slab/refcount 中哪些会变化。
3. **用指标证伪：** 判断是否适合缓存时问：结果能否被一个稳定 key 唯一定位？失效集合是否可控？重建成本是否明确？
4. **准备一个故障反例：** 为了模拟“按用户所有订单查询”，把每个查询结果缓存成一个 key 可以很快，但任何订单变化都要正确失效相关聚合 key，复杂度会转移到 invalidation。
5. **版本意识：** 本仓库源码锚定 Memcached `1.6.45`；默认参数与现代特性应以该版本官方源码/文档为准。

## 专家级展开（V2）

### A. 从第一性原理推导

Hash 索引擅长 exact-key lookup，而 SQL/范围/JOIN 需要 secondary index、排序结构、查询规划与一致性维护；Memcached 的性能来自明确拒绝这些能力。

这道题建议使用“**状态 → 所有者 → 转移条件 → 失败后果**”四步法推导，而不是背结论。先确定哪份状态是核心，再问由哪个模块维护，随后说明状态何时迁移，最后指出违反不变量会表现为什么 bug 或性能问题。

### B. 关键源码符号与阅读顺序

- `assoc_find`
- `assoc_insert`
- `assoc_delete`

建议在 `memcached-1.6.45` 源码树中用下面的方式定位，而不是按文件顺序从头读：

```bash
git grep -n "\bassoc_find\b" -- memcached.c assoc.c items.c
git grep -n "\bassoc_insert\b" -- memcached.c assoc.c items.c
git grep -n "\bassoc_delete\b" -- memcached.c assoc.c items.c
```

阅读函数时至少记录 5 个问题：**入参中的 key/hash/item 是谁创建的、当前持有哪些锁、item 是否已 `ITEM_LINKED`、refcount 谁持有、失败路径最终由谁释放资源**。

### C. 边界条件与反例

可以在应用层构造复合 key 或预计算结果，但这不是 Memcached 原生范围查询；索引失效和组合爆炸仍由应用承担。

面试中主动讲边界条件很加分，因为它能证明你区分了“默认实现”“协议语义”“架构经验”和“数学近似”。尤其要避免把平均 O(1)、默认 1MB、client-side hashing 等表述成无条件真理。

### D. 生产故障推演

为了模拟“按用户所有订单查询”，把每个查询结果缓存成一个 key 可以很快，但任何订单变化都要正确失效相关聚合 key，复杂度会转移到 invalidation。

遇到这类问题时，建议把故障链写成：

```text
触发条件 → Memcached 内部状态变化 → HIT/MISS/P99 变化 → origin/网络/CPU 后果 → 保护或恢复动作
```

这样回答能自然从源码层过渡到生产系统，而不是把“源码题”和“系统设计题”割裂开。

### E. 定量分析 / 可验证指标

判断是否适合缓存时问：结果能否被一个稳定 key 唯一定位？失效集合是否可控？重建成本是否明确？

工程上至少给出一个可以**测量或计算**的量。没有数字的“性能更好”“内存更省”“更稳定”通常无法指导容量规划，也很难在故障现场验证。
