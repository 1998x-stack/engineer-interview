# 第 012 题 · 从 set foo bar 开始，说出核心源码调用链。

> **必刷题** · **P0** · ★★★★★ · Item 与 SET/GET 源码链路  
> 本文是 PDF 对应题目的扩展版：保留原答案，并补充源码、复杂度、并发不变量、生产实践与实验。

## 题目

**从 set foo bar 开始，说出核心源码调用链。**

## 面试官在考什么

这道题用于判断候选人是否真正理解 **Item 生命周期、publication、refcount 与源码热路径**。

面试官通常不会满足于“术语定义”，而会沿着 `从 set foo bar 开始，说出核心源码调用链。` 继续追问到：**状态如何变化、哪个模块拥有这份状态、并发下怎样保持不变量、生产中用什么指标证明判断**。优秀回答应先给 30 秒结论，再主动给出一个反例或故障场景。

## 30-90 秒标准回答

> 文本 SET 经 parser → process_update_command → item_alloc/do_item_alloc → slabs_alloc；value 读入 ITEM_data 后，complete_nread_ascii → store_item/do_store_item → assoc_find → do_item_link/item_replace。

面试时建议先讲上面这句话，再根据追问选择展开源码或生产侧影响，不要一开始就陷入函数细节。

## 心智模型

**对象生命周期：** 核心不变量是 construct-before-publish 与 unlink-before-free。Item 把 Hash 索引、LRU 生命周期、Slab 物理内存和并发引用连接起来。

```mermaid
flowchart TD
  A[SET header] --> B[item_alloc]
  B --> C[Slab chunk]
  C --> D[read value into ITEM_data]
  D --> E[store_item]
  E --> F[assoc_find old]
  F --> G[do_item_link / replace]
  G --> H[assoc_insert]
  G --> I[item_link_q]
```

## 深度机制

### 1. 新 item 在读取 value 前已经取得 chunk。

从“对象生命周期”看，这一结论的重点不是记住术语，而是明确职责边界和失败方式。核心不变量是 construct-before-publish 与 unlink-before-free。Item 把 Hash 索引、LRU 生命周期、Slab 物理内存和并发引用连接起来。
### 2. 真正发布时 assoc_insert 与 item_link_q 把它同时接入 Hash 和 LRU。

高并发下 strict LRU 会把每个读请求变成共享链表写操作。Memcached 通过分段和后台维护，在“淘汰质量”和“锁/缓存一致性开销”之间做工程折中。
### 3. 覆盖旧值通常是 new object + replace，而不是任意原地覆盖。

从“对象生命周期”看，这一结论的重点不是记住术语，而是明确职责边界和失败方式。核心不变量是 construct-before-publish 与 unlink-before-free。Item 把 Hash 索引、LRU 生命周期、Slab 物理内存和并发引用连接起来。
### 4. 源码穿透

文本协议的 SET 不是“set foo bar”一行，而是 header 与 body 两阶段：`set foo 0 0 3\r\n` 后跟 `bar\r\n`。parser 在读完 header 后已经知道 key 与 value 长度，因此能先走 item_alloc。
### 5. 源码穿透

`item_alloc → do_item_alloc → slabs_clsid → do_item_alloc_pull/slabs_alloc` 解决的是“先获得最终内存”。连接随后把 `ritem` 指向 `ITEM_data(it)`，进入 `conn_nread`，让 body 直接落入 item。
### 6. 源码穿透

value 完整且 CRLF 校验通过后才进入 `store_item`。在 key 对应 item lock 内，`do_store_item` 先 `do_item_get/assoc_find` 判断旧对象，再选择 `do_item_link` 或 replace。
### 7. 源码穿透

`do_item_link` 是最接近 publication point 的位置：`assoc_insert` 使 key 可寻址，`item_link_q` 使其进入 LRU，refcount 增加缓存持有引用。

## 系统不变量

- **不变量 1：** 未完整构造的 Item 不能被 Hash 发布。
- **不变量 2：** 逻辑 unlink 后，只要 refcount 未归零就不能物理复用 chunk。

这些不变量比记忆具体函数名更稳定。版本升级可能调整代码组织，但破坏这些约束通常意味着正确性或生命周期出现问题。

## 复杂度与性能分析

- 单次操作通常很便宜，生产尾延迟更多由网络 RTT、序列化、锁等待和 miss 路径决定。
- 面试回答要把“算法复杂度”和“系统成本模型”分开。

进一步分析时要区分三个层面：**算法复杂度**（如 Hash 平均 O(1)）、**微架构成本**（cache miss、pointer chasing、cache-line bouncing）和 **系统成本**（RTT、序列化、回源）。高水平回答会主动指出这三者不是一回事。

1. **先确认语义边界：** 本题讨论的是 Item 生命周期、publication、refcount 与源码热路径，先区分 server 内部机制、客户端路由和应用回源三层，避免跨层归因。

3. **用指标证伪：** 对关键函数做采样或 eBPF/uprobes，按阶段统计时间：parse→alloc→body read→store/link→response。

5. **版本意识：** 本仓库源码锚定 Memcached `1.6.45`；默认参数与现代特性应以该版本官方源码/文档为准。

## 高频追问

### 追问 1：为什么先分配再读 value？

**回答提示：** 因为 header 已提供 value 长度，可以直接准备最终 item 空间，让 socket body 尽量直接落到目标内存，同时保持构造阶段不可见。
### 追问 2：哪个函数最接近 publication point？

**回答提示：** `do_item_link()` 最接近发布点：它把对象接入 assoc 与 LRU，使后续 GET 可以发现。

## 专家级展开（V2）

### A. 从第一性原理推导

SET 的关键不是记函数列表，而是识别两个阶段：构造 private item 与 publication。header 解析后先分配最终内存并读 body，完整校验后才在 item lock 下决定 link/replace。

这道题建议使用“**状态 → 所有者 → 转移条件 → 失败后果**”四步法推导，而不是背结论。先确定哪份状态是核心，再问由哪个模块维护，随后说明状态何时迁移，最后指出违反不变量会表现为什么 bug 或性能问题。

### B. 关键源码符号与阅读顺序

- `process_update_command`
- `process_update_cmd_start`
- `item_alloc`
- `do_item_alloc`
- `conn_nread`
- `complete_nread_ascii`
- `store_item`
- `do_store_item`
- `do_item_link`

建议在 `memcached-1.6.45` 源码树中用下面的方式定位，而不是按文件顺序从头读：

```bash
git grep -n "\bprocess_update_command\b" -- proto_text.c proto_parser.c items.c thread.c assoc.c slabs.c
git grep -n "\bprocess_update_cmd_start\b" -- proto_text.c proto_parser.c items.c thread.c assoc.c slabs.c
git grep -n "\bitem_alloc\b" -- proto_text.c proto_parser.c items.c thread.c assoc.c slabs.c
git grep -n "\bdo_item_alloc\b" -- proto_text.c proto_parser.c items.c thread.c assoc.c slabs.c
git grep -n "\bconn_nread\b" -- proto_text.c proto_parser.c items.c thread.c assoc.c slabs.c
```

阅读函数时至少记录 5 个问题：**入参中的 key/hash/item 是谁创建的、当前持有哪些锁、item 是否已 `ITEM_LINKED`、refcount 谁持有、失败路径最终由谁释放资源**。

### C. 边界条件与反例

如果客户端发送 header 后迟迟不发完整 body，已分配 item 会占用连接相关资源，但由于尚未 link，其他 GET 不应看到半成品。

面试中主动讲边界条件很加分，因为它能证明你区分了“默认实现”“协议语义”“架构经验”和“数学近似”。尤其要避免把平均 O(1)、默认 1MB、client-side hashing 等表述成无条件真理。

### D. 生产故障推演

SET P99 突增时不要只看 assoc：可能是大 value read、slab 申请/eviction、item lock 等待或网络 backpressure。

遇到这类问题时，建议把故障链写成：

```text
触发条件 → Memcached 内部状态变化 → HIT/MISS/P99 变化 → origin/网络/CPU 后果 → 保护或恢复动作
```

这样回答能自然从源码层过渡到生产系统，而不是把“源码题”和“系统设计题”割裂开。

### E. 定量分析 / 可验证指标

对关键函数做采样或 eBPF/uprobes，按阶段统计时间：parse→alloc→body read→store/link→response。

工程上至少给出一个可以**测量或计算**的量。没有数字的“性能更好”“内存更省”“更稳定”通常无法指导容量规划，也很难在故障现场验证。
