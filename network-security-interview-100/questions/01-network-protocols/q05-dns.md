# Q05 · DNS 完整解析过程是什么？DNS 有哪些安全问题？

## 面试官为什么问这题

判断候选人是否真正理解协议状态机、网络分层和组件可见性，而不是只会背端口号或工具参数。

通常不仅是在确认“是否知道名词”，还在观察以下能力：

- 数据从哪里来、经过哪一层？
- 哪一方维护状态？
- 安全控制能看到哪些字段或语义？
- 加密、代理或协议转换后可见性发生了什么变化？

## 30 秒回答

**一句话结论：** DNS 不只是解析服务，也是资产、信任和流量路径的一部分。

展开时优先抓住以下三点：

1. Browser/OS cache -> Recursive Resolver -> Root -> TLD -> Authoritative。
1. 掌握 A/AAAA/CNAME/MX/TXT/NS/TTL。
1. 安全风险包括 spoofing/cache poisoning、恶意 DNS、隧道、dangling DNS/subdomain takeover。

## 2-3 分钟标准回答

首先，Browser/OS cache -> Recursive Resolver -> Root -> TLD -> Authoritative。
其次，掌握 A/AAAA/CNAME/MX/TXT/NS/TTL。
DNS 是控制平面与发现机制，安全价值远高于“把域名翻译成 IP”。企业环境中的 DNS 日志经常用于资产发现、恶意域名检测和 C2 线索。
DNSSEC 解决的是数据来源真实性与完整性，不提供查询机密性；DoH/DoT 解决传输隐私，但也会改变企业监控可见性。
最后要把回答落到工程闭环：说明根因控制是什么、还能有哪些纵深防御，以及如何通过日志、测试或安全回归证明控制真正生效。

## 扩展解析：从“会回答”到“会做工程”

### 1. 更深一层的原理

DNS 同时是名称系统和重要控制平面；缓存、委派、权威服务器、解析器的角色要分清。

安全治理除了 DNSSEC，还包括资产生命周期、dangling record、日志与异常解析行为监控。

### 2. 边界条件与面试高分点

- **先定义边界**：明确主体、资产、数据/状态和信任边界，避免把问题描述成绝对结论。
- **区分根治与纵深**：根治方案应消除不安全的数据流、权限或协议状态；WAF、告警、限流等通常属于补充控制。
- **考虑失败模式**：不仅说明正常路径，还要考虑配置漂移、解析差异、权限过宽、依赖升级和异常条件。
- **给验证方式**：安全设计必须能被单元测试、集成测试、审计日志、检测规则或演练验证。

### 3. 工程化检查清单

- [ ] 优先用标准协议实现与成熟库
- [ ] 减少不必要协议转换和解析差异
- [ ] 为关键边界建立超时、限流、容量与异常处理
- [ ] 把网络控制与应用身份/授权结合，而不是单靠 IP
- [ ] 手工用 dig/nslookup 跟踪权威链路。
- [ ] 建立一份域名-证书-服务生命周期清单，检查失效记录。

### 4. 可观测性与证据

面试中主动补一句“我会从哪些证据验证”，通常很加分：

- 抓包/Flow 数据
- DNS/代理/负载均衡日志
- TLS 终止点信息
- 服务端连接与错误指标

### 5. 追问怎么接

#### 追问：DNSSEC 与 DoH/DoT 分别解决什么？

**回答要点：** 先给一句话结论，再用本题的核心原理解释边界条件；最后补充检测/修复/验证三个工程点。

#### 追问：为什么 CNAME/Dangling record 会引发子域接管风险？

**回答要点：** 先解释导致该现象的协议/信任边界，再说明成立所需条件，最后补充防守侧如何通过配置、日志或测试验证。

### 6. 面试官可能继续升级的场景题

- 如果这个问题发生在核心业务而不是测试环境，你会如何调整风险优先级、证据保全和修复节奏？
- 如果已有一层安全产品/框架默认保护，你如何验证它真的覆盖了 DNS 的边界，而不是只相信配置名称？
- 如果修复会影响兼容性或业务性能，你会如何设计灰度、监控和回滚方案？

## 专业深化 v2：面向高级工程师的题解

> 这一节是在 PDF 基线与第一轮扩展之上的第二层深化，重点补齐 **机制、边界、工程决策、证据、验证与追问树**。它不是利用手册，而是面向合法授权的安全工程与面试表达。

### A. 机制模型：先把问题抽象对

- DNS 是分布式命名系统；终端通常把递归工作交给 recursive resolver，而权威服务器回答自己负责区域的数据。
- 安全问题可分为完整性、可用性、隐蔽通道和资产生命周期四类，而不应只背“DNS 劫持”。
- DNS 记录本身也是资产控制面，错误的 CNAME/NS 生命周期可形成 dangling record 与接管风险。

### B. 成立条件、边界与典型失效模式

- 缓存和 TTL 会让配置变更不是瞬时生效；排障必须考虑缓存层。
- DNSSEC 主要解决 DNS 数据来源真实性/完整性，并不自动保证目标服务本身可信。
- DoH/DoT 会改变企业网络对 DNS 的可见性和治理方式。

### C. 工程设计：从“修一个点”到“设计控制面”

- 对关键域名启用变更审批、最小权限和 registrar/registry 账户强保护。
- 建立 DNS 资产盘点，持续发现 dangling records、异常 NS/MX/TXT 变化。
- 递归解析器做日志、威胁情报和异常查询检测，同时考虑隐私。
- 关键域根据业务需求评估 DNSSEC 与高可用权威架构。

### D. Detection & Evidence：如何证明你的判断

- resolver query logs：qname、qtype、rcode、latency、client。
- authoritative/registrar audit：记录变更、NS/DS 变更、账号活动。
- 被动 DNS、证书透明度和资产系统用于发现未知/遗留子域。

一个成熟回答要主动区分：**事实（日志/状态）**、**推断（关联分析）**、**假设（尚待验证）**。这能显著降低“看到一个异常就直接下结论”的面试失分。

### E. 修复后的验证与回归

- 模拟关键记录变更，验证监控与审批链路。
- 检查失效子域/第三方 SaaS 解绑后的 DNS 清理流程。
- 验证故障切换、TTL 策略和多权威服务器可用性。

### F. 面试追问树：把一题答成一棵知识树

1. 递归查询和迭代查询有什么区别？
2. DNSSEC 能不能防止所有 DNS 攻击？
3. 为什么 dangling CNAME 会演变成资产接管风险？

回答这些追问时，建议始终使用：**结论 → 原理 → 条件 → 反例/边界 → 工程控制 → 验证**。如果题目涉及生产环境，再补充可用性、兼容性、灰度和回滚。

### G. 这道题在真实工作中的“交付物”

企业 DNS 治理清单：域名资产、权威链、DNSSEC 状态、变更审计、第三方依赖与过期清理。

### H. 一页纸复盘

| 维度 | 应该能说清楚什么 |
|---|---|
| 根因 | DNS 通过递归解析、缓存和权威委派完成名称到数据的解析。 |
| 边界 | 缓存、加密 DNS、第三方托管会改变治理与可见性。 |
| 主要控制 | 身份/变更保护 + 资产生命周期 + DNS telemetry。 |
| 关键证据 | resolver/authoritative/registrar 日志。 |
| 验证 | 记录变更、故障切换和 dangling record 回归。 |
