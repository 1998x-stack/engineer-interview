# Q09 · CDN、反向代理、Load Balancer、WAF 分别解决什么问题？

## 面试官为什么问这题

判断候选人是否真正理解协议状态机、网络分层和组件可见性，而不是只会背端口号或工具参数。

通常不仅是在确认“是否知道名词”，还在观察以下能力：

- 数据从哪里来、经过哪一层？
- 哪一方维护状态？
- 安全控制能看到哪些字段或语义？
- 加密、代理或协议转换后可见性发生了什么变化？

## 30 秒回答

**一句话结论：** 先画代理链，再谈安全策略；否则很容易在错误位置加控制。

展开时优先抓住以下三点：

1. CDN 做边缘缓存与流量吸收；反向代理做转发与服务隐藏；LB 做负载分配；WAF 做应用层检测/阻断。
1. 这些能力可以共存在同一产品中。
1. 边缘控制不能替代后端授权与安全编码。

## 2-3 分钟标准回答

首先，CDN 做边缘缓存与流量吸收；反向代理做转发与服务隐藏；LB 做负载分配；WAF 做应用层检测/阻断。
其次，这些能力可以共存在同一产品中。
现代边缘服务经常集成 TLS、Bot、DDoS、WAF、缓存和路由，因此最重要的是确认“责任边界”和“实际启用的能力”。
安全上要特别关注真实客户端 IP 传递、Header 信任、缓存键、TLS 终止和代理链一致性。
最后要把回答落到工程闭环：说明根因控制是什么、还能有哪些纵深防御，以及如何通过日志、测试或安全回归证明控制真正生效。

## 扩展解析：从“会回答”到“会做工程”

### 1. 更深一层的原理

CDN、反向代理、负载均衡与 WAF 可以部署在同一产品中，但逻辑职责不同。

架构题应说明 TLS 在哪里终止、真实客户端地址如何传递、后端如何避免盲目信任代理 Header。

### 2. 边界条件与面试高分点

- **先定义边界**：明确主体、资产、数据/状态和信任边界，避免把问题描述成绝对结论。
- **区分根治与纵深**：根治方案应消除不安全的数据流、权限或协议状态；WAF、告警、限流等通常属于补充控制。
- **考虑失败模式**：不仅说明正常路径，还要考虑配置漂移、解析差异、权限过宽、依赖升级和异常条件。
- **给验证方式**：安全设计必须能被单元测试、集成测试、审计日志、检测规则或演练验证。

### 3. 工程化检查清单

- [ ] 优先用标准协议实现与成熟库
- [ ] 减少不必要协议转换和解析差异
- [ ] 为关键边界建立超时、限流、容量与异常处理
- [ ] 把网络控制与应用身份/授权结合，而不是单靠 IP
- [ ] 对一个系统记录真实流量经过的所有代理层。
- [ ] 检查后端是否错误信任客户端可伪造的转发 Header。

### 4. 可观测性与证据

面试中主动补一句“我会从哪些证据验证”，通常很加分：

- 抓包/Flow 数据
- DNS/代理/负载均衡日志
- TLS 终止点信息
- 服务端连接与错误指标

### 5. 追问怎么接

#### 追问：WAF 为什么不能修复越权？

**回答要点：** 先解释导致该现象的协议/信任边界，再说明成立所需条件，最后补充防守侧如何通过配置、日志或测试验证。

#### 追问：X-Forwarded-For 应该信任谁？

**回答要点：** 先给一句话结论，再用本题的核心原理解释边界条件；最后补充检测/修复/验证三个工程点。

### 6. 面试官可能继续升级的场景题

- 如果这个问题发生在核心业务而不是测试环境，你会如何调整风险优先级、证据保全和修复节奏？
- 如果已有一层安全产品/框架默认保护，你如何验证它真的覆盖了 Edge Architecture 的边界，而不是只相信配置名称？
- 如果修复会影响兼容性或业务性能，你会如何设计灰度、监控和回滚方案？

### 7. 常见回答层级

| 层级 | 表现 |
|---|---|
| 1/5 | 只能给出名词定义 |
| 2/5 | 能解释基本原理 |

## 专业深化 v2：面向高级工程师的题解

> 这一节是在 PDF 基线与第一轮扩展之上的第二层深化，重点补齐 **机制、边界、工程决策、证据、验证与追问树**。它不是利用手册，而是面向合法授权的安全工程与面试表达。

### A. 机制模型：先把问题抽象对

- CDN、反向代理、LB、WAF 是不同职责：缓存/边缘、代理/路由、流量分配、应用请求检测控制。
- 它们经常集成在一个产品里，但逻辑职责仍应分开，否则排障和安全边界会混乱。
- 最重要的架构问题是：谁终止 TLS、谁识别真实客户端、谁做认证、谁做最终授权。

### B. 成立条件、边界与典型失效模式

- WAF 不能理解所有业务对象权限，因此不能替服务端 authorization。
- X-Forwarded-For 等客户端标识只有在受信代理链中重写和验证才可信。
- CDN 绕过/源站直连会让边界控制失效，因此 origin exposure 是关键检查点。

### C. 工程设计：从“修一个点”到“设计控制面”

- 明确 trusted proxy chain，清理和重建来源身份 header。
- 源站只允许受控入口访问，减少边界绕过。
- 把 L7 限流、bot 管理、WAF 与应用授权区分为纵深控制。
- 记录 edge request ID 并传递到源站，建立可关联日志。

### D. Detection & Evidence：如何证明你的判断

- CDN/WAF access logs、rule decision、cache status。
- LB target health、backend connection/status。
- origin logs 与 edge logs 的 request ID 对齐和来源差异。

一个成熟回答要主动区分：**事实（日志/状态）**、**推断（关联分析）**、**假设（尚待验证）**。这能显著降低“看到一个异常就直接下结论”的面试失分。

### E. 修复后的验证与回归

- 尝试从预期外路径访问 origin，验证网络限制。
- 验证伪造 forwarding headers 不会影响身份/安全决策。
- 绕过缓存、不同协议版本和异常请求下检查控制一致性。

### F. 面试追问树：把一题答成一棵知识树

1. 反向代理和负载均衡为什么经常是同一设备但概念不同？
2. 如何安全地确定真实客户端 IP？
3. WAF 已拦 SQLi，为什么代码仍必须参数化？

回答这些追问时，建议始终使用：**结论 → 原理 → 条件 → 反例/边界 → 工程控制 → 验证**。如果题目涉及生产环境，再补充可用性、兼容性、灰度和回滚。

### G. 这道题在真实工作中的“交付物”

Edge architecture trust model：TLS、客户端身份、代理链、origin ACL、WAF/LB/CDN 责任和日志关联。

### H. 一页纸复盘

| 维度 | 应该能说清楚什么 |
|---|---|
| 根因 | 四类组件职责不同，关键在代理链与责任边界。 |
| 边界 | 源站绕过和不可信转发头会破坏边界假设。 |
| 主要控制 | 受信入口、header 重建、纵深控制、可关联日志。 |
| 关键证据 | edge/WAF/LB/origin 全链日志。 |
| 验证 | origin bypass 与 header spoofing 防护回归。 |
