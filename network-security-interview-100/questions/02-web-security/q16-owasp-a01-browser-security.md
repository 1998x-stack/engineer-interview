# Q16 · CSRF 的本质是什么？如何修复？

## 面试官为什么问这题

考察候选人能否用“Source -> Propagation -> Parser/Sink -> Impact”解释漏洞根因，并给出可验证的修复。

通常不仅是在确认“是否知道名词”，还在观察以下能力：

- 不可信数据从哪里进入？
- 最终进入什么解析/执行上下文？
- 数据与代码/结构是否真正分离？
- 根治控制与纵深防御分别是什么？

## 30 秒回答

**一句话结论：** CSRF 的核心是“伪造用户意图”，不是“偷到用户密码”。

展开时优先抓住以下三点：

1. 成立条件通常包含用户已认证、浏览器自动携带凭据、敏感操作缺少请求真实性校验。
1. 防护：CSRF Token、SameSite Cookie、Origin/Referer 校验、敏感操作再认证。
1. 状态改变不应依赖 GET。

## 2-3 分钟标准回答

首先，成立条件通常包含用户已认证、浏览器自动携带凭据、敏感操作缺少请求真实性校验。
其次，防护：CSRF Token、SameSite Cookie、Origin/Referer 校验、敏感操作再认证。
CSRF 利用的是应用对浏览器自动身份状态的信任，而不是在目标站点直接执行任意脚本。
现代 SameSite 默认策略降低了很多传统 CSRF，但跨站 SSO、复杂子域和兼容场景仍需系统设计。
最后要把回答落到工程闭环：说明根因控制是什么、还能有哪些纵深防御，以及如何通过日志、测试或安全回归证明控制真正生效。

## 扩展解析：从“会回答”到“会做工程”

### 1. 更深一层的原理

CSRF 依赖浏览器自动携带身份状态，因此防护核心是验证请求“确实由当前用户界面发起”。

SameSite、CSRF token、Origin 检查和敏感操作二次验证是互补控制。

### 2. 边界条件与面试高分点

- **先定义边界**：明确主体、资产、数据/状态和信任边界，避免把问题描述成绝对结论。
- **区分根治与纵深**：根治方案应消除不安全的数据流、权限或协议状态；WAF、告警、限流等通常属于补充控制。
- **考虑失败模式**：不仅说明正常路径，还要考虑配置漂移、解析差异、权限过宽、依赖升级和异常条件。
- **给验证方式**：安全设计必须能被单元测试、集成测试、审计日志、检测规则或演练验证。

### 3. 工程化检查清单

- [ ] 首选结构化 API、参数化和上下文编码
- [ ] 授权在可信服务端执行
- [ ] 对出站网络、文件、解析器实施最小能力
- [ ] 修复后建立单元/集成/安全回归测试
- [ ] 检查所有状态改变接口的 method 与 CSRF 策略。
- [ ] 为高风险操作设计 step-up authentication。

### 4. 可观测性与证据

面试中主动补一句“我会从哪些证据验证”，通常很加分：

- HTTP/反向代理日志
- 应用审计日志
- 数据库/下游服务异常
- WAF 仅作为辅助信号
- 安全测试回归结果

### 5. 追问怎么接

#### 追问：XSS 和 CSRF 哪个能绕过哪个？

**回答要点：** 先给一句话结论，再用本题的核心原理解释边界条件；最后补充检测/修复/验证三个工程点。

#### 追问：API 使用 Bearer Token 时 CSRF 风险如何变化？

**回答要点：** 按“资产/主体 -> 信任边界 -> 控制点 -> 可观测性 -> 回归验证”组织答案；优先给结构化、最小权限和默认拒绝的工程方案。

### 6. 面试官可能继续升级的场景题

- 如果这个问题发生在核心业务而不是测试环境，你会如何调整风险优先级、证据保全和修复节奏？
- 如果已有一层安全产品/框架默认保护，你如何验证它真的覆盖了 OWASP A01 / Browser Security 的边界，而不是只相信配置名称？
- 如果修复会影响兼容性或业务性能，你会如何设计灰度、监控和回滚方案？

## 专业深化 v2：面向高级工程师的题解

> 这一节是在 PDF 基线与第一轮扩展之上的第二层深化，重点补齐 **机制、边界、工程决策、证据、验证与追问树**。它不是利用手册，而是面向合法授权的安全工程与面试表达。

### A. 机制模型：先把问题抽象对

- CSRF 利用的是浏览器对目标站点自动携带认证状态，而目标服务未充分验证请求的“用户意图/来源真实性”。
- 是否存在 CSRF 取决于认证载体和请求方式：自动附带 Cookie 的风险模型与显式 Authorization token 不完全相同。
- 核心控制应使状态改变请求包含攻击站点无法伪造/获得的真实性信号。

### B. 成立条件、边界与典型失效模式

- SameSite 能显著降低常见 CSRF，但受 Cookie 属性、浏览器行为和业务跨站需求影响。
- GET 应保持幂等/无副作用；若 GET 改状态，浏览器预取/链接访问也会产生风险。
- XSS 可能破坏同源内的 CSRF token 防线，因此 CSRF 与 XSS 是纵深关系。

### C. 工程设计：从“修一个点”到“设计控制面”

- 状态修改请求使用 CSRF token 或框架成熟机制。
- 合理设置 SameSite/Secure/HttpOnly，并明确跨站登录/支付/SSO 场景。
- 对高风险动作采用重新认证/二次确认和业务级风控。
- 服务端可对 Origin 等信号进行适当校验，但不要依赖单一脆弱信号。

### D. Detection & Evidence：如何证明你的判断

- 服务端记录 method、Origin/Referer（注意隐私）、session/account 和结果。
- 异常来自跨站来源的状态修改请求可用于检测与复盘。
- 前端/网关日志验证 Cookie 属性和请求路径。

一个成熟回答要主动区分：**事实（日志/状态）**、**推断（关联分析）**、**假设（尚待验证）**。这能显著降低“看到一个异常就直接下结论”的面试失分。

### E. 修复后的验证与回归

- 构造合法跨站业务场景验证 SameSite 不误伤。
- 验证 token 与 session/请求上下文绑定、生命周期和错误处理。
- 检查所有 state-changing endpoint，包括旧 API 和非标准 method。

### F. 面试追问树：把一题答成一棵知识树

1. 为什么 Authorization Bearer token 常改变 CSRF 风险模型？
2. SameSite=Lax 能解决哪些场景，不能解决哪些？
3. 为什么 CSRF token 不能替代授权？

回答这些追问时，建议始终使用：**结论 → 原理 → 条件 → 反例/边界 → 工程控制 → 验证**。如果题目涉及生产环境，再补充可用性、兼容性、灰度和回滚。

### G. 这道题在真实工作中的“交付物”

状态修改接口清单 + 认证载体/CSRF 控制矩阵 + Cookie policy + 高风险动作二次验证策略。

### H. 一页纸复盘

| 维度 | 应该能说清楚什么 |
|---|---|
| 根因 | 浏览器自动携带身份，但服务端缺少请求真实性验证。 |
| 边界 | 认证载体、跨站业务和 XSS 会改变风险。 |
| 主要控制 | CSRF token + SameSite + 高风险动作验证。 |
| 关键证据 | Origin/session/action 日志。 |
| 验证 | 跨站与业务兼容性回归。 |
