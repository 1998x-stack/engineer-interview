## 面试官为什么问这题

判断候选人是否从“漏洞点”升级到浏览器安全模型、对象级授权、会话与联合身份的系统视角。

通常不仅是在确认“是否知道名词”，还在观察以下能力：

- 谁是主体？访问哪个对象/能力？
- 认证完成后授权在哪里执行？
- Token/Cookie 的生命周期和绑定关系是什么？
- 浏览器、Gateway 与后端分别承担什么安全责任？

## 30 秒回答

**一句话结论：** 访问控制的四要素：谁、对什么、做什么、在什么上下文。

展开时优先抓住以下三点：

1. 水平越权：同级主体访问别人的资源。
1. 垂直越权：低权限主体执行高权限功能。
1. 未授权：未认证主体访问受保护资源。

## 2-3 分钟标准回答

首先，水平越权：同级主体访问别人的资源。
其次，垂直越权：低权限主体执行高权限功能。
访问控制需要同时考虑 subject、object、action 和 context。RBAC 只表达 role 还不够，多租户、资源归属、敏感数据字段往往需要 ABAC/relationship-aware 的补充。
高分回答应强调 deny-by-default、server-side enforcement 和集中策略。
最后要把回答落到工程闭环：说明根因控制是什么、还能有哪些纵深防御，以及如何通过日志、测试或安全回归证明控制真正生效。

## 扩展解析：从“会回答”到“会做工程”

### 1. 更深一层的原理

认证只证明“你是谁”，授权才决定“你能做什么”；二者混淆是大量 API 漏洞的根因。

权限检查应位于可信服务端并覆盖所有入口，不能依赖前端按钮或路由隐藏。

### 2. 边界条件与面试高分点

- **先定义边界**：明确主体、资产、数据/状态和信任边界，避免把问题描述成绝对结论。
- **区分根治与纵深**：根治方案应消除不安全的数据流、权限或协议状态；WAF、告警、限流等通常属于补充控制。
- **考虑失败模式**：不仅说明正常路径，还要考虑配置漂移、解析差异、权限过宽、依赖升级和异常条件。
- **给验证方式**：安全设计必须能被单元测试、集成测试、审计日志、检测规则或演练验证。

### 3. 工程化检查清单

- [ ] 认证与授权明确分离
- [ ] 对象级授权靠后端业务上下文完成
- [ ] Token 最小权限、短生命周期、严格受众/签发方校验
- [ ] 浏览器策略作为边界的一部分但不替代服务端控制
- [ ] 建立“角色-资源-动作”矩阵。
- [ ] 为敏感管理功能增加二次授权/审批。

### 4. 可观测性与证据

面试中主动补一句“我会从哪些证据验证”，通常很加分：

- IdP/认证日志
- API Gateway/应用访问日志
- 对象级授权拒绝事件
- Session/Token 生命周期事件

### 5. 追问怎么接

#### 追问：RBAC 和 ABAC 怎么选？

**回答要点：** 按“资产/主体 -> 信任边界 -> 控制点 -> 可观测性 -> 回归验证”组织答案；优先给结构化、最小权限和默认拒绝的工程方案。

#### 追问：多租户系统如何防止 tenant escape？

**回答要点：** 按“资产/主体 -> 信任边界 -> 控制点 -> 可观测性 -> 回归验证”组织答案；优先给结构化、最小权限和默认拒绝的工程方案。

### 6. 面试官可能继续升级的场景题

- 如果这个问题发生在核心业务而不是测试环境，你会如何调整风险优先级、证据保全和修复节奏？
- 如果已有一层安全产品/框架默认保护，你如何验证它真的覆盖了 Access Control 的边界，而不是只相信配置名称？
- 如果修复会影响兼容性或业务性能，你会如何设计灰度、监控和回滚方案？

## 专业深化 v2：面向高级工程师的题解

> 这一节是在 PDF 基线与第一轮扩展之上的第二层深化，重点补齐 **机制、边界、工程决策、证据、验证与追问树**。它不是利用手册，而是面向合法授权的安全工程与面试表达。

### A. 机制模型：先把问题抽象对

- 水平越权是同权限主体跨对象，垂直越权是低权限主体执行高权限动作，未授权访问则没有有效认证主体。
- 三者都应回到 access-control policy，而不是 URL 是否隐藏或按钮是否显示。
- 成熟授权模型应能表达 subject、resource、action、context，而不是到处 if role==admin。

### B. 成立条件、边界与典型失效模式

- 角色本身不能表达所有对象关系；RBAC 常需结合 ABAC/ReBAC 或 ownership。
- 前端路由守卫只是 UX，不是安全边界。
- 服务间调用若信任来自上游的 role/header，需要明确身份真实性和 delegation。

### C. 工程设计：从“修一个点”到“设计控制面”

- 默认拒绝，权限显式授予。
- 统一 policy decision/enforcement 点并保留审计。
- 敏感管理动作使用独立权限与 JIT/审批机制。
- 对多租户、代理操作和 service account 建立特殊授权模型。

### D. Detection & Evidence：如何证明你的判断

- authz decision logs：subject、claims、resource、action、result。
- IdP/session logs 用于确认主体身份；应用数据用于确认资源归属。
- 权限变更 audit 用于解释“为什么某人今天拥有这个权限”。

一个成熟回答要主动区分：**事实（日志/状态）**、**推断（关联分析）**、**假设（尚待验证）**。这能显著降低“看到一个异常就直接下结论”的面试失分。

### E. 修复后的验证与回归

- 角色×资源×动作矩阵覆盖 allow 和 deny。
- 验证 UI、API、批量任务、后台 job 对同一策略一致。
- 权限撤销、角色变更后验证缓存/长期 token 不延迟生效。

### F. 面试追问树：把一题答成一棵知识树

1. RBAC 为什么不能解决所有对象级授权？
2. 授权缓存会带来什么一致性风险？
3. 服务到服务如何传递用户上下文而不信任任意 header？

回答这些追问时，建议始终使用：**结论 → 原理 → 条件 → 反例/边界 → 工程控制 → 验证**。如果题目涉及生产环境，再补充可用性、兼容性、灰度和回滚。

### G. 这道题在真实工作中的“交付物”

企业授权模型：policy schema、角色/属性/关系、enforcement points、decision logs 和 regression matrix。

### H. 一页纸复盘

| 维度 | 应该能说清楚什么 |
|---|---|
| 根因 | 服务端权限决策缺失或模型错误。 |
| 边界 | RBAC 限制、缓存、跨服务上下文。 |
| 主要控制 | default deny + central policy + JIT 敏感权限。 |
| 关键证据 | authn + authz decision + permission change logs。 |
| 验证 | 角色/对象/动作 deny/allow 回归。 |
