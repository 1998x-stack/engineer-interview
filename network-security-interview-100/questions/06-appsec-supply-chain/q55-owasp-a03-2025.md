# Q55 · 软件供应链攻击是什么？

## 面试官为什么问这题

考察代码级数据流思维和软件供应链全链路风险，而不是仅会运行扫描器。

通常不仅是在确认“是否知道名词”，还在观察以下能力：

- Source/Propagation/Sanitizer/Sink 在哪里？
- 问题发生在自研代码、依赖、构建还是发布链？
- 工具结果是否可达、可利用、影响关键资产？
- 如何把修复变成 SDLC 的可重复控制？

## 30 秒回答

**一句话结论：** 供应链安全保护的是“软件从源码到生产的完整生命链”。

展开时优先抓住以下三点：

1. 供应链覆盖开发机、源码、依赖、构建、CI/CD、制品、镜像仓库、更新渠道。
1. 风险既可能来自漏洞，也可能来自恶意变更、凭证泄露与构建基础设施被攻破。
1. 防护要做 provenance、签名、最小权限、职责分离和持续依赖治理。

## 2-3 分钟标准回答

首先，供应链覆盖开发机、源码、依赖、构建、CI/CD、制品、镜像仓库、更新渠道。
其次，风险既可能来自漏洞，也可能来自恶意变更、凭证泄露与构建基础设施被攻破。
OWASP Top 10:2025 将软件供应链失效提升到 A03，反映风险已从“用了有漏洞组件”扩大到整个构建和分发体系。
工程上要保证“生产部署的制品就是经过审查与构建的那个制品”，避免不同环境重复构建造成不可验证差异。
最后要把回答落到工程闭环：说明根因控制是什么、还能有哪些纵深防御，以及如何通过日志、测试或安全回归证明控制真正生效。

## 扩展解析：从“会回答”到“会做工程”

### 1. 更深一层的原理

供应链风险覆盖源代码、依赖、开发机、CI/CD、构建器、制品、仓库和更新链。

关键概念是 provenance、完整性、最小权限和可追溯性，而不仅是“依赖有 CVE”。

### 2. 边界条件与面试高分点

- **先定义边界**：明确主体、资产、数据/状态和信任边界，避免把问题描述成绝对结论。
- **区分根治与纵深**：根治方案应消除不安全的数据流、权限或协议状态；WAF、告警、限流等通常属于补充控制。
- **考虑失败模式**：不仅说明正常路径，还要考虑配置漂移、解析差异、权限过宽、依赖升级和异常条件。
- **给验证方式**：安全设计必须能被单元测试、集成测试、审计日志、检测规则或演练验证。

### 3. 工程化检查清单

- [ ] 把安全检查前移且与 owner/门禁联动
- [ ] 依赖/SBOM 解决可见性，风险仍需上下文判断
- [ ] Secrets 不进入源代码和长期日志
- [ ] 补丁分析聚焦根因和回归测试
- [ ] 绘制 software supply chain dataflow。
- [ ] 对制品引入签名与 provenance。

### 4. 可观测性与证据

面试中主动补一句“我会从哪些证据验证”，通常很加分：

- 代码仓与审计记录
- CI/CD 日志
- 依赖与制品元数据
- 扫描结果与代码 owner
- 构建 provenance/签名

### 5. 追问怎么接

#### 追问：依赖漏洞与依赖投毒有什么区别？

**回答要点：** 从目标、数据/状态位置、信任模型、可见性和适用场景五个维度对比，避免只列名词定义。

#### 追问：为什么 CI/CD 权限经常高于普通应用？

**回答要点：** 先解释导致该现象的协议/信任边界，再说明成立所需条件，最后补充防守侧如何通过配置、日志或测试验证。

### 6. 面试官可能继续升级的场景题

- 如果这个问题发生在核心业务而不是测试环境，你会如何调整风险优先级、证据保全和修复节奏？
- 如果已有一层安全产品/框架默认保护，你如何验证它真的覆盖了 OWASP A03:2025 的边界，而不是只相信配置名称？
- 如果修复会影响兼容性或业务性能，你会如何设计灰度、监控和回滚方案？

### 7. 常见回答层级

| 层级 | 表现 |
|---|---|
| 1/5 | 只能给出名词定义 |
| 2/5 | 能解释基本原理 |
| 3/5 | 能说明成立条件、边界和真实影响 |
| 4/5 | 能给出工程修复、检测和验证 |
| 5/5 | 能处理复杂追问、权衡与系统设计 |

## 专业深化 v2：面向高级工程师的题解

> 这一节是在 PDF 基线与第一轮扩展之上的第二层深化，重点补齐 **机制、边界、工程决策、证据、验证与追问树**。它不是利用手册，而是面向合法授权的安全工程与面试表达。

### A. 机制模型：先把问题抽象对

- 供应链安全覆盖 source、developer、dependency、build、CI/CD、artifact、registry、deployment、update 全链。
- 风险不仅是“依赖有漏洞”，还包括来源篡改、构建身份、artifact provenance、发布权限和更新信任。
- OWASP 2025 把 Software Supply Chain Failures 单列，体现风险从组件扩展到生产链。

### B. 成立条件、边界与典型失效模式

- SBOM 提供 visibility 但不能证明构建未被篡改。
- 签名证明某身份签了 artifact，但前提是 signing identity/key 可信。
- 依赖 pinning 解决可重复性部分问题，不能自动解决恶意 upstream。

### C. 工程设计：从“修一个点”到“设计控制面”

- 依赖来源/版本 policy、lockfile 和 review。
- CI runner 最小权限、隔离 untrusted PR、secret 最小化。
- 生成 provenance/attestation，artifact signing 与 registry policy。
- 部署 admission 验证来源与签名，建立快速 revoke。

### D. Detection & Evidence：如何证明你的判断

- repo/CI/build/registry/deploy audit。
- SBOM/provenance/signature/attestation。
- dependency update/maintainer/source changes。

一个成熟回答要主动区分：**事实（日志/状态）**、**推断（关联分析）**、**假设（尚待验证）**。这能显著降低“看到一个异常就直接下结论”的面试失分。

### E. 修复后的验证与回归

- 从 commit 到 production 做 provenance trace。
- 轮换 signing key/撤销 artifact 演练。
- 模拟依赖或 registry policy failure 验证 gate。

### F. 面试追问树：把一题答成一棵知识树

1. SBOM 为什么不是供应链安全的终点？
2. artifact signing 的 trust root 在哪里？
3. 如何隔离来自 fork PR 的 CI 执行？

回答这些追问时，建议始终使用：**结论 → 原理 → 条件 → 反例/边界 → 工程控制 → 验证**。如果题目涉及生产环境，再补充可用性、兼容性、灰度和回滚。

### G. 这道题在真实工作中的“交付物”

Software supply-chain control map + provenance/signing/admission + CI permissions + dependency governance。

### H. 一页纸复盘

| 维度 | 应该能说清楚什么 |
|---|---|
| 根因 | 软件生产链任一环节失信可把风险传播到发布物。 |
| 边界 | SBOM/签名依赖各自 trust root。 |
| 主要控制 | least-privilege CI + provenance + signed artifact + admission。 |
| 关键证据 | repo→build→registry→deploy lineage。 |
| 验证 | 端到端 provenance 与 revoke 演练。 |
