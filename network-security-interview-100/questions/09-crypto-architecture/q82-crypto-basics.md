## 面试官为什么问这题

考察是否理解密码学“正确组合和密钥管理”比背算法名称更重要，并能把技术控制放入架构与治理。

通常不仅是在确认“是否知道名词”，还在观察以下能力：

- 安全目标是机密性、完整性、真实性还是不可抵赖？
- 密钥如何生成、存储、轮换和吊销？
- 算法的 nonce/IV/参数有什么约束？
- 加密之后谁仍有解密权限？

## 30 秒回答

**一句话结论：** Encoding 改表示，Encryption 保护机密，Hash 做摘要；三者目标不同。

展开时优先抓住以下三点：

1. Encoding 是表示变换；Encryption 是有密钥可逆；Hash 是固定长度摘要/单向性质。
1. Base64 不是加密。
1. 密码存储应使用专门 KDF，而不是普通 hash。

## 2-3 分钟标准回答

首先，Encoding 是表示变换；Encryption 是有密钥可逆；Hash 是固定长度摘要/单向性质。
其次，Base64 不是加密。
安全问题经常来自把表示层当安全层，例如把 secret Base64 后就认为“加密”。
Hash 也不是天然适合密码：SHA-256 太快，攻击者能进行高吞吐离线猜测，所以需要 Argon2/bcrypt/scrypt/PBKDF2 等昂贵 KDF。
最后要把回答落到工程闭环：说明根因控制是什么、还能有哪些纵深防御，以及如何通过日志、测试或安全回归证明控制真正生效。

## 扩展解析：从“会回答”到“会做工程”

### 1. 更深一层的原理

Encoding 解决表示，Encryption 解决带密钥的机密性，Hash 提供摘要/完整性构件。

密码存储必须使用慢且可调的 password KDF，而不是普通快速 hash。

### 2. 边界条件与面试高分点

- **先定义边界**：明确主体、资产、数据/状态和信任边界，避免把问题描述成绝对结论。
- **区分根治与纵深**：根治方案应消除不安全的数据流、权限或协议状态；WAF、告警、限流等通常属于补充控制。
- **考虑失败模式**：不仅说明正常路径，还要考虑配置漂移、解析差异、权限过宽、依赖升级和异常条件。
- **给验证方式**：安全设计必须能被单元测试、集成测试、审计日志、检测规则或演练验证。

### 3. 工程化检查清单

## 专业深化 v2：面向高级工程师的题解

> 这一节是在 PDF 基线与第一轮扩展之上的第二层深化，重点补齐 **机制、边界、工程决策、证据、验证与追问树**。它不是利用手册，而是面向合法授权的安全工程与面试表达。

### A. 机制模型：先把问题抽象对

- Encoding 改变表示形式，Encryption 用密钥实现可逆保密，Hash 产生固定长度摘要并面向单向/完整性用途。
- Password hashing 又是 hash 的特殊工程场景：需要 salt 和故意昂贵的 KDF，而不是普通快速哈希。
- MAC/数字签名进一步提供有密钥的完整性/来源验证，不能与普通 hash 混为一谈。

### B. 成立条件、边界与典型失效模式

- Base64、hex、URL encoding 不提供保密性。
- 普通 hash 不能证明消息来自谁；任何人都可重新计算。
- encrypted data 若没有完整性保护也可能遭篡改，因此现代设计倾向 AEAD。

### C. 工程设计：从“修一个点”到“设计控制面”

- 数据传输/存储保密用标准加密协议。
- 密码使用专用 password hashing/KDF。
- 完整性/认证按场景使用 MAC/signature。
- 明确数据字段是“需要保密、完整性、可查找还是表示转换”。

### D. Detection & Evidence：如何证明你的判断

- crypto API/config 与 key usage。
- password hash scheme/version 参数。
- data format/version metadata。

一个成熟回答要主动区分：**事实（日志/状态）**、**推断（关联分析）**、**假设（尚待验证）**。这能显著降低“看到一个异常就直接下结论”的面试失分。

### E. 修复后的验证与回归

- 检查不存在把 Base64 当 encryption 的设计。
- password migration 能识别旧 hash 并升级。
- 加密数据篡改后必须被检测。

### F. 面试追问树：把一题答成一棵知识树

1. Hash 为什么不能替代数字签名？
2. 为什么密码不用 SHA-256 直接 hash？
3. Encryption 与 Encoding 在可逆性上都可能“能还原”，关键差别是什么？

回答这些追问时，建议始终使用：**结论 → 原理 → 条件 → 反例/边界 → 工程控制 → 验证**。如果题目涉及生产环境，再补充可用性、兼容性、灰度和回滚。

### G. 这道题在真实工作中的“交付物”

Data protection decision table：encoding/encryption/hash/KDF/MAC/signature 的用途、key、属性和 tests。

### H. 一页纸复盘

| 维度 | 应该能说清楚什么 |
|---|---|
| 根因 | 不同变换提供完全不同安全属性。 |
| 边界 | 普通 hash 无来源认证，encoding 无保密。 |
| 主要控制 | 按属性选标准 primitive。 |
| 关键证据 | API/config/hash scheme。 |
| 验证 | 篡改/旧格式/错误 primitive tests。 |
