## 面试官为什么问这题

考察是否理解密码学“正确组合和密钥管理”比背算法名称更重要，并能把技术控制放入架构与治理。

通常不仅是在确认“是否知道名词”，还在观察以下能力：

- 安全目标是机密性、完整性、真实性还是不可抵赖？
- 密钥如何生成、存储、轮换和吊销？
- 算法的 nonce/IV/参数有什么约束？
- 加密之后谁仍有解密权限？

## 30 秒回答

**一句话结论：** 密码存储目标不是“无法破解”，而是把离线猜测成本推高并可持续升级。

展开时优先抓住以下三点：

1. 使用 Argon2/scrypt/bcrypt/PBKDF2 等 password KDF。
1. 每个密码使用 unique salt，参数要可调且足够昂贵。
1. 可选 pepper 需单独安全管理。

## 2-3 分钟标准回答

首先，使用 Argon2/scrypt/bcrypt/PBKDF2 等 password KDF。
其次，每个密码使用 unique salt，参数要可调且足够昂贵。
密码验证本质上不可避免离线猜测风险，因此目标是让每次猜测足够昂贵。参数应根据当前硬件定期评估，而不是永久沿用默认值。
密码 reset、MFA 和 credential stuffing 防护同样属于认证系统，不要把密码 hash 当完整身份安全。
最后要把回答落到工程闭环：说明根因控制是什么、还能有哪些纵深防御，以及如何通过日志、测试或安全回归证明控制真正生效。

## 扩展解析：从“会回答”到“会做工程”

### 1. 更深一层的原理

密码哈希设计目标是提高离线猜测成本；salt 解决预计算/同密码同 hash，work factor 提高成本。

参数应可升级，且认证系统要结合 MFA、rate limit、泄露密码检测和安全恢复流程。

### 2. 边界条件与面试高分点

- **先定义边界**：明确主体、资产、数据/状态和信任边界，避免把问题描述成绝对结论。
- **区分根治与纵深**：根治方案应消除不安全的数据流、权限或协议状态；WAF、告警、限流等通常属于补充控制。
- **考虑失败模式**：不仅说明正常路径，还要考虑配置漂移、解析差异、权限过宽、依赖升级和异常条件。
- **给验证方式**：安全设计必须能被单元测试、集成测试、审计日志、检测规则或演练验证。

### 3. 工程化检查清单

- [ ] 使用成熟协议和库，不自创密码方案
- [ ] 密钥与数据分离管理
- [ ] 最小权限和轮换
- [ ] 用 CSF/Zero Trust 把密码控制纳入风险管理
- [ ] 基准测试 KDF cost。
- [ ] 检查历史 hash 升级/rehash 机制。

### 4. 可观测性与证据

面试中主动补一句“我会从哪些证据验证”，通常很加分：

- 证书/密钥生命周期
- KMS/HSM 审计
- TLS/证书错误
- 身份与授权日志
- 配置合规扫描

## 专业深化 v2：面向高级工程师的题解

> 这一节是在 PDF 基线与第一轮扩展之上的第二层深化，重点补齐 **机制、边界、工程决策、证据、验证与追问树**。它不是利用手册，而是面向合法授权的安全工程与面试表达。

### A. 机制模型：先把问题抽象对

- 密码存储目标是让数据库泄露后离线猜测昂贵，因此使用专用 memory-hard/slow KDF + unique salt。
- salt 防止预计算和相同密码 hash 相同；work factor/memory cost 提高每次猜测成本。
- pepper 可作为额外服务器侧秘密，但不能替代 KDF/salt。

### B. 成立条件、边界与典型失效模式

- 参数太低会随硬件进步变弱；太高会造成登录 DoS/性能问题。
- 旧 hash scheme 需要渐进迁移。
- 密码 hash 安全不等于账号安全，还需 MFA、rate limit、breach detection。

### C. 工程设计：从“修一个点”到“设计控制面”

- 优先 Argon2id 等适合平台的专用方案，参数按性能基准设定。
- 每用户随机 salt，必要时 pepper 放 KMS/HSM/secret manager。
- 登录成功时 opportunistic rehash 升级旧参数。
- 限制在线猜测并保护 reset/recovery。

### D. Detection & Evidence：如何证明你的判断

- 存储的 hash scheme/version/cost metadata。
- authentication failure/rate-limit/MFA logs。
- KMS pepper access（若使用）。

一个成熟回答要主动区分：**事实（日志/状态）**、**推断（关联分析）**、**假设（尚待验证）**。这能显著降低“看到一个异常就直接下结论”的面试失分。

### E. 修复后的验证与回归

- benchmark 验证目标硬件 latency 和并发。
- 测试旧 hash 登录后自动升级。
- 确认数据库中没有 plaintext/reversible password。

### F. 面试追问树：把一题答成一棵知识树

1. salt 为什么不需要保密？
2. pepper 与 salt 有什么不同？
3. 如何升级已有数百万用户的旧 password hash？

回答这些追问时，建议始终使用：**结论 → 原理 → 条件 → 反例/边界 → 工程控制 → 验证**。如果题目涉及生产环境，再补充可用性、兼容性、灰度和回滚。

### G. 这道题在真实工作中的“交付物”

Password hashing standard + parameter benchmark + migration strategy + auth abuse controls。

### H. 一页纸复盘

| 维度 | 应该能说清楚什么 |
|---|---|
| 根因 | 数据库泄露后需提高离线猜测成本。 |
| 边界 | 参数性能、旧 hash、在线攻击。 |
| 主要控制 | 专用 KDF + salt + 可选 pepper + MFA/rate limit。 |
| 关键证据 | hash metadata/auth/KMS。 |
| 验证 | benchmark、迁移、明文检查。 |
