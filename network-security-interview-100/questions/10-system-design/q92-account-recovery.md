# Q92 · 让你设计“忘记密码”功能，如何确保安全？

## 面试官为什么问这题

考察候选人能否把安全知识转成架构、路线图、指标和跨团队可执行方案。

通常不仅是在确认“是否知道名词”，还在观察以下能力：

- 保护的关键资产是什么？
- 最重要信任边界和 attack path 是什么？
- 什么控制能真正降低风险？
- 如何验证控制有效并向业务解释优先级？

## 30 秒回答

**一句话结论：** 账号恢复是认证系统的一部分，安全级别不能低于登录。

展开时优先抓住以下三点：

1. 不泄露账号是否存在；token 高熵、短期、单次、绑定账号与用途。
1. 全程 HTTPS、rate limit、成功后按策略失效会话并通知用户。
1. 高风险场景加入 step-up/人工恢复流程。

## 2-3 分钟标准回答

首先，不泄露账号是否存在；token 高熵、短期、单次、绑定账号与用途。
其次，全程 HTTPS、rate limit、成功后按策略失效会话并通知用户。
Account recovery 往往比登录本身更容易被忽略，却能直接重置凭据。token 必须不可预测并只存 hash/受控状态，使用后立即失效。
不能依赖“只有知道邮箱就可信”，邮件账户本身也可能被接管，因此高价值账户需要更强恢复机制。
最后要把回答落到工程闭环：说明根因控制是什么、还能有哪些纵深防御，以及如何通过日志、测试或安全回归证明控制真正生效。

## 扩展解析：从“会回答”到“会做工程”

### 1. 更深一层的原理

安全恢复的目标是让合法用户恢复访问，同时不能让攻击者借“恢复流程”绕过主认证。

Token 随机性、短期、单次使用、账户绑定、通知、速率限制和会话处理是核心。

### 2. 边界条件与面试高分点

- **先定义边界**：明确主体、资产、数据/状态和信任边界，避免把问题描述成绝对结论。
- **区分根治与纵深**：根治方案应消除不安全的数据流、权限或协议状态；WAF、告警、限流等通常属于补充控制。
- **考虑失败模式**：不仅说明正常路径，还要考虑配置漂移、解析差异、权限过宽、依赖升级和异常条件。
- **给验证方式**：安全设计必须能被单元测试、集成测试、审计日志、检测规则或演练验证。

### 3. 工程化检查清单

- [ ] 先事实基础再大规模改造
- [ ] 把安全设计成平台能力而非一次性项目
- [ ] 指标反映风险下降而非扫描数量
- [ ] 明确 owner、SLA、验证和 30/60/90 日路线图
- [ ] 为 reset 流程写威胁模型。
- [ ] 对成功 reset 发送多通道通知。

### 4. 可观测性与证据

面试中主动补一句“我会从哪些证据验证”，通常很加分：

- 架构/资产清单
- 身份与暴露面
- 关键控制覆盖率
- 事件与漏洞趋势
- 业务可恢复性指标

### 5. 追问怎么接

#### 追问：为什么 reset token 不应长期有效？

**回答要点：** 先解释导致该现象的协议/信任边界，再说明成立所需条件，最后补充防守侧如何通过配置、日志或测试验证。

#### 追问：如何处理用户邮箱已无法访问？

**回答要点：** 按“资产/主体 -> 信任边界 -> 控制点 -> 可观测性 -> 回归验证”组织答案；优先给结构化、最小权限和默认拒绝的工程方案。

### 6. 面试官可能继续升级的场景题

- 如果这个问题发生在核心业务而不是测试环境，你会如何调整风险优先级、证据保全和修复节奏？
- 如果已有一层安全产品/框架默认保护，你如何验证它真的覆盖了 Account Recovery 的边界，而不是只相信配置名称？
- 如果修复会影响兼容性或业务性能，你会如何设计灰度、监控和回滚方案？

### 7. 常见回答层级

| 层级 | 表现 |
|---|---|
| 1/5 | 只能给出名词定义 |
| 2/5 | 能解释基本原理 |
| 3/5 | 能说明成立条件、边界和真实影响 |
| 4/5 | 能给出工程修复、检测和验证 |
| 5/5 | 能处理复杂追问、权衡与系统设计 |

## 专业深化 v2：面向高级工程师的题解

> 这一节是在 PDF 基线与第一轮扩展之上的第二层深化，重点补齐 **机制、边界、工程决策、证据、验证与追问树**。它不是利用手册，而是面向合法授权的安全工程与面试表达。

### A. 机制模型：先把问题抽象对

- 密码重置本质是替代认证流程，安全强度不应显著低于正常登录。
- reset token 需高熵、短时、单次、绑定账户/用途，并在服务端安全验证。
- 流程还需抵抗账户枚举、滥用通知和 session persistence。

### B. 成立条件、边界与典型失效模式

- 邮件/短信渠道本身可能被攻陷，关键账号需要更强恢复策略。
- 返回统一提示可降低枚举，但后台仍需准确处理不存在账号。
- 重置后是否注销所有 session 要结合风险/UX，但至少应有明确策略。

### C. 工程设计：从“修一个点”到“设计控制面”

- 统一响应避免明显枚举。
- 安全随机 token，存 hash，TTL/one-time/use binding。
- rate limit/abuse monitoring。
- 成功重置通知用户并撤销高风险 session/refresh token。

### D. Detection & Evidence：如何证明你的判断

- reset request/issue/use/failure audit。
- IP/device/account abuse pattern。
- session revoke/password change events。

一个成熟回答要主动区分：**事实（日志/状态）**、**推断（关联分析）**、**假设（尚待验证）**。这能显著降低“看到一个异常就直接下结论”的面试失分。

### E. 修复后的验证与回归

- token reuse/expired/wrong account 应拒绝。
- 高频 reset abuse 与 enumeration tests。
- 成功重置后旧凭据/session 行为验证。

### F. 面试追问树：把一题答成一棵知识树

1. 为什么 reset token 最好服务端存 hash？
2. 统一错误提示会不会影响用户体验？
3. 高价值账号的 recovery 应如何更强？

回答这些追问时，建议始终使用：**结论 → 原理 → 条件 → 反例/边界 → 工程控制 → 验证**。如果题目涉及生产环境，再补充可用性、兼容性、灰度和回滚。

### G. 这道题在真实工作中的“交付物”

Account recovery design + token lifecycle + abuse controls + session invalidation + audit。

### H. 一页纸复盘

| 维度 | 应该能说清楚什么 |
|---|---|
| 根因 | 恢复流程可绕过正常认证，因此必须同等级保护。 |
| 边界 | 恢复渠道、枚举、session 生命周期。 |
| 主要控制 | 高熵单次短期 token + rate limit + revoke。 |
| 关键证据 | reset/session/abuse audit。 |
| 验证 | reuse/expiry/enumeration/session tests。 |
