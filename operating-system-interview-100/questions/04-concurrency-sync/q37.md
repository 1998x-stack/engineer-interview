# Q37 Spinlock 与 Mutex 如何选择？

> **一句话核心结论**：Spinlock 用 CPU 忙等换避免 sleep/wakeup；Mutex 在竞争时可能让线程睡眠，节省 CPU 但增加调度路径。

## 1. 为什么面试官喜欢问这题

这道题不是单独考一个名词，而是在检查候选人是否能把 **spinlock → mutex → contention** 放进完整的操作系统因果链。优秀回答应同时覆盖：概念边界、底层机制、Why、trade-off，以及至少一个 Linux/工程落点。

## 2. 核心结论（原 PDF）

Spinlock 用 CPU 忙等换避免 sleep/wakeup；Mutex 在竞争时可能让线程睡眠，节省 CPU 但增加调度路径。

## 3. 深度解析（原 PDF）

当临界区极短、锁很快释放、不能睡眠的内核上下文或线程数与 CPU 数匹配时，spin 可能更合适。若锁可能持有较久、过度超额订阅或等待涉及 I/O，busy-wait 会浪费大量 CPU。现代 mutex 也可能先短暂自旋后再睡眠。

## 4. 仓库增强：从机制而不是术语理解

- 先明确正确性条件，再讨论性能；一个“更快”的同步方案如果没有清晰 happens-before，通常没有讨论价值。
- 锁的成本不是只有 lock/unlock 指令，还包括 cache-line bouncing、睡眠/唤醒、scheduler latency 和优先级问题。
- atomic 只能保证特定原子操作；数据结构正确性仍依赖不变量、内存序和生命周期管理。

### 4.2 面试时应主动说明的边界

- **概念边界**：不要把本题中的核心对象与相邻抽象混为一谈；先明确“谁负责什么”。
- **时间边界**：区分创建/注册/触发/完成/回收等阶段，很多 OS 题的坑来自把不同阶段压成一句话。
- **性能边界**：区分快路径与慢路径、缓存命中与未命中、用户态与内核态、无竞争与有竞争。
- **正确性边界**：说明机制保证了什么、没有保证什么；避免“只要用了 X 就一定线程安全/一定持久/一定异步”之类绝对化表述。

### 9.2 机制级推演：把每一步说清楚

面试中建议先给出这一条**总调用链**：

```text
共享不变量 → 原子/锁协议 → 等待/唤醒 → 内存可见性 → progress
```

再展开本题的具体状态变化：

1. 尝试原子获取锁。
2. 失败时spinlock继续忙等。
3. mutex通常在短暂自旋后进入阻塞慢路径。
4. unlock唤醒等待者。
5. 选择取决于临界区时长、可睡眠环境与CPU数量。

> **关键不变量**：内核不可睡眠上下文不能用会sleep的mutex；单核上无意义长自旋尤其糟糕。

### 9.3 性能模型：不要只说“快/慢”

粗略原则：期望等待时间若小于睡眠/唤醒/调度成本，spin可能有利；否则烧CPU。

建议在回答中至少显式区分下面四类成本：

| 成本类型 | 本题应该追问什么 |
|---|---|
| CPU | 是否存在额外指令、扫描、copy、原子重试、内核路径？ |
| Cache / TLB | 是否破坏局部性、触发 cache-line migration、TLB miss/shootdown？ |
| 调度 / 等待 | 是否会 sleep/wakeup、context switch、排队、throttling？ |
| I/O / 持久化 | 是否会触发设备访问、writeback、flush、network round trip？ |

**面试技巧**：如果不能定量到具体纳秒，也不要编数字。更专业的表达是给出“成本由哪些变量决定”，并说明要通过 benchmark/perf/trace 在目标机器上验证。

### 9.4 Linux 实现与源码阅读导航

不要试图背完整源码。先沿对象关系找到“状态放在哪里、谁改变它”。

| 对象 / 接口 | 阅读重点 |
|---|---|
| `spin_lock` | 同步原语；重点区分快路径、竞争慢路径、owner/等待队列及可睡眠性。 |
| `mutex` | 同步原语；重点区分快路径、竞争慢路径、owner/等待队列及可睡眠性。 |
| `adaptive spinning` | 同步原语；重点区分快路径、竞争慢路径、owner/等待队列及可睡眠性。 |
| `futex user-space locks` | 用户态同步的内核等待/唤醒慢路径；关注地址key、wait queue与PI变体。 |

### 9.5 边界条件、反例与“不要这样回答”

- **本题最重要边界**：内核不可睡眠上下文不能用会sleep的mutex；单核上无意义长自旋尤其糟糕。
- 不要把“常见实现”说成“POSIX/硬件永远保证”；架构、文件系统、内核版本和配置都可能改变细节。
- 不要把**机制存在**等同于**性能一定更好**。只有 workload、竞争度、数据规模和硬件条件确定后，性能结论才成立。
- 不要跳过错误路径：权限失败、资源耗尽、超时、signal、进程退出、设备错误等经常是高级追问来源。

### 9.10 90 秒高级回答：把定义、机制、性能和边界连成一段

> **可直接口述的参考结构**：
> 
> Spinlock 用 CPU 忙等换避免 sleep/wakeup；Mutex 在竞争时可能让线程睡眠，节省 CPU 但增加调度路径。机制上，我会把它拆成：尝试原子获取锁；失败时spinlock继续忙等；mutex通常在短暂自旋后进入阻塞慢路径；unlock唤醒等待者；选择取决于临界区时长、可睡眠环境与CPU数量。性能上，粗略原则：期望等待时间若小于睡眠/唤醒/调度成本，spin可能有利；否则烧CPU。 Linux/工程实现上要关注 `spin_lock / mutex / adaptive spinning / futex user-space locks`。最后我会主动补充边界：内核不可睡眠上下文不能用会sleep的mutex；单核上无意义长自旋尤其糟糕。 这样回答的重点不是堆术语，而是让面试官看到“语义 → 状态变化 → 成本 → 实现 → 边界”的完整因果链。

### 9.11 如何把这道题做成一个小型系统实验

把实验设计成 **hypothesis → variable → observation → falsification** 四步：

1. **Hypothesis**：先写一句可证伪假设，例如“当某个关键资源/路径进入慢路径时，本题描述的成本会显著上升”。
2. **Independent variable**：只改变一个变量，例如并发度、工作集大小、CPU affinity、I/O 深度、cache 冷热、cgroup limit。
3. **Observation**：同时记录业务结果与 OS 证据，至少包含延迟/吞吐中的一个，以及本题对应的 kernel counter/trace。
4. **Falsification**：如果指标没有按预期变化，不要修改结论去迎合结果；检查是否测错层、是否被缓存/批处理掩盖、是否实际没有进入目标慢路径。

**实验报告最少应包含**：

```text
环境：kernel / CPU / memory / filesystem / container limits
负载：输入规模 / 并发 / 持续时间
变量：本轮只改变什么
结果：throughput / avg / P95 / P99（按适用场景选择）
OS证据：perf / proc / PSI / iostat / strace / tracepoint 中相关指标
结论：支持还是推翻原假设
```
