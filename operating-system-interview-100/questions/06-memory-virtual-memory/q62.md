# Q62 Page Fault 发生后 OS 做什么？

> **一句话核心结论**：CPU 发现 translation 不存在或权限不允许后同步陷入 kernel；kernel 检查 VA 是否属于合法 VMA，再决定建立匿名页、读取文件页、执行 COW、扩栈或向进程发送错误信号。

## 1. 为什么面试官喜欢问这题

这道题不是单独考一个名词，而是在检查候选人是否能把 **page-fault → fault-handler** 放进完整的操作系统因果链。优秀回答应同时覆盖：概念边界、底层机制、Why、trade-off，以及至少一个 Linux/工程落点。

## 2. 核心结论（原 PDF）

CPU 发现 translation 不存在或权限不允许后同步陷入 kernel；kernel 检查 VA 是否属于合法 VMA，再决定建立匿名页、读取文件页、执行 COW、扩栈或向进程发送错误信号。

## 3. 深度解析（原 PDF）

合法 fault 的处理路径取决于 mapping 类型；若需要磁盘 I/O，线程可能睡眠，完成后更新 PTE/TLB 并重新执行 faulting instruction。非法地址或违规写入则可能导致 SIGSEGV。

## 4. 仓库增强：从机制而不是术语理解

- 虚拟内存题应始终沿“地址翻译”和“页面驻留”两条线分开：TLB/page table 负责翻译，page fault/reclaim 负责驻留与权限异常。
- TLB miss、minor fault、major fault 是三个不同层级事件，成本差异可能跨多个数量级。
- 内存性能最终与 locality、working set、reclaim、NUMA 和 I/O 相关，不能只看 RSS。

### 4.2 面试时应主动说明的边界

- **概念边界**：不要把本题中的核心对象与相邻抽象混为一谈；先明确“谁负责什么”。
- **时间边界**：区分创建/注册/触发/完成/回收等阶段，很多 OS 题的坑来自把不同阶段压成一句话。
- **性能边界**：区分快路径与慢路径、缓存命中与未命中、用户态与内核态、无竞争与有竞争。
- **正确性边界**：说明机制保证了什么、没有保证什么；避免“只要用了 X 就一定线程安全/一定持久/一定异步”之类绝对化表述。

## 9. Linux / 工程实践

**建议实验：观察 fault、映射、reclaim 与 NUMA**

```bash
vmstat 1
pidstat -r -p <PID> 1
cat /proc/<PID>/smaps_rollup
numastat -p <PID> 2>/dev/null || true
```

这些命令不是为了“背工具”，而是训练从 OS 抽象回到可观测证据：看到什么现象、对应哪个内核子系统、下一步如何验证。

### 9.1 专项示例

```bash
perf stat -e page-faults,minor-faults,major-faults <command>
pidstat -r -p <PID> 1
```

fault 发生后先判断地址是否合法，再判断是 demand allocation、COW、file-backed fault 还是保护异常；只有一部分 fault 需要真正的存储 I/O。

### 9.2 机制级推演：把每一步说清楚

面试中建议先给出这一条**总调用链**：

```text
VA → TLB/page table → fault/reclaim → physical/page cache → observable metrics
```

再展开本题的具体状态变化：

1. CPU因not-present或permission问题触发fault。
2. 内核读取fault地址与访问类型。
3. 查找对应VMA并验证合法性。
4. 若是匿名页分配/zero-fill，文件映射则查page cache/读盘，COW则复制。
5. 更新页表并重试；非法则向进程发送SIGSEGV等。

> **关键不变量**：page fault不等于错误；demand paging和COW依赖“正常fault”。

### 9.3 性能模型：不要只说“快/慢”

minor fault不需阻塞读盘；major fault通常涉及存储I/O，尾延迟差异可达多个数量级。

建议在回答中至少显式区分下面四类成本：

| 成本类型 | 本题应该追问什么 |
|---|---|
| CPU | 是否存在额外指令、扫描、copy、原子重试、内核路径？ |
| Cache / TLB | 是否破坏局部性、触发 cache-line migration、TLB miss/shootdown？ |
| 调度 / 等待 | 是否会 sleep/wakeup、context switch、排队、throttling？ |
| I/O / 持久化 | 是否会触发设备访问、writeback、flush、network round trip？ |

**面试技巧**：如果不能定量到具体纳秒，也不要编数字。更专业的表达是给出“成本由哪些变量决定”，并说明要通过 benchmark/perf/trace 在目标机器上验证。

### 9.4 Linux 实现与源码阅读导航

不要试图背完整源码。先沿对象关系找到“状态放在哪里、谁改变它”。

| 对象 / 接口 | 阅读重点 |
|---|---|
| `handle_mm_fault` | 沿调用链确认它保存的状态、引用关系、快/慢路径以及可从用户态观察到的结果。 |
| `VMA lookup` | 连续虚拟地址区间及其权限/后备对象；page fault合法性判断的重要入口。 |
| `page cache` | 文件页缓存/映射；关注cache hit、dirty、readahead与writeback。 |
| `SIGSEGV` | 沿调用链确认它保存的状态、引用关系、快/慢路径以及可从用户态观察到的结果。 |

源码阅读建议遵循：

```text
用户态 API / syscall
        ↓
入口函数与参数校验
        ↓
核心内核对象 / 状态机
        ↓
等待队列 / 调度 / MM / VFS / block 等相邻子系统
        ↓
返回值、错误码与可观测指标
```

### 9.5 边界条件、反例与“不要这样回答”

- **本题最重要边界**：page fault不等于错误；demand paging和COW依赖“正常fault”。
- 不要把“常见实现”说成“POSIX/硬件永远保证”；架构、文件系统、内核版本和配置都可能改变细节。
- 不要把**机制存在**等同于**性能一定更好**。只有 workload、竞争度、数据规模和硬件条件确定后，性能结论才成立。
- 不要跳过错误路径：权限失败、资源耗尽、超时、signal、进程退出、设备错误等经常是高级追问来源。

### 9.6 高级面试追问树

1. 如果把第 2 步拿掉，系统会失去什么正确性或性能保证？
2. 这个机制在“无竞争/命中快路径”和“竞争/缺失慢路径”下分别发生什么？
3. 如何用 Linux 指标或 tracing 证明瓶颈真的来自本题机制，而不是相邻子系统？
4. 如果要求你在生产环境验证自己的答案，你会选哪些 **counter / tracepoint / syscall / /proc / cgroup** 证据？为什么？
5. 如果把环境从单核变成多核、从本地SSD变成网络存储、或从宿主机变成容器，这个结论哪里会变化？

### 9.7 可复现实验：从“知道”升级到“证据”


不要只截图一个结果；至少改变一个变量（例如并发度、文件大小、CPU affinity、cache冷热、内存压力）做对照实验。

### 9.10 90 秒高级回答：把定义、机制、性能和边界连成一段

> **可直接口述的参考结构**：
> 
> CPU 发现 translation 不存在或权限不允许后同步陷入 kernel；kernel 检查 VA 是否属于合法 VMA，再决定建立匿名页、读取文件页、执行 COW、扩栈或向进程发送错误信号。机制上，我会把它拆成：CPU因not-present或permission问题触发fault；内核读取fault地址与访问类型；查找对应VMA并验证合法性；若是匿名页分配/zero-fill，文件映射则查page cache/读盘，COW则复制；更新页表并重试；非法则向进程发送SIGSEGV等。性能上，minor fault不需阻塞读盘；major fault通常涉及存储I/O，尾延迟差异可达多个数量级。 Linux/工程实现上要关注 `handle_mm_fault / VMA lookup / page cache / SIGSEGV`。最后我会主动补充边界：page fault不等于错误；demand paging和COW依赖“正常fault”。 这样回答的重点不是堆术语，而是让面试官看到“语义 → 状态变化 → 成本 → 实现 → 边界”的完整因果链。

### 9.11 如何把这道题做成一个小型系统实验

把实验设计成 **hypothesis → variable → observation → falsification** 四步：

1. **Hypothesis**：先写一句可证伪假设，例如“当某个关键资源/路径进入慢路径时，本题描述的成本会显著上升”。
2. **Independent variable**：只改变一个变量，例如并发度、工作集大小、CPU affinity、I/O 深度、cache 冷热、cgroup limit。
3. **Observation**：同时记录业务结果与 OS 证据，至少包含延迟/吞吐中的一个，以及本题对应的 kernel counter/trace。
4. **Falsification**：如果指标没有按预期变化，不要修改结论去迎合结果；检查是否测错层、是否被缓存/批处理掩盖、是否实际没有进入目标慢路径。

**实验报告最少应包含**：

```text
环境：kernel / CPU / memory / filesystem / container limits
负载：输入规模 / 并发 / 持续时间
变量：本轮只改变什么
结果：throughput / avg / P95 / P99（按适用场景选择）
OS证据：perf / proc / PSI / iostat / strace / tracepoint 中相关指标
结论：支持还是推翻原假设
```
