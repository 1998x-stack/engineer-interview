# Q83 打开的文件被 rm 后为什么还能继续读？

> **一句话核心结论**：rm/unlink 删除的是目录项名称，而已经打开的 FD 仍持有内核对文件对象的引用。只有 link count 为 0 且没有打开引用时，文件数据才真正可回收。

## 1. 为什么面试官喜欢问这题

这道题不是单独考一个名词，而是在检查候选人是否能把 **unlink → open-reference → link-count** 放进完整的操作系统因果链。优秀回答应同时覆盖：概念边界、底层机制、Why、trade-off，以及至少一个 Linux/工程落点。

## 2. 核心结论（原 PDF）

rm/unlink 删除的是目录项名称，而已经打开的 FD 仍持有内核对文件对象的引用。只有 link count 为 0 且没有打开引用时，文件数据才真正可回收。

## 3. 深度解析（原 PDF）

这也是日志轮转、临时文件和“磁盘空间看似被占用但路径已不存在”故障的关键。可通过 /proc/<pid>/fd 查找 deleted open files。

## 4. 仓库增强：从机制而不是术语理解

- 先分清 namespace、对象身份、打开实例和缓存：filename、inode、open file description、fd、page cache 是不同层级。
- “write 返回”与“durable”不是同义词；崩溃一致性要讨论 writeback、fsync、journal 和设备 flush。
- 优化文件 I/O 时应先确认瓶颈是在 page cache、filesystem、block layer 还是设备，而不是直接套 direct I/O。

### 4.2 面试时应主动说明的边界

- **概念边界**：不要把本题中的核心对象与相邻抽象混为一谈；先明确“谁负责什么”。

### 9.2 机制级推演：把每一步说清楚

面试中建议先给出这一条**总调用链**：

```text
fd/path → VFS → dentry/inode/page cache → filesystem/block → stable storage
```

再展开本题的具体状态变化：

1. open建立struct file并增加对象引用。
2. rm/unlink删除目录项并减少inode link count。
3. 若link count变0但仍有open reference，inode/data仍保留。
4. 进程继续通过fd访问对象。
5. 最后一个open reference关闭后才可真正回收。

> **关键不变量**：路径名消失不等于对象立即消失；namespace生命周期和open object生命周期是两层。

### 9.3 性能模型：不要只说“快/慢”

日志文件“deleted但仍占磁盘”是经典运维问题，可通过lsof +L1定位。

建议在回答中至少显式区分下面四类成本：

| 成本类型 | 本题应该追问什么 |
|---|---|
| CPU | 是否存在额外指令、扫描、copy、原子重试、内核路径？ |
| Cache / TLB | 是否破坏局部性、触发 cache-line migration、TLB miss/shootdown？ |
| 调度 / 等待 | 是否会 sleep/wakeup、context switch、排队、throttling？ |
| I/O / 持久化 | 是否会触发设备访问、writeback、flush、network round trip？ |

**面试技巧**：如果不能定量到具体纳秒，也不要编数字。更专业的表达是给出“成本由哪些变量决定”，并说明要通过 benchmark/perf/trace 在目标机器上验证。

### 9.4 Linux 实现与源码阅读导航

不要试图背完整源码。先沿对象关系找到“状态放在哪里、谁改变它”。

| 对象 / 接口 | 阅读重点 |
|---|---|
| `unlink` | 沿调用链确认它保存的状态、引用关系、快/慢路径以及可从用户态观察到的结果。 |
| `inode i_nlink` | 文件系统对象元数据与数据映射身份；注意它不同于文件名和打开实例。 |
| `struct file refcount` | 进程打开文件状态；关注fd索引、open file description、offset/flags与引用计数。 |
| `dentry` | 路径名缓存/目录项对象；关注name lookup、负dentry及与inode的关系。 |

源码阅读建议遵循：

```text
用户态 API / syscall
        ↓
入口函数与参数校验
        ↓
核心内核对象 / 状态机
        ↓
等待队列 / 调度 / MM / VFS / block 等相邻子系统
        ↓
返回值、错误码与可观测指标
```

### 9.5 边界条件、反例与“不要这样回答”

- **本题最重要边界**：路径名消失不等于对象立即消失；namespace生命周期和open object生命周期是两层。
- 不要把“常见实现”说成“POSIX/硬件永远保证”；架构、文件系统、内核版本和配置都可能改变细节。
- 不要把**机制存在**等同于**性能一定更好**。只有 workload、竞争度、数据规模和硬件条件确定后，性能结论才成立。
- 不要跳过错误路径：权限失败、资源耗尽、超时、signal、进程退出、设备错误等经常是高级追问来源。

### 9.6 高级面试追问树

1. 如果把第 2 步拿掉，系统会失去什么正确性或性能保证？
2. 这个机制在“无竞争/命中快路径”和“竞争/缺失慢路径”下分别发生什么？
3. 如何用 Linux 指标或 tracing 证明瓶颈真的来自本题机制，而不是相邻子系统？
4. 如果要求你在生产环境验证自己的答案，你会选哪些 **counter / tracepoint / syscall / /proc / cgroup** 证据？为什么？
5. 如果把环境从单核变成多核、从本地SSD变成网络存储、或从宿主机变成容器，这个结论哪里会变化？

### 9.10 90 秒高级回答：把定义、机制、性能和边界连成一段

> **可直接口述的参考结构**：
> 
> rm/unlink 删除的是目录项名称，而已经打开的 FD 仍持有内核对文件对象的引用。只有 link count 为 0 且没有打开引用时，文件数据才真正可回收。机制上，我会把它拆成：open建立struct file并增加对象引用；rm/unlink删除目录项并减少inode link count；若link count变0但仍有open reference，inode/data仍保留；进程继续通过fd访问对象；最后一个open reference关闭后才可真正回收。性能上，日志文件“deleted但仍占磁盘”是经典运维问题，可通过lsof +L1定位。 Linux/工程实现上要关注 `unlink / inode i_nlink / struct file refcount / dentry`。最后我会主动补充边界：路径名消失不等于对象立即消失；namespace生命周期和open object生命周期是两层。 这样回答的重点不是堆术语，而是让面试官看到“语义 → 状态变化 → 成本 → 实现 → 边界”的完整因果链。

### 9.11 如何把这道题做成一个小型系统实验

把实验设计成 **hypothesis → variable → observation → falsification** 四步：

1. **Hypothesis**：先写一句可证伪假设，例如“当某个关键资源/路径进入慢路径时，本题描述的成本会显著上升”。
2. **Independent variable**：只改变一个变量，例如并发度、工作集大小、CPU affinity、I/O 深度、cache 冷热、cgroup limit。
3. **Observation**：同时记录业务结果与 OS 证据，至少包含延迟/吞吐中的一个，以及本题对应的 kernel counter/trace。
4. **Falsification**：如果指标没有按预期变化，不要修改结论去迎合结果；检查是否测错层、是否被缓存/批处理掩盖、是否实际没有进入目标慢路径。

**实验报告最少应包含**：

```text
环境：kernel / CPU / memory / filesystem / container limits
负载：输入规模 / 并发 / 持续时间
变量：本轮只改变什么
结果：throughput / avg / P95 / P99（按适用场景选择）
OS证据：perf / proc / PSI / iostat / strace / tracepoint 中相关指标
结论：支持还是推翻原假设
```
