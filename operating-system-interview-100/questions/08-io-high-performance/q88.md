# Q88 epoll LT 与 ET 有什么区别？

> **一句话核心结论**：LT 只要 FD 仍处于 ready 状态就会持续报告；ET 通常只在状态从非 ready 变为 ready 的边缘报告，因此必须一次尽量 drain 到 EAGAIN。

## 1. 为什么面试官喜欢问这题

这道题不是单独考一个名词，而是在检查候选人是否能把 **level-triggered → edge-triggered** 放进完整的操作系统因果链。优秀回答应同时覆盖：概念边界、底层机制、Why、trade-off，以及至少一个 Linux/工程落点。

## 2. 核心结论（原 PDF）

LT 只要 FD 仍处于 ready 状态就会持续报告；ET 通常只在状态从非 ready 变为 ready 的边缘报告，因此必须一次尽量 drain 到 EAGAIN。

## 3. 深度解析（原 PDF）

ET 常与 non-blocking FD 配合，否则某个 read 阻塞会卡住整个事件线程。ET 可减少重复通知，但状态机更复杂；LT 更容易写正确，性能未必差到必须换 ET。

## 4. 仓库增强：从机制而不是术语理解

- 先区分 readiness 与 completion，再讨论 select/poll/epoll/io_uring；这比背 API 差异更能应对追问。
- I/O 性能是 queueing、copy、syscall、context switch、interrupt/DMA 与设备并行度共同决定的。
- 所谓 zero-copy 通常是减少 CPU 参与的内存复制，不代表数据在硬件中从未移动。

## 9. Linux / 工程实践

**建议实验：观察 fd readiness、网络与设备 I/O**

```bash
ss -s
cat /proc/interrupts | head
iostat -xz 1
strace -f -e trace=epoll_wait,epoll_ctl,read,write <command>
```

这些命令不是为了“背工具”，而是训练从 OS 抽象回到可观测证据：看到什么现象、对应哪个内核子系统、下一步如何验证。

### 9.1 专项示例

```c
// ET 常见原则：non-blocking + drain until EAGAIN
for (;;) {
    ssize_t n = read(fd, buf, sizeof(buf));
    if (n > 0) consume(buf, n);
    else if (n < 0 && errno == EAGAIN) break;
    else break;
}
```

### 9.2 机制级推演：把每一步说清楚

面试中建议先给出这一条**总调用链**：

```text
submission/readiness → kernel queue → device/DMA → completion → event loop
```

再展开本题的具体状态变化：

1. LT在fd保持ready时可重复报告。
2. ET只在状态边缘变化时提示。
3. ET处理函数必须把资源drain到EAGAIN。
4. fd通常设为non-blocking避免单个连接阻塞event loop。
5. 遗漏drain会因没有新edge而造成“明明有数据却不再通知”。

> **关键不变量**：ET不是“一次只读一次”；恰恰通常要循环read直到EAGAIN。

### 9.3 性能模型：不要只说“快/慢”

ET可减少重复通知，但提高状态机正确性要求；LT更稳健易写。

建议在回答中至少显式区分下面四类成本：

| 成本类型 | 本题应该追问什么 |
|---|---|
| CPU | 是否存在额外指令、扫描、copy、原子重试、内核路径？ |
| Cache / TLB | 是否破坏局部性、触发 cache-line migration、TLB miss/shootdown？ |
| 调度 / 等待 | 是否会 sleep/wakeup、context switch、排队、throttling？ |
| I/O / 持久化 | 是否会触发设备访问、writeback、flush、network round trip？ |

**面试技巧**：如果不能定量到具体纳秒，也不要编数字。更专业的表达是给出“成本由哪些变量决定”，并说明要通过 benchmark/perf/trace 在目标机器上验证。

### 9.5 边界条件、反例与“不要这样回答”

- **本题最重要边界**：ET不是“一次只读一次”；恰恰通常要循环read直到EAGAIN。
- 不要把“常见实现”说成“POSIX/硬件永远保证”；架构、文件系统、内核版本和配置都可能改变细节。
- 不要把**机制存在**等同于**性能一定更好**。只有 workload、竞争度、数据规模和硬件条件确定后，性能结论才成立。
- 不要跳过错误路径：权限失败、资源耗尽、超时、signal、进程退出、设备错误等经常是高级追问来源。

### 9.10 90 秒高级回答：把定义、机制、性能和边界连成一段

> **可直接口述的参考结构**：
> 
> LT 只要 FD 仍处于 ready 状态就会持续报告；ET 通常只在状态从非 ready 变为 ready 的边缘报告，因此必须一次尽量 drain 到 EAGAIN。机制上，我会把它拆成：LT在fd保持ready时可重复报告；ET只在状态边缘变化时提示；ET处理函数必须把资源drain到EAGAIN；fd通常设为non-blocking避免单个连接阻塞event loop；遗漏drain会因没有新edge而造成“明明有数据却不再通知”。性能上，ET可减少重复通知，但提高状态机正确性要求；LT更稳健易写。 Linux/工程实现上要关注 `EPOLLET / O_NONBLOCK / epoll ready list`。最后我会主动补充边界：ET不是“一次只读一次”；恰恰通常要循环read直到EAGAIN。 这样回答的重点不是堆术语，而是让面试官看到“语义 → 状态变化 → 成本 → 实现 → 边界”的完整因果链。

### 9.11 如何把这道题做成一个小型系统实验

把实验设计成 **hypothesis → variable → observation → falsification** 四步：

1. **Hypothesis**：先写一句可证伪假设，例如“当某个关键资源/路径进入慢路径时，本题描述的成本会显著上升”。
2. **Independent variable**：只改变一个变量，例如并发度、工作集大小、CPU affinity、I/O 深度、cache 冷热、cgroup limit。
3. **Observation**：同时记录业务结果与 OS 证据，至少包含延迟/吞吐中的一个，以及本题对应的 kernel counter/trace。
4. **Falsification**：如果指标没有按预期变化，不要修改结论去迎合结果；检查是否测错层、是否被缓存/批处理掩盖、是否实际没有进入目标慢路径。

**实验报告最少应包含**：

```text
环境：kernel / CPU / memory / filesystem / container limits
负载：输入规模 / 并发 / 持续时间
变量：本轮只改变什么
结果：throughput / avg / P95 / P99（按适用场景选择）
OS证据：perf / proc / PSI / iostat / strace / tracepoint 中相关指标
结论：支持还是推翻原假设
```
