# Q06. None 到底是什么？为什么推荐 is None？

> **难度**：★  ·  **频率**：高  ·  **关键词**：`None`, `singleton`, `identity`

## 题目定位

判断候选人是否真正理解 Python 语义，而不是依赖“像 C++/Java 一样”的类比。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **None / singleton / identity** 的可推导模型。把“名字绑定、对象身份、对象状态、求值时机”四条线分开。遇到反直觉代码，先画名字到对象的引用关系，再判断操作是原地修改还是重新绑定。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

这类题的高分标准通常不是“知道答案”，而是能在 30-60 秒内先给清晰结论，并在追问时继续下钻到机制、边界和工程代价。

## 30-60 秒标准回答

> `None` 是 `NoneType` 的唯一常用实例，用来表示“没有值/缺失结果”等语义。检查它时推荐 identity comparison。

## 最小可运行实验

```python
_MISSING = object()

def f(value=_MISSING):
    if value is _MISSING:
        return 'argument not provided'
    if value is None:
        return 'explicit None'
```

### 实验怎么读

代码共 6 个非空行，建议逐行观察“名字绑定/对象状态/控制流”的变化，而不是只看最终输出。

### 1. 机制链路：这道题到底在系统的哪一层发生？

None 是 NoneType 的唯一实例，语义上常用于“缺失/无结果”哨兵；身份比较可绕开用户自定义 __eq__。

建议面试时把机制画成一条因果链，而不是堆术语：

```text
输入 / 语法 / API
        ↓
协议或对象模型
        ↓
CPython/标准库实现路径
        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q06. None 到底是什么？为什么推荐 is None？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

None 与 falsy 值不是同义词；0、''、[] 可能是合法业务值，不能用 if not x 代替 is None。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

本章多数题不是 Big-O 题，而是**语义成本题**：一次赋值究竟只是名字绑定，还是会触发对象创建、比较协议、哈希或用户代码。面试时要把“可观察语义”和“CPython 当前实现成本”分开。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

### 4. 生产工程场景

配置合并、数据库字段、缓存 miss 都要区分“没有值”和“值恰好为空/0”。

一个合格的工程回答不应停在“可以/不可以”，而应给出**选择依据**。推荐使用：

```text
需求约束 → 候选方案 → 成本/风险 → 观测指标 → 回退方案
```

这会自然把 Python 语法题提升到系统设计和可维护性层面。

### 5. CPython / 标准库源码阅读入口

**建议阅读入口：** Objects/object.c 中 None 单例相关实现；Data Model / builtins 文档。

源码阅读不要求面试现场背文件内容，而是要建立三个习惯：

1. 先从官方文档确定**语言/API 契约**；

### 6. 面试追问：完整回答示范

**追问：如果面试官故意把条件改掉，应该怎么回答？**

追问“为什么不是 == None”时答：== 可执行用户代码且可被重载，is None 更直接表达单例身份语义。

**推荐回答结构：**

1. 先指出新条件改变了哪个前提；
2. 保留仍然成立的语义；
3. 撤回不再成立的实现/性能结论；
4. 给一个最小反例或测量方法。

这种回答方式比“我记得文档说……”更稳健，也更容易应对陌生变体。

### 7. 实验升级：把结论变成可证伪假设

实现一个 __eq__ 对 None 返回 True 的怪异类，验证 == 与 is 的差异。

建议实验遵循：

```text
先写预测
  ↓
固定 Python 版本与平台
  ↓
运行最小实验
  ↓
记录输出 / 时间 / 内存 / 状态
  ↓
解释与预测不一致的地方
```

不要只贴运行结果；真正有价值的是解释“为什么”。性能实验至少 warm-up、多轮重复，并避免用单次 wall-clock 得出绝对结论。
