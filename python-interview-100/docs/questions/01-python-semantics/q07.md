# Q07. Python 的 truthy / falsy 规则是什么？

> **难度**：★★  ·  **频率**：高  ·  **关键词**：`bool`, `__bool__`, `__len__`

## 题目定位

判断候选人是否真正理解 Python 语义，而不是依赖“像 C++/Java 一样”的类比。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **bool / __bool__ / __len__** 的可推导模型。把“名字绑定、对象身份、对象状态、求值时机”四条线分开。遇到反直觉代码，先画名字到对象的引用关系，再判断操作是原地修改还是重新绑定。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

这类题的高分标准通常不是“知道答案”，而是能在 30-60 秒内先给清晰结论，并在追问时继续下钻到机制、边界和工程代价。

## 30-60 秒标准回答

> 布尔上下文并不要求对象本身是 bool。对象可以通过 `__bool__` 定义真假；若没有，通常会尝试 `__len__`；长度为 0 视为 False。

## 最小可运行实验

```python
class Bag:
    def __init__(self, items):
        self.items = items
    def __len__(self):
        return len(self.items)

print(bool(Bag([])))  # False
```

### 实验怎么读

代码共 6 个非空行，建议逐行观察“名字绑定/对象状态/控制流”的变化，而不是只看最终输出。 运行时先预测输出，再执行验证；预测错误的地方通常就是心智模型缺口。 类相关示例建议配合 `type()`、`__dict__`、`__mro__` 或 descriptor 方法调用顺序观察。

## 深度扩展：从“会答”到“能推导”

> 本节是仓库增强版新增内容。原题/PDF 给出核心结论；这里进一步补充机制、边界、工程决策和源码阅读入口。实现细节以 **Python 3.14 / CPython** 为主要基线，凡属于 CPython 当前实现而非语言规范的内容均按实现视角理解。

### 1. 机制链路：这道题到底在系统的哪一层发生？

bool(x) 优先使用 __bool__，缺失时回退 __len__；二者都未定义的普通对象默认真。

建议面试时把机制画成一条因果链，而不是堆术语：

```text
输入 / 语法 / API
        ↓
协议或对象模型
        ↓
CPython/标准库实现路径
        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q07. Python 的 truthy / falsy 规则是什么？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

__len__ 必须返回非负整数；错误实现会抛异常。truthiness 与“业务有效性”不是一回事。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

本章多数题不是 Big-O 题，而是**语义成本题**：一次赋值究竟只是名字绑定，还是会触发对象创建、比较协议、哈希或用户代码。面试时要把“可观察语义”和“CPython 当前实现成本”分开。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

### 4. 生产工程场景

设计领域对象时谨慎重载 __bool__，否则 if obj 的语义可能让调用者误判“存在/有效/非空”。

一个合格的工程回答不应停在“可以/不可以”，而应给出**选择依据**。推荐使用：

```text
需求约束 → 候选方案 → 成本/风险 → 观测指标 → 回退方案
```

这会自然把 Python 语法题提升到系统设计和可维护性层面。

### 5. CPython / 标准库源码阅读入口

**建议阅读入口：** Objects/object.c 的 PyObject_IsTrue；Data Model 的 truth value testing。

源码阅读不要求面试现场背文件内容，而是要建立三个习惯：

1. 先从官方文档确定**语言/API 契约**；
2. 再去 CPython 源码确认**当前实现为什么产生这种成本与行为**；
3. 最后用 `dis`、`inspect`、`timeit`、`tracemalloc`、最小并发实验等手段做可重复验证。

> 注意：CPython 内部函数名、文件组织和优化策略可能跨版本变化；源码细节只能用于解释当前实现，不能反向扩大为语言规范。

### 6. 面试追问：完整回答示范

**追问：如果面试官故意把条件改掉，应该怎么回答？**

追问“and/or 为什么能短路”时，可连接到 Q08：先求当前操作数真值，再决定是否求值右侧表达式。

**推荐回答结构：**

1. 先指出新条件改变了哪个前提；
2. 保留仍然成立的语义；
3. 撤回不再成立的实现/性能结论；
4. 给一个最小反例或测量方法。

这种回答方式比“我记得文档说……”更稳健，也更容易应对陌生变体。

### 7. 实验升级：把结论变成可证伪假设

自定义 __bool__ 打印日志，验证短路求值顺序和调用次数。

建议实验遵循：

```text
先写预测
  ↓
固定 Python 版本与平台
  ↓
运行最小实验
  ↓
记录输出 / 时间 / 内存 / 状态
  ↓
解释与预测不一致的地方
```

不要只贴运行结果；真正有价值的是解释“为什么”。性能实验至少 warm-up、多轮重复，并避免用单次 wall-clock 得出绝对结论。
