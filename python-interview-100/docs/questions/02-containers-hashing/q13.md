# Q13. 为什么 list.insert(0, x) / pop(0) 慢？

> **难度**：★  ·  **频率**：高  ·  **关键词**：`list`, `deque`, `data structure`

## 题目定位

判断候选人能否把容器 API 与底层数据结构、复杂度和哈希契约连接起来。

## 30-60 秒标准回答

> list 的元素引用位于连续数组中，头部插入/删除需要移动大量引用，复杂度 O(n)。两端频繁操作应考虑 deque。

## 最小可运行实验

```python
from collections import deque
q = deque()
q.append(1)
q.appendleft(0)
q.popleft()
```

### 实验怎么读

代码共 5 个非空行，建议逐行观察“名字绑定/对象状态/控制流”的变化，而不是只看最终输出。

- ❌ **常见误区**：把 deque 当成 list 的完全替代品。
  - **改进方式**：回答时先声明适用范围，再用一个反例或最小实验校验结论。

### 1. 机制链路：这道题到底在系统的哪一层发生？

list 头部插入/删除需要移动后续大量指针槽位，因此是 O(n)；deque 通过分块双端结构优化两端操作。

建议面试时把机制画成一条因果链，而不是堆术语：

```text
输入 / 语法 / API
        ↓
协议或对象模型
        ↓
CPython/标准库实现路径
        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q13. 为什么 list.insert(0, x) / pop(0) 慢？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

deque 的随机索引并不等价于 list；“换成 deque”应基于操作模式，而不是看到 O(n) 就机械替换。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

容器题必须同时回答**时间复杂度、空间成本、常数因子与退化条件**。平均 O(1) 不等于最坏 O(1)，摊还 O(1) 不等于每次 O(1)。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

### 4. 生产工程场景

队列/滑动窗口使用 deque；需要紧凑随机访问和尾部 append 的场景仍优先 list。

一个合格的工程回答不应停在“可以/不可以”，而应给出**选择依据**。推荐使用：

```text
需求约束 → 候选方案 → 成本/风险 → 观测指标 → 回退方案
```

### 7. 实验升级：把结论变成可证伪假设

timeit 比较 list.pop(0) 与 deque.popleft 在不同 n 下的趋势，不强调某台机器的绝对数字。

建议实验遵循：

```text
先写预测
```
