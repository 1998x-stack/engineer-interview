# Q29. lambda 与普通 def 的区别是什么？

> **难度**：★  ·  **频率**：中  ·  **关键词**：`lambda`, `expression`, `readability`

## 题目定位

判断候选人是否理解函数对象、作用域与调用包装，而不仅会写装饰器模板。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **lambda / expression / readability** 的可推导模型。所有函数机制题都问两个时间点：定义时发生什么、调用时发生什么。闭包、默认参数、装饰器、缓存都能用这个框架统一。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

这类题的高分标准通常不是“知道答案”，而是能在 30-60 秒内先给清晰结论，并在追问时继续下钻到机制、边界和工程代价。

## 30-60 秒标准回答

> lambda 创建匿名函数，函数体限制为单个表达式；它不是更快的函数语法。简单 key/callback 很适合，复杂逻辑应使用 def。

## 高分回答的四层结构

- **第一层 - 结论**：lambda 创建匿名函数，函数体限制为单个表达式；它不是更快的函数语法。简单 key/callback 很适合，复杂逻辑应使用 def。
- **第二层 - 原因**：挑选“原理拆解”中的 2-3 个关键点解释为什么，而不是重复定义。
- **第三层 - 边界**：主动说出至少一个 Gotcha，证明你知道结论并非无条件成立。
- **第四层 - 工程化**：把结论落到 API 设计、性能、并发、可维护性或调试策略。

所有函数机制题都问两个时间点：定义时发生什么、调用时发生什么。闭包、默认参数、装饰器、缓存都能用这个框架统一。

## 最小可运行实验

```python
users = [{'name': 'a', 'score': 9}, {'name': 'b', 'score': 7}]
users.sort(key=lambda u: u['score'], reverse=True)
```

### 实验怎么读

代码共 2 个非空行，建议逐行观察“名字绑定/对象状态/控制流”的变化，而不是只看最终输出。

### 1. 机制链路：这道题到底在系统的哪一层发生？

lambda 创建普通函数对象，只是语法受限为单个表达式且名字/可读性不同；性能不是其核心优势。

建议面试时把机制画成一条因果链，而不是堆术语：

```text

        ↓

        ↓

        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q29. lambda 与普通 def 的区别是什么？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

复杂 lambda 会降低 tracebacks、类型注解与调试可读性；不要为了“一行代码”牺牲维护性。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

函数机制的成本主要来自调用层级、闭包持有对象、包装器额外调用、缓存空间和 introspection。先保证语义与可维护性，再讨论微优化。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

### 4. 生产工程场景

排序 key、短小回调适合 lambda；领域逻辑、复用逻辑用 def。

一个合格的工程回答不应停在“可以/不可以”，而应给出**选择依据**。推荐使用：

```text
需求约束 → 候选方案 → 成本/风险 → 观测指标 → 回退方案
```

这会自然把 Python 语法题提升到系统设计和可维护性层面。

### 5. CPython / 标准库源码阅读入口

**建议阅读入口：** Grammar/Python/compile.c；Objects/funcobject.c。

源码阅读不要求面试现场背文件内容，而是要建立三个习惯：

1. 先从官方文档确定**语言/API 契约**；
2. 再去 CPython 源码确认**当前实现为什么产生这种成本与行为**；
3. 最后用 `dis`、`inspect`、`timeit`、`tracemalloc`、最小并发实验等手段做可重复验证。

> 注意：CPython 内部函数名、文件组织和优化策略可能跨版本变化；源码细节只能用于解释当前实现，不能反向扩大为语言规范。

### 6. 面试追问：完整回答示范

**追问：如果面试官故意把条件改掉，应该怎么回答？**

追问“lambda 能否有条件逻辑”时答：可使用条件表达式等 expression，但不能放 statement。

**推荐回答结构：**

1. 先指出新条件改变了哪个前提；
2. 保留仍然成立的语义；
3. 撤回不再成立的实现/性能结论；
4. 给一个最小反例或测量方法。

这种回答方式比“我记得文档说……”更稳健，也更容易应对陌生变体。

### 7. 实验升级：把结论变成可证伪假设

把一个多层 lambda 改写成 def，比较测试、类型提示和调试信息。

建议实验遵循：

```text
先写预测
  ↓
固定 Python 版本与平台
  ↓
运行最小实验
  ↓
记录输出 / 时间 / 内存 / 状态
```

不要只贴运行结果；真正有价值的是解释“为什么”。性能实验至少 warm-up、多轮重复，并避免用单次 wall-clock 得出绝对结论。
