# Q30. functools.lru_cache 有哪些工程陷阱？

> **难度**：★★★  ·  **频率**：高  ·  **关键词**：`cache`, `hashable`, `lifetime`

## 题目定位

判断候选人是否理解函数对象、作用域与调用包装，而不仅会写装饰器模板。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **cache / hashable / lifetime** 的可推导模型。所有函数机制题都问两个时间点：定义时发生什么、调用时发生什么。闭包、默认参数、装饰器、缓存都能用这个框架统一。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

这类题的高分标准通常不是“知道答案”，而是能在 30-60 秒内先给清晰结论，并在追问时继续下钻到机制、边界和工程代价。

## 30-60 秒标准回答

> `lru_cache` 通过参数作为 key 缓存返回值，适用于同输入同输出、参数可哈希且结果可安全复用的函数。它会持有 key/value，因此也影响对象生命周期和内存。

### 1. 机制链路：这道题到底在系统的哪一层发生？

lru_cache 用参数构造 hash key 保存结果，并用 LRU 结构限制容量；它改变了时间/空间和对象生命周期。


### 2. 边界条件：什么时候“标准答案”会失效？

缓存 instance method 会把 self 纳入 key，从而强引用实例；缓存依赖外部可变状态的函数会返回陈旧结果。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

函数机制的成本主要来自调用层级、闭包持有对象、包装器额外调用、缓存空间和 introspection。先保证语义与可维护性，再讨论微优化。
