# Q37. MRO 是什么？C3 linearization 解决什么问题？

> **难度**：★★★★  ·  **频率**：高  ·  **关键词**：`MRO`, `multiple inheritance`, `C3`

## 题目定位

判断候选人是否理解 Python 对象模型与属性查找协议，能否处理框架/ORM/元编程问题。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **MRO / multiple inheritance / C3** 的可推导模型。把属性访问看作协议而非“点号语法”。descriptor、MRO、super、metaclass 都是在控制对象模型中的查找与构造流程。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

这类题的高分标准通常不是“知道答案”，而是能在 30-60 秒内先给清晰结论，并在追问时继续下钻到机制、边界和工程代价。

## 30-60 秒标准回答

> MRO 决定多继承中的属性/方法查找顺序。Python 使用 C3 linearization 保证局部优先顺序、一致性与单调性。

## 高分回答的四层结构

- **第一层 - 结论**：MRO 决定多继承中的属性/方法查找顺序。Python 使用 C3 linearization 保证局部优先顺序、一致性与单调性。
- **第二层 - 原因**：挑选“原理拆解”中的 2-3 个关键点解释为什么，而不是重复定义。
- **第三层 - 边界**：主动说出至少一个 Gotcha，证明你知道结论并非无条件成立。
- **第四层 - 工程化**：把结论落到 API 设计、性能、并发、可维护性或调试策略。

## 最小可运行实验

```python
class A: pass
class B(A): pass
class C(A): pass
class D(B, C): pass
print(D.__mro__)
```

### 实验怎么读

代码共 5 个非空行，建议逐行观察“名字绑定/对象状态/控制流”的变化，而不是只看最终输出。 运行时先预测输出，再执行验证；预测错误的地方通常就是心智模型缺口。 类相关示例建议配合 `type()`、`__dict__`、`__mro__` 或 descriptor 方法调用顺序观察。

## 深度扩展：从“会答”到“能推导”

> 本节是仓库增强版新增内容。原题/PDF 给出核心结论；这里进一步补充机制、边界、工程决策和源码阅读入口。实现细节以 **Python 3.14 / CPython** 为主要基线，凡属于 CPython 当前实现而非语言规范的内容均按实现视角理解。

### 1. 机制链路：这道题到底在系统的哪一层发生？

MRO 给多继承定义一致的线性查找顺序；C3 需要保持局部优先级和单调性，避免子类改变祖先已有相对顺序。

建议面试时把机制画成一条因果链，而不是堆术语：

```text
输入 / 语法 / API
        ↓
协议或对象模型
        ↓
CPython/标准库实现路径
        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q37. MRO 是什么？C3 linearization 解决什么问题？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

不是所有继承图都可线性化；不一致基类顺序会在 class 创建时报错。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

对象模型题的核心成本是**属性查找链和抽象复杂度**。descriptor/metaclass 能力很强，但每增加一层隐式协议都会提高调试和维护成本。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

### 4. 生产工程场景

Mixin 设计必须遵循 cooperative 方法签名与 super 链；多继承复杂时组合通常更容易维护。

一个合格的工程回答不应停在“可以/不可以”，而应给出**选择依据**。推荐使用：

```text
需求约束 → 候选方案 → 成本/风险 → 观测指标 → 回退方案
```

这会自然把 Python 语法题提升到系统设计和可维护性层面。
