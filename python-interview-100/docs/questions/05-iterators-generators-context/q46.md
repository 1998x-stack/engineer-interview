# Q46. yield from 不只是语法糖吗？

> **难度**：★★★★  ·  **频率**：中  ·  **关键词**：`yield from`, `delegation`, `generator`

## 题目定位

判断候选人能否写出内存友好的惰性流水线，并正确管理资源和异常。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **yield from / delegation / generator** 的可推导模型。惰性计算的核心是“状态可以暂停并继续”，资源管理的核心是“所有控制流路径上都能确定性释放”。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

## 最小可运行实验

```python
def child():
    yield 1
    return 99

def parent():
    result = yield from child()
    print('child returned', result)
```

### 实验怎么读

代码共 6 个非空行，建议逐行观察“名字绑定/对象状态/控制流”的变化，而不是只看最终输出。 运行时先预测输出，再执行验证；预测错误的地方通常就是心智模型缺口。

## 易错点 / Gotchas

- ❌ **常见误区**：只说“等价于 for x in child: yield x”。

- ❌ **常见误区**：不知道 return value 可通过 yield from 获取。
  - **改进方式**：回答时先声明适用范围，再用一个反例或最小实验校验结论。

## 深度扩展：从“会答”到“能推导”

> 本节是仓库增强版新增内容。原题/PDF 给出核心结论；这里进一步补充机制、边界、工程决策和源码阅读入口。实现细节以 **Python 3.14 / CPython** 为主要基线，凡属于 CPython 当前实现而非语言规范的内容均按实现视角理解。

### 1. 机制链路：这道题到底在系统的哪一层发生？

yield from 建立委托关系，除了转发 yield 值，还转发 send/throw/close，并捕获子生成器的 StopIteration.value。

建议面试时把机制画成一条因果链，而不是堆术语：

```text
输入 / 语法 / API
        ↓
协议或对象模型
        ↓
CPython/标准库实现路径
        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q46. yield from 不只是语法糖吗？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

简单 for-yield 只转发值，不能完整模拟异常/双向通信/返回值协议。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

惰性计算的关键指标是**峰值内存、首项延迟、吞吐和可重复消费性**。O(1) 内存必须结合生成器内部状态与下游缓存一起判断。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

### 4. 生产工程场景

组合 parser/state machine 时 yield from 可减少委托样板；现代 async 使用 await 表达类似“暂停并委托”的思想。

一个合格的工程回答不应停在“可以/不可以”，而应给出**选择依据**。推荐使用：

```text
需求约束 → 候选方案 → 成本/风险 → 观测指标 → 回退方案
```

这会自然把 Python 语法题提升到系统设计和可维护性层面。

