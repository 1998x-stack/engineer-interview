# Q58. circular import 为什么会产生 partially initialized module？

> **难度**：★★★  ·  **频率**：极高  ·  **关键词**：`circular import`, `module initialization`, `architecture`

## 30-60 秒标准回答

> A 执行到 import B 后暂停；B 再 import A 时，A 已在 sys.modules 中但顶层代码尚未执行完，因此 B 可能访问到尚未定义的 A 属性。

### 1. 机制链路：这道题到底在系统的哪一层发生？

循环导入问题本质是“模块执行顺序 + 提前缓存未完成 module”；当 B 读取 A 尚未执行到的名字时就出现 partially initialized 错误。

建议面试时把机制画成一条因果链，而不是堆术语：

```text
输入 / 语法 / API
        ↓
协议或对象模型
        ↓
CPython/标准库实现路径
        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q58. circular import 为什么会产生 partially initialized module？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

把 import 移进函数可延迟依赖但不一定解决架构耦合；过多局部 import 会隐藏依赖图。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

CPython 内存题要区分**对象生命周期、Python heap、allocator、native heap 与 OS RSS**；import 题要区分查找、编译缓存和模块执行。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

### 4. 生产工程场景

常用治理是抽公共抽象到第三模块、依赖反转、只在 TYPE_CHECKING 下导入类型、减少 top-level side effects。

一个合格的工程回答不应停在“可以/不可以”，而应给出**选择依据**。推荐使用：

```text
需求约束 → 候选方案 → 成本/风险 → 观测指标 → 回退方案
```

### 6. 面试追问：完整回答示范

**追问：如果面试官故意把条件改掉，应该怎么回答？**

追问“为什么 from a import x 更容易失败”时答：它在导入时立即要求属性 x 已存在，而 import a 后晚些访问可能避开时间窗口。

2. 保留仍然成立的语义；
