# Q63. Python 3.14 free-threaded CPython 改变了什么？

> **难度**：★★★★★  ·  **频率**：高  ·  **关键词**：`free-threading`, `PEP703`, `Python3.14`

## 题目定位

判断候选人是否会基于 workload 和数据共享成本选择并行模型，同时理解现代 free-threaded Python 的边界。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **free-threading / PEP703 / Python3.14** 的可推导模型。并发选择是成本模型：CPU/I/O 比例、共享状态、序列化、隔离、第三方扩展兼容与部署模型共同决定方案。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

这类题的高分标准通常不是“知道答案”，而是能在 30-60 秒内先给清晰结论，并在追问时继续下钻到机制、边界和工程代价。

## 30-60 秒标准回答

> Python 3.13 起提供禁用 GIL 的 free-threaded build；Python 3.14 进入更正式的支持阶段，但仍不是默认构建。它允许线程在多核上并行执行 Python 代码，但第三方扩展兼容性与线程安全要求更高。

## 高分回答的四层结构

- **第一层 - 结论**：Python 3.13 起提供禁用 GIL 的 free-threaded build；Python 3.14 进入更正式的支持阶段，但仍不是默认构建。它允许线程在多核上并行执行 Python 代码，但第三方扩展兼容性与线程安全要求更高。

### 1. 机制链路：这道题到底在系统的哪一层发生？

free-threaded build 把 GIL 变成可选；为维持对象安全，CPython 引入更细粒度同步和相应引用计数/容器策略，使 Python 线程可在多核并行。

建议面试时把机制画成一条因果链，而不是堆术语：

```text
输入 / 语法 / API
        ↓
协议或对象模型
        ↓
CPython/标准库实现路径
        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q63. Python 3.14 free-threaded CPython 改变了什么？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

它仍非默认构建；第三方 C 扩展可能不兼容甚至触发重新启用 GIL，单线程性能也存在额外开销。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

并发模型应比较**任务粒度、同步/IPC、数据共享、启动成本、故障隔离和运行时模式**，而不是背固定的线程/进程口诀。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

源码阅读不要求面试现场背文件内容，而是要建立三个习惯：

### 6. 面试追问：完整回答示范

**追问：如果面试官故意把条件改掉，应该怎么回答？**

追问“list/dict 是否线程安全”时答：实现使用内部锁保持类似安全性，但官方不承诺可依赖复合并发修改语义。

**推荐回答结构：**

1. 先指出新条件改变了哪个前提；
2. 保留仍然成立的语义；
3. 撤回不再成立的实现/性能结论；
4. 给一个最小反例或测量方法。

这种回答方式比“我记得文档说……”更稳健，也更容易应对陌生变体。

### 7. 实验升级：把结论变成可证伪假设

在可用环境中检查 sysconfig Py_GIL_DISABLED 与 sys._is_gil_enabled，并对 CPU workload 做线程扩展测试。

建议实验遵循：

```text
先写预测
  ↓
固定 Python 版本与平台
  ↓
运行最小实验
  ↓
记录输出 / 时间 / 内存 / 状态
  ↓
解释与预测不一致的地方
```

不要只贴运行结果；真正有价值的是解释“为什么”。性能实验至少 warm-up、多轮重复，并避免用单次 wall-clock 得出绝对结论。
