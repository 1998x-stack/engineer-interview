# Q68. fork、spawn、forkserver 有什么区别？

> **难度**：★★★★  ·  **频率**：高  ·  **关键词**：`multiprocessing start method`, `fork`, `spawn`

## 题目定位

判断候选人是否会基于 workload 和数据共享成本选择并行模型，同时理解现代 free-threaded Python 的边界。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **multiprocessing start method / fork / spawn** 的可推导模型。并发选择是成本模型：CPU/I/O 比例、共享状态、序列化、隔离、第三方扩展兼容与部署模型共同决定方案。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

这类题的高分标准通常不是“知道答案”，而是能在 30-60 秒内先给清晰结论，并在追问时继续下钻到机制、边界和工程代价。

## 30-60 秒标准回答

> 三者定义 worker 进程如何启动：fork 复制当前进程状态，spawn 启动干净解释器并重新导入，forkserver 由专门服务进程负责 fork。不同平台/版本默认值不同。

### 1. 机制链路：这道题到底在系统的哪一层发生？

spawn 启动干净解释器并重新导入主模块；fork 复制当前进程状态；forkserver 由单线程服务器负责 fork，降低多线程 fork 风险。

建议面试时把机制画成一条因果链，而不是堆术语：

```text

        ↓
协议或对象模型
        ↓
CPython/标准库实现路径
        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q68. fork、spawn、forkserver 有什么区别？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

Python 3.14 POSIX 默认 forkserver，macOS 默认 spawn；依赖默认值的程序跨版本会变化。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

并发模型应比较**任务粒度、同步/IPC、数据共享、启动成本、故障隔离和运行时模式**，而不是背固定的线程/进程口诀。

| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |
