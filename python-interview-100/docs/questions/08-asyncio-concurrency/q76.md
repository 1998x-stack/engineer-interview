# Q76. 为什么不能随便吞 asyncio.CancelledError？

> **难度**：★★★★  ·  **频率**：极高  ·  **关键词**：`cancellation`, `CancelledError`, `cleanup`

## 题目定位

判断候选人能否写生产级异步代码，而不是只会 `async def` / `await` 语法。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **cancellation / CancelledError / cleanup** 的可推导模型。asyncio 的高阶问题不是 async/await 语法，而是任务所有权、取消传播、超时、背压、资源上限和故障边界。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

## 30-60 秒标准回答

> 取消是 asyncio 结构化并发的重要控制信号。协程应在 finally 中清理；若显式捕获 CancelledError，通常清理后要继续传播，否则 TaskGroup/timeout 等上层机制可能行为异常。

## 最小可运行实验

```python
async def worker():
    resource = await acquire()
    try:
        await run(resource)
    finally:
        await release(resource)
```

### 实验怎么读

代码共 6 个非空行，建议逐行观察“名字绑定/对象状态/控制流”的变化，而不是只看最终输出。 异步示例要额外观察任务何时挂起、何时恢复，以及是否存在阻塞调用。

### 2. 边界条件：什么时候“标准答案”会失效？

CancelledError 继承 BaseException，且 TaskGroup/timeout 内部依赖取消协议；吞掉它会破坏结构化并发。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：
