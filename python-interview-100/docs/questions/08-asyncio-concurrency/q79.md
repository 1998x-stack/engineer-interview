# Q79. Semaphore 在 async 服务中解决什么问题？

> **难度**：★★  ·  **频率**：高  ·  **关键词**：`Semaphore`, `rate limit`, `bounded concurrency`

## 题目定位

判断候选人能否写生产级异步代码，而不是只会 `async def` / `await` 语法。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **Semaphore / rate limit / bounded concurrency** 的可推导模型。asyncio 的高阶问题不是 async/await 语法，而是任务所有权、取消传播、超时、背压、资源上限和故障边界。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

这类题的高分标准通常不是“知道答案”，而是能在 30-60 秒内先给清晰结论，并在追问时继续下钻到机制、边界和工程代价。

## 30-60 秒标准回答

> Semaphore 限制同时进入某个关键资源的任务数量，用于保护数据库连接、第三方 API、文件描述符和内存，而不是提高无限并发。

## 核心心智模型

asyncio 的高阶问题不是 async/await 语法，而是任务所有权、取消传播、超时、背压、资源上限和故障边界。

## 最小可运行实验

```python
sem = asyncio.Semaphore(20)

async def call_upstream(x):
    async with sem:
        return await client.get(x)
```

### 实验怎么读

代码共 4 个非空行，建议逐行观察“名字绑定/对象状态/控制流”的变化，而不是只看最终输出。 异步示例要额外观察任务何时挂起、何时恢复，以及是否存在阻塞调用。

### 1. 机制链路：这道题到底在系统的哪一层发生？

Semaphore 控制同时进入某资源临界区的任务数量，是应用层 backpressure/资源保护的一种手段。


对于 **Q79. Semaphore 在 async 服务中解决什么问题？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

Semaphore 只限制并发数，不自动实现速率限制、队列长度上限、超时或公平性。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

async 性能的核心是**event-loop 可运行时间、在途任务数、资源容量和尾延迟**。无限并发常常把等待问题转化为排队与内存问题。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

### 4. 生产工程场景

外部 API、DB connection、浏览器实例等都应根据容量设置 concurrency budget，并配合 timeout/retry/jitter。

一个合格的工程回答不应停在“可以/不可以”，而应给出**选择依据**。推荐使用：

```text
需求约束 → 候选方案 → 成本/风险 → 观测指标 → 回退方案
```

这会自然把 Python 语法题提升到系统设计和可维护性层面。
