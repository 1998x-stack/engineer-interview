# Q87. unit test 与 integration test 如何划分？

> **难度**：★★  ·  **频率**：高  ·  **关键词**：`testing`, `test pyramid`, `feedback`

## 题目定位

判断候选人是否具备大型 Python 工程的契约、测试与可复现构建意识。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **testing / test pyramid / feedback** 的可推导模型。类型、测试、打包的共同目标是把隐式约束变成可自动检查的契约，并降低大型代码库中的变更成本。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

这类题的高分标准通常不是“知道答案”，而是能在 30-60 秒内先给清晰结论，并在追问时继续下钻到机制、边界和工程代价。

## 30-60 秒标准回答

> unit test 关注小范围逻辑并提供快速反馈；integration test 验证组件真实协作。边界不应只按“有没有数据库”机械定义，而应看测试隔离范围和目标风险。

## 高分回答的四层结构

- **第一层 - 结论**：unit test 关注小范围逻辑并提供快速反馈；integration test 验证组件真实协作。边界不应只按“有没有数据库”机械定义，而应看测试隔离范围和目标风险。
- **第二层 - 原因**：挑选“原理拆解”中的 2-3 个关键点解释为什么，而不是重复定义。
- **第三层 - 边界**：主动说出至少一个 Gotcha，证明你知道结论并非无条件成立。
- **第四层 - 工程化**：把结论落到 API 设计、性能、并发、可维护性或调试策略。

## 核心心智模型

类型、测试、打包的共同目标是把隐式约束变成可自动检查的契约，并降低大型代码库中的变更成本。

建议把本题画成一张最小执行图：输入/名字或任务从哪里来，经过哪些协议或数据结构，最终在哪个边界产生可观察结果。只要执行路径能画清楚，大多数追问都可以现场推导。

## 最小可运行实验

```python
# unit: pure pricing function
# integration: repository + real test DB
# e2e: HTTP request -> DB -> response
```

### 实验怎么读

代码共 3 个非空行，建议逐行观察“名字绑定/对象状态/控制流”的变化，而不是只看最终输出。

## 深度扩展：从“会答”到“能推导”

> 本节是仓库增强版新增内容。原题/PDF 给出核心结论；这里进一步补充机制、边界、工程决策和源码阅读入口。实现细节以 **Python 3.14 / CPython** 为主要基线，凡属于 CPython 当前实现而非语言规范的内容均按实现视角理解。

### 1. 机制链路：这道题到底在系统的哪一层发生？

unit test 隔离小逻辑、反馈快；integration test 验证组件边界与真实协作；二者覆盖的是不同故障空间。

建议面试时把机制画成一条因果链，而不是堆术语：

```text
输入 / 语法 / API
        ↓
协议或对象模型
        ↓
CPython/标准库实现路径
        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q87. unit test 与 integration test 如何划分？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

把所有依赖都 mock 后的“单元测试”可能只验证 mock 交互而不验证真实 SQL/序列化/事务。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

typing/testing/packaging 的收益更多体现为**缺陷前移、接口稳定、重构成本和可重复构建**，不应只用运行时性能衡量。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

### 4. 生产工程场景

按风险分层：核心纯逻辑大量 unit；数据库契约/HTTP adapter 用 integration；少量 end-to-end 验证关键路径。

一个合格的工程回答不应停在“可以/不可以”，而应给出**选择依据**。推荐使用：

```text
需求约束 → 候选方案 → 成本/风险 → 观测指标 → 回退方案
```

这会自然把 Python 语法题提升到系统设计和可维护性层面。

### 5. CPython / 标准库源码阅读入口

**建议阅读入口：** unittest/pytest 生态概念；测试金字塔/契约测试为工程扩展。

源码阅读不要求面试现场背文件内容，而是要建立三个习惯：

1. 先从官方文档确定**语言/API 契约**；
2. 再去 CPython 源码确认**当前实现为什么产生这种成本与行为**；
3. 最后用 `dis`、`inspect`、`timeit`、`tracemalloc`、最小并发实验等手段做可重复验证。

> 注意：CPython 内部函数名、文件组织和优化策略可能跨版本变化；源码细节只能用于解释当前实现，不能反向扩大为语言规范。

### 6. 面试追问：完整回答示范

**追问：如果面试官故意把条件改掉，应该怎么回答？**

追问“如何划边界”时答：以速度、确定性、外部资源、故障定位和契约价值共同决定。

**推荐回答结构：**

1. 先指出新条件改变了哪个前提；
2. 保留仍然成立的语义；
3. 撤回不再成立的实现/性能结论；
4. 给一个最小反例或测量方法。

这种回答方式比“我记得文档说……”更稳健，也更容易应对陌生变体。

### 7. 实验升级：把结论变成可证伪假设

选一个 repository service，分别设计纯逻辑单测和真实 SQLite integration test。

建议实验遵循：

```text
先写预测
  ↓
固定 Python 版本与平台
  ↓
运行最小实验
  ↓
记录输出 / 时间 / 内存 / 状态
  ↓
解释与预测不一致的地方
```

不要只贴运行结果；真正有价值的是解释“为什么”。性能实验至少 warm-up、多轮重复，并避免用单次 wall-clock 得出绝对结论。

### 8. Code Review 视角

看到与本题相关的代码时，可以快速检查：

- 是否把**实现细节**误当语言保证；
- 是否存在隐藏的共享状态、对象持有或副作用；
- 是否在错误的抽象层做优化；
- 是否有比当前 magic/技巧写法更显式、可测试的方案；
- 是否缺少针对边界条件的测试；
- 如果升级 Python 版本，哪些假设需要重新 benchmark 或验证。
