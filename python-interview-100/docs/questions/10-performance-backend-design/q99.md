# Q99. 1 亿 URL 找 Top-K，如何设计？

> **难度**：★★★★  ·  **频率**：高  ·  **关键词**：`Top-K`, `heap`, `partition`

## 题目定位

判断候选人能否把 Python 语言知识上升为性能工程与服务架构决策。

### 面试官真正想确认什么

本题的中心不是记忆一个结论，而是建立 **Top-K / heap / partition** 的可推导模型。性能优化必须从测量开始；系统设计必须把吞吐、尾延迟、容量隔离、背压、可观测性和故障恢复放在同一张图里讨论。 面试时建议先给结论，再说明边界条件，最后用一个最小例子证明自己的解释。

这类题的高分标准通常不是“知道答案”，而是能在 30-60 秒内先给清晰结论，并在追问时继续下钻到机制、边界和工程代价。

## 30-60 秒标准回答

> 若 distinct URL 数可放内存：hash count O(n)，再用大小 K 的 heap 做 O(m log K)。若无法放内存，先按 hash 分区到磁盘/分布式节点，再局部计数和局部 Top-K，最后合并。

## 高分回答的四层结构

- **第一层 - 结论**：若 distinct URL 数可放内存：hash count O(n)，再用大小 K 的 heap 做 O(m log K)。若无法放内存，先按 hash 分区到磁盘/分布式节点，再局部计数和局部 Top-K，最后合并。
- **第二层 - 原因**：挑选“原理拆解”中的 2-3 个关键点解释为什么，而不是重复定义。
- **第三层 - 边界**：主动说出至少一个 Gotcha，证明你知道结论并非无条件成立。
- **第四层 - 工程化**：把结论落到 API 设计、性能、并发、可维护性或调试策略。

性能优化必须从测量开始；系统设计必须把吞吐、尾延迟、容量隔离、背压、可观测性和故障恢复放在同一张图里讨论。

## 最小可运行实验

```python
# exact, memory allows
from collections import Counter
from heapq import nlargest
counts = Counter(stream)
print(nlargest(k, counts.items(), key=lambda kv: kv[1]))
```

### 实验怎么读

代码共 5 个非空行，建议逐行观察“名字绑定/对象状态/控制流”的变化，而不是只看最终输出。 运行时先预测输出，再执行验证；预测错误的地方通常就是心智模型缺口。

## 易错点 / Gotchas

- ❌ **常见误区**：直接 `sorted(counts.items())` 忽略 m 很大时 O(m log m)。

- ❌ **常见误区**：只讲算法不问内存/是否允许近似。
  - **改进方式**：回答时先声明适用范围，再用一个反例或最小实验校验结论。

## 深度扩展：从“会答”到“能推导”

> 本节是仓库增强版新增内容。原题/PDF 给出核心结论；这里进一步补充机制、边界、工程决策和源码阅读入口。实现细节以 **Python 3.14 / CPython** 为主要基线，凡属于 CPython 当前实现而非语言规范的内容均按实现视角理解。

### 1. 机制链路：这道题到底在系统的哪一层发生？

精确 Top-K 的常见方案是先统计频次，再维护大小 k 的最小堆；若唯一 key 也超内存，就先分区/外部聚合。

建议面试时把机制画成一条因果链，而不是堆术语：

```text
输入 / 语法 / API
        ↓
协议或对象模型
        ↓
CPython/标准库实现路径
        ↓
可观察行为
        ↓
性能、正确性与工程后果
```

对于 **Q99. 1 亿 URL 找 Top-K，如何设计？**，高分回答的关键是指出上面每一层之间的因果关系，并明确哪些属于语言保证，哪些只是当前 CPython 的实现选择。

### 2. 边界条件：什么时候“标准答案”会失效？

仅保存全局大小 k 的 heap 不能在未统计频次时解决任意重复 URL 精确 Top-K，除非使用近似算法/特殊数据模型。

面试中主动给出边界，通常比多背三个 API 更能体现成熟度。可以使用下面的句式：

> “这个结论在 ___ 前提下成立；如果换成 ___，需要重新评估 ___。”

这样可以避免把“平均复杂度”“默认 CPython”“当前标准库实现”说成绝对规律。

### 3. 成本模型：不要只说对错，还要说代价

性能与系统设计题要用**测量→定位→建模→改动→回归**闭环。任何没有 workload、基线和瓶颈证据的‘最快方案’都不专业。

回答成本问题时至少考虑以下维度：

| 维度 | 应回答的问题 |
|---|---|
| 正确性 | 是否有隐藏副作用、竞态、生命周期或协议约束？ |
| 时间 | 单次、平均、摊还、最坏复杂度分别是什么？ |
| 空间 | 是否复制、缓存、持有对象或制造峰值内存？ |
| 可维护性 | 行为是显式 API 还是隐藏在 magic method / decorator / runtime hook 中？ |
| 可移植性 | 结论属于 Python 语言规范、CPython，还是某个平台/第三方库？ |

### 4. 生产工程场景

分布式可 map-side count→partition by URL→reduce count→local top-k→global merge；近似场景可 Count-Min Sketch/Space-Saving。

一个合格的工程回答不应停在“可以/不可以”，而应给出**选择依据**。推荐使用：

```text
需求约束 → 候选方案 → 成本/风险 → 观测指标 → 回退方案
```

这会自然把 Python 语法题提升到系统设计和可维护性层面。

### 5. CPython / 标准库源码阅读入口

**建议阅读入口：** collections.Counter、heapq；分布式部分为算法工程扩展。

源码阅读不要求面试现场背文件内容，而是要建立三个习惯：

1. 先从官方文档确定**语言/API 契约**；
2. 再去 CPython 源码确认**当前实现为什么产生这种成本与行为**；
3. 最后用 `dis`、`inspect`、`timeit`、`tracemalloc`、最小并发实验等手段做可重复验证。

> 注意：CPython 内部函数名、文件组织和优化策略可能跨版本变化；源码细节只能用于解释当前实现，不能反向扩大为语言规范。

### 6. 面试追问：完整回答示范

**追问：如果面试官故意把条件改掉，应该怎么回答？**

追问“复杂度”时答：计数 O(n)，m 个唯一 key 后选 Top-K 可 O(m log k)，内存 O(m)；外部分区改变内存/IO权衡。

**推荐回答结构：**

1. 先指出新条件改变了哪个前提；
2. 保留仍然成立的语义；
3. 撤回不再成立的实现/性能结论；
4. 给一个最小反例或测量方法。

这种回答方式比“我记得文档说……”更稳健，也更容易应对陌生变体。

### 7. 实验升级：把结论变成可证伪假设

实现精确 Counter+heap 与近似 sketch 版本，对 Zipf 数据比较误差和内存。

建议实验遵循：

```text
先写预测
  ↓
固定 Python 版本与平台
  ↓
运行最小实验
  ↓
记录输出 / 时间 / 内存 / 状态
  ↓
解释与预测不一致的地方
```

不要只贴运行结果；真正有价值的是解释“为什么”。性能实验至少 warm-up、多轮重复，并避免用单次 wall-clock 得出绝对结论。

### 8. Code Review 视角

看到与本题相关的代码时，可以快速检查：

- 是否把**实现细节**误当语言保证；
- 是否存在隐藏的共享状态、对象持有或副作用；
- 是否在错误的抽象层做优化；
- 是否有比当前 magic/技巧写法更显式、可测试的方案；
- 是否缺少针对边界条件的测试；
- 如果升级 Python 版本，哪些假设需要重新 benchmark 或验证。
