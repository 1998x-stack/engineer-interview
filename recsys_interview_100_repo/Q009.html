Q009. 如果推荐系统 CTR 突然下降 20%，怎么排查？

难度：★★★　 来源标签：系统设计　 章节：第 1 章 · 系统架构与业务理解

题目定位

这道题位于 第 1 章：系统架构与业务理解。面试官通常希望候选人能给出可落地方案、权衡与验证路径；最终要落到 模型/数据/系统/指标 四个层面的约束，而不是停留在术语复述。

本章主线：把推荐系统理解为受 QPS、SLA、数据闭环、实验体系和业务目标共同约束的工程系统。

30 秒回答

先按“数据→流量→服务→特征→候选→模型→策略→实验”分层排查，优先验证是否为埋点、流量结构或服务故障，而不是第一时间归因模型。

深入拆解

检查埋点与 denominator 是否变化、实验分桶是否 SRM、请求成功率和时延是否异常、特征缺失率与 freshness、ANN 索引版本、召回量与分数分布。 做时间维度、用户维度、场景维度、模型版本维度切片，定位异常从何时/何群体开始。 若所有模型同时掉，通常先怀疑数据或流量；只有新模型掉，则优先查模型/特征/serving skew。

公式 / 工程抓手

排障核心：找到最早发生分布断点的层，而不是盯最终 CTR。

系统设计的第一性原理

推荐系统首先是一个受预算约束的决策系统。面试时建议明确五个预算：候选规模、特征读取、模型计算、端到端延迟、实验/迭代速度。一个方案如果只在模型指标上成立，却无法在这些预算内运行，就不是工业答案。

可以把整条链抽象成：

$$\text{Logs}\rightarrow\text{Data/Features}\rightarrow\text{Candidate Generation}\rightarrow\text{Scoring}\rightarrow\text{List Optimization}\rightarrow\text{Exposure}\rightarrow\text{Feedback}$$

每个箭头都可能产生分布变化和信息损失。因此分析系统时，要同时回答：输入分布是什么、这一层丢掉什么、下一层还能否补救、线上如何观测。

针对本题的关键推导

线上指标突降要按“数据→流量→候选→特征→模型→策略→实验”分层定位，并优先排查共享基础设施，因为模型 bug 往往不是最高先验。

这里建议把回答进一步拆成四层证据链：

  1. 定义层：一句话说明“如果推荐系统 CTR 突然下降 20%，怎么排查？”讨论的对象和优化目标；
  2. 机制层：给出公式、数据生成过程或计算复杂度，解释为什么会有效；
  3. 系统层：指出它在完整推荐链路中的上游输入、下游依赖、成本和失败传播路径；
  4. 验证层：给出 offline slice、线上 A/B、guardrail 与回滚条件。

90 秒标准回答（建议练到可以脱稿）

线上指标突降要按“数据→流量→候选→特征→模型→策略→实验”分层定位，并优先排查共享基础设施，因为模型 bug 往往不是最高先验。 具体到工程上，可以用下面的数量级来理解：CTR 下降 20% 但曝光量和候选数正常，进一步发现实时 user feature freshness 从 2 分钟变成 2 小时；回滚特征流即可恢复，无需回滚模型。 因此我不会只看单一离线指标，而会把这项方法放回完整链路，联合检查候选/特征分布、P95/P99、成本以及线上主指标。如果出现“离线好、线上差”，我会优先检查数据与 serving 一致性、截断/近似误差和策略覆盖。最后还要说明边界：只看全局均值会掩盖问题。必须切 region/app_version/user cohort/traffic source/model version，避免平均值把局部事故冲淡。

这段 90 秒回答的顺序是 结论 → 机制 → 数量级 → 工程验证 → 边界。对于大多数推荐算法题，这比从论文历史开始讲更稳。

容易混淆的概念

模型指标 vs 系统指标；候选质量 vs 排序质量；请求级优化 vs 用户长期效用；平均延迟 vs P99。

上线验证与监控

离线先做 stage-wise oracle 与分层 slice；线上用稳定 A/B 验证 primary metric，同时守住延迟、负反馈、留存等 guardrail。任何链路改动都应记录候选集合和 score 分布，便于解释增益来自哪里。

建议至少记录这些字段： request_id、user/session、route candidates、每层 input/output 数、feature/model/index/config version、各 stage latency、final scores、rerank reason、exposure/feedback。日志字段不是越多越好，关键是能把一次线上曝光追溯到样本、特征、模型、索引和实验版本。

一个可用于面试的具体例子

CTR 下降 20% 但曝光量和候选数正常，进一步发现实时 user feature freshness 从 2 分钟变成 2 小时；回滚特征流即可恢复，无需回滚模型。

面试里具体数字的价值不是“显得真实”，而是迫使方案满足数量级约束。即使没有真实业务数据，也可以明确说“下面用数量级举例”，然后说明候选数、样本量、维度、QPS 或延迟如何影响设计。

工程决策矩阵

决策维度 面试中要给出的证据
候选规模 每层 input/output 数量、截断率、oracle 上限
延迟 P50/P95/P99、超时率、降级路径
数据 样本窗口、特征 freshness、标签延迟
质量 Recall/GAUC/NDCG 与线上 primary metric
稳定性 回滚、版本一致性、监控与事故隔离

回答时不要把所有维度都平均展开。先指出当前题目的第一瓶颈，再解释为什么其他维度是二阶约束，这会比罗列术语更像真实工程决策。

参考实现 / 伪代码

request
  -> load user/context features
  -> parallel_recall(routes, deadline)
  -> merge_dedup_quota
  -> coarse_rank
  -> fine_rank(multi_objective)
  -> rerank(constraints, diversity, exploration)
  -> expose + log(all_versions, candidates, scores)

这段代码不是为了背 API，而是帮助建立“输入—状态—输出—监控”的工程直觉。真实系统还应记录 feature/model/index/experiment 等版本，确保线上结果能够复现。

边界条件与反例

只看全局均值会掩盖问题。必须切 region/app_version/user cohort/traffic source/model version，避免平均值把局部事故冲淡。

一个强候选人应该主动说明什么时候不应该使用当前方法。这能证明你理解的是归纳偏置与业务条件，而不是模型名称。

面试官继续追问时，建议用这套框架

  • 追公式：先定义符号，再说明每一项改变了什么概率/几何/梯度；
  • 追为什么：从数据分布或复杂度出发，不用“实验发现更好”作为唯一理由；
  • 追线上：给 P95/P99、候选数、内存、特征 freshness、回退路径；
  • 追效果：区分离线增量、stage-wise oracle、线上 causal lift；
  • 追失败：给至少一个会让方案失效的分布变化或系统约束。

Senior / Staff 级加分点

如果面试岗位偏高级，可以进一步讨论：

  • 反事实与增量价值：新模块到底创造了新候选/新信息，还是复制已有能力；
  • Pareto frontier：质量、延迟、成本、稳定性之间是否存在更优点，而不是只报单指标；
  • 可观测性：出现线上退化时，能否在 10~30 分钟内通过 dashboard/slice 定位到具体 stage；
  • 可演进性：模型升级是否要求全量重建特征/索引，是否支持 shadow、canary 和快速 rollback；
  • 组织成本：跨团队依赖、数据口径与长期维护是否会吞掉理论收益。

工业级工程视角

  • 排障先看全局/分桶/端上/版本/流量结构，再定位召回、特征、模型或实验系统。
  • 先明确规模：DAU/MAU、item 数、QPS、峰值流量、P50/P95/P99 SLA。
  • 把离线数据链路、在线特征链路、模型发布链路、实验链路分别画出来。
  • 任何模型提升都要回答：候选分布是否改变？latency 增量多少？回滚路径是什么？
  • 业务指标必须配护栏：例如 CTR 上升时同时看时长、负反馈、留存与生态指标。

面试中建议主动报出的数字/约束

  • 跌幅、发生时间、受影响端/人群、流量比例、最近发布版本、score/candidate 分布。

推荐回答结构（白板版）

  1. 先用 1-2 句话定义核心概念或结论。
  2. 再解释“为什么”，给出机制、公式或数据生成过程。
  3. 补充工业约束：规模、延迟、样本分布、内存/算力或线上一致性。
  4. 给出至少一个反例/失败模式，证明你理解适用边界。
  5. 最后用线上验证方案收尾：离线分桶 + A/B + guardrail。

连续追问参考答案

追问 1：如何判断是流量季节性还是系统故障？

对比历史同星期/节假日、外部活动与 control baseline，再看故障是否与版本、地域、端、feature freshness、错误率同步。季节性通常跨模型一致且平滑，系统故障常与某版本/链路突变高度相关。

追问 2：哪些监控应该预先建设？

至少有流量/曝光、candidate count、route overlap、feature missing/freshness、score distribution、各 stage P50/P99、timeout/fallback、业务 primary/guardrail，并能按 model/index/app/region/user cohort slice。

追问 3：分数分布正常但 CTR 掉了说明什么？

说明模型 raw score 本身未明显漂移，但展示环境、候选组成、位置、UI、埋点或用户流量可能变了。继续查 candidate overlap、position distribution、曝光日志、客户端版本和 calibration by slice。

追问 4：只有 iOS CTR 跌、Android 正常，你下一步查什么？

优先查 iOS app/version 发布、埋点、UI/位置、网络/feature 请求、设备特征默认值和实验覆盖；再对比同模型下候选与 score 分布。端特异退化通常先从客户端/流量差异排，而不是重训全局模型。

追问 5：如果 AUC 正常但线上 CTR 跌，最可能是哪几类问题？

候选分布/流量变了、train-serving skew、score calibration/阈值、位置/展示变化、延迟超时回退、策略覆盖或日志问题都可能。AUC 只说明离线排序能力，不验证线上数据和决策链。
