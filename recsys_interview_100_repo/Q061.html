Q061. ESMM 有什么不足？后续模型为什么继续改？

难度：★★★　 来源标签：论文追问　 章节：第 5 章 · 多任务、多目标与 CVR 建模

题目定位

这道题位于 第 5 章：多任务、多目标与 CVR 建模。面试官通常希望候选人能解释因果机制，而不是只给定义；最终要落到 模型/数据/系统/指标 四个层面的约束，而不是停留在术语复述。

本章主线：理解任务关系、负迁移、样本选择偏差、转化漏斗与连续目标建模。

30 秒回答

ESMM 解决了经典的样本选择偏差（SSB）与数据稀疏问题，但 $pCVR$ 通过乘法关系间接约束，仍可能出现估计偏差与误差放大。后续工作如 ESCM² 等继续从反事实校正、因果约束和多阶段行为建模等方向改进。

深入拆解

面试不要求背所有后续模型，但要知道 ESMM 并非无偏真理。 中间行为（加购、收藏、进店）可以提供更密集监督，但行为图的概率链必须定义严谨。 高级回答应讨论 counterfactual missingness 与 exposure policy。

V2 深度版：从“会答”到“能落地”

多任务建模的第一性原理

多任务学习的本质是受控共享。共享能提高样本效率，但也会通过共享参数传递冲突梯度。分析任何 MTL 模型都可以沿三条线：任务标签空间是否一致、梯度是否冲突、模型如何分配共享/私有容量。

$$L(\theta)=\sum_t \lambda_t L_t(\theta_{shared},\theta_t)$$

真正难点通常不在写出这条式子，而在决定哪些参数该共享、$\lambda_t$ 如何对应业务价值，以及线上多个目标如何合成最终排序。

针对本题的关键推导

ESMM 解决了样本空间和稀疏的核心痛点，但 pCVR 是通过乘积约束间接学习，存在估计偏差、概率放大和因果混杂问题；ESCM² 等引入 counterfactual/causal 思路。

这里建议把回答进一步拆成四层证据链：

  1. 定义层：一句话说明“ESMM 有什么不足？后续模型为什么继续改？”讨论的对象和优化目标；
  2. 机制层：给出公式、数据生成过程或计算复杂度，解释为什么会有效；
  3. 系统层：指出它在完整推荐链路中的上游输入、下游依赖、成本和失败传播路径；
  4. 验证层：给出 offline slice、线上 A/B、guardrail 与回滚条件。

90 秒标准回答（建议练到可以脱稿）

ESMM 解决了样本空间和稀疏的核心痛点，但 pCVR 是通过乘积约束间接学习，存在估计偏差、概率放大和因果混杂问题；ESCM² 等引入 counterfactual/causal 思路。 具体到工程上，可以用下面的数量级来理解：当 pCTR 很小时，pCVR≈pCTCVR/pCTR 对微小误差非常敏感，数值上会放大。 因此我不会只看单一离线指标，而会把这项方法放回完整链路，联合检查候选/特征分布、P95/P99、成本以及线上主指标。如果出现“离线好、线上差”，我会优先检查数据与 serving 一致性、截断/近似误差和策略覆盖。最后还要说明边界：“后续模型更复杂”不代表必然更好；需要看标签可用性、稳定性和线上增益。

这段 90 秒回答的顺序是 结论 → 机制 → 数量级 → 工程验证 → 边界。对于大多数推荐算法题，这比从论文历史开始讲更稳。

容易混淆的概念

共享表示 vs 共享专家；任务相关性 vs 标签共现；loss 平衡 vs 业务权重；多任务提升 vs Pareto/跷跷板。

上线验证与监控

离线逐任务看 metric、calibration、gradient conflict、gate/expert usage；线上用多指标 Pareto 评价，并设置不能被牺牲的 guardrail。新增任务必须证明共享带来增量而非负迁移。

建议至少记录这些字段： task labels、loss scale、task weights、gradient norm/cosine、gate entropy、expert utilization、per-task prediction/calibration。日志字段不是越多越好，关键是能把一次线上曝光追溯到样本、特征、模型、索引和实验版本。

工程决策矩阵

决策维度 需要监控
Task relation label overlap、gradient cosine、相关性
Expert/Gate expert usage、gate entropy、collapse
Loss scale、动态权重、task-specific convergence
Calibration 每任务 reliability / ECE

回答时不要把所有维度都平均展开。先指出当前题目的第一瓶颈，再解释为什么其他维度是二阶约束，这会比罗列术语更像真实工程决策。

参考实现 / 伪代码

shared = shared_or_experts(x)
loss = 0.0
for task in tasks:
    pred = task_head[task](route(task, shared))
    loss += weight[task] * criterion[task](pred, label[task])
loss.backward()

这段代码不是为了背 API，而是帮助建立“输入—状态—输出—监控”的工程直觉。真实系统还应记录 feature/model/index/experiment 等版本，确保线上结果能够复现。

边界条件与反例

“后续模型更复杂”不代表必然更好；需要看标签可用性、稳定性和线上增益。

一个强候选人应该主动说明什么时候不应该使用当前方法。这能证明你理解的是归纳偏置与业务条件，而不是模型名称。

面试官继续追问时，建议用这套框架

  • 追公式：先定义符号，再说明每一项改变了什么概率/几何/梯度；
  • 追为什么：从数据分布或复杂度出发，不用“实验发现更好”作为唯一理由；
  • 追线上：给 P95/P99、候选数、内存、特征 freshness、回退路径；
  • 追效果：区分离线增量、stage-wise oracle、线上 causal lift；
  • 追失败：给至少一个会让方案失效的分布变化或系统约束。

Senior / Staff 级加分点

如果面试岗位偏高级，可以进一步讨论：

  • 反事实与增量价值：新模块到底创造了新候选/新信息，还是复制已有能力；
  • Pareto frontier：质量、延迟、成本、稳定性之间是否存在更优点，而不是只报单指标；
  • 可观测性：出现线上退化时，能否在 10~30 分钟内通过 dashboard/slice 定位到具体 stage；
  • 可演进性：模型升级是否要求全量重建特征/索引，是否支持 shadow、canary 和快速 rollback；
  • 组织成本：跨团队依赖、数据口径与长期维护是否会吞掉理论收益。

工业级工程视角

  • 后续模型通常从 causal/debias、label dependency、估计偏差等角度继续修正 ESMM。
  • 先定义 task graph：哪些 label 是漏斗关系、哪些并列、哪些存在延迟或缺失。
  • 监控每个 task 的 loss scale、gradient norm、样本量和 gate/expert utilization。
  • 多任务收益必须按 task 分桶检查，防止“平均上涨、关键任务下降”。
  • CVR/GMV 等延迟 label 要明确观察窗、归因窗和 late-arriving data 处理。

连续追问参考答案

追问 1：ESCM² 的反事实思想是什么？

核心是把曝光→点击→转化链中的选择偏差显式视为因果/反事实问题，用 propensity/因果约束校正“只在点击后观察 CVR”的机制，而不只靠 ESMM 的乘积结构。具体实现应以论文公式为准。

追问 2：中间行为如何建成多阶段转化链？

把 impression→click→cart→order 看成多阶段 funnel，可增加对应 task/head 或构建有向转化图，利用条件概率关系共享表示。要注意不同阶段 label delay 和 sample space。

追问 3：为什么除法式 pCVR 容易放大误差？

pCVR≈pCTCVR/pCTR，当 pCTR 很小时，分母的微小绝对误差会导致较大相对误差；两模型误差还可能相关。需要 clipping、joint calibration 或避免直接数值除法解释。

追问 4：如何比较 ESMM、ESCM² 与普通 CVR baseline？

统一 point-in-time 数据与候选，按全曝光/点击子空间、新老用户/品类评估 CVR calibration、CTCVR ranking 和线上 GMV/转化；同时比较复杂度和 propensity 估计稳定性。

追问 5：如果 propensity 本身估计不准怎么办？

做 overlap/weight diagnostics、clipping/SNIPS，并采用 doubly robust 结合 outcome model；更重要的是通过受控随机探索改善 propensity 可识别性。错误 propensity 下“理论无偏”不再成立。
