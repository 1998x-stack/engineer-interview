# Q010. 如何评价一个推荐项目做得好不好？

> **难度**：★★★　 **来源标签**：项目拷打　 **章节**：第 1 章 · 系统架构与业务理解

## 题目定位

这道题位于 **第 1 章：系统架构与业务理解**。面试官通常希望候选人能给出可落地方案、权衡与验证路径；最终要落到 **模型/数据/系统/指标** 四个层面的约束，而不是停留在术语复述。

**本章主线**：把推荐系统理解为受 QPS、SLA、数据闭环、实验体系和业务目标共同约束的工程系统。

## 30 秒回答

项目评价至少需要四层证据：模型离线指标、召回/排序任务指标、线上业务指标、长期用户或生态指标；再加资源成本与稳定性。一个真正成功的项目要证明增益来自你的改动，并能稳定上线。

## 深入拆解

离线 AUC/GAUC/NDCG 只是筛选信号；召回看 Recall@K/HitRate；线上看 CTR、时长、CVR、GMV 等；长期看留存、活跃天数、满意度。 必须给 baseline、数据窗口、实验流量、置信区间和持续时间；只说“提升 2%”不够可信。 线上收益还要扣除计算、显存、延迟和维护成本，工业系统看 ROI。

### 公式 / 工程抓手

`项目价值 ≈ Online Lift × Traffic Value - Serving/Engineering Cost`

## V2 深度版：从“会答”到“能落地”

### 系统设计的第一性原理

推荐系统首先是一个**受预算约束的决策系统**。面试时建议明确五个预算：候选规模、特征读取、模型计算、端到端延迟、实验/迭代速度。一个方案如果只在模型指标上成立，却无法在这些预算内运行，就不是工业答案。

可以把整条链抽象成：

$$\text{Logs}\rightarrow\text{Data/Features}\rightarrow\text{Candidate Generation}\rightarrow\text{Scoring}\rightarrow\text{List Optimization}\rightarrow\text{Exposure}\rightarrow\text{Feedback}$$

每个箭头都可能产生分布变化和信息损失。因此分析系统时，要同时回答：**输入分布是什么、这一层丢掉什么、下一层还能否补救、线上如何观测。**

### 针对本题的关键推导

项目价值要建立从“改了什么”到“为什么有效”再到“线上收益”的证据链，并能说明反事实：如果去掉某个组件，指标会怎样。

这里建议把回答进一步拆成四层证据链：

1. **定义层**：一句话说明“如何评价一个推荐项目做得好不好？”讨论的对象和优化目标；
2. **机制层**：给出公式、数据生成过程或计算复杂度，解释为什么会有效；
3. **系统层**：指出它在完整推荐链路中的上游输入、下游依赖、成本和失败传播路径；
4. **验证层**：给出 offline slice、线上 A/B、guardrail 与回滚条件。

### 90 秒标准回答（建议练到可以脱稿）

> 项目价值要建立从“改了什么”到“为什么有效”再到“线上收益”的证据链，并能说明反事实：如果去掉某个组件，指标会怎样。 具体到工程上，可以用下面的数量级来理解：“AUC +0.5%”不够。强回答会给样本规模、基线、增量实验、召回/排序分桶、P99、在线 lift、实验周期和置信区间。 因此我不会只看单一离线指标，而会把这项方法放回完整链路，联合检查候选/特征分布、P95/P99、成本以及线上主指标。如果出现“离线好、线上差”，我会优先检查数据与 serving 一致性、截断/近似误差和策略覆盖。最后还要说明边界：不要把团队整体收益全部归因于个人模型；面试官会通过 ablation、时间线和 ownership 追问识别夸大。

这段 90 秒回答的顺序是 **结论 → 机制 → 数量级 → 工程验证 → 边界**。对于大多数推荐算法题，这比从论文历史开始讲更稳。

### 容易混淆的概念

模型指标 vs 系统指标；候选质量 vs 排序质量；请求级优化 vs 用户长期效用；平均延迟 vs P99。

### 上线验证与监控

离线先做 stage-wise oracle 与分层 slice；线上用稳定 A/B 验证 primary metric，同时守住延迟、负反馈、留存等 guardrail。任何链路改动都应记录候选集合和 score 分布，便于解释增益来自哪里。

**建议至少记录这些字段：** request_id、user/session、route candidates、每层 input/output 数、feature/model/index/config version、各 stage latency、final scores、rerank reason、exposure/feedback。日志字段不是越多越好，关键是能把一次线上曝光追溯到样本、特征、模型、索引和实验版本。

### 一个可用于面试的具体例子

“AUC +0.5%”不够。强回答会给样本规模、基线、增量实验、召回/排序分桶、P99、在线 lift、实验周期和置信区间。

面试里具体数字的价值不是“显得真实”，而是迫使方案满足数量级约束。即使没有真实业务数据，也可以明确说“下面用数量级举例”，然后说明候选数、样本量、维度、QPS 或延迟如何影响设计。

### 工程决策矩阵

| 决策维度 | 面试中要给出的证据 |
|---|---|
| 候选规模 | 每层 input/output 数量、截断率、oracle 上限 |
| 延迟 | P50/P95/P99、超时率、降级路径 |
| 数据 | 样本窗口、特征 freshness、标签延迟 |
| 质量 | Recall/GAUC/NDCG 与线上 primary metric |
| 稳定性 | 回滚、版本一致性、监控与事故隔离 |

回答时不要把所有维度都平均展开。先指出当前题目的**第一瓶颈**，再解释为什么其他维度是二阶约束，这会比罗列术语更像真实工程决策。

### 参考实现 / 伪代码

```text
request
  -> load user/context features
  -> parallel_recall(routes, deadline)
  -> merge_dedup_quota
  -> coarse_rank
  -> fine_rank(multi_objective)
  -> rerank(constraints, diversity, exploration)
  -> expose + log(all_versions, candidates, scores)
```

这段代码不是为了背 API，而是帮助建立“输入—状态—输出—监控”的工程直觉。真实系统还应记录 feature/model/index/experiment 等版本，确保线上结果能够复现。

### 边界条件与反例

不要把团队整体收益全部归因于个人模型；面试官会通过 ablation、时间线和 ownership 追问识别夸大。

一个强候选人应该主动说明**什么时候不应该使用当前方法**。这能证明你理解的是归纳偏置与业务条件，而不是模型名称。

### 面试官继续追问时，建议用这套框架

- **追公式**：先定义符号，再说明每一项改变了什么概率/几何/梯度；
- **追为什么**：从数据分布或复杂度出发，不用“实验发现更好”作为唯一理由；
- **追线上**：给 P95/P99、候选数、内存、特征 freshness、回退路径；
- **追效果**：区分离线增量、stage-wise oracle、线上 causal lift；
- **追失败**：给至少一个会让方案失效的分布变化或系统约束。

### Senior / Staff 级加分点

如果面试岗位偏高级，可以进一步讨论：

- **反事实与增量价值**：新模块到底创造了新候选/新信息，还是复制已有能力；
- **Pareto frontier**：质量、延迟、成本、稳定性之间是否存在更优点，而不是只报单指标；
- **可观测性**：出现线上退化时，能否在 10~30 分钟内通过 dashboard/slice 定位到具体 stage；
- **可演进性**：模型升级是否要求全量重建特征/索引，是否支持 shadow、canary 和快速 rollback；
- **组织成本**：跨团队依赖、数据口径与长期维护是否会吞掉理论收益。

## 工业级工程视角

- 项目复盘建议固定回答：baseline→改动→离线→A/B→成本→失败实验→归因。
- 先明确规模：DAU/MAU、item 数、QPS、峰值流量、P50/P95/P99 SLA。
- 把离线数据链路、在线特征链路、模型发布链路、实验链路分别画出来。
- 任何模型提升都要回答：候选分布是否改变？latency 增量多少？回滚路径是什么？
- 业务指标必须配护栏：例如 CTR 上升时同时看时长、负反馈、留存与生态指标。

### 面试中建议主动报出的数字/约束

- 样本量/候选量、离线指标、线上 lift、P95/P99 latency、内存/显存与成本。

## 推荐回答结构（白板版）

1. 先用 1-2 句话定义核心概念或结论。
2. 再解释“为什么”，给出机制、公式或数据生成过程。
3. 补充工业约束：规模、延迟、样本分布、内存/算力或线上一致性。
4. 给出至少一个反例/失败模式，证明你理解适用边界。
5. 最后用线上验证方案收尾：离线分桶 + A/B + guardrail。

## 常见失分

- **PDF 原始失分点**：只展示离线 AUC，或只展示一个没有实验设计信息的线上百分比。
- 只讲架构图，不给规模、SLA、候选数和指标。
- 只给“最佳实践”结论，不说明适用条件与失败边界。

## 连续追问参考答案

### 追问 1：提升来自模型还是数据？

做正交 ablation：固定数据换模型、固定模型换数据，再测试交互项；同时保持训练步数、特征版本和 evaluation split 一致。若只有“数据+模型”同时变化才涨，应明确存在 interaction，不能把收益单归因模型。

### 追问 2：为什么离线涨线上不涨？

逐层排查 offline-online gap：候选/流量分布、特征 point-in-time、校准、延迟/超时、策略覆盖和实验功效。最有价值的是建立历史模型的 offline delta vs online lift scatter，知道哪些离线指标真正有预测力。

### 追问 3：如果成本翻倍但指标只涨 0.1% 是否上线？

同时报告 effect size、95% CI、基线量级和业务价值。统计显著只能说明与零效应不一致，不能说明 ROI 足够；大流量场景极小 uplift 也可能显著但不值得成本。

### 追问 4：如何用 ablation 证明每个改动的增量价值？

从同一 baseline 出发逐项 add-one/remove-one，并测试关键交互组合；报告 delta metric、置信区间、成本和 cohort。若多个改动强交互，应使用 factorial/小型组合实验而非把顺序增益当独立贡献。

### 追问 5：如何证明短期提升没有牺牲长期价值？

设置长期 holdout 或至少跨周观察 retention、负反馈、内容生态与复访；建立短期 proxy 与长期指标相关性。对可能有 novelty effect 的改动，不应只看首日/首周 uplift。
