Redis 有哪些核心数据类型？分别怎么选？

难度： 基础必会
所属章节： 01 · 数据结构与数据建模
PDF 对应页： 7
目标： 先在 60 秒内给结论，再用机制、边界和生产验证把答案展开。

1. 30–60 秒面试标准回答

经典类型包括 String、Hash、List、Set、Sorted Set、Stream，以及 Bitmap、Bitfield、HyperLogLog、Geo。 Redis 8 还应知道 JSON、Time Series、Bloom/Cuckoo、Count-Min Sketch、Top-K、t-digest、Vector Set；8.8 新增 Array。

2. PDF 原理拆解

真正考点是“访问模式 -> 数据结构”。 整体值/计数器选 String； 对象字段频繁局部更新选 Hash； 双端队列选 List； 唯一成员和集合运算选 Set； 按 score 排序选 ZSet； 需要历史、ACK、消费组时选 Streams。

3. PDF 高频追问与答题抓手

  • 追问 1 如果数据规模扩大 100 倍，Redis 有哪些核心数据类型？分别怎么选的结论会发生什么变化？

  • 追问 2 如何用 OBJECT ENCODING / MEMORY USAGE / --bigkeys 等手段验证你的判断？

答题抓手：回答时说明主操作、复杂度、数据规模和失效/迁移风险，比单纯枚举类型更专业。

4. PDF 易错点 / Gotchas

不要把所有对象都 JSON 序列化进 String；也不要忽略 Big Key、Cluster 多 key 同 slot 等工程约束。

5. PDF 工程落地

回答时说明主操作、复杂度、数据规模和失效/迁移风险，比单纯枚举类型更专业。

PDF 一句话拿分： 经典类型包括 String、Hash、List、Set、Sorted Set、Stream，以及 Bitmap、Bitfield、HyperLogLog、Geo。
GitHub 增强版一句话： “选类型”的本质是把访问模式映射到最小必要语义：是否需要排序、唯一性、局部字段更新、历史回放、概率统计或二级查询。

6. 深度扩展：从“会答”到“能设计”

“选类型”的本质是把访问模式映射到最小必要语义：是否需要排序、唯一性、局部字段更新、历史回放、概率统计或二级查询。选择错误通常会在数据放大后演变成 Big Key、Hot Key 或 CROSSSLOT。

6.1 成本 / 复杂度模型

String GET/SET O(1)；Hash/Set 常见单元素操作均摊 O(1)；ZSet 插入/删除通常 O(log N)；范围查询与返回元素数相关。

6.2 生产判断框架

  • 先确定主读写路径，再选数据结构，不要从命令出发反推业务。
  • 任何集合型结构都要给出最大基数、增长上限与清理策略。

6.3 面试时应主动补出的边界

  • 先说明当前结论成立的前提：数据规模、读写比、是否 Cluster、是否允许数据丢失/陈旧。
  • 如果涉及集合或批处理，必须说明 Big Key、单次返回体积和核心执行路径阻塞风险。
  • 如果涉及 HA/一致性，必须明确网络分区、进程崩溃和 failover 后的行为，而不是只描述正常路径。
  • 如果涉及性能，优先给出可观测指标和验证实验，不用“Redis 很快”替代测量。

6.4 可观测与验证指标

  • command latency / p99
  • key count 与 value/member 分布
  • MEMORY USAGE / encoding
  • 单次 reply bytes

6.5 故障注入 / 实验设计

用真实 value 大小与成员基数压测，而不是只用 16-byte GET/SET；记录 p99、网络带宽和内存/element。

6.6 面试白板图

flowchart LR
  A[业务访问模式] --> B{需要什么语义?}
  B -->|整体值/计数| S[String]
  B -->|字段更新| H[Hash]
  B -->|唯一集合| T[Set]
  B -->|score 排序| Z[Sorted Set]
  B -->|历史+ACK| X[Stream]
  S & H & T & Z & X --> R[检查基数/Big Key/Cluster]

13. 专业深挖补充（v2）

来源说明： 第 1–5 节保留 PDF 母版主线；本节是 GitHub 增强内容，结合 Redis 官方文档、当前版本实现语义与生产工程实践扩展。

13.1 核心机制再推导

数据类型选择应从访问模式反推：主键查询、字段更新、集合关系、顺序/排序、时间日志、概率统计、向量/全文检索分别对应不同原语。最重要的是估算“单 key 基数”和“最坏单命令工作量”。

不要停留在“记住结论”。面试时建议把本题改写成一条因果链：

业务目标 / SLO
  ↓
Redis 提供的原语或内部机制
  ↓
复杂度、内存、网络与一致性成本
  ↓
故障/扩容时的边界
  ↓
可观测指标与验证实验

13.2 复杂度、容量与性能模型

不要只看 Big-O：还要把元素基数、value bytes、reply bytes、Cluster slot 和热点分布一起纳入成本。

计算复杂度只说明算法增长趋势，生产还必须补充四个量：

  1. N 到底是什么：key 数、member 数、字段数、请求数还是字节数；
  2. 一次返回多少字节：很多“查找 O(1)”最终被大 reply 的网络/序列化成本主导；
  3. 最坏 key/slot/shard 多大：平均值无法解释热点和尾延迟；
  4. 背景任务是否叠加：fork、rewrite、expire、eviction、reshard 都可能与前台 workload 竞争资源。

13.3 生产案例推演

订单对象如果每次整体读取且整体失效，String JSON 很自然；如果只改状态/物流字段，Hash/JSON 局部更新更合适；若要二级索引，则需要 Query Engine 而不是在应用层全扫描。

面试中不要只说“可以这样做”，还应给出验收口径：

  • 功能正确：正常路径和重试路径结果一致；
  • 性能正确：用真实 value/member 分布测 p50/p99/p999；
  • 故障正确：节点重启、超时、网络分区或消费者崩溃后状态可解释；
  • 运维正确：有容量阈值、报警、回滚和恢复演练。

13.4 失败模式 / 什么时候不该这么做

同一种业务可以有多种可行建模；错误通常来自忽略 Big Key、跨 slot、返回体积和 TTL 策略，而不是“选错命令名字”。

进一步判断时，可以问自己：

  • 这个方案是不是把问题从 Redis 转移到了客户端，却没有减少总体复杂度？
  • 如果 key、QPS、成员数扩大 10～100 倍，是否出现不可分割的单点成本？
  • 如果 primary 在最坏时刻故障，已经返回给用户的结果是否仍然成立？
  • 如果 Redis 整层不可用，业务是 fail-open、fail-closed 还是降级到其他数据源？

13.5 源码阅读路线

建议从 命令语义 → 数据结构 → 生命周期/故障路径 三层阅读，而不是从 server.c 顺序翻完整仓库。

  • 推荐入口：src/object.c + 对应 src/t_*.c 命令实现
  • 第一步：在该 Redis 版本的 command table 中定位命令 handler；
  • 第二步：跟到对象编码/数据结构操作，记录关键 Big-O 和可能的全量遍历；
  • 第三步：继续追踪 replication、AOF/RDB、lazyfree、Cluster 等副作用；
  • 第四步：对照官方命令页的 time complexity、版本变更与 ACL category。

源码路径属于阅读导航，不是稳定 API；升级 Redis 后应以目标 tag/commit 为准。

13.6 高频追问：标准应答

追问 A：如果数据规模扩大 100 倍，结论会变吗？
要重新估算元素数、value/reply bytes、热点和 Cluster。真正考点是“访问模式 -> 数据结构”。整体值/计数器选 String；对象字段频繁局部更新选 Hash；双端队列选 List；唯一成员和集合运算选 Set；按 score 排序选 ZSet；需要历史、ACK、消费组时选 Streams。

追问 B：什么时候不该用这个方案？
同一种业务可以有多种可行建模；错误通常来自忽略 Big Key、跨 slot、返回体积和 TTL 策略，而不是“选错命令名字”。 这类边界比背命令更能体现工程判断。

13.7 面试官继续深挖时的回答结构

可以按下面顺序组织 2～5 分钟回答：

  1. 定义：一句话说明它解决什么问题；
  2. 机制：画出数据流/状态机，说明 Redis 内部怎样实现；
  3. 复杂度：给 Big-O，同时指出 N 与 byte size；
  4. 边界：Big Key、Hot Key、Cluster、复制、故障时会怎样；
  5. 方案：为什么选它，而不是最相近的替代方案；
  6. 验证：给出线上指标、命令或故障注入；
  7. 版本：若是 Redis 8.x 新能力，明确最低版本和回滚兼容。
