Hash 和 String JSON 应该怎么选？

难度： 基础必会
所属章节： 01 · 数据结构与数据建模
PDF 对应页： 9
目标： 先在 60 秒内给结论，再用机制、边界和生产验证把答案展开。

1. 30–60 秒面试标准回答

核心取舍是服务端字段级操作 vs 应用层整体序列化。Hash 能 HGET/HSET 局部字段；String JSON 简单、跨语言、整体缓存方便；Redis 8 的原生 JSON 又提供文档级局部更新和索引能力。

2. PDF 原理拆解

小 Hash 常使用紧凑编码，可能很省内存，但超多字段会变成 Big Key。 Redis 8.10 Compact Hash 面向大量共享 schema 的 Hash，通过复用字段名进一步降低内存； 是否更省必须用 MEMORY USAGE 和真实 workload 验证。

3. PDF 高频追问与答题抓手

  • 追问 1 如果数据规模扩大 100 倍，Hash 和 String JSON 应该怎么选的结论会发生什么变化？

  • 追问 2 如何用 OBJECT ENCODING / MEMORY USAGE / --bigkeys 等手段验证你的判断？

答题抓手：先看读写粒度、schema、对象数量，再选择 String/Hash/JSON；大量同 schema 小对象可关注 8.10 Compact Hash。

4. PDF 易错点 / Gotchas

不要为“省 key 数”把所有用户塞进一个 Hash；也不要假设 Hash 一定比 JSON String 省内存。

5. PDF 工程落地

先看读写粒度、schema、对象数量，再选择 String/Hash/JSON；大量同 schema 小对象可关注 8.10 Compact Hash。

PDF 一句话拿分： 核心取舍是服务端字段级操作 vs 应用层整体序列化。
GitHub 增强版一句话： Hash 与整体 JSON 的核心权衡是“字段级访问 vs 整体对象原子读写/序列化便利”。

6. 深度扩展：从“会答”到“能设计”

Hash 与整体 JSON 的核心权衡是“字段级访问 vs 整体对象原子读写/序列化便利”。Redis 8.10 的 compact hash 进一步改变了同构对象的内存成本模型，但只有字段集合高度共享时收益明显。

6.1 成本 / 复杂度模型

HGET/HSET 常见均摊 O(1)；HGETALL O(N)，N 为 fields 数量。

6.2 生产判断框架

  • 先确定主读写路径，再选数据结构，不要从命令出发反推业务。
  • 任何集合型结构都要给出最大基数、增长上限与清理策略。

6.3 面试时应主动补出的边界

  • 先说明当前结论成立的前提：数据规模、读写比、是否 Cluster、是否允许数据丢失/陈旧。
  • 如果涉及集合或批处理，必须说明 Big Key、单次返回体积和核心执行路径阻塞风险。
  • 如果涉及 HA/一致性，必须明确网络分区、进程崩溃和 failover 后的行为，而不是只描述正常路径。
  • 如果涉及性能，优先给出可观测指标和验证实验，不用“Redis 很快”替代测量。

6.4 可观测与验证指标

  • command latency / p99
  • key count 与 value/member 分布
  • MEMORY USAGE / encoding
  • 单次 reply bytes

6.5 故障注入 / 实验设计

用真实 value 大小与成员基数压测，而不是只用 16-byte GET/SET；记录 p99、网络带宽和内存/element。

6.6 面试白板图

9. 版本与实现注意

Redis 8.10 引入 compact hashes；大量同 schema Hash 可能共享字段模板降低内存。

内部编码、命令集合和新能力会随版本变化。面试中建议先给经典语义，再说明当前版本增量。

13. 专业深挖补充（v2）

来源说明： 第 1–5 节保留 PDF 母版主线；本节是 GitHub 增强内容，结合 Redis 官方文档、当前版本实现语义与生产工程实践扩展。

13.1 核心机制再推导

Hash、String JSON、Redis JSON 的核心差异是“服务器是否理解内部字段”。Hash 的字段是一层平面映射；String JSON 对 Redis 只是字节；Redis JSON 支持文档路径更新和与 Query Engine 配合。

不要停留在“记住结论”。面试时建议把本题改写成一条因果链：

业务目标 / SLO
  ↓
Redis 提供的原语或内部机制
  ↓
复杂度、内存、网络与一致性成本
  ↓
故障/扩容时的边界
  ↓
可观测指标与验证实验

13.2 复杂度、容量与性能模型

不要只看 Big-O：还要把元素基数、value bytes、reply bytes、Cluster slot 和热点分布一起纳入成本。

计算复杂度只说明算法增长趋势，生产还必须补充四个量：

  1. N 到底是什么：key 数、member 数、字段数、请求数还是字节数；
  2. 一次返回多少字节：很多“查找 O(1)”最终被大 reply 的网络/序列化成本主导；
  3. 最坏 key/slot/shard 多大：平均值无法解释热点和尾延迟；
  4. 背景任务是否叠加：fork、rewrite、expire、eviction、reshard 都可能与前台 workload 竞争资源。

13.3 生产案例推演

用户 profile 只有十几个稳定字段且常做单字段读写，可用 Hash；复杂嵌套配置且要 JSONPath/索引，可用 JSON；只做整体 cache-aside 时 String 往往最简单。

面试中不要只说“可以这样做”，还应给出验收口径：

  • 功能正确：正常路径和重试路径结果一致；
  • 性能正确：用真实 value/member 分布测 p50/p99/p999；
  • 故障正确：节点重启、超时、网络分区或消费者崩溃后状态可解释；
  • 运维正确：有容量阈值、报警、回滚和恢复演练。

13.4 失败模式 / 什么时候不该这么做

不要把一个租户的所有对象塞进单 Hash 来省 key；那会把迁移、删除、过期和热点都集中在一个 Big Key 上。

进一步判断时，可以问自己：

  • 这个方案是不是把问题从 Redis 转移到了客户端，却没有减少总体复杂度？
  • 如果 key、QPS、成员数扩大 10～100 倍，是否出现不可分割的单点成本？
  • 如果 primary 在最坏时刻故障，已经返回给用户的结果是否仍然成立？
  • 如果 Redis 整层不可用，业务是 fail-open、fail-closed 还是降级到其他数据源？

13.5 源码阅读路线

建议从 命令语义 → 数据结构 → 生命周期/故障路径 三层阅读，而不是从 server.c 顺序翻完整仓库。

  • 推荐入口：src/object.c + 对应 src/t_*.c 命令实现
  • 第一步：在该 Redis 版本的 command table 中定位命令 handler；
  • 第二步：跟到对象编码/数据结构操作，记录关键 Big-O 和可能的全量遍历；
  • 第三步：继续追踪 replication、AOF/RDB、lazyfree、Cluster 等副作用；
  • 第四步：对照官方命令页的 time complexity、版本变更与 ACL category。

源码路径属于阅读导航，不是稳定 API；升级 Redis 后应以目标 tag/commit 为准。

13.6 高频追问：标准应答

追问 A：如果数据规模扩大 100 倍，结论会变吗？
要重新估算元素数、value/reply bytes、热点和 Cluster。小 Hash 常使用紧凑编码，可能很省内存，但超多字段会变成 Big Key。Redis 8.10 Compact Hash 面向大量共享 schema 的 Hash，通过复用字段名进一步降低内存；是否更省必须用 MEMORY USAGE 和真实 workload 验证。

追问 B：什么时候不该用这个方案？
不要把一个租户的所有对象塞进单 Hash 来省 key；那会把迁移、删除、过期和热点都集中在一个 Big Key 上。 这类边界比背命令更能体现工程判断。

13.7 面试官继续深挖时的回答结构

可以按下面顺序组织 2～5 分钟回答：

  1. 定义：一句话说明它解决什么问题；
  2. 机制：画出数据流/状态机，说明 Redis 内部怎样实现；
  3. 复杂度：给 Big-O，同时指出 N 与 byte size；
  4. 边界：Big Key、Hot Key、Cluster、复制、故障时会怎样；
  5. 方案：为什么选它，而不是最相近的替代方案；
  6. 验证：给出线上指标、命令或故障注入；
  7. 版本：若是 Redis 8.x 新能力，明确最低版本和回滚兼容。
