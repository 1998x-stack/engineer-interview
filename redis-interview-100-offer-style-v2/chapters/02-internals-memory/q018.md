# Q018 · 什么是 Hot Key？

> **难度：** 基础必会  
> **所属章节：** 02 · 底层编码与内存机制  
> **PDF 对应页：** 23  
> **目标：** 先在 60 秒内给结论，再用机制、边界和生产验证把答案展开。

## 1. 30–60 秒面试标准回答

Hot Key 指请求量高度集中到少数 key。即使 Cluster 有很多 shard，一个 key 仍只属于一个 slot 和一个 primary，因此热点不会被自动均摊。

## 2. PDF 原理拆解

热点可以是读热点、写热点或大结果集热点； 多个 key 因 hash tag/业务分布集中在同一 slot 还会形成 Hot Slot。 应按 shard、slot、key 看流量，而不是只看集群平均 CPU。

## 3. PDF 高频追问与答题抓手

- 追问 1 如果数据规模扩大 100 倍，什么是 Hot Key 的结论会发生什么变化？

- 追问 2 如何用 OBJECT ENCODING / MEMORY USAGE / --bigkeys 等手段验证你的判断？

答题抓手：面试加分点：指出“单 Hot Key 加机器通常无效”，需要本地缓存、副本化、请求合并或重构 key。

## 4. PDF 易错点 / Gotchas

不要把 Hot Key 和 Big Key 混为一谈；也不要认为扩容节点数自动解决单热点。

## 5. PDF 工程落地

面试加分点：指出“单 Hot Key 加机器通常无效”，需要本地缓存、副本化、请求合并或重构 key。

> **PDF 一句话拿分：** Hot Key 指请求量高度集中到少数 key。  
> **GitHub 增强版一句话：** Hot Key 是流量集中而非 value 大。


## 6. 深度扩展：从“会答”到“能设计”

Hot Key 是流量集中而非 value 大。Cluster 只能按 key 分 slot，一个极热 key 仍然落在单 shard，因此热点必须在数据模型、客户端缓存或请求合并层处理。

### 6.1 成本 / 复杂度模型

内部优化常在“紧凑线性结构”和“通用索引结构”间切换，阈值附近需要用真实 workload benchmark。

### 6.2 生产判断框架

- 使用 `OBJECT ENCODING`、`MEMORY USAGE` 和真实数据分布验证内部编码假设。
- 不要把内部 encoding 当稳定 API；版本升级后实现可能变化。

### 6.3 面试时应主动补出的边界

- 先说明当前结论成立的前提：数据规模、读写比、是否 Cluster、是否允许数据丢失/陈旧。
- 如果涉及集合或批处理，必须说明 Big Key、单次返回体积和核心执行路径阻塞风险。
- 如果涉及 HA/一致性，必须明确网络分区、进程崩溃和 failover 后的行为，而不是只描述正常路径。
- 如果涉及性能，优先给出可观测指标和验证实验，不用“Redis 很快”替代测量。

### 6.4 可观测与验证指标

- `used_memory / RSS / fragmentation`
- `encoding 分布`
- `allocator stats`
- `Big Key 与对象基数分布`

### 6.5 故障注入 / 实验设计

构造小对象→大对象的阈值实验，观察 OBJECT ENCODING、MEMORY USAGE 与延迟何时发生跃迁。

## 13. 专业深挖补充（v2）

> **来源说明：** 第 1–5 节保留 PDF 母版主线；本节是 GitHub 增强内容，结合 Redis 官方文档、当前版本实现语义与生产工程实践扩展。

### 13.1 核心机制再推导

Hot Key 是流量分布问题，不是内存大小问题。Cluster 的平均 CPU 很低也可能有一个 primary 因单 key/slot 过热而打满。

不要停留在“记住结论”。面试时建议把本题改写成一条因果链：

```text
业务目标 / SLO
  ↓
Redis 提供的原语或内部机制
  ↓
复杂度、内存、网络与一致性成本
  ↓
故障/扩容时的边界
  ↓
可观测指标与验证实验
```

### 13.2 复杂度、容量与性能模型

`load_shard = Σ QPS(key_i) × cost(command_i)`；热点看最大 shard/slot，而不是平均值。

计算复杂度只说明算法增长趋势，生产还必须补充四个量：

1. **N 到底是什么**：key 数、member 数、字段数、请求数还是字节数；
2. **一次返回多少字节**：很多“查找 O(1)”最终被大 reply 的网络/序列化成本主导；
3. **最坏 key/slot/shard 多大**：平均值无法解释热点和尾延迟；
4. **背景任务是否叠加**：fork、rewrite、expire、eviction、reshard 都可能与前台 workload 竞争资源。

### 13.3 生产案例推演

营销活动开始后商品详情 key 从 5k QPS 突增到 300k QPS，其他 shard 空闲；此时扩两个新 primary 并不会自动迁移这个单 key 的负载。

面试中不要只说“可以这样做”，还应给出验收口径：

- 功能正确：正常路径和重试路径结果一致；
- 性能正确：用真实 value/member 分布测 p50/p99/p999；
- 故障正确：节点重启、超时、网络分区或消费者崩溃后状态可解释；
- 运维正确：有容量阈值、报警、回滚和恢复演练。

### 13.4 失败模式 / 什么时候不该这么做

不要只看节点平均值；热点检测要按 key/slot/shard 和读写方向分层。

进一步判断时，可以问自己：

- 这个方案是不是把问题从 Redis 转移到了客户端，却没有减少总体复杂度？
- 如果 key、QPS、成员数扩大 10～100 倍，是否出现不可分割的单点成本？
- 如果 primary 在最坏时刻故障，已经返回给用户的结果是否仍然成立？
- 如果 Redis 整层不可用，业务是 fail-open、fail-closed 还是降级到其他数据源？

### 13.5 源码阅读路线

建议从 **命令语义 → 数据结构 → 生命周期/故障路径** 三层阅读，而不是从 `server.c` 顺序翻完整仓库。

- 推荐入口：命令统计/对象访问路径 + `src/evict.c`（LFU/LRU 元数据）
- 第一步：在该 Redis 版本的 command table 中定位命令 handler；
- 第二步：跟到对象编码/数据结构操作，记录关键 Big-O 和可能的全量遍历；
- 第三步：继续追踪 replication、AOF/RDB、lazyfree、Cluster 等副作用；
- 第四步：对照官方命令页的 `time complexity`、版本变更与 ACL category。

> 源码路径属于阅读导航，不是稳定 API；升级 Redis 后应以目标 tag/commit 为准。

### 13.6 高频追问：标准应答

**追问 A：如果数据规模扩大 100 倍，结论会变吗？**  
要重新估算元素数、value/reply bytes、热点和 Cluster。热点可以是读热点、写热点或大结果集热点；多个 key 因 hash tag/业务分布集中在同一 slot 还会形成 Hot Slot。应按 shard、slot、key 看流量，而不是只看集群平均 CPU。

**追问 B：什么时候不该用这个方案？**  
不要只看节点平均值；热点检测要按 key/slot/shard 和读写方向分层。 这类边界比背命令更能体现工程判断。

### 13.7 面试官继续深挖时的回答结构

可以按下面顺序组织 2～5 分钟回答：

1. **定义**：一句话说明它解决什么问题；
2. **机制**：画出数据流/状态机，说明 Redis 内部怎样实现；
3. **复杂度**：给 Big-O，同时指出 N 与 byte size；
4. **边界**：Big Key、Hot Key、Cluster、复制、故障时会怎样；
5. **方案**：为什么选它，而不是最相近的替代方案；
6. **验证**：给出线上指标、命令或故障注入；
7. **版本**：若是 Redis 8.x 新能力，明确最低版本和回滚兼容。
