# Q024 · Redis 有哪些 maxmemory 淘汰策略？

> **难度：** 基础必会  
> **所属章节：** 03 · TTL、缓存模式与淘汰  
> **PDF 对应页：** 30  
> **目标：** 先在 60 秒内给结论，再用机制、边界和生产验证把答案展开。

## 1. 30–60 秒面试标准回答

常见有 allkeys-lru/lfu/random、volatile-lru/lfu/random/ttl、noeviction。`allkeys-*` 从所有 key 选牺牲者， `volatile-*` 只从设置 TTL 的 key 中选。

## 2. PDF 原理拆解

通用 cache 常从 allkeys-lru 或 allkeys-lfu 开始评估； noeviction 适合不能默默丢业务状态、宁愿显式写失败的场景。 策略选择依访问分布，不存在固定万能答案。

## 3. PDF 高频追问与答题抓手

- 追问 1 这个机制在高并发或故障时最容易失效在哪里？

- 追问 2 如果目标从“性能优先”改成“数据安全优先”，方案需要怎么变？

答题抓手：答题先说明候选集合，再说明 victim 选择算法，最后结合 workload 解释 LRU/LFU。

## 4. PDF 易错点 / Gotchas

不要把 maxmemory 当物理 RAM 上限；不要以为 volatile 策略会自动给无 TTL key 加 TTL。

## 5. PDF 工程落地

答题先说明候选集合，再说明 victim 选择算法，最后结合 workload 解释 LRU/LFU。

> **PDF 一句话拿分：** 常见有 allkeys-lru/lfu/random、volatile-lru/lfu/random/ttl、noeviction。  
> **GitHub 增强版一句话：** 淘汰策略首先是业务语义选择：纯缓存更常用 allkeys 类，混合持久/缓存数据才可能使用 volatile 类。


## 6. 深度扩展：从“会答”到“能设计”

淘汰策略首先是业务语义选择：纯缓存更常用 allkeys 类，混合持久/缓存数据才可能使用 volatile 类。`noeviction` 并非“更安全”，它会把压力转移成写失败。

### 6.1 成本 / 复杂度模型

淘汰决策使用近似采样，实际开销取决于内存压力与淘汰频率。

### 6.2 生产判断框架

- 缓存方案必须同时写出 miss、回源、失效、重试和降级路径。
- 关注 hit ratio 之外的数据库 QPS、stale window 与 p99。

### 6.3 面试时应主动补出的边界

- 先说明当前结论成立的前提：数据规模、读写比、是否 Cluster、是否允许数据丢失/陈旧。
- 如果涉及集合或批处理，必须说明 Big Key、单次返回体积和核心执行路径阻塞风险。
- 如果涉及 HA/一致性，必须明确网络分区、进程崩溃和 failover 后的行为，而不是只描述正常路径。
- 如果涉及性能，优先给出可观测指标和验证实验，不用“Redis 很快”替代测量。

### 6.4 可观测与验证指标

- `hit ratio / miss QPS`
- `DB fallback QPS`
- `evicted_keys / expired_keys`
- `stale window 与 rebuild latency`

### 6.5 故障注入 / 实验设计

人为让热点 key 同时失效或让缓存层不可用 30 秒，验证 singleflight、DB 限流和降级是否真的生效。

## 13. 专业深挖补充（v2）

> **来源说明：** 第 1–5 节保留 PDF 母版主线；本节是 GitHub 增强内容，结合 Redis 官方文档、当前版本实现语义与生产工程实践扩展。

### 13.1 核心机制再推导

maxmemory policy 有两个维度：候选集合（allkeys/volatile）与牺牲者策略（LRU/LFU/random/TTL）。`noeviction` 则把压力反馈给写请求。

不要停留在“记住结论”。面试时建议把本题改写成一条因果链：

```text
业务目标 / SLO
  ↓
Redis 提供的原语或内部机制
  ↓
复杂度、内存、网络与一致性成本
  ↓
故障/扩容时的边界
  ↓
可观测指标与验证实验
```

### 13.2 复杂度、容量与性能模型

策略优劣用 `hit_rate × miss_cost`、热点半衰期和内存预算评估；复杂度之外更关键是工作负载分布。

计算复杂度只说明算法增长趋势，生产还必须补充四个量：

1. **N 到底是什么**：key 数、member 数、字段数、请求数还是字节数；
2. **一次返回多少字节**：很多“查找 O(1)”最终被大 reply 的网络/序列化成本主导；
3. **最坏 key/slot/shard 多大**：平均值无法解释热点和尾延迟；
4. **背景任务是否叠加**：fork、rewrite、expire、eviction、reshard 都可能与前台 workload 竞争资源。

### 13.3 生产案例推演

纯缓存池用 allkeys-lfu；混合“不可丢状态 + 可丢缓存”最好不要共用一个实例，否则 allkeys 策略可能淘汰业务状态，volatile 策略又可能没有足够候选。

面试中不要只说“可以这样做”，还应给出验收口径：

- 功能正确：正常路径和重试路径结果一致；
- 性能正确：用真实 value/member 分布测 p50/p99/p999；
- 故障正确：节点重启、超时、网络分区或消费者崩溃后状态可解释；
- 运维正确：有容量阈值、报警、回滚和恢复演练。

### 13.4 失败模式 / 什么时候不该这么做

把不同 durability 语义的数据混在同一实例，会让 eviction policy 很难正确配置。

进一步判断时，可以问自己：

- 这个方案是不是把问题从 Redis 转移到了客户端，却没有减少总体复杂度？
- 如果 key、QPS、成员数扩大 10～100 倍，是否出现不可分割的单点成本？
- 如果 primary 在最坏时刻故障，已经返回给用户的结果是否仍然成立？
- 如果 Redis 整层不可用，业务是 fail-open、fail-closed 还是降级到其他数据源？

### 13.5 源码阅读路线

建议从 **命令语义 → 数据结构 → 生命周期/故障路径** 三层阅读，而不是从 `server.c` 顺序翻完整仓库。

- 推荐入口：`src/evict.c`
- 第一步：在该 Redis 版本的 command table 中定位命令 handler；
- 第二步：跟到对象编码/数据结构操作，记录关键 Big-O 和可能的全量遍历；
- 第三步：继续追踪 replication、AOF/RDB、lazyfree、Cluster 等副作用；
- 第四步：对照官方命令页的 `time complexity`、版本变更与 ACL category。

> 源码路径属于阅读导航，不是稳定 API；升级 Redis 后应以目标 tag/commit 为准。

### 13.6 高频追问：标准应答

**追问 A：如果数据规模扩大 100 倍，结论会变吗？**  
要重新估算元素数、value/reply bytes、热点和 Cluster。通用 cache 常从 allkeys-lru 或 allkeys-lfu 开始评估；noeviction 适合不能默默丢业务状态、宁愿显式写失败的场景。策略选择依访问分布，不存在固定万能答案。

**追问 B：什么时候不该用这个方案？**  
把不同 durability 语义的数据混在同一实例，会让 eviction policy 很难正确配置。 这类边界比背命令更能体现工程判断。

### 13.7 面试官继续深挖时的回答结构

可以按下面顺序组织 2～5 分钟回答：

1. **定义**：一句话说明它解决什么问题；
2. **机制**：画出数据流/状态机，说明 Redis 内部怎样实现；
3. **复杂度**：给 Big-O，同时指出 N 与 byte size；
4. **边界**：Big Key、Hot Key、Cluster、复制、故障时会怎样；
5. **方案**：为什么选它，而不是最相近的替代方案；
6. **验证**：给出线上指标、命令或故障注入；
7. **版本**：若是 Redis 8.x 新能力，明确最低版本和回滚兼容。
