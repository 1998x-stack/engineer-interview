# Q097 · 设计一个秒杀库存系统，你会怎么用 Redis？

> **难度：** 系统设计  
> **所属章节：** 10 · Redis 8.x 与系统设计压轴题  
> **PDF 对应页：** 110  
> **目标：** 先在 60 秒内给结论，再用机制、边界和生产验证把答案展开。

## 1. 30–60 秒面试标准回答

秒杀不能只回答 `DECR stock`。完整链路应包括入口限流、用户去重、Redis 原子预扣库存、成功事件进入 Streams/MQ、数据库最终建单、支付超时/失败补偿和幂等。

## 2. PDF 原理拆解

Lua/Function 可原子执行“是否重复购买 + stock>0 + 扣减 + 写 reservation/event”。

`DB 用唯一约束/状态机保证事件幂等；`

Redis 扣库存成功但 DB 失败必须有补偿，不是简单无条件加回库存。

## 3. PDF 高频追问与答题抓手

- 追问 1 你会用哪些指标或实验验证这个方案，而不是凭经验判断？

- 追问 2 当 p99、内存或可用性目标冲突时，你会如何做权衡？

答题抓手：高分框架：流量控制 -> 原子预扣 -> durable event -> DB 幂等 -> 补偿 -> 监控/对账。

## 4. PDF 易错点 / Gotchas

不要把 Redis 原子扣减等价为全链路分布式事务；不要没有幂等 ID 和补偿状态机。

## 5. PDF 工程落地

高分框架：流量控制 -> 原子预扣 -> durable event -> DB 幂等 -> 补偿 -> 监控/对账。

> **PDF 一句话拿分：** 秒杀不能只回答 `DECR stock`。  
> **GitHub 增强版一句话：** 秒杀系统要把“Redis 原子扣库存”和“订单业务事务”分开。


## 6. 深度扩展：从“会答”到“能设计”

秒杀系统要把“Redis 原子扣库存”和“订单业务事务”分开。前者解决高并发预占，后者仍需异步落库、幂等、超时释放、支付补偿与对账。

### 6.1 成本 / 复杂度模型

新版数据结构与系统设计需要同时量化吞吐、内存、准确性、可用性和运维复杂度。

### 6.2 生产判断框架

- 新版能力要说明版本基线与回退方案。
- 系统设计必须把容量、可用性、一致性和成本写成可验证指标。

### 6.3 面试时应主动补出的边界

- 先说明当前结论成立的前提：数据规模、读写比、是否 Cluster、是否允许数据丢失/陈旧。
- 如果涉及集合或批处理，必须说明 Big Key、单次返回体积和核心执行路径阻塞风险。
- 如果涉及 HA/一致性，必须明确网络分区、进程崩溃和 failover 后的行为，而不是只描述正常路径。
- 如果涉及性能，优先给出可观测指标和验证实验，不用“Redis 很快”替代测量。

### 6.4 可观测与验证指标

- `per-shard peak QPS`
- `headroom after failover`
- `RPO/RTO drill result`
- `cost per million ops / memory efficiency`

### 6.5 故障注入 / 实验设计

做容量和故障演练而非只做功能测试：单 shard 过载、replica 提升、缓存雪崩、网络分区、恢复和回滚。

### 6.6 面试白板图

```mermaid
flowchart LR
  U[Users] --> G[Gateway rate limit]
  G --> R[Redis atomic stock reservation]
  R --> Q[Stream/MQ]
  Q --> O[Order service]
  O --> D[(DB)]
  O --> C[Compensation / timeout release]
```

## 13. 专业深挖补充（v2）

> **来源说明：** 第 1–5 节保留 PDF 母版主线；本节是 GitHub 增强内容，结合 Redis 官方文档、当前版本实现语义与生产工程实践扩展。

### 13.1 核心机制再推导

秒杀系统最关键的是把“高并发资格判断”与“最终订单事实”分层。Redis 只负责快速原子预扣/幂等，可靠 MQ/DB 完成最终落单并有补偿状态机。

不要停留在“记住结论”。面试时建议把本题改写成一条因果链：

```text
业务目标 / SLO
  ↓
Redis 提供的原语或内部机制
  ↓
复杂度、内存、网络与一致性成本
  ↓
故障/扩容时的边界
  ↓
可观测指标与验证实验
```

### 13.2 复杂度、容量与性能模型

新版能力/系统设计应把吞吐、内存、准确性、版本兼容和回滚成本同时量化。

计算复杂度只说明算法增长趋势，生产还必须补充四个量：

1. **N 到底是什么**：key 数、member 数、字段数、请求数还是字节数；
2. **一次返回多少字节**：很多“查找 O(1)”最终被大 reply 的网络/序列化成本主导；
3. **最坏 key/slot/shard 多大**：平均值无法解释热点和尾延迟；
4. **背景任务是否叠加**：fork、rewrite、expire、eviction、reshard 都可能与前台 workload 竞争资源。

### 13.3 生产案例推演

Lua/Function 检查用户未购与库存>0后扣减并写 reservation，再投递 Stream/MQ；DB 用唯一订单约束，失败后补偿释放库存或记录对账任务。

面试中不要只说“可以这样做”，还应给出验收口径：

- 功能正确：正常路径和重试路径结果一致；
- 性能正确：用真实 value/member 分布测 p50/p99/p999；
- 故障正确：节点重启、超时、网络分区或消费者崩溃后状态可解释；
- 运维正确：有容量阈值、报警、回滚和恢复演练。

### 13.4 失败模式 / 什么时候不该这么做

不要把 Redis 扣减成功当订单事务提交；进程崩溃、消息重复、支付超时和补偿重入都必须设计幂等。

进一步判断时，可以问自己：

- 这个方案是不是把问题从 Redis 转移到了客户端，却没有减少总体复杂度？
- 如果 key、QPS、成员数扩大 10～100 倍，是否出现不可分割的单点成本？
- 如果 primary 在最坏时刻故障，已经返回给用户的结果是否仍然成立？
- 如果 Redis 整层不可用，业务是 fail-open、fail-closed 还是降级到其他数据源？

### 13.5 源码阅读路线

建议从 **命令语义 → 数据结构 → 生命周期/故障路径** 三层阅读，而不是从 `server.c` 顺序翻完整仓库。

- 推荐入口：`src/eval.c`/Functions + Streams/DB 幂等链路
- 第一步：在该 Redis 版本的 command table 中定位命令 handler；
- 第二步：跟到对象编码/数据结构操作，记录关键 Big-O 和可能的全量遍历；
- 第三步：继续追踪 replication、AOF/RDB、lazyfree、Cluster 等副作用；
- 第四步：对照官方命令页的 `time complexity`、版本变更与 ACL category。

> 源码路径属于阅读导航，不是稳定 API；升级 Redis 后应以目标 tag/commit 为准。

### 13.6 高频追问：标准应答

**追问 A：新版能力上线时最容易遗漏什么？**  
不要把 Redis 原子扣减等价为全链路分布式事务；不要没有幂等 ID 和补偿状态机。 应明确版本基线、客户端兼容、资源隔离、灰度指标和回滚路径。

**追问 B：如何证明这个方案值得用？**  
高分框架：流量控制 -> 原子预扣 -> durable event -> DB 幂等 -> 补偿 -> 监控/对账。 用真实数据集测吞吐、p99、内存、准确性/召回和故障恢复，而不是只做功能 demo。

### 13.7 面试官继续深挖时的回答结构

可以按下面顺序组织 2～5 分钟回答：

1. **定义**：一句话说明它解决什么问题；
2. **机制**：画出数据流/状态机，说明 Redis 内部怎样实现；
3. **复杂度**：给 Big-O，同时指出 N 与 byte size；
4. **边界**：Big Key、Hot Key、Cluster、复制、故障时会怎样；
5. **方案**：为什么选它，而不是最相近的替代方案；
6. **验证**：给出线上指标、命令或故障注入；
7. **版本**：若是 Redis 8.x 新能力，明确最低版本和回滚兼容。
