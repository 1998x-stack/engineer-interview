Q001 为什么 Transformer 能取代 RNN/LSTM？

章节：1. Transformer 总体架构与设计动机
难度：2/5 · 频率：高频 · 形式：概念 / 推导 / 追问
内容分层：PDF Core 来自原 PDF 的观点重排；Professional Expansion 为在不改变 PDF 主结论基础上的原创扩展。

1. 面试官在考什么 — PDF Core

判断你是否从计算图、并行性和长距离依赖路径理解 Transformer 的设计动机，而不是只会 说“Attention 更强”。

2. 30 秒回答 — PDF Core

RNN 的隐藏状态具有严格时间依赖，训练沿序列维度串行；Self-Attention 可以一次计算所有 token 间的相关性，并 把任意两个 token 的信息传播路径缩短到一层。代价是标准 Attention 在长序列上引入 O(T²) 的 pairwise 计算与中间 存储。 h_t=f(h_{t-1},x_t) vs. Attention(X)=softmax(QKᵀ/√d_k)V

3. 核心公式 / Shape

RNN: $h_t=f(h_{t-1},x_t)$；Attention block 核心成本约 $O(Td^2+T^2d)$。

4. 深度拆解 — PDF Core

  • RNN 的关键递推是 h_t=f(h_{t-1},x_t)，因此 h_t 不能在 h_{t-1} 未完成时计算。
  • Self-Attention 直接形成 T×T 的交互图，训练阶段序列维度可并行。
  • 长距离依赖的“最短路径长度”由 RNN 的 O(T) 降到单层 Attention 的 O(1)。
  • Transformer 不是“无序列依赖”：自回归解码仍然逐 token 串行；它主要解除训练阶段的递推依赖。
  • 真正的 trade-off 是：更好的并行性与全局交互，换来 Attention 在长上下文下的二次复杂度与显存/带宽压力。

5. Professional Expansion：为什么这题值得深挖

把比较拆成计算图、最短依赖路径和硬件并行三层。RNN 的递推边决定序列维串行；Self-Attention 把序列建成稠密可微图，但也引入 T×T 交互。

5.1 工程实现 / 系统视角

用 profiler 分别测 QKV/MLP GEMM 与 attention kernel；当 T≪d 时 O(Td²) 可能比 O(T²d) 更主导。

5.2 边界条件与反例

不要把训练并行性与自回归 decode 并行性混为一谈。

5.3 建议亲手做的验证实验

  • 固定 d，扫描 T=128→8192，记录 attention/MLP wall-clock 占比。
  • 记录至少一种 correctness metric 与一种 performance metric；不要只凭“代码能运行”判定实现正确。

5.4 3 分钟专业版答法

面试时可以按下面节奏展开：

第一句给结论：RNN 的隐藏状态具有严格时间依赖，训练沿序列维度串行；Self-Attention 可以一次计算所有 token 间的相关性，并 把任意两个 token 的信息传播路径缩短到一层。代价是标准 Attention 在长序列上引入 O(T²) 的 pairwise 计算与中间 存储。 h_t=f(h_{t-1},x_t) vs. Attention(X)=softmax(QKᵀ/√d_k)V
第二层讲机制：RNN 的关键递推是 h_t=f(h_{t-1},x_t)，因此 h_t 不能在 h_{t-1} 未完成时计算。；Self-Attention 直接形成 T×T 的交互图，训练阶段序列维度可并行。；长距离依赖的“最短路径长度”由 RNN 的 O(T) 降到单层 Attention 的 O(1)。
第三层补工程条件：把本题放到真实 Tensor Shape、训练/推理阶段与硬件约束下重新检查；如果结论涉及“更快/更省/更稳定”，必须说明比较基线和适用条件。
最后主动给验证：用最小行为测试、数值 parity、profiler 或 ablation 证明，而不是停留在直觉。

5.5 复杂度与资源矩阵

维度 本题应如何分析
参数量 关注 Attention / FFN / embedding 的参数主项；head 数与总 hidden size 的关系必须说清。
FLOPs 同时比较 $O(Td^2)$ 的投影/MLP 与 $O(T^2d)$ 的 token-pair 交互。
Activation 训练阶段保存中间激活；层数与 sequence length 都会放大显存。
并行性 训练 sequence 维可并行，但自回归生成仍存在 token-level dependency。
主要验证 shape invariant、gradient path、tiny overfit。

5.6 本题关键不变量

  • Residual 子层的输入输出 hidden width 必须一致。
  • 训练并行性与 autoregressive decode 串行性要分开陈述。
  • 对任何“更快/更强”的结论都注明 T、d、batch 与任务条件。

6. 面试中的推导顺序

  1. 先定义：一句话说明对象是什么、输入输出是什么。
  2. 再公式：写最小核心公式，并标出关键维度。
  3. 解释 Why：它解决前一代方案的什么瓶颈。
  4. 算成本：参数、FLOPs、activation/KV memory、IO/通信分别看。
  5. 讲 Gotcha：至少指出一个数值或实现陷阱。
  6. 收束 Trade-off：明确什么条件下它不一定更优。

7. 常见失分点 — PDF Core

  • 把“训练并行”误说成“生成也完全并行”；或者只回答“能看到全局”。

8. 面试官继续追问 — PDF Core

如果序列长度 T 很短、hidden size d 很大，Attention 一定是主要算力瓶颈吗？请写出 O(Td²+T²d) 并讨论 主导项。

扩展追问树

  • 如果把关键超参数扩大 4 倍，参数量 / FLOPs / 显存 / latency 哪一项最先成为瓶颈？
  • 如果在 训练 与 增量推理 两个阶段分别使用，本题结论有哪些不同？
  • 如何写一个最小单元测试或 ablation，证明你的解释而不是只靠直觉？

13. 深入推导：把结论变成可验证的模型

Transformer 相对 RNN 的核心优势不是“Attention 天生更聪明”，而是计算图更适合现代硬件。RNN 在时间轴上存在长度为 $T$ 的依赖链；Self-Attention 把同层 token 连接成稠密图，使训练时可把序列维工作转化为大规模 GEMM。代价是连接数从局部递推变成 $T^2$ 级 pairwise interaction。

面试时最好把“表达能力、优化难度、硬件效率”分开讨论：同样的理论复杂度并不能保证同样的 wall-clock；在短序列、大 $d$ 场景，QKV/MLP 的 $O(Td^2)$ 可能比 attention 的 $O(T^2d)$ 更主导。

13.1 本章心智模型

从“为什么需要 Transformer”一路回答到 block、shape、residual 与模块职责。核心是建立计算图和张量图。

这意味着面试时不要停在术语层。每个结论至少回答四个问题：成立所需假设是什么？张量/概率对象是什么？成本落在哪里？怎样设计反例或单测证伪？

14. 题目特异的工程 Checklist

  • 不只写 big-O：把计算、HBM IO、网络通信、allocator 与调度分别量化。
  • 任何“更快”都说明硬件、batch/context 分布、精度和质量基线。
  • 同时看平均与 P95/P99，防止吞吐优化牺牲尾延迟。
  • 设计 rollback/quality regression，确保系统优化没有改变模型语义。

15. 推荐验证协议

  1. Parameterized unit tests：覆盖不同 B/T/H/dtype/mask。
  2. Behavioural test：测试未来泄漏、padding invariance、cache reset 等语义。
  3. Oracle comparison：优化代码与朴素 reference 比较输出和梯度。

验证结果建议至少记录：

类型 最低要求
Correctness reference parity / invariant / leakage test 至少一项
Numerical NaN/Inf、max/RMS、dtype 差异
Performance wall-clock、显存/bytes、P95/P99（系统题）
Quality loss/perplexity/任务指标；结构改动必须做回归

16. 面试官真正想听到的“边界条件”

  • 不要把渐进复杂度等同于实际速度：kernel、batch、长度、硬件与 IO 会改变主导项。
  • 不要把一种实现当成数学定义：mask 语义、layout、fused kernel、cache allocator 都可能变化。
  • 不要把单点 benchmark 当成普遍规律：至少说明 $B,T,d,H$、dtype、device 和任务分布。
  • 不要把“能运行”当成“正确”：Transformer 很多 bug 会正常降 loss，但存在未来泄漏、错误广播或 cache position 错位。

17. Whiteboard / Coding 表达模板

当面试官要求现场推导或编码，可按以下顺序：

  1. 写输入输出 shape 与符号定义；
  2. 写最小核心公式，不先写优化；
  3. 写 2–3 个 invariants/assertions；
  4. 给 reference 实现或手算小例子；
  5. 再讨论 fused kernel、cache、并行或量化；
  6. 最后给测试与 benchmark 设计。

Strong Hire 信号：不仅能解释“为什么”，还能说出“什么情况下不成立，以及我会怎么证明”。
