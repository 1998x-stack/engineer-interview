Q090 Coding：从零实现 Multi-Head Attention

章节：8. 长上下文、高性能 Attention 与 MoE
难度：3/5 · 频率：高频 · 形式：概念 / 推导 / 追问
内容分层：PDF Core 来自原 PDF 的观点重排；Professional Expansion 为在不改变 PDF 主结论基础上的原创扩展。

1. 面试官在考什么 — PDF Core

代码与 shape 共同考察，必须正确处理 reshape、mask、softmax、合并 heads。

2. 30 秒回答 — PDF Core

实现时把 Q/K/V 投影到 [B,H,T,D_h]，计算 scaled score，在 logits 上应用 mask，沿 key 维 softmax，乘 V，再 transpose/reshape 回 [B,T,d] 并做 W_O。

3. 核心公式 / Shape

4. 深度拆解 — PDF Core

  • 保证 d_model%num_heads==0。
  • transpose 后注意 contiguous/view。
  • mask dtype 与广播 shape。
  • 训练/推理 dropout 行为。 代码 / 伪代码骨架 class MHA(nn.Module): def forward(self, x, mask=None): B,T,D = x.shape q = self.q(x).view(B,T,self.h,self.dh).transpose(1,2) k = self.k(x).view(B,T,self.h,self.dh).transpose(1,2) v = self.v(x).view(B,T,self.h,self.dh).transpose(1,2) s = (q @ k.transpose(-2,-1)) / math.sqrt(self.dh) if mask is not None: s = s.masked_fill(~mask, float('-inf')) a = torch.softmax(s, dim=-1) y = a @ v y = y.transpose(1,2).contiguous().view(B,T,D) return self.o(y)

5. Professional Expansion：为什么这题值得深挖

面试实现要同时证明数学、shape、mask、数值稳定和 layout 正确；最好准备一个朴素 oracle 与 SDPA 对照。

5.1 工程实现 / 系统视角

代码中写 assert、stable mask、contiguous/reshape，测试 self/cross/causal。

5.2 边界条件与反例

能跑不代表语义正确。

5.3 建议亲手做的验证实验

  • 实现后做 gradcheck/forward parity。
  • 记录至少一种 correctness metric 与一种 performance metric；不要只凭“代码能运行”判定实现正确。

5.4 3 分钟专业版答法

面试时可以按下面节奏展开：

第一句给结论：实现时把 Q/K/V 投影到 [B,H,T,D_h]，计算 scaled score，在 logits 上应用 mask，沿 key 维 softmax，乘 V，再 transpose/reshape 回 [B,T,d] 并做 W_O。
第二层讲机制：保证 d_model%num_heads==0。；transpose 后注意 contiguous/view。；mask dtype 与广播 shape。
第三层补工程条件：把本题放到真实 Tensor Shape、训练/推理阶段与硬件约束下重新检查；如果结论涉及“更快/更省/更稳定”，必须说明比较基线和适用条件。
最后主动给验证：用最小行为测试、数值 parity、profiler 或 ablation 证明，而不是停留在直觉。

5.5 复杂度与资源矩阵

维度 本题应如何分析
算法复杂度 先写理论 FLOPs / memory，再判断实现是否改变函数本身。
硬件复杂度 HBM IO、SRAM tile、kernel launch、通信可能比 FLOPs 更决定 wall-clock。
质量风险 近似 attention / quantization / sparsity 需要单独做 quality regression。
长上下文 T 增长同时放大 compute、KV、position extrapolation 与 TTFT。
主要验证 profiler + memory trace + accuracy/perplexity + length sweep。

5.6 本题关键不变量

  • 理论复杂度与实际 wall-clock 分开报告。
  • 任何近似/量化/稀疏优化都必须做 quality regression。
  • benchmark 必须给出硬件、dtype、batch、context/output length。

6. Reference Implementation / Test Skeleton

import math
import torch
import torch.nn as nn

class MultiHeadAttention(nn.Module):
    def __init__(self, d_model: int, num_heads: int):
        super().__init__()
        assert d_model % num_heads == 0
        self.h = num_heads
        self.dh = d_model // num_heads
        self.qkv = nn.Linear(d_model, 3 * d_model, bias=False)
        self.out = nn.Linear(d_model, d_model, bias=False)

    def forward(self, x, mask=None):
        B, T, D = x.shape
        q, k, v = self.qkv(x).chunk(3, dim=-1)
        def split(t):
            return t.view(B, T, self.h, self.dh).transpose(1, 2)
        q, k, v = map(split, (q, k, v))
        scores = q @ k.transpose(-2, -1) / math.sqrt(self.dh)
        if mask is not None:
            scores = scores.masked_fill(~mask, float("-inf"))
        p = torch.softmax(scores, dim=-1)
        y = p @ v
        y = y.transpose(1, 2).contiguous().view(B, T, D)
        return self.out(y)

13. 深入推导：把结论变成可验证的模型

从零实现 MHA 时，优先写一个“慢但清晰”的 reference，再优化。reference 应显式检查 D % H == 0、mask broadcast、softmax dim、dropout/eval、contiguous reshape；之后用 PyTorch SDPA/FlashAttention 做 oracle parity。

面试 coding 的高分点是边写边说 shape contract，并主动给出 causal leakage 单测，而不是最后才调 tensor size error。

13.1 本章心智模型

把高效 Transformer 放到 GPU/通信/稀疏计算上讨论，区分算法复杂度和系统效率。

这意味着面试时不要停在术语层。每个结论至少回答四个问题：成立所需假设是什么？张量/概率对象是什么？成本落在哪里？怎样设计反例或单测证伪？

14. 题目特异的工程 Checklist

attention 检查表

  • 写出 Q/K/V 与 score 的完整 shape，尤其区分 $T_q$、$T_k$、$H_q$、$H_{kv}$。
  • 明确 softmax 的归一化轴、mask 语义与 fully-masked row 行为。
  • 用一个朴素 reference implementation 对 fused/optimized kernel 做数值 parity。
  • 性能分析同时报告 FLOPs、HBM bytes、kernel launch 与是否 materialize $T^2$ 中间量。

coding 检查表

  • 先写 shape/assertion 和行为不变量，再写优化代码。
  • 使用参数化测试覆盖 $B=1,T=1,H=1$、非方形 $T_q e T_k$、padding、GQA 和 dtype。
  • reference 路径优先清晰正确，optimized 路径必须对 oracle 做 parity。
  • profiler 中区分真正 kernel 时间与隐式 .contiguous() / copy / allocation。

15. 推荐验证协议

  1. Parameterized unit tests：覆盖不同 B/T/H/dtype/mask。
  2. Behavioural test：测试未来泄漏、padding invariance、cache reset 等语义。
  3. Oracle comparison：优化代码与朴素 reference 比较输出和梯度。

验证结果建议至少记录：

类型 最低要求
Correctness reference parity / invariant / leakage test 至少一项
Numerical NaN/Inf、max/RMS、dtype 差异
Performance wall-clock、显存/bytes、P95/P99（系统题）
Quality loss/perplexity/任务指标；结构改动必须做回归

16. 面试官真正想听到的“边界条件”

  • 不要把渐进复杂度等同于实际速度：kernel、batch、长度、硬件与 IO 会改变主导项。
  • 不要把一种实现当成数学定义：mask 语义、layout、fused kernel、cache allocator 都可能变化。
  • 不要把单点 benchmark 当成普遍规律：至少说明 $B,T,d,H$、dtype、device 和任务分布。
  • 不要把“能运行”当成“正确”：Transformer 很多 bug 会正常降 loss，但存在未来泄漏、错误广播或 cache position 错位。

17. Whiteboard / Coding 表达模板

当面试官要求现场推导或编码，可按以下顺序：

  1. 写输入输出 shape 与符号定义；
  2. 写最小核心公式，不先写优化；
  3. 写 2–3 个 invariants/assertions；
  4. 给 reference 实现或手算小例子；
  5. 再讨论 fused kernel、cache、并行或量化；
  6. 最后给测试与 benchmark 设计。

Strong Hire 信号：不仅能解释“为什么”，还能说出“什么情况下不成立，以及我会怎么证明”。
