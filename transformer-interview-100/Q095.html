Q095 Coding：如何验证 KV Cache 实现正确？

章节：9. Coding / Debug / System Design
难度：4/5 · 频率：高频 · 形式：概念 / 推导 / 追问
内容分层：PDF Core 来自原 PDF 的观点重排；Professional Expansion 为在不改变 PDF 主结论基础上的原创扩展。

1. 面试官在考什么 — PDF Core

最关键是 full forward 与 incremental forward 的等价性。

2. 30 秒回答 — PDF Core

对同一输入，路径 A 一次性 full forward 得到各位置 logits；路径 B 逐 token 使用 cache。对应位置 logits 应在浮点 容差内一致。随后扩展测试 batch、padding、GQA、RoPE offset、cache reset。

3. 核心公式 / Shape

$logits_{full}\approx logits_{incremental}$。

4. 深度拆解 — PDF Core

  • FP16 fused kernel 可能有小数值差异，应使用合理 tolerance。
  • 最常见错误不是 K/V concat，而是 position/RoPE offset。
  • 必须测试 cache truncate/reorder 场景。 代码 / 伪代码骨架 full = model(ids, use_cache=False).logits past = None parts = [] for t in range(ids.size(1)): out = model(ids[:, t:t+1], past_key_values=past, use_cache=True) parts.append(out.logits) past = out.past_key_values inc = torch.cat(parts, dim=1) torch.testing.assert_close(full, inc, rtol=1e-3, atol=1e-3)

5. Professional Expansion：为什么这题值得深挖

Cache correctness 用 full forward vs incremental decode logits parity；再覆盖 batch、GQA、RoPE、padding、cache reset/reorder。

5.1 工程实现 / 系统视角

比较每一步最后 token logits。

5.2 边界条件与反例

只比较最终生成文本可能漏掉小误差。

5.3 建议亲手做的验证实验

  • 设置 atol/rtol 并定位首个偏离 step。
  • 记录至少一种 correctness metric 与一种 performance metric；不要只凭“代码能运行”判定实现正确。

5.4 3 分钟专业版答法

面试时可以按下面节奏展开：

第一句给结论：对同一输入，路径 A 一次性 full forward 得到各位置 logits；路径 B 逐 token 使用 cache。对应位置 logits 应在浮点 容差内一致。随后扩展测试 batch、padding、GQA、RoPE offset、cache reset。
第二层讲机制：FP16 fused kernel 可能有小数值差异，应使用合理 tolerance。；最常见错误不是 K/V concat，而是 position/RoPE offset。；必须测试 cache truncate/reorder 场景。 代码 / 伪代码骨架 full = model(ids, use_cache=False).logits past = None parts = [] for t in range(ids.size(1)): out = model(ids[:, t:t+1], past_key_values=past, use_cache=True) parts.append(out.logits) past = out.past_key_values inc = torch.cat(parts, dim=1) torch.testing.assert_close(full, inc, rtol=1e-3, atol=1e-3)
第三层补工程条件：把本题放到真实 Tensor Shape、训练/推理阶段与硬件约束下重新检查；如果结论涉及“更快/更省/更稳定”，必须说明比较基线和适用条件。
最后主动给验证：用最小行为测试、数值 parity、profiler 或 ablation 证明，而不是停留在直觉。

5.5 复杂度与资源矩阵

维度 本题应如何分析
Correctness 先定义 shape/mask/finite/parity 等不变量，再写实现。
复杂度 避免隐藏的 torch.cat、contiguous copy、重复 materialization。
测试 优先行为级测试：future leakage、full-vs-cache、tiny overfit。
可维护性 开发态 fail-fast assertions；生产态转化为静态约束或 kernel contract。
主要验证 pytest 参数化 B/T/H/GQA/padding/dtype/device 边界。

5.6 本题关键不变量

  • 先失败于错误不变量，而不是让错误广播到后续层。
  • 单元测试覆盖 B=1、T=1、H=1、padding/GQA 等边界。
  • 优化版本必须与 reference/oracle 做 parity。

6. Reference Implementation / Test Skeleton

@torch.no_grad()
def assert_cache_parity(model, ids):
    full = model(ids, use_cache=False).logits
    past = None
    steps = []
    for t in range(ids.size(1)):
        out = model(ids[:, t:t+1], past_key_values=past, use_cache=True)
        past = out.past_key_values
        steps.append(out.logits[:, -1:])
    inc = torch.cat(steps, dim=1)
    torch.testing.assert_close(full, inc, atol=1e-4, rtol=1e-4)

13. 深入推导：把结论变成可验证的模型

KV cache parity 测试：对同一序列，一次 full forward 获取每个位置 logits；再逐 token incremental forward，拼接每步 logits，两者应在容忍误差内一致。

测试矩阵必须覆盖 T=1、batch>1、不同长度、left/right padding、GQA、RoPE、cache reset/reorder 和不同 dtype。只测单样本短序列很容易漏 bug。

13.1 本章心智模型

把知识转成可验证代码：先不变量与 reference，再优化；System Design 必须有容量和回归闭环。

这意味着面试时不要停在术语层。每个结论至少回答四个问题：成立所需假设是什么？张量/概率对象是什么？成本落在哪里？怎样设计反例或单测证伪？

14. 题目特异的工程 Checklist

inference 检查表

  • 分开 prefill 与 decode：前者偏大 GEMM，后者偏 KV bandwidth/调度。
  • 指标至少报告 TTFT、TPOT/ITL、throughput 与 P95/P99。
  • 容量估算从权重、KV、workspace、allocator overhead 四部分扣显存。
  • full-forward 与 incremental/cache 路径必须做 logits parity。

coding 检查表

  • 先写 shape/assertion 和行为不变量，再写优化代码。
  • 使用参数化测试覆盖 $B=1,T=1,H=1$、非方形 $T_q e T_k$、padding、GQA 和 dtype。
  • reference 路径优先清晰正确，optimized 路径必须对 oracle 做 parity。
  • profiler 中区分真正 kernel 时间与隐式 .contiguous() / copy / allocation。

15. 推荐验证协议

  1. Parameterized unit tests：覆盖不同 B/T/H/dtype/mask。
  2. Behavioural test：测试未来泄漏、padding invariance、cache reset 等语义。
  3. Oracle comparison：优化代码与朴素 reference 比较输出和梯度。

验证结果建议至少记录：

类型 最低要求
Correctness reference parity / invariant / leakage test 至少一项
Numerical NaN/Inf、max/RMS、dtype 差异
Performance wall-clock、显存/bytes、P95/P99（系统题）
Quality loss/perplexity/任务指标；结构改动必须做回归

16. 面试官真正想听到的“边界条件”

  • 不要把渐进复杂度等同于实际速度：kernel、batch、长度、硬件与 IO 会改变主导项。
  • 不要把一种实现当成数学定义：mask 语义、layout、fused kernel、cache allocator 都可能变化。
  • 不要把单点 benchmark 当成普遍规律：至少说明 $B,T,d,H$、dtype、device 和任务分布。
  • 不要把“能运行”当成“正确”：Transformer 很多 bug 会正常降 loss，但存在未来泄漏、错误广播或 cache position 错位。

17. Whiteboard / Coding 表达模板

当面试官要求现场推导或编码，可按以下顺序：

  1. 写输入输出 shape 与符号定义；
  2. 写最小核心公式，不先写优化；
  3. 写 2–3 个 invariants/assertions；
  4. 给 reference 实现或手算小例子；
  5. 再讨论 fused kernel、cache、并行或量化；
  6. 最后给测试与 benchmark 设计。

Strong Hire 信号：不仅能解释“为什么”，还能说出“什么情况下不成立，以及我会怎么证明”。
