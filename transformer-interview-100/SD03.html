SD03 估算一个 LLM 服务能承载多少并发

1. 先做“显存上限”，再做“延迟上限”

最大并发不是单一显存公式。真实并发：

[ C_{real}=\min(C_{memory}, C_{latency}, C_{scheduler}, C_{throughput}) ]

2. 显存账本

GPU 可用显存减去：

  1. 模型权重；
  2. runtime / NCCL / CUDA context；
  3. kernel workspace / CUDA graph；
  4. KV cache pool；
  5. adapter / logits / sampling buffer；
  6. safety margin。

KV 主项

单请求：

[ M_{req}=2LT H_{kv}D_hs ]

若长度动态，必须使用请求的“当前 token 数”或容量规划分位数。

示例

32 层、8 KV heads、head dim 128、BF16、32K tokens：

[ M_{req}\approx 4.0\ GiB ]

这说明 32K 并发服务的核心压力可能不是参数，而是 KV。

3. GQA/MQA 的容量影响

若从 $H_q=32$ 的 MHA 改成 $H_{kv}=8$ 的 GQA，K/V 主项约降至 1/4。若 MQA $H_{kv}=1$，进一步下降。

但不要只用 cache 公式判断模型质量，需要训练/微调验证。

4. Length Distribution

平均长度几乎从来不够：

  • P50 prompt 可能 800；
  • P95 8K；
  • P99 32K。

少数长请求会占据大量 KV blocks 并拖高 decode iteration 时间。

建议按 token buckets 做 admission / quotas。

5. 延迟约束

即使显存还能放更多 request，batch 增大后每个 decode iteration 变慢，TPOT 可能超过 SLA。因此通过 sweep 得到：

concurrency → TTFT / TPOT / tokens/s / KV occupancy

真实容量取 SLA 边界点，不取 OOM 点。

6. Prefix Sharing

若大量请求共享 system prompt，可共享 prefix KV，从而降低重复 cache。但容量模型要考虑：

  • prefix cache hit rate；
  • unique suffix；
  • eviction；
  • tenant isolation。

7. Beam / Best-of-N

生成多个候选常近似乘大 decoder state/KV 成本；若底层实现支持共享 prefix blocks，可降低初期复制，但分叉后仍增长。

8. 容量规划表

输入 必填
Model L, Hq, Hkv, Dh, dtype
Hardware GPU count, memory, interconnect
Traffic QPS, prompt/output P50/P95/P99
SLA TTFT/TPOT/P99
Runtime block size, max batched tokens
Features prefix cache, LoRA, speculative

9. 线上保护

  • hard max context；
  • per-tenant token quota；
  • admission control；
  • queue timeout；
  • KV occupancy high-watermark；
  • graceful shedding。

10. 面试官加压

“80GB H100 可以放多少个请求？”

不能直接回答一个数字。先扣权重/runtime，再代入模型 KV 公式和长度分布，最后用 P99 latency benchmark 校正。
