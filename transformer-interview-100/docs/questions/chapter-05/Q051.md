# Q051 · 为什么 Decoder-only 成为通用 LLM 主流之一？

> **章节**：5. BERT、GPT 与 Encoder-Decoder  
> **难度**：3/5 · **频率**：高频 · **形式**：概念 / 推导 / 追问  
> **内容分层**：`PDF Core` 来自原 PDF 的观点重排；`Professional Expansion` 为在不改变 PDF 主结论基础上的原创扩展。

## 1. 面试官在考什么 — PDF Core

从目标统一、数据接口与 scaling 解释。

## 2. 30 秒回答 — PDF Core

> Decoder-only 用一个 next-token objective 就能把文档、对话、代码、工具轨迹等统一为 token stream；结构简 单、scaling 与 serving 统一、in-context learning 自然。但这不意味着 Encoder 或 Encoder-Decoder 在所有任务 上都落后。

## 3. 核心公式 / Shape

统一 token stream + next-token objective 是 decoder-only 的主要接口优势。

## 4. 深度拆解 — PDF Core

- 统一接口降低多任务架构复杂度。
- prompt 和 answer 同一上下文中自然条件化。
- retrieval encoder、翻译/语音等场景仍可能更适合其他范式。

## 5. Professional Expansion：为什么这题值得深挖

Decoder-only 用统一 token stream 和 next-token objective 覆盖 instruction、few-shot、tool traces 等多种任务，训练/推理接口简单且易 scaling。

### 5.1 工程实现 / 系统视角

讨论任务特性、参数共享、serving 统一性与限制。

### 5.2 边界条件与反例

主流不等于理论上压倒 encoder-decoder。

### 5.3 建议亲手做的验证实验

- 对翻译/embedding 任务分析 decoder-only 的额外成本。
- 记录至少一种 **correctness metric** 与一种 **performance metric**；不要只凭“代码能运行”判定实现正确。

### 5.4 3 分钟专业版答法

面试时可以按下面节奏展开：

> **第一句给结论**：Decoder-only 用一个 next-token objective 就能把文档、对话、代码、工具轨迹等统一为 token stream；结构简 单、scaling 与 serving 统一、in-context learning 自然。但这不意味着 Encoder 或 Encoder-Decoder 在所有任务 上都落后。  
> **第二层讲机制**：统一接口降低多任务架构复杂度。；prompt 和 answer 同一上下文中自然条件化。；retrieval encoder、翻译/语音等场景仍可能更适合其他范式。  
> **第三层补工程条件**：把本题放到真实 Tensor Shape、训练/推理阶段与硬件约束下重新检查；如果结论涉及“更快/更省/更稳定”，必须说明比较基线和适用条件。  
> **最后主动给验证**：用最小行为测试、数值 parity、profiler 或 ablation 证明，而不是停留在直觉。

### 5.5 复杂度与资源矩阵

| 维度 | 本题应如何分析 |
|---|---|
| 监督密度 | MLM 只在 mask 位计主要监督；CLM 通常几乎每个有效 token 都贡献 next-token loss。 |
| Mask | 双向/causal 可见性决定信息流，不要只从“模型名字”判断。 |
| 训练-推理差异 | Teacher Forcing 与 autoregressive rollout 的条件分布不同。 |
| 任务匹配 | 分类/检索/生成/seq2seq 的接口和延迟要求会影响架构选择。 |
| 主要验证 | label alignment、mask 可见性、下游任务与生成行为。 |

### 5.6 本题关键不变量

- 当前预测位置不能直接看到其监督目标。
- padding/无效 token 不应污染 attention 或 loss。
- 训练目标与推理方式的差异必须显式说明。

## 6. 面试中的推导顺序

1. **先定义**：一句话说明对象是什么、输入输出是什么。
2. **再公式**：写最小核心公式，并标出关键维度。
3. **解释 Why**：它解决前一代方案的什么瓶颈。
4. **算成本**：参数、FLOPs、activation/KV memory、IO/通信分别看。
5. **讲 Gotcha**：至少指出一个数值或实现陷阱。
6. **收束 Trade-off**：明确什么条件下它不一定更优。

## 7. 常见失分点 — PDF Core

- 把主流归因成“Decoder 参数更多”。

## 8. 面试官继续追问 — PDF Core

> 在固定总参数下，Encoder-Decoder 与 Decoder-only 的算力分配有什么不同？

### 扩展追问树

- 如果把关键超参数扩大 4 倍，**参数量 / FLOPs / 显存 / latency** 哪一项最先成为瓶颈？

- 如何写一个最小单元测试或 ablation，证明你的解释而不是只靠直觉？

## 9. 一语中的 — PDF Core

**Decoder-only 用一个 next-token objective 就能把文档、对话、代码、工具轨迹等统一为 token stream；结构简单、 scaling 与 serving 统一、in-context learning 自然。**

## 13. 深入推导：把结论变成可验证的模型

Decoder-only 的优势是统一接口：预训练、指令、few-shot、工具描述和输出都可序列化到一个 causal token stream。规模化训练与 serving 也只维护一种主架构。

但“主流”不代表所有任务都最优。高吞吐 embedding/retrieval 可能更适合 encoder；固定 source 的大量 target decode 可利用 encoder-decoder 的 source encoding 复用。

### 13.1 本章心智模型

> 从 attention 可见性与概率分解理解 BERT/GPT/encoder-decoder，而不是只背模型名。

这意味着面试时不要停在术语层。每个结论至少回答四个问题：**成立所需假设是什么？张量/概率对象是什么？成本落在哪里？怎样设计反例或单测证伪？**

## 14. 题目特异的工程 Checklist

**inference 检查表**

- 分开 prefill 与 decode：前者偏大 GEMM，后者偏 KV bandwidth/调度。
- 指标至少报告 TTFT、TPOT/ITL、throughput 与 P95/P99。
- 容量估算从权重、KV、workspace、allocator overhead 四部分扣显存。
- full-forward 与 incremental/cache 路径必须做 logits parity。

## 15. 推荐验证协议

1. **Full-vs-cache parity**：逐 token logits 与 full forward 相同。
2. **Length sweep**：从短到长记录 TTFT/TPOT/KV bytes，验证复杂度趋势。
3. **Concurrency sweep**：增加并发直到 P99/SLA 或显存首先触顶，得到真实容量曲线。

验证结果建议至少记录：

| 类型 | 最低要求 |
|---|---|
| Correctness | reference parity / invariant / leakage test 至少一项 |
| Numerical | NaN/Inf、max/RMS、dtype 差异 |
| Performance | wall-clock、显存/bytes、P95/P99（系统题） |
| Quality | loss/perplexity/任务指标；结构改动必须做回归 |

## 16. 面试官真正想听到的“边界条件”

- **不要把渐进复杂度等同于实际速度**：kernel、batch、长度、硬件与 IO 会改变主导项。
- **不要把一种实现当成数学定义**：mask 语义、layout、fused kernel、cache allocator 都可能变化。
- **不要把单点 benchmark 当成普遍规律**：至少说明 $B,T,d,H$、dtype、device 和任务分布。
- **不要把“能运行”当成“正确”**：Transformer 很多 bug 会正常降 loss，但存在未来泄漏、错误广播或 cache position 错位。

## 17. Whiteboard / Coding 表达模板

当面试官要求现场推导或编码，可按以下顺序：

1. 写输入输出 shape 与符号定义；
2. 写最小核心公式，不先写优化；
3. 写 2–3 个 invariants/assertions；
4. 给 reference 实现或手算小例子；
5. 再讨论 fused kernel、cache、并行或量化；
6. 最后给测试与 benchmark 设计。

> **Strong Hire 信号**：不仅能解释“为什么”，还能说出“什么情况下不成立，以及我会怎么证明”。
