# Q064 · Transformer 初始化不合理有哪些症状？

> **章节**：6. 训练、优化与分布式  
> **难度**：4/5 · **频率**：高频 · **形式**：概念 / 推导 / 追问  
> **内容分层**：`PDF Core` 来自原 PDF 的观点重排；`Professional Expansion` 为在不改变 PDF 主结论基础上的原创扩展。

## 1. 面试官在考什么 — PDF Core

从训练曲线与统计量反推初始化问题。

## 2. 30 秒回答 — PDF Core

> 可能出现 activation std 随层爆炸/衰减、attention logits 极端、前几步 loss 抖动、gradient norm 异常、深层几乎 不学习等。排查应查看按层 activation/gradient statistics。

## 3. 核心公式 / Shape

关注 layerwise $RMS(x_l)$、$\|g_l\|$、update/weight ratio。

## 4. 深度拆解 — PDF Core

- 不要只观察总 loss。
- Norm 能缓解但不能消除所有尺度问题。
- 深度、residual scale、LR 与初始化相互作用。

## 5. Professional Expansion：为什么这题值得深挖

错误初始化会表现为 activation/gradient 随层爆炸或衰减、attention logits 异常、早期 loss 不降；诊断应看 layerwise statistics。

### 5.1 工程实现 / 系统视角

检查 fan-in、residual scaling、embedding/output scale。

### 5.2 边界条件与反例

仅看全局 grad norm 会掩盖局部层异常。

### 5.3 建议亲手做的验证实验

- 导出每层 RMS heatmap。
- 记录至少一种 **correctness metric** 与一种 **performance metric**；不要只凭“代码能运行”判定实现正确。

### 5.4 3 分钟专业版答法

面试时可以按下面节奏展开：

> **第一句给结论**：可能出现 activation std 随层爆炸/衰减、attention logits 极端、前几步 loss 抖动、gradient norm 异常、深层几乎 不学习等。排查应查看按层 activation/gradient statistics。  
> **第二层讲机制**：不要只观察总 loss。；Norm 能缓解但不能消除所有尺度问题。；深度、residual scale、LR 与初始化相互作用。  
> **第三层补工程条件**：把本题放到真实 Tensor Shape、训练/推理阶段与硬件约束下重新检查；如果结论涉及“更快/更省/更稳定”，必须说明比较基线和适用条件。  
> **最后主动给验证**：用最小行为测试、数值 parity、profiler 或 ablation 证明，而不是停留在直觉。

### 5.5 复杂度与资源矩阵

| 维度 | 本题应如何分析 |
|---|---|
| 显存 | 权重、梯度、optimizer state、activation 四类必须分开估算。 |
| 数值 | FP16/BF16、loss scaling、grad clipping、NaN 定位都要看 first non-finite。 |
| 步数语义 | gradient accumulation 后 scheduler/clip/optimizer 应按 optimizer-step 定义。 |
| 通信 | DP/TP/PP/CP 的收益受网络拓扑与 collective 开销约束。 |
| 主要验证 | 固定 batch 参数 delta、layerwise grad、throughput/MFU、恢复一致性。 |

### 5.6 本题关键不变量

- 任何 NaN 都先找 first non-finite，而不是先调参。
- optimizer/scheduler/clip 的 step 语义必须与 accumulation 一致。
- 多 GPU 方案要同时满足显存约束和通信可承受。

## 6. 面试中的推导顺序

1. **先定义**：一句话说明对象是什么、输入输出是什么。
2. **再公式**：写最小核心公式，并标出关键维度。
3. **解释 Why**：它解决前一代方案的什么瓶颈。
4. **算成本**：参数、FLOPs、activation/KV memory、IO/通信分别看。
5. **讲 Gotcha**：至少指出一个数值或实现陷阱。
6. **收束 Trade-off**：明确什么条件下它不一定更优。

## 7. 常见失分点 — PDF Core

- 认为“loss 能下降就说明初始化没问题”。

## 8. 面试官继续追问 — PDF Core

> 如何用 1 个 forward 的 layer-wise std 曲线判断潜在尺度异常？

### 扩展追问树

- 如果把关键超参数扩大 4 倍，**参数量 / FLOPs / 显存 / latency** 哪一项最先成为瓶颈？
- 如果在 **训练** 与 **增量推理** 两个阶段分别使用，本题结论有哪些不同？
- 如何写一个最小单元测试或 ablation，证明你的解释而不是只靠直觉？

## 9. 一语中的 — PDF Core

## 13. 深入推导：把结论变成可验证的模型

不良初始化的典型症状有初始 loss 异常、activation std 随深度爆炸/衰减、attention entropy 极端、gradient norm 层间失衡、训练前几百步频繁 overflow。

诊断时画 layer-wise activation RMS、gradient RMS 与 residual branch/output ratio，比只看全局 loss 更敏感。初始化问题常与 Norm placement 和 LR 共同出现。

### 13.1 本章心智模型

> 建立训练故障树：objective、loss mask、数值精度、optimizer、并行和 scaling。

这意味着面试时不要停在术语层。每个结论至少回答四个问题：**成立所需假设是什么？张量/概率对象是什么？成本落在哪里？怎样设计反例或单测证伪？**

## 14. 题目特异的工程 Checklist

**training 检查表**

- 每次异常先定位首个非有限 activation/gradient，再调整超参数。
- 记录 optimizer step、effective batch、LR schedule 与 gradient norm。
- 分布式场景确认全局 norm、参数 shard 和 collective 语义。
- 做 tiny-overfit + fixed-seed 单卡基线，作为大规模训练的 correctness oracle。

## 15. 推荐验证协议

1. **Tiny overfit**：极小数据在单卡 FP32 下应稳定降到很低 loss。
2. **Finite hooks**：每层 forward/backward hook 捕获首个 NaN/Inf。
3. **Scale sweep**：对 LR、batch、dtype 做小网格，验证异常是否与某个数值条件相关。

验证结果建议至少记录：

| 类型 | 最低要求 |
|---|---|
| Correctness | reference parity / invariant / leakage test 至少一项 |
| Numerical | NaN/Inf、max/RMS、dtype 差异 |
| Performance | wall-clock、显存/bytes、P95/P99（系统题） |
| Quality | loss/perplexity/任务指标；结构改动必须做回归 |

## 16. 面试官真正想听到的“边界条件”

- **不要把渐进复杂度等同于实际速度**：kernel、batch、长度、硬件与 IO 会改变主导项。
- **不要把一种实现当成数学定义**：mask 语义、layout、fused kernel、cache allocator 都可能变化。
- **不要把单点 benchmark 当成普遍规律**：至少说明 $B,T,d,H$、dtype、device 和任务分布。
- **不要把“能运行”当成“正确”**：Transformer 很多 bug 会正常降 loss，但存在未来泄漏、错误广播或 cache position 错位。

## 17. Whiteboard / Coding 表达模板

当面试官要求现场推导或编码，可按以下顺序：

1. 写输入输出 shape 与符号定义；
2. 写最小核心公式，不先写优化；
3. 写 2–3 个 invariants/assertions；
4. 给 reference 实现或手算小例子；
5. 再讨论 fused kernel、cache、并行或量化；
6. 最后给测试与 benchmark 设计。

> **Strong Hire 信号**：不仅能解释“为什么”，还能说出“什么情况下不成立，以及我会怎么证明”。
