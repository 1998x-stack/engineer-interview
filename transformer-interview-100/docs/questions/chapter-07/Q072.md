# Q072 · MHA、MQA、GQA 的区别？

> **章节**：7. 自回归推理与 KV Cache  
> **难度**：3/5 · **频率**：高频 · **形式**：概念 / 推导 / 追问  
> **内容分层**：`PDF Core` 来自原 PDF 的观点重排；`Professional Expansion` 为在不改变 PDF 主结论基础上的原创扩展。

## 1. 面试官在考什么 — PDF Core

直接连接模型质量与 KV Cache 内存。

## 2. 30 秒回答 — PDF Core

> MHA 每个 Q head 有独立 K/V head；MQA 所有 Q heads 共享一套 K/V；GQA 让一组 Q heads 共享一个 KV head，是 质量与推理效率的折中。 H_kv: MHA=H_q, GQA<H_q, MQA=1

## 3. 核心公式 / Shape

MHA: $H_{kv}=H_q$；MQA: $H_{kv}=1$；GQA: $1<H_{kv}<H_q$。

## 4. 深度拆解 — PDF Core

- H_kv 从 H_q 降低会线性缩小 KV cache 的 head 维度部分。
- MQA 极端 H_kv=1。
- GQA 通常按 group 复制/映射 KV 到多个 Q heads。

## 5. Professional Expansion：为什么这题值得深挖

MHA 每个 Q head 对应独立 K/V；MQA 所有 Q 共享一套 K/V；GQA 在两者之间按 group 共享，主要降低 KV memory/bandwidth。

### 5.1 工程实现 / 系统视角

显式写 H_q/H_kv 与 repeat/group 语义。

### 5.2 边界条件与反例

GQA 的收益不只参数，而更重要是 serving KV。

### 5.3 建议亲手做的验证实验

- 算 Hq=32,Hkv=8 的 cache 压缩倍数。
- 记录至少一种 **correctness metric** 与一种 **performance metric**；不要只凭“代码能运行”判定实现正确。

### 5.4 3 分钟专业版答法

面试时可以按下面节奏展开：

> **第一句给结论**：MHA 每个 Q head 有独立 K/V head；MQA 所有 Q heads 共享一套 K/V；GQA 让一组 Q heads 共享一个 KV head，是 质量与推理效率的折中。 H_kv: MHA=H_q, GQA<H_q, MQA=1  
> **第二层讲机制**：H_kv 从 H_q 降低会线性缩小 KV cache 的 head 维度部分。；MQA 极端 H_kv=1。；GQA 通常按 group 复制/映射 KV 到多个 Q heads。  
> **第三层补工程条件**：把本题放到真实 Tensor Shape、训练/推理阶段与硬件约束下重新检查；如果结论涉及“更快/更省/更稳定”，必须说明比较基线和适用条件。  
> **最后主动给验证**：用最小行为测试、数值 parity、profiler 或 ablation 证明，而不是停留在直觉。

### 5.5 复杂度与资源矩阵

| 维度 | 本题应如何分析 |
|---|---|
| KV Memory | $M_{KV}=2LBTH_{kv}D_h\cdot bytes$；按请求长度分布与 beam/prefix sharing 修正。 |
| Prefill | 大矩阵计算，关注 TTFT、FlashAttention、chunking。 |
| Decode | 常受 KV 读取、memory bandwidth、batch scheduler 限制。 |
| 并发 | continuous batching/paged KV 改变 capacity 与 fragmentation。 |
| 主要验证 | TTFT/TPOT/P99、tokens/s、KV occupancy、full-vs-incremental parity。 |

### 5.6 本题关键不变量

- full forward 与 cache 路径在相同条件下应数值等价。
- KV cache 的 position/layout/reorder 必须随 batch 生命周期正确更新。
- 性能要同时看 TTFT、TPOT 与尾延迟，不能只看总 tokens/s。

## 6. 面试中的推导顺序

1. **先定义**：一句话说明对象是什么、输入输出是什么。
2. **再公式**：写最小核心公式，并标出关键维度。
3. **解释 Why**：它解决前一代方案的什么瓶颈。
4. **算成本**：参数、FLOPs、activation/KV memory、IO/通信分别看。
5. **讲 Gotcha**：至少指出一个数值或实现陷阱。
6. **收束 Trade-off**：明确什么条件下它不一定更优。

## 13. 深入推导：把结论变成可验证的模型

MHA 每个 Q head 对应独立 K/V head；MQA 所有 Q heads 共享一组 K/V；GQA 介于两者之间。KV cache 和 K/V projection 成本大致按 $H_{kv}$ 缩放，因此 MQA 节省最大。

质量 trade-off 来自 K/V 表示瓶颈：过度共享可能限制不同 query heads 的 memory representation。GQA 用少量 KV groups 通常在质量与 serving 效率间折中。

### 13.1 本章心智模型

> 从增量计算与内存生命周期理解 KV cache、serving scheduler、paged memory 和 decode 加速。

这意味着面试时不要停在术语层。每个结论至少回答四个问题：**成立所需假设是什么？张量/概率对象是什么？成本落在哪里？怎样设计反例或单测证伪？**

## 14. 题目特异的工程 Checklist

**inference 检查表**

- 分开 prefill 与 decode：前者偏大 GEMM，后者偏 KV bandwidth/调度。
- 指标至少报告 TTFT、TPOT/ITL、throughput 与 P95/P99。
- 容量估算从权重、KV、workspace、allocator overhead 四部分扣显存。
- full-forward 与 incremental/cache 路径必须做 logits parity。

## 15. 推荐验证协议

1. **Full-vs-cache parity**：逐 token logits 与 full forward 相同。
2. **Length sweep**：从短到长记录 TTFT/TPOT/KV bytes，验证复杂度趋势。
3. **Concurrency sweep**：增加并发直到 P99/SLA 或显存首先触顶，得到真实容量曲线。

验证结果建议至少记录：

| 类型 | 最低要求 |
|---|---|
| Correctness | reference parity / invariant / leakage test 至少一项 |
| Numerical | NaN/Inf、max/RMS、dtype 差异 |
| Performance | wall-clock、显存/bytes、P95/P99（系统题） |
| Quality | loss/perplexity/任务指标；结构改动必须做回归 |

## 16. 面试官真正想听到的“边界条件”

- **不要把渐进复杂度等同于实际速度**：kernel、batch、长度、硬件与 IO 会改变主导项。
- **不要把一种实现当成数学定义**：mask 语义、layout、fused kernel、cache allocator 都可能变化。
- **不要把单点 benchmark 当成普遍规律**：至少说明 $B,T,d,H$、dtype、device 和任务分布。
- **不要把“能运行”当成“正确”**：Transformer 很多 bug 会正常降 loss，但存在未来泄漏、错误广播或 cache position 错位。

## 17. Whiteboard / Coding 表达模板

当面试官要求现场推导或编码，可按以下顺序：

1. 写输入输出 shape 与符号定义；
2. 写最小核心公式，不先写优化；
3. 写 2–3 个 invariants/assertions；
4. 给 reference 实现或手算小例子；
5. 再讨论 fused kernel、cache、并行或量化；
6. 最后给测试与 benchmark 设计。

> **Strong Hire 信号**：不仅能解释“为什么”，还能说出“什么情况下不成立，以及我会怎么证明”。
