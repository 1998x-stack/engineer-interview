# Q092 · Coding：给 Transformer 加 KV Cache

> **章节**：9. Coding / Debug / System Design

> **内容分层**：`PDF Core` 来自原 PDF 的观点重排；`Professional Expansion` 为在不改变 PDF 主结论基础上的原创扩展。

## 1. 面试官在考什么 — PDF Core

考察对增量 Attention 的数据结构理解。

## 2. 30 秒回答 — PDF Core

> API 需要接收 past_k/past_v，对新 token 只投影 k_new/v_new，并把它们写入 cache；Q 只使用当前 token。生产 实现避免每步 torch.cat 复制历史，通常预分配或使用 block/paged cache。

## 3. 核心公式 / Shape

cache append 逻辑：写入 $K[:,:,t,:],V[:,:,t,:]$ 并更新 current_len。

## 4. 深度拆解 — PDF Core

- cache shape 常为 [B,H_kv,T,D_h]。
- position ids 从 past length 继续。
- batch 中不同 sequence length 需配合 cache slot/metadata。
- beam reordering 会重排 cache。 代码 / 伪代码骨架 def step(x_new, past_k, past_v): q = q_proj(x_new) k_new = k_proj(x_new) v_new = v_proj(x_new) # teaching version; production should avoid repeated full concat k = torch.cat([past_k, k_new], dim=-2) v = torch.cat([past_v, v_new], dim=-2) y = attention(q, k, v) return y, (k, v)

## 5. Professional Expansion：为什么这题值得深挖

KV cache 的关键不是 cat 出正确结果，而是增量 position、layout、预分配与 batch reorder；生产实现追求 O(1) append metadata/写入。

### 5.1 工程实现 / 系统视角

实现接口返回 present_kv，并验证 RoPE offset。

### 5.2 边界条件与反例

每步 torch.cat 会导致反复复制。

### 5.3 建议亲手做的验证实验

- 实现 preallocated cache + current_len。
- 记录至少一种 **correctness metric** 与一种 **performance metric**；不要只凭“代码能运行”判定实现正确。

面试时可以按下面节奏展开：

### 5.5 复杂度与资源矩阵

| 维度 | 本题应如何分析 |

- 优化版本必须与 reference/oracle 做 parity。

## 6. Reference Implementation / Test Skeleton

```python
# 概念性预分配 KV cache；真实生产实现通常使用 paged/block allocator
class KVCache:
    def __init__(self, B, Hkv, max_t, Dh, device, dtype):
        self.k = torch.empty(B, Hkv, max_t, Dh, device=device, dtype=dtype)
        self.v = torch.empty_like(self.k)
        self.length = 0

    def append(self, k_new, v_new):
        t = k_new.size(-2)
        self.k[:, :, self.length:self.length+t] = k_new
        self.v[:, :, self.length:self.length+t] = v_new
        self.length += t
        return self.k[:, :, :self.length], self.v[:, :, :self.length]
```

## 13. 深入推导：把结论变成可验证的模型

KV cache 实现的正确 API 应显式携带 `past_key_value`、当前位置/position id 和 cache layout。朴素 `torch.cat` 每步复制历史 cache，复杂度和内存分配都很差；高性能实现预分配或用 paged blocks 原地写入。

RoPE/GQA 是 cache 最常见深层 bug：新 K 必须按绝对 decode position 旋转，K/V head layout 与 Q group mapping 必须一致。

### 13.1 本章心智模型

> 把知识转成可验证代码：先不变量与 reference，再优化；System Design 必须有容量和回归闭环。

这意味着面试时不要停在术语层。每个结论至少回答四个问题：**成立所需假设是什么？张量/概率对象是什么？成本落在哪里？怎样设计反例或单测证伪？**

## 14. 题目特异的工程 Checklist

**inference 检查表**

- 分开 prefill 与 decode：前者偏大 GEMM，后者偏 KV bandwidth/调度。
- 指标至少报告 TTFT、TPOT/ITL、throughput 与 P95/P99。
- 容量估算从权重、KV、workspace、allocator overhead 四部分扣显存。
- full-forward 与 incremental/cache 路径必须做 logits parity。

**coding 检查表**

- 先写 shape/assertion 和行为不变量，再写优化代码。
- 使用参数化测试覆盖 $B=1,T=1,H=1$、非方形 $T_q
e T_k$、padding、GQA 和 dtype。
- reference 路径优先清晰正确，optimized 路径必须对 oracle 做 parity。
- profiler 中区分真正 kernel 时间与隐式 `.contiguous()` / copy / allocation。

## 15. 推荐验证协议

1. **Parameterized unit tests**：覆盖不同 B/T/H/dtype/mask。
2. **Behavioural test**：测试未来泄漏、padding invariance、cache reset 等语义。
3. **Oracle comparison**：优化代码与朴素 reference 比较输出和梯度。

验证结果建议至少记录：

| 类型 | 最低要求 |
|---|---|
| Correctness | reference parity / invariant / leakage test 至少一项 |
| Numerical | NaN/Inf、max/RMS、dtype 差异 |
| Performance | wall-clock、显存/bytes、P95/P99（系统题） |
| Quality | loss/perplexity/任务指标；结构改动必须做回归 |

## 16. 面试官真正想听到的“边界条件”

- **不要把渐进复杂度等同于实际速度**：kernel、batch、长度、硬件与 IO 会改变主导项。
- **不要把一种实现当成数学定义**：mask 语义、layout、fused kernel、cache allocator 都可能变化。
- **不要把单点 benchmark 当成普遍规律**：至少说明 $B,T,d,H$、dtype、device 和任务分布。
- **不要把“能运行”当成“正确”**：Transformer 很多 bug 会正常降 loss，但存在未来泄漏、错误广播或 cache position 错位。

## 17. Whiteboard / Coding 表达模板

当面试官要求现场推导或编码，可按以下顺序：

1. 写输入输出 shape 与符号定义；
2. 写最小核心公式，不先写优化；
3. 写 2–3 个 invariants/assertions；
4. 给 reference 实现或手算小例子；
5. 再讨论 fused kernel、cache、并行或量化；
6. 最后给测试与 benchmark 设计。

> **Strong Hire 信号**：不仅能解释“为什么”，还能说出“什么情况下不成立，以及我会怎么证明”。
