# SD02 · 设计高吞吐 LLM Serving

## 1. 需求定义

先把“高吞吐”约束成可测指标：

- 模型参数量 / dtype / TP size；
- prompt P50/P95/P99；
- output P50/P95/P99；
- TTFT SLA；
- TPOT/ITL SLA；
- requests/s 与 tokens/s；
- 最大并发与租户公平性。

吞吐和尾延迟通常冲突，因此必须给 SLA，而不是只追求 tokens/s。

## 2. 请求生命周期

```text
HTTP/gRPC
  ↓
Tokenizer
  ↓
Admission Control / Scheduler
  ↓
Prefill Queue ──→ Chunked Prefill
  ↓
KV Block Allocation
  ↓
Decode Iterations ← Continuous Batching
  ↓
Sampling / Stop Check
  ↓
Streaming Response
  ↓
KV Release
```

## 3. Prefill 与 Decode 分开优化

### Prefill

特点：长 Q/K，GEMM 大，算术强度高。

优化：

- FlashAttention/SDPA；
- prefix cache；
- chunked prefill；
- prompt batching；
- tokenizer pipeline 并行。

主要指标：TTFT。

### Decode

特点：每步 query length≈1，要读取完整历史 KV，常 memory-bandwidth bound。

优化：

- GQA/MQA；
- paged KV；
- continuous batching；
- KV quantization；
- speculative decoding；
- CUDA graphs / kernel fusion。

主要指标：TPOT/ITL。

## 4. KV Cache 容量

\[
M_{KV}=2LBTH_{kv}D_hs
\]

还要额外考虑：

- allocator block 尾部浪费；
- beam / best-of-N；
- prefix sharing；
- workspace；
- model weights；
- CUDA graph reserved memory。

生产 capacity planning 应使用真实请求长度分布，而不是平均长度。

## 5. Scheduler 设计

核心目标同时包括：

- GPU utilization；
- TTFT；
- TPOT；
- fairness；
- OOM avoidance。

策略例子：

- continuous batching；
- prefill/decode priority；
- chunked prefill；
- max batched tokens；
- preemption / swap / recompute；
- tenant quotas。

## 6. Paged KV / Prefix Cache

Paged KV 将逻辑 token 序列映射到物理 KV blocks，降低 contiguous preallocation 和 fragmentation。

Prefix cache 适合 system prompt、共享长前缀；必须考虑：

- cache key 包含模型/tokenizer/adapter/version；
- eviction policy；
- 多租户隔离；
- cache pollution。

## 7. 并行与硬件拓扑

- TP：高频 collective，优先同节点 NVLink/NVSwitch；
- PP：层间 activation 传输；
- DP replicas：横向扩 QPS；
- Expert Parallel：MoE all-to-all；
- disaggregated prefill/decode：在特定 workload 下分开资源池。

## 8. 量化

权重量化降低模型 memory / bandwidth；KV 量化降低长上下文并发成本。每种量化都必须有：

- quality regression；
- kernel support；
- latency benchmark；
- fallback path。

## 9. SLO 监控

必须按长度分桶：

| 指标 | 作用 |
|---|---|
| Queue Time | admission/scheduler 压力 |
| TTFT | prefill 体验 |
| TPOT/ITL | decode 流畅度 |
| P95/P99 | 尾延迟 |
| KV occupancy | 容量瓶颈 |
| active sequences | 实际并发 |
| preemption | scheduler 过载信号 |
| tokens/s | GPU 总吞吐 |

## 10. 故障与降级

- OOM 前 admission control；
- 超长 prompt 截断/异步队列；
- 降低 max output；
- speculative/offload 功能快速关闭；
- 模型 replica unhealthy 自动摘除；
- tokenizer/model revision 一致性检查。

## 11. 面试追问

**为什么 continuous batching 有效？** 不等最长 request，iteration 级回收和加入请求。

**为什么吞吐提高后 P99 可能恶化？** batch 更大和排队更久，会提高 GPU 利用但增加 queue/iteration latency。

**为什么 FlashAttention 不能单独解决 decode？** decode 的 query 很短，主要瓶颈常是 KV 读取和调度，而非完整 $T^2$ 中间矩阵。
