JWT 放 localStorage 还是 HttpOnly Cookie？

PDF 母版题解

1. 面试官在考什么

不是只考定义。 这道题通常同时观察你是否能：①识别安全边界；②解释根因；③知道常见错误做法为什么失效；④给出可落地、可验证的工程控制。

2. 原理与机制

不存在脱离威胁模型的绝对答案。localStorage 更暴露于 XSS 直接窃取；HttpOnly Cookie 降低直接读取风险但需要完整的 CSRF 防护。浏览器根据 cookie 的 Domain/Path/Secure/SameSite 等属性决定何时附带 Cookie；HttpOnly 主要限制脚本读取而不阻止浏览器自动发送。因此一个 Cookie 的安全性是“传输 + 脚本可见性 + 跨站发送 + 作用域”共同结果。认证问题要沿完整生命周期分析：credential enrollment → login → session/token issuance → refresh/rotation→ step-up → logout/revocation → recovery。单独讨论“登录接口”通常是不完整的。

抽象模型 Identity security = credential + session/token lifecycle + recovery + step-up + revocation.

3. 工程防御与设计原则

  • 使用成熟身份协议与库

  • 短生命周期凭据、轮换、撤销和重认证

  • 保护恢复链路与高风险操作

  • 记录异常认证事件但不记录秘密

  • 把控制写成可测试安全不变量，并为失败路径、边界条件和回归场景补充自动化测试。

4. 常见错误答案 / Gotchas

  • 误区：只讨论 token 格式，不讨论生命周期

  • 误区：把“已登录”当成“当前操作者可信”

  • 误区：忽略恢复、撤销、轮换和异常登录

5. 面试追问

  • token 被盗后如何缩小影响？

  • 权限改变后旧 token/session 如何处理？

  • 高风险操作如何做 step-up？

6. 一分钟回答模板

先给结论：不存在脱离威胁模型的绝对答案。localStorage 更暴露于 XSS 直接窃取；HttpOnly Cookie 降低直接读取风险但需要完整的 CSRF 防护。 然后我会从安全边界解释机制：浏览器根据 cookie 的Domain/Path/Secure/SameSite 等属性决定何时附带 Cookie；HttpOnly 主要限制脚本读取而不阻止浏览器自动发送。因此一个 Cookie 的安全性是“传输 + 脚本可见性 + 跨站发送 + 作用域”共同结果。 工程上不会只做单点补丁，而会落实为服务端/平台层控制、最小权限、异常路径和回归测试；最后再说明这个机制不能解决什么，以及如何通过日志、测试或代码审计验证控制确实生效。

GitHub 增强版：深度展开

不存在脱离威胁模型的唯一答案。localStorage 的主要问题是同源脚本可读，XSS 发生时令牌容易被直接窃取；HttpOnly Cookie 降低直接读取，但浏览器会自动携带，因此必须考虑 CSRF。

浏览器端存储方案还受到跨域架构、刷新令牌策略、前端第三方脚本、子域隔离和页面生命周期影响。

高安全 Web 应用常把长期凭据留在受保护 Cookie/后端会话，把前端可见令牌缩短生命周期并缩小 scope。

安全不变量（Security Invariants）

  • 高价值长期凭据应尽量避免暴露给普通页面脚本。
  • 自动携带凭据的方案必须有独立的请求意图/CSRF 防护。

代码审计 / 设计评审 / 测试视角

  • 列出所有 token 的存储位置、生命周期、scope、可读主体和发送机制。
  • 检查第三方 JS 是否能接触 localStorage；检查 Cookie 是否配置 Secure/HttpOnly/SameSite。
  • 验证刷新令牌轮换、登出、设备撤销和跨站请求保护。

新增 Gotchas

  • 把 Cookie 与 JWT 当成互斥概念。
  • 只比较 XSS，不考虑 CSRF 和 token replay。

新增高阶追问

  • BFF 模式如何改变浏览器 token 存储风险？
  • XSS 存在时 HttpOnly Cookie 仍能被如何滥用？

专业增强版 V2：从面试答案到 AppSec 工程

本节是在 PDF 母版和前述 GitHub 增强版基础上的第二轮扩展。重点不再是“记住漏洞名”，而是训练 Threat Modeling → Secure Design → Code Review → Verification → Operations 的完整闭环。

8.1 威胁建模：先定义资产、主体与边界

本题应放在 身份凭据、会话令牌、授权委托与敏感操作再认证的生命周期 中理解。与本题直接相关的核心资产包括：密码、会话标识、访问令牌、刷新令牌、授权码、MFA 状态。

推荐用下面的最小威胁模型回答：

Untrusted / Lower-trust Actor
        │
        │ input / identity / state transition
        ▼
Trust Boundary / Parser / Policy / Capability
        │
        │ security decision
        ▼
Protected Asset / Sensitive Action / Privileged Capability

典型失败模式是：把“令牌存在”误当成“令牌当前仍可信”，忽略签发、绑定、过期、撤销与重放。因此真正需要保护的不是某个字符串或某个 UI 控件，而是“跨边界之后系统仍然满足哪些安全属性”。

8.2 关键安全不变量：把最佳实践变成可测试规则

  • Invariant 1：高价值长期凭据应尽量避免暴露给普通页面脚本。
  • Invariant 2：自动携带凭据的方案必须有独立的请求意图/CSRF 防护。

高级面试回答要进一步说明：安全不变量应在最靠近关键资源/危险能力的位置再次成立。网关、WAF、前端或 SDK 可以提供前置保护，但不能成为唯一的最终安全边界。

8.3 失败链（Failure Chain）分析

入口数据/身份/状态
    ↓
规范化、解析或对象绑定
    ↓
安全检查缺失 / 检查位置错误 / 检查与执行语义不一致
    ↓
敏感资源、解释器、内部能力或业务状态被访问
    ↓
机密性 / 完整性 / 可用性 / 租户隔离 / 业务不变量受损

分析时建议逐项回答：

  1. Source 是什么：HTTP 参数、Cookie、Header、JWT claim、数据库旧值、消息、第三方 API，还是管理员配置？
  2. 中间发生了什么 Transform：decode、normalize、deserialize、ORM binding、proxy rewrite、cache keying、模板渲染？
  3. 谁做安全决策：浏览器、CDN、WAF、网关、Controller、Service、Policy Engine、数据库？
  4. 真正的 Sink/Asset 在哪：数据对象、系统能力、内部网络、文件系统、敏感业务动作还是跨租户资源？
  5. Decision 与 Execution 是否使用相同语义：这是很多高阶漏洞的共同根因。

8.4 代码审计：从关键词搜索升级为数据流与控制流审计

与本题相关的重点概念：token-storage、localstorage、httponly-cookie、xss、csrf。审计时不要只搜漏洞名称，而应建立下列视图：

Entry Point
  ├─ Authentication Context
  ├─ Authorization / Validation
  ├─ Normalization / Parsing
  ├─ Business State
  └─ Sensitive Sink / Capability

建议审计步骤：

  • 先找入口与调用图：HTTP handler、GraphQL resolver、WebSocket message handler、后台任务、Webhook、CLI/管理接口。
  • 再找安全上下文的来源：当前用户、tenant、role、scopes、session、trusted proxy、配置环境。
  • 检查控制是否集中且一致：是否存在“某些路由有 middleware、另一些内部入口没有”的分叉。
  • 检查 TOCTOU/异步边界：安全检查与真正执行之间是否跨事务、队列或服务。
  • 检查失败路径：超时、依赖不可用、解析失败、空值、部分成功时是否 fail secure。

8.5 架构设计：控制应该放在哪里

本章推荐的总体设计原则是：认证、会话、授权委托分层；短期令牌、长期凭据和高风险操作使用不同保护强度。

可以把控制拆成四层：

层级 目标 本题评审重点
Edge / Browser 降低明显恶意或错误流量 不能把它当最终授权/业务安全边界
Application / Policy 建立可信身份与策略决策 决策输入必须来自可信上下文
Domain / Data 强制业务与资源不变量 最靠近资产处再次校验
Runtime / Operations 限制缺陷影响并提供证据 最小权限、隔离、日志、告警、回滚

8.6 安全验证矩阵：如何证明“真的修好了”

# 验证动作 期望证据
1 覆盖登录前后会话状态转换与旧令牌失效 形成可重复、可审计的证据
2 验证过期、撤销、重放、登出、密码修改后的令牌行为 形成可重复、可审计的证据
3 OAuth 流程校验 issuer/audience/state/PKCE/redirect URI 等安全不变量 形成可重复、可审计的证据
4 敏感操作验证 step-up/reauthentication 与审计事件 形成可重复、可审计的证据

进一步建议把验证拆成四个层次：

  • Unit：证明单个 policy/validator/serializer 在边界输入下行为正确。
  • Integration：证明框架、代理、数据库、浏览器等真实组合仍保持同一安全语义。
  • Negative Regression：为曾经的失败条件建立永久回归测试。
  • Runtime Evidence：日志、指标和告警能看到拒绝、异常、策略漂移与重复攻击趋势。

8.7 专业补充：容易被忽略的工程细节

  • 浏览器 Cookie 策略必须和会话威胁模型一起设计，而不是把单个属性当作万能开关。
  • 特别注意 Domain/Path、站点边界、第三方上下文、子域信任与会话过期的组合效应。
  • JWT 是令牌格式，不自动提供撤销、保密性或正确授权语义。
  • 验证时需要固定允许算法，并校验 issuer、audience、时间声明、token type 与 key selection。

8.8 设计权衡：Senior/Staff 面试应该说什么

安全性、用户体验、跨设备登录和会话连续性之间存在直接张力，应由风险分级决定。

成熟回答应避免“安全永远越严格越好”的绝对化表述，而要讨论：

  • 控制的安全收益；
  • 对兼容性、性能、开发效率和运维复杂度的影响；
  • 是否存在更容易证明正确的设计；
  • 控制失败时是否有第二道边界；
  • 是否能通过平台能力把正确做法变成默认路径。

8.9 防御性案例推演

假设一个生产系统已经部署了针对本题的修复，不应只问“正常请求是否成功”。评审应同时构造：

正常主体 + 正常资源/状态     → 允许
正常主体 + 非本人资源/非法状态 → 拒绝
异常/缺失安全上下文           → 拒绝或进入安全降级
依赖超时/解析失败              → 不得 fail-open
并发/重试/重复消息             → 不得破坏业务不变量
旧客户端/旧 API 版本           → 不得绕过新控制

这套推演能把“漏洞修复”升级为“系统安全属性验证”。

8.10 面试回答分层

30 秒版：给出根因 + 一条最重要安全不变量。

2 分钟版：补充信任边界、错误防御、正确控制层级和一个验证方法。

5 分钟高级版：再加入架构权衡、异常路径、回归证据、可观测性和与相邻漏洞的边界。

面试官真正区分候选人的地方，通常不是能否说出漏洞定义，而是能否回答：

“你如何证明这个系统在真实架构、异常状态和未来代码变更下仍然保持安全？”
