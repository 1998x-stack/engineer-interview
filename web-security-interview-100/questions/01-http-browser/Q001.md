# Q001 HTTP 是无状态协议，为什么 Web 应用还能维持登录状态？

> **母版一句话结论（PDF）**  
> 会话状态不是由 HTTP 自动保存，而是由应用通过 Cookie/Token 与服务端状态或自包含令牌建立关联。安全重点是会话标识的生命周期、随机性、绑定、过期与授权检查。

## PDF 母版题解

### 1. 面试官在考什么

不是只考定义。 这道题通常同时观察你是否能：①识别安全边界；②解释根因；③知道常见错误做法为什么失效；④给出可落地、可验证的工程控制。

### 2. 原理与机制

会话状态不是由 HTTP 自动保存，而是由应用通过 Cookie/Token 与服务端状态或自包含令牌建立关联。安全重点是会话标识的生命周期、随机性、绑定、过期与授权检查。基础概念题的高分答案不是背定义，而是说明安全边界、浏览器/服务器各自负责什么，以及该概念不能解决什么问题。基础概念题的高分答案不是背定义，而是说明安全边界、浏览器/服务器各自负责什么，以及该概念不能解决什么问题。

**抽象模型 Security = explicit trust boundary + correct parser semantics + server-side enforcement**

### 3. 工程防御与设计原则

-  明确客户端/服务端职责和信任边界

-  对输入先解析规范化，再基于结构做策略判断

-  用安全默认值并记录关键安全状态变化

-  把控制写成可测试安全不变量，并为失败路径、边界条件和回归场景补充自动化测试。

### 4. 常见错误答案 / Gotchas

-  误区：把浏览器策略当成服务端授权

-  误区：只背定义，不说明边界与不能解决的问题

-  误区：忽略代理/CDN/第三方组件对语义的改变

### 5. 面试追问

-  这个机制解决不了什么？

-  如果前面还有 CDN/反向代理，安全结论会改变吗？

-  你会如何把该概念转成自动化测试？

### 6. 一分钟回答模板

先给结论：会话状态不是由 HTTP 自动保存，而是由应用通过 Cookie/Token 与服务端状态或自包含令牌建立关联。安全重点是会话标识的生命周期、随机性、绑定、过期与授权检查。 然后我会从安全边界解释机制：基础概念题的高分答案不是背定义，而是说明安全边界、浏览器/服务器各自负责什么，以及该概念不能解决什么问题。 工程上不会只做单点补丁，而会落实为服务端/平台层控制、最小权限、异常路径和回归测试；最后再说明这个机制不能解决什么，以及如何通过日志、测试或代码审计验证控制确实生效。

### 7. 复习检查

-  □ 我能否用自己的话解释“根因”而不是背定义？

-  □ 我能否给出至少一个错误防御，并解释为什么错误？

-  □ 我能否把修复方案转成可验证的测试或代码审计检查点？

## GitHub 增强版：深度展开

HTTP 的“无状态”指协议层不会自动记住上一次请求的业务身份；应用可以在协议之上建立状态关联。最常见的两种实现是服务端 Session（客户端只持有随机会话标识）与自包含 Token（客户端持有带声明和完整性保护的令牌）。

安全性不取决于“是否用了 JWT”，而取决于会话生命周期：创建、认证后轮换、空闲/绝对超时、吊销、登出、并发会话控制以及权限变化后的失效策略。

会话标识应被视为临时凭据。它一旦泄露，在有效期内往往具有与密码接近的业务价值，因此需要传输保护、最小作用域、异常登录检测和审计。

### 安全不变量（Security Invariants）

- **认证状态必须可过期、可吊销、可审计。**
- **每个敏感请求都必须重新做授权判断；会话只证明身份上下文，不证明操作权限。**

### 代码审计 / 设计评审 / 测试视角

- 定位 Session/Token 创建逻辑，检查随机性、长度、签发者和存储位置。
- 检查登录成功后是否生成新会话标识，注销/改密/禁用账户后旧会话是否失效。
- 检查所有敏感接口是否基于当前主体重新执行授权，而不是仅凭“有会话”放行。

### 安全设计示例（防御性）

```text
Request -> read session/token -> resolve principal -> authorize action -> execute
                         |-> expired/revoked? reject
```

### 新增 Gotchas

- 把“无状态 API”理解成“不需要会话安全设计”。
- 把长期有效的 Bearer Token 当普通配置值保存。

### 新增高阶追问

- 服务端 Session 与自包含 JWT 在吊销、扩展性和一致性上的 trade-off 是什么？
- 权限发生变化时，如何让已有会话及时反映新权限？


## 专业增强版 V2：从面试答案到 AppSec 工程

> 本节是在 PDF 母版和前述 GitHub 增强版基础上的第二轮扩展。重点不再是“记住漏洞名”，而是训练 **Threat Modeling → Secure Design → Code Review → Verification → Operations** 的完整闭环。

### 8.1 威胁建模：先定义资产、主体与边界

本题应放在 **浏览器安全模型、HTTP 状态传递、Origin/Site 边界与传输层边界** 中理解。与本题直接相关的核心资产包括：**会话身份、跨源数据、请求语义、敏感响应与信任上下文**。

推荐用下面的最小威胁模型回答：

```text
Untrusted / Lower-trust Actor
        │
        │ input / identity / state transition
        ▼
Trust Boundary / Parser / Policy / Capability
        │
        │ security decision
        ▼
Protected Asset / Sensitive Action / Privileged Capability
```

典型失败模式是：**把浏览器行为、服务器信任和网络传输混为一谈，导致控制放错层级**。因此真正需要保护的不是某个字符串或某个 UI 控件，而是“跨边界之后系统仍然满足哪些安全属性”。

### 8.2 关键安全不变量：把最佳实践变成可测试规则

- **Invariant 1**：认证状态必须可过期、可吊销、可审计。
- **Invariant 2**：每个敏感请求都必须重新做授权判断；会话只证明身份上下文，不证明操作权限。

高级面试回答要进一步说明：**安全不变量应在最靠近关键资源/危险能力的位置再次成立**。网关、WAF、前端或 SDK 可以提供前置保护，但不能成为唯一的最终安全边界。

### 8.3 失败链（Failure Chain）分析

```text
入口数据/身份/状态
    ↓
规范化、解析或对象绑定
    ↓
安全检查缺失 / 检查位置错误 / 检查与执行语义不一致
    ↓
敏感资源、解释器、内部能力或业务状态被访问
    ↓
机密性 / 完整性 / 可用性 / 租户隔离 / 业务不变量受损
```

分析时建议逐项回答：

1. **Source 是什么**：HTTP 参数、Cookie、Header、JWT claim、数据库旧值、消息、第三方 API，还是管理员配置？
2. **中间发生了什么 Transform**：decode、normalize、deserialize、ORM binding、proxy rewrite、cache keying、模板渲染？
3. **谁做安全决策**：浏览器、CDN、WAF、网关、Controller、Service、Policy Engine、数据库？
4. **真正的 Sink/Asset 在哪**：数据对象、系统能力、内部网络、文件系统、敏感业务动作还是跨租户资源？
5. **Decision 与 Execution 是否使用相同语义**：这是很多高阶漏洞的共同根因。

### 8.4 代码审计：从关键词搜索升级为数据流与控制流审计

与本题相关的重点概念：`http-无状态性`、`session`、`cookie`、`token`、`会话生命周期`。审计时不要只搜漏洞名称，而应建立下列视图：

```text
Entry Point
  ├─ Authentication Context
  ├─ Authorization / Validation
  ├─ Normalization / Parsing
  ├─ Business State
  └─ Sensitive Sink / Capability
```

建议审计步骤：

- **先找入口与调用图**：HTTP handler、GraphQL resolver、WebSocket message handler、后台任务、Webhook、CLI/管理接口。
- **再找安全上下文的来源**：当前用户、tenant、role、scopes、session、trusted proxy、配置环境。
- **检查控制是否集中且一致**：是否存在“某些路由有 middleware、另一些内部入口没有”的分叉。
- **检查 TOCTOU/异步边界**：安全检查与真正执行之间是否跨事务、队列或服务。
- **检查失败路径**：超时、依赖不可用、解析失败、空值、部分成功时是否 fail secure。

### 8.5 架构设计：控制应该放在哪里

本章推荐的总体设计原则是：**浏览器策略负责限制客户端能力；服务端仍必须独立完成身份、授权和输入语义验证**。

可以把控制拆成四层：

| 层级 | 目标 | 本题评审重点 |
|---|---|---|
| Edge / Browser | 降低明显恶意或错误流量 | 不能把它当最终授权/业务安全边界 |
| Application / Policy | 建立可信身份与策略决策 | 决策输入必须来自可信上下文 |
| Domain / Data | 强制业务与资源不变量 | 最靠近资产处再次校验 |
| Runtime / Operations | 限制缺陷影响并提供证据 | 最小权限、隔离、日志、告警、回滚 |

### 8.6 安全验证矩阵：如何证明“真的修好了”

| # | 验证动作 | 期望证据 |
|---:|---|---|
| 1 | 浏览器/开发者工具验证 Cookie、Origin、重定向与请求携带行为 | 形成可重复、可审计的证据 |
| 2 | 服务端集成测试验证认证与授权不依赖前端状态 | 形成可重复、可审计的证据 |
| 3 | 反向代理/网关测试验证 Host、Scheme、Forwarded 等上下文一致 | 形成可重复、可审计的证据 |
| 4 | 日志中保留 request-id、主体、来源与策略决策结果 | 形成可重复、可审计的证据 |

进一步建议把验证拆成四个层次：

- **Unit**：证明单个 policy/validator/serializer 在边界输入下行为正确。
- **Integration**：证明框架、代理、数据库、浏览器等真实组合仍保持同一安全语义。
- **Negative Regression**：为曾经的失败条件建立永久回归测试。
- **Runtime Evidence**：日志、指标和告警能看到拒绝、异常、策略漂移与重复攻击趋势。

### 8.7 专业补充：容易被忽略的工程细节

- HTTP 无状态描述的是协议请求之间没有天然会话关联；应用层会话是通过客户端携带的关联标识和服务端/令牌状态重新建立连续身份。
- 专业回答要区分 server-side session、stateless token 与 distributed session store：三者改变状态存放位置，但都需要安全生命周期与撤销策略。

### 8.8 设计权衡：Senior/Staff 面试应该说什么

兼容性、跨域体验、单点登录与严格浏览器策略之间需要显式权衡。

成熟回答应避免“安全永远越严格越好”的绝对化表述，而要讨论：

- 控制的**安全收益**；
- 对兼容性、性能、开发效率和运维复杂度的影响；
- 是否存在更容易证明正确的设计；
- 控制失败时是否有第二道边界；
- 是否能通过平台能力把正确做法变成默认路径。

### 8.9 防御性案例推演

假设一个生产系统已经部署了针对本题的修复，不应只问“正常请求是否成功”。评审应同时构造：

```text
正常主体 + 正常资源/状态     → 允许
正常主体 + 非本人资源/非法状态 → 拒绝
异常/缺失安全上下文           → 拒绝或进入安全降级
依赖超时/解析失败              → 不得 fail-open
并发/重试/重复消息             → 不得破坏业务不变量
旧客户端/旧 API 版本           → 不得绕过新控制
```

这套推演能把“漏洞修复”升级为“系统安全属性验证”。

### 8.10 面试回答分层

**30 秒版**：给出根因 + 一条最重要安全不变量。

**2 分钟版**：补充信任边界、错误防御、正确控制层级和一个验证方法。

**5 分钟高级版**：再加入架构权衡、异常路径、回归证据、可观测性和与相邻漏洞的边界。

面试官真正区分候选人的地方，通常不是能否说出漏洞定义，而是能否回答：

> **“你如何证明这个系统在真实架构、异常状态和未来代码变更下仍然保持安全？”**
