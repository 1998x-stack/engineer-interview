### 3. 工程防御与设计原则

-  首选结构化/参数化 API

-  对无法参数化的结构位置使用严格映射 allowlist

-  最小化解释器权限

-  用 SAST/代码审计验证危险 sink

-  把控制写成可测试安全不变量，并为失败路径、边界条件和回归场景补充自动化测试。

-  误区：只检查 HTTP 输入，忽略数据库/队列/第三方 API 的二阶数据

## GitHub 增强版：深度展开

CRLF/响应拆分的根因是用户数据进入 HTTP 头部或协议结构，导致解释器把数据当作新的 header/message 边界。

这说明“输出编码必须匹配输出上下文”：HTML escape 对 HTTP header context 没有直接保护。

现代框架通常会拒绝非法 header 字符，但仍应使用结构化 header API、避免自行拼接原始响应。

### 安全不变量（Security Invariants）

- **不可信输入不得改变 HTTP 消息结构。**
- **协议层字段必须通过结构化 API 生成。**

### 代码审计 / 设计评审 / 测试视角

- 搜索动态 Location、Content-Disposition、Set-Cookie、日志转发等 header 构造。
- 确认框架 API 会验证 header value，禁止原始响应拼接。
- 检查代理/CDN 对重复/异常 header 的处理差异。

### 新增 Gotchas

- 对 header 值做 HTML encode。
- 假设上游代理一定会清洗异常换行。

### 新增高阶追问

- CRLF Injection 与 Request Smuggling 的共同点是什么？
- Content-Disposition 文件名应如何安全处理？


## 专业增强版 V2：从面试答案到 AppSec 工程

> 本节是在 PDF 母版和前述 GitHub 增强版基础上的第二轮扩展。重点不再是“记住漏洞名”，而是训练 **Threat Modeling → Secure Design → Code Review → Verification → Operations** 的完整闭环。

### 8.1 威胁建模：先定义资产、主体与边界

本题应放在 **Source → Transform → Interpreter/Sink 的代码与数据边界** 中理解。与本题直接相关的核心资产包括：**数据库查询语义、系统命令、模板执行上下文、解析器能力与响应结构**。

推荐用下面的最小威胁模型回答：

```text
Untrusted / Lower-trust Actor
        │
        │ input / identity / state transition
        ▼
Trust Boundary / Parser / Policy / Capability
        │
        │ security decision
        ▼
Protected Asset / Sensitive Action / Privileged Capability
```

典型失败模式是：**不可信数据参与语法树、查询对象、命令行、模板或协议结构的构造**。因此真正需要保护的不是某个字符串或某个 UI 控件，而是“跨边界之后系统仍然满足哪些安全属性”。

### 8.2 关键安全不变量：把最佳实践变成可测试规则

- **Invariant 1**：不可信输入不得改变 HTTP 消息结构。
- **Invariant 2**：协议层字段必须通过结构化 API 生成。

高级面试回答要进一步说明：**安全不变量应在最靠近关键资源/危险能力的位置再次成立**。网关、WAF、前端或 SDK 可以提供前置保护，但不能成为唯一的最终安全边界。

### 8.3 失败链（Failure Chain）分析

```text
入口数据/身份/状态
    ↓
规范化、解析或对象绑定
    ↓
安全检查缺失 / 检查位置错误 / 检查与执行语义不一致
    ↓
敏感资源、解释器、内部能力或业务状态被访问
    ↓
机密性 / 完整性 / 可用性 / 租户隔离 / 业务不变量受损
```

分析时建议逐项回答：

1. **Source 是什么**：HTTP 参数、Cookie、Header、JWT claim、数据库旧值、消息、第三方 API，还是管理员配置？
2. **中间发生了什么 Transform**：decode、normalize、deserialize、ORM binding、proxy rewrite、cache keying、模板渲染？
3. **谁做安全决策**：浏览器、CDN、WAF、网关、Controller、Service、Policy Engine、数据库？
4. **真正的 Sink/Asset 在哪**：数据对象、系统能力、内部网络、文件系统、敏感业务动作还是跨租户资源？
5. **Decision 与 Execution 是否使用相同语义**：这是很多高阶漏洞的共同根因。

### 8.4 代码审计：从关键词搜索升级为数据流与控制流审计

与本题相关的重点概念：`crlf-injection`、`http-header`、`response-splitting`、`header-injection`、`编码上下文`。审计时不要只搜漏洞名称，而应建立下列视图：

```text
Entry Point
  ├─ Authentication Context
  ├─ Authorization / Validation
  ├─ Normalization / Parsing
  ├─ Business State
  └─ Sensitive Sink / Capability
```

建议审计步骤：

- **先找入口与调用图**：HTTP handler、GraphQL resolver、WebSocket message handler、后台任务、Webhook、CLI/管理接口。
- **再找安全上下文的来源**：当前用户、tenant、role、scopes、session、trusted proxy、配置环境。
- **检查控制是否集中且一致**：是否存在“某些路由有 middleware、另一些内部入口没有”的分叉。
- **检查 TOCTOU/异步边界**：安全检查与真正执行之间是否跨事务、队列或服务。
- **检查失败路径**：超时、依赖不可用、解析失败、空值、部分成功时是否 fail secure。

### 8.5 架构设计：控制应该放在哪里

本章推荐的总体设计原则是：**优先取消解释器；其次使用参数化/结构化 API；结构性动态位置使用严格映射 allowlist**。

可以把控制拆成四层：

| 层级 | 目标 | 本题评审重点 |
|---|---|---|
| Edge / Browser | 降低明显恶意或错误流量 | 不能把它当最终授权/业务安全边界 |
| Application / Policy | 建立可信身份与策略决策 | 决策输入必须来自可信上下文 |
| Domain / Data | 强制业务与资源不变量 | 最靠近资产处再次校验 |
| Runtime / Operations | 限制缺陷影响并提供证据 | 最小权限、隔离、日志、告警、回滚 |

### 8.6 安全验证矩阵：如何证明“真的修好了”

| # | 验证动作 | 期望证据 |
|---:|---|---|
| 1 | SAST/代码审计跟踪 source 到危险 sink | 形成可重复、可审计的证据 |
| 2 | 单元测试验证 query/command/template 结构固定、值单独绑定 | 形成可重复、可审计的证据 |
| 3 | 对动态标识符、排序、字段名、模板选择做 allowlist 测试 | 形成可重复、可审计的证据 |
| 4 | 最小权限验证单点缺陷不能扩大为高权限执行 | 形成可重复、可审计的证据 |

进一步建议把验证拆成四个层次：

- **Unit**：证明单个 policy/validator/serializer 在边界输入下行为正确。
- **Integration**：证明框架、代理、数据库、浏览器等真实组合仍保持同一安全语义。
- **Negative Regression**：为曾经的失败条件建立永久回归测试。
- **Runtime Evidence**：日志、指标和告警能看到拒绝、异常、策略漂移与重复攻击趋势。

### 8.7 专业补充：容易被忽略的工程细节

- 协议分隔符注入说明输出编码必须匹配具体协议上下文。
- 现代框架通常会限制非法头部字符，但仍要审计手工响应构造、代理重写和日志/邮件等其他行协议。

### 8.8 设计权衡：Senior/Staff 面试应该说什么

通用“灵活表达式”能力越强，安全边界越难验证；安全设计通常要牺牲部分动态性。

成熟回答应避免“安全永远越严格越好”的绝对化表述，而要讨论：

- 控制的**安全收益**；
- 对兼容性、性能、开发效率和运维复杂度的影响；
- 是否存在更容易证明正确的设计；
- 控制失败时是否有第二道边界；
- 是否能通过平台能力把正确做法变成默认路径。

### 8.9 防御性案例推演

假设一个生产系统已经部署了针对本题的修复，不应只问“正常请求是否成功”。评审应同时构造：

```text
正常主体 + 正常资源/状态     → 允许
正常主体 + 非本人资源/非法状态 → 拒绝
异常/缺失安全上下文           → 拒绝或进入安全降级
依赖超时/解析失败              → 不得 fail-open
并发/重试/重复消息             → 不得破坏业务不变量
旧客户端/旧 API 版本           → 不得绕过新控制
```

这套推演能把“漏洞修复”升级为“系统安全属性验证”。

### 8.10 面试回答分层

**30 秒版**：给出根因 + 一条最重要安全不变量。

**2 分钟版**：补充信任边界、错误防御、正确控制层级和一个验证方法。

**5 分钟高级版**：再加入架构权衡、异常路径、回归证据、可观测性和与相邻漏洞的边界。

面试官真正区分候选人的地方，通常不是能否说出漏洞定义，而是能否回答：

> **“你如何证明这个系统在真实架构、异常状态和未来代码变更下仍然保持安全？”**
