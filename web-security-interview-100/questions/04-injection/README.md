# Injection 家族

用“数据进入解释器”统一理解 SQL/NoSQL/Command/SSTI/XXE/LDAP/XPath/CRLF 与二阶注入。

## 本章目标

- 能给出定义，更能解释根因、信任边界与失败模式。
- 能把防御方案写成可验证的安全不变量。
- 能从代码审计、设计评审和测试三个视角验证控制。

## 专业学习框架

### 1. 本章统一抽象

- **分析镜头**：Source → Transform → Interpreter/Sink 的代码与数据边界
- **核心资产**：数据库查询语义、系统命令、模板执行上下文、解析器能力与响应结构
- **典型失败模式**：不可信数据参与语法树、查询对象、命令行、模板或协议结构的构造
- **推荐架构原则**：优先取消解释器；其次使用参数化/结构化 API；结构性动态位置使用严格映射 allowlist

### 2. 学习顺序

1. 先掌握本章所有题目的一句话结论。
2. 再尝试不用漏洞名，仅用“资产—信任边界—安全不变量”解释问题。
3. 第三遍从代码审计视角定位入口、策略点与 sink。
4. 第四遍为每题写至少一个 negative regression test。
5. 最后练习 30 秒、2 分钟、5 分钟三档面试回答。

### 3. 本章验证基线

- SAST/代码审计跟踪 source 到危险 sink
- 单元测试验证 query/command/template 结构固定、值单独绑定
- 对动态标识符、排序、字段名、模板选择做 allowlist 测试
- 最小权限验证单点缺陷不能扩大为高权限执行

### 4. Senior / Staff 级讨论点

通用“灵活表达式”能力越强，安全边界越难验证；安全设计通常要牺牲部分动态性。

高级候选人应能说明：控制为什么放在当前层、其它层还能提供什么纵深防御、异常路径如何处理、控制如何被持续验证，以及当架构演进时如何避免策略漂移。
